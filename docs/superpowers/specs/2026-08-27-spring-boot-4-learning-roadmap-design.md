# Spring Boot 4 학습 로드맵

작성일: 2026-08-27
상태: active — 다음 체크포인트에서 개정한다

---

## 0. 이 문서가 있는 이유

세션 대화는 사라진다. 메모리에는 **핵심 결정만** 남겼고, 주차별 계획·체크포인트·기각안의 근거는 들어 있지 않다. 이 문서가 그것을 담는다.

이 문서는 **학습 계획**이지 CosmoRoute의 명세가 아니다. 그래서 CosmoRoute의 `docs/`가 아니라 여기에 둔다 — 그쪽 `docs/README.md`는 *"여기에 없는 문서는 active specification이 아니다"*라고 선언해 두었고, 학습 로드맵을 거기 넣으면 그 규율이 흐려진다.

---

## 1. 목표와 제약

### 1.1 목표

Angular/NestJS 기반의 개발 경험을 가진 상태에서, **취업 선택지를 넓히기 위해 Java/Spring으로 전환**한다.

최종 목표는 둘 중 하나다.

- **경력 전환 백엔드/풀스택** — 서비스를 배포까지 해본 경험을 살려 Java/Spring 팀으로
- **AI 백엔드 / LLM 엔지니어** — Spring + AI 결합 포지션

그 전에 **통과해야 할 게이트**가 있다: JPA 영속성 컨텍스트, N+1, `@Transactional` 전파, 스프링 빈 생명주기 같은 백엔드 면접 단골을 설명할 수 있는 수준.

> **게이트는 지원할 포지션이 아니다.** 콘티온을 배포까지 해본 경력을 신입으로 포지셔닝하면 손해다. 경력 전환·AI 백엔드 면접에서도 같은 주제를 **더 깊게** 묻는다. 즉 게이트의 *내용*은 필수지만 *라벨*은 붙이지 않는다.

### 1.2 시간 제약

| 시간대 | 용도 |
|---|---|
| 아침 ~ 오후 6시 | Spring (주력) |
| 저녁 | 콘티온 |

즉 Spring이 주 35~40시간의 **주력**이고, 콘티온이 보조다.

### 1.3 콘티온 병행 규칙

콘티온은 MVP 배포가 끝났고 사용자가 아직 많지 않다.

- **개인약관 작업까지만** 진행해 법적 리스크를 닫고 유지보수 모드로 둔다.
- **스케줄·채팅은 보류한다.** 둘 다 무겁다 — 스케줄은 반복 규칙·타임존·일정 충돌 판정, 채팅은 실시간 연결·메시지 순서 보장·읽음 처리·재연결 누락 복구. 낮에 새 스택을, 저녁에 익숙한 스택의 어려운 신규 도메인을 동시에 하면 둘 다 놓친다.
- **저녁에는 구현하지 않는다.** 코드베이스 복습 + 요구사항·도메인 모델 초안까지만.
- **저녁 산출물을 "확정된 설계"로 끊지 않는다.** "요구사항 + 도메인 모델 초안 + 미결정 목록"까지다. 반복 규칙 저장 전략이나 메시지 순서 보장 방식은 Spring에서 트랜잭션 경계·이벤트 설계를 만난 뒤 결정해야 더 나은 답이 나온다.

## 2. 채택안과 기각안

### 2.1 채택 — C안: 재정렬 이중 트랙 + JPA 보강 트랙

책 챕터를 **CosmoRoute 슬라이스가 요구하는 순서로 재배열**하고, 책이 다루지 않는 JPA 내부는 별도 트랙으로 보강한다.

### 2.2 기각 — A안: 책 완주 우선

Ch2 → Ch15를 순서대로 끝내고 그다음 구현에 집중.

- **기각 사유**: 지금 필요 없는 챕터(Ch8 Native, Ch9·10 Reactive)까지 정가로 정리하고, JPA 보강이 들어갈 자리가 없다. 무엇보다 **책 순서가 필요 순서와 다르다.**

### 2.3 기각 — B안: 슬라이스 주도 발췌

슬라이스가 요구하는 절만 골라 읽는다.

- **기각 사유**: "내가 안 만난 주제"를 모르게 된다. 면접에서 뚫리는 지점이 정확히 그것이다. chapter 단위 coverage 검증 체계도 무너진다.

## 3. 계획을 바꾼 발견 세 가지

### 3.1 이 책만으로는 게이트를 못 넘는다

*Learning Spring Boot 4* Ch3 "Querying for Data"는 **책 26쪽 · 6절**이다.

```
01 Spring Data 추가          04 커스텀 파인더 · 정렬 · limit
02 DTO · Entity · POJO       05 Query by Example
03 리포지토리 · 선언적 쿼리    06 커스텀 JPA 쿼리
```

여기 **없는 것**: 영속성 컨텍스트 · 1차 캐시 · 쓰기 지연 · 더티 체킹 / 연관관계 매핑과 연관관계 주인 / 프록시 · 지연 로딩 · N+1 · fetch join · `@EntityGraph` / `@Transactional` 전파 · 격리 · 락 / OSIV.

즉 **한국 백엔드 면접 단골 JPA 주제가 통째로 빠져 있다.** Ch15의 data layer 절도 Boot 4 변경점이지 기본기가 아니다.

→ **`part-0-jpa-foundations` 보조 트랙**을 만든 근거.

### 3.2 Ch15는 마지막에 읽으면 손해다

Ch15의 9개 절이 영역별로 1:1 대응한다(Core / Web·API / Data / Security / Testing / Messaging / Observability / Native / Migration).

해당 영역 챕터를 끝낸 직후 짝 절을 읽는 편이 낫다. 나중에 몰아 읽으면 "무엇이 바뀌었는지"는 알아도 "왜 그렇게 바뀌었는지"가 안 붙는다. CosmoRoute는 **이미 Boot 4.1.0을 쓰고 있어서** 이 지식이 즉시 필요하다.

**단, 생성과 읽기를 분리한다.**

```
생성  →  챕터 단위 통째로   (coverage 규율 유지)
읽기  →  절 단위 짝짓기     (Ch3 읽고 → 15-03만)
```

### 3.3 정리는 병목이 아니다 ← 계획의 절반을 바꾼 발견

파일 타임스탬프 실측:

```
Ch1 상세 재작성   16:41 → 17:02   약 21분    8노트 · 2,533줄
Ch2 상세 재작성   17:31 → 18:22   약 51분   15노트 · 5,175줄 + 이미지 10개
```

원래 계획은 "Ch2 8노트에 5일"을 기준선으로 잡고 그 배율로 전체 일정을 조정할 생각이었다. **틀렸다.** 노트 생산은 에이전트가 하므로 챕터당 1시간 미만이다.

그러면 진짜 병목은 이렇게 이동한다.

| 활동 | 주체 | 비용 |
|---|---|---|
| 정리 | 에이전트 | 챕터당 20~50분 — **병목 아님** |
| 읽기 | 사용자 | 챕터당 2,500~5,200줄 |
| 인출 | 사용자 | deep-tutor 인출 연습 |
| 구현 | 사용자 | CosmoRoute 슬라이스 |

CLAUDE.md가 이미 이 구분을 갖고 있다 — *"`prepared`는 원문 대조와 노트 작성까지 끝난 상태이며, **사용자의 실제 인출 성공을 뜻하지 않는다.**"*

**함의**: 15챕터를 다 정리해도 며칠이면 끝나고, 그러면 **읽지 않은 노트 수만 줄이 쌓인다.** 산출물의 생산 비용이 0에 가까워지면 파일 수가 "진도"로 읽히는 착시가 생기는데, 학습에서 그 지표는 아무것도 측정하지 않는다.

→ **생성 속도를 읽기 속도에 묶는 규율**이 필요하다(§5.3).

## 5. 개정된 트랙 구조

### 5.1 하루 리듬

```
오전 3~4h   읽기 · 인출   그날의 대상은 '책 챕터' 또는 'JPA 보강' 중 하나 (섞지 않음)
오후 4~5h   구현          CosmoRoute — 오전에 읽은 것을 그날 안에 씀
저녁 2~3h   콘티온        코드 복습 + 요구사항·도메인 모델 초안 (구현 아님)
```

**금요일 오후는 구현 대신 회고**에 쓴다. `_global/session-log.md` 갱신, 측정치 기록(쿼리 수·응답시간 before/after), 다음 주 범위 확정.

측정치는 나중에 몰아서 만들 수 없는 유일한 재료다 — 그날 재야 남는다.

### 5.2 오전 트랙의 정체가 바뀌었다

§3.3의 발견 때문에 오전은 **"노트 쓰기"가 아니라 "읽기 + 인출"**이다.

```
읽기    노트를 읽는다
인출    deep-tutor 인출 연습 — 노트를 덮고 자기 말로 설명한다
기록    막힌 지점을 _global/gaps.md 와 노트의 "막혔던 지점"에 남긴다
```

노트의 `<!-- ==== 아래는 내 영역 ==== -->` 아래 세 섹션(`내 설명 시도` · `막혔던 지점` · `리뷰 이력`)이 이 단계에서 채워진다. **에이전트는 거기에 자기 설명을 쓰지 않는다.**

### 5.3 읽기 부채 규율

정리 세션이 9챕터를 다 만들면 수만 줄이 쌓인다. 규율 하나를 건다.

> **정리는 읽기보다 1~2챕터 앞을 유지한다.** 다 만들어 두지 않는다.

다 만들지 않는 이유는 두 가지다. 읽지 않은 노트가 부채가 되는 것이 하나고, **구현에서 나온 발견이 이후 챕터 노트의 강조점을 바꿀 수 있다는 것**이 다른 하나다. 실제로 Ch2 작업에서 sequenceDiagram 렌더 버그처럼 하면서 발견한 것이 반영됐다.

### 5.4 오후 트랙의 상태 — 열렸다 (2026-08-27 개정)

> **원래 적었던 것**: *"CosmoRoute의 기획 중 멈춘 부분이 있어 재확립이 필요하다. 그래서 오후 트랙의 첫 작업은 슬라이스 구현이 아니라 기획 재확립이다. 이것이 끝나기 전에는 `slice/material-substance-mapping` spec을 쓰지 않는다."*
>
> 그 기획 재확립이 같은 날 끝났다. 그리고 그 결과 **첫 슬라이스가 바뀌었다.** 아래가 개정된 내용이다.

CosmoRoute 저장소 담당 세션이 `slice/planning-reset` 브랜치(커밋 `a7df780`·`a9820bb`)로 기획을 재확립했다. 문서 6개가 바뀌었다 — `docs/adr/0010-...md`(신규, proposed), `docs/product/requirements.md`, `docs/slices/discovery-screens-1/spec.md`, `docs/domain/boundary-catalog.md`, `docs/domain/invariants.md`, `docs/README.md`.

#### 첫 슬라이스가 바뀐 이유

`slice/material-substance-mapping`을 지금 시작하면 **관통이 불가능하다.** `api.substance` 테이블이 비어 있고 채울 경로가 아예 없기 때문이다.

```text
MFDS · CosIng ──① 실 HTTP ──▶ ingestion.substance ──② 투영 ──▶ api.substance ──▶ material_substance
                  경로 없음      Identify·Merge 있음    경로 없음      (원래 잡았던 첫 슬라이스)
```

**이 세션이 읽기 전용으로 직접 확인한 사실**이다.

| 확인 | 결과 |
|---|---|
| `RestClient`·`WebClient`·`RestTemplate`·`HttpExchange`·`@Scheduled` | Java 소스 **0건** |
| `SubstanceStore`가 쓰는 대상 | `JdbcClient`로 **ingestion 자체 스키마**(`V1__canonical_schema.sql`). JPA도 쓰지 않는다 |
| `api.substance`를 채우는 운영 코드 | **없음.** `SchemaInvariantsTest`의 테스트 픽스처 한 곳뿐 |

`api`와 `ingestion`의 `substance`는 **이름만 같은 별개 테이블**이다. `api` 쪽 DDL 주석이 이미 그렇게 적어 두었다 — *"수집 시스템이 소유하고 이 앱은 저작하지 않는다(ADR-0001). 여기 있는 것은 feed로 받은 projection이다."* 그 projection을 만드는 코드가 없었던 것이다.

원래 로드맵은 이 공백을 "실 HTTP 미연결" 하나로 봤는데 실제로는 **둘**이었다. 그래서 담당 세션이 `SUB-005`(api 투영)를 `requirements.md`에 신설했다.

#### 개정된 슬라이스 순서

| Step | 브랜치 | 다루는 것 | 필요한 학습 |
|---|---|---|---|
| **0** ✅ | `slice/specialchem-recheck` · `slice/planning-reset` | 기획 재확립 · ADR-0010 proposed. **2026-08-28 main 머지 완료**(`7e3bc50`·`f81a69f`) | — |
| **1** | `slice/substance-feed-sync` | SUB-001 실 HTTP + SUB-005 api 투영 | Ch2(HTTP service client) · Ch6(설정 외부화) · **part-0 j3**(모듈 간 트랜잭션 경계) · Ch5(WireMock + Testcontainers) |
| **2** | `slice/material-substance-mapping` | DISC-006 — §6.1의 결정 13개를 그대로 소비 | **part-0 j1·j2·j3 전부** · Ch3 |
| **3** | `slice/discovery-screens-1` | 바이어 화면. 여기서 성분이 화면에 나온다 | Ch2(Web/API) |
| **—** | `slice/source-check-requires-person` | ADR-0010 강제 지점. **순서 미정** — 아래 「신설 슬라이스」 참고 | Ch5 · Ch3 |

#### 감수한 대가

`discovery-screens-1`이 뒤로 밀리면서 **바이어 화면이 그만큼 늦어진다.** `apps/web-public` 소스가 0파일이고 바이어 경로는 한 번도 관통된 적이 없다 — `admin-screens-1`은 관통 과정에서 결함 셋을 잡았으므로, 관통이 늦어지는 것은 실제 위험이다.

사용자가 *"급하다고 좋을 건 없다"*로 판단했고, 그 대가는 CosmoRoute 쪽 `discovery-screens-1/spec.md` 머리말에 명시되어 있다.

#### 해소된 질문 — INV-20의 강제 지점은 사라지지 않는다 (2026-08-28)

> **제기했던 것**: 같은 브랜치의 `invariants.md`에 *"INV-20의 ✅는 '부재'로 강제된다 — 스크래퍼를 한 줄 쓰는 순간 사라지는데 이 표의 ✅는 남는다"*는 경고가 추가됐는데, `substance-feed-sync`가 바로 이 저장소의 첫 HTTP fetcher다. 강제 지점이 무너지는가?

**무너지지 않는다.** `invariants.md` §2의 *"(자동 수집 코드 없음)"*이 **강제 메커니즘이 아니라 증상을 적은 것**이었고, 그 서술만 거짓이 된다.

실제로 막고 있는 사슬은 넷이고, **이 세션이 읽기 전용으로 전수 확인했다.**

| 고리 | 확인 결과 |
|---|---|
| ① 큐레이션 쓰기 코드가 전부 `catalog/internal/` 안 | 서로 다른 두 grep의 **합집합 12파일 — 밖에 0건** |
| ② `CuratedCatalogService`가 package-private | `class CuratedCatalogService {` — `public` 없음 |
| ③ `currentUser.require()`로 주체 강제 | 54행·83행. 없으면 `IllegalStateException` |
| ④ `ModuleStructureTest`가 ①을 매 빌드 검증 | Spring Modulith `ApplicationModules.verify()` |
| ⑤ 관리자 쓰기 엔드포인트도 internal 안 | `CuratedCatalogController`가 `catalog/internal/`에 있다 |

**HTTP 클라이언트의 부재에 기대는 고리가 하나도 없다.** fetcher가 몇 개 생기든 ①~⑤는 그대로다.

⑤가 §2의 *"큐레이션 입력 경로가 관리자 HTTP 엔드포인트뿐"*을 실제로 성립시킨다. 컨트롤러가 internal이라 **다른 모듈이 타입을 참조할 수 없고 Spring MVC 라우팅으로만 닿는다** — 이것도 ④의 검증 범위 안이다.

> **파일 수를 적지 않는 이유**: 세는 방식에 따라 8·9·12로 달라진다. CosmoRoute 세션의 `OPERATOR_CURATED|curatedDraft|Company.curated`는 8개, 이 세션의 `curated|Curated`는 9개를 잡았고 **둘 다 불완전했다** — 전자는 리터럴 없이 서비스만 호출하는 4개(`CuratedCatalogController`·`Errors`·`NotFound`·`RuleViolation`)를, 후자는 대문자 상수만 든 3개(`CatalogVisibility`·`CompanyOrigin`·`MaterialOrigin`)를 놓쳤다. **합집합 12개가 전부 `catalog/internal/` 안**이라는 사실만 적는다.

근거가 하나 더 있다. `substance-feed-sync`가 쓰는 `api.substance`에는 **`origin`도 `created_by_user_id`도 없다**(확인함 — `origin_definition` 하나뿐). 순수 투영 테이블이라(ADR-0001) 큐레이션 행을 만들 **수단 자체가 없고**, 만들려 해도 ②④가 접근을 막는다.

> **이름 함정**: `substance.origin_definition`은 **기원**(식물성·광물성)이지 `company.origin`·`material.origin`의 provenance 열거형이 아니다. 이름이 비슷해 헷갈릴 자리다.

#### Step 1의 확정된 범위 (사용자 승인 완료)

```
SUB-001   MFDS 실 HTTP
SUB-005   api.substance 투영
   (a)    invariants.md §2 의 INV-20 서술을 위 4단 사슬로 교체
   (b)    ArchUnit 규칙 1개 — catalog 모듈이 HTTP 클라이언트 타입에 의존하지 않는다
```

**불변식 재작성은 들어가지 않는다.** §1 원문은 그대로이고 바뀌는 것은 §2 매핑표의 "무엇이 이걸 막고 있나" 서술뿐이라, ADR이 필요한 변경이 아니다 — 불변식을 고치는 것이 아니라 **기록을 사실과 맞추는 것**이다.

(b)가 필요한 이유는 ①이 지금은 사실이지만 **아무도 세고 있지 않기** 때문이다. `ModuleStructureTest`의 javadoc이 같은 논리를 이미 적어 두었다 — *"'나뉘어 있다'는 말은 **검증되지 않으면 사실이 아니다.**"* ArchUnit 1.4.2가 spring-modulith 경유로 이미 test 클래스패스에 있어(Gradle 캐시에서 확인) 새 의존성 없이 된다.

(b)의 알려진 대가: 나중에 `primary_source_url` 링크 생존 확인 같은 것이 필요해지면 이 테스트가 빨개진다. **그게 의도다** — 그때 판단을 강제하는 것.

   설정 외부화       HTTP service client     WireMock · Testcontainers
   ────────────────────── 여기서 Step 1 substance-feed-sync 착수 가능
   ↓
Ch3 (4,032줄)
   Spring Data
   ────────────────────── 여기서 Step 2 material-substance-mapping 착수 가능
   ↓

| Ch2 절 | 언제 |
|---|---|
| `02` MVC 컨트롤러 · `04c` 생성자 주입 · `05` JSON API · `08` 버저닝 · `09` **HTTP service client** · `10` JSpecify | **Step 1 전에** |

|---|---|

## 6. `part-0`이 남긴 결정 목록

> **2026-08-27 개정**: 아래 §6.1의 결정 목록은 이제 **Step 2 `slice/material-substance-mapping`**에서 소비된다. 첫 슬라이스가 `slice/substance-feed-sync`로 바뀌었기 때문이다(§5.4). CosmoRoute 담당 세션이 코드로 재검증한 결과 **결정 내용 자체는 전부 유효**하다 — 연결 엔티티 필요, `@Any` 불가(물리 FK 둘 다 존재), `open-in-view` 미설정(= 켜짐), `ddl-auto: validate` 확인.
>
> Step 1이 새로 요구하는 것은 §5.5의 읽는 순서에 반영했다. 실 HTTP 클라이언트·설정 외부화·모듈 간 트랜잭션 경계·WireMock 테스트다.

첫 슬라이스가 시작될 때 그대로 쓸 수 있도록 근거와 함께 남겨 둔다. 상세는 `chapter-j2/_map.md`와 `chapter-j3/_coverage.md`에 있다.

### 6.1 첫 슬라이스에서 정할 것

| 결정할 것 | 결론 | 근거 |
|---|---|---|
| 조인 테이블 매핑 | **연결 엔티티** | `@ManyToMany`는 조인 테이블에 FK 둘만 가정. `material_substance`엔 자체 PK + 배타적 대상 |
| 배타적 대상 표현 | **널 허용 `@ManyToOne` 둘** | `@Any`는 물리 FK를 걸 수 없다(공식 문서 명시). 이 저장소는 불변식을 DB가 강제한다 |
| 원료 쪽 컬렉션 | **둔다** | 생명주기 종속 + 중복 검사를 엔티티 안에서 |
| fetch 전략 | **`LAZY` 명시** | `@ManyToOne` 기본값이 즉시 |
| 전이 설정 | **`PERSIST`·`MERGE` + `orphanRemoval`** | 소프트 삭제라 `REMOVE`는 거의 안 쓰임 |
| 부모 조회 | 대량이면 `getReference`, 검증 필요하면 `findById` | 전자는 SELECT를 아끼고 존재 검증을 못 한다 |
| "둘 중 하나" 강제 지점 | **엔티티** — 정적 팩터리 + private 생성자 | 잘못된 상태를 만들 경로 자체를 없앤다 |
| `default_batch_fetch_size` | **켠다** | 설정 한 줄, 매핑 무수정, 페이징과 호환 |
| `spring.jpa.open-in-view` | **`false` 명시** | 프론트가 분리되어 서버 뷰가 없다. 현재 미설정 = 켜짐 |
| 목록 연관 전략 | 단일 연관은 엔티티 그래프, 컬렉션은 배치 페칭 | 컬렉션 페치 조인은 페이징을 깬다 |
| DTO 변환 위치 | 서비스 트랜잭션 안 | OSIV를 끄면 강제된다 |
| 쿼리 카운트 검증 | 목록 API에 붙인다 | N+1은 기능 테스트를 통과한다 |

### 6.2 미루는 것과 재개 조건

| 항목 | 재개 조건 |
|---|---|
| `@Version` (낙관적 락) | 동시 수정이 **실제로 관측됐을 때.** ADR과 함께 |
| `@DynamicUpdate` | `@Version`이 선행 조건 |
| `Persistable` (여분 SELECT 제거) | 대량 삽입 경로가 생기고 쿼리 수를 측정한 뒤 |
| `fail_on_pagination_over_collection_fetch` | 첫 슬라이스 안정화 후 |
| 2차 캐시 · 커넥션 풀 튜닝 | 측정 없이 조정할 값이 아니다 |

**"지금"과 "미룸"을 가르는 기준은 하나다 — 실제로 관측된 문제가 있는가.** 이 구분 자체가 포트폴리오에서 말할 수 있는 판단 근거가 된다.

육안 확인용 PNG는 `-o x.png -w 1400 -b white`. 한글 라벨은 약 12~13자에서 **단어 중간에 줄바꿈**되므로 stateDiagram 전이 라벨은 짧게 쪼개고(전이를 둘로 나눠도 된다) note 본문도 짧은 줄로 유지한다.

### 8.2 용어 이름에 정규식 메타문자를 쓰면 안 된다

`check-note.sh`의 용어집 대조는 `grep -qE "^## +${용어}( |\(|$)"`다. 용어 이름이 정규식으로 해석된다.

`## N+1-문제`를 정확히 등재하고 `[[N+1-문제]]`를 걸었는데 `FAIL 용어집 미등재`가 났다. `+`가 "앞 문자 1회 이상"으로 해석된 것이다. **에러 메시지가 "미등재"라고 말하지만 실제 원인은 이름의 문자다** — 용어집을 아무리 봐도 원인이 안 보인다.

피할 문자: `+ * ? . [ ] ( ) { } ^ $ | \`
해결: `N+1-문제` → `N-플러스-1-문제`. 제한은 `[[링크]]`와 `## 제목`에만 적용되고, 산문에서는 "N+1"을 그대로 써도 된다.
