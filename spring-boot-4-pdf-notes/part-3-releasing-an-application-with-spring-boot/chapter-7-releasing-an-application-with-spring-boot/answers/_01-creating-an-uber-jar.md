## Q1. 개발하는 곳과 운영하는 곳이 다르다는 사실에서 도출되는 요구

> **IDE에서 서버까지 가는 단계 수를 최소화하는 것.**

**이 사실은 시대와 무관하다** — 1997년의 **CD를 굽고 시내 반대편으로 운반하던 절차**든, 지금의 **전 세계에 흩어진 다섯 명과 AWS**든 마찬가지다. 건물 이쪽 끝의 개발자 자리와 저쪽 끝의 서버실도 같다.

**왜 단계 수가 핵심인가**: 단계마다 **사람이 개입하고, 버전이 어긋나고, 절차가 문서로만 존재**한다. 저자의 1997년 경험이 그 극단이다 — **부서장 서명을 직접 받으러 다니고, 17쪽짜리 절차를 따라 이틀.**

**파생 요구 하나 더**: 옮겨진 것이 **자기가 필요한 것을 전부 갖고 있어야** 한다. 안 그러면 **대상 환경을 미리 맞춰 두는 단계**가 다시 늘어난다 → Q2의 1단계.

## Q2. WAR/EAR 절차의 다섯 단계 중 uber JAR이 없애는 것

**다섯 개 전부다.**

| 단계 | 하는 일 | **uber JAR** |
|---|---|---|
| 1 | 대상 서버에 **애플리케이션 서버 설치** | **내장 서버가 함께 온다** |
| 2 | **WAR 파일 생성** | JAR 하나 |
| 3 | 서드파티 의존성을 조립 파일로 묶어 **EAR 생성** | **의존성이 이미 안에 있다** |
| 4 | **관리 UI에 업로드** | `java -jar` |
| 5 | **서버 재시작** | 프로세스를 띄우면 끝 |

**책의 표현이 신랄하다** — *"레거시 절차… 흉한 조립 파일… 끔찍한 UI".*

> **문제는 단계 수만이 아니다. 애플리케이션이 자기가 필요한 것을 전부 갖고 있지 않다.**

**서버는 밖에 있고, 버전은 운영팀이 정하고, 개발 환경과 다를 수 있다.** 그래서 **"내 컴퓨터에서는 됐는데"**가 구조적으로 발생한다.

**5단계의 부수 피해도 있다** — 서버 재시작은 **그 서버의 다른 앱까지 영향**을 준다. uber JAR은 **프로세스가 곧 애플리케이션**이므로 그 결합이 없다.

## Q3. `clean`과 `package`

| 부분 | **하는 일** | 왜 필요한가 |
|---|---|---|
| `clean` | `target` 폴더와 생성물 삭제 | **이전 빌드의 잔재가 섞이지 않게** 한다 |
| `package` | Maven의 package 단계 실행 | 그 앞의 `validate`·`compile`·`test-compile`·`test`를 **순서대로 부른다** |

**`package` 하나가 테스트까지 도는 이유는 Maven의 생명주기 때문이다.** Maven 단계는 **누적적**이다 — 어떤 단계를 부르면 **그 앞의 모든 단계가 순서대로 실행**된다.

> **그래서 테스트를 통과하지 못하면 아티팩트가 나오지 않는다.**

**이것이 설계적으로 좋은 이유**: **검증되지 않은 것이 배포 가능한 형태로 존재할 수 없다.** [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/02-testing-domain-objects|Ch5]]에서 쌓은 테스트가 여기서 **게이트**가 된다.

**`clean`을 생략하면**: 지운 클래스가 `target`에 남아 **JAR에 섞여 들어갈 수 있다.** 릴리스 아티팩트를 만들 때는 넣는 편이 안전하다.

**실행 환경**: `mvnw`는 **POSIX 셸 스크립트**라 Linux·macOS에서 돌고, **Windows에서는 `./mvnw.cmd`**를 쓴다. Initializr 프로젝트에는 **둘 다** 들어 있다.

## Q4. 일곱 단계 중 4단계가 없으면

**JAR이 실행되지 않는다.**

**4단계 = Spring Boot 로더 코드를 넣는다.**

> **표준 JVM에는 제약이 하나 있다 — JAR 안에 들어 있는 JAR을 클래스패스로 인식하지 못한다.**

```
BOOT-INF/lib/spring-core-7.0.0.jar
        ↑ JVM 은 이것을 "파일 하나"로 본다. 클래스패스가 아니다.
```

**로더가 하는 일**: **새 JAR의 진입점이 되어, 안쪽 JAR들을 읽을 수 있는 클래스로더를 만들고 거기서 애플리케이션을 띄운다.**

**책의 표현**: *"**JAR 파일을 내부에서 읽을 수 있는 접착 코드**로, 실행 가능한 JAR이 되게 해 준다."*

**즉 6단계(의존성을 JAR 그대로 담는다)와 짝을 이룬다** — 풀지 않고 담기로 한 결정(Q6)이 **로더를 필수로 만든다.** 풀어서 섞는 shaded 방식이라면 로더가 필요 없다. **두 결정은 하나의 선택의 양면이다.**

## Q5. 원본을 `.jar.original`로 남기는 이유

**재패키징 전의 원본을 보존해 문제가 생기면 비교할 수 있게 하기 위해서다.**

```
1. 표준 Maven이 만든 JAR 을 가져와 푼다
2. 원본을 .jar.original 로 옆에 남긴다     ← 여기
3. 원래 이름으로 새 JAR 을 만든다
```

**3단계와 함께 읽어야 한다** — **새 JAR이 원래 이름을 가져간다.** 그러면 원본은 이름을 잃는데, 버리는 대신 **접미사를 붙여 남긴다.**

**3단계가 이름을 물려받는 이유**: **이름이 같아야 빌드 스크립트와 배포 절차가 바뀌지 않는다.** 재패키징이 **투명하게** 일어난다.

**`.jar.original`이 쓸모 있는 경우**:
- **재패키징이 뭔가를 망가뜨렸는지** 확인할 때 — 안의 내용을 비교
- **표준 JAR로 배포해야 하는** 경우(라이브러리로 쓸 때)
- **크기 차이**를 보고 무엇이 추가됐는지 확인

> **"지워도 되는 쓰레기"가 아니다.**

## Q6. shaded JAR 방식의 세 문제

| 문제 | **왜 생기나** |
|---|---|
| **비클래스 파일이 엉뚱한 곳에 간다** | **여러 JAR에 같은 경로의 리소스**가 있으면 충돌한다 |
| **서드파티가 예상 밖으로 동작한다** | **자기 JAR 구조를 전제로 만든 라이브러리**가 있다 |
| **라이선스 위반 위험** | **재배포 형태에 조건을 거는 라이선스**가 있다 |

**차이의 근원**:

| | **shaded JAR** | **uber JAR** |
|---|---|---|
| 서드파티 JAR을 | **푼다** | **풀지 않고 그대로 담는다** |
| 결과 | **모든 클래스가 한 덩어리로 섞임** | **JAR 경계가 그대로 유지됨** |
| 필요한 것 | — | **중첩 JAR을 읽는 로더**(Q4) |

**지원 요청에까지 영향을 주는 이유**: **재패키징된 JAR로 버그를 신고하면 라이브러리 관리자가 지원을 거부할 수 있다** — **원래 배포된 형태로 쓰이지 않았기** 때문이다.

**즉 shading은 라이브러리를 "내가 개조한 것"으로 만든다.** 그 개조가 문제의 원인일 수 있으므로, 관리자 입장에서 **재현할 수 없는 신고**가 된다.

**책의 결론**: *"**Spring Boot는 서드파티 JAR이 늘 그렇듯 거기 있는 것처럼 우리 코드가 돌게 해 준다. shading이 필요 없다.**"*

**공정한 인정**: uber JAR은 Spring Boot의 발명이 아니다. **Maven Shade 플러그인이 2007년부터** 있었다. **기여는 방식**이다.

## Q7. "1만 개 복제"가 가능하려면

**아티팩트가 불변이고 자기 완결적이어야 한다.**

```
불변      → 1만 개가 전부 "같은 것"이라고 말할 수 있다
자기 완결 → 각 복제본이 대상 환경에 아무것도 요구하지 않는다
```

**불변이 아니면**: 복제본마다 **다른 설정이 박혀** 있게 되고, **어느 것이 무엇인지** 추적할 수 없다. [[../chapter-6-configuring-an-application-with-spring-boot/04-setting-properties-with-environment-variables|Ch6]]이 "JAR을 열지 마라"고 한 이유가 이 규모에서 증폭된다 — **1만 개를 각각 열 수는 없다.**

**자기 완결이 아니면**: **1만 대에 애플리케이션 서버를 먼저 설치**해야 한다. Q2의 1단계가 1만 번이다.

**그래서 이 절의 세 가지 결과가 서로 맞물린다**:
- **Tomcat 설치 불필요**(내장 Tomcat 11 — Boot 4.x 기본, Jakarta Servlet 6.x 세대)
- **WAR/EAR 절차 불필요**
- **클라우드에 그대로** → *"이 전체를 클라우드에 올리고 **1만 개 복제하라**고 명령할 수 있다"*

**남는 조건 하나**: **그래도 JDK는 필요하다** → Q8, [[02-building-a-docker-container]].

**[[04a-scaling-with-spring-boot]]의 예고이기도 하다** — 불변 아티팩트 하나를 여러 벌 띄우는 것이 **수평 확장의 전제**다.

## Q8. 이동식 주택 비유가 깨지는 지점

**비유**: uber JAR은 **"가구가 다 들어간 이동식 주택"**이다. **부지만 있으면 그대로 산다.**

**깨지는 지점**: **여전히 부지(JDK)가 필요하다는 점을 가볍게 보이게 한다.**

> **실제로 그것이 이 절이 남기는 마지막 질문이고, 컨테이너는 부지까지 함께 싣는 방식이다.**

```
uber JAR:  코드 + 의존성 + 내장 서버   ← 여기까지
남는 것:   JDK, OS, 커널              ← 대상 환경이 제공해야 한다
```

**"부지만 있으면"이 가벼운 조건이 아닌 이유**:
- **JDK 버전이 다르면** 안 뜨거나 다르게 돈다
- **1만 대에 JDK를 깔고 버전을 맞추는 것**이 Q7의 실제 걸림돌
- **"내 컴퓨터에서는 됐는데"**가 이 층에서 재발한다

**즉 uber JAR은 Q2의 다섯 단계를 없앴지만 "런타임을 맞춰 둔다"는 단계는 남겼다.** 그 단계까지 없애는 것이 **컨테이너**이고, [[02-building-a-docker-container]]가 이어받는다.

**비유가 맞는 부분은 남는다** — **안에 필요한 것이 다 들어 있고, 통째로 옮긴다**는 핵심. 깨지는 것은 **"아무 부지나 된다"**는 인상이다.
