## Q1. 이미지를 만들어 실행까지 했는데도 릴리스가 아닌 이유

**그 이미지가 내 기계의 로컬 저장소에만 있기 때문이다.**

```text
docker.io/library/ch7:0.0.1-SNAPSHOT   ← 이름은 그럴듯하지만 로컬 전용
```

**배포 대상 서버가 이 이미지를 가져갈 방법이 없다.**

**파일로 뽑아 복사하면?** — **[[01-creating-an-uber-jar]]이 없앤 "물리적으로 운반하는" 시대로 되돌아간다.** 1997년의 CD와 다를 게 없다.

> **컨테이너 레지스트리가 그 자리를 대신한다.** 이미지를 거기 올려 두면 어느 기계에서든 `docker pull`로 받는다.

**책의 요지**: *"**컨테이너를 만드는 것이 하나라면, 그 컨테이너를 운영에 릴리스하는 것은 결정적이다.**"* (Josh Long: *"Production is the happiest place on Earth!"*)

**즉 이 장의 흐름은 "만든다 → 옮길 수 있게 한다"의 반복이다** — uber JAR이 서버 의존을, 컨테이너가 런타임 의존을 없앴고, **레지스트리가 운반 문제를 없앤다.**

## Q2. `docker tag`가 필요한 이유

**로컬 이미지에 완전히 정규화된 이름을 부여해 원격 레지스트리로 push할 수 있게 하기 위해서다.**

**`docker.io/library/ch7`의 `library`는 Docker Hub의 공식 이미지 전용 네임스페이스다.**

```
docker.io/library/ch7          ← library = 공식 이미지 자리. 여기엔 못 올린다
docker.io/<your_id>/...        ← 내 계정 네임스페이스로 갈아 끼운다
```

**즉 기본 이름이 이미 "남의 자리"를 가리키고 있다.** [[02a-building-the-right-type-of-container]]에서 본 `docker.io/library/` 기본 접두사가 **로컬에서는 편의였지만 발행에서는 장애물**이 된다.

**`docker tag`가 복사하지 않는다는 점도 중요하다** — **같은 이미지에 이름을 하나 더** 붙인다. 디스크를 두 배 쓰지 않는다.

## Q3. 태그의 세 부분

| 부분 | 이 예에서 | **어떤 질문에 답하나** |
|---|---|---|
| **namespace** | `<your_id>` | **누구의 것인가** |
| **name** | `learning-spring-boot-4th-edition-ch7` | **무엇인가** |
| **tag** | `0.0.1-SNAPSHOT` | **어느 버전인가** |

```
<your_id> / learning-spring-boot-4th-edition-ch7 : 0.0.1-SNAPSHOT
    └─┬─┘              └────────┬────────┘            └────┬────┘
   소유자             무엇                              버전
```

**세 축이 필요한 이유**: 공개 레지스트리에는 **전 세계의 이미지가 한 이름 공간에** 있다. `ch7`이라는 이름은 **수천 명이 쓸 수 있으므로** 소유자로 구분해야 하고, 같은 것의 여러 릴리스가 있으므로 버전이 필요하다.

**namespace가 인증과 묶인다** — `docker login`한 계정의 네임스페이스에만 push할 수 있다. **소유권이 이름에 인코딩**돼 있다.

## Q4. 로컬 이름과 다른 이름을 고르는 실질적 이유

> **이 이름이 로컬 이름과 같을 필요가 없다.**

**로컬에서는 `ch7`이라는 짧은 이름이 편하지만, 공개 레지스트리에서는 그것만으로 무엇인지 알 수 없다.**

```
로컬:  ch7                                     ← 내 기계에 몇 개 없으니 충분
공개:  learning-spring-boot-4th-edition-ch7    ← 수백만 개 중에서 식별돼야 한다
```

**책도 "이미지가 공개될 수 있으므로 더 서술적이거나 표준화된 이름을 고를 수 있다"고 덧붙인다.**

**두 이름이 최적화하는 대상이 다르다**:
- **로컬 이름** — **타이핑 편의.** `docker run ch7`
- **원격 이름** — **검색과 식별.** 남이 보고 무엇인지 알아야 한다

**"표준화된"이 함의하는 것**: 조직에서는 **`팀명-서비스명-환경`** 같은 규칙을 정해 둔다. 그러면 레지스트리 목록만 봐도 소속과 용도가 읽힌다.

## Q5. `latest`에 대한 흔한 오해

| **오해** | **사실** |
|---|---|
| `latest`는 Docker가 자동으로 최신을 가리킨다 | **발행자가 직접 옮겨야** 그렇게 된다 |
| `0.0.1-SNAPSHOT`은 고정된 버전이다 | **이것도 옮길 수 있다.** 스냅숏을 갱신할 때마다 같은 태그로 push하는 것이 흔하다 |
| 태그가 같으면 내용도 같다 | **보장되지 않는다** |

> **`latest`는 규칙이 아니라 관례다.**

**첫 번째가 가장 위험하다** — Docker는 `latest`에 **아무 특별 대우도 하지 않는다.** 발행자가 갱신을 잊으면 **`latest`가 1년 전 이미지**를 가리킨 채 남는다.

**두 번째가 실무에서 자주 문다** — CI가 매 커밋마다 `0.0.1-SNAPSHOT`으로 push하면, **어제 받은 것과 오늘 받은 것이 다르다.** 그런데 태그가 같으므로 **캐시된 이미지를 쓰는 노드는 옛 것을 계속 돌린다.**

**책의 경고**: 여러 릴리스를 관리하는 발행자들이 여러 태그를 함께 운영하게 되면서, **어떤 컨테이너의 태그든 채택하기 전에 그 태깅 전략을 확인해야** 한다.

## Q6. 이미지 내용은 불변인데 배포가 재현되지 않는 이유

**이미지 내용 자체는 불변이지만 태그는 가변이기 때문이다.**

```
태그 이름 (latest · 0.0.1-SNAPSHOT)
      │ 가리킨다
      ▼
   다이제스트 A  →  이미지 내용은 불변
      ┊ 나중에 옮겨질 수 있다
      ▼
   다이제스트 B  →  이미지 내용은 불변
```

**태그는 물건에 붙는 라벨이 아니라 물건을 가리키는 포인터다**(Q8).

**그래서 "이 태그로 배포했다"는 진술이 시점 없이는 무의미하다** — 같은 명령이 **다른 결과**를 낸다.

**해법**: **재현 가능한 배포가 필요하면 태그가 아니라 다이제스트(`@sha256:...`)로 고정한다.**

```
image: myapp:1.2.3                    ← 옮겨질 수 있다
image: myapp@sha256:cab14ec…          ← 내용이 곧 이름. 절대 안 바뀐다
```

**[[02a-building-the-right-type-of-container]]의 build-image 로그가 그 예다** — Paketo 이미지들이 **다이제스트와 함께 찍혀** 있다(`paketobuildpacks/builder-noble-java-tiny@sha256:cab14ec…`). **무엇을 썼는지 정확히 남긴 것**이다.

**[[01-creating-an-uber-jar]]의 불변 아티팩트 원칙과의 관계**: 아티팩트는 불변인데 **그것을 가리키는 이름이 가변**이라, **원칙이 이름 층에서 새어 나간다.**

## Q7. `Visibility: Public`이 이 장 뒷부분과 이어지는 지점

**기본이 공개라면 소스에 담긴 것이 전부 공개된다.**

> **설정 파일에 자격 증명이 들어 있으면 그대로 새어 나간다.**

**이것이 [[04-tuning-and-scaling-in-production]]이 설정을 이미지 밖에 두는 이유 중 하나다.**

```
설정을 이미지 안에 굽는다  →  이미지를 공개하면 설정도 공개
설정을 이미지 밖에 둔다    →  이미지는 공개해도 안전, 설정은 배포 시 주입
```

**[[../chapter-6-configuring-an-application-with-spring-boot/02-creating-profile-based-property-files|Ch6]]이 이미 같은 말을 했다** — *"`application-production.properties`를 JAR에 넣으면 그 안에 운영 DB 주소와 자격 증명이 들어간다."* **여기서는 그 JAR이 공개 레지스트리에 올라간다는 점이 추가된다.**

**즉 위험이 한 단계 커진다**:
```
Ch6:  JAR 이 형상 관리·노트북·CI 로그에 남는다
Ch7:  이미지가 인터넷 전체에 공개된다
```

**Note 하나 더**: 스크린샷은 **저자의 저장소**이고, 태깅과 push에는 **자기 Docker Hub ID를 써야** 한다.

## Q8. 택배 송장 비유가 깨지는 지점

**비유**: 태깅은 **"택배 송장에 받는 사람 주소를 적는 것"**이다. **물건은 그대로고 이름표만 붙는다.**

**깨지는 지점**: **주소가 나중에 다른 물건으로 옮겨 갈 수 있다는 성질을 담지 못한다.**

> **태그는 물건에 붙는 라벨이 아니라 물건을 가리키는 포인터라, 같은 이름이 다음 주에는 다른 이미지를 가리킬 수 있다.**

```
송장:  물건에 물리적으로 붙어 있다      → 물건을 따라간다
태그:  레지스트리의 이름 → 다이제스트 매핑 → 매핑을 바꾸면 다른 것을 가리킨다
```

**Q5·Q6가 이 성질의 두 결과다** — `latest`가 옮겨지는 것도, 배포가 재현 안 되는 것도 **포인터이기 때문**이다.

**비유가 맞는 부분은 남는다** — **물건 자체는 그대로**(이미지 내용은 불변), **이름표만 붙인다**(`docker tag`는 복사하지 않는다). 깨지는 것은 **붙는가 가리키는가**의 차이다.

**정확한 비유로 고치면**: 송장보다 **사물함 번호표**에 가깝다. 번호는 그대로인데 **관리자가 안의 물건을 바꿔 넣을 수 있다.** 그래서 "3번 사물함의 것"이 시점에 따라 다르고, 확실히 하려면 **물건의 지문(다이제스트)**을 봐야 한다.
