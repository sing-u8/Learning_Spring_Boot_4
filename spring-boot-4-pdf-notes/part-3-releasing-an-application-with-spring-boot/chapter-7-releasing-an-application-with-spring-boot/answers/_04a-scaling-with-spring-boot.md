## Q1. 한 기계에서 같은 JAR을 두 번 띄우면

**포트가 겹쳐 두 번째가 기동에 실패한다.**

```text
% java -jar target/ch7-0.0.1-SNAPSHOT.jar   # 8080에 뜬다
% java -jar target/ch7-0.0.1-SNAPSHOT.jar   # 8080? 이미 쓰고 있다 → 실패
```

**[[04-tuning-and-scaling-in-production]]의 `SERVER_PORT=9001` 방식으로 풀 수는 있지만 매번 타이핑해야 한다.** 그리고 인스턴스마다 **바꿀 것이 포트 하나로 끝나지 않을 수 있다.**

**더 근본적인 문제가 뒤에 있다** — 포트를 나눠도 **데이터가 나뉜다**(Q6). 포트 충돌은 **즉시 드러나는 문제**이고, 데이터 분리는 **조용한 문제**다.

## Q2. 포트를 9000·9001·9002로 정한 근거

**운영팀이 구성한 로드 밸런서의 설정에 맞춘다.**

> **로드 밸런서가 대상 목록을 갖고 있으므로 인스턴스들이 그 목록의 주소로 떠야 한다.**

```
로드 밸런서 대상 목록:  host:9000, host:9001, host:9002
                              ↓ 그래서
인스턴스들이 그 포트로 떠야 한다
```

**즉 포트 번호는 애플리케이션이 자유롭게 정하는 값이 아니라 인프라와의 계약이다.**

**방향이 중요하다** — 애플리케이션이 포트를 정하고 로드 밸런서가 따라오는 것이 아니라, **인프라가 정한 것에 애플리케이션이 맞춘다.** 그것이 [[04-tuning-and-scaling-in-production]]의 "외부에서 설정을 주입한다"가 필요한 이유다 — **애플리케이션은 자기 포트를 모르는 채로 빌드된다.**

**§6의 단서**: **로드 밸런서 자체는 이 장에서 다루지 않는다.** **포트를 맞춰 두는 것까지가 애플리케이션 쪽의 몫**이다.

## Q3. 프로파일의 일반적 용법과 이 절의 용법

| | **일반적 용법** | **이 절의 용법** |
|---|---|---|
| 나누는 것 | **환경** (dev / test / prod) | **같은 환경 안의 서로 다른 복제본** |
| 예 | `application-test.properties` | `application-instance1.properties` |
| 동시에 뜨나 | **보통 하나만** | **셋이 동시에 돈다** |

> **프로파일이 "상황"을 나누는 일반적 장치라는 것이 드러난다.**

**[[../chapter-6-configuring-an-application-with-spring-boot/02-creating-profile-based-property-files|Ch6]]의 규칙은 그대로다** — **파일 이름의 `-instance1` 부분이 프로파일 이름**이고, 애노테이션도 등록도 필요 없다.

**이 용법이 가능한 이유**: 프로파일 메커니즘은 **"이 이름이 켜지면 이 파일을 더 읽는다"**일 뿐, **그 이름이 무엇을 뜻하는지 전혀 모른다.** 환경 이름으로 쓰든 인스턴스 번호로 쓰든 동작이 같다.

**책의 정리**: *"**프로파일은 단순한 단일 애플리케이션으로 시작한 것을 여러 인스턴스로 돌리는 강력한 방법이다.**"*

## Q4. 세 인스턴스가 "바이트 단위로 같은 코드"라는 사실

**어느 인스턴스에서 버그가 나든 나머지 둘에서도 재현된다.**

```
ch7-0.0.1-SNAPSHOT.jar (불변 아티팩트 하나)
     ├─ SPRING_PROFILES_ACTIVE=instance1 → :9000
     ├─ SPRING_PROFILES_ACTIVE=instance2 → :9001
     └─ SPRING_PROFILES_ACTIVE=instance3 → :9002

▶ 세 번 모두 같은 JAR 파일이다. 달라진 것은 환경 변수 하나뿐이다.
```

**왜 이것이 중요한가**:

| | **같은 아티팩트** | 인스턴스마다 다른 빌드 |
|---|---|---|
| 버그 재현 | **어디서든 재현된다** | **"그 노드에서만 나요"** |
| 롤백 | **하나만 되돌리면 된다** | 무엇을 되돌릴지 정해야 한다 |
| 검증 | **한 번 테스트한 것이 전부** | 조합마다 검증 필요 |
| 진단 | **차이는 설정뿐**이므로 후보가 좁다 | 코드 차이도 후보 |

**마지막 줄이 실무에서 가장 크다** — 장애가 났을 때 **"코드가 다른가?"를 후보에서 지울 수 있다.** [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/02-testing-domain-objects|Ch5]]에서 배운 "원인 후보 줄이기"가 배포 층에서 반복된다.

**[[01-creating-an-uber-jar]]의 "1만 개 복제"가 여기서 세 개로 시연된다.**

## Q5. 프로파일 이름 오타가 조용히 실패하는 이유

**오류가 나지 않고 해당 파일이 그냥 안 읽힌다.**

```
SPRING_PROFILES_ACTIVE=instace1     ← 오타
        ↓
application-instace1.properties 를 찾는다 → 없다 → 그냥 넘어간다
        ↓
server.port 오버라이드가 없다 → 기본값 8080 으로 뜬다
```

**왜 오류가 아닌가**: **프로파일 파일은 있으면 읽고 없으면 안 읽는 선택적 자원**이다. [[../chapter-6-configuring-an-application-with-spring-boot/02-creating-profile-based-property-files|Ch6]]의 "가산적" 성질이 그렇게 설계돼 있다 — **모든 프로파일이 자기 파일을 가질 필요가 없다.**

**그래서 "없다"와 "이름이 틀렸다"를 구별할 방법이 없다.**

**잡는 방법 — 확인 로그를 본다**:
```text
c.l.Chapter7Application : The following 1 profile is active: "instance1"
```

**이 줄이 무엇이 활성화됐는지 바로 알려 준다.** 오타가 있으면 `"instace1"`이라고 찍히므로 **눈으로 확인**할 수 있다.

**증상으로도 알 수 있다** — **포트가 8080이면** 오버라이드가 안 먹은 것이다. 다만 이 진단은 **두 번째 인스턴스를 띄울 때 포트 충돌**로야 드러날 수도 있다.

## Q6. 인메모리 DB로 세 인스턴스를 돌릴 때의 증상

| 사용자 행동 | **결과** |
|---|---|
| **인스턴스 1에 동영상을 등록** | **인스턴스 1의 메모리에만 저장** |
| **새로고침 → 로드 밸런서가 인스턴스 2로 보냄** | **방금 등록한 것이 안 보인다** |
| **다시 새로고침 → 인스턴스 3** | **역시 안 보인다** |
| **인스턴스 1을 재시작** | **데이터가 통째로 사라진다** |

> **사용자 눈에는 데이터가 사라졌다 나타났다 한다.**

**책의 문제 제기**: *"우리는 아직 끝나지 않았다. 이 애플리케이션의 기본 설정이 **인메모리 HSQL 데이터베이스**이기 때문이다. 즉 **세 인스턴스가 공통 데이터베이스를 공유하지 않는다.**"*

**진단이 어려운 이유**: **재현이 불규칙하다.** 로드 밸런서가 어느 인스턴스로 보내느냐에 따라 **보였다 안 보였다** 한다. 개발자가 확인할 때는 **우연히 같은 인스턴스에 붙어** 정상으로 보일 수 있다.

**증상의 종류가 [[04-tuning-and-scaling-in-production]]의 포트 문제와 다르다** — 포트 충돌은 **기동 시점에 시끄럽게** 실패하고, 데이터 분리는 **런타임에 조용히** 잘못된 결과를 낸다.

## Q7. 수평 확장이 성립하기 위한 두 조건

**① 불변 아티팩트** — 모든 인스턴스가 **바이트 단위로 같은 코드**여야 한다(Q4). 그래야 "어느 인스턴스든 같다"고 말할 수 있다.

**② 무상태 인스턴스** — **자기 안에 지속 상태를 두지 않아야** 한다.

> **인스턴스가 상태를 갖고 있으면 "어느 인스턴스가 받아도 같은 결과"가 성립하지 않는다.**

```
①만 있으면:  코드는 같은데 데이터가 다르다 → Q6 의 증상
②만 있으면:  데이터는 같은데 코드가 다르다 → 노드별로 다른 동작
둘 다 있어야: 어느 인스턴스가 받아도 같은 결과
```

**포트를 나눈 것만으로는 확장이 아니다. 상태를 밖으로 빼야 확장이 된다.** 그것이 [[04b-configuring-a-shared-database]]의 주제다.

**상태는 데이터베이스만이 아니다**(§6) — **세션이나 캐시를 인스턴스 안에 두면 같은 문제가 생긴다.** 사용자가 인스턴스 1에서 로그인하고 인스턴스 2로 가면 **다시 로그인**해야 한다.

**§6의 또 다른 단서**: **한 기계에 세 벌을 띄우는 것은 진짜 확장이 아니다.** **CPU와 메모리를 나눠 쓰므로 처리량이 세 배가 되지 않는다.** 예제로서의 시연이다.

## Q8. 세 무대 비유가 깨지는 지점

**비유**: **"같은 대본으로 무대를 세 개 여는 것."** **배우도 대사도 같고 극장 주소만 다르다.**

**깨지는 지점**: **관객이 무대 사이를 오간다는 점을 담지 못한다.**

> **실제로 로드 밸런서는 같은 사용자의 요청을 매번 다른 인스턴스로 보낼 수 있어서, 세 무대가 같은 이야기의 같은 지점에 있어야 한다. 그것이 공유 데이터베이스가 필요한 이유다.**

```
극장:  관객은 한 무대에서 끝까지 본다 → 무대끼리 진행이 달라도 문제없다
확장:  관객이 매 장면마다 다른 무대로 순간이동 → 진행이 같아야 한다
```

**Q6의 증상이 이 비유로 설명된다** — 1막을 무대 1에서 보고 2막을 무대 2에서 보면, **무대 2는 1막에서 무슨 일이 있었는지 모른다.**

**비유가 맞는 부분은 남는다** — **대본이 같다**(Q4의 불변 아티팩트), **주소만 다르다**(포트). 깨지는 것은 **관객의 이동**이고, 그것이 조건 ②(무상태)를 요구한다.

**정확한 비유로 고치면**: 무대보다 **같은 은행의 창구 여러 개**에 가깝다. 어느 창구로 가든 **같은 장부를 본다.** 창구가 각자 장부를 들고 있으면 은행이 아니다 — [[04b-configuring-a-shared-database]]의 비유가 그것이다.
