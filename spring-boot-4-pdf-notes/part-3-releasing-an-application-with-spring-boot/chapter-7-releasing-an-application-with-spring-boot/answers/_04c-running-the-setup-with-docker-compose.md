## Q1. 터미널 네 개로 띄우는 방식의 네 문제

| 문제 | **결과** |
|---|---|
| **순서를 지켜야 한다** | **DB가 먼저 떠야 한다** |
| **명령을 기억해야 한다** | **팀원마다 다르게 띄운다** |
| **종료도 하나씩** | **정리를 잊는다** |
| **재현이 안 된다** | **"내 환경에서는 됐는데"** |

> **책의 정리**: *"인스턴스를 하나씩 수동으로 띄우는 것은 **Spring Boot 프로파일이 어떻게 동작하는지 보여 주는 데는 도움이 되지만**, 실제 시나리오에서는 **Docker Compose로 환경 전체를 정의하고 명령 하나로 시작**하는 편이 더 흔하다."*

**공통 뿌리**: **구성이 사람의 머릿속에만 있다.** [[01-creating-an-uber-jar]]의 "17쪽짜리 절차"와 같은 문제 — **문서로만 존재하는 절차**는 지켜지지 않는다.

**Compose가 하는 일은 그 절차를 파일로 만드는 것**이다. 파일이면 **형상 관리에 들어가고, 리뷰되고, 재현된다.**

## Q2. 컨테이너 안에서 `localhost`가 데이터베이스를 못 가리키는 이유

**컨테이너 안에서 `localhost`는 그 컨테이너 자신이다.**

```
호스트에서 java -jar:   localhost:5432 → 호스트의 매핑된 포트 → DB 컨테이너  ✅
컨테이너 안에서:        localhost:5432 → 자기 자신 → 그 안에 DB 가 없다      ❌
```

**컨테이너가 격리된 네트워크 스택을 갖는다는 [[02-building-a-docker-container]]의 성질**이 여기서 함정이 된다. 각 컨테이너의 `localhost`는 **자기만의 루프백**이다.

**해법 — 서비스 이름 해석**:
```properties
spring.datasource.url=jdbc:postgresql://postgres:5432/postgres
#                                       └──┬───┘
#                            compose.yml 의 서비스 이름
```

> **"Docker Compose로 실행하면 서비스들이 내부 네트워크로 통신하므로, `localhost` 대신 서비스 이름(`postgres`)으로 데이터베이스를 참조한다. Docker가 자동으로 해석해 준다."**

**모든 서비스가 같은 기본 Compose 네트워크에 속하므로 서비스 이름으로 통신할 수 있다.**

**[[04b-configuring-a-shared-database]]의 `--name my-postgres`가 여기서 값을 낸다** — **컨테이너를 이름으로 찾을 수 있어야** 이 방식이 성립한다. [[02a-building-the-right-type-of-container]]의 임의 이름(`angry_cray`)으로는 불가능하다.

**주소를 바꾼 뒤 이미지를 다시 만들어야 한다** — `./mvnw spring-boot:build-image`.

## Q3. 포트 매핑에서 왼쪽만 다르고 오른쪽이 같아도 되는 근거

```text
instance1:  "9000:8080"
instance2:  "9001:8080"
instance3:  "9002:8080"
             호스트  컨테이너
```

**컨테이너마다 네트워크 스택이 격리돼 있으므로 내부 포트가 겹쳐도 충돌하지 않는다.**

| | **호스트에서 직접 실행** | **컨테이너** |
|---|---|---|
| 포트 충돌 | **일어난다** — 한 OS의 포트 공간을 공유 | **일어나지 않는다** — 각자 네트워크 스택 |
| 앱이 쓰는 포트 | **인스턴스마다 달라야 한다** | **전부 8080이어도 된다** |
| 구분하는 곳 | **애플리케이션 설정** | **매핑** |

> **애플리케이션은 자기가 8080에 떠 있다고만 알면 되고, 밖에서 어느 포트로 보이는지는 배치가 정한다.**

**이것이 [[04a-scaling-with-spring-boot]]과 근본적으로 다른 점이다** — 거기서는 **애플리케이션이 자기 포트를 알아야** 했다(그래서 프로파일마다 `server.port`). 여기서는 **관심사가 배치로 옮겨 간다.**

> **원문의 공백**: **그러면 `application-instance{N}.properties`의 `server.port`(9000·9001·9002)는 어떻게 되나?** 컨테이너 안에서 그 값이 적용되면 **앱은 9000에 뜨는데 매핑은 8080을 가리키므로 연결되지 않는다.** 책은 이 점을 설명하지 않는다.
>
> **더 근본적인 문제**: [[04-tuning-and-scaling-in-production]]은 그 파일들을 **"로컬 폴더", 즉 JAR 옆에** 만들라고 했다. 그런데 `compose.yml`은 `image: ch7:0.0.1-SNAPSHOT`을 그대로 띄운다. **호스트의 파일은 이미지 안에 없다.** 그대로 따르면 **컨테이너가 프로파일 설정을 찾지 못하고 DB 접속 정보도 적용되지 않는다.** 이미지에 담으려면 `src/main/resources`에 두고 다시 빌드해야 하고, **그러면 `server.port` 문제가 앞의 형태로 남는다.**

## Q4. `depends_on`이 보장하는 것과 보장하지 않는 것

**보장하는 것: 기동 순서.** 데이터베이스 컨테이너가 애플리케이션보다 **먼저 시작**된다.

**보장하지 않는 것: 준비 상태.**

> **"컨테이너가 시작됐다"까지이고 "PostgreSQL이 연결을 받을 준비가 됐다"는 아니다.**

```
docker compose up
   └ postgres 컨테이너 시작           ← depends_on 이 보장하는 지점
   └ instance1 컨테이너 시작
        └ DB 접속 시도                ← 이 시점에 PostgreSQL 은 아직 초기화 중일 수 있다
```

**데이터베이스는 초기화에 몇 초가 걸리므로, 그 사이 인스턴스의 연결 시도가 실패할 수 있다.**

**책은 이것을 "보장한다"고 설명하는데, 정확히는 순서만 보장한다.**

**운영에서 필요한 것**: **헬스 체크 기반의 기동 조건** — `condition: service_healthy`. 데이터베이스가 **실제로 응답할 때까지** 기다린다.

**[[../../part-5-observing-spring-boot-4-applications/chapter-13-observing-spring-boot-4-applications/03a-setting-up-the-logging-infrastructure|Ch13]]에서도 같은 성질이 나온다.**

**대안적 방어**: 애플리케이션 쪽에서 **연결 재시도**를 하도록 두는 것. "의존 대상이 아직 없을 수 있다"를 전제로 설계하는 편이 분산 환경에서 견고하다.

## Q5. 사전 적재 코드가 인스턴스 셋에서 만드는 문제

**세 번 실행된다.**

```
docker compose up -d
   ├─ instance1 기동 → 사전 적재 실행
   ├─ instance2 기동 → 사전 적재 또 실행
   └─ instance3 기동 → 사전 적재 또 실행
              ↓ 공유 DB
   같은 데이터가 세 벌  또는  키 충돌로 기동 실패
```

**[[../../part-2-creating-an-application-with-spring-boot/chapter-3-querying-for-data-with-spring-boot/03-creating-repositories-and-declarative-queries|Ch3]]과 [[../../part-2-creating-an-application-with-spring-boot/chapter-4-securing-an-application-with-spring-boot/06f-displaying-user-details-on-the-site|Ch4]]에서 사용자 로그인 정보와 동영상 항목을 사전 적재하는 코드를 넣었다.**

**인스턴스가 하나일 때는 문제가 없었다.**

**두 가지 결과 중 어느 쪽이 나오나**:
- **유니크 제약이 있으면** → **기동 실패**(시끄러운 실패, 그나마 낫다)
- **없으면** → **중복 데이터**(조용한 실패, 나중에 발견)

**[[04a-scaling-with-spring-boot]]의 "무상태 인스턴스" 원칙의 또 다른 얼굴이다** — **인스턴스가 기동할 때마다 하는 일이 있으면, 인스턴스를 늘리는 순간 그 일이 여러 번 일어난다.**

**같은 형태의 문제가 더 있다**: 스케줄러, 캐시 워밍, 마이그레이션 실행 — **"한 번만 해야 하는 일"을 모든 인스턴스가 한다.**

## Q6. "애플리케이션은 데이터 관리 정책의 수단이 아니다"

> **"시작하고 멈추며 여러 인스턴스로 도는 애플리케이션은 지속 데이터 관리 정책을 적용하는 수단이 아니다(is NOT the vehicle)."**

**근거**: 애플리케이션의 생명주기가 **데이터의 생명주기와 맞지 않는다.**

| | **애플리케이션** | **데이터** |
|---|---|---|
| 몇 개 | **여럿**(수평 확장) | **하나**(공유 DB) |
| 언제 시작 | **수시로**(재배포·오토스케일·재시작) | 한 번 |
| 몇 번 실행돼야 하나 | **여러 번 실행돼도 안전해야** | **정확히 한 번** |

**"기동할 때마다 실행된다"와 "정확히 한 번 실행돼야 한다"가 구조적으로 충돌한다.** Q5가 그 충돌의 구체적 결과다.

**권하는 방식**:
| 방식 | 내용 |
|---|---|
| **데이터베이스 마이그레이션 도구** | **Flyway나 Liquibase**가 스키마 변경과 기준 데이터를 **버전 관리된 절차**로 다룬다 |
| **DBA 통제 프로세스** | **사람이 통제하는 절차** |

**마이그레이션 도구가 푸는 방식**: **어떤 스크립트를 실행했는지 DB에 기록**한다. 그래서 **몇 번을 돌려도 한 번만** 적용된다 — 실행 주체가 여럿이어도 안전하다.

**[[04b-configuring-a-shared-database]]의 `ddl-auto=update` 경계와 이어진다** — 스키마도 데이터도 **애플리케이션이 자동으로 손대는 것**은 운영에서 위험하다.

## Q7. `@Profile("setup")`이 하는 일과 주의 사항

**하는 일**: **데이터 적재 빈이 `setup` 프로파일이 활성일 때만 컨텍스트에 올라간다.**

```java
@Profile("setup")
@Bean CommandLineRunner initData(...) { ... }
```

**평소 실행에서는 그 빈 자체가 없으므로 Q5의 세 번 실행이 일어나지 않는다.**

**이 장의 최종 코드에는 `application-setup.properties`와 그 제약이 들어 있다.**

**주의 사항**: **사전 적재를 하고 싶으면 `setup` 프로파일로 실행하되, 데이터베이스를 띄운 뒤 딱 한 번만 하라.**

```
1. docker compose up -d postgres        (DB 먼저)
2. SPRING_PROFILES_ACTIVE=setup ...     (한 번만)
3. docker compose up -d                 (평소 실행 — setup 없음)
```

**두 번 하면 Q5의 문제가 그대로 재발한다** — 프로파일이 **횟수를 세어 주지는 않는다.**

**즉 `@Profile("setup")`은 "자동 실행을 끈 것"이지 "한 번만 실행되게 만든 것"이 아니다.** 한 번만을 보장하려면 Q6의 마이그레이션 도구가 필요하다. **이것은 예제 코드의 대응책**이지 운영 해법이 아니다.

## Q8. Compose로 감당이 안 되는 규모

> **"여기서부터는 한계가 없다. 열두 벌도 돌릴 수 있다. **다만 이런 방식으로 하고 싶지는 않을 것이다.**"**

**필요한 것: 오케스트레이션** — **여러 컨테이너의 배치·확장·네트워킹·롤링 업데이트를 자동 관리.**

| 도구 | 성격 | **대가** |
|---|---|---|
| **Kubernetes** | 지배적인 오케스트레이션 플랫폼 | 세밀한 제어와 확장성, 대신 **운영 복잡도와 가파른 학습 곡선** |
| **Argo CD · Flux** | Kubernetes용 **GitOps** 도구. **Git 저장소를 감시해 실제 상태를 원하는 상태에 맞춘다** | GitHub Actions·GitLab CI·Jenkins·Tekton 같은 CI와 짝을 이룬다 |
| **Spinnaker** | 지속적 전달 플랫폼. 고급 배포 전략 지원 | 다른 인프라와의 통합이 필요하고, **새 Kubernetes GitOps 구성에서는 덜 선택된다** |
| **VMware Tanzu** | 엔터프라이즈 플랫폼 | 통합된 경험 대신 **유연성이 낮다.** **2023년 말 Broadcom 인수 후 로드맵·라이선스를 확인해야 한다** |

**Compose의 근본 한계**(§6): **한 호스트용이다.** **여러 기계에 걸친 배치는 오케스트레이션의 몫**이다.

**책의 태도가 균형 잡혀 있다** — 각각 장단이 있고, **환경이 요구하는 제어 수준과 복잡도에 따라** 고르라는 것이다. **"Kubernetes를 쓰라"가 아니다.**

## Q9. 무대 세팅 지시서 비유가 깨지는 지점

**비유**: Compose 파일은 **"무대 세팅 지시서"**다. **무엇을 어디에 놓고 어떤 순서로 올릴지 한 장에 적혀 있다.**

**깨지는 지점**: **지시서가 배우까지 만들어 내지는 않는다는 점을 흐린다.**

> **Compose는 이미 만들어진 이미지를 배치할 뿐이고, 이미지가 없거나 낡았으면 아무리 정확한 지시서도 옛 공연을 올린다. 그래서 이 절이 `build-image`를 다시 돌리는 것으로 시작한다.**

```
지시서:  "배우 A를 무대 왼쪽에"  → 배우 A 가 준비돼 있다고 전제
Compose: image: ch7:0.0.1-SNAPSHOT → 그 태그가 가리키는 이미지를 쓴다
                                     (낡았어도 모른다)
```

**[[03-publishing-an-image-to-docker-hub]]의 태그 문제가 여기서 다시 나온다** — **태그는 포인터**이므로, `ch7:0.0.1-SNAPSHOT`이 **어제 구운 것**을 가리킬 수 있다. Q2의 `localhost` → `postgres` 변경도 **다시 굽지 않으면 반영되지 않는다.**

**증상**: `compose.yml`을 아무리 고쳐도 **동작이 안 바뀐다.** 그리고 **오류가 안 난다** — 옛 이미지가 정상적으로 뜬다.

**비유가 맞는 부분은 남는다** — **한 장에 전체가 적혀 있다**(Q1의 해법), **순서가 명시된다**(`depends_on`). 깨지는 것은 **지시서와 대상의 분리**다.
