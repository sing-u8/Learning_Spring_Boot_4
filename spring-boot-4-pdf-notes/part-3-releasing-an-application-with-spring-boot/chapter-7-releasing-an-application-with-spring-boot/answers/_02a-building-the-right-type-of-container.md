## Q1. 통짜 이미지에서 자바 파일 한 줄을 고치면

**전부 다시 만들어지고, 배포할 때 전부 다시 전송된다.**

```text
[ 베이스 OS + JRE + Spring Boot + Spring Framework + Mustache + ... + 내 코드 ]
                                                                      ↑ 여기 한 줄
      └────────────────────── 이 레이어 전체가 무효 ──────────────────────┘
```

> **바뀐 것은 몇 바이트인데 수백 MB가 오간다.**

**책의 예가 정확하다** — **Spring Framework 7.0.0 GA 릴리스**는 **캐시해 두기에 딱 좋은 것**이다. **계속 다시 받을 이유가 없다.** 그런데 내 코드가 같은 레이어에 섞여 있으면 **자바 파일 하나가 바뀔 때마다 그것까지 통째로 다시 받아야 한다.**

**비용이 나타나는 곳**: 빌드 시간, **레지스트리 전송량**, 배포 시간, 그리고 **롤백 속도.**

**해법**: **Spring Boot·Spring Framework·Mustache 같은 라이브러리는 한 레이어에, 내 코드는 별도 레이어에** — 계층형 이미지.

## Q2. 레이어 무효화 규칙이 요구하는 설계

**규칙**: **한 레이어의 내용이 바뀌면 그 레이어와 그 위의 모든 레이어가 무효가 된다.**

**그래서 "변경 빈도가 낮은 것을 아래에"가 나온다.**

```
아래 ─ 베이스 이미지     (거의 안 바뀜)
     ─ JRE              (분기~연 단위)
     ─ 의존성           (릴리스마다)
위   ─ 내 코드          (하루에도 여러 번)   ← 가장 자주 바뀌는 것을 맨 위에
```

**거꾸로 두면**: 의존성이 내 코드 위에 있으면, **코드를 고칠 때마다 의존성 레이어도 무효**가 된다. 캐시가 **한 번도 안 듣는다.**

**즉 무효화가 위쪽으로만 전파되므로, 자주 바뀌는 것을 위에 두면 무효화 범위가 최소가 된다.**

```
좋음: 코드 변경 → 최상위 레이어만 무효     → 의존성 레이어는 캐시 재사용
나쁨: 코드 변경 → 중간 레이어 무효         → 그 위 전부 다시
```

**Q9의 비유가 깨지는 지점이 바로 이 방향성이다.**

## Q3. `layers.idx`가 언제 만들어졌고 여기서 어떻게 쓰이는가

**[[01-creating-an-uber-jar]]의 7단계 중 마지막 단계에서 만들어졌다.**

> **`BOOT-INF` 아래의 `layers.idx`와 `classpath.idx`** — uber JAR을 만들 때 이미 **어떤 파일이 어느 레이어에 속하는지 적어 두었다.**

**여기서의 역할**: **이미지를 조립할 때 그 목록대로 레이어를 나눈다.** 그래서 **아무것도 설정하지 않아도 제대로 나뉜다.**

**책이 짚는 변화**: **예전에는 이 계층 분리에 여러 수동 단계가 필요했다.** 지금은 Spring Boot 팀이 **계층형 방식을 기본 설정으로** 만들었다.

**설계적으로 읽으면**: **분류 정보를 아는 쪽(빌드)이 그것을 기록**하고, **쓰는 쪽(이미지 조립)이 읽는다.** 이미지를 만드는 도구가 **자바 의존성 구조를 다시 분석할 필요가 없다.**

**[[02-building-a-docker-container]]의 "이미지는 uber JAR 위에 세워진다"가 여기서 구체적 의미를 얻는다** — 재료일 뿐 아니라 **조립 설명서까지 함께** 온다.

## Q4. build-image 로그에서 이미지 이름의 출처

> **이미지 이름 `docker.io/library/ch7:0.0.1-SNAPSHOT`은 pom의 module 이름과 version에서 나온다.**

```
docker.io/library / ch7 : 0.0.1-SNAPSHOT
      └─┬──┘        └┬┘    └──────┬─────┘
   기본 접두사   artifactId      version
```

**실무적으로 중요한 이유**: **이미지 이름을 따로 지정하지 않았는데도 나온다.** **pom을 바꾸면 이미지 이름도 따라 바뀐다.**

**그래서 생기는 것**: 버전을 올리면 **이미지 태그가 자동으로 따라온다** — 사람이 두 곳을 맞출 필요가 없다.

**주의**: `docker.io/library/`는 **기본 접두사**다. **배포용 이미지는 네임스페이스를 명시해야** 한다 → [[03-publishing-an-image-to-docker-hub]].

> **원문 불일치**: 이 로그는 `spring-boot-maven-plugin:**4.0.0**`인데, 바로 아래 절의 컨테이너 실행 로그 배너는 `Spring Boot (v**4.1.0**)`이다. **같은 프로젝트의 두 출력이 서로 다른 버전을 가리킨다.**

## Q5. Paketo가 하는 네 가지 일

| 하는 일 | **직접 하려면** |
|---|---|
| 애플리케이션 종류 자동 감지(자바) | Dockerfile에 직접 적는다 |
| **베이스 이미지 선택** | 어느 OS·어느 배포판을 쓸지 정한다 |
| **올바른 자바 런타임 설치** | JDK 버전과 배포판을 고르고 설치 스크립트를 쓴다 |
| **캐싱 효율을 최대화하도록 레이어 구성** | **무엇을 어느 레이어에 둘지 손으로 설계한다** |

> **가장 까다로운 것은 네 번째다.**

**이유**: 앞의 셋은 **한 번 정하면 되는 선택**이다. 네 번째는 **지속적인 설계 판단**이 필요하다 —
- 의존성 중에서도 **자주 바뀌는 것과 안 바뀌는 것**을 갈라야 하고
- **스냅샷 의존성**은 릴리스 의존성과 다르게 다뤄야 하고
- 프로젝트가 커지면 **그 분류를 계속 갱신**해야 한다

**그리고 틀려도 안 드러난다** — 잘못 나눠도 **이미지는 정상 동작**한다. **느려질 뿐이다.** Q2의 "거꾸로 두면 캐시가 한 번도 안 듣는다"가 조용히 일어난다.

**책의 Note**: **Spring Boot는 컨테이너화를 직접 하지 않고 Paketo에 위임한다.** 일을 대신 해 주는 컨테이너를 내려받아 쓰는 구조다.

## Q6. builder 이미지와 run 이미지

| 이미지 | **언제 쓰이나** | **최종 결과물에** |
|---|---|---|
| **빌더 이미지** `builder-noble-java-tiny` | **빌드 중** | **포함되지 않는다** |
| **런 이미지** `ubuntu-noble-run-tiny` | **실행 시** | **포함된다** |

**빌더에는 있고 런에는 없는 것**: JDK(컴파일용), 빌드 도구, 감지 스크립트 — **실행에 필요 없는 것 전부.**

**이름의 `tiny`가 힌트다** — **런타임에 필요한 최소한만 담아 최종 이미지를 작게** 만든다.

**왜 나누는가**: **빌드 도구를 최종 이미지에 담으면**
- **이미지가 커진다**
- **공격 표면이 넓어진다** — 컴파일러가 운영 컨테이너 안에 있을 이유가 없다

**같은 아이디어를 Dockerfile로 하면 멀티 스테이지 빌드다.** Paketo는 그것을 **기본 구조로** 갖는다.

**"builder 이미지가 최종 이미지에 들어간다"는 오해** — 들어가지 않는다. **빌드에만 쓰이고, 최종은 run 이미지 위에 세워진다.**

## Q7. `Calculating JVM memory…` 로그가 알려 주는 것

**Paketo가 컨테이너에 할당된 메모리를 보고 JVM 옵션을 계산한다.**

```
Calculating JVM memory based on 7163580K available memory
```

> **손으로 `-Xmx`를 주지 않아도 된다.**

**왜 이 기능이 필요한가**: **JVM은 기본적으로 호스트 전체 메모리를 기준으로 힙을 잡는다.** 컨테이너에 512MB만 할당했는데 JVM이 호스트의 32GB를 보고 힙을 잡으면 **OOM으로 죽는다.**

**Paketo가 하는 일**: cgroup 한도를 읽어 **힙·메타스페이스·스레드 스택을 그 안에 맞춰** 계산한다.

**같은 로그에서 읽을 것이 더 있다**:
- **`PID 1`** — 컨테이너 안에서 애플리케이션이 **1번 프로세스**다. **컨테이너의 수명이 곧 이 프로세스의 수명**이다.
- **`/workspace/BOOT-INF/classes`** — [[01-creating-an-uber-jar]]의 그 구조가 **컨테이너 안에 풀려 있다.**
- **`started by cnb`** — Paketo가 만든 **비루트 사용자.** **보안상 root로 돌지 않는다.**

**세 번째가 중요하다** — 컨테이너를 root로 돌리는 것은 흔한 취약점이고, **Paketo는 기본으로 그것을 피한다.**

## Q8. 컨테이너의 임의 이름이 함정이 되는 상황

**스크립트에 이름을 박아 둘 수 없다.**

```bash
% docker ps
CONTAINER ID   ...   NAMES
5e4fb7fdead2   ...   angry_cray     ← 띄울 때마다 다르다
```

**이름은 Docker가 붙인 사람 친화적 임의 이름**이고, **띄울 때마다 다르게 생성된다.**

**함정이 되는 순간**:
- **배포 스크립트**가 `docker stop angry_cray`를 담을 수 없다
- **CI 파이프라인**이 특정 컨테이너를 지목할 수 없다
- **다른 컨테이너가 이 컨테이너를 이름으로 찾을 수 없다** → [[04c-running-the-setup-with-docker-compose]]에서 데이터베이스를 `my-postgres`로 부르는 문제

**해법**: **`--name`이나 Compose의 `container_name`으로 고정**한다.

> **[[04c-running-the-setup-with-docker-compose]]에서 `container_name`을 고정하는 이유가 그것이다.**

**제어 수단은 셋 다 가능하다** — **해시 ID, 임의 이름, Docker Desktop의 클릭.** 대화형으로는 임의 이름이 편하고, **자동화에는 고정 이름이나 ID**를 써야 한다.

## Q9. 옷을 겹쳐 입는 비유가 깨지는 지점

**비유**: 레이어 캐싱은 **"옷을 겹쳐 입는 것"**이다. **안에 입은 옷은 그대로 두고 겉옷만 갈아입는다.**

**깨지는 지점**: **아래 것을 바꾸면 위를 다 벗어야 한다는 방향성을 담지 못한다.**

> **Docker에서는 아래 레이어가 바뀌면 그 위의 모든 레이어가 무효가 되므로, 변경 빈도가 낮은 것을 반드시 아래에 두어야 한다. 순서가 성능을 결정한다.**

```
옷:     셔츠를 갈아입어도 재킷은 그대로 (물리적으로 분리)
레이어: 아래를 바꾸면 위가 전부 무효    (내용이 아래에 의존)
```

**왜 그런가**: Docker 레이어는 **아래 레이어 위의 차분(diff)**이다. 아래가 달라지면 **그 위의 차분이 무엇을 기준으로 한 것인지 알 수 없게** 된다.

**실무적 귀결**(§6): **레이어를 나눠도 베이스가 바뀌면 소용없다.** **JRE 버전을 올리면 그 위가 다 무효**가 된다. 그래서 JRE 업그레이드는 **전체 재전송을 각오**해야 하는 이벤트다.

**"레이어를 나누면 이미지가 커진다"는 오해도 함께 정리하면** — **총 크기는 비슷하고 재빌드·재전송되는 양이 줄어든다.** 이득은 **크기가 아니라 변화량**에 있다.

**비유가 맞는 부분은 남는다** — **부분만 갈아입는다**는 핵심. 깨지는 것은 **독립성**이고, 그것이 Q2의 설계 요구를 낳는다.
