## Q1. uber JAR이 남긴 조건이 문제가 되는 상황

**남긴 조건: "JDK만 있으면 어디서나 돈다."**

| 상황 | **문제** |
|---|---|
| **대상에 자바가 아예 없다** | **설치해야 한다** |
| **자바 21이 깔려 있는데 앱은 25가 필요하다** | **업그레이드가 다른 앱에 영향을 준다** |
| **한 머신에서 여러 자바 버전이 필요하다** | **버전 관리 도구가 또 필요하다** |
| 개발 환경과 미묘하게 다르다 | **"내 컴퓨터에서는 됐는데"** |

**두 번째가 특히 아프다** — [[01-creating-an-uber-jar]]이 없앤 **"서버 재시작이 다른 앱에 영향을 준다"**는 문제가 **런타임 층에서 재발**한다. 공유 자원이 톰캣에서 JDK로 옮겨 갔을 뿐이다.

> **uber JAR이 서버 설치를 없앴듯, 이번에는 런타임 설치까지 없애는 것이 목표다.**

**즉 [[01-creating-an-uber-jar]]의 이동식 주택 비유에서 "부지"에 해당하던 것을 함께 싣는다.**

## Q2. 컨테이너선 비유가 설명하는 성질

**규격이 같아서 내용물을 몰라도 다룰 수 있다는 것.**

> **세계 화물의 대부분을 나르는 선박 컨테이너는 규격이 같다.** 그래서 물건을 만드는 쪽은 **세계 어디서나 같은 크기·구조의 컨테이너가 처리된다**는 것을 알고 계획을 세울 수 있다.

**소프트웨어에서**: **안에 무엇이 들었든 바깥 규격이 같으므로 그것을 다루는 도구(엔진, 오케스트레이터, 레지스트리)가 내용물을 몰라도 된다.**

```
Java 앱 / Python 앱 / Postgres / Redis
        └────────┬────────┘
        전부 같은 방식으로 띄우고, 재고, 옮기고, 죽인다
```

**이 성질이 만드는 것**: **생태계.** Kubernetes가 자바를 알 필요가 없고, CI가 언어를 알 필요가 없다. **인터페이스가 하나**이므로 도구가 그 하나만 지원하면 된다.

**Q4의 "널리 채택됐다"가 이 성질의 결과다** — 규격이 같으니 **모두가 같은 도구에 투자**할 수 있었다.

## Q3. 컨테이너가 VM보다 가벼운 근본 이유

**호스트 커널을 공유하기 때문이다.**

**구현**: Docker는 **Linux namespace와 control groups(cgroups)**를 containerd·runc 같은 하위 런타임을 통해 쓴다. 그 결과 각 컨테이너는 **격리된 프로세스 트리, 메모리 뷰, 네트워크 스택**을 가지면서 **호스트 커널은 공유한다.**

| | **가상 머신** | **컨테이너** |
|---|---|---|
| **커널** | **자기 것** | **호스트와 공유** |
| 부팅 | **OS 부팅** (수십 초) | **프로세스 시작** (수백 ms) |
| 크기 | **GB 단위** | **MB 단위** |
| 격리 수준 | 강함 | **커널을 공유하므로 상대적으로 약함** |
| 만드는 비용 | 무겁다 | **필요할 때 즉석에서** |

**커널이 없다는 것이 나머지 전부를 설명한다** — 부팅할 OS가 없으니 빠르고, 담을 OS가 없으니 작고, **커널을 나눠 쓰니 격리가 그만큼 약하다.**

> **"통째로 가상 머신을 만드느라 시간을 낭비하는 대신 필요할 때 컨테이너를 띄운다. 애플리케이션 지향적인 성격 덕에 훨씬 민첩한 선택이 된다."**

**"가벼운 가상 머신"이라는 표현이 오해를 부른다** — 정도의 차이가 아니라 **종류의 차이**다.

## Q4. Docker 설치 요구를 부담으로 보지 않는 근거

| 근거 | **뜻** |
|---|---|
| **모든 주요 클라우드가 컨테이너 워크로드를 지원** | **배포 대상이 이미 준비돼 있다** |
| **대부분의 CI/CD가 컨테이너 기반 빌드를 지원** | **파이프라인이 이미 준비돼 있다** |
| **오케스트레이션 생태계가 형성됨** | **규모를 키울 길이 있다** |
| **Docker가 2023년 AtomicJar를 인수해 Testcontainers를 유지보수** | **Ch5에서 이미 Docker를 깔았다** |

> **결론: 개발자와 시스템 관리자에게 로컬과 배포 환경에 Docker 설치를 요구하는 것은 일반적으로 운영 부담으로 여겨지지 않는다.**

**네 번째가 이 책 안에서 특히 실용적이다** — [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/06-adding-testcontainers|Ch5 · Testcontainers 추가]]에서 이미 Docker를 깔았다면 **추가 요구가 없다.** 테스트를 위해 이미 치른 비용이 배포에서 회수된다.

**논증의 형태를 보면**: "Docker가 좋다"가 아니라 **"이미 거기 있다"**다. **새 요구를 만드는 것이 아니라 기존 요구를 재사용**한다는 논거이며, [[01-creating-an-uber-jar]]의 "단계 수를 줄인다"와 같은 관점이다.

## Q5. `package`와 `build-image`의 성격 차이

| | `./mvnw clean package` | `./mvnw spring-boot:build-image` |
|---|---|---|
| **무엇인가** | Maven **표준 생명주기 단계** | **Maven goal**(플러그인이 제공하는 실행 단위) |
| **어떻게 불리나** | **앞 단계를 순서대로 부른다** | **직접 지정해 부른다** |
| 산출물 | uber JAR | **컨테이너 이미지** |
| 누가 훅했나 | `spring-boot-maven-plugin`이 **package에 훅** | 같은 플러그인의 **별도 goal** |

**`spring-boot:build-image`의 문법**: **`spring-boot:`가 플러그인 이름, `build-image`가 goal 이름.**

> **표준 단계가 아니므로 이름을 직접 적어야 한다.**

**왜 표준 단계가 아닌가**: Maven의 생명주기는 **모든 자바 프로젝트가 공유하는 것**이다. "컨테이너 이미지를 만든다"는 **모든 프로젝트가 하는 일이 아니므로** 표준 단계에 자리가 없다. **플러그인 고유 동작은 goal로 노출**한다.

**이 구분이 실무에서 드러나는 곳**: CI 스크립트에서 `mvn clean package`는 관례이고, `mvn spring-boot:build-image`는 **명시적 선택**이다.

## Q6. "baking"이 담는 함의

**Docker 세계의 표현으로 baking은 컨테이너를 돌리는 데 필요한 모든 부품을 조립하는 것이다.**

> **한 번 구우면 그 이미지로 필요한 만큼 인스턴스를 띄운다.**

```
소스 → package → build-image → 이미지 ─┬─ 인스턴스 1
                    (한 번 굽는다)      ├─ 인스턴스 2
                                       └─ 인스턴스 N
```

**"굽는다"가 함의하는 것**:
- **되돌릴 수 없다** — 구운 뒤에 재료를 바꿀 수 없다 = **불변 아티팩트**
- **굽기와 먹기가 분리된다** — 빌드 시점과 실행 시점이 다르다
- **한 번의 비용으로 여러 결과** — 조립은 한 번, 실행은 N번

**"굽는 것과 실행하는 것은 같이 일어난다"는 오해가 흔하다** — **분리돼 있다.**

**이미지가 불변 아티팩트라는 점이 [[04a-scaling-with-spring-boot]]의 전제가 된다** — **같은 이미지를 세 벌 띄우고 설정만 다르게** 주는 것이 이 장 후반부의 내용이다. [[01-creating-an-uber-jar]]의 "1만 개 복제"가 여기서 구체화된다.

## Q7. `build-image`가 먼저 `package`를 도는 것의 두 결과

```text
build-image
  └ package 실행
      └ 표준 단위 테스트 실행
      └ uber JAR 조립
  └ 그 uber JAR을 재료로 이미지 조립
```

**① 테스트를 통과하지 못하면 이미지도 안 나온다.** **릴리스 아티팩트에 검증이 강제된다.**

[[01-creating-an-uber-jar]]에서 `package`가 테스트를 도는 성질이 **한 층 위로 전파**된다. **JAR에 걸린 게이트가 이미지에도 걸린다.**

**② 이미지는 uber JAR 위에 세워진다.** [[01-creating-an-uber-jar]]의 결과물이 **그대로 재료**다.

**두 번째가 설계적으로 중요하다** — 컨테이너화가 **기존 산출물을 대체하지 않고 감싼다.** 그래서
- uber JAR로 배포하던 팀이 **같은 아티팩트로** 컨테이너 배포로 갈 수 있다
- [[01-creating-an-uber-jar]]의 `layers.idx`가 **[[02a-building-the-right-type-of-container]]에서 재료로 쓰인다**

**"`build-image`는 JAR과 별개로 이미지를 만든다"는 오해**를 이 순서가 정정한다.

## Q8. 컨테이너선 비유가 깨지는 지점

**비유는 "규격이 같아서 어디서나 처리된다"를 잘 설명한다(Q2).**

**깨지는 지점**: **컨테이너가 배와 무관하게 존재한다는 인상을 준다.**

> **실제로 컨테이너는 호스트 커널 위에서만 산다 — 배 없이 떠 있을 수 없고, 배(호스트 OS)의 종류가 바뀌면 실을 수 있는 것도 달라진다.**

```
선박 컨테이너:  부두에 놓아도 존재한다. 배는 운반 수단일 뿐
소프트웨어 컨테이너: 커널이 없으면 존재 자체가 불가능 (Q3)
```

**구체적 귀결**:
- **Linux 이미지는 Linux 커널이 필요하다** — macOS/Windows의 Docker Desktop이 뒤에서 Linux VM을 돌리는 이유
- **아키텍처가 다르면 안 돈다** — `amd64` 이미지를 `arm64`에서 그대로 못 쓴다
- **커널 버전에 따라 동작이 달라질 수 있다**

**즉 "어디서나"에 조건이 붙는다** — **같은 종류의 배 위에서만.**

**§6이 같은 말을 다르게 한다** — **컨테이너 런타임이 없으면 여전히 못 돈다. 요구가 JDK에서 런타임으로 옮겨 갔을 뿐이다.** 다만 Q4가 그 요구는 **이미 널리 충족돼 있다**고 말한다.

**비유가 맞는 부분은 남는다** — **규격 통일이 생태계를 만든다**는 핵심. 깨지는 것은 **독립성**이다.
