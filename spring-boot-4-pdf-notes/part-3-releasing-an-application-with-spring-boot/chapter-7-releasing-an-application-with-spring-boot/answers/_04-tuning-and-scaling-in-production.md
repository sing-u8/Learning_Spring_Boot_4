## Q1. "손대기 시작해야 진짜 운영"이 요구하는 것

> **"릴리스 후에 조정하고, 만지작거리고, 손보기 시작해야 애플리케이션이 진짜 운영에 있는 것이다. 그것이 운영이라는 일의 본질이다."**

**요구하는 것: 재빌드 없이 동작을 바꿀 수 있어야 한다.**

**조정 대상은 포트만이 아니다** — **서버 포트, 데이터베이스 연결, 로그 레벨, 특정 프로파일 활성화.** 그리고 **uber JAR로 돌든 컨테이너로 돌든 마찬가지**다.

**왜 이것이 배포의 연장이 아니라 별개 요구인가**: 배포는 **한 번**이지만 조정은 **계속**된다. 조정할 때마다 빌드→테스트→배포 파이프라인을 돌려야 한다면
- **새벽 두 시의 로그 레벨 변경에 30분**이 든다
- **매번 새 아티팩트**가 생겨 [[03-publishing-an-image-to-docker-hub]]의 태그가 늘어난다
- **불변 아티팩트 원칙이 무의미**해진다 — 매번 다른 것을 배포하므로

**그래서 "같은 아티팩트 + 다른 설정"이 필요하다.** 이 절 전체가 그 방법이고, [[04a-scaling-with-spring-boot]]이 그것을 확장한다.

## Q2. 포트를 바꾸는 세 가지 나쁜 방법

| 방법 | **문제** |
|---|---|
| **소스의 `application.properties`를 고치고 재빌드** | **불변 아티팩트 원칙이 깨진다. 테스트한 것과 다른 바이너리가 나간다** |
| **uber JAR을 풀어 안의 설정을 고치고 다시 묶기** | **[[../chapter-6-configuring-an-application-with-spring-boot/04-setting-properties-with-environment-variables|Ch6]]이 강하게 금지한 방법** — 서명 무효, 기록 없음, 다음 배포에 사라짐 |
| **환경마다 다른 JAR을 빌드** | **아티팩트가 환경 수만큼 늘어난다** |

**세 방법이 공유하는 결함**: **바이너리를 환경의 함수로 만든다.** 그러면
- "이 버전을 테스트했다"는 진술이 **어느 환경의 것인지 물어야** 하고
- 환경이 늘 때마다 **빌드가 늘고**
- **롤백할 때 어느 것으로 돌아갈지** 헷갈린다

**[[01-creating-an-uber-jar]]의 "1만 개 복제"가 여기서 조건을 드러낸다** — 복제 가능하려면 **하나여야** 한다.

## Q3. `SERVER_PORT=9000`이 동작하는 근거

**[[../chapter-6-configuring-an-application-with-spring-boot/04-setting-properties-with-environment-variables|Ch6의 완화된 바인딩]]과 [[../chapter-6-configuring-an-application-with-spring-boot/05-ordering-property-overrides|Ch6의 우선순위]] 두 규칙이다.**

```
① 완화된 바인딩:  SERVER_PORT  ──매핑──▶  server.port
   (셸이 점을 못 쓰므로 대문자·밑줄 표기를 같은 키로 인정)

② 우선순위:      환경 변수(5) > Config Data(3)
   (JAR 안의 application.properties 를 이긴다)
```

**둘 다 필요하다** — ①만 있으면 **키는 맞지만 JAR 안 값에 진다.** ②만 있으면 **애초에 그 키를 표현할 수 없다.**

**확인**: 로그 마지막 줄이 답을 준다 — `Tomcat started on port **9000**`.

> **아티팩트는 손대지 않았다. 같은 JAR이 명령만 달라져 다르게 동작한다.**

**그리고 이것은 포트에 국한되지 않는다** — **어떤 프로퍼티든** 같은 방식으로 덮을 수 있다.

## Q4. 명령이 똑같은데 결과가 달라지는 이유

**Spring Boot가 기동할 때 주위를 둘러보고 로컬 폴더의 `application.properties`를 발견하기 때문이다.**

> **"그리고 그 설정을 JAR 안에 있는 것에 대한 오버라이드로 적용한다."**

```bash
% java -jar target/ch7-0.0.1-SNAPSHOT.jar     # 명령은 처음과 똑같다
# 현재 폴더에 application.properties (server.port=9000) 가 있으면
→ Tomcat started on port 9000
```

**동작이 명령이 아니라 실행 위치에 달려 있다.**

**이것이 Q3의 환경 변수 방식보다 나은 점**: 책의 지적대로 **"매번 그 추가 파라미터를 치는 건 좀 번거롭다."** 파일로 두면 **한 번 적고 계속 쓴다.**

**대가**: **명령만 봐서는 무엇이 적용되는지 알 수 없다.** 같은 명령이 디렉터리에 따라 다르게 동작하므로, **"왜 포트가 9000이지?"**를 조사하려면 **현재 디렉터리를 봐야** 한다. 이 성질은 [[../chapter-6-configuring-an-application-with-spring-boot/04-setting-properties-with-environment-variables|Ch6]]의 `export` 함정과 같은 모양이다 — **보이지 않는 상태가 결과를 바꾼다.**

## Q5. JAR 밖 파일이 JAR 안 파일을 이기는 규칙

**[[../chapter-6-configuring-an-application-with-spring-boot/05-ordering-property-overrides|Ch6 · 프로퍼티 우선순위]]의 Config Data 4단계다.**

| # | 파일 | 어디에 |
|---:|---|---|
| 1 | `application.properties` | **JAR 안** (가장 낮음) |
| 2 | `application-{profile}.properties` | JAR 안 |
| **3** | **`application.properties`** | **JAR 밖** ← 방금 만든 파일 |
| 4 | `application-{profile}.properties` | JAR 밖 (가장 높음) |

> **위치가 우선순위를 결정한다.**

**정렬은 (위치, 프로파일) 순이다** — **JAR 밖 기본 파일(3)이 JAR 안 프로파일 파일(2)보다 높다.**

**왜 위치가 먼저인가**: **JAR 밖은 배포 환경이 통제하는 자리**이고 **JAR 안은 빌드가 통제하는 자리**다. **배포가 빌드를 이겨야** 같은 아티팩트를 여러 환경에 쓸 수 있다(Q2).

**[[../chapter-6-configuring-an-application-with-spring-boot/05-ordering-property-overrides|Ch6]]이 "JAR을 열지 마라"고 경고하면서 동시에 "그럴 필요가 없다"고 한 이유가 바로 이 구조다.**

## Q6. `/opt/app/` 배치가 지키는 원칙

```text
/opt/app/
├── ch7-0.0.1-SNAPSHOT.jar        ← 손대지 않는다. 모든 환경에서 같은 파일
└── application.properties        ← 환경마다 다르다
```

**지키는 원칙: 불변 아티팩트 + 외부화된 설정.**

**두 파일의 성격이 정반대다**:

| | JAR | 설정 파일 |
|---|---|---|
| 환경 간 | **동일** | **다르다** |
| 누가 만드나 | **빌드** | **배포** |
| 검증 대상 | **CI가 테스트** | 환경별 검토 |
| 바뀌는 빈도 | 릴리스마다 | **필요할 때** |

**[[../chapter-6-configuring-an-application-with-spring-boot/05-ordering-property-overrides|Ch6]]의 Twelve-Factor 3번(설정)이 파일 배치로 구현된 모습이다** — **코드와 설정의 완전한 분리.**

**남는 책임**(§6): **외부 파일도 배포 절차가 보존해야 한다.** **자동으로 따라가지 않는다.** JAR은 레지스트리에서 오지만 설정 파일은 **누군가 거기 두어야** 한다 → Q8.

## Q7. 이 절이 다음 절로 넘어가는 요구

> **"설정 오버라이드는 작은 조정에 그치지 않는다. 어떤 프로퍼티든 오버라이드할 수 있고, **서로 다른 설정으로 여러 애플리케이션 인스턴스를 지원**할 수도 있다."**

**구체적 요구**: **매니저가 트래픽 증가에 대응하려고 같은 애플리케이션의 인스턴스를 여러 개 돌리라고 요청한다.**

**파일 하나로는 안 되는 이유**:
```
/opt/app/application.properties  에 server.port=9000
        ↓
세 인스턴스를 띄우면 셋 다 9000 을 원한다 → 두 번째부터 기동 실패
```

**인스턴스가 여럿이면 각자 다른 포트가 필요하고, 각자 다른 설정이 필요하다.**

**그때 쓰는 것이 프로파일이고, [[04a-scaling-with-spring-boot]]의 주제다.**

**이 장의 흐름이 여기서 한 번 더 꺾인다**:
```
01~03:  하나를 어디든 옮길 수 있게 만든다
04:     옮긴 뒤 조정할 수 있게 만든다
04a~:   같은 것을 여러 벌 띄운다
```

## Q8. 설정 스위치 비유가 깨지는 지점

**비유**: 이 구조는 **"가전제품의 설정 스위치"**다. **제품을 뜯지 않고 겉의 스위치로 동작을 바꾼다.**

**깨지는 지점**: **스위치가 제품에 붙어 있다는 인상을 준다.**

> **여기서는 설정 파일이 아티팩트 밖에 따로 있어서, 제품을 옮길 때 스위치가 따라오지 않는다. 배포 절차가 둘을 함께 옮겨 주어야 한다.**

```
가전제품:  스위치가 본체에 있다 → 제품을 옮기면 설정도 따라간다
JAR + 파일: 둘이 별개 → 새 서버에 JAR 만 올리면 설정이 없다
```

**실무 사고**: 새 노드를 추가했는데 **설정 파일을 빠뜨려** 기본값(8080)으로 뜬다. 그리고 **아무 오류도 안 난다** — 정상 기동하고 **엉뚱한 포트**에 있을 뿐이다.

**방어**: **배포 스크립트·컨테이너 이미지 정의·Kubernetes ConfigMap** 등에 설정을 넣어 **함께 이동하는 단위**로 만든다. [[../chapter-6-configuring-an-application-with-spring-boot/04-setting-properties-with-environment-variables|Ch6]]이 "형상 관리에 반영하라"고 한 것과 같은 요구다.

**컨테이너에서는 이 문제가 더 뚜렷해진다**(§5) — **파일을 컨테이너 안에서 보이는 위치에 두어야** 하며, **그 함정이 [[04c-running-the-setup-with-docker-compose]]에 있다.**

**비유가 맞는 부분은 남는다** — **뜯지 않고 바꾼다**는 핵심. 깨지는 것은 **결합도**다.
