## Q1. JAR을 풀어 프로퍼티를 고치는 방법의 네 문제

```text
JAR 압축 해제 → 프로퍼티 파일 편집 → 다시 압축 → 배포
```

**책의 표현으로 "20년 전에나 통했을 꼼수"다.**

| 문제 | **결과** |
|---|---|
| **불변 아티팩트가 깨진다** | **배포된 것과 CI가 검증한 것이 다른 바이너리가 된다** |
| **서명·체크섬이 무효가 된다** | **통제된 파이프라인과 보안 릴리스 절차를 우회한다** |
| **기록이 남지 않는다** | **누가 무엇을 왜 고쳤는지 아무 데도 없다** |
| **다음 배포에 사라진다** | **새 JAR을 올리면 수정이 조용히 되돌아간다** |

**네 번째가 가장 배신감이 크다** — 고쳐서 문제가 해결됐는데, **다음 릴리스에 같은 문제가 재발**한다. 그리고 **그때는 원인이 더 안 보인다**(이미 고쳤다고 기억하므로).

**두 번째는 조직 차원의 문제다** — 릴리스 절차가 존재하는 이유 자체를 무력화한다. **"이 바이너리가 검증된 것"이라는 주장이 성립하지 않게 된다.**

> **책의 표현대로 "Spring 팀의 실전 경험 덕에 그럴 필요가 없다."**

**[[02-creating-profile-based-property-files]]에서 이미 "나쁜 해법 ②"로 나왔던 것이 여기서 정면으로 다뤄진다.**

## Q2. `SPRING_PROFILES_ACTIVE`가 대문자와 밑줄인 이유

**셸 쪽 사정이다.**

> **많은 셸에서 환경 변수 이름에 점(`.`)을 쓸 수 없다.** `spring.profiles.active=test` 같은 형태는 **유효한 변수 이름이 아니다.**

**그렇다고 Spring이 점을 포기하면 프로퍼티 파일 표기가 망가진다.**

```
Spring 이 원하는 것:  spring.profiles.active   (계층을 점으로)
셸이 허용하는 것:      SPRING_PROFILES_ACTIVE   (영숫자와 밑줄)
        └────────────┬────────────┘
          양쪽을 잇는 규칙이 필요하다 → 완화된 바인딩
```

**즉 Spring이 이상한 이름을 요구하는 것이 아니라, 각 매체의 제약을 존중한 결과다.**

**대문자인 것도 셸 관례다** — 환경 변수는 관례적으로 대문자를 쓴다(지역 셸 변수와 구분하기 위해).

**이 규칙 덕분에 표기가 각 매체의 제약을 따르면서도 의미는 하나로 유지된다.**

## Q3. 완화된 바인딩이 없다면

**같은 설정을 매체마다 다른 키로 취급해야 한다.**

```
spring.profiles.active     프로퍼티 파일
SPRING_PROFILES_ACTIVE     환경 변수
spring-profiles-active     kebab-case
--spring.profiles.active   명령줄 인자
        └──────┬──────┘
           전부 같은 키
```

**없으면 불가능해지는 것들**:
- **환경 변수로 프로퍼티를 덮는 것 자체** — 점을 못 쓰므로 애초에 표현이 안 된다
- **같은 설정을 매체를 바꿔 지정하는 것** — 개발은 파일, 운영은 환경 변수로 가는 흐름이 깨진다
- **Q1의 대안이 사라진다** — 환경 변수가 안 되면 **JAR을 여는 것 말고 방법이 없어진다**

> **핵심은 이것이 프로파일 전용이 아니라는 것이다.** 어떤 프로퍼티든 이 방식으로 덮을 수 있다.

```
server.port         →  SERVER_PORT
app.config.header   →  APP_CONFIG_HEADER
```

**[[../../part-2-creating-an-application-with-spring-boot/chapter-4-securing-an-application-with-spring-boot/08b-adding-oauth-client-to-a-spring-boot-project|Ch4의 `clientId` / `client-id`]]도 같은 규칙이 작동한 예다.**

**주의할 경계**(§6): **키에 하이픈이나 대문자가 섞여 있으면**(`app.config.someValue`) **환경 변수 이름 규칙과 정확히 맞추기 까다롭다.** 매핑이 완전히 자유롭지는 않다.

## Q4. `VAR=x cmd`와 `export VAR=x`의 차이

```bash
SPRING_PROFILES_ACTIVE=alternate ./mvnw spring-boot:run    # 이 명령에만
export SPRING_PROFILES_ACTIVE=test                          # 셸 세션 전체
```

| | **적용 범위** | 셸로 돌아오면 |
|---|---|---|
| `VAR=x cmd` | **그 한 번의 실행에만** | **변수가 없다** |
| `export VAR=x` | **그 셸이 살아 있는 동안 이후 모든 명령** | 남아 있다 |

**실무 혼란**: **`export`는 잊어버리기 쉽다.**

> **30분 뒤에 "왜 테스트 계정으로 뜨지?" 하며 헤매는 상황이 여기서 나온다.**

**왜 진단이 어려운가**:
- **코드에도 파일에도 아무 흔적이 없다** — grep으로 못 찾는다
- **다른 터미널에서는 재현되지 않는다** — "내 컴퓨터에서는 되는데"의 반대 버전
- **명령줄에도 안 보인다** — 30분 전에 친 `export`는 스크롤 위로 사라졌다

**확인하는 법**: `env | grep SPRING` 또는 `echo $SPRING_PROFILES_ACTIVE`.

**책은 셸별 세부를 각자 문서로 넘긴다** — 알아야 할 것은 **범위가 다르다는 사실 자체**다.

## Q5. `test,alternate`를 켰을 때 사용자가 3명인 이유

**리스트 교체 규칙 때문이다.**

```
application.properties       alice · bob · admin
application-test.properties  test1 · test2 · test3      ← 앞의 것을 교체
application-alternate.yaml   yaml1 · yaml2 · yaml3      ← 다시 교체
                                    ↓
                             최종: yaml1 · yaml2 · yaml3
```

**두 규칙이 겹쳐 작동한다**:

**① 적용 순서 — 왼쪽에서 오른쪽으로.** `alternate`가 마지막이므로 **새 프로퍼티를 얹고 중복은 덮는다.**

**② 리스트 교체** — [[02-creating-profile-based-property-files]]의 그 규칙. **`test`의 세 명과 `alternate`의 세 명이 합쳐져 여섯이 되지 않는다.**

> **"둘 다 켰으니 둘 다 들어가겠지"가 스칼라 값에는 부분적으로 맞지만**(각각 다른 키라면 둘 다 살아남는다) **같은 리스트에는 틀리다.**

**구분해야 할 두 경우**:
```
서로 다른 키:   test 가 server.port, alternate 가 logging.level → 둘 다 산다
같은 키(리스트): 둘 다 app.config.users                        → 마지막 것만 산다
```

**이 결과가 직관과 어긋나기 쉬운 이유**: **프로파일을 "켠다"는 표현이 누적을 연상시킨다.** 실제로는 **프로퍼티 출처를 순서대로 얹는 것**이고, 같은 키는 나중이 이긴다.

## Q6. 환경 변수보다 우선순위가 높은 것

**최소 세 가지**:
1. **시스템 프로퍼티**(`-D`로 JVM에 넘기는 값)
2. **`SPRING_APPLICATION_JSON`**
3. **명령줄 인자**(`--spring.profiles.active=...`)

> **"환경 변수가 가장 우선한다"는 오해가 흔하다. 아니다.**

**실무적 귀결**: 환경 변수로 값을 넣었는데 **안 먹으면** 위 셋을 의심한다. 특히 **컨테이너 이미지의 `ENTRYPOINT`에 `-D`가 박혀 있는 경우**가 흔하다 — 환경 변수를 아무리 바꿔도 이기지 못한다.

**[[02-creating-profile-based-property-files]]이 짚지 않은 지점이 여기서 회수된다** — 그 절은 `-D`와 환경 변수를 **동등한 선택지**로 제시했지만, **둘을 동시에 지정하면 `-D`가 이긴다.**

**전체 순서는 [[05-ordering-property-overrides]]에 있다.**

## Q7. 배송 지시 스티커 비유가 깨지는 지점

**비유**: 환경 변수 오버라이드는 **"봉인된 상자를 뜯지 않고 겉에 배송 지시를 붙이는 것"**에 가깝다. **상자는 그대로고 취급 방식만 달라진다.**

**깨지는 지점**: **지시 스티커가 배송이 끝나면 사라진다는 점을 흐린다.**

> **실제로 환경 변수는 그 실행에만 남고 아무 기록도 남기지 않는다. 다음 배포에서 같은 지시가 필요하면 다시 붙여야 하고, 그걸 아는 사람이 자리를 비우면 아무도 모른다.**

```
실제 스티커:  상자에 붙어 있다 → 다음 사람도 본다
환경 변수:    프로세스에만 있다 → 프로세스가 죽으면 사라진다
```

**Q1의 문제와 같은 모양이 남아 있다** — JAR 편집도 **기록이 남지 않는** 것이 문제였는데, **명령줄 환경 변수도 아무 데도 남지 않는다.**

**차이는 무엇이 훼손되는가다**:
```
JAR 편집:   아티팩트가 훼손된다 + 기록 없음   ← 둘 다 나쁘다
환경 변수:  아티팩트는 그대로 + 기록 없음     ← 절반만 해결
```

**그래서 나머지 절반을 푸는 방법이 따로 필요하다**:
- **컨테이너 정의 / Kubernetes 매니페스트 / systemd unit**에 적어 **형상 관리에 넣는다**
- 또는 [[02-creating-profile-based-property-files]]의 **`spring.config.additional-location`**으로 **파일**을 공급한다 — 파일은 남는다

> **긴급 조치는 기록해야 한다.** [[05-ordering-property-overrides]]가 이 위험을 Note로 다시 경고한다.

**비유가 맞는 부분은 남는다** — **상자를 뜯지 않는다**는 핵심. 깨지는 것은 **지시의 수명**이다.
