## Q1. 프로퍼티 파일이 하나뿐일 때의 세 가지 나쁜 해법

| 해법 | **문제** |
|---|---|
| **① 환경마다 다른 JAR을 빌드한다** | **배포한 것과 테스트한 것이 다른 바이너리가 된다.** 불변 아티팩트 원칙이 깨진다 |
| **② 배포할 때 JAR을 열어 프로퍼티를 고친다** | [[04-setting-properties-with-environment-variables]]에서 **책이 강하게 금지**하는 방법 |
| **③ 코드에 `if (env == "test")`를 넣는다** | **환경 목록이 코드에 박혀** 새 환경을 추가할 때마다 **재빌드** |

**①이 가장 미묘하게 위험하다** — 테스트를 통과한 바이너리와 배포된 바이너리가 **다른 물건**이므로, 테스트가 무엇을 보증했는지 말할 수 없게 된다.

**③은 [[01-creating-custom-properties]]가 이미 푼 문제의 재발이다** — 값을 코드 밖으로 뺐는데 **환경 이름이 다시 코드로 들어온다.**

> **프로파일이 네 번째 답이다** — "이 설정 묶음은 이 상황에서만 쓴다"고 **이름 붙이는 장치.**

## Q2. 프로파일 파일을 만드는 데 필요한 것

**파일 이름뿐이다. 애노테이션도 등록도 필요 없다.**

```
application-test.properties
           └┬─┘
     이 접미사가 이 파일을 test 프로파일과 묶는다
```

**[[01-creating-custom-properties]]와 대비된다** — 거기서는 **`@EnableConfigurationProperties`가 없으면 빈이 안 만들어졌다.** 여기서는 **규약만으로 동작한다.**

**왜 그럴 수 있나**: 설정 타입은 **자바 타입**이므로 컨테이너에 등록해야 하지만, 프로퍼티 파일은 **Boot가 기동 시 정해진 이름 패턴으로 찾는 자원**이다. **찾는 쪽이 이미 규칙을 안다.**

**활성화하는 세 가지 방법**:
```bash
-Dspring.profiles.active=test          # JVM 시스템 프로퍼티
export SPRING_PROFILES_ACTIVE=test     # 환경 변수 (Unix)
# IDE 실행 구성의 Active profiles 필드 (쉼표로 여러 개)
```

> **셋 다 애플리케이션 바깥에서 정한다.** 코드에도, JAR 안에도 "지금 어느 프로파일인가"가 적혀 있지 않다. **같은 아티팩트가 실행 시점의 지시에 따라 다르게 동작한다.**

**책이 짚지 않는 것**: `-D`와 환경 변수를 **동등한 선택지**로 제시하지만, [[05-ordering-property-overrides]]의 우선순위 목록을 보면 **시스템 프로퍼티가 환경 변수보다 높다.** **둘을 동시에 지정하면 `-D`가 이긴다.**

## Q3. `ROLE_NOTHING` 계정이 존재하는 이유

**아무 권한도 없는 사용자로 "막히는 경로"를 시험하기 위한 계정이다.**

**[[../../part-2-creating-an-application-with-spring-boot/chapter-4-securing-an-application-with-spring-boot/05-securing-web-routes-and-http-verbs|Ch4의 인가 규칙]]에는 `ROLE_NOTHING`이 없다.** 그것이 핵심이다 — **어떤 규칙에도 걸리지 않는 역할**이라야 "거부된다"를 검증할 수 있다.

```
test1 : ROLE_NOTHING  → 막혀야 한다        (부정 경로)
test2 : ROLE_USER     → 일반 경로가 열린다  (긍정 경로)
test3 : ROLE_ADMIN    → 관리 경로도 열린다  (긍정 경로 · 다른 역할)
```

> **성공 경로만이 아니라 실패 경로를 시험하려면 이런 계정이 필요하다.**

**[[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/08-testing-security-policies|Ch5의 보안 테스트]]가 코드로 한 일을, 여기서는 계정 데이터로 한다** — 거기서는 `@WithMockUser`를 빼서 미인증을 만들었고, 여기서는 **권한이 없는 실제 계정**을 둔다. 테스트 팀이 **브라우저로 직접** 부정 경로를 밟아 볼 수 있게 하는 것이다.

**세 계정의 역할이 서로 다르다는 점도 설계다** — 한 계정으로는 (주체 × 경로) 격자를 못 채운다.

## Q4. "가산적"이라는 성질이 프로파일 파일의 내용을 바꾸는 방식

**프로파일 파일에는 달라지는 것만 적으면 된다.**

> **프로파일 파일은 기본 파일을 대체하지 않는다.** `test` 프로파일을 켜면 `application-test.properties`가 **추가로** 읽힌다.

```
application.properties          application-test.properties
  header  · intro · users         header · intro · users
  server.port=8080                (없음)
        └──────────────┬──────────────┘
                  합쳐진 환경
  header/intro/users → test 파일 값 (나중이 이김)
  server.port=8080   → 기본 파일 값 (test에 없으므로 살아남음)
```

**`server.port`가 요점이다** — **프로파일 파일에 없는 키는 기본 파일의 값이 그대로 남는다.**

**대체 방식이었다면**: 프로파일 파일에 **전체 설정을 복사**해야 한다. 그러면
- 기본 파일을 고칠 때마다 **모든 프로파일 파일을 함께** 고쳐야 하고
- **환경 간 차이가 무엇인지 읽을 수 없게** 된다

**가산적이므로 프로파일 파일 자체가 "이 환경에서 무엇이 다른가"의 문서가 된다.**

**단, 예외가 하나 있다** → Q5.

## Q5. 리스트가 병합되지 않는 이유

**병합 규칙을 정할 방법이 없기 때문이다.**

**두 리스트를 합친다면**:
- **순서는?** 기본 것이 앞인가 프로파일 것이 앞인가
- **중복은 어떻게 판정하나?** `username`이 같으면 같은 사용자인가
- **같은 인덱스를 겹쳐 쓰나?** `users[0]`이 양쪽에 있으면 병합인가 교체인가

> **답이 하나로 정해지지 않는다. 그래서 Spring Boot는 "합치지 않는다"는 단순하고 예측 가능한 규칙을 골랐다.**

| 상황 | **스칼라 (`header`)** | **리스트 (`users`)** |
|---|---|---|
| 기본에만 있음 | 기본값 | 기본 리스트 |
| 프로파일에만 있음 | 프로파일 값 | 프로파일 리스트 |
| 양쪽에 있음 | 프로파일 값 | **프로파일 리스트로 통째 교체** |
| **기본 3개 + 프로파일 1개** | — | **최종 1개** (4개가 아니다) |

**실무 사고**: **기본 파일에 사용자 3명을 두고 테스트 프로파일에 1명만 추가했는데 기본 3명이 전부 사라진다.**

**설계 판단으로 읽으면**: **예측 가능한 규칙 하나**가 **상황마다 다르게 똑똑한 규칙 여럿**보다 낫다는 선택이다. 후자는 **언제 어떻게 동작할지 외워야 하고**, 외운 것이 틀렸을 때 조용히 잘못된 결과를 낸다.

## Q6. 개발을 기본값으로 두는 것이 안전한 이유

| 전략 | 프로파일 없이 실행하면 | 평가 |
|---|---|---|
| **개발을 기본으로** | **개발 환경에 붙는다** | **더 안전하고 흔한 방법** |
| 운영을 기본으로 | **운영에 붙는다** | 위험 |

**막는 사고**: **프로파일 지정을 깜빡한 실행이 의도치 않게 운영 시스템에 연결된다.**

> **로컬에서 테스트를 돌렸는데 운영 DB를 건드리는 상황이 여기서 나온다.**

**설계 원칙**: **실수했을 때 어느 쪽으로 넘어지는가.**

```
개발이 기본  → 잊으면 "개발에 붙는다"       → 아무 일도 안 일어난다
운영이 기본  → 잊으면 "운영에 붙는다"       → 되돌릴 수 없는 일이 일어난다
```

**비대칭이 핵심이다** — 잊는 일은 **양쪽 모두 일어나지만**, 그 대가가 전혀 다르다.

**[[../../part-2-creating-an-application-with-spring-boot/chapter-4-securing-an-application-with-spring-boot/01-spring-security-filter-chain-foundations|Ch4]]에서 Spring Security의 기본값이 "전부 잠김"이었던 것과 같은 판단이다** — **안전한 쪽을 기본값으로.**

## Q7. `spring.config.location`과 `additional-location`

| 프로퍼티 | **하는 일** | **결과** |
|---|---|---|
| `spring.config.location` | **기본 탐색 위치를 대체한다** | **classpath의 `application.properties`가 더 이상 읽히지 않는다** |
| **`spring.config.additional-location`** | 기본 위치에 **더한다** | **기본값은 살아 있고 외부 값이 덮는다** |

> **책의 권고**: 대부분의 경우 `additional-location`이나 `spring.config.import`를 쓰라. **기본 탐색 동작을 유지한 채 필요한 위치만 더하는 쪽이 안전하다.**

**`location`을 쓰면 무엇이 깨지나**: 기본 파일이 **통째로 사라진다.** Q4의 "달라지는 것만 적는다"가 성립하지 않게 되고, **외부 파일에 모든 설정을 복사**해야 한다. 하나라도 빠지면 **기동 실패이거나, 더 나쁘게는 기본값으로 조용히 동작**한다.

**왜 외부 공급이 필요한가 — 운영 설정은 아티팩트 안에 담기지 않는다.**

`application-production.properties`를 JAR에 넣으면 그 안에 **운영 DB 주소와 자격 증명**이 들어간다. **그 JAR은 형상 관리에 들어가고, 개발자 노트북에 복사되고, CI 로그에 남는다.**

```bash
-Dspring.config.additional-location=file:/opt/app/config/
# 또는
export SPRING_CONFIG_ADDITIONAL_LOCATION=file:/opt/app/config/
```

**같은 원리가 클라우드에서도 그대로다** — AWS든 Azure든 Tanzu든, **코드를 고치는 게 아니라 환경마다 알맞은 설정을 공급해** 애플리케이션을 적응시킨다.

## Q8. 투명 필름 비유가 깨지는 지점

**비유**: 프로파일은 **기본 도면 위에 올리는 투명 필름**이다. **필름에 그린 선만 바뀌고 나머지는 원래 도면이 비쳐 보인다.**

**깨지는 지점**: **리스트가 통째로 교체된다는 예외를 담지 못한다.**

> **필름 비유대로라면 사용자 목록도 겹쳐 보여야 하는데, 실제로는 필름에 사용자 칸이 하나라도 그려져 있으면 아래 도면의 사용자 칸 전체가 가려진다.**

```
스칼라 (server.port):  필름에 없다 → 아래가 비쳐 보인다   ✅ 비유대로
리스트 (users):        필름에 1명  → 아래 3명이 전부 가려진다  ❌ 비유가 안 맞는다
```

**비유가 맞는 부분은 남는다** — **덧칠이지 대체가 아니다**(Q4)라는 핵심 통찰. 깨지는 것은 **덧칠의 단위**다. 필름은 **선 단위**로 겹치지만 Spring은 **키 단위**로 겹치고, **리스트는 그 키 하나가 통째로 값 전체**다.

**그래서 정확한 비유로 고치면**: 필름이 아니라 **칸이 있는 서식지를 겹치는 것**에 가깝다. **칸을 비워 두면 아래가 보이고, 칸에 뭐라도 쓰면 그 칸 전체가 새 내용이 된다.** `users`는 **여러 줄로 보이지만 칸 하나**다.
