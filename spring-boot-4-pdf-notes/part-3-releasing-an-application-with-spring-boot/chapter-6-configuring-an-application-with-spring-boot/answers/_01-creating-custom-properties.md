## Q1. `@Value`로 값을 하나씩 꺼내는 방식의 세 문제

| 문제 | **결과** |
|---|---|
| **키가 문자열이다** | **오타를 컴파일러가 못 잡는다. 값을 쓰는 순간 터진다** |
| **관련된 값들이 흩어진다** | **"이 앱이 가진 설정이 뭐지?"에 답하려면 코드 전체를 grep 해야 한다** |
| **복합 구조를 못 담는다** | **`List<UserAccount>` 같은 것을 `@Value` 하나로 받을 수 없다** |

**첫 번째가 실무에서 가장 아프다** — 실패가 **기동 시점이 아니라 그 값을 처음 읽는 순간**에 온다. 잘 안 타는 분기에 있으면 **운영에서 처음 터진다.**

> **설정을 제대로 하려면 값 하나가 아니라 설정 한 벌을 다룰 수 있어야 한다.**

**`@ConfigurationProperties`가 각각을 어떻게 뒤집는가**:
- 키가 **필드 이름**이 된다 → 오타는 컴파일 오류
- 설정이 **타입 하나**에 모인다 → 그 record를 열면 전부 보인다
- **중첩·리스트·커스텀 타입**을 받는다 → `List<UserAccount>`가 가능해진다

## Q2. 프로퍼티 키를 결정하는 두 요소

**접두사와 필드 이름뿐이다.**

```java
@ConfigurationProperties("app.config")
public record AppConfig(String header, String intro, List<UserAccount> users) {}
//                      └──────┬─────┘
//   app.config  +  header  →  app.config.header
```

> **`AppConfig`라는 이름은 아무 의미가 없다. 책도 "무슨 이름을 붙이든 상관없다"고 못 박는다.**

**클래스 이름이 무관한 이유**: 키는 **접두사에서 시작해 필드 이름으로 이어지는 경로**다. 클래스는 **그 경로들을 담는 그릇**일 뿐 경로의 일부가 아니다. 그래서 리팩터링으로 클래스 이름을 바꿔도 프로퍼티 파일은 안 건드려도 된다 — **반대로 필드 이름을 바꾸면 프로퍼티 파일도 바꿔야 한다.**

**여기서 얻는 것이 타입 안전 바인딩이다** — `header`가 `String`, `users`가 `List<UserAccount>`라고 선언해 두면 **값이 그 모양이 아닐 때 기동 시점에 실패한다.** Q1의 첫 번째 문제가 여기서 해결된다.

## Q3. record에 setter가 없는데 값이 채워지는 메커니즘

**생성자 바인딩이다.**

**record는 컴포넌트와 일치하는 정규 생성자를 갖고, Spring Boot는 바인딩할 때 그것을 자동으로 쓴다.**

```
프로퍼티 3개 읽기 → AppConfig(header, intro, users) 생성자 호출 → 완성된 객체
```

**그래서 `@ConstructorBinding`이 필요 없다** — 이 애노테이션은 `@ConfigurationProperties` 타입에 **생성자가 여러 개일 때만** 어느 것을 쓸지 지정하는 용도다.

**생성자 바인딩이 주는 것은 편의가 아니라 성질이다**:

| 성질 | 왜 좋은가 |
|---|---|
| **불변** | **기동 후 아무도 설정을 바꿀 수 없다.** 런타임 중 값이 달라지는 사고가 없다 |
| **완전한 상태** | **객체가 만들어졌다면 모든 필드가 채워진 것이다.** 반쯤 채워진 중간 상태가 없다 |
| **`final` 가능** | **스레드 안전성을 공짜로** 얻는다 |

**두 번째가 setter 방식과 결정적으로 다르다** — setter 바인딩은 **일부만 채워진 객체가 잠시 존재**한다. 그 사이에 누가 읽으면 `null`을 본다. 생성자 바인딩에는 그 창이 없다.

**대가는 §6에 있다** — **런타임에 바뀌어야 하는 값은 이 방식이 맞지 않다.**

## Q4. `@EnableConfigurationProperties`를 어디에 붙일 것인가

| 상황 | **권장 위치** | 이유 |
|---|---|---|
| **특정 빈 하나만 쓰는 설정** | **그 빈 정의에** | **"이 빈은 설정 한 벌을 동반한다"가 코드에 드러난다** |
| **여러 빈이 쓰는 앱 전역 설정** | **진입점 클래스에** | **소유자가 특정되지 않으므로** 최상위에 둔다 |

> **기술적으로는 아무 데나 붙여도 된다** — 컴포넌트 스캔에 잡히는 Spring 빈이기만 하면 컨텍스트에 추가된다.

**즉 판단 기준은 동작이 아니라 의도 표현이다.** "누가 이 설정의 주인인가"를 코드 배치로 말하는 것.

**이 장의 `AppConfig`가 진입점에 붙은 이유**: `header`/`intro`는 `HomeController`가 쓰고 `users`는 보안 쪽이 쓸 것이므로 **주인이 하나가 아니다.**

**대안**: **`@ConfigurationPropertiesScan`**을 쓰면 타입을 하나하나 나열하지 않아도 된다. **설정 타입이 늘어날수록 유리하다** — 새 설정 타입을 만들 때마다 진입점을 고치지 않아도 된다.

**그리고 등록은 선택이 아니다** — **프로퍼티 파일에 값을 적었다고 애플리케이션이 쓸 수 있는 것은 아니다.** 빈이 없으면 주입할 것이 없다.

## Q5. `.properties`에서 리스트를 인덱스로 펴야 하는 근본 이유

**`.properties` 형식에는 계층이 없기 때문이다.**

> **한 줄이 키 하나와 값 하나뿐이다.**

```properties
app.config.users[0].username=alice
app.config.users[0].authorities[0]=ROLE_USER
```

**그래서 "리스트의 0번째 항목의 username"을 표현하려면 그 경로를 키 이름 안에 전부 적어야 한다.**

**형식이 담을 수 있는 것**: 평평한 `key=value` 쌍.
**표현해야 하는 것**: 객체 안의 리스트 안의 객체 안의 리스트.

**해법은 구조를 키 문자열로 인코딩하는 것**이고, 그것이 `[0]` 표기다.

**대가**:
- **줄이 급격히 길어진다** — 사용자 3명에 **11줄**
- **인덱스를 손으로 관리해야 한다** — 중간에 하나 빼면 번호를 다시 매겨야 한다
- **`authorities[0]`처럼 중첩 리스트**가 나오면 더 나빠진다

> **이 투박함이 [[03-switching-to-yaml-and-metadata]]로 넘어가는 동기가 된다.**

## Q6. `String → GrantedAuthority` 변환에 컨버터가 필요한 이유

**어떤 구현체를 만들어야 하는지 Spring이 알 도리가 없기 때문이다.**

```text
"ROLE_USER"  --???-->  GrantedAuthority
                        ↑ 인터페이스다
```

**프로퍼티 파일은 문자열 key-value 쌍**이고, `UserAccount` 안의 `authorities`는 `List<GrantedAuthority>`인데 **`GrantedAuthority`는 인터페이스**다.

**`String → int`, `String → boolean` 같은 흔한 변환은 Spring이 내장 컨버터로 처리한다.** 그런데 인터페이스는 **인스턴스를 만들 수 없다** — 구현체를 골라야 하고, 그 선택은 자명하지 않다.

**그래서 직접 만들어 등록한다**:

```java
@Bean
@ConfigurationPropertiesBinding
Converter<String, GrantedAuthority> converter() {
    return new Converter<String, GrantedAuthority>() {
         @Override public GrantedAuthority convert(String source) {
             return new SimpleGrantedAuthority(source);
         }
    };
}
```

| 요소 | 하는 일 |
|---|---|
| `@Bean` | **컨텍스트에 등록해야 발견된다** |
| **`@ConfigurationPropertiesBinding`** | 일반 변환이 아니라 **프로퍼티 바인딩용**임을 알린다 |
| `convert(String)` | 문자열을 `SimpleGrantedAuthority`로 감싼다 |

**중요한 단서**: **바인딩은 애플리케이션 생명주기의 아주 이른 시점에 일어난다.** 그래서 **이 컨버터에 다른 Spring 빈을 주입하면 안 된다** — **아직 만들어지지 않았을 수 있다.** 자기 완결적으로 유지해야 한다.

## Q7. 메서드 참조로 줄이면 깨지는 이유

**핵심은 "선언으로 박혀 있는가"다.**

```java
return source -> new SimpleGrantedAuthority(source);   // 람다        → 안 된다
return SimpleGrantedAuthority::new;                    // 메서드 참조 → 안 된다
```

**원인은 자바의 타입 소거다.**

| | **익명 클래스** | **메서드 참조 / 람다** |
|---|---|---|
| 클래스 파일에 | **`Converter<String, GrantedAuthority>`를 구현한다고 적혀 있다** | **선언된 타입 인자가 없다** |
| Spring이 | **읽어낸다** | **무엇을 무엇으로 바꾸는지 모른다** |
| 결과 | 컨버터가 선택된다 | **컨버터가 선택되지 않아 바인딩 실패** |

**즉 타입 소거가 제네릭을 지우는 것은 맞지만, 지워지지 않는 자리가 있다** — **상위 타입을 구현/상속한다는 선언**은 클래스 파일에 남는다. 익명 클래스는 그 자리를 쓰고, 람다는 그 자리가 없다.

**가장 나쁜 점**: **컴파일은 통과하고 런타임에 바인딩이 실패한다.** 그리고 **IDE가 그렇게 줄이라고 권한다.**

## Q8. `GrantedAuthorityCnv`가 메서드를 하나도 추가하지 않는데도 문제를 푸는 이유

**타입 인자를 선언에 박아 둔 이름을 만들어 주기 때문이다.**

```java
interface GrantedAuthorityCnv extends Converter<String, GrantedAuthority> {}

@Bean
@ConfigurationPropertiesBinding
GrantedAuthorityCnv converter() {
    return SimpleGrantedAuthority::new;   // 이제 된다
}
```

**`GrantedAuthorityCnv`가 하는 일은 `Converter<String, GrantedAuthority>`라는 조합에 이름을 붙이는 것뿐이다.**

**그런데 그 이름이 인터페이스 선언이므로 타입 인자가 클래스 파일에 남는다.**

```
Q7의 문제:  람다 객체에 타입 인자가 없다
이 해법:    타입 인자를 인터페이스 선언 쪽으로 옮겼다
            → 람다는 여전히 타입 인자가 없지만,
              빈의 반환 타입 GrantedAuthorityCnv 가 그것을 갖고 있다
```

**메서드가 없어도 되는 이유**: Spring이 필요로 하는 것은 **동작이 아니라 타입 정보**다. `Converter`의 `convert` 메서드는 이미 상위 인터페이스에 있고, 추가할 것이 없다.

**책의 평가가 솔직하다** — **코드량은 사실상 같고, 같은 정보를 어디에 두느냐의 차이**일 뿐이다. **빈 정의 안에 다 펼쳐 두는 게 읽기 쉬운지, 별도 인터페이스로 빼는 게 나은지는 취향이다.**

## Q9. 봉인되는 서류 비유가 깨지는 지점

**비유**: `@ConfigurationProperties`는 **서식 있는 신청서**다. **칸마다 무엇을 적어야 하는지(타입)가 정해져 있어서, 잘못 적으면 접수 단계에서 반려된다.**

**깨지는 지점**: **이 비유는 신청서를 제출한 뒤에는 고칠 수 없다는 점을 흐린다.**

> **실제로 이 객체는 기동 시점에 한 번 채워지고 그대로 굳는다. 접수 후 정정이 가능한 서류가 아니라, 봉인되는 서류에 가깝다.**

**Q3의 불변성이 여기서 대가로 돌아온다**:
```
장점:  런타임 중 값이 달라지는 사고가 없다
대가:  런타임에 값을 바꿔야 하는 요구를 이 방식으로 못 푼다
       → 바꾸려면 재기동해야 한다
```

**실무적으로 어떤 경우가 걸리나**: 기능 토글, 임계값 튜닝, 로그 레벨 — **운영 중에 조정하고 싶은 것들.** 이런 것은 Spring Cloud Config의 `@RefreshScope`나 별도 설정 저장소가 필요하다.

**이 장이 그 대신 제공하는 것은 다른 층위의 유연성이다** — **재빌드 없이 바꿀 수 있다.** [[02-creating-profile-based-property-files]]의 프로파일, [[04-setting-properties-with-environment-variables]]의 환경 변수가 **배포 시점에** 값을 갈아 끼운다. **런타임 갱신이 아니라 배포 단위 갱신**이다.
