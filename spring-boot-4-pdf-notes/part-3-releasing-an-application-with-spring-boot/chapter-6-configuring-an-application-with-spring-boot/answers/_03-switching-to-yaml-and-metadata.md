## Q1. `.properties`가 리스트에 인덱스를 요구하는 근본 이유

**`.properties`에는 계층이 없기 때문이다.**

> **한 줄이 키 하나와 값 하나뿐이므로, 구조를 표현하려면 그 구조를 키 이름 안에 문자열로 인코딩할 수밖에 없다.**

```properties
app.config.users[0].authorities[0]=ROLE_USER
└───┬────┘└─┬─┘└┬┘ └────┬────┘└┬┘
  접두사   필드 인덱스   필드   인덱스
       ↑ 이 전부가 하나의 "키 문자열"이다
```

**인덱스 표기법이 바로 그 인코딩이다.**

**대가**:
- **`app.config.users`가 아홉 번 반복된다**
- **`[0]`, `[1]`, `[2]`를 사람이 관리한다** — 중간에 하나 끼워 넣으려면 **아래 인덱스를 전부 밀어야** 한다

**YAML이 푸는 지점**: 형식 자체가 계층을 갖는다 → **접두사를 한 번만 쓰고, 인덱스를 하이픈이 대신한다.**

> **순서 관리를 사람에서 형식으로 옮긴 것**이다.

## Q2. YAML이 짧아지는 이유와 그 대가가 같은 성질에서 나온다

**둘 다 "들여쓰기가 곧 구조"이기 때문이다.**

| 요소 | **짧아지는 이유** | **대가** |
|---|---|---|
| 들여쓰기가 계층을 표현한다 | **접두사를 반복하지 않아도 된다** | **공백 하나가 구조를 바꾼다** |
| 위치가 소속을 결정한다 | **어디에 속하는지 눈에 보인다** | **한 줄만 봐서는 전체 키를 모른다** |

```
.properties:  한 줄이 자기 완결적       → 길지만 각 줄이 독립
YAML:         한 줄이 위쪽에 의존       → 짧지만 각 줄이 문맥에 매인다
```

> **원인은 장점과 같은 것이다** — 들여쓰기 유의.

| | `.properties` | **YAML** |
|---|---|---|
| 한 줄의 의미 | **자기 완결적** | 위쪽 들여쓰기에 의존 |
| 공백 실수의 영향 | 없다 | **구조가 바뀐다** |
| 200줄에서 오류 찾기 | 그 줄만 보면 된다 | **위로 거슬러 올라가야 한다** |
| 병합 충돌 | 줄 단위로 명확 | **들여쓰기가 어긋나기 쉽다** |

**그래서 우열이 아니라 트레이드오프다** — **짧고 중첩이 깊은 설정에는 YAML, 평평하고 긴 설정에는 `.properties`.**

**섞어 쓸 수도 있다** — Spring Boot는 `application.properties`와 `application.yaml`을 **둘 다 읽는다.**

## Q3. 300줄 YAML에서 40번째 줄의 들여쓰기가 어긋나면

**그 아래 260줄이 통째로 엉뚱한 부모 밑으로 들어간다.**

> **그런데 오류는 저 아래 어딘가에서 "알 수 없는 프로퍼티" 형태로 보고된다.**

```
40행:  들여쓰기 두 칸 어긋남      ← 진짜 원인
  │
  └─▶ 41~300행이 다른 부모 밑으로
        │
        └─▶ 280행쯤에서 "app.config.foo 를 바인딩할 수 없다"  ← 보고되는 위치
```

**진단이 어려운 이유**: **원인과 증상의 거리가 멀다.** 그리고 **증상이 여러 개**로 나온다 — 260줄이 전부 잘못됐으므로 오류 메시지가 쏟아지고, **어느 것이 첫 원인인지 알 수 없다.**

**`.properties`였다면**: 잘못된 줄 **하나만** 문제가 된다. **오류 메시지의 키가 곧 잘못된 줄**이다.

**책의 경고 그대로** — **큰 파일에서 위쪽에 생긴 오류는 찾기 어렵다.**

**실무적 방어**: 파일을 **나눈다**(프로파일별·관심사별), 에디터의 **YAML 린터**를 켠다, **탭을 금지**하고 공백만 쓴다.

**추가 함정**: **YAML의 암묵적 타입 변환** — `on`/`off`/`yes`/`no`가 **불리언**으로, 앞자리 0이 붙은 숫자가 다르게 해석된다. **문자열임을 확실히 하려면 따옴표**를 쓴다.

## Q4. IDE 코드 완성이 동작하는 메커니즘

**IDE가 Spring Boot의 소스를 읽는 게 아니라, classpath의 메타데이터 JSON을 읽는다.**

```
Spring Boot 각 모듈이 자기 설정 키들을
META-INF/spring-configuration-metadata.json 에 실어 배포
        ↓
IDE 가 classpath 에서 그 파일들을 모은다
        ↓
"server." 까지 치면 server.port 가 뜬다
```

**설정 메타데이터**에 담기는 것: **설정 키의 이름·타입·설명.**

**부수 효과**: 완성 목록에는 **표준 key/value 표기**로 뜨지만, **YAML 파일에서 고르면 YAML 형식으로 자동 변환돼 삽입된다.**

**이 메커니즘의 중요한 성질**: **내 프로퍼티와 프레임워크 프로퍼티가 같은 메커니즘 위에 있다.** 그래서 **내가 만든 `@ConfigurationProperties` 타입도 같은 방식으로 완성 목록에 띄울 수 있다**(Q5) — 특별 대우가 아니라 **같은 파일 형식에 참여**하는 것이다.

## Q5. `spring-boot-configuration-processor`가 `optional`인 이유

**컴파일할 때만 필요하기 때문이다.**

```
AppConfig record  ──▶  컴파일 시점 애노테이션 프로세서  ──▶  metadata.json
                                                              │
                                                              ▼
                                                        IDE 가 읽는다
```

> **생성된 JSON은 JAR에 들어가지만 프로세서 자체는 런타임에 아무 일도 하지 않는다.**

**`<optional>true</optional>`의 효과**: **이 프로젝트를 의존하는 다른 프로젝트에 전이되지 않는다.**

**왜 전이를 막아야 하나**: 내 라이브러리를 쓰는 쪽은 **내 메타데이터 JSON은 필요하지만 그것을 만든 프로세서는 필요 없다.** 전이시키면 **남의 빌드에 불필요한 애노테이션 프로세서**를 강제하게 된다.

**같은 원리를 이미 봤다** — [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/06-adding-testcontainers|Ch5]]의 `runtime`/`test` scope, [[01-creating-custom-properties]]의 컨버터. **의존성에 "언제 필요한가"를 정확히 적는 것**이 남의 빌드를 보호한다.

**실용적 단서**: **Initializr가 설정 메타데이터 지원을 고르면 이미 넣어 주는 경우가 많으니, 손으로 추가하기 전에 `pom.xml`을 먼저 확인하라.**

## Q6. Figure 6.2에서 `List<UserAccount>` 타입 표시가 가능한 이유

**메타데이터 JSON이 `@ConfigurationProperties` 타입의 필드 타입을 그대로 담기 때문이다.**

```text
app.config.users     List<UserAccount>
app.config.header    String
app.config.intro     String
```

**이름만이 아니라 선언한 타입까지 함께 나온다.**

> **[[01-creating-custom-properties]]에서 얻은 타입 안전 바인딩이 여기서 편집기 지원으로 되돌아온다** — **타입을 선언해 뒀기 때문에 IDE가 그 타입을 보여 줄 수 있다.**

**대비**: `@Value("${app.config.header}")` 방식이었다면 **키가 문자열 리터럴**이므로 프로세서가 **무엇이 설정 키인지 알아낼 방법이 없다.** 타입은커녕 이름조차 목록에 못 올린다.

**즉 `@ConfigurationProperties`의 이득이 한 겹 더 있다**:
- 기동 시점 검증 (Q: [[01-creating-custom-properties]])
- 설정이 한 타입에 모임
- **편집기가 키와 타입을 안다** ← 이것

**화면에서 함께 읽히는 것**: 목록 아래쪽에 `server.jetty.accesslog.append`, `spring.application.name` 같은 **내장 프로퍼티들이 섞여 있다.** Q4의 "같은 메커니즘"이 눈으로 확인되는 지점이다.

> **원문 불일치**: 본문은 `application-alternate.yaml`을 만들라고 하는데 화면의 편집기 탭은 **`application-alt.yaml`**이다. 실행 예제가 `SPRING_PROFILES_ACTIVE=alternate`이므로 **`application-alternate.yaml`이 맞다.**

## Q7. 메타데이터가 없으면 프로퍼티 바인딩이 실패하는가

**아니다. 정상 동작한다.**

> **메타데이터는 편집기 편의를 위한 것이지 바인딩의 조건이 아니다.**

```
바인딩:  Environment 에서 키를 읽어 @ConfigurationProperties 타입에 넣는다
         → 런타임 동작. metadata.json 을 보지 않는다

메타데이터: IDE 가 완성 후보를 만들 때 읽는다
         → 편집 시점 동작. 애플리케이션은 관여하지 않는다
```

**두 방향 모두 성립하지 않는다**:
- **메타데이터가 없어도** 애플리케이션은 정상 동작한다
- **메타데이터가 있어도** 잘못된 값이 막히지 않는다 — 검증이 아니라 **목록**이다

**실무적 함의**: 메타데이터가 없는 것은 **버그가 아니라 편의 부재**다. "완성이 안 뜬다"는 이유로 급하게 고칠 일이 아니고, 반대로 **"완성에 떴으니 맞는 키"**라고 안심할 일도 아니다 — 오타는 여전히 **기동 시점 바인딩**이 잡는다.

## Q8. 주소록 비유가 깨지는 지점

**비유**: `.properties`와 YAML의 관계는 **"전체 주소를 매번 적는 것과 주소록에 시·구·동을 접어 두는 것"**에 가깝다. **접어 두면 짧고 구조가 보인다.**

**깨지는 지점**: **접힌 계층이 깨졌을 때의 결과를 가볍게 보이게 한다.**

> **주소록이라면 한 항목만 틀리지만, YAML은 들여쓰기가 어긋나는 순간 그 아래 전부가 다른 부모로 들어간다. 한 글자가 아니라 문서의 나머지가 함께 무너진다.**

```
주소록:  "서울시" 아래 한 항목의 동 이름이 틀림 → 그 한 집만 못 찾는다
YAML:    40행 들여쓰기가 틀림                  → 41~300행 전부가 엉뚱한 곳으로 (Q3)
```

**차이의 근원**: 주소록의 계층은 **눈에 보이는 표제**로 표시되지만, YAML의 계층은 **공백**으로 표시된다. **보이지 않는 문자가 구조를 결정**하므로 어긋난 것을 눈으로 못 찾는다.

**비유가 맞는 부분은 남는다** — **반복을 접어 두면 짧아지고, 소속이 눈에 보인다**는 이득. 깨지는 것은 **오류의 전파 범위**다.

**정확한 비유로 고치면**: 주소록보다 **파이썬 코드의 들여쓰기**에 가깝다. 한 줄의 들여쓰기를 잘못하면 **그 줄이 다른 블록에 속하게 되고**, 문법 오류가 아니라 **조용히 다른 동작**을 한다. YAML도 같다 — **파싱은 성공하고 구조만 달라진다.**
