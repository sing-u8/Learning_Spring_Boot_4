## Q1. 우선순위 규칙 한 문장

> **나중에 고려되는 소스가 앞의 소스가 정한 값을 덮는다.**

**목록은 낮음 → 높음 순이다.**

| # | 프로퍼티 소스 |
|---:|---|
| 1 | `SpringApplication.setDefaultProperties()` |
| 2 | `@PropertySource` |
| **3** | **Config Data** (`application.properties`·`.yaml`과 프로파일 변형) |
| 4 | `RandomValuePropertySource` |
| **5** | **OS 환경 변수** |
| **6** | **자바 시스템 프로퍼티** (`-D`) |
| 7~9 | JNDI · `ServletContext` · `ServletConfig` |
| 10 | `SPRING_APPLICATION_JSON` |
| **11** | **명령줄 인자** (`--key=value`) |
| **12~14** | **테스트** (`properties` 속성 · `@DynamicPropertySource` · `@TestPropertySource`) |
| **15** | **DevTools 전역 설정** `$HOME/.config/spring-boot` |

**"목록의 위쪽이 우선순위가 높다"는 흔한 오해다** — **아래쪽이 높다.**

## Q2. `application.properties`가 낮은 자리에 있는 것이 좋은 설계인 이유

**기준값을 정하는 자리이기 때문이다.**

> **이 파일은 기준값을 정하기 좋은 자리이고, 환경 변수·명령줄 인자·테스트 프로퍼티가 필요할 때 그 기준을 덮는다.**

```
낮은 자리 = "누구나 덮을 수 있다"
         = "여기 적은 것은 기본값이지 강제가 아니다"
```

**반대였다면 무엇이 깨지나**: `application.properties`가 가장 높았다면
- **환경 변수로 운영 값을 주입하는 것이 불가능**해진다 → [[04-setting-properties-with-environment-variables]]의 전략이 통째로 무너진다
- **테스트가 자기 값으로 못 돈다** → Q3
- **[[02-creating-profile-based-property-files]]의 프로파일 덧칠도 성립하지 않는다**

**즉 낮다는 것은 약하다는 뜻이 아니라 "덮이도록 설계됐다"는 뜻이다.** 이 장 전체가 그 성질 위에 서 있다.

**층을 목적별로 나누는 것이 실무 지침이다**: **기준값**(`application.properties`) / **환경별**(프로파일 파일·외부 파일) / **긴급 조정**(환경 변수·명령줄).

## Q3. 테스트 관련 항목이 12–14번에 몰려 있는 이유

**테스트는 무슨 일이 있어도 자기가 정한 값으로 돌아야 하기 때문이다.**

> **`application.properties`에 무엇이 있든 `@TestPropertySource`가 이긴다.**

**왜 그래야 하나**: 테스트가 **환경에 좌우되면 테스트가 아니다.** 개발자 A의 로컬 설정과 CI의 설정이 다르면 **같은 코드가 다른 결과**를 낸다.

**구체적 사례**: [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/07-testing-repositories-with-testcontainers|Ch5의 Testcontainers 테스트]]가 `@TestPropertySource`로 `ddl-auto=create-drop`을 **강제**한 것이 이 성질에 기대고 있다. **프로젝트 설정이 `ddl-auto=validate`여도 테스트는 스키마를 만든다.**

**`@DynamicPropertySource`(13)가 함께 있는 이유**: **실행 중 결정되는 값**을 넣어야 하기 때문이다 — Ch5의 컨테이너 임의 포트가 그것이다. 정적 파일로는 표현할 수 없는 값이므로 **가장 늦게, 가장 강하게** 들어가야 한다.

**셋이 나란히 있는 것도 의미가 있다** — 테스트가 값을 지정하는 방법 **세 가지가 모두 같은 대역**에 있어서, **어느 방법을 쓰든 프로덕션 설정을 이긴다.**

## Q4. DevTools가 가장 높은 이유와 운영에서의 위험

**이유**: **개발자 개인 기계의 편의 설정이 프로젝트 설정에 막히면 곤란하기 때문이다.**

```
$HOME/.config/spring-boot   ← 개인 환경. 프로젝트가 아니라 사람에 속한다
```

**그리고 운영에는 DevTools가 아예 없다** — 그것이 이 배치를 안전하게 만드는 전제다.

**위험**: **DevTools가 운영 배포물에 포함되면 그 전제가 깨진다.**

```
가장 높은 우선순위를 갖는 소스가 개발용 모듈이다
        ↓
운영 배포물에 포함되면
        ↓
예측 불가능한 오버라이드가 생긴다
```

**구체적으로**: 서버의 `$HOME/.config/spring-boot`에 누군가 남긴 값이 **모든 배포 설정을 이긴다.** 그리고 그 파일은 **형상 관리에도, 배포 스크립트에도 없다** — 아무도 그것을 보지 않는다.

**방어**: DevTools 의존성을 `optional`/`runtime`+`developmentOnly`로 두어 **실행 가능한 JAR에 포함되지 않게** 한다.

## Q5. Config Data 안의 네 단계 — 위치가 먼저다

| # | 파일 | 어디에 |
|---:|---|---|
| 1 | `application.properties` | **JAR 안** |
| 2 | `application-{profile}.properties` | **JAR 안** |
| 3 | `application.properties` | **JAR 밖** |
| 4 | `application-{profile}.properties` | **JAR 밖** |

> **위치가 먼저 결정한다.**

**증거**: **JAR 밖 기본 파일(3)이 JAR 안 프로파일 파일(2)보다 높다.**

```
"JAR 안의 프로파일 파일이 JAR 밖의 기본 파일보다 강하다"  → 틀렸다
```

**두 축이 교차하지만 정렬 순서는 (위치, 프로파일)이다** — 먼저 안/밖으로 가르고, 그 안에서 기본/프로파일로 가른다.

**왜 위치가 먼저인가**: **JAR 밖은 배포 환경이 통제하는 자리**이고, JAR 안은 **빌드가 통제하는 자리**다. **배포가 빌드를 이겨야** 같은 아티팩트를 여러 환경에 쓸 수 있다(Q6).

**프로파일이 각 위치에서 기본보다 높은 것도 일관적이다** — **더 구체적으로 지정한 쪽이 이긴다.**

## Q6. "JAR을 열지 마라"는 경고가 회수되는 방식

**JAR 밖이 JAR 안을 이기므로, 열 필요가 없다.**

```text
/opt/app/
├── myapp.jar                    ← 손대지 않는다
└── application.properties       ← 여기 적은 값이 이긴다
```

> **실행 가능한 JAR 옆에 프로퍼티 파일을 하나 두면 그 값이 안쪽 값을 덮는다.**

**[[04-setting-properties-with-environment-variables]]의 네 문제가 전부 해소된다**:

| JAR 편집의 문제 | **JAR 옆 파일** |
|---|---|
| 불변 아티팩트가 깨진다 | **아티팩트는 그대로** |
| 서명·체크섬 무효 | **JAR을 안 건드리므로 유효** |
| 기록이 남지 않는다 | **파일이 남는다** — 배포 스크립트·이미지 정의에 넣으면 형상 관리됨 |
| 다음 배포에 사라진다 | **배포 절차가 보존하면 남는다** |

**단, 마지막 것은 조건부다** — **JAR 밖 파일은 자동으로 따라가지 않는다.** 배포 스크립트나 이미지 정의에 **포함시켜야** 한다. 안 하면 새 서버에 배포할 때 그 파일이 없다.

**[[02-creating-profile-based-property-files]]의 `spring.config.additional-location`이 같은 아이디어의 명시적 버전이다** — 위치를 관례에 맡기지 않고 지정한다.

## Q7. 명령줄 즉석 조정의 진짜 위험

**조직적인 것이다. 기술적으로는 완벽히 동작한다.**

> **문제는 기술이 아니라 기록이다.**

| 방법 | **어디에 남나** | **다음 배포 때** |
|---|---|---|
| 형상 관리된 프로파일 파일 | **git** | **살아남는다** |
| JAR 옆 외부 파일 | 서버 파일 시스템 | 배포 스크립트가 보존하면 남는다 |
| **명령줄 인자** | **그 실행뿐** | **사라진다** |
| 환경 변수 | 그 셸이나 컨테이너 정의 | 정의가 바뀌면 사라진다 |

**책의 표현**: *"**공들여 해결책을 만들어 놨는데 그 변경을 반영하지 않은 패치에 덮여 사라지는 것보다 나쁜 건 없다.**"*

**시나리오**: 새벽 두 시에 명령줄로 값을 바꿔 장애를 잡았다. **다음 주 정기 배포가 그 값을 지운다.** 장애가 재발하고, **이번에는 "저번에 고쳤는데?"라는 잘못된 전제**로 조사를 시작한다.

**권고**: 즉석 조정을 했으면 **기록해 두고, 형상 관리에 반영하는 것을 고려하라. 아마도 별도 프로파일 형태로.**

**즉 편의성과 지속성이 반비례한다** — 목록에서 **높은 소스일수록 쓰기 쉽고 남지 않는다.**

## Q8. Twelve-Factor의 세 번째 factor와 이 장의 대응

**세 번째 factor는 설정이고, 요지는 한 줄이다** — **환경마다 달라질 만한 것은 전부 외부화하라.**

| 이 장에서 한 일 | **Twelve-Factor의 관점** |
|---|---|
| 문구를 `@ConfigurationProperties`로 뺐다 ([[01-creating-custom-properties]]) | **코드에서 설정을 분리** |
| 환경별 프로파일 파일을 만들었다 ([[02-creating-profile-based-property-files]]) | **환경마다 다른 값을 다른 곳에** |
| 운영 설정을 아티팩트 밖에 두었다 | **코드와 설정의 완전한 분리** |
| 환경 변수로 덮을 수 있게 했다 ([[04-setting-properties-with-environment-variables]]) | **실행 시점 주입** |

**Twelve-Factor App**: **2011년 Heroku가 정리한, 클라우드에서 잘 돌아가는 애플리케이션의 12가지 원칙.**

**책의 태도가 균형 잡혀 있다** — *"**12가지 factor가 전부 지금도 유효한지, 다음 프로젝트에 다 적용될지는 논쟁적이다.** 하지만 그중 다수는 애플리케이션을 배포하고 연결하고 쌓아 올리기 쉽게 만든다."*

**핵심 판별**: **"이 값이 환경마다 달라지는가?"** 달라진다면 코드 밖으로, 안 달라진다면 코드 안에 둬도 된다. [[01-creating-custom-properties]]의 `header`/`intro`는 전자였고, 그래서 이 장이 시작됐다.

## Q9. 겹쳐 인쇄한 문서 비유가 깨지는 지점

**비유**: 15단계는 **"여러 장을 겹쳐 인쇄한 문서"**다. **나중에 찍힌 잉크가 앞의 글씨를 덮는다.**

**깨지는 지점**: **덮인 글씨가 여전히 거기 있다는 인상을 준다.**

> **실제로 Spring은 앞의 값을 지우지 않고 더 높은 소스를 먼저 조회할 뿐이다. 그래서 높은 소스에서 그 키가 사라지면 아래 값이 다시 드러난다. 지워진 게 아니라 가려져 있었던 것이다.**

```
인쇄:   덮으면 원래 글씨가 훼손된다 → 되돌릴 수 없다
Spring: 조회 순서일 뿐              → 위 값을 없애면 아래 값이 다시 보인다
```

**이 차이가 실무에서 드러나는 순간**: **환경 변수를 지웠더니 예상 못 한 값이 나온다.** "지웠으니 없어지겠지"가 아니라 **"아래 층의 값이 드러난다"**가 맞다. `application.properties`의 기준값으로 돌아가는 것이다.

**Q2의 설계와 이어진다** — **낮은 층이 기준값을 갖고 있다**는 것은, **높은 층을 걷어내면 안전한 기본값으로 되돌아간다**는 뜻이다. 겹쳐 인쇄였다면 그런 복원이 없다.

**비유가 맞는 부분은 남는다** — **순서가 결과를 결정한다**, **나중이 이긴다**. 깨지는 것은 **가림과 훼손의 차이**다.

**정확한 비유로 고치면**: 인쇄보다 **투명 시트를 겹쳐 위에서 내려다보는 것**에 가깝다. 위 시트를 치우면 아래가 그대로 보인다. [[02-creating-profile-based-property-files]]의 필름 비유가 여기서 더 잘 맞는다 — 다만 **거기서 깨졌던 리스트 교체 예외는 여기서도 그대로 남는다.**
