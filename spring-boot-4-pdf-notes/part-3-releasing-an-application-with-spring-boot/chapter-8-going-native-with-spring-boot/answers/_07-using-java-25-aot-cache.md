## Q1. JVM 시작 7단계 중 AOT Cache가 앞당기는 것

**표준 JVM 시작**:
1. **class가 메모리로 로드된다**
2. **tiered compilation 안에서 실행이 시작된다**
3. **메서드가 돌면서 런타임이 프로파일링 정보를 모은다**
4. **JIT가 자주 쓰이는 "hot" 경로를 찾아낸다**
5. 그 메서드들이 점점 더 최적화된 기계어로 컴파일된다
6. 프로파일 데이터가 쌓이고 상위 최적화가 적용되면서 **warmup** 동안 성능이 개선된다
7. **steady-state 처리량**에 도달한다

**AOT Cache가 앞당기는 것: 1~4단계.**

**두 JEP가 그것을 나눠 맡는다**:
| JEP | 제목 | **하는 일** |
|---|---|---|
| **483** | Ahead-of-Time Class Loading and Linking | **class 로딩·링크 결과를 미리 만들어 둔다** (1~2) |
| **515** | Ahead-of-Time Method Profiling | **메서드 프로파일을 미리 수집해 둔다** (3~4) |

**그대로 남는 것: 5~7단계 — JIT의 실제 컴파일과 지속적 최적화.**

> **그리고 JIT 능력은 온전히 남는다.**

**요점은 3~6번이 매번 처음부터 반복된다는 것이다** — **어제 이 서버가 알아낸 최적화는 오늘 새 인스턴스에 전달되지 않는다.** AOT Cache는 그 전달 경로를 만든다.

**문제가 되는 네 상황**: **자주 재시작 / 동적 스케일 / cold start가 중요 / 서버리스·버스트.** 반대로 **오래 도는 서비스에서는 이 워밍업 비용이 대체로 수용 가능**하다.

> **책이 빠뜨린 JEP** — Java 25에서 "두 단계 대신 단일 training-run 명령"을 실제로 가능하게 한 것은 **JEP 514 Ahead-of-Time Command-Line Ergonomics**다. 다음 절이 쓰는 **`-XX:AOTCacheOutput`이 바로 이 JEP가 도입한 옵션**인데 근거로 인용되지 않았다. 이 옵션이 켜지면 **JVM이 내부적으로 `AOTMode=create` 하위 호출을 스스로 오케스트레이션**한다 — **두 단계가 사라진 것이 아니라 JVM이 대신 밟아 주는 것**이다.

## Q2. "중간 지대"라 불리는 이유

**네이티브 바이너리를 만들지 않고 JVM에서 계속 돌면서 startup만 개선하기 때문이다.**

```
표준 JVM ────────── AOT Cache ────────── 네이티브 이미지
느린 startup        빠른 startup          가장 빠른 startup
JIT 있음            JIT 있음              JIT 없음
peak 처리량 최고    peak 처리량 보존      peak 처리량 손실
제약 없음           제약 없음             리플렉션·프록시·조건 제약
```

**AOT Cache가 지키는 넷**:
- **네이티브 바이너리를 만들지 않는다**
- **애플리케이션은 JVM에서 계속 돈다**
- **JIT 컴파일러가 살아 있다**
- **peak 처리량 성능이 보존된다**

**"peak 처리량이 보존된다"의 의미**: **네이티브는 JIT가 없어 실행 패턴에 맞춘 최적화를 못 한다.** **오래 도는 고부하 서비스에서는 JVM 쪽이 최종 처리량에서 앞설 수 있다.** **AOT Cache는 그 이점을 지키면서 초반만 앞당긴다.**

**즉 네이티브는 "초반을 얻고 후반을 내주는" 거래이고, AOT Cache는 "초반을 조금 얻되 후반을 그대로 두는" 거래다.**

**비유로 보면** 산악 등반의 고정 로프 — **앞선 팀이 박아 둔 로프가 있으면 같은 구간을 훨씬 빨리 통과한다.** 그러면서도 **로프가 없는 새 구간은 여전히 스스로 개척할 수 있다** — **JIT가 살아 있다는 뜻**이다.

**깨지는 지점 둘**: **로프는 누가 박았든 쓸 수 있지만 AOT 캐시는 정확히 같은 빌드와 같은 JVM 버전에만 맞는다**([[07a-enabling-aot-cache-for-spring-boot]]). 그리고 **로프는 루트를 안전하게 만들지만 캐시는 정확성에 관여하지 않는다** → Q4.

## Q3. "AOT"가 이 장에서 쓰인 세 가지 뜻

| 이름 | 뜻 | 층 | 관련 노트 |
|---|---|---|---|
| **GraalVM의 AOT 컴파일** | **바이트코드를 미리 기계어로 번역해 바이너리 생성** | 컴파일러 | [[01-why-graalvm-native-image]] |
| **Spring AOT** | **빌드 시점에 애플리케이션 구조(bean 그래프·metadata) 확정** | 프레임워크 | [[02-adapting-an-application-for-native-image]] |
| **Java AOT Cache** | **컴파일·프로파일 산출물을 실행 사이에 보존** | JVM | 이 노트 |

> **문맥마다 어느 것인지 확인해야 한다.**

**책이 못 박는 구분**:
| | **Spring AOT 처리** | **Java AOT Cache** |
|---|---|---|
| 층 | **프레임워크** | **JVM** |
| 시점 | **빌드** | **실행 사이** |
| 다루는 것 | **애플리케이션 구조** | **런타임 성능** |

**Spring AOT 엔진은 "무엇이 bean인가"를 미리 정하고, Java AOT Cache는 "이 메서드를 어떻게 컴파일했었나"를 기억한다.**

> **이름만 겹칠 뿐 서로 독립적이며, 함께 쓸 수도 있다.**

**세 개의 관계**:
- **GraalVM AOT는 Spring AOT를 필요로 한다** — 도달성 분석이 Spring 구조를 봐야 하므로
- **Java AOT Cache는 둘 다 필요로 하지 않는다** — JVM 기능이므로
- **Spring AOT + Java AOT Cache** 조합이 [[07a-enabling-aot-cache-for-spring-boot]]의 주제다

**계보**: Java 25는 **Java 24가 도입한 AOT Cache 지원**을 이어받아 캐시 생성을 **단일 training-run 명령**으로 단순화했다. **Project Leyden**(= Java의 시작·워밍업 시간을 줄이는 OpenJDK 프로젝트)의 일부다.

## Q4. AOT Cache 도입 리스크가 네이티브보다 낮은 이유

**캐시는 정확성에 관여하지 않기 때문이다.**

```
AOT Cache 가 없거나 무효  →  그냥 평소대로 느리게 시작한다   (성능만 손해)
네이티브에서 클래스가 잘림 →  예외가 난다                   (동작이 깨진다)
```

> **순수한 성능 장치이므로 캐시가 없거나 무효여도 프로그램은 그냥 느리게 정상 동작한다. 이 점이 네이티브 이미지의 "잘려 나가면 예외"와 결정적으로 다르다.**

**리스크 비교**:

| | **네이티브** | **AOT Cache** |
|---|---|---|
| 실패 모드 | **런타임 예외** — 배포 후 그 경로를 밟을 때 | **성능 저하만** |
| 코드 변경 | 힌트 등록, 조건부 구성 재검토 | **없음** |
| 검증 부담 | **실행 경로를 넓게 훑는 통합 테스트 필수** | 평소대로 |
| 되돌리기 | 다시 빌드 | **캐시 파일을 빼면 끝** |

**그래서 도입 순서의 권고가 나온다** — [[03a-why-native-images-pay-off]]와 [[04b-graalvm-and-third-party-libraries]]가 **"중간 지대를 먼저 검토하라"**고 한 이유가 이것이다. **이득이 작더라도 비용과 리스크가 훨씬 작다.**

**남는 경계**(§6):
- **극단적 cold start**가 요구되면 **네이티브가 여전히 앞선다**
- **Java 24 미만**에서는 못 쓴다 → CDS([[06-using-buildpacks-with-java-aot-cache]])
- **메모리 사용량을 줄이는 것이 목표**라면 **도움이 안 된다** — JVM이 그대로 있다
- **오래 도는 소수 인스턴스**라면 **워밍업 비용 자체가 무시할 만하다**

**네 전략의 비교는 [[07b-comparing-four-execution-strategies]]에서 마무리된다.**
