## Q1. 20초 startup이 "5.6시간"이 되는 계산

```
1,000 인스턴스 × 20초 = 20,000초 = 5.6시간
```

**그것이 5.6시간의 과금 시간이다. 아무 요청도 처리하지 않으면서.**

> **클라우드 요금은 "일한 시간"이 아니라 "켜져 있던 시간"에 매겨진다.** 시작하는 20초 동안 인스턴스는 **CPU와 메모리를 잡고 있고, 요금은 그대로 붙는다.**

**그리고 이 5.6시간은 배포할 때마다 붙는다.** **지속 배포**를 받아들여 패치 커밋마다 밀어내면 **청구서가 손을 벗어날 수 있다.** 책의 표현이 정확하다 — **운영 관점에서는 아닐지 몰라도 청구 관점에서는 확실히** 문제다.

**성립 조건 둘**:

| 조건 | **없으면** |
|---|---|
| **인스턴스 수가 많다** | **3대 × 20초 = 1분. 아무 의미 없다** |
| **교체가 잦다** | **분기에 한 번 배포하면 연 4회 × 5.6시간** |

**이 절이 하는 일은 0.5초와 20초의 차이를 개발자의 체감이 아니라 회계의 단위로 옮기는 것이다.** 개발자에게 20초는 **커피 한 모금**이지만, 곱하면 회계 항목이 된다.

## Q2. 이 논증이 무력해지는 배포 환경

**① 인스턴스가 적고 오래 사는 환경.** **3대 × 20초 = 1분.** 네이티브의 **빌드 비용(161초 × 빌드 횟수)이 그 이득을 훨씬 넘는다.**

**② 배포가 드문 환경.** **절감액은 배포 횟수에 비례한다.** 분기 배포면 **연 4회**다.

> **[[01-why-graalvm-native-image]]가 짚은 두 무대 — 대규모 지속 배포와 서버리스 — 밖에서는 이 논증이 힘을 잃는다.**

**반대로 서버리스에서는 조건이 더 극단적이다** — **인스턴스 수명이 몇 초라서 cold start가 전체 실행 시간의 상당 부분**을 차지한다. 20초 기동에 3초 실행이면 **일한 시간보다 켜는 시간이 길다.**

**세 번째 무력화 조건**(§6): **최고 처리량이 중요한 워크로드**. **JIT를 잃는 대가를 따로 계산**해야 한다 → [[07b-comparing-four-execution-strategies]].

**그리고 먼저 검토할 중간 지대가 있다**(§6) — **JVM에 남으면서 startup을 줄이는 방법**이 있고 **빌드 비용이 훨씬 싸다** → [[07-using-java-25-aot-cache]].

## Q3. 0.1초와 실측 0.528초

**실측값으로 계산해야 한다.**

> **원문의 숫자 불일치** — 책 p.239–240은 **"우리 앱이 방금 그랬듯 0.1초에 뜬다면"**이라고 쓰지만, **바로 앞 p.238의 실제 로그는 0.528초**다. **0.1초는 이 장 어디에서도 측정되지 않은 값**이며, **"5.6시간 → 17분" 대비도 그 가정 위에** 서 있다.

| | 책의 가정(0.1초) | **실측(0.528초)** |
|---|---|---|
| 1,000 인스턴스 | **17분 미만** | **약 8.8분** |
| 20초 대비 | 약 1/200 | **약 1/38** |

**결과가 어떻게 달라지나**: **여전히 큰 개선이지만 17분과는 다르다.**

> **논증의 방향은 맞고 숫자만 낙관적이다.**

**실무적 함의**: 도입을 설득할 때 **0.1초를 인용하면 검증 단계에서 신뢰를 잃는다.** **자기 애플리케이션의 실측값**으로 계산해야 하고, 그 값은 **의존성 구성에 따라 크게 달라진다.**

**그리고 20초라는 기준값도 확인해야 한다** — 이 장의 JVM 기동 실측이 20초인지, 예시로 든 숫자인지. **양쪽 숫자가 다 자기 것이어야** 계산이 성립한다.

## Q4. 절감되는 비용과 새로 생기는 비용

| | **어디에서 측정하나** |
|---|---|
| **절감** | **런타임 과금** — 클라우드 인스턴스 시간 |
| **신규 비용** | **빌드 시간과 CI 자원** — 161초, Peak RSS 5.03GB |

> **배포가 잦을수록 앞의 이득이 커지지만 뒤의 비용도 같이 커진다. 하루 20번 빌드하면 CI에서 54분이 더 든다.**

**같은 변수(배포 횟수)가 양쪽에 곱해진다는 것이 핵심이다**:
```
이득 =  (JVM 기동 - 네이티브 기동) × 인스턴스 수 × 배포 횟수
비용 =  (네이티브 빌드 - 표준 빌드) × 배포 횟수
                                        ↑ 인스턴스 수가 곱해지지 않는다
```

**그래서 인스턴스 수가 손익분기를 결정한다** — 배포 횟수는 양쪽에 붙으므로 **약분되고**, **인스턴스 수만 이득 쪽에 남는다.** Q2의 "인스턴스가 적으면 무력하다"가 이 식에서 나온다.

**메모리 이야기도 방향이 갈린다**:
- **절약**: **런타임 메모리** — JVM의 힙·메타스페이스·JIT 코드 캐시가 통째로 없어진다
- **증가**: **실행 파일 크기(159.62MB)**, **빌드 시 메모리(5.03GB)**

**포기한 것의 재평가도 함께**: **write once, run anywhere를 잃은 것이 실은 손해가 아닐 수 있다.** 조건 하나 — **지속 배포 시스템이 타깃 환경과 같은 OS에서 앱을 빌드한다면.** **쓰지 않는 기능을 내주는 것은 손해가 아니다.** 그 조건을 만드는 방법이 [[04-building-native-container-images]]다.

**비유로 보면** 엘리베이터 대기 — **개인의 체감과 조직의 비용은 다른 단위다.** **깨지는 지점 둘**:
- **엘리베이터는 동시에 기다리므로 벽시계 시간은 여전히 20초지만, 클라우드 과금은 인스턴스마다 따로 매겨져 실제로 합산된다** — **비유보다 클라우드 쪽이 더 나쁘다**
- **엘리베이터를 빠르게 만드는 비용은 한 번이지만, 네이티브 빌드 비용은 빌드할 때마다** 지불한다
