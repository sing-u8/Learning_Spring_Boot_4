## Q1. 네 전략을 네 축으로

| | **표준 JVM** | **JVM + AOT Cache** | **네이티브 이미지** | **CRaC** |
|---|---|---|---|---|
| **시작 시간** | 가장 느림 | **눈에 띄게 개선** | **대체로 가장 빠른 cold start** | **복원 후 극단적으로 빠를 수 있음** |
| **런타임 모델** | **JIT 전적 의존**, tiered compilation, 워밍업 필요 | **JIT 완전 유지**, 워밍업만 단축 | **JIT 없음** — 미리 컴파일된 바이너리 | **일반 JVM 런타임과 동적 기능 유지** |
| **메모리** | 표준 | 표준 | **대체로 낮음** | 표준 |
| **빌드 복잡도** | **낮게 유지** | 낮음 (training run 추가) | **높음** — 빌드 시점 설정, 리플렉션·프록시·직렬화 제약 | 중간 (체크포인트 워크플로) |

**세 문장으로 압축한 차이**:
| 방식 | **무엇을 미리 해 두나** |
|---|---|
| **네이티브 이미지** | **전부를 미리 컴파일**해 플랫폼 전용 바이너리로 |
| **AOT cache** | **컴파일된 산출물을 캐시**해 HotSpot에 남은 채 워밍업 단축 |
| **CRaC** | **초기화된 JVM 프로세스 상태를 복원** |

**표준 JVM이 내주는 것과 얻는 것**: **startup 지연을 내주고 최대의 유연성과 장기 처리량 최적화를 얻는다.**

> **정확한 수치는 애플리케이션·훈련 또는 체크포인트 워크플로·컨테이너 구성·하드웨어에 크게 좌우된다.**

**놓치기 쉬운 것**: **네이티브에서 JIT가 없다는 것은 startup만 바꾸는 게 아니라 steady-state 처리량의 상한도 바꾼다** → Q4.

## Q2. AOT Cache가 "나머지 셋과 층이 다르다"

**표준 JVM의 대안이 아니라 그 위에 얹는 개선이기 때문이다.**

```
배타적 선택:   표준 JVM  |  네이티브 이미지  |  CRaC
그 위에 얹기:  표준 JVM + AOT Cache
```

> **"표준 JVM이냐 AOT Cache냐"가 아니라 "AOT Cache를 켜느냐 마느냐"에 가깝다.**

**책의 표현**: **AOT Cache는 이 모델을 보완한다.** **애플리케이션은 JVM에 남고 완전한 JIT 최적화 능력을 유지하되, startup과 워밍업 시간이 준다.** — **네이티브 컴파일의 추가 제약 없이 더 반응성 있는 해법.**

**표 하나에 나란히 놓여 있어 네 개의 배타적 선택지처럼 보이지만** 그렇지 않다.

**비유의 깨짐이 이것이다** — 식당 개점 준비 비유가 **넷을 나란히 놓지만 실제로 AOT Cache는 다른 셋과 층이 다르다.**

**실무적 귀결 — 도입 순서**(§6): **가장 싼 것부터 시도한다.** **AOT Cache는 코드 변경이 없고 실패해도 느려질 뿐이다. 네이티브는 그 반대다.**

```
1. AOT Cache 를 켜 본다        (코드 변경 0, 리스크 0)
2. 측정한다
3. 부족하면 네이티브나 CRaC 를 검토한다
```

**그리고 측정 없이 고르지 않는다** — 책도 **"정확한 수치는 크게 좌우된다"**고 못 박는다.

## Q3. CRaC의 "Coordinated"가 이름에 들어가는 이유

**체크포인트에 열린 소켓·파일 핸들·만료된 토큰이 담기므로, 애플리케이션이 체크포인트/복원 이벤트에 협조해야 하기 때문이다.**

```
체크포인트 시점:  DB 커넥션 풀이 열려 있다, 소켓이 열려 있다, 토큰이 유효하다
        ↓ (시간이 지난 뒤)
복원 시점:        그 커넥션은 끊겼다, 그 토큰은 만료됐다
```

> **주방 사진은 재료가 상하지 않지만 CRaC 체크포인트는 열린 소켓·파일 핸들·만료된 토큰을 담고 있어 복원 시 정리가 필요하다.**

**그래서 애플리케이션이 협조해야 한다** — 체크포인트 직전에 **커넥션을 닫고**, 복원 직후에 **다시 연다.** 라이브러리와 프레임워크가 그 훅을 구현해야 한다.

**CRaC**: **Coordinated Restore at Checkpoint.** **완전히 초기화된 애플리케이션을 체크포인트로 떠 두었다가 나중에 복원**한다. **CRIU**(= 리눅스에서 프로세스를 파일로 덤프·복원하는 기반 기술) 위에 서 있고, **현재 Linux 지향 워크플로**를 겨냥한다.

**왜 네이티브 대신 CRaC를 고르나**: **일반 JVM 런타임과 그 동적 기능, 표준 JVM 동작을 유지하면서** startup을 줄이려는 것이다.

> **책이 CRaC만 명령을 보여 주지 않는다** — 나머지 셋은 실제 명령이 나오는데 CRaC는 소개에서 끝난다. **Spring 쪽 진입점은 실제로 존재하고 [[07a-enabling-aot-cache-for-spring-boot]]의 스위치와 정확히 짝을 이룬다**:

| | 속성 | 하는 일 |
|---|---|---|
| AOT Cache · CDS | `spring.context.exit=onRefresh` | refresh 후 **종료** |
| **CRaC** | **`spring.context.checkpoint=onRefresh`** | refresh 후 **체크포인트** |

**둘 다 Spring Framework 6.1부터 `DefaultLifecycleProcessor`가 구현한다.** 게다가 **Spring Boot는 CRaC MXBean이 classpath에 있으면 시작 배너를 `Started` 대신 `Restored`로 바꾸고, 가동 시간도 마지막 복원 이후로 보고한다.**

> **즉 CRaC는 "언급만 되는 미래 기술"이 아니라 이미 통합된 경로다.**

**§6의 제약**: **CRaC를 비-Linux 환경에 계획하지 않는다.**

## Q4. 처리량이 최우선인 서비스에서 네이티브를 고르면

**steady-state 처리량의 상한을 잃는다.**

> **JIT가 없다는 것은 startup만 바꾸는 게 아니라 steady-state 처리량의 상한도 바꾼다. 실행 패턴에 맞춘 최적화가 불가능하기 때문이다.**

**JIT가 하는 일 중 AOT가 못 하는 것**:
- **실제 프로파일 기반 인라이닝** — 어느 분기가 자주 타는지 보고 최적화
- **가상 호출의 단형화** — 실제로 한 구현만 쓰이면 직접 호출로 바꿈
- **탈최적화와 재컴파일** — 가정이 깨지면 되돌리고 다시 최적화

**AOT는 빌드 시점의 추측만으로 최적화하므로 이 셋이 없다.**

> **오래 도는 고부하 서비스의 최종 처리량은 JIT가 있는 쪽이 앞설 수 있다.**

**"네이티브가 항상 가장 빠르다"는 틀리다** — **cold start에서는 대체로 그렇다.** 그러나
- **복원 후의 CRaC가 더 빠를 수 있고**
- **오래 도는 고부하 서비스의 최종 처리량은 JIT가 있는 쪽이 앞설 수 있다**

> **축이 하나가 아니다.**

**그래서 워크로드가 선택을 결정한다**:
```
짧고 자주 뜬다  (서버리스·오토스케일)  → 네이티브 / CRaC
길게 고부하로 돈다                     → 표준 JVM + AOT Cache
메모리가 목표                          → 네이티브 (나머지 셋은 JVM 유지)
```

**마지막 줄이 §6의 지침이다** — **메모리가 목표라면 선택지가 사실상 네이티브 하나다.**
