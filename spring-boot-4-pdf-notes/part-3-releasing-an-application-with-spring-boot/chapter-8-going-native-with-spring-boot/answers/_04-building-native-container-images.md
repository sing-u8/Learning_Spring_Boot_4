## Q1. `-Pnative spring-boot:build-image`가 결합하는 두 개념

| 조각 | **어디서 왔나** | **하는 일** |
|---|---|---|
| `spring-boot:build-image` | **[[../chapter-7-releasing-an-application-with-spring-boot/02-building-a-docker-container|Ch7]]** | **buildpack으로 컨테이너 이미지 조립** |
| `-Pnative` | **이 장 ([[02-adapting-an-application-for-native-image]])** | **Spring AOT 처리 + GraalVM 툴체인 활성화** |

**풀려는 문제**: **MacBook에서 만든 `Mach-O 64-bit executable arm64`가 Linux 클라우드에서 실행되지 않는다.**

**발상**: **Linux용 실행 파일이 필요하면 Linux에서 빌드하면 된다.** 그리고 **내 노트북에 Linux가 없어도 Docker는 Linux 컨테이너를 띄울 수 있다.**

**단계마다의 이유**:
1. **Maven이 `native` profile을 켠다** — Spring AOT가 돌아야 **bean 구조가 확정되고 GraalVM용 metadata가 생성**된다
2. **buildpack 빌더 컨테이너를 띄운다** — **그 컨테이너가 Linux다.** 여기서부터 모든 컴파일이 Linux 위에서 일어난다
3. **빌더 안에서 `native-image`가 돈다** — **내 노트북에 GraalVM이 없어도 된다.** 빌더 이미지가 갖고 있다
4. **결과 실행 파일이 런타임 이미지에 담긴다** — **배포 단위가 컨테이너여야** 클라우드에 그대로 올라간다

**팀 관점의 문제도 함께 풀린다** — **macOS·Windows·Linux 사용자가 섞여 있으면 각자 다른 실행 파일**이 나오는데, 이 방식은 **누가 빌드해도 같은 결과**를 낸다.

## Q2. buildpack이 해결해 주는 것과 아닌 것

| | **해결해 준다** | **해결해 주지 않는다** |
|---|---|---|
| **OS** | **macOS/Windows → Linux** ✅ | |
| **CPU 아키텍처** | | **arm64 → amd64** ❌ |

> **buildpack이 해결해 주는 것은 OS다. CPU 아키텍처까지 자동으로 넘어가지는 않는다.**

**Apple Silicon에서 amd64 이미지를 만들려면 별도 설정이 필요하고, 에뮬레이션이 끼면 빌드가 크게 느려진다.**

**왜 그런가**: 빌더 컨테이너는 **호스트 커널 위에서 돈다**([[../chapter-7-releasing-an-application-with-spring-boot/02-building-a-docker-container|Ch7]]의 컨테이너 성질). **OS 사용자 공간은 컨테이너가 제공하지만 CPU 명령어 집합은 호스트의 것**이다. 다르면 **에뮬레이션**이 필요하고, 그것은 느리고 때로 실패한다.

**세 번째로 해결되지 않는 것 — 빌드 자원**: **컨테이너 안에서 도는 것도 같은 `native-image` 컴파일이다.** [[03-building-and-running-a-native-application]]의 **Peak RSS 5.03GB가 Docker 데몬에 할당된 메모리 안에서** 필요하다. **Docker Desktop 기본 메모리로는 부족할 수 있다** — §6이 **"빌드가 원인 불명으로 죽는 가장 흔한 이유"**라고 짚는다.

**`-Pnative`를 빼면 전혀 다른 결과**: `./mvnw spring-boot:build-image`만 쓰면 **Ch7의 JVM 기반 레이어드 이미지**가 나온다. **겉보기에 둘 다 "Docker 이미지"라 헷갈리기 쉬운데, 안에 든 것이 JAR이냐 네이티브 실행 파일이냐로 갈린다.**

## Q3. 로컬 네이티브 빌드보다 더 느린 이유

**컨테이너를 띄우고, 그 안에서 [[03-building-and-running-a-native-application]]에서 본 161초짜리 컴파일을 돌리기 때문이다.**

```
로컬:      native-image 컴파일 (161초)
컨테이너:  빌더 이미지 pull + 컨테이너 기동 + 같은 161초 컴파일 + 런타임 이미지 조립
```

**즉 컴파일 비용은 그대로이고 컨테이너 오버헤드가 더해진다.**

**아키텍처가 다르면 더 나빠진다**(Q2) — 에뮬레이션이 끼면 **컴파일 자체가 몇 배 느려진다.**

**그래서 §6의 지침이 나온다**:
- **로컬 OS와 배포 OS가 같다면 로컬 빌드가 더 빠르다.** **컨테이너 오버헤드를 낼 이유가 없다**
- **개발 반복 중에는 쓰지 않는다.** **이 명령은 CI나 릴리스 단계용**이다
- **컨테이너가 필요 없는 배포**(VM에 실행 파일만 올리는 경우)라면 **타깃과 같은 OS의 CI 러너에서 로컬 방식으로** 빌드하는 편이 단순하다

**비유의 깨짐 하나가 이것이다** — 현지 공장 비유에서 **공장은 한 번 세워 두고 계속 쓰지만 buildpack 빌더는 매 빌드마다 컴파일 전체를 다시** 한다. **캐시가 있어도 161초짜리 단계는 대체로 다시 돈다.**

## Q4. 배포 절차가 Ch7과 같은 것이 이득인 이유

**네이티브라는 사실이 배포 파이프라인을 바꾸지 않기 때문이다.**

**이미지가 나온 뒤의 선택지는 앞 장에서 이미 배운 것들이다**:
- **로컬에서 `docker run`으로 돌린다**
- **클라우드 제공자에 푸시한다**
- **Docker Hub에 배포한다**

> **컨테이너라는 공통 포장이 그 차이를 흡수한다.**

**[[../chapter-7-releasing-an-application-with-spring-boot/02-building-a-docker-container|Ch7]]의 컨테이너선 비유가 여기서 값을 낸다** — **안에 무엇이 들었든 바깥 규격이 같으므로 그것을 다루는 도구가 내용물을 몰라도 된다.** 안에 든 것이 **JAR이든 네이티브 실행 파일이든** 레지스트리·오케스트레이터·CI는 **똑같이 다룬다.**

**이 방식의 두 이득**:
1. **크로스 플랫폼 해결**(Q1)
2. **기존 배포 흐름을 그대로 쓸 수 있다**

**두 번째가 도입 비용을 결정한다** — 네이티브로 전환하는 데 **배포 인프라를 새로 만들 필요가 없다.** 바꾸는 것은 **빌드 명령 하나**이고, 그 뒤는 전부 같다.

**대조**: 컨테이너를 쓰지 않았다면 **실행 파일을 어떻게 옮길지, 어떻게 버전을 관리할지, 어떻게 롤백할지**를 전부 다시 설계해야 했다. [[../chapter-7-releasing-an-application-with-spring-boot/03-publishing-an-image-to-docker-hub|Ch7]]이 푼 문제들이 그대로 다시 나온다.

**해외 가구 비유로 보면**: **설계도(소스)만 보내고 조립은 현지에서 한다.** **깨지는 지점 둘** —
- **현지 공장은 진짜 현지에 있지만 빌더 컨테이너는 내 기계 위에서 돈다** → Q2의 아키텍처 문제
- **공장은 한 번 세워 두고 쓰지만 빌더는 매번 다시 컴파일한다** → Q3
