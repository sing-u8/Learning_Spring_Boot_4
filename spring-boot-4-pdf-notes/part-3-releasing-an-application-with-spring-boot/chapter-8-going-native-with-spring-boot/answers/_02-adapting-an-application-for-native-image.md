## Q1. `Class.forName(props.get("x"))`가 도달성 분석에서 문제가 되는 이유

**정적 분석기의 눈에 `Class.forName`의 인자는 그냥 문자열이다.**

```
정적 분석기가 보는 것:

   main()  ──▶ 컨트롤러  ──▶ 서비스  ──▶ Class.forName( ??? )
                                                        │
                                    화살표를 그릴 대상이 없다
                                                        ▼
                                            MyHandler  ← 아무 화살표도 안 닿는다
                                                        ▼
                                                  도달 불가 → 잘려 나간다
```

**`native-image`가 하는 일**: 실행 파일을 **작고 빠르게** 만들려면 **안 쓰는 것을 버려야** 한다. 무엇이 안 쓰이는지 알기 위해 **도달성 분석**을 쓴다 — **`main` 메서드, 리플렉션 힌트, resource 설정, 프레임워크가 준 metadata를 진입점으로 삼아 호출 그래프를 따라간다. 거기서 닿지 않는 것은 최종 이미지에서 잘라낸다.**

**어떤 클래스가 들어올지 알 수 없으니 그 클래스로 가는 화살표를 그릴 수 없고, 화살표가 없으면 도달 불가로 판정돼 잘려 나간다.**

**가장 나쁜 점**: **실행하면 `ClassNotFoundException`이 뜨는데, 그때는 이미 배포된 뒤다.** **빌드는 성공한다.**

**해법**: 그 클래스를 **런타임 힌트**로 명시적으로 등록한다 → [[05-configuring-reflection-and-runtime-hints]].

## Q2. "리플렉션이 지원되지 않는다"가 틀린 이유

> **책이 직접 바로잡는다 — "네이티브에서는 리플렉션과 프록시가 지원되지 않는다"는 서술은 거짓이다.**

**정확히 고쳐 말하면**:

| | 틀린 서술 | **맞는 서술** |
|---|---|---|
| **리플렉션** | 지원되지 않는다 | **지원되되 대상을 등록해야 한다** |
| **동적 프록시** | 지원되지 않는다 | **런타임 생성이 안 될 뿐 빌드 시점 생성은 된다** |

> **사용의 제약이지 지원의 부재가 아니다.**

**왜 이 구분이 중요한가**: "지원 안 됨"으로 이해하면 **리플렉션을 쓰는 라이브러리를 전부 포기**해야 한다고 결론짓게 된다. 실제로는 **등록하면 된다** — Jackson도 JPA도 네이티브에서 돈다.

**그리고 Spring 쪽이 스스로를 고쳤다**:
- Spring Framework는 **리플렉션 의존을 줄였다**
- Spring Boot는 configuration class의 **프록시를 가능한 한 피한다** — 애플리케이션 전체의 프록시 수를 줄이려고
- **Spring 팀과 GraalVM 팀이 함께 작업**했다 — 한쪽은 불필요한 리플렉션을 걷어내고, 다른 쪽은 Spring 기반 앱을 더 잘 지원하도록

> **"네이티브가 잘 돌아간다"는 것은 저절로 된 것이 아니라 양쪽이 서로에게 맞춰 온 결과다.**

**남는 함정**: **내 코드가 리플렉션을 안 써도 의존 라이브러리가 쓴다.** 그래서 [[04b-graalvm-and-third-party-libraries]]가 별도 주제가 된다.

## Q3. `@Profile`이 빌드 시점에 평가된다는 사실이 파이프라인을 바꾸는 방식

**하나의 아티팩트를 여러 환경에 배포하는 모델이 성립하지 않을 수 있다.**

**Spring AOT 엔진이 애플리케이션을 분석하고 그 순간 알려진 것을 기준으로 구조를 확정한다. 런타임이 아니다.**

**결과 셋**:
1. **`@Profile`과 `@ConditionalOnProperty`가 시작할 때가 아니라 빌드할 때 평가된다**
2. **런타임에 property를 바꿔도 애플리케이션 컨텍스트가 다시 만들어지지 않는다**
3. **컴파일 후에 새 bean 설정을 들여올 수 없다**

> **특정 profile용 실행 파일이 필요하면 그 profile을 빌드 때 켜야 한다.**

**JVM 세계의 습관이 정면으로 깨진다**:

| | **JVM** | **네이티브** |
|---|---|---|
| 아티팩트 | **하나** | **환경마다 다를 수 있다** |
| 환경 구분 | `SPRING_PROFILES_ACTIVE` | **빌드 파라미터** |
| CI 빌드 횟수 | 1 | **환경 수만큼** |
| 검증 | **배포물 하나를 테스트** | **각 빌드를 따로 테스트** |

**[[../chapter-7-releasing-an-application-with-spring-boot/04a-scaling-with-spring-boot|Ch7]]의 "바이트 단위로 같은 코드"와 [[../chapter-6-configuring-an-application-with-spring-boot/02-creating-profile-based-property-files|Ch6]]의 "환경마다 JAR을 빌드하지 마라"가 여기서 흔들린다.** 그 원칙을 지키려면 **조건부 bean 구성을 쓰지 않는 설계**로 가야 한다.

**주의할 경계**: 모든 설정이 빌드 시점인 것은 아니다. **bean 구조를 바꾸지 않는 값**(포트, DB URL, 로그 레벨)은 여전히 런타임에 주입된다. **구조를 바꾸는 조건**만 빌드로 굳는다.

**§6의 귀결**: **플러그인 아키텍처**(런타임에 JAR을 얹어 기능을 늘리는 구조)는 **닫힌 세계 가정과 근본적으로 충돌**한다.

## Q4. Hibernate 바이트코드 강화를 빌드 시점으로 옮기는 이유

**네이티브에서는 런타임 바이트코드 조작과 프록시 기반 동작이 더 제약되는데, Hibernate가 lazy loading을 구현하는 방식이 바로 그 둘이기 때문이다.**

```
런타임에 하려던 일  →  네이티브의 제약에 걸린다
        ↓
빌드로 당긴다       →  제약에 걸리지 않는다
```

**`enhance` 골이 하는 일**: **컴파일된 엔티티 클래스의 바이트코드를 빌드 중에 고쳐 놓는다.**

**해당되는 기능**: **lazy attribute loading, dirty tracking, association management.**

**언제 필요한가**: **Boot 4의 AOT 엔진이 흔한 네이티브 설정은 자동 처리하므로 대부분의 Spring Data JPA 앱은 추가 설정이 필요 없다.** 위 **바이트코드 강화 기능에 기대고 있을 때만** 플러그인을 넣는다(§6).

> **주의 — 책이 제시하는 세 옵션은 이미 deprecated다.** `enableLazyInitialization`·`enableDirtyTracking`·`enableAssociationManagement`는 Hibernate 공식 문서 기준 **모두 deprecated for removal**이고, **lazy loading은 제거 후 기본 활성이 될 예정**이다. 책은 현재 권장 설정처럼 제시하지만 **쓰는 Hibernate 버전의 문서를 확인해야** 한다.

**일반화하면 이 장 전체의 패턴이다** — **런타임에 하던 일을 빌드로 옮긴다.** Spring AOT도, 프록시 사전 생성도, 도달성 분석도 같은 방향이다. 그 대가가 Q3의 유연성 상실이다.

**비유로 보면** 이사 짐 줄이기 — 도달성 분석은 **"지난 1년간 쓴 물건만 가져간다"**는 규칙이다. **깨지는 지점 둘**:
- **사람은 "이건 안 썼지만 필요할 때가 있다"고 예외를 만들 수 있다.** 도달성 분석은 규칙만 따르므로 **예외 목록을 우리가 써 줘야** 한다 → [[05-configuring-reflection-and-runtime-hints]]
- **이사는 짐을 버려도 나중에 다시 살 수 있지만** 네이티브 이미지는 그럴 수 없다 — **빠진 클래스는 런타임에 복구되지 않고 예외가 될 뿐이다**
