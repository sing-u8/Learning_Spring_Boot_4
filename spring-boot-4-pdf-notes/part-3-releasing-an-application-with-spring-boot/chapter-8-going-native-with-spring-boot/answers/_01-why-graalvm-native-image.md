## Q1. 30초 startup이 20년 전에는 문제가 아니었다가 지금 문제가 된 이유

**배포 방식이 바뀌었기 때문이다.**

**예전의 전제**: **웹 앱은 한 번 뜨면 몇 주씩 살아 있고, 30초는 그 몇 주에 비하면 없는 시간이다.**

**그 전제가 두 곳에서 무너졌다.**

**① 지속 배포.** **인스턴스 10,000개가 동시에 돌면서 하루에도 여러 번 교체되는 시스템**에서 30초는 **더 이상 한 번이 아니다.**

```
교체할 때마다 10,000번 지불하는 시간
        ↓
지속 배포를 열심히 할수록 더 자주 지불한다
```

**역설이 여기 있다** — **배포를 잘할수록 이 비용이 커진다.** 개선하려는 실천이 그 자체로 비용을 증폭시킨다.

**② 실행 가능 함수.** **AWS Lambda 같은 플랫폼에서는 함수 하나가 애플리케이션 전체로 배포**되고, **요청이 올 때 즉시 띄운다.** 이 **서버리스** 모델에서 **cold start는 기술 선택을 좌우하는 1순위 지표**가 된다.

**②가 ①보다 극단적이다** — ①에서는 30초가 **배포 시간**에 섞이지만, ②에서는 **사용자가 직접 기다린다.**

**[[../chapter-7-releasing-an-application-with-spring-boot/04a-scaling-with-spring-boot|Ch7]]의 "1만 개 복제"가 여기서 비용을 드러낸다** — 수평 확장이 쉬워질수록 **기동 비용이 곱해진다.**

## Q2. JVM이 시작할 때 하는 네 가지 중 네이티브 이미지가 없애는 것

**JVM이 뜨면서 하는 일**:
1. **바이트코드로 된 class 파일 수천 개를 찾아 읽는다**
2. **검증하고 링크하고 초기화한다**
3. **처음엔 인터프리터로 실행한다 — 느리다**
4. **실행하면서 프로파일을 모아, 자주 도는 코드를 JIT로 점점 최적화한다**

> **3번과 4번이 startup을 잡아먹는다.**

**네이티브 이미지가 없애는 것: 네 가지 전부.**

```
1. 실행 파일을 메모리에 올린다.
2. main 부터 실행한다.  끝.

▶ class 로딩도, 인터프리터 구간도, 워밍업도 없다.
```

**이 장의 예제가 0.528초에 뜨는 이유다.**

**대가 — 4번을 없앤 것이 그대로 대가가 된다.**

**JIT는 실행 중에 실제 패턴을 보고 최적화한다.** AOT는 **빌드 시점의 추측**으로만 최적화한다. 그래서
- **오래 도는 서비스에서는 최고 처리량이 JVM 쪽이 더 높을 수 있다**
- **"네이티브가 항상 빠르다"는 틀리다** — **빠른 것은 시작**이다

**그리고 이 비용이 매 인스턴스가 처음부터 다시 지불하는 것이라는 점이 Q1과 이어진다** — **앞 인스턴스가 애써 알아낸 최적화는 프로세스가 죽는 순간 사라진다.** 인스턴스가 자주 교체될수록 **JIT의 투자 회수 기간이 짧아진다.**

**이 트레이드오프가 [[07b-comparing-four-execution-strategies]]의 핵심이다.**

## Q3. "GraalVM에서 돌린다"가 이 장에서 실제로 뜻하는 것

**`native-image` AOT 컴파일러로 독립 실행 파일을 만든다는 뜻이다. VM으로서의 GraalVM을 쓰는 것이 아니다.**

| GraalVM의 얼굴 | 무엇인가 | **이 장에서 쓰는가** |
|---|---|---|
| **런타임(VM)** | Graal 컴파일러를 JIT로 쓰는 JVM. 여러 언어를 한 VM에서 돌린다 | **아니오** |
| **`native-image` 도구** | 애플리케이션을 **AOT 컴파일해 독립 실행 파일**을 만드는 컴파일러 | **예, 이것만** |

> **그래서 최종 산출물에는 JVM이 아예 없다.**

**혼동의 출처는 책 자체다** — 책 p.230은 **"GraalVM은 본질적으로 새로운 가상 머신"**이라 소개하며 **"JAR을 JVM 말고 GraalVM에서 돌려라"**라고 쓴다. **그건 GraalVM의 한 얼굴**이다.

**같은 이름이 두 가지를 가리키니 "GraalVM에서 돌린다"는 문장이 나올 때마다 어느 쪽인지 확인해야 한다.**

**판별법**: **산출물에 JVM이 있는가.**
```
VM 으로서의 GraalVM: JAR 을 넣는다 → VM 이 실행한다      (JVM 있음)
native-image:        JAR 을 넣는다 → 실행 파일이 나온다   (JVM 없음)
```

## Q4. write once, run anywhere를 포기해도 괜찮은 조건

**CI가 타깃과 같은 OS·아키텍처에서 빌드하는 경우다.**

> **"어디서나 돌아간다"는 성질은 애초에 쓰지 않던 성질이다.**

**Java 초창기의 혁명이 무엇이었나**: **그 이전에는 배포할 기계 아키텍처마다 따로 컴파일해야 했다.** 바이트코드와 JVM이 그 짐을 없앴고, **덤으로 JIT 같은 컴파일 이후 최적화까지** 열어 줬다.

**네이티브 이미지는 그 시절로 되돌아간다** — **산출물은 빌드한 플랫폼 전용**이다.

**손해가 아닌 조건**:
- **배포 대상이 하나로 고정돼 있다** — 예: `linux/amd64` 컨테이너만
- **CI가 그 플랫폼에서 빌드한다** — [[04-building-native-container-images]]가 그 방법
- **개발자 기계에서 만든 바이너리를 배포하지 않는다**

**손해가 되는 조건**: 여러 아키텍처를 지원해야 하면 **아키텍처마다 빌드 파이프라인**이 필요하다. `amd64`와 `arm64`를 둘 다 지원하면 **빌드가 두 배**다.

**[[../chapter-7-releasing-an-application-with-spring-boot/02-building-a-docker-container|Ch7]]의 컨테이너 논의와 이어진다** — 컨테이너도 **아키텍처별로 이미지가 다르다.** 이미 그 제약을 받아들인 배포라면 **네이티브가 새 제약을 더하지 않는다.**

**비유로 보면**: 즉석 요리(JVM)와 밀키트(네이티브). 다만 **깨지는 지점 둘**이 있다 —
- **밀키트는 아무 데서나 데울 수 있지만 네이티브 이미지는 만든 플랫폼에서만 돈다.** **오히려 원재료(바이트코드) 쪽이 이동성이 좋다.**
- **밀키트는 "무엇이 들어갈지"를 요리사가 정하지만, 네이티브 이미지는 컴파일러가 도달성 분석으로 정한다.** **요리사가 넣으려던 재료가 조용히 빠질 수 있고**, 그 문제가 [[02-adapting-an-application-for-native-image]]의 주제다.
