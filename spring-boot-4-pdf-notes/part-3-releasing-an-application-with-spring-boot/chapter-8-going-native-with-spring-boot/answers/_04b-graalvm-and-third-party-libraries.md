## Q1. 빌드가 성공했는데 실행 중에 실패하는 이유

**네이티브 빌드 성공은 "도달 가능하다고 판정된 코드가 컴파일됐다"는 뜻이지, 필요한 코드가 다 담겼다는 뜻이 아니다.**

```
도달성 분석: 화살표가 안 닿는 것은 잘라낸다
        ↓
잘려 나간 것이 실제로는 필요했다
        ↓
빌드는 조용히 성공한다
        ↓
그 경로를 처음 실행할 때 터진다  ← 배포 후일 수 있다
```

> **잘려 나간 것은 그 경로를 실행할 때 드러난다.**

**어디서 오는가**: **실제 프로젝트의 `pom.xml`을 열어 보면 Spring 것이 아닌 의존성이 훨씬 많다** — 로깅, JSON, 검증, 메트릭, 클라이언트 SDK, 사내 공용 라이브러리, **그리고 그것들이 다시 끌고 오는 전이 의존성.** **네이티브 빌드는 이 전체를 도달성 분석에 넣는다.**

**그중 하나라도 런타임 리플렉션에 기대고 있으면 이 일이 일어난다.**

**대응**: **네이티브 전환에는 실행 경로를 넓게 훑는 통합 테스트가 JVM 때보다 더 중요하다.** 그리고 **JVM 테스트는 통과한다** — 잘라내기가 없으므로.

**가장 위험한 조합**: **자주 안 타는 예외 처리 경로**의 리플렉션. 통합 테스트도 안 밟고, **장애 상황에서 처음 실행된다.**

## Q2. 네이티브에서 위험한 라이브러리 두 부류

> **네이티브 이미지는 라이브러리가 GraalVM의 분석 모델에 협조해 주기를 요구한다. 협조하지 않는 두 부류가 있다.**

| 부류 | 무엇인가 |
|---|---|
| **과도하게 reflective한 라이브러리** | 특히 **런타임 리플렉션에 크게 기대는** 것 |
| **동적인 라이브러리** | **런타임에 클래스를 만들거나 바꾸는** 것 |

**이런 것들은 추가 설정이나 힌트가 필요하다** → [[05-configuring-reflection-and-runtime-hints]].

**빌드 시점에 알려져야 하는 네 가지**(닫힌 세계 가정):
| 알려져야 할 것 | **왜** |
|---|---|
| **리플렉션** | **대상 클래스로 가는 화살표를 정적으로 그릴 수 없다** |
| **동적 프록시** | **런타임 생성이 불가능하므로 미리 만들어야 한다** |
| **직렬화** | **역직렬화는 이름으로 타입을 찾는 리플렉션이다** |
| **resource 로딩** | **코드에 참조가 없는 파일은 이미지에 안 담긴다** |

**Spring 쪽은 됐다** — **Web, Data, Security, Actuator**가 내장 AOT 처리와 네이티브 지원을 갖는다. `@RestController`, `JpaRepository`, `SecurityFilterChain`, `/actuator/health`는 **이미 검증된 영역**이다.

**주의**: **"Spring이 지원하니 Spring Data JPA도 문제없다"**는 대체로 맞지만, **Hibernate의 lazy loading처럼 런타임 바이트코드 조작에 기대는 기능**은 별도 처리가 필요하다([[02-adapting-an-application-for-native-image]]).

## Q3. reachability metadata가 있으면 사용하는 쪽이 안 해도 되는 것

**아무것도 안 해도 된다 — 힌트를 직접 쓰지 않아도 된다.**

**reachability metadata**: 라이브러리가 **"내 안에서는 여기에 리플렉션이 쓰인다"고 미리 싣는 설정**이다.

```
라이브러리가 metadata 를 함께 배포
        ↓
빌드 시 GraalVM 이 그것을 읽는다
        ↓
사용하는 쪽은 [[05-configuring-reflection-and-runtime-hints]] 의 힌트를 쓸 필요가 없다
```

> **주류 라이브러리는 대체로 GraalVM을 지원하거나 reachability metadata를 함께 배포한다.**

**출처가 두 곳이라는 점이 실무 지식이다**:
- **라이브러리가 자기 JAR에 싣는 경우**
- **GraalVM 커뮤니티가 별도 저장소에 모아 두는 경우** — **후자를 쓰려면 빌드 설정에 그 저장소를 켜야 한다**

**"안 된다"가 "영영 안 된다"가 아니다**: **네이티브 지원은 Java 생태계 안에서 점진적으로 올라오고 있다.** Spring 팀은 spring.io/blog에서 모범 사례와 개선 사항을 계속 낸다.

**실무적 귀결**: **의존성 하나를 올릴 때마다 네이티브 지원 상태가 달라질 수 있다 — 좋은 쪽으로도, 나쁜 쪽으로도.** 그래서 **의존성 업그레이드마다 네이티브 빌드와 통합 테스트를 다시 돌린다**(§6).

## Q4. 네이티브 전환 프로젝트를 시작할 때 의존성 목록으로 먼저 할 일

> **라이브러리 목록을 뽑아 네이티브 지원 여부를 확인하는 것이 첫 작업이다.**

**왜 이것이 첫 작업인가**: **의존성 트리가 넓고 통제 밖이라면 네이티브 전환의 난이도를 먼저 조사해야** 한다. 코드를 다 고친 뒤에 **못 쓰는 라이브러리를 발견하면** 그때까지의 작업이 헛수고가 된다.

**확인 결과에 따른 분기**:
| 상태 | 대응 |
|---|---|
| metadata를 함께 배포 | **그대로 쓴다** |
| 커뮤니티 저장소에 있다 | **빌드 설정에 저장소를 켠다** |
| 없고 소스를 못 고친다 | **힌트로 우회하거나 교체를 검토한다** |
| 근본적으로 동적이다 | **네이티브를 포기하거나 그 부분을 분리한다** |

**그리고 네이티브가 막히면 중간 지대를 본다**(§6) — **JVM에 남으면서 startup을 줄이면 이 문제가 아예 사라진다** → [[07-using-java-25-aot-cache]]. **의존성 조사에서 벽이 보이면 이 선택지를 먼저 비교**하는 것이 합리적이다.

**책이 이 절을 닫으며 다음 절로 넘기는 문장도 함께**: **어떤 경우에는 호환되는 라이브러리를 고르는 것만으로 해결되지 않는다.** AOT 분석이 다 추론할 수 없을 때 **우리가 그 정보를 명시적으로 줘야** 하고, 그 수단이 **런타임 힌트**다.

**비유로 보면** 해외 이주 서류 — **동행하는 가족 구성원 하나가 서류를 안 갖췄으면 전체가 막힌다.** **깨지는 지점 둘**:
- **출국장에서는 막히지만 네이티브 이미지는 빌드가 조용히 성공한다** — **"출국은 됐는데 현지에서 못 산다"**에 가깝다(Q1)
- **서류는 본인이 준비할 수 있지만 라이브러리의 리플렉션은 내가 소스를 고칠 수 없다** — 그래서 **힌트라는 우회로**가 필요하다
