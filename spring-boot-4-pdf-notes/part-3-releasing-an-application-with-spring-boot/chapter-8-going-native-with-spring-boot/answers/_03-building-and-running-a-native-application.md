## Q1. `clean package`와 `-Pnative native:compile`의 산출물 차이

| | `./mvnw clean package` | `./mvnw -Pnative clean native:compile` |
|---|---|---|
| **산출물** | **uber JAR** | **빌드한 플랫폼용 실행 파일** |
| **실행 방법** | `java -jar target/ch8.jar` | **`target/ch8`** (JVM 없이 직접) |
| **이식성** | **write once, run anywhere** | **같은 OS·아키텍처에서만** |
| 빌드 시간 | 수십 초 | **수 분** (메서드 컴파일만 161초) |
| 빌드 메모리 | 보통 | **Peak RSS 5.03GB** |
| 크기 | 수십 MB | **159.62MB** |

**필요한 도구도 다르다**: **Boot 4는 빌드와 실행에 Java 17 이상이면 되지만, 네이티브 이미지 생성은 표준 JDK를 넘어선다.** **GraalVM 배포판**(또는 `native-image`가 설치된 호환 JDK)이 있어야 한다.

**`file target/ch8`로 확인된다** — 저자의 기계에서는 **`Mach-O 64-bit executable arm64`**가 나온다.

**주의 — `-Pnative`를 붙인 `package`는 또 다르다**: **여전히 JAR을 만들되 Spring AOT 처리를 추가로 돌린다.** 그 산출물이 [[07a-enabling-aot-cache-for-spring-boot]]에서 쓰인다. **세 가지 조합이 있는 셈이다.**

**JDK 전환**: macOS·Linux에서는 **SDKMAN**이 가장 간단하다(`sdk use java 25.0.2-graal`). **최신 GraalVM은 현재 Java 버전과 정렬**돼 있어 **툴링이 JDK 배포판 안에 통합**돼 있다 — 예전처럼 "JDK 따로, GraalVM 따로"가 아니다.

## Q2. 이미지를 키우는 주범을 찾으려면

**코드 영역 기여 top 목록을 본다.**

```
hibernate-core  21.60MB
java.base       16.18MB
svm.jar          9.74MB
```

> **이미지를 키우는 것이 내 코드가 아니라 의존성임이 드러난다. Hibernate 하나가 전체의 13%다.**

**빌드 출력에서 읽을 다른 줄들**:

| 읽을 곳 | 값 | **무엇을 뜻하나** |
|---|---|---|
| 단계별 시간 | `[6/8] Compiling methods... 161.0s @ 6.14GB` | 8단계 중 **메서드 컴파일이 압도적** — 빌드가 느린 이유 |
| 이미지 크기 | **159.62MB** (코드 영역 94.15 / 이미지 힙 63.70 / 기타 1.78) | Q3 |
| 이미지 힙 객체 | `27.36MB byte[] for code metadata`, **`1.65MB byte[] for reflection metadata`** | **리플렉션 힌트가 공짜가 아니라 이미지에 실리는 비용** |
| 자원 소모 | **`Peak RSS: 5.03GB`**, `CPU load: 4.00` | **CI 러너 메모리 스펙의 기준** → Q4 |
| Recommendations | PGO, `--march=native`, max heap | 더 짜낼 여지 |

**`Security report`도 눈여겨볼 만하다** — **"Binary includes Java deserialization"**. **네이티브 이미지도 역직렬화 취약점에서 자유롭지 않다.**

**실무적 활용**: 이미지가 너무 크면 **의존성을 줄이는 것이 내 코드를 줄이는 것보다 효과적**이다. 그리고 **reflection metadata 줄**을 보면 [[05-configuring-reflection-and-runtime-hints]]에서 등록한 힌트의 비용이 눈에 보인다.

## Q3. 159.62MB와 "메모리를 적게 쓴다"는 모순인가

**모순이 아니다. 두 숫자가 서로 다른 것을 잰다.**

```
159.62MB  = 실행 파일 크기  (디스크)
적게 쓴다  = 런타임 메모리     (RAM)
```

> **"네이티브는 작다"는 말은 파일이 아니라 런타임 메모리 얘기다.**

**왜 파일이 커지나**: **JVM이 하던 일을 실행 파일이 떠맡았다.** 런타임, 표준 라이브러리, 필요한 모든 클래스가 **파일 안에** 들어간다. uber JAR은 **바이트코드**를 담지만 네이티브 파일은 **기계어 + 이미지 힙**을 담는다.

**왜 런타임 메모리는 줄어드나**: **클래스 메타데이터, JIT 컴파일러, 프로파일링 데이터, 코드 캐시**가 없다. 그리고 **필요한 것만 들어 있으므로** 로드할 것도 적다.

**두 숫자를 섞으면 배포 스토리지 계획이 틀어진다** — "네이티브니까 이미지가 작겠지"로 컨테이너 레지스트리 용량을 잡으면 어긋난다.

**비유로 보면** 사진 인화 — **인화한 사진은 크기와 종이가 정해지지만 필름은 나중에 다른 크기로도 뽑을 수 있다.** 그래서 **네이티브 실행 파일이 JAR보다 커진다.** (다른 하나의 깨짐: **액자는 아무 벽에나 걸 수 있지만 네이티브 실행 파일은 같은 OS·아키텍처에서만 걸린다.**)

**함께 기억할 것**: **`java -jar`가 아니므로 JVM 옵션(`-Xmx` 등)도 그대로 통하지 않는다.** `-XX:MaximumHeapSizePercent` 같은 **네이티브 전용 옵션**을 쓴다.

## Q4. 로컬에서 되던 네이티브 빌드가 CI에서 실패하면

**가장 먼저 CI 러너의 메모리 스펙을 확인한다.**

> **Peak RSS 5.03GB는 흔한 CI 러너의 기본 메모리를 넘길 수 있다. 네이티브 빌드가 로컬에선 되는데 CI에서 OOM으로 죽는 전형적 원인이다.**

**왜 이것이 1순위인가**:
- **증상이 명확하지 않다** — OOM이 컴파일러 내부에서 나면 **자바 오류처럼 보이지 않는다**
- **로컬 노트북은 16~32GB**인데 **CI 기본은 2~7GB**인 경우가 흔하다
- **빌드 로그에 숫자가 이미 있다** — Q2의 `Peak RSS` 줄

**다음으로 확인할 것**:
1. **CI에 GraalVM이 설치돼 있는가** — 표준 JDK로는 `native:compile`이 안 된다
2. **아키텍처가 같은가** — 로컬 `arm64`, CI `amd64`면 다른 문제가 날 수 있다
3. **빌드 타임아웃** — 161초 이상 걸리는 단계가 타임아웃에 걸릴 수 있다

**구조적 대응**(§6): **빌드 시간이 개발 반복을 막으면 평소 개발은 JVM으로 하고 네이티브 빌드는 CI에만 둔다.** 그리고 **로컬 OS와 배포 OS가 다르면** 여기서 만든 실행 파일을 쓸 수 없으므로 [[04-building-native-container-images]]로 간다.

**놓치기 쉬운 것**: **의존성을 바꾼 뒤에는 반드시 네이티브 빌드를 다시 돌린다.** **JVM에서 되는 것이 네이티브에서 안 될 수 있다** — [[04b-graalvm-and-third-party-libraries]].
