## Q1. `spring-boot-starter-webmvc` 한 줄에서 MVC 빈이 생기기까지

질문이 요구하는 것은 단계 나열이 아니라 **두 시점의 경계를 어디에 긋느냐**다.

### 빌드 시점 — 산출물은 빈이 아니라 클래스패스다

1. 개발자가 스타터 하나를 선언한다. — 라이브러리 목록이 아니라 “Servlet 기반 MVC를 쓴다”는 아키텍처 결정을 표현하기 위해서다.
2. Maven·Gradle이 그 스타터의 전이 의존성을 따라간다. — 기능을 구성하는 모듈을 빠짐없이 넣기 위해서다.
3. Boot의 의존성 관리(BOM)가 각 모듈의 버전을 정렬한다. — 개별 최신 버전을 섞어 호환이 깨지는 문제를 줄이기 위해서다.

✅ 실제로 무엇이 들어오는지는 `starter/spring-boot-starter-webmvc/build.gradle`에서 확인된다.

```groovy
api(project(":starter:spring-boot-starter"))          // 로깅·설정 등 공통 기반
api(project(":starter:spring-boot-starter-jackson"))  // JSON
api(project(":starter:spring-boot-starter-tomcat"))   // 내장 서블릿 컨테이너
api(project(":module:spring-boot-http-converter"))    // HTTP 메시지 변환
api(project(":module:spring-boot-webmvc"))            // MVC와 그 자동 구성
```

**여기까지의 결과물은 빈이 아니라 달라진 클래스패스뿐이다.** 애플리케이션은 아직 시작하지도 않았다.

### 시작 시점 — 조건을 평가해 빈 정의를 보탠다

4. 자동 구성이 새 클래스패스를 검사한다. — 그 기술을 실제로 쓸 조건이 갖춰졌는지 확인하기 위해서다.
5. 이미 등록된 사용자 빈과 프로퍼티를 포함한 추가 조건을 평가한다. — 스타터가 있다는 이유만으로 사용자의 명시적 구성을 덮지 않기 위해서다.
6. 조건을 만족하는 기반 빈과 런타임 관례를 적용한다. — 반복 인프라 조립을 줄이기 위해서다.

### 경계에서 틀리기 쉬운 것

```text
틀림:  starter = 자동으로 생성된 bean

맞음:  starter 선언 → 관련 의존성 유입 → classpath 변화
       → auto-configuration 조건 평가 → 필요한 bean 등록
```

스타터는 **빈을 하나도 만들지 않는다.** 클래스패스를 바꿔 자동 구성의 *입력*을 만들 뿐이고, 실제 객체 생성과 와이어링은 그다음에 애플리케이션 컨텍스트가 한다. [[01-autoconfiguring-spring-beans]]의 “자동 구성은 빈 정의를 보태고, 컨텍스트가 객체를 만든다”와 이어 붙이면 세 단계 사슬이 완성된다.

> **스타터 → 클래스패스 → (조건 평가) → 빈 정의 → (컨텍스트) → 객체**

## Q2. 스타터와 자동 구성이 같은 기능이 아닌 이유

세 가지가 전부 다르다.

| | 스타터 | 자동 구성 |
|---|---|---|
| 언제 | 빌드 의존성 해석 | 애플리케이션 시작 |
| 누가 | Maven·Gradle | JVM 안의 Spring Boot 코드 |
| 무엇을 내놓나 | 클래스패스의 변화 | 컨텍스트의 빈 정의 |
| 어디 적혀 있나 | `pom.xml` / `build.gradle` | 라이브러리 안의 `@AutoConfiguration` 클래스 |

**판별은 양방향으로 해 보면 확실하다.**

- *스타터를 넣었는데 빈이 안 생길 수 있는가?* — **있다.** 조건이 거짓이면(예: 사용자가 같은 타입의 빈을 이미 제공했으면) 자동 구성이 물러난다. 스타터는 그대로 있는데 빈은 없다.
- *스타터 없이 빈이 생길 수 있는가?* — **있다.** 개별 의존성을 직접 골라 넣어도 자동 구성의 클래스 조건이 충족되면 빈은 등록된다. 스타터는 편의이지 필수 관문이 아니다.

두 방향 모두 성립한다는 사실 자체가 둘이 별개 기능이라는 증거다. 하나가 다른 하나를 **함의하지 않는다.**

이어져 보이는 이유는 스타터가 자동 구성 모듈과 그 기반 라이브러리를 함께 끌고 오기 때문이다. 인과의 사슬로 연결돼 있을 뿐, 같은 층의 같은 일이 아니다.

## Q3. 스타터와 BOM은 각각 어느 질문에 답하는가

| | 스타터 | BOM |
|---|---|---|
| 답하는 질문 | **무엇을** 함께 가져올까 | 각 모듈을 **어느 버전으로** 쓸까 |
| 결과 | 관련 모듈이 클래스패스에 들어온다 | Spring과 주요 서드파티 버전이 정렬된다 |

증거는 빌드 파일에 그대로 보인다.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
</dependency>
```

`<version>`이 없다. 스타터가 “무엇”만 말하고 “어느 버전”은 다른 곳에서 오기 때문이다. 두 관심사가 한 곳에 있었다면 이 줄에 버전이 있어야 했다.

**왜 굳이 나눠 두었나.** 합쳐 두면 버전 하나를 올릴 때 목록까지 함께 건드려야 한다. 분리돼 있으므로 스타터 선언은 그대로 두고 Boot 버전만 올려 전체를 정렬할 수 있고, 반대로 스타터를 쓰지 않고 개별 의존성을 직접 골라도 BOM 관리 아래에 있으면 버전은 여전히 맞는다. **두 축을 독립적으로 움직일 수 있다는 것이 분리의 실익이다.**

**경계**: 스타터만으로 버전 호환이 다 풀리지 않고, BOM만으로 필요한 라이브러리가 자동 선택되지 않는다. 각자 다른 질문에만 답한다.

## Q4. Spring MVC · WebFlux · Spring Web의 관계

**한 줄**: Spring Web은 **공통 기반**이고, MVC와 WebFlux는 그 위에서 갈라지는 **실행 모델**이다.

| 구분 질문 | Spring MVC | Spring WebFlux | Spring Web |
|---|---|---|---|
| 무엇인가 | Servlet 기반 완성 웹 스택 | 리액티브·논블로킹 완성 웹 스택 | 두 스택이 공유하는 HTTP 추상화·애노테이션 기반 |
| 빌드 의도 | `starter-webmvc` | `starter-webflux` | 보통 완성 스택을 통해 함께 들어온다 |
| 핵심 차이 | 전통적 Servlet 요청 처리 | 리액티브 실행 모델 | **실행 모델 선택 자체가 아니다** |

**가장 흔한 함정**은 세 번째 열 마지막 칸이다. 두 스택이 `@GetMapping` 같은 같은 애노테이션을 쓸 수 있다고 해서 **실행 모델이 같아지지 않는다.** 공유하는 것은 요청을 표현하는 어휘이지 요청을 처리하는 방식이 아니다.

✅ 물증이 스타터 구성에 있다. `spring-boot-starter-webmvc`는 `spring-boot-starter-tomcat`을 끌어온다 — Servlet 컨테이너다. WebFlux 스타터는 그 자리에 리액티브 실행 모델에 맞는 것이 들어간다. **실행 모델의 선택이 빌드 파일 한 줄에서 이미 끝난다.**

**선택 기준**: 더 최신이라서 WebFlux를 고르거나 익숙해서 MVC를 고르는 것이 아니라, 애플리케이션의 I/O 특성과 팀이 감당할 프로그래밍 모델을 기준으로 정한다.

## Q5. MVC 스타터의 여섯 범위와 별도로 선택해야 하는 것

### 책이 열거한 여섯 가지

1. **Spring MVC와 공통 Spring Web 인프라** — 컨트롤러·요청·응답을 다루는 프로그래밍 모델이 필요하므로
2. **Jackson을 통한 JSON 직렬화·역직렬화** — Java 객체와 HTTP JSON 본문을 변환해야 하므로
3. **내장 서블릿 컨테이너** — 외부 애플리케이션 서버에 WAR를 배포하지 않고 독립 실행하기 위해
4. **검증과 오류 처리 인프라** — 잘못된 요청을 일관되게 판별하고 응답하기 위해 (아래 주의 참조)
5. **로깅과 구성 지원** — 실행 상태를 관찰하고 환경별 값을 바꿀 수 있어야 하므로
6. **MVC 스택에 범위를 맞춘 자동 구성** — 리액티브 스택과 섞지 않고 선택한 아키텍처의 빈만 구성하기 위해

✅ 실제 좌표는 다섯 줄이고(`spring-boot-starter`, `-jackson`, `-tomcat`, `spring-boot-http-converter`, `spring-boot-webmvc`), 기능 여섯 개가 그 안에 담긴다. 공통 기반인 `spring-boot-starter`가 5번(로깅·설정)을 맡는 구조다.

### 별도로 선택해야 하는 것 — 템플릿 엔진

`starter-webmvc`는 실행 가능한 웹 애플리케이션의 기반을 주지만 **서버 측 HTML 템플릿 엔진은 포함하지 않는다.** Thymeleaf 같은 서버 렌더링을 원하면 목적에 맞는 별도 스타터를 고른다.

이유를 생각해 보면 당연하다. JSON API만 내는 서비스와 서버가 HTML을 그리는 서비스는 **다른 아키텍처**다. 스타터가 그 선택을 대신하면 “API 전용 서비스에 쓰지도 않는 템플릿 엔진이 들어와 있는” 상태가 기본값이 된다. 명시성을 택한 것이다.

### ⚠ 검증도 자동으로 따라오지 않을 수 있다 — 이번 대조에서 찾은 것

✅ 위 다섯 줄에 **Bean Validation 스타터가 없다.** 책은 4번에서 “검증과 오류 처리 인프라”를 MVC 스타터의 범위로 열거하지만 실제 좌표에서는 확인되지 않는다. `@Valid`로 요청 본문을 검증하려면 `spring-boot-starter-validation`을 따로 추가해야 할 수 있다. 오류 처리(`@ExceptionHandler`, 기본 오류 응답)는 MVC 모듈 쪽 기능이라 별개다.

이 대조는 저장소 `main` 브랜치의 빌드 파일을 본 것이므로, 실제로 쓰는 버전에서 `mvn dependency:tree`나 `./gradlew dependencies`로 한 번 확인하는 편이 안전하다.

**그 밖에 별도로 필요한 것**: 데이터베이스 드라이버, 비즈니스 기능 라이브러리, 운영 환경의 비밀값.

## Q6. Jakarta EE API에 의존하는 것이 모순이 아닌 이유

대립처럼 들리는 이유는 **“Jakarta EE”라는 이름 하나가 층이 다른 두 가지를 가리키기 때문**이다.

| 가리키는 것 | 내용 | Spring과의 관계 |
|---|---|---|
| ① 개별 **API 사양** | `jakarta.servlet`, `jakarta.persistence`, `jakarta.validation` — 인터페이스와 계약만 정의한다 | **가져다 쓴다.** 경쟁 대상이 아니다 |
| ② 완전한 **엔터프라이즈 런타임** | 그 사양을 다 구현한 애플리케이션 서버 + EJB·CDI 중심 프로그래밍 모델 | **여기가 대안 관계다** |

Spring이 대체한 것은 ②이고, 계속 의존하는 것은 ①이다. 두 층을 한 이름으로 부르니 모순처럼 보일 뿐이다.

**그러면 왜 ①까지 자체 규약으로 갈아치우지 않았나.** Servlet API는 “HTTP 요청을 Java 객체로 만들어 애플리케이션에 넘긴다”는 **컨테이너와 애플리케이션 사이의 계약**이다. Tomcat·Jetty·Undertow는 그 계약의 서로 다른 구현이다. Spring MVC가 자기만의 서버 규약을 만들었다면 그 컨테이너를 하나도 못 쓰고, 서버를 바꿀 때마다 애플리케이션을 고쳐야 했을 것이다. **표준 계약에 의존하는 것은 구현 교체 가능성을 사는 값이다.**

이것은 [[01-autoconfiguring-spring-beans]]에서 `BookRepository`가 `DataSource`라는 계약에만 의존한 것과 **같은 형태의 판단**이며, 그 판단이 프레임워크 규모로 적용된 것이다. 계약에 의존하고 구현은 밖에서 고른다.

### 공식 문서에서 확인되는 근거 셋

- ✅ Spring Boot 4는 **Servlet 6.1**을 요구하고 Tomcat 11.0.x·Jetty 12.1.x를 지원하며, “any Servlet 6.1+ compatible container”에 배포할 수 있다고 명시한다. 교체 가능성이 문서화된 계약이다.
- ✅ Boot의 BOM이 `jakarta.servlet-api` 6.1.0, `jakarta.persistence-api` 3.2.0, `jakarta.validation-api` 3.1.1 같은 **사양 API의 버전을 직접 관리한다.** 감추는 것이 아니라 정면으로 의존한다.
- ✅ Boot 4는 빌드 단계에서 `javax.*` 의존성을 **금지한다**(`javax.batch`·`javax.cache`·`javax.money`만 예외). `javax.*` → `jakarta.*`는 사양 소유권이 Oracle에서 Eclipse Foundation으로 넘어가며 이름공간이 바뀐 결과이고, Boot 4는 그 이관을 완료된 것으로 강제한다.

## Q7. 테스트 스타터가 기술별로 나뉘면 생기는 이점

이점이 성격이 다른 **두 축**이다. 한 덩어리로 말하면 둘 다 흐려진다.

| 축 | 나뉘기 전 | 나뉜 뒤 |
|---|---|---|
| **테스트 범위** | 대상 계층과 무관한 의존성까지 들어와, 무엇을 띄워야 하는지가 빌드에서 안 드러난다 | 대상 계층에 맞춘 지원만 들어온다. 컨텍스트가 작아 **빠르고**, 실패 시 **의심할 범위가 좁다** |
| **빌드 가독성** | 테스트 의존성 한 줄이 모든 프로젝트에서 똑같아 정보가 없다 | 빌드 파일만 보고 “이 프로젝트가 어느 계층을 시험하는가”를 읽을 수 있다 |

두 번째 축은 운영 스타터에서 `webmvc`와 `webflux`를 이름으로 가른 것과 **같은 논리가 테스트에 적용된 것**이다. 빌드 파일이 라이브러리 목록이 아니라 설계 선언이 된다.

절차로 쓰면 셋이다.

1. 운영 코드의 기술 스택을 먼저 식별한다. — MVC 테스트와 JPA 테스트는 띄워야 할 인프라가 다르므로
2. 그 기술과 짝을 이루는 테스트 지원을 고른다. — 관련 없는 전체 의존성을 무조건 가져오지 않기 위해
3. 테스트 범위에 맞는 컨텍스트와 도구를 쓴다. — 속도와 실패 원인의 명확성을 높이기 위해

### ⚠ 책의 단순화 — 대체가 아니라 누적이다

✅ 이 서술은 기술별 테스트 스타터가 범용 테스트 스타터를 **대체했다**는 인상을 줄 수 있으나 그렇지 않다. Spring Boot 4 공식 문서는 여전히 “대부분의 개발자는 `spring-boot-starter-test`를 쓴다”고 안내하며, 그 범용 스타터가 JUnit Jupiter·AssertJ·Hamcrest 같은 공통 도구를 가져오고 **거기에 더해** 해당 애플리케이션에 맞는 기술별 `-test` 모듈을 함께 쓰는 구성을 설명한다. 둘은 **누적 관계**다.

또한 이번 대조에서 실제 좌표로 확인된 이름은 `spring-boot-jdbc-test`·`spring-boot-data-jdbc-test`처럼 `spring-boot-{기술}-test` 형태의 **모듈**이었다. 책이 쓰는 `spring-boot-starter-webmvc-test`·`spring-boot-starter-data-jpa-test`라는 정확한 **스타터** 좌표는 이번 대조에서 확인하지 못했다. 빌드 파일에 적기 전에 쓰는 버전의 좌표를 확인한다.

## 이 답안을 읽은 뒤의 재출제 문항

읽는 것은 인출이 아니다. 다음에는 **같은 문장을 반복하지 않고** 엣지 형태로 다시 묻는다.

1. `spring-boot-starter-webmvc`를 넣었는데 기대한 빈이 안 생겼다. 빌드 시점과 시작 시점 중 어디를 먼저 의심하고, 각각 무엇으로 확인하는가?
2. 스타터를 **쓰지 않고** 개별 의존성만으로 같은 결과를 낼 수 있는가? 낼 수 있다면 무엇을 잃는가?
3. Boot 버전만 올리고 스타터 선언은 한 줄도 안 고쳤는데 서드파티 라이브러리 버전이 바뀌었다. 누가 그렇게 했는가?
4. 팀이 `@RestController`와 `@GetMapping`을 그대로 두고 WebFlux로 옮기려 한다. 애노테이션이 같으니 코드는 그대로여도 되는가?
5. API만 내는 서비스에 Thymeleaf가 들어와 있다. 어떻게 들어왔을 수 있으며 무엇을 확인하는가?
6. "Spring은 Jakarta EE를 안 쓴다"고 말하는 사람에게 반례를 세 개 댄다면?
7. `@Valid`를 붙였는데 검증이 동작하지 않는다. 어디부터 보는가?
