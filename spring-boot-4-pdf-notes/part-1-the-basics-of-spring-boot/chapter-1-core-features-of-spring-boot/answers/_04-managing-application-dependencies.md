## Q1. Data JPA만 올리는데 왜 Framework·MVC·Integration까지 확인해야 하나

**한 라이브러리의 버전은 그 라이브러리만의 문제가 아니기 때문이다.** 두 방향으로 번진다.

1. **위로** — 새 Spring Data 릴리스는 특정 Spring Framework 버전을 전제로 만들어진다. 현재 Framework가 그보다 낮으면 컴파일은 되어도 런타임 API가 어긋날 수 있다.
2. **옆으로** — 새 Data 버전이 끌고 오는 **전이 의존성**이 바뀌면, 같은 라이브러리를 공유하는 MVC나 Integration이 다른 버전을 보게 된다.

그래서 "Query by Example 개선 하나"를 얻는 일이 **생태계 전체의 호환 조합 검증**으로 번진다. 책이 든 예처럼 릴리스 노트를 뒤지고 충돌을 푸는 데 일주일이 갈 수 있다.

**핵심 통찰**: 자동 구성과 스타터가 줄여 준 **시작 비용**을, 이 문제가 **유지보수 단계에서 다시 청구한다.** 의존성 관리는 그 청구서를 막는 장치다.

**그리고 최신이 최선이 아니다.** 각 라이브러리의 최신을 모아도 가장 안정적인 조합이 되지 않는다. 릴리스 시점, API 변경, 전제하는 기반 버전이 서로 다르기 때문이다. **버전 정렬의 목표는 개별 최대 숫자가 아니라 조합 전체의 일관성이다.**

## Q2. 스타터·BOM·자동 구성이 각각 답하는 질문

```text
starter-webmvc:              무엇을 함께 가져올까?
spring-boot-dependencies BOM: 그것들을 어느 버전으로 가져올까?
auto-configuration:          가져온 기술을 보고 어떤 bean을 만들까?
```

| | 답하는 질문 | 시점 | 결과물 |
|---|---|---|---|
| 스타터 | **무엇을** | 빌드 의존성 해석 | 관련 모듈이 클래스패스에 |
| BOM | **어느 버전으로** | 빌드 버전 해석 | 버전이 정렬된 그래프 |
| 자동 구성 | **어떤 빈을** | 애플리케이션 시작 | 컨텍스트의 빈 정의 |

**세 질문을 분리하면 빌드 문제와 런타임 구성 문제를 혼동하지 않게 된다.** 빈이 안 생겼을 때 앞의 둘(클래스패스에 들어왔나, 버전이 맞나)과 뒤의 하나(조건이 참인가) 중 어디를 볼지 갈린다.

## Q3. `dependencyManagement`에 BOM을 import해도 자동 포함되지 않는 이유

**`dependencyManagement`는 "규칙"을 선언하는 자리이지 "주문"을 넣는 자리가 아니다.**

| | `dependencyManagement` | `dependencies` |
|---|---|---|
| 선언하는 것 | 그 라이브러리가 **필요해졌을 때** 적용할 버전 규칙 | 실제로 빌드·런타임에 **필요한** 라이브러리 |
| 결과 | 클래스패스에 아무것도 추가되지 않음 | 클래스패스에 들어감 |

BOM 자체가 그 증거다. **BOM은 라이브러리 바이너리 묶음이 아니다.** 애플리케이션 기능을 실행하지 않고, 다른 의존성을 해석할 때 쓸 버전 제약만 제공한다.

**왜 그렇게 설계했나.** Boot BOM은 수백 개 라이브러리의 버전을 관리한다. import만으로 다 들어온다면 Kafka도 안 쓰는 앱에 Kafka가 들어올 것이다. **"알고 있다"와 "쓴다"를 분리해야** 큰 목록을 관리하면서도 애플리케이션은 필요한 것만 담을 수 있다.

세 단계로 읽으면 이렇다.

1. `dependencyManagement`에서 BOM을 import한다 — 의존성을 추가하기 **전에** 적용할 버전 표를 알려 주기 위해
2. 실제 필요한 것만 `dependencies`에 선언한다 — 관리 대상 전체를 무조건 넣지 않기 위해
3. 버전을 생략하면 Maven이 BOM 제약을 쓴다 — 수동 숫자 관리와 충돌을 줄이기 위해

**단, 전이 경로로도 들어온다.** `dependencies`에 직접 안 적어도 스타터가 끌고 오면 포함된다.

## Q4. Boot 버전 하나를 올리면 함께 이동하는 것

**네 범주**

- **Spring Framework 기본 버전**
- **Spring 포트폴리오** — Data, Security, Integration 등
- **관리되는 주요 서드파티** — Jackson, DB 드라이버, 로깅 라이브러리 등
- **자동 구성과 스타터 모듈 자체**

마지막 항목이 중요하다. Boot 업그레이드는 라이브러리 버전만 바꾸는 게 아니라 **조립 정책 자체**를 바꾼다. [[01-autoconfiguring-spring-beans]]에서 본 Boot 4의 모듈 분할이 그 예다.

**따라야 할 네 단계**

1. 릴리스 노트와 마이그레이션 가이드를 읽는다 — 관리 목록이 일관돼도 **동작 변경**은 남으므로
2. Boot 버전 속성을 올린다 — 기준점을 한곳에서 바꾸기 위해
3. 실제 dependency tree를 확인한다 — 직접 override와 관리 밖 라이브러리가 예상대로 풀렸는지 보기 위해
4. 전체 테스트를 실행한다 — BOM은 조합을 지원할 뿐 **애플리케이션의 사용 방식까지 검증하지 않으므로**

**정확한 의미**: "Boot 버전만 바꾸면 모든 것이 무조건 호환된다"가 아니라 **"검증할 조합의 출발점을 Boot가 제공해 수동 조합 비용을 크게 줄인다"**이다.

## Q5. Maven과 Gradle 문법이 달라도 같은 원리가 적용되는 이유

**BOM이 빌드 도구의 산물이 아니라 별도로 배포되는 아티팩트이기 때문이다.** `spring-boot-dependencies`는 버전 제약의 목록일 뿐이고, 그것을 **읽어 적용하는 방식만** 도구마다 다르다.

| | Maven | Gradle |
|---|---|---|
| 대표 방식 | Boot parent 사용, 또는 `dependencyManagement`로 BOM import | Boot 플러그인 + `io.spring.dependency-management` 플러그인, 또는 Gradle native platform |
| 읽는 대상 | **같은 `spring-boot-dependencies`** | **같은 `spring-boot-dependencies`** |

**도구와 무관한 세 단계**

1. Boot 버전을 선택한다 — 관리 목록의 정확한 릴리스를 정하기 위해
2. 그 버전의 BOM을 의존성 해석에 연결한다 — 같은 큐레이션을 적용하기 위해
3. 관리 대상 의존성의 버전을 생략한다 — DSL은 달라도 **버전 정렬의 단일 출처**를 유지하기 위해

DSL은 문법이고, 원리는 "**하나의 기준점 → 하나의 버전 표 → 생략된 버전**"이다.

## Q6. CVE 패치가 나왔을 때 실제로 해야 할 단계

**BOM이 하는 일과 프로젝트가 해야 할 일이 나뉜다.**

Boot 팀 쪽:

1. 취약점이 Spring 또는 관리 서드파티에 보고된다 — 영향 범위를 공통 식별자로 추적하기 위해
2. Boot 팀이 **지원 조합 안에서** 수정 버전을 고른다 — 한 취약점을 고치다 다른 호환성이 깨지는 위험을 줄이기 위해
3. Boot 패치 릴리스와 BOM을 함께 배포한다 — 사용자가 **같은 기준 버전 변경**으로 코드와 제약을 맞추기 위해

프로젝트 쪽:

4. **Boot 패치 버전을 올리고 테스트한다** — 실제로 수정 버전을 적용하고 자체 동작을 검증하기 위해

**여기가 핵심이다.** BOM 사용만으로 취약점이 자동 치료되지 않는다. **실제로 업그레이드해야 한다.** 그리고 두 사각지대를 따로 점검한다 — **BOM 관리 밖의 라이브러리**와 **자체 override**. 둘 다 Boot 패치가 손대지 않는 영역이다.

**흔한 오해**: "관리 목록에 있다 = 최신 보안 패치를 쓴다"가 아니다. 쓰는 Boot 라인이 아직 지원 중인지, 실제 패치 버전이 무엇인지, 최종 dependency graph가 어떤지 확인해야 한다.

## Q7. Spring Framework 버전 재정의를 권장하지 않는 이유

**override 자체는 가능하다. 문제는 무엇을 함께 가져오느냐다.**

Framework는 다른 모든 Spring 포트폴리오가 **전제로 삼는 기반**이다. Data도 Security도 Integration도 "어떤 Framework 버전 위에서 동작한다"를 가정하고 빌드·테스트된다. Framework만 임의로 옮기면 **그 위의 모든 모듈이 검증되지 않은 조합에 놓인다.** 한 줄을 바꿨는데 검증 범위 전체가 무너지는 것이다.

override 전에 다섯 가지를 확인한다.

| 확인 질문 | 이유 |
|---|---|
| Boot가 그 버전을 관리하는가 | 관리 밖이면 호환성 검증 범위가 달라진다 |
| 새 버전이 현재 Framework 기준을 지원하는가 | 컴파일은 돼도 런타임 API가 어긋날 수 있다 |
| 전이 의존성이 무엇을 바꾸는가 | 한 줄이 여러 하위 라이브러리를 움직인다 |
| 전체 테스트가 관련 경로를 덮는가 | 조합 변경의 회귀를 검출해야 한다 |
| **다음 Boot 릴리스로 기다릴 수 있는가** | 장기 override 유지 비용을 피할 수 있다 |

마지막 질문이 실무에서 가장 자주 정답이다.

**대가**: override는 "Boot를 쓰면서 자유를 잃지 않는다"는 확장 지점이지만, **큐레이션 경계 밖으로 나간 부분의 책임을 함께 가져온다.** override를 여러 개 쌓으면 사실상 자체 BOM을 만드는 셈이 되어 Boot 업그레이드의 이점이 줄어든다.

## Q8. "미리 구운 케이크" 비유의 장점과 경계

**책의 표현**: Spring Framework가 재료 모음이고, Spring Boot는 미리 구운 케이크다.

**비유가 잘 설명하는 것**

- 호환 조합이 **이미 검증되어** 있다 — 밀가루와 설탕 비율을 내가 안 정해도 된다
- 기본 조립이 **준비되어** 있다 — 자동 구성이 기본 빈을 만들어 둔다
- 시작 비용이 낮다 — 재료를 모으는 단계를 건너뛴다

**비유가 깨지는 지점 — 사용자 코드**

실제 케이크는 완성되면 재료를 교체하기 어렵다. **Spring Boot 애플리케이션은 그렇지 않다.** 사용자 빈, 설정, 의존성 override로 조합을 바꿀 수 있다. [[01-autoconfiguring-spring-beans]]의 백오프가 정확히 그 장치다 — 사용자가 자기 재료를 넣으면 Boot 것이 물러난다.

**그리고 한 겹 더 있는 경계**: **바꿀 수 있다는 것과 그 조합을 Boot 팀이 검증했다는 것은 별개다.** 케이크에서 밀가루를 빼고 다른 걸 넣을 수는 있는데, 그 결과가 어떨지는 아무도 시험해 보지 않았다. Q7의 override 책임이 여기서 나온다.

**한 문장으로**: 비유는 *제공되는 것*을 잘 설명하고, *바꿀 수 있다는 것*과 *바꿨을 때의 책임*을 설명하지 못한다.
