## Q1. `my.app.header`가 서비스까지 전달되는 두 연결 단계

**두 단계는 출발점과 목적지가 다르다.** 같은 "주입"이라는 말을 써서 섞이기 쉽다.

| | 프로퍼티 바인딩 | 의존성 주입 |
|---|---|---|
| 무엇을 | 외부 문자열 값 | 완성된 설정 객체 |
| 어디로 | 설정 객체의 프로퍼티 | 그것을 필요로 하는 빈 |
| 방향 | 값 → 설정 객체 | 설정 객체 → 소비자 |
| 하는 주체 | 구성 프로퍼티 바인더 | 애플리케이션 컨텍스트 |

**1단계 — 바인딩**

1. 컴포넌트 스캔이 `MyCustomProperties`를 빈 후보로 찾는다. — 바인딩 결과를 주입받을 관리 객체가 필요하므로
2. Boot가 `@ConfigurationProperties`와 `my.app` 접두사를 읽는다. — 이 객체가 소비할 키 범위를 정하기 위해
3. 최종 프로퍼티 환경에서 `my.app.header`를 찾는다. — 여러 소스가 합쳐진 **승자** 값을 쓰기 위해
4. 키의 나머지 이름(`header`)을 객체 프로퍼티에 대응시킨다.
5. 필요한 타입으로 변환해 설정한다. — 코드가 원시 문자열을 파싱하지 않게 하기 위해

**2단계 — 주입**

6. 완성된 설정 빈을 `PageTextService` 생성자에 넣는다. — 서비스가 구성 소스를 직접 조회하지 않게 하기 위해

**3번 단계의 함정 — 소스마다 표기가 다르다**

"여러 소스가 합쳐진 승자 값"이라고 했는데, 그 소스 중 **환경 변수에는 점을 쓸 수 없다.** 리눅스 셸 변수 이름은 영문자·숫자·밑줄만 허용하고 관례상 대문자다. 그래서 컨테이너 플랫폼은 이렇게 준다.

```bash
MY_APP_HEADER="Learning Spring Boot 4"
```

Spring Boot는 **느슨한 바인딩**으로 이를 표준형 `my.app.header`로 되돌린다. 두 소스가 **같은 키로 인식돼야** 우선순위 비교가 의미를 갖는다.

✅ **표준형 → 환경 변수 규칙 세 가지**: ① 점을 밑줄로 ② **하이픈은 지운다** ③ 대문자로. 그래서 `spring.main.log-startup-info`는 `SPRING_MAIN_LOGSTARTUPINFO`다. 하이픈이 밑줄이 되는 게 아니라 **사라진다**는 점이 함정이다. 리스트는 인덱스를 밑줄로 감싼다 — `my.service[0].other` → `MY_SERVICE_0_OTHER`.

✅ **적을 때는 kebab-case 권장.** 공식 문서가 `my.person.first-name=Rod`처럼 소문자 kebab으로 저장하기를 권한다. 표준형에 가장 가까워 다른 표기로 옮길 때 규칙을 한 번만 적용하면 되기 때문이다.

**경계**: 이 느슨함은 ✅ `@ConfigurationProperties` 바인딩의 규칙이다. 그리고 대소문자를 봐준다고 **오타까지 봐주지는 않는다** — `my.app.headr`는 그냥 존재하지 않는 키이고 조용히 무시된다.

## Q2. `@Component`와 `@ConfigurationProperties`의 책임

| 애노테이션 | 책임 | 없으면 |
|---|---|---|
| `@Component` | 컴포넌트 스캔이 이 클래스를 발견해 **Spring bean으로 등록**하게 한다 | 바인딩할 대상 객체가 컨텍스트에 없다 |
| `@ConfigurationProperties(prefix="my.app")` | `my.app` 아래 값을 **이 타입에 묶으라**고 알린다 | 빈은 있지만 값이 채워지지 않는다 |

**"등록"과 "바인딩"이라는 서로 다른 두 일**이다. 가변 JavaBean 예제에서는 둘 다 필요하지만, record 방식에서는 `@Component` 대신 `@ConfigurationPropertiesScan`이나 `@EnableConfigurationProperties`가 등록을 맡는다 → Q3.

이 분리가 [[01-autoconfiguring-spring-beans]]의 "빈이라는 것"과 "그 빈에 무엇을 넣을지"의 구분과 같은 결이다.

## Q3. 가변 JavaBean과 record의 차이

| | 가변 JavaBean | record |
|---|---|---|
| **등록** | `@Component` | `@ConfigurationPropertiesScan` 또는 `@EnableConfigurationProperties(X.class)` |
| **바인딩 경로** | setter로 값을 넣는다 | **생성자 매개변수**로 값을 넣는다 |
| **가변성** | 생성 후에도 바꿀 수 있다 | 불변 — 만들어지면 끝 |
| **필요한 것** | private 필드 + getter/setter + 인자 없는 생성자 | record 컴포넌트 선언만 |

```java
// 가변
@Component
@ConfigurationProperties(prefix = "my.app")
public class MyCustomProperties { /* getter/setter */ }

// 불변
@ConfigurationProperties(prefix = "my.app")
public record MyCustomProperties(String header, String footer) {}
```

**왜 등록 방식이 달라지나.** record는 setter가 없으므로 "빈 객체를 만든 뒤 값을 채우는" 순서가 성립하지 않는다. **값이 있어야 객체를 만들 수 있다.** 그래서 스캔·enable이 "이 타입을 구성 프로퍼티 빈으로 만들라"고 별도로 알려 주고, 바인더가 생성자 인자에 값을 연결한다.

record 쪽 순서: ① record 컴포넌트가 생성자 매개변수가 된다 ② scan/enable이 등록 대상임을 알린다 ③ 바인더가 생성자 인자에 값을 연결한다.

**경계**: record가 불변성을 주지만 런타임 실시간 갱신 모델은 아니다. 일반적인 Boot 구성은 **시작 시점의 값으로 객체를 만든다.**

## Q4. 접두사가 충돌과 탐색 비용을 줄이는 방식

접두사(`my.app`)는 설정 키의 공통 앞부분이다. 두 가지를 동시에 한다.

**충돌 방지**: Boot 내장 키(`server.*`, `spring.*`)와 애플리케이션 고유 키가 같은 이름 공간에서 부딪히지 않는다. 만약 접두사 없이 `header`라고만 쓰면 어느 라이브러리가 같은 이름을 쓸지 알 수 없다.

**탐색 비용 절감**: 서로 관련된 설정이 한 접두사 아래 모이므로,

- 관련 키가 하나의 클래스에 모인다
- 코드가 `"my.app.header"` 같은 문자열을 반복하지 않는다
- 필드 타입이 허용되는 값의 형태를 표현한다
- 기본값을 설정 객체 가까이 둘 수 있다
- IDE가 구성 메타데이터로 키 탐색과 자동완성을 제공하기 쉬워진다

**비유와 그 한계**: 접두사는 아파트 동 주소, 각 필드는 호수다. `my.app` 동의 `header` 호로 값이 배달된다. 다만 **타입 변환에서 비유가 깨진다** — 우편은 주소만 맞으면 같은 방식으로 전달되지만, 바인더는 문자열을 숫자·기간·목록·중첩 객체로 변환해야 하고 변환 불가능한 값은 **시작 오류**가 된다.

**경계**: 관련 없는 설정을 하나의 거대한 `AppProperties`에 다 넣으면 접두사의 경계와 책임이 흐려진다. 기능별로 응집된 타입을 만든다.

## Q5. 기본값을 넣어도 되는 설정과 위험한 설정

**판별 질문 하나**: *이 설정이 없는 상태가 정말 정상인가?*

| | 넣어도 되는 것 | 위험한 것 |
|---|---|---|
| 성격 | 부재가 허용되는 선택 설정 | 반드시 외부에서 와야 하는 값 |
| 예 | 페이지 제목(`"My Application"`), 페이지 크기, 타임아웃, 재시도 횟수 | 인증 토큰, DB 접속 정보, 외부 API 주소, 암호화 키 |
| 기본값의 효과 | 설정이 빠져도 의미 있게 동작한다 | **누락을 숨긴다** |

```java
private String header = "My Application";   // 안전
private String githubPersonalCode = "";     // 위험 — 빈 값으로 조용히 시작한다
```

**왜 위험한가.** 토큰에 기본값을 두면 설정을 빠뜨린 채로 애플리케이션이 **정상 시작한다.** 실패가 시작 시점이 아니라 첫 API 호출 시점, 즉 훨씬 나중에 그리고 다른 모습으로 나타난다. 원인에서 먼 곳에서 증상이 터진다.

**대안**: 필수 설정은 시작 시 검증한다. 기본값을 두는 대신 없으면 즉시 실패하게 만드는 편이 안전하다.

## Q6. 토큰을 구성 프로퍼티로 옮긴 것만으로 끝나지 않는 이유

**옮긴 것이 해결하는 것과 해결하지 않는 것이 다르다.**

| 해결한 것 (외부화) | 해결하지 않은 것 (기밀성) |
|---|---|
| 토큰 값이 **소스 코드에 없다** | 평문 파일에 그대로 있을 수 있다 |
| 토큰이 바뀌어도 **재빌드·재배포 불필요** | 그 파일이 Git에 커밋될 수 있다 |
| 환경마다 다른 값 공급 가능 | 로그에 찍힐 수 있다 |
| 비밀 접근 지점이 한 클래스로 제한됨 | 파일 권한·저장 매체 암호화·회전 정책이 없다 |

**한 문장으로**: **외부화는 배포 유연성을 주고, 기밀성은 별도 문제다.** JAR 밖에 있다는 사실만으로 안전하지 않다.

코드가 하는 일도 정확히 그렇게 읽어야 한다.

1. 비밀값의 **구조와 이름만** 코드에 둔다 — 어떤 설정이 필요한지 컴파일 시점에 표현하기 위해
2. **실제 값은 실행 환경**에서 공급한다 — 토큰 변경이 재빌드를 요구하지 않게 하기 위해
3. 설정 객체를 필요한 API 클라이언트에 **주입**한다 — 비밀 접근 지점을 제한하기 위해

세 단계 어디에도 "안전하게 저장한다"가 없다. 그건 비밀 저장소·권한·회전·로그 마스킹이 하는 일이다.
