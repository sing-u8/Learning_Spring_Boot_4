## Q1. `server.port`가 없을 때와 9000일 때의 차이

두 경우 **갈라지는 지점은 딱 한 단계**다. 나머지는 같다.

| 단계 | 없을 때 | 9000일 때 |
|---|---|---|
| 1. 표준 위치에서 `application.properties`를 찾는다 | 같음 | 같음 |
| 2. 키·값을 프로퍼티 환경에 적재한다 | 이 키가 없다 | `server.port=9000`이 들어간다 |
| 3. 웹 서버 자동 구성이 `server.port` 최종값을 조회한다 | 같음 | 같음 |
| **4. 값을 정한다** | **기본 8080** | **9000이 기본값을 덮는다** |
| 5. 내장 서버가 그 포트에 바인딩한다 | 8080 | 9000 |

**핵심은 3번이 양쪽에서 똑같이 일어난다는 것이다.** 자동 구성은 "설정이 있나 없나"를 특별 취급하지 않고 **항상 최종값을 조회**한다. 값이 없을 때 8080을 쓰는 것도 조회 결과에 대한 처리이지 다른 경로가 아니다. 그래서 설정을 생략해도 실행되고, 필요할 때만 한 줄로 바꿀 수 있다.

**실무 맥락**: 한 컴퓨터에서 두 Boot 앱을 띄우면 둘째 프로세스가 8080 충돌로 시작하지 못한다. 다만 포트를 바꿨다고 방화벽, 컨테이너 포트 노출, 로드 밸런서 라우팅까지 따라오지는 않는다.

## Q2. 기본값이 있으면서도 제어권이 유지되는 이유

**"convention over configuration"은 구성을 없애는 것이 아니라, 반드시 써야 하는 구성만 남기는 것이다.**

선택지를 양극단으로 놓고 보면 왜 중간이 필요한지가 보인다.

| 극단 | 문제 |
|---|---|
| 모든 값을 코드로 직접 구성 | 반복 설정이 많고 서버 구현 교체가 어렵다 |
| 모든 값을 Boot 기본값으로 고정 | 포트·SSL·스레드 등 운영 요구를 반영할 수 없다 |

구성 프로퍼티는 **"객체 구조는 자동 구성이, 환경에 따라 달라지는 값은 외부 입력이"** 라는 분담을 만든다. 8080은 바꿀 수 없는 규칙이 아니라 **설정이 없을 때 적용하는 값**이다.

이것은 [[01-autoconfiguring-spring-beans]]의 백오프와 **같은 철학의 다른 층위**다. 백오프는 "사용자가 빈을 주면 자동 구성이 물러난다"이고, 프로퍼티는 "사용자가 값을 주면 기본값이 물러난다". 둘 다 *제안하되 강요하지 않는다*.

**경계**: 프로퍼티만으로 임의의 객체 구조를 만들 수는 없다. 설정판으로 밝기는 바꿔도 배선을 새로 깔 수는 없다. 기본 구성이 제공하지 않는 구조는 사용자 빈이나 별도 구성 코드가 필요하다.

## Q3. Tomcat에서 Jetty로 바꿔도 `server.port`가 유지되는 구조적 이유

**공통 프로퍼티 모델이라는 추상화 층이 하나 끼어 있기 때문이다.**

1. 개발자가 웹 서버 스타터 조합을 선택한다. — 어느 서블릿 컨테이너를 쓸지 정하기 위해
2. 그 컨테이너의 자동 구성이 활성화된다. — Tomcat 또는 Jetty의 실제 서버 객체를 만들기 위해
3. **두 자동 구성이 모두 같은 공통 서버 프로퍼티 모델에서 `server.port`를 읽는다.** — 컨테이너 교체가 애플리케이션 설정의 전면 재작성을 요구하지 않게 하기 위해
4. 컨테이너 고유 기능이 필요하면 전용 프로퍼티를 추가한다. — 공통 추상화로 표현 못 하는 세부 조절을 보존하기 위해

3번이 답이다. 애플리케이션이 Tomcat의 설정 API를 직접 부르는 것이 아니라, **양쪽 자동 구성이 같은 프로퍼티를 읽어 각자의 서버 객체에 적용한다.** 서버 구현이 바뀌어도 애플리케이션이 쓰는 키는 그대로다.

이것도 [[01-autoconfiguring-spring-beans]]에서 `BookRepository`가 `DataSource` 계약에만 의존한 것과 같은 형태다. **공통 계약에 기대면 구현을 갈아끼울 수 있다.**

## Q4. 공통 프로퍼티와 컨테이너 전용 프로퍼티가 각각 푸는 문제

| | 공통 프로퍼티 (`server.port`) | 컨테이너 전용 프로퍼티 |
|---|---|---|
| 푸는 문제 | **기술 교체 비용** — 서버를 바꿔도 설정을 다시 쓰지 않는다 | **표현력 손실** — 추상화가 못 담는 고유 기능에 접근한다 |
| 대가 | 모든 서버의 공통분모까지만 표현할 수 있다 | 그 키를 쓰는 순간 서버 구현에 묶인다 |

**둘은 트레이드오프 관계이지 상하 관계가 아니다.** 공통 키만 있으면 교체는 쉬운데 세밀한 튜닝이 안 되고, 전용 키만 있으면 튜닝은 되는데 교체가 어렵다. Boot는 둘 다 열어 두고 **어디까지 이식성을 지킬지 개발자가 정하게** 한다.

**흔한 오해**: `server.port`가 공통으로 동작한다고 해서 "모든 서버 설정이 동일하다"로 확대하면 안 된다. 스레드 풀, 커넥션 옵션 같은 것은 서버마다 모델이 다르다.

## Q5. Undertow 지원 제거가 보여 주는 것

**사실 관계**: Spring Boot 4는 Servlet 6.1 호환 런타임을 요구한다. Tomcat 11과 Jetty 12.1 계열이 그 기준을 충족한다. 출판 시점에 Undertow는 Servlet 6.1과 호환되지 않아 Boot 4에서 스타터와 내장 서버 지원이 제거되었다. (✅ Boot 4는 Servlet 6.1을 요구하고 Tomcat 11.0.x·Jetty 12.1.x를 지원하며 "any Servlet 6.1+ compatible container"에 배포 가능하다고 명시한다.)

**보여 주는 것 두 가지**

1. **구성 프로퍼티가 서버 교체를 쉽게 해도 기반 표준 버전 호환성까지 무시할 수는 없다.** `server.port`가 이식 가능하다는 것은 *지원 목록 안에서* 참이다. 목록에서 빠지면 프로퍼티 호환성은 아무 소용이 없다 — 그 서버로는 애초에 시작할 수 없으니까.
2. **과거 메이저 버전에서 되던 조합이 새 메이저에서도 유지된다고 가정하면 안 된다.** 이식성은 "무한히 갈아끼울 수 있다"가 아니라 "지원되는 것들 사이에서 갈아끼울 수 있다"이다.

**한 문장으로**: 추상화는 그 아래 층이 존재할 때만 작동한다. 계약이 이식성을 주지만, 그 계약을 만족하는 구현이 남아 있어야 한다.

## Q6. properties와 yml이 표현 방식 외에 동일하게 해결하는 것

비교표는 보통 **차이**만 보여 주지만, 질문은 반대를 묻는다. 네 가지가 같다.

| 같은 것 | 뜻하는 바 |
|---|---|
| **키 이름 공간** | `server.port`와 `server:` / `port:`는 **같은 키**다. 형식을 바꿔도 키를 다시 짓지 않는다 |
| **우선순위 층** | 둘 다 config data라는 **한 층**에 속한다. YAML이라서 더 세거나 약하지 않다 |
| **도달 지점** | 둘 다 같은 Spring `Environment`로 들어간다. 소비자는 어느 형식에서 왔는지 알지 못한다 |
| **바인딩 규칙** | ✅ 같은 느슨한 바인딩 규칙이 적용된다. 단순 프로퍼티에서 camelCase·kebab-case·밑줄 표기를 똑같이 허용한다 |

**실제로 갈리는 지점**은 표현 문법과 ✅ **리스트 표기**다. properties는 대괄호 인덱스나 쉼표 구분, YAML은 YAML 리스트 문법이나 쉼표 구분을 쓴다.

**진짜 규칙이 다른 곳은 두 파일 형식 사이가 아니다.** ✅ **파일과 환경 변수 사이**다. 환경 변수는 대문자와 밑줄만 쓸 수 있어 표기 자체가 달라진다 — `my.app.header`가 `MY_APP_HEADER`가 된다. 그래서 "형식을 뭘 쓰지"보다 "이 값이 어느 **소스**에서 오는지"가 훨씬 중요한 구분이다. 그 규칙은 [[03a-creating-custom-properties]]에서 다룬다.

**주의**: `application.properties`(파일 형식)와 `-Dserver.port=9000`(JVM 시스템 프로퍼티)은 이름이 비슷해도 **다른 프로퍼티 소스**다. 우선순위가 다르다.

## 재출제 문항

1. 두 Boot 앱을 한 서버에 띄우려 `server.port`를 바꿨는데 여전히 접속이 안 된다. 프로퍼티 밖에서 무엇을 확인하겠는가?
2. `server.port`가 이식 가능하다는 말은 어떤 조건에서 참인가? 그 조건이 깨진 실제 사례는?
3. 팀이 `application.properties`를 `application.yml`로 전부 옮기려 한다. 우선순위나 키 이름 중 바뀌는 것이 있는가?
4. 자동 구성의 8080과 사용자의 9000 중 후자가 이기는 구조는, `@ConditionalOnMissingBean`의 백오프와 어떻게 같고 어떻게 다른가?
5. 컨테이너 전용 프로퍼티를 하나 쓰기 시작하면 무엇을 잃는가?
