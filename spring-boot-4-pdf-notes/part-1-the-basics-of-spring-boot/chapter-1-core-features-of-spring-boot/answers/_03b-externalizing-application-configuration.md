## Q1. JAR 내부와 외부에 같은 `server.port`가 있으면

**외부가 이긴다.** 그리고 그 순서가 유용한 이유가 이 절 전체의 핵심이다.

config data 파일만 떼어 보면 낮은 순위 → 높은 순위는 이렇다.

| 순위 | 파일 | 왜 그 자리인가 |
|---:|---|---|
| 1 | JAR **내부** 일반 `application.properties` | 애플리케이션과 함께 배포할 기본을 제공 |
| 2 | JAR **내부** 프로파일별 파일 | 패키지된 환경 변형이 내부 일반값을 덮게 |
| 3 | JAR **외부** 일반 파일 | 배포 환경의 공통 설정이 패키지 내부 값을 바꾸게 |
| 4 | JAR **외부** 프로파일별 파일 | 현재 배포 환경의 가장 구체적인 파일이 이기게 |

**두 축이 겹쳐 있다** — 내부/외부, 그리고 일반/프로파일별. 더 바깥이고 더 구체적일수록 강하다.

**왜 유용한가.** 이 순서가 **하나의 JAR를 여러 환경에 배포**하는 것을 가능하게 한다. 안전한 기본값을 JAR에 넣어 두고, 배포 환경은 자기가 바꿔야 할 키만 외부 파일에 적는다. 반대 순서였다면 환경마다 다른 JAR를 만들어야 했을 것이다.

**주의**: 이건 config data **안에서의** 순서다. 명령행 인자가 같은 키를 주면 전체 우선순위에서 명령행이 다시 이긴다 → Q4.

## Q2. 일반 파일과 프로파일 전용 파일의 병합

**합치는 단위는 파일이 아니라 키다.** 프로파일 파일이 일반 파일을 통째로 대체하지 않는다.

```properties
# application.properties
my.app.database-url=https://prod-db.example.com:1234/prod
my.app.timeout=30
```

```properties
# application-test.properties
my.app.database-url=http://test-db.example.com:1234/test
```

`test` 프로파일이 활성이면 결과는 `database-url`은 test 값, `timeout`은 **30 그대로**다. 프로파일 파일에 없는 키는 일반 파일 값이 살아남는다.

**그래서 프로파일 파일에는 차이만 적는다.** 공통값을 복제하지 않아도 되는 것이 이 설계의 이득이다.

**여러 프로파일을 함께 활성화하면** 공식 문서 기준 **뒤에 지정된 프로파일이 앞을 이기는 last-wins** 규칙이 적용된다.

**경계 — 모든 값이 키 단위로 영리하게 합쳐지지는 않는다.** 리스트나 한 덩어리 값은 높은 소스의 값이 **통째로 대체**될 수 있다. 투명 필름을 겹친다는 비유가 여기서 깨진다. 타입별로 어떤 단위로 바인딩되는지 확인해야 한다.

## Q3. `spring.profiles.active=test`를 준 뒤의 전체 흐름

```bash
java -Dspring.profiles.active=test -jar learning-spring-boot-4.jar
```

1. `application.properties`를 읽는다. — 모든 환경이 공유할 기준 설정을 마련하기 위해
2. `spring.profiles.active=test`에서 활성 프로파일 이름을 얻는다. — 어떤 변형을 추가로 적용할지 결정하기 위해
3. `application-test.properties`를 읽는다. — 테스트에서 달라지는 값만 별도로 표현하기 위해
4. 프로파일 파일의 같은 키가 일반 파일 값을 덮는다. — 공통값을 복제하지 않고 차이만 관리하기 위해
5. 최종값을 구성 객체나 자동 구성에 바인딩한다. — 코드가 환경 이름을 직접 분기하지 않게 하기 위해

**5번이 목적지다.** 프로파일의 요점은 "코드에 `if (env == test)`를 안 쓰는 것"이다. 코드는 최종값만 보고, 그 값이 어느 프로파일에서 왔는지 모른다.

**책의 실천 예에 대한 주의**: 책은 `application.properties`를 운영값으로 두고 다른 환경을 프로파일로 덮는 방법을 제안한다. 이것은 Boot가 강제하는 규칙이 **아니며**, 민감한 운영값을 JAR 내부 기본 파일에 넣으라는 뜻으로 읽어서는 안 된다. 조직에 따라 기본 파일에는 안전한 공통값만 두고 `prod`도 명시적으로 활성화하는 편이 낫다.

## Q4. 프로퍼티 소스 전체 순위를 큰 층으로 복원하기

15단계를 통째로 외우는 대신 **네 층**으로 접는다.

```text
코드·기본값  <  애플리케이션 config data  <  실행 환경·명령행  <  테스트 전용 override
```

| 층 | 대표 소스 | 성격 |
|---|---|---|
| 1. 코드·기본값 | `setDefaultProperties()`, `@PropertySource` | 프로그램이 스스로 가진 값 |
| 2. config data | `application.properties`/YAML, `random.*` | 애플리케이션이 패키징·배포하는 파일 |
| 3. 실행 환경·명령행 | OS 환경 변수, 시스템 프로퍼티, JNDI, Servlet 파라미터, `SPRING_APPLICATION_JSON`, **명령행 인자** | 이번 실행이 주는 값 |
| 4. 테스트 전용 | 테스트 `properties` 속성, `@DynamicPropertySource`, `@TestPropertySource`, DevTools | 테스트가 확실히 이겨야 하는 값 |

**층의 논리**: 뒤로 갈수록 *더 구체적인 이번 실행의 의도*다. 파일은 여러 실행이 공유하고, 명령행은 이번 한 번이고, 테스트는 무슨 일이 있어도 이겨야 한다.

**하지만 이 요약을 규칙으로 착각하면 안 된다.** "환경에 가까울수록 항상 높다"는 **기억 보조**일 뿐이다. 층 안에서의 세부 순서(예: 테스트 소스들끼리)가 필요할 때는 공식 목록을 확인해야 한다.

## Q5. `spring.config.location`과 `spring.config.additional-location`

**한 글자 차이가 아니라 정반대다.**

| | `spring.config.location` | `spring.config.additional-location` |
|---|---|---|
| 기본 검색 위치에 하는 일 | ✅ **대체한다** | ✅ **더한다** |
| JAR 내부 `application.properties` | 지정 위치에 없으면 **읽히지 않는다** | 그대로 읽힌다 |
| 같은 키가 겹치면 | 지정 위치의 값만 존재한다 | ✅ 추가 위치의 값이 **기본 위치의 값을 덮는다** |
| 쓰는 상황 | 설정 소스를 완전히 통제할 때 | 패키지된 기본값 위에 환경 값만 얹을 때 |

**잘못 쓰면 이렇게 터진다.** 운영 배포에서 `spring.config.location=file:/opt/app/config/`만 주고 그 디렉터리에 바꿀 키 몇 개만 적어 두면, **JAR 안에 넣어 둔 기본값 전체가 사라진다.** 기본값을 남기고 일부만 덮으려던 의도였다면 `additional-location`이 맞다.

**세 가지 더**

- ✅ **없는 위치를 지정하면 애플리케이션이 시작되지 않는다.** 기본 동작이 `ConfigDataLocationNotFoundException`을 던지는 것이다. 있을 수도 없을 수도 있는 위치면 `optional:` 접두사를 붙인다(`optional:file:./config/`). 전부 무시하려면 `spring.config.on-not-found=ignore`.
- ✅ **디렉터리는 `/`로 끝낸다.** 그래야 `spring.config.name`이 만든 파일 이름이 뒤에 붙는다. 파일을 직접 가리키면 그대로 import된다. 두 경우 모두 프로파일별 파일까지 확장해 찾는다.
- ✅ **여러 위치는 적은 순서대로 처리되고 뒤가 앞을 덮는다.**

**둘 다 공통인 제약**: ✅ 이 키들은 **환경 프로퍼티로 줘야 한다** — OS 환경 변수, 시스템 프로퍼티, 명령행 인자. 설정 파일을 *찾기 위해* 먼저 알아야 하는 값이라, 일반 `application.properties` 안에 적으면 이미 늦다.

## Q6. 외부화가 비밀 관리를 해결하지 못하는 이유

**두 문제가 다르기 때문이다.**

| 외부화가 푸는 문제 | 비밀 관리가 푸는 문제 |
|---|---|
| 값을 바꾸려고 **재빌드하지 않기** | 값을 **아무나 못 보게 하기** |
| 같은 JAR를 여러 환경에 배포하기 | 유출 시 **회전**하기 |
| 코드와 설정의 생명주기 분리 | 접근 **감사** |

JAR 밖에 있다는 사실은 **위치**에 관한 것이지 **보호**에 관한 것이 아니다. 외부 평문 파일은 여전히 다음에 노출된다 — 파일 권한이 넓을 때, 저장 매체가 암호화되지 않았을 때, 로그에 찍힐 때, 백업에 남을 때, 그 파일이 실수로 저장소에 커밋될 때.

**필요한 것**: 파일 권한, 저장 매체 암호화, 비밀 회전, 로그 마스킹, 별도 비밀 관리 시스템.

**같은 형태의 함정 하나 더**: **높은 우선순위가 항상 더 "옳은" 값이라는 뜻도 아니다.** 잘못 남은 명령행 옵션이나 환경 변수가 안전한 파일 값을 조용히 덮을 수 있다.

## Q7. 값이 예상과 다를 때의 역추적 순서

"파일을 읽었는가?"만 묻지 않는다. **가능성이 높고 확인이 싼 것부터** 여섯 단계다.

1. **키 이름이 정확한가.** — 오타는 우선순위 문제가 아니라 *존재하지 않는 설정*을 만든다. 조용히 무시되므로 제일 먼저 본다.
2. **어떤 프로파일이 활성인가.** — 다른 프로파일 파일이 덮을 수 있다.
3. **내부·외부 파일의 위치는.** — 같은 파일명이라도 위치가 우선순위를 바꾼다.
4. **환경 변수·시스템 프로퍼티·명령행에 같은 키가 있나.** — 파일보다 높은 소스가 **조용히** 승리할 수 있다. 여기서 느슨한 바인딩 표기(`MY_APP_HEADER`)도 함께 본다.
5. **테스트라면 테스트 전용 프로퍼티를 확인한다.** — 일반 실행과 다른 최상위 값이 적용된다.
6. **최종값이 어느 설정 객체·자동 구성에 바인딩되는가.** — 값이 존재해도 소비자가 **다른 키를 읽고 있을** 수 있다.

**순서의 논리**: 1~3은 "내가 적은 것"의 문제, 4~5는 "다른 소스가 이긴" 문제, 6은 "값은 맞는데 아무도 안 읽는" 문제다. 뒤로 갈수록 확인 비용이 크다.
