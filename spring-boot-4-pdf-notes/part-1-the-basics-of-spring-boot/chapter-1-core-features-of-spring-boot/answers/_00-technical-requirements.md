## Q1. `java --version`이 25인데 IDE 빌드가 Java 17로 실행될 수 있는 이유

**"설치된 JDK"와 "각 도구가 실제로 선택한 JDK"가 다른 것이기 때문이다.**

**Java 버전이 결정되는 지점이 셋이다**:

| 확인 위치 | 무엇을 확인하나 | 어긋났을 때 |
|---|---|---|
| **터미널** | `java --version`, `javac --version` | **셸에서 실행한 빌드만 다른 결과** |
| **IDE** | Project SDK, language level, Gradle/Maven JVM | **편집기는 허용하는데 빌드는 거부**하거나 그 반대 |
| **빌드 도구** | Maven/Gradle이 실행되는 JVM | **테스트·플러그인이 예상과 다른 Java에서 실행** |

**`java --version`은 셋 중 하나만 답한다** — **현재 셸이 참조하는 실행 파일**이다. IDE는 자기 설정(Project SDK)을 따로 갖고 있고, 빌드 도구도 마찬가지다.

**SDKMAN의 한계가 여기 있다**:

> **SDKMAN은 셸의 JDK 전환을 돕지만, 이미 열려 있는 IDE의 프로젝트 SDK까지 항상 바꾸지는 않는다.**

```text
sdk use java 25.0.1-tem
  → 이 셸의 java 가 25 가 된다
  → 이미 열린 IntelliJ 의 Project SDK 는 그대로다
  → 같은 소스가 두 결과를 낸다
```

**출발 장면이 정확히 이 상황이다** — **소스 파일은 같아도 컴파일 가능한 문법과 API, 테스트 실행 결과가 달라질 수 있다.**

**그래서 첫 장의 도구 준비가 부록이 아니다**:

> **이후 모든 실습의 재현성을 결정하는 전제다.**

## Q2. "Java 17과 호환"과 "책은 JDK 25"가 양립하는 방식

**"실행할 수 있는 최소 버전"과 "책이 예제를 작성하고 확인한 기준 버전"은 같은 말이 아니다.**

```text
Spring Boot 4.0 의 기준선 : Java 17          ← 프레임워크가 요구하는 최소
이 책의 학습 환경         : Java 25          ← 저자가 예제를 쓰고 검증한 버전
```

**§5의 정리**:

- **"Java 17과 호환된다"는 말은 Java 17이 책의 모든 실습에서 가장 적합하다는 뜻이 아니다.**
- **이 책은 Java 25를 설치 기준으로 삼는다.** 특히 **뒤 장에서 Java 25의 기능을 직접 다루는 부분**은 그 기준을 따라야 한다.

**구체적으로 무엇이 걸리나** — Ch11의 **가상 스레드**, Ch8의 **AOT Cache**(Java 24+ 도입, buildpack 지원은 25+)가 Java 17에서는 그대로 안 된다. **기준선이 17이라는 것은 "Boot가 뜬다"는 뜻이지 "책의 모든 예제가 돈다"는 뜻이 아니다.**

**Ch15의 같은 구분과 이어진다** — 거기서도 **"Java 25는 이 책의 선택이지 요구사항이 아니다. 기준선은 Java 17이고, AOT Cache 같은 일부 기능만 더 높은 버전을 요구한다"**고 정리한다.

**일반화하면 두 숫자를 항상 구분해야 한다**:

| 숫자 | 뜻 | 어길 때 |
|---|---|---|
| **최소 지원 버전** | 그 아래면 **안 뜬다** | 기동 실패 |
| **권장/기준 버전** | 저자·팀이 **검증한 환경** | **일부 기능이 조용히 안 된다** |

## Q3. Temurin·OpenJDK·Oracle JDK의 관계 — "구현과 배포판"

| | 정체 |
|---|---|
| **OpenJDK** | **Java SE의 오픈 소스 구현 프로젝트** — 소스 코드 |
| **Eclipse Temurin** | **OpenJDK 소스를 빌드·시험해 배포하는 바이너리** — Eclipse Adoptium 제공 |
| **Oracle JDK, Azul Zulu** | **"다른 Java 언어"가 아니라 배포·지원 정책이 다른 JDK 선택지** |

```text
OpenJDK (소스)
   ├─ Eclipse Temurin  (무료, TCK 통과)
   ├─ Oracle JDK       (상용 지원 계약)
   ├─ Azul Zulu        (상용 지원 계약)
   └─ Amazon Corretto 등
      ↑ 전부 같은 Java 언어를 구현한다. 다른 것은 빌드·배포·지원 정책이다.
```

**`sdk install java 25.0.1-tem`의 `tem`이 Temurin이다.**

**책이 Temurin을 고르는 이유** — **무료·오픈 소스이고 표준 **TCK**(=Java 사양 호환성을 검증하는 시험 모음)를 통과한 배포판**이라는 점. **과거 이름인 AdoptOpenJDK와 연결되는 배포판**이기도 하다.

**"TCK 통과"가 무엇을 보장하나** — **Java SE 사양대로 동작한다는 검증**이다. 이 시험을 통과하지 않은 빌드는 **Java라고 부를 수 없고**, 미묘한 동작 차이가 있을 수 있다.

****장기지원**에 대한 주의**:

> **"영원히 무료 지원된다"는 뜻이 아니다. Oracle JDK, Azul Zulu처럼 상용 지원 계약이 필요한 조직은 비용, 패치 정책, 인증 요구를 따로 검토해야 한다.**

**책의 판단**: **상용 지원이 필요하지 않은 학습·일반 개발 환경에 Temurin을 충분한 선택으로 본다.**

**Windows에서는 두 경로**: **WSL 안에서 SDKMAN**을 쓰거나, **Adoptium의 Temurin 설치 파일**을 쓴다.

## Q4. IDE와 빌드 도구의 책임 — 무엇을 공유 저장소에 남기나

**빌드 정의를 저장소에 남긴다 — `pom.xml`이나 `build.gradle`이다.**

| | **IDE** | **빌드 도구** |
|---|---|---|
| 책임 | **개발 과정을 편리하게** — 편집·탐색·디버깅 | **실제로 빌드하고 실행** |
| 설정 위치 | **개인 환경**(`.idea/`, 워크스페이스) | **`pom.xml` / `build.gradle`** |
| 공유하나 | **아니다** | **그렇다** |

**§6의 규칙**:

> **IDE가 프로젝트의 빌드 정의를 대신하지 않는다. 다른 사람과 재현 가능한 설정은 `pom.xml`이나 `build.gradle` 같은 빌드 파일에 남아야 한다.**

**IDE에만 있는 설정이 왜 위험한가**:

```text
내 IDE 에서만 Java 25 로 설정했다
  → 내 컴퓨터에서는 빌드된다
  → 동료가 클론하면 그의 IDE 기본값을 따른다
  → CI 는 IDE 를 안 쓴다 → 빌드 파일만 본다
  → "내 컴퓨터에서는 되는데요"
```

**빌드 파일에 남기면** — **IDE·CI·동료의 셸이 전부 같은 기준**을 읽는다. Java 버전(`<maven.compiler.release>`, `sourceCompatibility`), 의존성, 플러그인 설정이 **한 곳에 정본으로** 있다.

**Q1과 이어진다** — **세 지점의 Java 버전을 맞추는 것**도, **빌드 도구 쪽을 정본으로 삼고 나머지를 거기에 맞추는 것**이 순서다.

**IDE 선택 자체는 개인의 문제다**(§2.3) — IntelliJ IDEA(Community/Ultimate), Spring Tools 4 for Eclipse, Spring Tools 4 for VS Code 중 **같은 프로젝트를 열어 실행해 보고**, **한 달 정도 써 본 뒤 정한다.** **텍스트 편집기를 써도 학습할 수 있다** — 비유의 한계가 그것이다: **작업대가 없으면 요리가 곤란하지만, IDE 없이도 명령행과 텍스트 편집기로 빌드하고 실행할 수 있다.**

## Q5. GitHub 완성 코드를 복사하지 않고 활용하는 순서

**읽는 절과 그 장의 코드 상태를 맞춰 보며 대조한다.**

```text
https://github.com/PacktPublishing/Learning-Spring-Boot-4
```

**세 단계**(§2.4):

1. **GitHub 계정을 만든다** — 저장소 접근뿐 아니라 **현대 개발 도구와 협업 서비스에 연결하기 쉽다**
2. **책의 저장소를 내려받거나 웹에서 확인한다** — **지면에서 생략된 import, 파일 위치, 장별 최종 상태를 대조**하기 위해
3. **현재 읽는 절과 해당 장의 코드 상태를 맞춰 본다** — **완성본만 복사하면 중간 변경의 이유를 놓친다**

> **원본 저장소는 정답을 대신 외우는 곳이 아니라, 책의 서술과 실행 가능한 전체 문맥 사이의 간격을 메우는 자료다.**

**실용적인 대조 순서**:

```text
① 먼저 책을 따라 직접 쓴다
② 안 되면 원본에서 "그 절에 해당하는 부분"만 본다
     — 지면이 생략한 import 나 파일 위치가 대부분의 원인이다
③ 되고 나서 원본 전체와 비교한다
     — 내가 다르게 쓴 곳이 있으면 왜 그런지 확인한다
```

**②가 핵심이다** — 막혔을 때 **완성본 전체를 복사하면** 그 절이 가르치려던 것을 건너뛴다. **막힌 지점에 해당하는 조각만** 본다.

**§6의 경계**:

> **책의 GitHub 코드는 출판 시점의 기준이다. 보안 패치나 Spring Boot 최신 패치 버전까지 자동으로 반영한다고 가정하면 안 된다.**

**그래서 §2.5의 원칙이 따라온다** — **공식 문서와 책의 버전을 함께 읽는다.** 이 노트의 주 근거는 책의 Spring Boot 4.0 서술이지만, **최신 공식 문서의 지원 상한과 패치 버전은 시간이 지나면서 달라질 수 있으므로**, 실제 프로젝트를 만들 때는 **선택한 Spring Boot 버전의 시스템 요구사항을 다시 확인해야 한다.**

3. Temurin과 Oracle JDK는 다른 Java인가? "TCK 통과"가 보장하는 것은?
