## Q1. `@Tool`과 `@McpTool`을 정하는 기준

> **"이 도구를 우리 앱 말고 누가 쓸 것인가?" 아무도 없으면 `@Tool`, 있으면 MCP다.**

| | **툴 콜링** | **MCP** |
|---|---|---|
| 맞는 것 | **현재 Spring Boot 애플리케이션에 밀착된 내부 로직.** 배포 단위가 같고 노출할 이유가 없는 것 | **상호운용성이 목적인 것.** 같은 도구를 여러 AI 애플리케이션·프레임워크·생태계가 나눠 쓸 때 |

**푸는 문제**: **`@Tool`은 현재 Spring AI 프로세스 안에서만 유효**하다. **회사에 AI 진입점이 여럿**(웹 챗봇, Claude Desktop, 파트너사 어시스턴트, 슬랙 봇)**이면 나머지 셋은 각자 가격 조회를 다시 구현**한다 — **같은 로직 네 벌, 정책이 바뀌면 네 곳 수정, 그중 하나는 빠뜨린다.**

**REST API로 안 되는 이유**: **절반만 맞다.** **API는 있는데 AI가 그 API의 존재와 사용법을 어떻게 아느냐가 남는다.** **각 client마다 사람이 설정해 줘야** 하고 **도구가 추가될 때마다 반복**한다.

> **MCP가 그 "발견"까지 규약으로 만든다.** **client가 server에 붙으면 어떤 도구가 있는지, 인자가 무엇인지, 무엇에 쓰는지를 프로토콜로 물어본다.**

**"MCP가 툴 콜링을 대체한다"는 오해다**(§5) — **MCP client가 발견한 원격 도구도 결국 `ToolCallback`으로 변환되어 툴 콜링 메커니즘을 타고 실행된다.** **MCP는 도구를 어디서 가져올지를 바꿀 뿐**이고 **8단계 흐름은 [[04b-tool-calling]]과 똑같다.**

## Q2. Tools·Resources·Prompts를 나눈 기준

**부수효과의 유무다.**

| capability | **무엇인가** | **부수효과** |
|---|---|---|
| **Tools** | **model이 런타임에 호출할 수 있는 실행 가능한 함수** | **실행하면 뭔가 일어난다** |
| **MCP 리소스** | **URI로 접근하는 읽기 전용 context** — 파일, DB record, API 응답 | **읽기만 한다** |
| **MCP 프롬프트** | **재사용 가능한 prompt template** | **문구일 뿐이다** |

> **client가 각각을 다르게 다룰 수 있어야 한다.**

**실무적 의미**: client가 **Tools는 사용자 확인을 받고, Resources는 자동으로 읽고, Prompts는 목록에 보여 주는** 식으로 **정책을 나눌 수 있다.**

**Resources는 RAG 문서와 성격이 비슷하고**, **Prompts는 [[04a-prompt-engineering-in-spring-ai]]의 `.st` 파일을 공유 가능하게 만든 형태**다.

## Q3. 한 애플리케이션이 client이자 server가 되는 것

**능력이 조합될 수 있다.**

> **파일 시스템 server에서 문서를 읽어 우리 지식으로 만들고, 그 지식을 다시 우리 도구로 노출하는 식이다.**

| 역할 | 하는 일 |
|---|---|
| **`McpClient`** | **원격 server의 능력을 발견하고 연결을 관리** — 파일 시스템, 날씨, 다른 AI 시스템의 도구를 **가져다 쓴다** |
| **`McpServer`** | **자기 능력을 원격 client에 노출** — TechStore 도구를 Claude Desktop이나 파트너 앱에 **내준다** |
| **`McpSession`** | **capability 협상, 메시지 조율, 세션 상태, 오류 처리** — **양쪽이 공유** |

> **이 대칭이 MCP를 흥미롭게 만든다. 우리 앱이 소비자이면서 공급자이므로, 능력이 조합될 수 있다.**

**[[06b-consuming-mcp-tools-as-a-client]]가 그것을 실제로 보여 준다** — **같은 애플리케이션을 두 번 띄워** 하나는 서버, 하나는 client로 쓴다.

## Q4. 전송 계층을 분리한 이득

**같은 도구를 로컬 프로세스로도 원격 HTTP로도 노출할 수 있다.**

> **도구 코드는 그대로 두고 transport만 바꾼다.**

| transport | **방식** | **언제** |
|---|---|---|
| **STDIO** | **프로세스 표준 입출력** | **CLI로 띄우는 로컬 server.** Claude Desktop이 로컬 도구를 부를 때 |
| **SSE** | **HTTP streaming** | **이 장의 예제가 쓰는 방식** |
| **Streamable HTTP** | HTTP | **사양이 원격 server의 권장 transport로 옮겨 간 방식** |

**MCP 메시지는 JSON-RPC이고, 그것을 무엇으로 실어 나를지는 별개**다.

**SSE와 Streamable HTTP**(§5) — **둘 다 HTTP 기반이지만 사양의 권장이 후자로 옮겨 갔다.** **기존 client 호환이 필요하면 SSE, 새로 만들면 Streamable HTTP**다 → [[06a-exposing-application-tools-as-an-mcp-server]]에서 설정으로 고른다.

**§6의 경계**: **소비자가 우리 앱 하나뿐이면 MCP는 배관만 늘린다** · **신뢰하지 않는 server에 붙지 않는다** — **원격 도구는 실행 경로이고, 원격 응답은 prompt에 들어간다** · **부수효과가 큰 도구를 함부로 노출하지 않는다** — **우리가 모르는 client가 부른다** · **네트워크 실패를 계산에 넣는다.**

**비유로 보면** USB — **표준 포트가 생기자 아무 기기나 아무 컴퓨터에 꽂히게 됐다.** **깨지는 지점 둘**:
- **USB는 꽂으면 동작하지만 MCP는 도구를 부를지가 여전히 model의 판단**이다 — **설명이 나쁘면 꽂혀 있어도 안 쓴다**
- **USB 기기는 대체로 안전하지만 MCP 도구는 실행 권한**이다 — **신뢰하지 않는 server에 붙는 것은 신뢰하지 않는 코드를 실행 경로에 넣는 것**과 같고, **그 server가 돌려주는 내용은 간접 프롬프트 인젝션 통로**가 될 수 있다
