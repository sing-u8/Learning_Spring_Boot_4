## Q1. 총 응답 시간을 줄이지 못하는데도 도입할 가치

**첫 조각이 도착하는 시간이 200배 빨라지기 때문이다.**

```
.call():    0ms ─────────── 20초 대기 ─────────── 전체 응답
.stream():  0ms → 100ms 첫 token → 이후 계속 흐름 → 20초에 완료
                  ↑ 체감 성능이 여기서 결정된다
```

> **model은 애초에 통째로 답을 만들지 않는다. token을 하나씩 순서대로 생성한다. 첫 token은 100밀리초 만에 나와 있는데, `.call()`이 그것을 20초 동안 붙들고 있는 것이다.**

**숫자로 말하면**: **총 20초는 그대로**지만 **첫 바이트까지가 20,000ms → 100ms**다.

**사용자 행동이 그 차이를 만든다** — **"사용자는 8초쯤에 '멈췄나?' 하고 새로고침을 누르고, 그러면 20초가 처음부터 다시 시작된다."** 스트리밍은 **그 재시작을 없앤다.**

**"스트리밍이 더 빠르다"는 오해다**(§5) — **총 지연은 같다.** **바뀌는 것은 첫 바이트까지의 시간**이고 **처리량이나 비용은 개선되지 않는다.**

**§6의 경계**: **응답이 짧으면 이득이 없다** — **한두 문장짜리 분류·의도 판정 응답에 SSE 배관을 얹으면 client 코드만 복잡해진다.**

## Q2. `produces = TEXT_EVENT_STREAM_VALUE`를 빼면

**브라우저가 연결이 끝날 때까지 버퍼링한다.**

> **client에게 "이 응답은 조각으로 온다"고 알린다. 이게 없으면 브라우저가 연결이 끝날 때까지 버퍼링한다.**

**즉 서버는 흘려보내는데 client가 모아서 한 번에 보여 준다** — **스트리밍의 이득이 사라진다.** 코드는 다 맞는데 **화면 동작이 `.call()`과 같아진다.**

**세 곳이 달라져야 한다**:
| 위치 | 동기 | **스트리밍** | **왜** |
|---|---|---|---|
| `produces` | 기본값 | **`TEXT_EVENT_STREAM_VALUE`** | **client에게 알린다** |
| 반환형 | `String` | **`Flux<String>`** | **시간에 걸쳐 방출되는 흐름** |
| 실행 | `.call()` | **`.stream()`** | **model을 streaming 모드로** |

**같은 함정이 프록시 층에도 있다**(§6) — **nginx 같은 리버스 프록시가 응답을 모아 보내면 서버가 아무리 흘려도 client는 통째로 받는다.** **SSE 경로는 프록시 버퍼링을 꺼야** 한다. `curl`의 `--no-buffer`도 같은 이유다.

**`text/event-stream`은 SSE 형식**이다 — **서버가 하나의 HTTP 연결 위에서 client로 데이터를 조각조각 밀어 주는 단방향 streaming 메커니즘.** 각 줄에 **`data:` 접두**가 붙고 client가 그것을 떼고 이어 붙인다.

> **원문 표기 오류**(§5): 책 p.418의 항목 설명은 **`.Stream()`으로 대문자 S**로 적는다. **같은 쪽 코드 블록에는 소문자 `.stream()`**으로 정확히 쓰여 있어 **설명 항목만의 오타**다. **같은 종류의 오타가 [[04b-tool-calling]]의 `.Call()`, [[05c-building-the-rag-pipeline-with-advisors]]의 `.User(...)`에도** 나온다.

## Q3. 신용카드 번호가 섞일 수 있는 endpoint에 스트리밍

**쓸 수 없다. 이미 보낸 조각을 회수할 방법이 없기 때문이다.**

> **응답 후처리(필터링, 마스킹, [[07d-security-best-practices-for-ai-applications]]의 `SafeGuardAdvisor` 같은 검사)를 하려면 전체를 봐야 하는데, 스트리밍은 그 기회를 없앤다. 이것이 두 방식의 진짜 트레이드오프다.**

```
.call():    전체 응답 → 검사 → (문제 있으면 차단) → 전송
.stream():  조각 → 전송 → 조각 → 전송 → ...
                    ↑ 이미 나갔다. 되돌릴 수 없다
```

**비유의 깨짐이 이것이다** — **양동이라면 내용을 보고 "이건 못 주겠다"며 버릴 수 있지만, 스트리밍은 이미 보낸 조각을 회수할 방법이 없다.**

**§6의 경계**: **응답 전체를 검사해야 하면 못 쓴다.** **마스킹·차단·후처리가 필요한 응답은 스트리밍하는 순간 이미 나간 조각을 되돌릴 수 없다.**

**부분적 대안**: **버퍼를 두고 N토큰씩 모아 검사한 뒤 흘린다** — 첫 바이트 시간을 조금 희생하고 검사 기회를 얻는다. 다만 **경계를 걸친 패턴**(카드 번호가 두 조각에 걸침)은 여전히 어렵다.

**구조화 응답과도 안 맞는다**(§6) — **`.entity(...)`는 완성된 JSON이 있어야 매핑한다. 반쯤 온 JSON은 파싱할 수 없다.**

## Q4. `Flux<String>`을 반환하는 시점의 응답 본문

**아무것도 만들어져 있지 않다.**

> **controller가 값을 반환할 때 아직 내용이 하나도 없다. 반환되는 것은 "앞으로 여기로 조각이 흐를 것"이라는 약속이고, 실제 조각은 그 뒤에 하나씩 흘러든다.**

**[[../../part-4-scaling-an-application-with-spring-boot/chapter-9-writing-reactive-web-controllers/01b-reactive-streams-details|Ch9]]의 "조립은 실행이 아니다"와 같은 사실**이다 — **`Flux`는 레시피**이고, **프레임워크가 구독할 때 실행**된다.

**`Flux`**: **Project Reactor에서 0개 이상의 값을 시간에 걸쳐 방출하는 reactive 타입.**

**`.content()`가 동기 버전과 이름이 같지만 하는 일이 다르다** — **완성된 text를 꺼내는 게 아니라, 스트림에서 오는 각 조각의 text 부분만 뽑아 흘려보낸다.**

**WebFlux를 넣는 이유도 이 성질 때문이다** — **응답 하나가 열린 채 오래 유지되는 동안 스레드를 붙잡고 있으면 안 된다.**

**"WebFlux를 넣으면 앱 전체가 reactive가 되는가"**(§5) — **아니다.** **`spring-boot-starter-webmvc`와 `spring-boot-starter-webflux`가 함께 있으면 Spring Boot는 기본적으로 MVC(Servlet) 스택으로 뜨고, `Flux`를 반환하는 handler만 그 자리에서 스트리밍으로 동작한다.** ([[../../part-4-scaling-an-application-with-spring-boot/chapter-9-writing-reactive-web-controllers/02-creating-a-webflux-application|Ch9]]에서는 이것이 **함정**이었는데, 여기서는 **의도적 활용**이다.)

**token 단위 관찰**: `-source`가 별도 조각으로 오는 것에서 **model이 나누는 단위가 단어가 아니라 token**임이 드러난다 — `open` + `-source`.
