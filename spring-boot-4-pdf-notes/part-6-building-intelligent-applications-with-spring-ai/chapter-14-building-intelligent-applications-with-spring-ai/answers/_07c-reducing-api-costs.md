## Q1. 입력이 출력의 40배가 되는 구조

**한 요청에 실린 것들**:
| 항목 | 크기 | 출처 |
|---|---|---|
| **시스템 프롬프트** | 매번 동일, 200 token | [[02-building-llm-integrations-with-chatclient]]의 `defaultSystem` |
| **대화 이력** | 턴마다 누적 | [[05d-conversation-memory-with-chat-memory-advisor]] |
| **RAG 청크 4개** | 매번 검색, 수백~수천 token | [[05c-building-the-rag-pipeline-with-advisors]] |
| **도구 정의와 설명** | 매번 동일 | [[04b-tool-calling]] |
| **실제 사용자 질문** | **수십 token** | — |

> **사용자가 쓴 문장은 전체의 1%도 안 된다. 나머지 99%는 우리가 붙인 것이고, 그중 상당 부분은 요청마다 똑같다.**

**두 가지 낭비가 보인다**:
1. **매번 똑같은 접두부를 다시 보내고 다시 계산시킨다** → 프롬프트 캐싱
2. **사소한 작업까지 frontier model에 보낸다** → 로컬 모델 분산

**출력이 적은 이유**: model이 만드는 답변은 **수백 token 수준**이고, 대화가 길어져도 **답변 길이는 크게 안 는다.** 그래서 **비대칭이 커진다.**

## Q2. 시스템 프롬프트 맨 앞에 `현재 시각: {now}`를 넣으면

**캐시가 통째로 무효가 된다.**

> **prompt 캐싱도 접두부가 글자 단위로 일치해야 하므로, 시스템 프롬프트에 타임스탬프나 사용자 이름 같은 변하는 값을 앞쪽에 넣으면 캐시가 통째로 무효가 된다.**

**핵심 단어는 접두부(prefix)**다 — **prompt의 앞부분이 글자 단위로 같아야** 한다.

**그래서 prompt를 조립하는 순서가 비용에 영향을 준다**:
```
좋음:  [시스템 프롬프트][도구 정의] ... [RAG 청크][사용자 질문]
        └─── 고정 (캐시 가능) ───┘  └─── 변동 ───┘

나쁨:  [현재 시각][시스템 프롬프트] ...
        └ 매번 달라진다 → 그 뒤 전부 캐시 무효
```

> **고정된 것(시스템 프롬프트, 도구 정의)을 앞에, 변하는 것(검색 청크, 사용자 질문)을 뒤에 두면 캐시가 걸릴 여지가 커진다.**

**프롬프트 캐싱**: **여러 요청이 같은 prompt 접두부를 공유할 때 이미 처리한 token을 재사용하는 provider 기능** — **지연과 비용을 함께 줄인다.** **OpenAI의 prompt caching은 자동으로 동작**하고, **우리가 할 일은 prompt 구조를 캐시 친화적으로 짜고 수치로 효과를 확인**하는 것이다.

**§6의 경계**: **캐시를 전제로 prompt를 억지로 고정하지 않는다** — **응답 품질에 필요한 동적 context를 빼면서까지 캐시를 노리면 본말이 뒤집힌다.**

## Q3. 두 캐시 값이 각각 커지는 시점

| 값 | **의미** | **커지는 시점** |
|---|---|---|
| **`getCacheReadInputTokens()`** | **캐시에서 재사용된 입력 token = 실제로 아낀 양** | **두 번째 요청 이후** |
| **`getCacheCreationInputTokens()`** | **나중에 재사용하려고 저장한 token** | **첫 요청** |

> **`getCacheCreationInputTokens()`가 크면 손해인가 — 아니다. 그건 다음 요청을 위해 저장한 양이다. 첫 요청에서 크고 이후 요청에서 `getCacheReadInputTokens()`가 커지는 것이 정상 패턴이다.**

**한 번만 쓰이고 마는 prompt라면 이득이 없다** — 저장만 하고 재사용이 없다.

**네 값을 함께 읽어야 그림이 나온다**:
```java
usage.getPromptTokens()              // 이번 요청의 입력 token
usage.getGenerationTokens()          // 생성된 출력 token
usage.getCacheReadInputTokens()      // 아낀 토큰
usage.getCacheCreationInputTokens()  // 저장한 토큰
```

**[[02-building-llm-integrations-with-chatclient]]에서 본 `ChatResponse` JSON의 `cacheReadInputTokens: 0`이 바로 이 값**이다 — **첫 요청이라 아직 캐시가 없어 0**이었다.

**"캐시 히트가 출력 token도 줄여 주는가"**(§5) — **아니다.** **캐싱은 입력 접두부에만 걸린다.** **생성은 매번 새로 일어나므로 출력 token은 그대로**다.

**"RAG 청크를 캐시로 줄일 수 있는가"**(§5) — **어렵다.** **검색 결과는 질문마다 달라지므로 접두부가 아니다.** **청크 비용은 캐싱이 아니라 top-K 조정으로** 줄인다.

## Q4. 로컬 model로 넘길 작업을 정하는 기준

**① 작업의 난이도.** **분류, 의도 탐지, 가벼운 요약 같은 작업은 비싼 원격 추론이 필요 없다.**

> **"이 문의는 환불/배송/기술지원 중 무엇인가"를 판정하는 데 frontier model을 쓰는 것은 계산기로 될 일에 슈퍼컴퓨터를 쓰는 격이다.**

**② 출력의 양과 형태.** **`YES`/`NO` 수준의 짧은 출력**이면 경량 model로 충분하다 — [[07a-evaluating-llm-response-quality]]의 **`FactCheckingEvaluator`를 Bespoke-Minicheck로** 돌리라는 권고가 그 사례다.

**③ 품질 저하를 감당할 수 있는가** — **§6: 로컬 model로 넘긴 작업은 반드시 평가한다. 품질 저하가 조용히 진행된다.**

**교체가 쉬운 이유**: **같은 `ChatClient` abstraction을 쓰므로 구현 방식이 사실상 동일**하다 — **달라지는 것은 설정된 provider뿐**이다. **[[01-introducing-llms-and-spring-ai]]의 추상화가 값을 하는 지점**이다.

**두 로컬 추론 엔진**: **Ollama**(로컬 model을 내려받아 실행하고 API로 노출)와 **Docker Model Runner**(Docker Desktop 통합 GPU 가속 — **Ollama 기반 Spring AI 설정과 호환**).

**"로컬 모델은 공짜"는 오해다**(§5) — **API 비용이 0일 뿐 GPU·전기·운영 부담은 남는다.** 그리고 **로컬 추론이 느리면 사용자 대기 시간으로 비용이 옮겨 간다.**

**비유로 보면** — **프롬프트 캐싱은 택배 정기 배송**(같은 주소·포장을 재사용), **로컬 모델은 편의점과 대형마트를 나눠 쓰는 것**(우유 하나 사러 마트에 가지 않는다).

**깨지는 지점 둘**:
- **정기 배송은 주소가 한 글자만 달라도 새로 입력**해야 한다 → Q2
- **편의점은 물건이 비싸지만 로컬 model은 품질이 다르다** — **"싸니까 다 로컬로"는 품질 사고로 돌아온다**

**§6의 나머지 경계**: **개인정보가 든 prompt 접두부를 공유 캐시에 태우는 것을 확인 없이 하지 않는다** — **provider의 캐시 격리 정책을 확인** · **비용 절감을 측정 없이 판단하지 않는다** — [[07b-ai-and-observability]]의 metric 없이는 **무엇이 얼마나 줄었는지 알 수 없다.**
