## Q1. model이 "As I mentioned"라고 말할 수 있는 기술적 이유

**애플리케이션이 이전 대화 이력을 prompt에 다시 실어 보냈기 때문이다.**

> **model은 여전히 아무것도 기억하지 않는다. 애플리케이션이 이력을 들고 있다가 매 요청 다시 실어 보내는 것이다.**

**기본적으로 `ChatClient` 상호작용은 스테이트리스**다 — **각 요청이 이전 요청을 기억하지 않는 성질.** **model은 이번 요청에 담긴 것만 본다.**

> **HTTP가 stateless한 것과 같은 이유이며, 해법도 비슷하다 — 상태를 애플리케이션이 들고 있다가 매번 다시 실어 보낸다.**

**메모리 없이 무너지는 예**:
```
1턴  "환불 정책이 뭔가요?"  → "30일 이내 원래 포장 상태로..."
2턴  "디지털 상품은요?"      → "어떤 디지털 상품에 대해 말씀하시는 건가요?"
                              ↑ 1턴을 모른다
```

**결과 하나**: **5턴째 요청은 1턴째보다 token을 더 쓴다** → Q4.

**[[04-designing-prompts-and-tool-calling]]의 "시스템 프롬프트가 매 요청 다시 전송되는 이유"와 같은 사실**이다 — **model에는 세션이 없다.**

## Q2. 세 층으로 나눈 설계의 이득

```
MessageChatMemoryAdvisor      ← advisor: 이력을 prompt 에 주입
  └ MessageWindowChatMemory   ← 정책: 최근 N턴만 유지 (슬라이딩 윈도)
      └ InMemoryChatMemoryRepository ← 저장소: 어디에 담을까
```

**production 전환에서의 이득**: **저장소만 갈아 끼우면 된다.**

> **메모리는 별도 bean이다. 그래야 컨트롤러가 주입받아 advisor에 넘길 수 있고, 저장소 구현을 바꿀 때 여기만 고치면 된다.**

**`InMemoryChatMemoryRepository`의 문제**(§6): **재시작하면 대화가 사라지고, 인스턴스가 둘이면 사용자가 어느 인스턴스에 붙느냐에 따라 기억이 달라진다.**

**JDBC·Redis 저장소로 바꾸면** — **`chatMemory()` bean 메서드 한 곳**만 고치고 **컨트롤러와 advisor는 그대로**다.

**정책 층이 따로 있는 것도 이득이다** — **윈도 크기를 바꾸거나 요약 기반 메모리로 바꿔도** 저장소와 advisor는 그대로다.

**[[05c-building-the-rag-pipeline-with-advisors]]의 advisor/retriever 두 층과 같은 설계**다 — **관심사마다 교체 지점을 둔다.**

**`defaultSystem`이 "Java 전문가"에서 "TechStore 상담원"으로 바뀐 것**도 짚어 둘 만하다 — **이 애플리케이션의 persona가 이 한 곳에서 정해진다**([[02-building-llm-integrations-with-chatclient]]).

## Q3. `conversationId`를 기본값 그대로 서비스하면

**모든 사용자가 한 대화를 공유한다.**

> **`default-session`을 그대로 쓰면 모든 사용자가 한 대화를 공유한다. 시연에서는 편하지만 실제 서비스에서는 절대 안 된다.**

**구체적으로 벌어지는 일**:
- **A가 자기 주문번호를 말하면 B의 다음 질문 prompt에 그것이 실린다** — **개인정보 유출**
- **대화가 서로 뒤엉켜 답이 엉뚱해진다**
- **윈도가 금방 차서** 각자의 맥락이 밀려난다

**대응**: **인증된 사용자 ID나 세션 ID**를 `conversationId`로 쓴다. **클라이언트가 보내는 값을 그대로 믿으면** 남의 대화를 조회할 수 있으므로 **서버가 정한 값**이어야 한다.

**§6의 관련 경계**: **민감한 대화를 무기한 보관하지 않는다** — **이력은 개인정보가 될 수 있고, [[07d-security-best-practices-for-ai-applications]]의 로그·trace 노출 문제와 곧장 이어진다.**

**"메모리 ≠ RAG"도 함께**(§5) — **메모리는 "우리가 방금 나눈 말", RAG는 "회사가 가진 문서"**다. **둘 다 prompt에 텍스트를 주입하지만 출처와 수명이 다르다.**

## Q4. 30턴 대화의 비용과 완화책

**매 요청의 token이 이력 길이에 비례해 늘어난다.**

> **창 크기가 비용이다. 이력이 길수록 매 요청의 token이 늘어난다. 무한 보존이 아니라 슬라이딩 윈도인 이유다.**

```
1턴:  시스템 + 질문                              → 적다
30턴: 시스템 + 29턴 이력 + 질문 + RAG 청크 4개   → 컨텍스트 윈도를 채운다
```

**완화책**:
- **`MessageWindowChatMemory`의 슬라이딩 윈도** — **최근 N턴만 유지.** 이 예제의 기본 정책이다
- **요약 기반 메모리** — 오래된 턴을 요약문 하나로 압축
- **RAG 청크 수와 함께 예산을 관리** — 둘 다 같은 컨텍스트 윈도를 나눠 쓴다([[01-introducing-llms-and-spring-ai]])

**윈도가 짧으면**: 오래된 맥락을 잃는다 — **"아까 말한 그 상품"이 안 통한다.** **길이와 비용의 맞바꿈**이다.

**§6의 나머지 경계**: **단발 질의에는 붙이지 않는다** — **분류·요약처럼 이전 맥락이 무의미한 endpoint에 메모리를 붙이면 관련 없는 이력이 답을 오염시킨다.**

**메모리 advisor를 어디에 등록할지도 그 판단이다**(§5) — **이 예제는 컨트롤러에서 요청마다 붙여 이 endpoint에만** 적용된다. **`defaultAdvisors(...)`로 등록하면 그 client의 모든 호출**에 붙는다. **검색 endpoint처럼 메모리가 없어야 하는 경로가 섞여 있으면 전자, 애플리케이션 전체가 챗봇이면 후자**다.

**advisor 셋을 함께 엮은 것도 이 절의 결론**이다 — `SimpleLoggerAdvisor`(관측), `MessageChatMemoryAdvisor`(기억), `RetrievalAugmentationAdvisor`(지식)가 **한 체인**에 들어간다. [[05c-building-the-rag-pipeline-with-advisors]]가 말한 **"같은 자리에 같은 방식으로 붙는다"**의 실제 모습이다.
