## Q1. "model이 실행하지 않고 요청만 한다"가 드러나는 단계

**4번이다.**

| # | 일어나는 일 | **왜 필요한가** |
|---:|---|---|
| 2 | 애플리케이션이 prompt와 **도구 목록·설명**을 함께 보낸다 | **model은 존재를 모르는 도구를 부를 수 없다** |
| 3 | model이 도구가 필요하다고 **판단한다** | **분기 로직이 우리 코드가 아니라 model 안에 있다** |
| **4** | **최종 응답 대신 도구 이름과 인자를 담은 tool-call 요청을 돌려준다** | **model은 실행 권한이 없다. 요청만 할 수 있다** |
| **5** | **Spring AI가 그 요청을 가로채 해당 Java 메서드를 호출한다** | **실행 권한은 우리 프로세스에 있다. 이 경계가 안전장치다** |
| 7 | 결과를 **추가 context로** model에 다시 보낸다 | **model이 결과를 문장으로 옮기려면 결과를 봐야 한다** |

> **model은 실행 권한이 없다. 요청만 할 수 있다.**

**왜 중요한가**: **실행 권한이 우리 프로세스에 있다는 것이 안전장치**다. model이 **무엇을 부를지 제안**하지만 **실제로 무엇이 실행되는지는 우리 코드가 정한다** — 인자 검증, 권한 검사, 거부가 5번 자리에서 가능하다.

> **호출자에게 이 왕복은 완전히 투명하다.** 우리 코드는 `.call().content()` 한 줄만 부르고 **중간 단계를 보지 못한다. 추가 orchestration 코드는 없다.**

## Q2. `description`을 "Gets data."로 바꾸면

**model이 도구를 안 부르거나 엉뚱할 때 부른다.**

> **model이 이 문장만 보고 도구를 고른다. 메서드 본문도, 반환 타입의 의미도 model은 모른다.**

```
"Returns the current date and time in ISO-8601 format."
   → "지금 몇 시?" 질문에 확실히 매칭

"Gets data."
   → 어떤 질문에도 애매하다 → 안 부르거나 아무 때나 부른다
```

**§6의 관련 경계**: **도구가 많아지면 선택 정확도가 떨어진다.** **설명이 비슷한 도구를 여럿 두면 model이 헷갈린다. 이름과 설명을 서로 구별되게** 쓴다.

**"내가 도구를 고른다"는 오해다**(§5) — **우리는 후보 목록을 준다. 선택은 model이 한다.** 그래서 **도구가 안 불렸을 때 고칠 곳은 분기 코드가 아니라 `description`**이다.

**`name` 속성도 같은 원리다** — **생략하면 Java 메서드 이름이 도구 이름**이 되고, **`get`·`find`처럼 일반적인 이름이면 model이 목적을 짐작하기 어려우니 명시적인 이름**을 주는 편이 낫다. **같은 원칙이 [[06a-exposing-application-tools-as-an-mcp-server]]의 `@McpTool`에도** 적용된다.

> **원문 표기 오류**(§5): 책 p.430의 항목 설명은 **`.Call().content()`로 대문자 C**로 적는다. **코드 블록에는 소문자 `.call()`**이므로 **설명 항목만의 오타**다. 같은 종류가 [[03-reactive-streaming-with-chatclient]]의 `.Stream()`, [[05c-building-the-rag-pipeline-with-advisors]]의 `.User(...)`에도 있다.

## Q3. 두 도구가 불린 예제에서 우리가 작성하지 않은 코드

**도구 선택 로직, 호출 순서, 인자 추출, 결과 병합 — 즉 orchestration 전부다.**

```java
chatClient.prompt().user(question).tools(dateTimeTools).call().content();
//                                 └────────┬────────┘
//                          bean 을 통째로 넘긴다. 메서드를 하나하나 등록하지 않는다
```

**`.tools(bean)`이 하는 일**: **Spring AI가 그 안에서 `@Tool`이 붙은 메서드를 전부 찾아 model에 노출한다.**

**우리가 안 쓴 것**:
- **"가격 질문이면 A, 시각 질문이면 B" 분기** — model이 판단(3단계)
- **인자 파싱** — model이 인자를 채워 보낸다(4단계)
- **두 도구를 순서대로 부르는 코드** — Spring AI가 왕복을 반복
- **결과를 문장으로 조립하는 코드** — model이 한다(8단계)

**우리가 쓴 것은 셋뿐**: **`@Tool` 메서드 본문**, **`description`**, **`.tools(bean)` 한 줄.**

**`.tools(bean)`은 그 요청에만 적용된다**(§5) — **모든 요청에 붙이려면 builder에서 `defaultTools(...)`**를 쓴다. [[05d-conversation-memory-with-chat-memory-advisor]]에서 advisor에도 같은 `default...` 패턴이 나온다.

**주의**: **도구 결과 문자열이 곧 응답은 아니다** — **`getProductPrice`가 `"Price: $49.99"`를 반환해도 사용자가 보는 문장은 model이 다시 쓴 것**이다. **정확한 값이 그대로 보이길 원하면 그 값을 응답에서 따로 꺼내 쓰거나 구조화 응답**을 쓴다.

## Q4. `deleteOrder(Long id)`를 `@Tool`로 노출하기 전에

**① 부수효과의 크기.** **조회는 안전하지만 `deleteOrder(id)` 같은 도구는 model의 판단 하나로 실행된다.**

**② 확인 절차나 권한 검사.** **메서드 안에 두거나 아예 노출하지 않는다.**

> **부수효과가 큰 작업을 그대로 노출하지 않는다.**

**추가로 확인할 것**:
- **인자가 조작될 수 있다** — model이 채우는 `id`는 **사용자 입력에서 유래**한다. 프롬프트 인젝션으로 **남의 주문 ID**가 들어올 수 있다([[04a-prompt-engineering-in-spring-ai]] Q3)
- **멱등성** — 8단계 왕복이 재시도되면 **두 번 실행**될 수 있다
- **감사 기록** — **누가 왜 삭제했는지**가 남아야 한다. "model이 판단했다"는 근거가 되지 않는다

**Q1의 5번 단계가 방어 지점이다** — **실행 권한이 우리 프로세스에 있으므로**, 메서드 안에서 **권한 검사와 확인 절차**를 넣을 수 있다.

**가장 안전한 설계**: **조회 도구만 노출하고, 변경은 사용자 확인을 거치는 별도 흐름**으로 둔다. model은 **"주문 12345를 삭제할까요?"라고 제안**하고 **실제 삭제는 사용자가 버튼을 누를 때** 일어난다.

**§6의 나머지 경계**: **대량의 비정형 지식에는 맞지 않는다** — **정책 문서 200쪽을 도구로 반환할 수는 없다. 그건 RAG의 일**([[05-implementing-rag-with-vector-stores-and-advisors]]). **프로세스 밖에서는 못 쓴다** — **`@Tool`은 현재 Spring AI 프로세스 안에서만 유효**하고, 공유하려면 [[06-building-chatbots-and-mcp-integration]]의 **MCP**가 필요하다.
