## Q1. FAQ 전체를 시스템 프롬프트에 넣는 것과 RAG

| | **전체를 프롬프트에** | **RAG** |
|---|---|---|
| **비용** | **매 요청 전체 분량의 token** | **관련된 몇 조각만** |
| **정확도** | **필요한 두 문장이 39개의 무관한 항목 속에 파묻힌다** | 관련 조각만 있어 주의가 집중된다 |
| 한계 | **문서가 200쪽이면 아예 들어가지도 않는다** | 양에 관계없이 top-K만 |
| 갱신 | 프롬프트 수정 | **재색인** |

> **`getFaqDocument()`가 40개 항목 전문을 반환하면 매 요청 그 전체가 prompt로 들어간다.**

**세 번째 대안(fine-tuning)도 안 되는 이유**: **비싸고 오래 걸리며, 정책이 바뀔 때마다 다시 해야 한다.**

> **RAG가 이 셋 사이를 지나간다. model을 건드리지 않고, 문서 전체를 넣지도 않고, 이번 질문에 관련된 몇 조각만 찾아 넣는다.**

**이름 그대로다** — **Retrieval(검색)로 Augmented(증강)된 Generation(생성).**

**세 단계**:
| 단계 | **하는 일** | **왜 필요한가** |
|---|---|---|
| **검색** | 질문을 임베딩으로 바꿔 top-K 조각을 찾는다 | **넣을 수 있는 양이 유한하므로 골라야 한다** |
| **증강** | 조각을 prompt에 끼워 넣는다 | **model이 볼 수 있는 것은 오직 prompt뿐** |
| **생성** | 주어진 근거에 기대어 답한다 | **그라운딩** |

**"RAG는 model을 학습시킨다"는 오해다**(§5) — **model 가중치는 손대지 않는다.** **바뀌는 것은 prompt의 내용뿐**이고, 그래서 **문서를 고치면 다음 요청부터 바로 반영되고 model 교체와도 독립적**이다.

## Q2. 색인 offline / 질의 online 분리가 없으면

**요청마다 문서 전체를 임베딩해야 하므로 느려진다.**

> **임베딩 생성은 비싼 연산인데, 문서 쪽은 한 번만 하고 질의 쪽만 매번 한다.**

| | **색인 — offline** | **질의 — online** |
|---|---|---|
| 언제 | **애플리케이션이 뜰 때(또는 문서가 바뀔 때) 한 번** | **요청마다** |
| 하는 일 | 조각내기 → 임베딩 → 벡터 스토어 저장 | 질문 임베딩 → 검색 → prompt → 생성 |
| 사용자가 보나 | **못 본다** | 본다 |
| 관련 노트 | [[05b-ingesting-documents-with-the-etl-pipeline]] | [[05c-building-the-rag-pipeline-with-advisors]] |

**분리가 없으면**: 문서 200쪽을 **매 요청 임베딩**하게 된다 — **비용과 지연이 문서 양에 비례**해 늘고, RAG의 이점이 통째로 사라진다.

**질의 쪽 임베딩은 한 번뿐이다** — **질문 하나**만 벡터로 바꾸면 되므로 싸다. **비대칭이 이 설계의 핵심**이다.

## Q3. "재고 있나요?"를 RAG로 답하게 하면

**낡은 값을 근거 있게 답한다.**

> **가격이 바뀌면 문서를 다시 색인해야 하고, 그 사이 model은 낡은 값을 근거 있게 답한다. 최신성이 중요한 값은 도구로 가져와야 한다.**

**"근거 있게"가 문제를 키운다** — RAG 응답은 **문서를 인용**하므로 **더 믿음직해 보인다.** 사용자는 **틀린 재고를 확신을 갖고** 받는다.

| | **툴 콜링** | **RAG** |
|---|---|---|
| 데이터 성격 | **구조화·실시간** | 비정형·대량 |
| 예 | **가격, 재고, 현재 시각, 주문 상태** | 문서, 계약, 정책 |
| **정확성의 근원** | **메서드가 정확한 값을 반환한다** | **검색이 맞는 조각을 찾아야 한다** |
| **최신성** | **호출 시점의 값** | **마지막 색인 시점의 문서** |

**§6의 지침**: **자주 바뀌는 구조화 값(가격·재고·잔액)에는 쓰지 않는다. 도구로 조회한다.**

**둘은 보완적이다** — **실무 AI 애플리케이션은 대개 둘 다** 쓴다. [[05d-conversation-memory-with-chat-memory-advisor]]의 챗봇이 그 형태다.

## Q4. RAG를 붙였는데도 환각이 나오면

**먼저 검색 품질을 의심한다.**

> **검색이 엉뚱한 조각을 가져오면 model은 그 조각을 근거로 자신 있게 틀린 답을 한다. 게다가 근거가 붙어 있어 더 믿음직해 보인다. 검색 품질이 곧 답변 품질이다.**

**"RAG를 쓰면 환각이 사라진다"는 오해다**(§5) — **줄어들 뿐이다.**

**확인 순서**:
1. **검색된 조각이 무엇인가** — 그 조각으로 답할 수 있는 질문이었나
2. **청킹이 적절한가** — 문장이 중간에서 잘려 의미가 깨졌나([[05b-ingesting-documents-with-the-etl-pipeline]])
3. **top-K가 적절한가** — 너무 적어 못 찾았나, 너무 많아 흩어졌나
4. **애초에 문서에 그 내용이 있나** — 없으면 검색이 아무리 좋아도 답이 없다

**top-K를 키우면 항상 좋은가**(§5) — **아니다.** **context가 풍부해지지만 prompt 크기와 token 비용이 같이 커지고, 무관한 조각이 섞여 들어와 model의 주의를 흩뜨린다.**

**비유로 보면** 오픈북 시험 — **교재 몇 쪽을 찾아 책상에 올려 준다.** **깨지는 지점 셋**:
- **학생은 필요하면 책을 더 넘겨 본다. model은 넘겨 볼 수 없다** — **우리가 올려 준 top-K 조각이 전부**
- **학생은 "이 자료로는 답할 수 없다"고 말할 줄 안다. model은 자료가 부족해도 그럴듯하게 채워 넣을 수 있다** → [[07a-evaluating-llm-response-quality]]
- **책상에 올린 자료가 오염되어 있으면 학생은 그걸 지시로 읽을 수도 있다** → [[07d-security-best-practices-for-ai-applications]]의 **간접 프롬프트 인젝션**

**§6의 나머지 경계**: **문서가 몇 문단뿐이라면 그냥 시스템 프롬프트에** · **정확한 인용이 법적으로 요구되면 검색된 원문을 함께 보여 주고 model 요약은 보조로** · **오염 가능한 출처를 무검증 색인하지 않는다** — **벡터 스토어에 들어간 문장은 언젠가 prompt가 된다.**
