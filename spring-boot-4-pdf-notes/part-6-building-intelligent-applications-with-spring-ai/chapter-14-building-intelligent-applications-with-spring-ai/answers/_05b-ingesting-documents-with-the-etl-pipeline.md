## Q1. 통째로 임베딩하면 검색 단계에서 무너지는 것

**① 벡터가 무의미해진다.** `product-faq.txt` 전체를 벡터 하나로 만들면 **"환불·배송·보증·사양·결제가 전부 섞인 무언가"의 좌표**가 된다. **"환불 정책이 뭔가요?"의 벡터와 별로 가깝지 않다.**

**② top-K가 무의미해진다.** **검색에 걸려도 돌려주는 것은 문서 전체**라, **top-K로 걸러 낸 의미가 없어진다.**

**③ 컨텍스트 윈도에 안 들어간다.** **검색 결과가 곧 prompt에 붙는데, 200쪽 문서 한 덩어리는 붙일 수가 없다.**

> **그래서 읽고 → 쪼개고 → 저장하는 세 단계가 필요하다.**

**ETL 파이프라인**: **문서를 읽고 가공해 저장하는 데이터 처리 경로** — **데이터 엔지니어링에서 오래 쓰인 Read → Transform → Load**가 그대로 들어온다.

## Q2. 세 인터페이스를 함수형 인터페이스에 대응시키면

| Spring AI | **함수형 패턴** | **명확해지는 것** |
|---|---|---|
| **`DocumentReader`** | **`Supplier`** | **입력 없이 값을 만들어 낸다** — 출처가 무엇이든 `Document`로 통일 |
| **`DocumentTransformer`** | **`Function`** | **문서 목록을 받아 문서 목록을 낸다** — 그래서 여러 개를 이어 붙일 수 있다 |
| **`DocumentWriter`** | **`Consumer`** | **받아서 소비하고 끝난다** — 반환값이 없다 |

**중요한 사실 하나**: **`VectorStore`가 `DocumentWriter`를 구현한다.** 그래서 **별도 어댑터 없이 pipeline의 종착점**이 될 수 있다.

**그것이 `accept()`라는 메서드 이름의 이유이기도 하다**(§5) — **`Consumer.accept(T)`가 그 인터페이스의 메서드 이름이라 `save`나 `write`가 아니라 `accept`**가 됐다.

**대응이 주는 것**: **각 단계의 계약이 자바 표준 개념으로 읽힌다.** 이름을 외우지 않아도 **`Supplier`니까 만들어 내고, `Function`이니까 변환하고, `Consumer`니까 끝**이라는 것이 바로 보인다.

**그리고 출처가 바뀌어도 나머지가 그대로다** — `TextReader` 자리에 `PagePdfDocumentReader`·`MarkdownDocumentReader`·`TikaDocumentReader`·`JsonReader`를 넣으면 된다. **어떤 reader를 쓰든 나머지 pipeline은 그대로**이고, **이것이 세 단계를 인터페이스로 나눠 둔 이유**다.

## Q3. `vectorStore.accept(chunks)`가 하는 두 일

**① 임베딩 생성**(OpenAI API 호출, **비용 발생**) **② DB 저장.**

> **청크가 100개면 임베딩 API를 그만큼 부른다. 그래서 이 단계가 offline인 것이다.**

**한 줄에 압축돼 있어 비용이 안 보인다** — 코드만 보면 **DB insert 한 번**처럼 읽히지만 실제로는 **네트워크 왕복 100번 + 과금**이다.

**§6의 관련 경계**: **한 번에 대량을 색인할 때 rate limit을 고려한다.** **청크마다 임베딩 API 호출이 나가므로 수천 개를 한꺼번에 밀면 제한에 걸린다.**

**나머지 요소들의 이유**:
| 요소 | **왜 필요한가** |
|---|---|
| `@PostConstruct` | **첫 요청이 오기 전에 벡터 스토어가 채워져 있어야** 검색이 성립 |
| `@Value("classpath:...")` | **jar에 함께 패키징되어 배포 시 경로가 어긋나지 않는다** |
| `getCustomMetadata().put("source", ...)` | **"이 답의 근거가 어느 파일이었나"를 되짚을 유일한 실마리** |
| `withChunkSize(800)` | **작으면 검색 정밀도, 크면 문맥 보존** — **RAG 품질의 조절 손잡이** |
| `withMinChunkSizeChars(100)` | **의미 없는 파편이 독립 청크로 남는 것을 막는다** |

**청크 크기의 트레이드오프**:
| 크기 | **장점** | **단점** |
|---|---|---|
| 작다(200) | **정확한 문장을 집는다** | **문맥이 잘려 "그것은 30일입니다"처럼 주어가 없는 조각** |
| 크다(2000) | **문맥이 온전하다** | **무관한 내용이 딸려 와 prompt를 채우고 주의를 흩뜨린다** |

**800은 "FAQ 한두 항목"에 해당**하고, **정답은 실험으로 찾는다** — [[07a-evaluating-llm-response-quality]]가 그 채점 도구다.

> **원문의 구버전 API**(§5): 책 코드는 `withChunkSize(800)`·`withMinChunkSizeChars(100)`을 쓰는데 **책 자신이 바로 다음 쪽에서** 최신 Spring AI는 **`with` 접두를 뗀 `chunkSize(...)`·`minChunkSizeChars(...)`** 스타일이라고 경고한다. **즉 예제 코드가 이미 구버전 API**다.

## Q4. `@PostConstruct` 색인을 3-인스턴스 환경에 두면

**같은 문서가 세 벌 중복 색인되고, 재시작할 때마다 임베딩 API 비용이 또 든다.**

> **애플리케이션이 뜰 때마다 다시 색인한다. 인스턴스를 여러 개 띄우면 같은 문서가 중복 색인되고, 재시작할 때마다 임베딩 API 비용이 또 든다. 시연·학습용 구성이며, production에서는 별도 색인 작업이나 중복 확인이 필요하다.**

**중복 색인의 실질적 피해**:
- **검색 결과가 같은 조각으로 채워진다** — top-K 4개가 **전부 동일한 청크의 복사본**일 수 있다
- **저장 공간과 검색 시간이 는다**
- **비용이 인스턴스 수 × 재시작 횟수만큼** 든다

**[[../../part-3-releasing-an-application-with-spring-boot/chapter-7-releasing-an-application-with-spring-boot/04c-running-the-setup-with-docker-compose|Ch7]]과 [[../../part-4-scaling-an-application-with-spring-boot/chapter-10-working-with-data-reactively/04-loading-data-with-r2dbcentitytemplate|Ch10]]이 같은 문제를 짚었다** — **"기동할 때마다 하는 일"은 인스턴스를 늘리는 순간 여러 번 일어난다.** Ch7은 `@Profile("setup")`으로, Ch12는 마이그레이션 도구로 막았다.

**여기서의 대응**: **별도 색인 작업(배치·CLI)**으로 빼거나, **문서 해시로 중복 확인** 후 skip.

**§6의 나머지 경계**:
- **자주 바뀌는 데이터를 색인하지 않는다** — **재색인 비용과 지연 때문에 낡은 답**이 나온다. [[04b-tool-calling]]로 조회
- **신뢰할 수 없는 출처를 그대로 넣지 않는다** — **색인된 문장은 언젠가 prompt가 되므로** [[07d-security-best-practices-for-ai-applications]]의 **간접 프롬프트 인젝션 통로**
- **개인정보가 든 문서를 무분별하게 넣지 않는다** — **검색되어 prompt에 실리고, 관측 설정에 따라 로그·trace에도** 남을 수 있다

**비유의 깨짐도 함께**: 색인 카드 만들기 — **사서는 문맥을 보고 카드를 나누지만 `TokenTextSplitter`는 token 개수로 자를 뿐**이라 **한 답변이 두 청크로 갈라져 어느 쪽도 완전하지 않게** 될 수 있다. 그리고 **카드는 사람이 읽고 고칠 수 있지만 저장된 것은 벡터라 사람이 읽을 수 없다** — 그래서 **`source` 메타데이터**를 붙인다.
