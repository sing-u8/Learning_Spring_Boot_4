## Q1. `assertEquals`와 `contains`가 둘 다 부적합한 이유

**`assertEquals` — 맞는 답을 실패시킨다**(위음성):
- "You can return items within 30 days for a full refund."
- "환불은 구매 후 30일 이내에 가능합니다."
- "Our return window is 30 days from purchase, provided the item is unused."

> **셋 다 맞는 답이다. 문자열은 전부 다르다.**

**`contains("30 days")` — 틀린 답을 통과시킨다**(위양성):
> **"Unlike our competitors who offer 30 days, we do not accept returns." — `contains`는 통과, 내용은 정반대.**

**근본 원인**: **전통적 software에서는 정확성이 대체로 이진적**이다(`add(2, 3)`은 5거나 아니거나). **LLM 응답은 스펙트럼 위에 있다** — **문법은 완벽한데 사실이 틀렸을 수도, 사실은 맞는데 질문과 무관할 수도, 아예 환각일 수도** 있다.

> **그래서 필요한 것은 의미적 품질을 재는 방법이고, 가장 실효적인 방법이 다른 model에게 채점을 맡기는 것이다.**

## Q2. `DOCUMENT_CONTEXT`를 안 넘기면

**평가자가 자기 학습 지식으로 판단하게 되어 판정이 무의미해진다.**

> **평가자는 답만 보고 판단하지 않는다. model이 실제로 본 근거를 함께 받는다. 그래야 "이 답이 그 근거로부터 나올 수 있는가"를 물을 수 있다.**

**TechStore 같은 가상 회사의 정책은 평가할 방법이 없다**(§5) — 평가 model의 학습 데이터에 **없기 때문**이다.

**평가 흐름 5단계에서 4번이 핵심**:
```
1. 사용자 질문
2. RAG pipeline 통과 (검색 → prompt 주입)
3. model 이 근거 기반 응답 생성
4. 원래 질문 + 검색된 context + 생성된 답 → 평가자 model    ← 세 가지 전부
5. 평가자가 관련성·정확성·근거 기반 여부를 판정
```

> **근거 없이 답만 보면 평가자도 자기 학습 지식으로 판단하게 되어, 우리 회사 정책 같은 private 지식은 평가할 수 없다.**

**`DOCUMENT_CONTEXT`**: **advisor가 응답 metadata에 채워 두는 검색 문서 key** — **이번 요청에서 실제로 검색된 청크**를 꺼낸다. **이 값 없이는 "근거에 기반했는가"를 물을 수 없다.**

**그래서 `.call().chatResponse()`가 필요하다** — **text가 아니라 전체 응답을 받아야 metadata에 닿는다**([[02-building-llm-integrations-with-chatclient]]의 세 형태 중 두 번째).

## Q3. 두 평가기가 각각 잡는 실패

| 평가기 | **보는 것** | **잡는 실패의 예** |
|---|---|---|
| **`RelevancyEvaluator`** | **"이 답이 그 질문에 대한 답인가"** | **검색이 엉뚱한 청크를 집어 model이 배송 정책으로 환불 질문에 답한 경우** |
| **`FactCheckingEvaluator`** | **"이 문장들이 근거 문서에 실제로 있는가"** | **그라운딩이 무너진 지점, 즉 환각** |

> **둘을 나눈 이유는 실패 유형이 다르기 때문이다. 관련은 있는데 지어낸 답, 사실인데 동문서답 — 한 지표로는 구분되지 않는다.**

**구체적 예를 만들면**:
```
질문:  "환불 정책이 뭔가요?"

Relevancy 실패:  "배송은 2~3일 걸립니다."          (사실이지만 질문과 무관)
FactChecking 실패: "환불은 60일 이내 가능합니다."   (관련은 있지만 문서에 없다)
```

**테스트가 잡는 것이 model 품질만이 아니다** — **`isPass()`가 실패하면 RAG pipeline이 잘못된 청크를 가져왔거나, 지식 베이스에 답이 없거나**다. **즉 색인·검색 설정의 회귀**를 잡는다. **[[05b-ingesting-documents-with-the-etl-pipeline]]의 청크 크기를 바꿨을 때 좋아졌는지 나빠졌는지를 이걸로 판단**한다.

**평가자를 싸게 만들 수 있다** — **평가 model이 애플리케이션 model과 같을 필요가 없다.** **`FactCheckingEvaluator`는 경량 model과 잘 맞고**, **Bespoke Minicheck**를 **Ollama**로 돌리면 **`YES`/`NO` 수준의 짧은 출력만 내므로 최소 token으로, 외부 API 비용 0으로** 평가한다.

**이 조합이 실용적인 이유**: **평가가 호출 수를 두 배로 늘린다.** **응답 한 번마다 평가 한 번이면 비용이 두 배**인데, **평가 쪽을 로컬 경량 model로 돌리면 그 증가분이 사라진다** → [[07c-reducing-api-costs]].

## Q4. 매 커밋마다 돌리면 안 되는 이유

1. **느리다** — **`@SpringBootTest`로 컨텍스트를 띄우고 실제 벡터 스토어를 읽는다**
2. **돈이 든다** — **model API를 두 번 호출한다**(생성 1 + 평가 1)
3. **네트워크에 의존한다** — 외부 API가 죽으면 빌드가 깨진다

> **CI에서 매 커밋 돌릴 성질의 것이 아니라, 릴리스 전이나 nightly에 도는 통합 테스트다.**

**"평가 테스트는 단위 테스트다"는 오해다**(§5) — **통합 테스트**다.

**네 번째 이유도 있다 — 결과가 결정적이지 않다.** **평가자도 model이라 위양성·위음성이 있고**, **같은 답을 두 번 채점하면 다르게 나올 수 있다.** 매 커밋 게이트로 쓰면 **무작위로 빌드가 깨진다.**

> **"PASS가 나오면 답이 맞다" — 이 테스트의 가치는 개별 판정의 정확성이 아니라 회귀 감지에 있다.** **어제 통과하던 질문 세트가 오늘 절반 실패하면 뭔가 바뀐 것이다.**

**§6의 경계**:
- **결정적 출력에는 필요 없다** — **구조화 응답의 필드 존재 여부, 숫자 범위 같은 것은 평범한 assertion으로.** **LLM 평가는 자연어 품질에만**
- **모든 요청을 실시간 평가하지 않는다** — **응답 지연이 두 배, 비용도 두 배.** **표본 추출이나 오프라인 배치**가 현실적
- **평가 결과를 그대로 사용자에게 보여 주지 않는다**
- **평가 데이터에 민감 정보가 담긴다** — **질문·검색 문서·답이 모두 평가 model로 전송**된다. **외부 API를 평가자로 쓰면 그 데이터가 나간다** → [[07d-security-best-practices-for-ai-applications]]

**평가와 생성에 같은 model을 쓰는 것**(§5) — **편하지만 편향을 공유한다. 가능하면 다른 계열 model을 평가자로** 둔다.

**비유로 보면** 논문 심사 — **심사위원이 원고와 참고문헌을 함께 받아 "이 주장이 저 문헌으로 뒷받침되는가"를 본다.** **깨지는 지점 셋**:
- **심사위원은 책임을 지지만 평가 model은 틀려도 아무 대가가 없고 실제로 틀린다**
- **심사위원은 "제 전문이 아닙니다"라고 사퇴할 수 있지만 model은 모르는 분야도 판정을 낸다**
- **저자와 심사위원이 같은 편향을 공유**할 수 있다 — **같은 계열 model을 쓰면 같은 종류의 실수를 서로 못 알아본다**
