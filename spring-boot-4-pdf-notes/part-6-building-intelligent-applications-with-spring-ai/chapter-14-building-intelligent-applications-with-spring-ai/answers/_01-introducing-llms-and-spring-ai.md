## Q1. "model이 우리 가격표를 모른다" — tool calling인가 RAG인가

**tool calling이다.**

> **tool calling은 가격·재고·현재 시각 같은 구조화된 실시간 데이터, RAG는 문서·계약·정책 같은 대량의 비정형 지식을 맡는다.**

**판단 기준 셋**:
| | **tool calling** | **RAG** |
|---|---|---|
| 데이터 성격 | **구조화** (DB 행, API 응답) | **비정형** (문서, 정책) |
| 시점 | **실시간** — 지금 값 | 비교적 정적 |
| 양 | 질의 하나로 몇 건 | **대량** — 검색이 필요 |

**가격표는 셋 다 tool calling 쪽**이다 — `PRICES` 테이블의 **지금 값**을 **한 행** 읽으면 된다.

**세 실패 예의 배정**:
```
"spring-book 지금 얼마예요?"  → tool calling (DB 조회)
"지금 몇 시죠?"                → tool calling (시계)
"환불 정책이 어떻게 되나요?"   → RAG (정책 문서 검색)
```

**세 번째가 가장 위험하다** — **그럴듯한 답이 나온다.** "보통 30일 이내"인데 **우리 정책은 14일**이고, **틀렸다는 신호가 응답 어디에도 없다.**

**원인은 하나다** — **LLM은 학습 때 익힌 패턴으로 다음 토큰을 예측할 뿐, 우리 시스템에 살아 있는 연결을 갖고 있지 않다.**

**둘은 경쟁이 아니라 분업**이며, 이 장에서 반복해 나온다.

## Q2. 컨텍스트 윈도를 두 배로 늘리면

**좋아지는 것**: **대화 이력을 더 넣을 수 있고, RAG로 더 많은 문서 조각을 넣을 수 있다.**

**나빠지는 것**: **token 소비와 비용이 커진다.**

**핵심 사실 하나** — **prompt와 생성될 응답이 같은 예산을 나눠 쓴다.**

```
창 8K:  prompt 6K 넣으면 응답은 2K 까지
창 16K: prompt 6K 넣으면 응답은 10K 까지  ← 응답 여유가 는다
        prompt 14K 넣으면 응답은 2K       ← 넣은 만큼 줄어든다
```

> **대화 이력 20턴을 넣으면 그만큼 답이 짧아진다.**

**비용은 정비례한다** — provider가 **token 단위로 과금**하므로, prompt를 두 배로 넣으면 **매 요청 비용이 두 배**다. 요청이 하루 10만 건이면 그 차이가 그대로 청구서다.

**"컨텍스트 윈도가 크면 RAG가 필요 없다"는 오해다**(§5) — **넣을 수 있는 양과 넣어야 할 양은 다르다.** **사내 문서가 수천 쪽이면 아무리 창이 넓어도 전부는 못 넣고, 넣을 수 있다 해도 매 요청 수천 쪽 분량의 token을 지불**하게 된다. **RAG는 "관련된 몇 조각만" 넣기 위한 것**이다.

## Q3. `DataSource` 교체 비유가 깨지는 지점

> **`DataSource`는 뒤에 무엇이 있든 `SELECT`가 같은 결과를 준다. model provider는 그렇지 않다.**

**깨지는 것들**:
- **같은 prompt를 OpenAI와 Anthropic에 보내면 다른 문장이 나온다**
- **tool calling 지원 여부**가 다르다
- **structured output의 정확도**가 다르다
- **지원하는 modality**가 다르다

> **Spring AI가 지켜 주는 것은 코드의 모양이지 응답의 동등성이 아니다.**

**실무적 귀결**: **provider를 바꾸면 prompt와 평가를 다시 돌려야 한다** — [[07a-evaluating-llm-response-quality]]가 필요한 또 하나의 이유다.

**§6도 같은 말을 한다**: **추상화가 응답 품질을 옮겨 주지는 않는다.** **provider를 바꾸면 prompt·평가·비용 계산을 다시** 해야 한다.

**비유가 맞는 부분은 남는다** — **`DataSource`를 H2에서 PostgreSQL로 바꿔도 repository 코드는 그대로**이듯, **provider를 바꿔도 `ChatClient` 코드는 그대로**다. 깨지는 것은 **결과의 동등성**이다.

**Spring AI가 푸는 것이 정확히 두 번째 문제**라는 점도 함께 — **첫 번째(model이 우리 데이터를 모른다)는 여전히 RAG와 tool calling으로 풀어야** 하고, Spring AI는 **그 해법을 provider 중립적으로 쓸 수 있게** 만든다.

## Q4. `ChatClient`가 `Client`인 이유

**`WebClient`·`RestClient`와 같은 자리를 노렸기 때문이다.**

> **"요청을 fluent하게 조립해서 원격 시스템에 보내고 응답을 꺼낸다"는 역할이 같다.**

```
prompt().user(...).call().content()
get().uri(...).retrieve().body(...)
        ↑ 리듬이 같다
```

**반대로 `ChatModel`은 "model 한 번 호출"이라는 더 낮은 층**이라 **`Model`이라는 이름**을 쓴다.

| | **`ChatModel`** | **`ChatClient`** |
|---|---|---|
| 층 | **provider 중립 저수준 chat abstraction** | **fluent 고수준 client** |
| 하는 일 | **한 번의 model 호출** | **prompt 조립 + advisor 체인 + 응답 변환** |
| 누가 쓰나 | **starter가 구현, 직접 쓸 일은 적다** | **우리가 실제로 만지는 것** |
| 이 장에서 | [[07a-evaluating-llm-response-quality]]의 test에서 evaluator를 직접 만들 때만 | **거의 전부** |

**이름이 층을 알려 준다** — Spring의 다른 `*Client`들과 나란히 놓으면 **"내가 만질 것"**임이 바로 읽힌다.

**네 추상 전체**:
| 추상 | 맡는 일 |
|---|---|
| `ChatModel` | 한 번의 model 호출 |
| **`EmbeddingModel`** | **의미의 수치화** → [[05a-embeddings-and-vector-stores]] |
| **`VectorStore`** | **의미 기반 검색** — pgvector 뒤에 숨는다 |
| **`ChatClient`** | **prompt 조립 → 실행 → 응답 소비** |

**§6의 경계도 함께**: **결정적 정답이 있는 일에 LLM을 끼우지 않는다** — **세금 계산, 재고 차감, 권한 판정은 확률적 생성이 아니라 코드가** 해야 하고, **model은 그 결과를 말로 옮기는 자리**에 둔다.
