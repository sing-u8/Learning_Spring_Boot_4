## Q1. `public` 필드가 `0`으로 읽히는 과정 — 두 객체 그림으로

**값이 들어 있는 객체와 내가 읽고 있는 객체가 다르다.**

```text
        [프록시]                          [타깃 객체]
CatalogPolicy$$SpringCGLIB$$0          CatalogPolicy
┌──────────────────────────────┐      ┌──────────────────────────┐
│ maxSubstancesPerMaterial = 0 │      │ maxSubstancesPerMaterial │
│   ↑ 상속받아 존재하지만       │      │              = 40        │
│     아무도 값을 안 넣었다     │      │   ↑ 생성자가 채웠다      │
│                              │      │                          │
│ private Object target; ──────┼─────▶│                          │
│                              │      │                          │
│ enforce() { target.enforce() }│     │ enforce() { ... }        │
└──────────────────────────────┘      └──────────────────────────┘
        ↑
   주입된 것은 이쪽이다
   policy.maxSubstancesPerMaterial → 0
```

**두 가지가 겹쳤다**:

**① 필드 읽기는 위임할 수 없다** — **프록시는 메서드 호출을 타깃에 위임하지만**, `policy.maxSubstancesPerMaterial`은 **메서드 호출이 아니라 필드 접근**이다. **JVM은 이것을 프록시 인스턴스 자신의 필드에서 곧장 읽는다. 가로챌 지점이 없다.**

**② **생성자 우회**** — CGLIB 프록시 인스턴스는 **Objenesis를 통해 만들어져 프록시된 객체의 생성자가 두 번 호출되지 않는다.** 생성자를 아예 부르지 않으므로 `this.maxSubstancesPerMaterial = max` 줄이 **프록시 인스턴스에서는 실행되지 않고**, `int` 필드는 **JVM 기본값 `0`으로 남는다.**

**중요한 단서 — 정확히는 JVM에 달렸다**: 공식 문서가 **JVM이 생성자 우회를 허용하지 않으면 생성자가 두 번 불릴 수 있다**고 적는다. 그런 환경에서는 **프록시 필드에도 `40`이 들어가 이 증상이 재현되지 않는다.**

> **즉 값이 `0`이냐 `40`이냐가 환경에 따라 갈린다는 것 자체가 문제다 — 어느 쪽이든 필드를 프록시 너머로 읽는 코드는 신뢰할 수 없다.**

**비유와 그 한계 — 콜센터 대표번호**: 대표번호로 전화하면 담당자에게 연결된다(메서드 위임). 그런데 **명함 뒷면에 담당자 개인 메모를 기대할 수는 없다** — 명함은 연결 수단일 뿐이다(필드).

→ **깨지는 지점**: 명함에는 **애초에 메모 칸이 없다.** CGLIB 프록시에는 **필드가 물리적으로 존재한다** — 상속했으니까. **존재하는데 비어 있다는 점이 더 나쁘다.** 컴파일도 되고 접근도 되고 예외도 안 난다. **그냥 `0`이 나올 뿐이다.**

**§6**: **상태를 `public` 필드로 노출하지 않는다.** **getter로 노출하면 위임된다.**

## Q2. CGLIB가 생성자를 우회하는 이유

**우회하지 않으면 생성자가 두 번 실행되기 때문이다.**

```text
프록시는 대상 클래스의 하위 클래스다
  → 하위 클래스 인스턴스를 만들면 Java 규칙상 부모 생성자가 먼저 돈다
  → 그런데 타깃 객체는 이미 따로 만들어져 있다 (생성자가 이미 한 번 돌았다)
  → 우회하지 않으면 같은 생성자가 두 번 실행된다
```

**두 번 실행되면 무엇이 문제인가**:

| 생성자에 있는 것 | 두 번 돌면 |
|---|---|
| **부수 효과** (등록, 카운터 증가, 로깅) | **두 번 일어난다** |
| **무거운 초기화** (연결, 파일 읽기) | **두 배 비용** |
| **검증 예외** | 두 번째에서 다르게 터질 수 있다 |

**그래서 Objenesis로 생성자 없이 인스턴스를 만든다** — 공식 문서: *"CGLIB 프록시 인스턴스는 Objenesis를 통해 만들어져 **프록시된 객체의 생성자가 두 번 호출되지 않는다.**"*

**대가가 Q1의 증상이다** — 생성자를 안 부르므로 **프록시의 필드는 전부 기본값**(`0`, `null`, `false`)이다.

**즉 교환이다**:

```text
[생성자를 부른다]     필드는 채워진다 · 부수 효과가 두 번 일어난다
[생성자를 우회한다]   부수 효과는 한 번 · 필드가 비어 있다  ← Spring 의 선택
```

**Spring이 후자를 고른 이유** — **필드를 프록시 너머로 읽는 것은 애초에 하지 말아야 할 일**이지만, **부수 효과가 두 번 일어나는 것은 우회할 방법이 없다.** 더 위험한 쪽을 막은 것이다.

## Q3. 공식 문서의 CGLIB 제약 네 가지를 한 문장으로 유도하기

**한 문장**:

> **CGLIB 프록시는 대상 클래스를 상속해 메서드를 오버라이드한 하위 클래스다.**

| 공식 문서의 제약 | 유도 |
|---|---|
| **`final` 클래스는 프록시할 수 없다** | **확장(상속)할 수 없기 때문** |
| **`final` 메서드는 어드바이스할 수 없다** | **오버라이드할 수 없기 때문** |
| **`private` 메서드는 어드바이스할 수 없다** | **오버라이드할 수 없기 때문** |
| **보이지 않는 메서드**(다른 패키지 부모의 패키지 전용) | **사실상 private이라 오버라이드할 수 없기 때문** |
| 생성자가 두 번 호출되지 않는다(Objenesis) | **하위 클래스 인스턴스를 만들면 부모 생성자가 돌기 때문에 우회**(Q2) |
| Java 모듈 시스템에서 제약이 있을 수 있다 | 런타임 클래스 생성이 모듈 캡슐화와 충돌 |

**한 문장에서 더 나오는 것들**:

- **오버라이드는 메서드에만 가능** → **필드 접근은 가로채기 불가**(Q1)
- **하위 클래스 인스턴스는 별개의 객체** → **필드가 비어 있음**(Q1)
- **타깃 안으로 들어간 뒤의 호출은 프록시 밖** → ****자기 호출****

> **한계 목록을 외우는 대신, 프록시가 무엇으로 만들어지는지를 한 문장으로 붙들면 모든 사례가 유도된다.**

**네 번째 항목이 특히 조용하다** — **다른 패키지에 있는 부모 클래스의 패키지 전용 메서드는 문법상 `private`이 아닌데도 하위 클래스에서 오버라이드할 수 없다.** **코드만 봐서는 왜 어드바이스가 안 붙는지 알 수 없다.**

## Q4. `private` 메서드의 `@Transactional`에 경고가 없는 이유 — 판정 단계로

**어느 단계에서도 "잘못됐다"고 판단할 근거가 없기 때문이다.**

```text
1. 컴파일러는 통과시킨다
     — 애노테이션은 메타데이터일 뿐이고, 컴파일러는 그것이 런타임에 어떻게 쓰일지 모른다

2. 자동 프록시 생성기가 포인트컷을 평가한다
     — 대상 판정을 해야 한다

3. 트랜잭션 포인트컷은 오버라이드 가능한 메서드만 후보로 본다
     — 오버라이드할 수 없는 메서드에 어드바이스를 붙일 방법이 애초에 없다

4. 그 메서드는 매칭 목록에서 빠진다
     — 매칭시켜 봐야 실행할 수 없다

5. 다른 메서드가 매칭되면 프록시는 만들어진다
     — 클래스 전체가 아니라 메서드 단위로 판정한다

6. doWork() 호출은 어드바이스 없이 곧장 실행된다
     — 프록시가 그 메서드를 오버라이드하지 않았으므로 가로챌 코드가 없다
```

> **각 단계는 자기 규칙에 맞게 동작했을 뿐이다. 그래서 경고가 나오지 않는다.**

**§5의 정확한 표현**:

> **`@Transactional`이 실패하는 것이 아니다. 애초에 그 메서드는 어드바이스 후보 목록에 오르지 않는다.** 실행 시점에 **트랜잭션 관련 코드가 한 줄도 개입하지 않는다.**

**"안 되는" 게 아니라 "없는" 것이다.**

> **실패가 아니라 아무 일도 일어나지 않음으로 나타난다.**

**이것이 이 함정이 위험한 이유다** — 실패는 로그를 남기지만 **부재는 아무것도 남기지 않는다.**

**§6**: **`private` 메서드에 AOP 애노테이션을 붙이지 않는다.** **조용히 무시된다. IDE 경고도 대부분 없다.**

## Q5. 자기 호출이 Spring의 결함이 아니라 Java의 규칙인 이유

**Java에서 `this.bar()`는 자기 자신의 메서드를 부르는 것이고, 그 호출 경로에 프록시가 낄 자리가 문법적으로 없다.**

공식 문서: *"호출이 마침내 타깃 객체에 도달하고 나면, 그 객체가 자기 자신에게 하는 `this.bar()`나 `this.foo()` 같은 메서드 호출은 **프록시가 아니라 `this` 참조에 대해 실행된다.** (…) **자기 호출은 그 메서드 호출에 연결된 어드바이스가 실행될 기회를 얻지 못한다는 뜻이다.**"*

```text
프록시는 외부에서 이 객체를 가리키는 참조일 뿐이다
객체 자신은 자기를 감싼 프록시의 존재를 모른다
  → this 는 언제나 자기 자신이다
  → Java 가 그렇게 정의했다
```

**Spring이 이 규칙을 바꿀 수 있는가 — 없다.** `this`의 의미는 **언어 명세**다. 프레임워크가 개입할 층이 아니다.

**공식 문서의 권장 해법도 이 인식과 일치한다**:

> *"가장 좋은 접근은(여기서 '좋은'은 느슨하게 쓴 표현이다) **자기 호출이 일어나지 않도록 코드를 리팩터링하는 것**이다."*

**프레임워크 기능으로 우회하는 것이 아니라 호출 구조 자체를 바꾸라는 말이다.**

**`AopContext.currentProxy()`에 대한 평가는 냉정하다** — 이 방식은 *"코드를 **Spring AOP에 완전히 결합시키고**, 클래스 자신이 AOP 컨텍스트에서 사용되고 있다는 사실을 알게 만들어 **AOP의 이점 일부를 없앤다**."* `exposeProxy` 설정도 따로 켜야 한다.

**§6**: **`AopContext.currentProxy()`를 쓰지 않는다.**

**그래서 이 문제는 "프록시 방식을 선택한 대가"이지 AOP 자체의 한계가 아니다**(Q9).

## Q6. `this.`를 생략하면 다른가

**같다. 컴파일러가 `this.`를 채워 넣을 뿐이다.**

| 호출 형태 | 프록시를 지나는가 | 어드바이스 |
|---|---|---|
| 다른 빈이 주입받아 호출 | **지난다** | 동작 |
| 컨트롤러 → 서비스 | **지난다** | 동작 |
| 같은 클래스 안 `this.method()` | 안 지난다 | 무효 |
| **같은 클래스 안 `method()` (this 생략)** | **안 지난다** | **무효 — `this.`가 생략됐을 뿐 같다** |
| `@PostConstruct` 안에서 자기 메서드 | 안 지난다 | 무효 — **게다가 프록시가 아직 없다** |
| 람다·익명 클래스 안에서 자기 메서드 | 안 지난다 | 무효 |
| 필드 직접 접근 | **가로챌 수 없다** | 해당 없음 |

**네 번째 행이 실무에서 가장 많이 놓친다** — **`this.`를 안 썼다고 다른 호출이 되는 것이 아니다.**

**왜 헷갈리는가** — `this.`가 없으면 **"어디선가 온 호출"처럼 보인다.** 특히 메서드가 길거나 클래스가 크면 **같은 클래스의 메서드인지 눈에 안 들어온다.**

**§6**: **`this.` 생략이 다른 호출이라고 기대하지 않는다. 컴파일러가 채워 넣을 뿐 동일하다.**

**다섯 번째와 여섯 번째도 같은 이유다**:

- **`@PostConstruct`** — 자기 호출인 데다 c1-03에서 본 대로 **그 시점에는 프록시가 아직 존재하지도 않는다.** 두 겹으로 안 된다.
- **람다·익명 클래스** — 그 안의 `method()`는 **바깥 클래스의 `this.method()`**로 컴파일된다. 역시 자기 호출이다.

## Q7. CGLIB로 바꿔서 해결되는 문제와 안 되는 문제

| 문제 | JDK → CGLIB 전환으로 해결되나 |
|---|---|
| 인터페이스에 없는 메서드 호출 | **된다** |
| 구현체로 캐스팅 실패 | **된다** |
| **자기 호출** | **안 된다** |
| **`final` 메서드** | **안 된다 (CGLIB에서 오히려 새로 생기는 제약)** |
| **필드 접근** | **안 된다** |

**축이 다르기 때문이다**:

```text
프록시 타입   : 프록시가 "어떻게 생겼는가"
자기 호출     : 호출이 "프록시를 거치는가"
필드 접근     : 애초에 "가로챌 수 있는 지점인가"
```

**앞의 둘은 프록시 타입 문제이고, 뒤의 셋은 그보다 근본적인 층이다.**

**네 번째 줄이 아이러니다** — **CGLIB로 바꾸면 `final` 관련 제약이 새로 생긴다.** JDK 프록시는 대상 클래스를 상속하지 않으므로 `final`과 무관했다. **문제를 해결하려다 다른 문제를 얻는 경로다.**

**§5**: **`@Transactional`이 안 먹을 때 프록시 타입부터 바꿔 보는 것이 대개 헛수고인 이유다.**

**올바른 진단 순서**([[02-advisor-pointcut-and-auto-proxy-creation]] Q7):

```text
1. 프록시이기는 한가?        AopUtils.isAopProxy()
2. 그 메서드가 후보인가?     private / final 확인
3. 호출이 프록시를 지나는가? this. 또는 같은 클래스 내부 호출 확인
   ─────────────────────────────────────────
4. (그제서야) 프록시 타입
```

## Q8. Kotlin이 특히 자주 걸리는 이유와 해결책

**Kotlin은 클래스와 메서드가 기본 `final`이다.**

```text
Java   : 기본 open (오버라이드 가능). final 을 의식적으로 붙여야 한다
Kotlin : 기본 final. open 을 의식적으로 붙여야 한다
```

**그래서 아무 생각 없이 쓴 Kotlin `@Service` 클래스는 CGLIB가 상속할 수 없어 프록시가 만들어지지 않는다.**

**평범하게 작성한 코드가 전부 걸린다는 점이 특징이다** — Java에서는 `final`을 **일부러 붙인 클래스**만 문제인데, Kotlin에서는 **아무것도 안 붙인 모든 클래스**가 문제다.

**해결책 — `kotlin-spring` 컴파일러 플러그인**:

> **`@Component`·`@Transactional` 등이 붙은 클래스를 자동으로 `open`으로 바꿔 준다.**

**Spring Initializr가 Kotlin 프로젝트에 이 플러그인을 기본 포함시키는 이유가 이것이다.**

> **플러그인을 빼면 조용히 트랜잭션이 사라진다.**

**§6**: **Kotlin에서는 `kotlin-spring` 플러그인 유무를 확인한다.**

**진단 포인트**: Kotlin 프로젝트에서 `@Transactional`이 안 먹으면 **빌드 파일의 `plugin("kotlin-spring")` 또는 `allOpen` 설정을 먼저 본다.** 코드를 아무리 봐도 답이 없다 — **문제가 빌드 설정에 있기 때문이다.**

**대안** — 클래스마다 `open`을 직접 붙일 수도 있지만, **빠뜨리면 조용히 실패**하므로 플러그인이 훨씬 안전하다.

## Q9. AspectJ 위빙에 자기 호출 문제가 없는 이유 — 그럼에도 클래스 분리를 택하는 이유

**없는 이유 — 프록시가 아니라 바이트코드 안에 어드바이스를 직접 넣기 때문이다.**

```text
[Spring AOP — 프록시]
  원본 클래스는 그대로. 밖에서 감싼다
  → this.method() 는 원본 안에서 원본을 부른다
  → 어드바이스가 없다

[AspectJ — 위빙]
  원본 클래스의 바이트코드가 바뀐다
  → method() 안에 어드바이스 코드가 삽입돼 있다
  → this.method() 든 뭐든 그 코드를 지난다 ✅
```

**공식 문서가 언급한다** — **AspectJ의 컴파일 시점·로드 시점 위빙에는 이 자기 호출 문제가 없다.**

**그리고 자기 호출만이 아니다** — [[02-advisor-pointcut-and-auto-proxy-creation]] Q8의 세 제약(필드·생성자·`static`)과 이 노트의 `final`·`private` 제약이 **전부 없어진다.** 코드 자체를 고치니까.

**그럼에도 대개 클래스 분리를 택하는 이유**:

| 이유 | 내용 |
|---|---|
| **빌드·실행 설정이 무겁다** | 컴파일 시점 위빙은 **AspectJ 컴파일러**가, 로드 시점 위빙은 **자바 에이전트**가 필요하다 |
| **디버깅이 어려워진다** | 소스와 실행되는 바이트코드가 다르다 |
| **클래스 분리가 대개 더 싸다** | 클래스 하나 추가로 끝난다 |
| **분리는 설계 개선이기도 하다** | c1-03·j3-03에서 본 대로 **"트랜잭션 경계가 다르면 다른 책임"** |

**§6**: **자기 호출이 반복적으로 문제가 되면 프록시 방식 자체를 재검토한다.** AspectJ 위빙에는 이 문제가 없지만 **빌드·실행 설정이 무거워진다. 대개는 클래스 분리가 더 싸다.**

**"반복적으로"가 조건이다** — 한두 번이면 분리로 충분하다. **프로젝트 전반에서 계속 부딪히면** 그때 도구를 바꿀 근거가 생긴다.

## Q10. "인터페이스를 뒀으니 `final`이 안전하다"가 위험한 가정인 이유

**Spring Boot 기본이 CGLIB이기 때문이다.**

```text
[순수 Framework + 인터페이스 있음]
  → JDK 프록시
  → 대상 클래스를 상속하지 않는다
  → final 메서드도 문제없다. 인터페이스에 선언돼 있기만 하면 프록시가 갖는다 ✅

[Spring Boot 기본]
  → CGLIB (인터페이스가 있어도)
  → 대상 클래스를 상속한다
  → final 메서드는 오버라이드 불가 → 어드바이스 없음 ❌
```

**§5**:

> **"인터페이스를 뒀으니 괜찮다"는 가정은 설정에 의존한다.**

**왜 특히 위험한가 — 세 겹이다**:

1. **가정이 참인 환경이 실제로 있다** — 순수 Framework에서는 맞다. 그래서 **어디선가 배운 것이 틀린 게 아니다.**
2. **설정 한 줄로 뒤집힌다** — `spring.aop.proxy-target-class`를 누가 바꾸면 조용히 깨진다.
3. **실패가 조용하다** — Q4대로 **경고가 없다.**

**같은 종류의 위험한 가정들**:

| 가정 | 왜 위험한가 |
|---|---|
| "인터페이스가 있으면 JDK 프록시" | **Boot에서 틀리다**([[01-jdk-dynamic-proxy-vs-cglib]] Q4) |
| "인터페이스를 뒀으니 `final`이 안전" | 같은 이유 |
| "프록시니까 캐스팅되겠지" | 프록시 타입에 따라 갈린다 |

**전부 "프록시 타입이 무엇인가"에 의존하는 가정**이고, **그건 설정이다.**

**§6의 규칙이 이 셋을 한 번에 막는다**: **프록시 대상 클래스에 `final`을 붙이지 않는다.** 설정이 무엇이든 안전하다.

**일반화하면** — **프록시 타입에 의존하는 코드를 쓰지 않는다.** 어느 쪽에서도 동작하는 코드를 쓰면 **설정 변경이 코드를 깨뜨리지 않는다.**
