## Q1. 같은 컨테이너의 두 `@Service` 중 하나만 프록시인 이유

**Spring은 모든 빈을 감싸지 않는다. 감쌀 이유가 있는 빈만 감싼다.**

공식 문서의 판정 규칙:

> *"`DefaultAdvisorAutoProxyCreator`는 각 어드바이저에 담긴 포인트컷을 자동으로 평가해 각 비즈니스 객체에 어떤 어드바이스를 적용해야 하는지 확인한다. (…) **어떤 어드바이저의 어떤 포인트컷도 비즈니스 객체의 어떤 메서드와도 매칭되지 않으면 그 객체는 프록시되지 않는다.**"*

```text
MaterialService  → @Transactional 이 있다
                 → 트랜잭션 어드바이저의 포인트컷이 매칭된다
                 → 프록시가 만들어진다 ✅

AuditLogger      → 어떤 메서드도 등록된 포인트컷과 매칭되지 않는다
                 → 원본이 그대로 등록된다 ❌
```

**"Spring이 모든 빈을 프록시로 감싼다"고 알고 있으면 이 결과를 설명할 수 없다.** 그러면 `AuditLogger`에 `@Transactional`을 붙였는데 안 먹는 상황에서 **엉뚱한 곳을 뒤지게 된다.**

**비유와 그 한계 — 공항 보안 검색의 정밀 검사 대상 선별**: 모두가 기본 검색은 거치지만, **정밀 검사는 특정 조건에 걸린 사람만** 받는다. 조건에 안 걸린 사람은 **정밀 검사대 자체를 지나가지 않는다.**

→ **깨지는 지점**: 공항은 사람을 통과시킨 뒤 **필요하면 다시 부를 수 있다.** 컨테이너는 못 한다 — **판정은 빈이 만들어지는 그 한 번뿐**이고, 그때 프록시가 아니면 **애플리케이션이 살아 있는 내내 프록시가 아니다.** 나중에 조건이 바뀌어도 **소급되지 않는다.**

## Q2. 매칭되는 포인트컷이 없을 때 프록시를 안 만드는 것이 최적화인 이유

**감싸는 데 실제 비용이 들고, 어드바이스가 없으면 그 비용이 순수한 손해이기 때문이다.**

**프록시 하나가 지불하는 비용**:

| 비용 | 내용 |
|---|---|
| **호출마다** | **인터셉터 체인을 거친다** — 어드바이스가 0개여도 체인 진입·위임은 일어난다 |
| **스택 트레이스** | **길어진다** — `$$SpringCGLIB$$` 프레임이 낀다. 디버깅이 어려워진다 |
| **메모리** | 클래스 하나 + 인스턴스 하나가 더 생긴다 |
| **시작 시간** | 바이트코드 생성·클래스 로딩 |

> **필요 없는 빈까지 감싸는 것은 순수한 손해다.**

**"순수한"이 정확한 표현이다** — 어드바이스가 있으면 그 비용은 **기능의 대가**다. 어드바이스가 없으면 **대가만 있고 기능이 없다.**

**규모를 생각하면 더 분명하다** — Boot 애플리케이션의 빈은 수백~수천 개인데, 그중 AOP가 필요한 것은 대개 **서비스 계층 일부**다. **전부 감싸면 대부분이 낭비**가 된다.

**§6의 관련 경계**: **포인트컷을 너무 넓게 잡지 않는다.** `execution(* com.cosmoroute..*.*(..))` 같은 표현은 **거의 모든 빈을 프록시로 만든다.** 시작 시간·메모리·스택 깊이가 전부 늘고 **디버깅이 어려워진다.**

## Q3. 자동 프록시 생성기에 어드바이스가 아니라 어드바이저를 등록해야 하는 이유

**포인트컷이 없으면 "누구에게 적용할지"를 판정할 수 없기 때문이다.**

공식 문서가 직접 설명한다 — 등록하는 것은 인터셉터나 순수 어드바이스가 아니라 **반드시 어드바이저여야 한다**:

> *"**평가할 포인트컷이 있어야** 후보 빈 정의에 대해 각 어드바이스의 적용 가능 여부를 검사할 수 있기 때문이다."*

**풀어 쓰면**:

```text
어드바이스만 있다면
  "무엇을 할지"는 안다 (트랜잭션을 연다)
  "누구에게 할지"는 모른다
  → 컨테이너는 빈 수천 개를 훑으며 판정해야 하는데
  → 판정 기준이 없으면 전부 감싸거나 하나도 안 감싸는 수밖에 없다

포인트컷이 그 기준이다
```

**설계 원리로 말하면 — "무엇을 할지"와 "어디에 할지"를 분리해서 각각 독립적으로 정의하고, 둘을 짝지어 등록한다.**

**분리의 이득**: 같은 어드바이스를 **다른 포인트컷과 짝지어** 재사용할 수 있고, 같은 포인트컷 표현식을 **여러 어드바이스가 공유**할 수 있다.

**다섯 용어가 한 문장이다**(§2.1):

> ****위빙** 시점에, **포인트컷**에 매칭되는 **조인 포인트**에서, **어드바이스**를 **타깃 객체** 대신 실행한다.**

| 용어 | `@Transactional`에서는 |
|---|---|
| **조인 포인트** | `MaterialService.findAll()` 호출 |
| **포인트컷** | "`@Transactional`이 붙은 메서드" |
| **어드바이스** | 트랜잭션 시작·커밋·롤백 코드 |
| **어드바이저** | **위 둘의 짝** |
| **타깃 객체** | `MaterialService` 인스턴스 |

## Q4. 포인트컷 평가가 메서드 단위인 것이 왜 중요한가

**"이 클래스의 이 메서드에만 트랜잭션"이 가능해지기 때문이다.**

**판정과 생성의 7단계 중 4번**:

> **각 어드바이저의 포인트컷을 이 빈의 메서드 하나하나에 평가한다** — **클래스 단위가 아니라 메서드 단위로 매칭되어야 "어떤 메서드에만 트랜잭션"이 가능하기 때문이다.**

```text
class MaterialService {
    @Transactional void save()    ← 매칭 ✅ 어드바이스를 거친다
    List<Material> findAll()      ← 매칭 ❌ 곧장 타깃으로 위임
    void reindex()                ← 매칭 ❌
    ... 나머지 7개                 ← 매칭 ❌
}

→ 프록시는 만들어진다 (하나라도 매칭됐으니까)
→ 나머지 아홉 개는 어드바이스 없이 곧장 타깃으로 위임된다
```

**두 판정이 층이 다르다는 점이 핵심이다**:

| 판정 | 단위 | 결과 |
|---|---|---|
| **프록시를 만들까?** | **클래스** — 하나라도 매칭되면 만든다 | 프록시 존재 여부 |
| **어드바이스를 걸까?** | **메서드** — 매칭된 것만 | 인터셉터 체인 구성 |

**메서드 단위가 아니었다면** — `@Transactional`을 하나만 붙여도 **클래스의 모든 메서드가 트랜잭션 안에서 돌게** 된다. 조회 메서드까지 쓰기 트랜잭션에 들어가고, `readOnly` 구분도 불가능해진다.

**진단에도 쓰인다**(§5) — **"프록시인데 그 메서드만 안 걸림"**이라는 상태가 존재하는 이유가 이 메서드 단위 평가다. `getClass()`에 `$$SpringCGLIB$$`가 보이는데 그 메서드만 안 도는 것이라면, **그 메서드가 포인트컷에 안 맞은 것**이다 — `private`·`final` 여부를 확인한다.

## Q5. `@Transactional`만 붙이고 아무것도 등록 안 해도 동작하는 이유

**Boot가 트랜잭션 어드바이저를 자동 구성으로 등록해 두었고, 포인트컷 기반 판정이 나머지를 알아서 하기 때문이다.**

**두 종류의 자동 프록시 생성기**:

| | `BeanNameAutoProxyCreator` | `DefaultAdvisorAutoProxyCreator` |
|---|---|---|
| 판정 기준 | **빈 이름**(리터럴·와일드카드) | **포인트컷 평가** |
| 설정 | 이름 목록을 **직접 나열** | **나열 불필요** |
| 문서의 평가 | 최소한의 설정으로 여러 객체에 같은 구성 | *"더 일반적이고 극도로 강력한"* |
| **새 빈이 추가되면** | **이름을 추가해야 함** | **자동으로 판정됨** |

공식 문서: *"현재 컨텍스트의 적격 어드바이저를 **자동 프록시 어드바이저의 빈 정의에 특정 빈 이름을 포함시킬 필요 없이** 자동으로 적용한다"*, 그리고 **새 비즈니스 객체의 빈 정의가 추가되면 필요에 따라 자동으로 프록시된다.**

**그래서 내가 할 일은 애노테이션 하나뿐이다**:

```text
@Transactional 을 붙인다
  → Boot 자동 구성이 등록해 둔 트랜잭션 어드바이저의 포인트컷이 매칭한다
  → 자동 프록시 생성기가 알아서 프록시를 만든다
  → 아무것도 등록하지 않았는데 동작한다
```

**중요한 단서**(§2.4): **실제 프로젝트에서 `DefaultAdvisorAutoProxyCreator`라는 이름을 찾으면 안 나온다.**

**공식 문서가 판정 규칙을 설명하며 드는 예가 이 클래스일 뿐**, Boot 애플리케이션에 실제로 등록되는 것은 같은 계열의 다른 구현이다:

- `@EnableAspectJAutoProxy` 경로 → **`AnnotationAwareAspectJAutoProxyCreator`**
- 트랜잭션 경로 → **`InfrastructureAdvisorAutoProxyCreator`**

**전부 같은 추상 클래스(`AbstractAutoProxyCreator`)를 공유하므로 "어드바이저의 포인트컷을 평가해, 매칭이 하나도 없으면 원본을 그대로 반환한다"는 규칙은 동일하다.**

## Q6. `@Aspect` 하나와 어드바이저의 개수 관계

**`@Aspect` 하나가 어드바이저 여러 개로 분해된다.**

| 축 | **애스펙트(`@Aspect`)** | **어드바이저(`Advisor`)** |
|---|---|---|
| 층 | **개발자가 쓰는 표현** | **프레임워크 내부 단위** |
| 담는 것 | **여러 개의** 어드바이스 + 포인트컷 | **정확히 하나씩** |
| 관계 | 어드바이저 여러 개로 **분해된다** | 분해의 **결과물** |

```java
@Aspect
class LoggingAspect {
    @Before("...")      void a() {}   ┐
    @After("...")       void b() {}   ├─→ 어드바이저 3개
    @AfterThrowing("…") void c() {}   ┘
}
```

**`@Aspect` 클래스에 `@Before`·`@After`를 세 개 쓰면 내부적으로 어드바이저 세 개가 된다.**

> **자동 프록시 생성기가 평가하는 단위는 어드바이저다.**

**왜 분해하는가** — 판정이 **"어드바이스 하나 + 포인트컷 하나"** 단위로 이루어져야 하기 때문이다(Q3). 애스펙트 하나에 서로 다른 포인트컷의 어드바이스가 섞여 있으면 **통째로 판정할 수 없다.**

**실무 함의**: 애스펙트를 만들 때 **"이 클래스에 어드바이스를 몇 개 넣을까"는 조직화의 문제**이지 성능이나 판정에 영향을 주지 않는다. **어차피 분해된다.**

**§6**: **`@Aspect` 클래스 자신은 어드바이스 대상이 아니다.** **자기가 자기를 감쌀 수 없고**, 감싸려 해도 c1의 **특수 시작 단계** 문제에 걸린다.

## Q7. "프록시가 아니다"와 "프록시인데 안 지나간다"를 구별하는 법

**`getClass()`를 먼저 찍고, 그다음 호출 경로를 본다.**

| 상태 | `getClass()` | 원인 | 해결 |
|---|---|---|---|
| **프록시 아님** | **원본 클래스명** | 매칭되는 포인트컷 0개 | **애노테이션 확인** |
| **프록시인데 그 메서드만 안 걸림** | `$$SpringCGLIB$$` | 그 메서드가 **포인트컷에 안 맞음** | **`private`·`final` 여부 확인** |
| **프록시인데 안 지나감** | `$$SpringCGLIB$$` | **자기 호출** | **구조 변경** |

**진단 순서**:

```text
1. getClass() 를 찍는다 (또는 AopUtils.isAopProxy)
     원본 클래스명  → 첫 번째 줄. 애노테이션이 정말 붙어 있는지, 스캔되는지
     $$SpringCGLIB$$ → 다음으로

2. 그 메서드의 접근자를 본다
     private / final → 두 번째 줄

3. 호출 경로를 본다
     this.method() 또는 같은 클래스 안에서 부름 → 세 번째 줄
```

**세 번째가 가장 헷갈린다**:

> **프록시도 있고 어드바이스도 걸렸는데 호출이 그 길로 안 간다.**

**증상이 셋 다 똑같기 때문이다** — "`@Transactional`이 안 먹는다". 그런데 **원인도 해결책도 전부 다르다.** 그래서 **증상에서 바로 해결로 뛰지 말고 위 순서를 밟아야** 한다.

**스택 트레이스도 단서다**(c2-01 Q9) — **`$$SpringCGLIB$$` 프레임이 보이면 프록시를 지나고 있다**는 증거이고, **없으면 안 지났다.**

**세 번째 줄이 [[03-why-final-private-and-self-invocation-break]]의 주제다.**

## Q8. Spring AOP로 할 수 없는 세 가지 가로채기

**공식 문서가 못박는다** — *"Spring AOP에서 **조인 포인트는 항상 메서드 실행**을 나타낸다."*

**그래서 불가능한 것**:

| 불가능한 것 | 왜 |
|---|---|
| **필드 읽기·쓰기 가로채기** | 필드 접근은 메서드 호출이 아니다. 프록시가 개입할 지점이 없다 |
| **생성자 호출 가로채기** | 프록시는 **이미 만들어진 객체를 감싼다.** 생성 자체는 프록시 이전이다 |
| **`static` 메서드 가로채기** | 인스턴스에 묶이지 않는다. **프록시 인스턴스를 거칠 방법이 없다** |

**이유는 프록시의 어떤 성질 때문인가 — "타깃 객체를 필드로 들고 호출을 위임한다"는 성질이다**(c2-01 Q8).

```text
프록시가 개입할 수 있는 것 = 프록시를 거쳐 들어오는 호출
                            ↑ 인스턴스 메서드 호출뿐이다

필드 접근   → 참조로 직접 간다. 프록시를 안 거친다
생성자      → 프록시가 존재하기 전이다
static      → 클래스에 직접 간다. 인스턴스가 개입하지 않는다
```

**§6**: **필드·생성자·`static`에 개입해야 한다면 Spring AOP가 도구가 아니다. 조인 포인트 범위 밖이다.**

**답은 AspectJ 위빙이다** — **바이트코드를 직접 고치므로** 프록시의 제약을 받지 않는다. 대신 **빌드 설정이 무거워진다**([[03-why-final-private-and-self-invocation-break]] Q9).

**같은 뿌리에서 나오는 제약이 하나 더 있다** — **`private` 메서드**도 프록시로는 못 잡는다. 오버라이드할 수 없기 때문이다.

## Q9. 인터셉터 체인이 양파처럼 겹친다는 말

**한 메서드에 어드바이스가 여럿 붙으면 겹겹이 감싸이고, 호출은 바깥에서 안으로 들어갔다가 다시 나온다.**

공식 문서의 구현 힌트: Spring을 포함한 많은 AOP 프레임워크가 어드바이스를 **인터셉터로 모델링하고 조인 포인트 주위에 인터셉터 체인을 유지한다.**

```text
호출 → [트랜잭션 어드바이스]
          [캐시 어드바이스]
             [로깅 어드바이스]
                [타깃 메서드]        ← 실제 로직
             [로깅 어드바이스 뒷부분]
          [캐시 어드바이스 뒷부분]
       [트랜잭션 어드바이스 뒷부분]  → 반환
```

**순서가 뜻하는 바 — 바깥일수록 먼저 시작하고 나중에 끝난다.**

**그래서 순서가 의미를 바꾼다**:

| 순서 | 결과 |
|---|---|
| **트랜잭션이 캐시보다 바깥** | 캐시 조회도 트랜잭션 안에서 일어난다 |
| **캐시가 트랜잭션보다 바깥** | **캐시 적중 시 트랜잭션이 아예 안 열린다** |

**두 번째가 대개 원하는 동작이다** — 캐시에 있으면 DB에 갈 이유가 없으니 트랜잭션도 필요 없다. **순서 하나가 커넥션 사용량을 바꾼다.**

**§6의 경고**: **어드바이스 순서에 의존하는 설계를 피한다.** `@Order`로 정할 수는 있지만, **순서가 결과를 바꾸는 구조는 나중에 어드바이스가 하나 추가되면 깨진다.**

**"양파"라는 비유가 정확한 이유** — 양파는 **껍질을 벗기는 순서가 정해져 있고**, 안쪽에 닿으려면 **바깥을 전부 지나야** 한다. 어드바이스도 그렇다. **중간을 건너뛸 수 없다.**

## Q10. 위빙을 직조에 비유할 때 깨지는 지점

**Spring AOP에서는 프록시를 벗기면 원본이 그대로 나온다. 진짜로 엮이지 않았다.**

**이름의 유래**(§2.5):

- ****조인 포인트**** — "애스펙트와 원래 코드가 **합류(join)**하는 지점". 두 흐름이 만나는 자리
- ****포인트컷**** — "지점들을 **잘라 낸(cut)** 것". 모든 조인 포인트 중 관심 있는 부분집합
- ****위빙**** — **직조, 실을 엮는 일.** 애스펙트라는 씨실을 원래 코드라는 날실에 끼워 하나의 천을 만든다는 은유
- ****어드바이스**** — "조언"이 아니라 **법률·의료의 "처방·지시"**에 가깝다

→ **직조 비유가 깨지는 지점**:

> **실제 직조는 천이 완성되면 씨실과 날실을 분리할 수 없다. Spring AOP의 런타임 위빙은 그렇지 않다 — 프록시를 벗기면 원본 객체가 그대로 나온다(`AopProxyUtils.ultimateTargetClass`).**

```text
[진짜 위빙 — AspectJ]
  바이트코드 자체가 바뀐다
  → 원본 클래스 파일에 어드바이스 코드가 삽입된다
  → 분리할 수 없다. 한 몸이다

[Spring AOP — 덧씌우기]
  프록시가 원본을 감싼다
  → 원본은 손상 없이 그대로 있다
  → AopProxyUtils.ultimateTargetClass() 로 꺼낼 수 있다
```

> **진짜로 엮여 한 몸이 되는 것은 AspectJ의 바이트코드 위빙이고, Spring의 것은 "덧씌우기"에 가깝다.**

**이 차이가 이 챕터 전체의 제약을 설명한다**:

| 덧씌우기라서 | 결과 |
|---|---|
| 원본이 별도로 존재한다 | **자기 호출** 문제 |
| 밖에서만 감싼다 | **`private`·`final`** 제약 |
| 메서드 호출만 가로챈다 | **필드·생성자·`static`** 불가(Q8) |

**AspectJ에는 이 셋이 전부 없다** — 코드 자체를 고치니까. **대신 빌드 시점 위빙이나 로드타임 위빙 설정이 필요하고, 그 무게 때문에 대부분의 프로젝트가 Spring AOP를 쓴다.**
