## Q1. `ClassCastException: $Proxy142 cannot be cast to ...Impl`의 이유 — 타입 관계로

**`$Proxy142`와 `MaterialServiceImpl`은 형제이지 상속 관계가 아니기 때문이다.**

```text
              MaterialService (인터페이스)
                    ╱          ╲
      $Proxy142               MaterialServiceImpl
      (implements)            (implements)
           ↑                        ↑
      공통 부모를 가진 형제일 뿐, 서로 상속하지 않는다
      → Java 타입 규칙상 캐스팅될 수 없다
```

**`@Transactional` 때문에 자동 프록시 생성기가 원본 대신 프록시를 등록했고, 그 프록시는 `MaterialService` 인터페이스는 구현했지만 `MaterialServiceImpl`을 상속하지는 않았다.**

**"주입은 성공하고 컴파일도 통과한다"** — 주입 지점의 선언 타입이 `MaterialService`이므로 **인터페이스 기준으로는 아무 문제가 없다.** 캐스팅은 컴파일러가 **"될 수도 있다"**고만 판정하고 실제 검사는 런타임에 한다.

**CGLIB였다면 성공한다**:

```text
[JDK 동적 프록시]                      [CGLIB 프록시]
  class $Proxy142                        class MaterialServiceImpl$$SpringCGLIB$$0
        implements MaterialService             extends MaterialServiceImpl
  (MaterialServiceImpl) 캐스팅 실패      (MaterialServiceImpl) 캐스팅 성공
```

> **핵심은 상속 관계의 유무다. CGLIB 프록시는 원본의 하위 클래스이므로 원본 타입으로 캐스팅된다. JDK 프록시는 형제라 안 된다.**

**§6**: **프록시된 빈을 구현 클래스로 캐스팅하지 않는다.** **프록시 타입에 따라 되기도 하고 안 되기도 하는 코드는 설정 변경 하나로 깨진다.** 필요한 메서드가 있으면 **인터페이스에 올린다.**

## Q2. 인터페이스에 없는 메서드가 "존재하지 않는" 이유

**인터페이스에 선언되지 않았으니 프록시가 흉내 낼 대상이 아니고, 클래스 파일에 아예 생성되지 않는다.**

```text
$Proxy142 가 만들어질 때
  → MaterialService 인터페이스의 메서드 목록을 읽는다
  → findAll() 하나뿐이다
  → findAll() 만 구현한 클래스를 바이트코드로 생성한다
  → reindexInternal() 은 그 클래스에 없다
```

**"안 하는 것"이 아니라 "없는 것"이다.**

**차이가 왜 중요한가**:

| | "호출되지 않는다" | **"존재하지 않는다"** |
|---|---|---|
| 메서드는 | 있는데 무시된다 | **아예 없다** |
| 리플렉션으로 찾으면 | 찾아진다 | **`NoSuchMethodException`** |
| 인터페이스 타입으로 부르면 | — | **컴파일 오류** |
| 캐스팅해서 부르면 | 동작할 수도 | **캐스팅에서 먼저 실패**(Q1) |

**비유와 그 한계 — 역할 대역 배우**: 원작 배우가 못 나와 대역을 세웠는데, 대역에게 준 것은 **대본에 적힌 대사 목록**(인터페이스)뿐이다. 대역은 대본에 있는 장면은 완벽히 소화하지만, **원작 배우가 사석에서 하던 취미(인터페이스에 없는 메서드)는 아예 모른다.**

→ **깨지는 지점**: 대역 배우는 사람이라 **대본에 없는 즉흥 연기라도 할 수 있다.** JDK 프록시는 못 한다 — **인터페이스에 없는 메서드는 클래스 파일에 아예 생성되지 않으므로 호출할 방법 자체가 존재하지 않는다.**

**그래서 CGLIB가 존재한다** — **인터페이스가 없는 클래스도 프록시하고 싶고, 인터페이스에 없는 메서드도 살리고 싶다.** 그러려면 **인터페이스를 구현하는 대신 클래스를 상속**해야 한다.

## Q3. Framework의 프록시 선택 규칙

**공식 문서의 한 문장**:

> *"프록시될 대상 객체가 **인터페이스를 최소 하나 구현하면 JDK 동적 프록시**가 사용되고, 대상 타입이 구현한 모든 인터페이스가 프록시된다. 대상 객체가 **아무 인터페이스도 구현하지 않으면** 대상 타입의 런타임 생성 하위 클래스인 **CGLIB 프록시**가 만들어진다."*

**5단계**:

1. **자동 프록시 생성기가 대상 빈을 판정한다** — 어드바이스를 붙일 필요가 없는 빈까지 감싸면 낭비다(판정 방법은 [[02-advisor-pointcut-and-auto-proxy-creation]])
2. **대상 타입이 인터페이스를 구현하는지 본다** — 두 생성 방식 중 하나를 골라야 한다
3. **구현했으면 그 인터페이스들로 JDK 프록시** — **표준 JDK 기능만으로 되고 별도 바이트코드 라이브러리가 필요 없다**
4. **안 했으면 대상 타입을 상속한 하위 클래스** — **인터페이스가 없으면 흉내 낼 계약이 없어 상속밖에 방법이 없다**
5. **어느 쪽이든 타깃 객체를 필드로 들고 호출을 위임한다** — **실제 로직은 원본에 있고 프록시는 앞뒤로 어드바이스만 끼운다**

**1단계가 프록시 생성보다 먼저라는 점을 놓치기 쉽다** — **"어떤 프록시를 만드는가"보다 "만들기는 하는가"가 앞선다.**

## Q4. Spring Boot에서 규칙이 달라지는 방식과 이유

**Boot는 인터페이스가 있어도 CGLIB를 기본으로 쓴다.**

**Framework 문서 자신이 단서를 단다**: *"전역 기본 프록시 타입은 설정에 따라 다를 수 있다. 코어 프레임워크는 기본적으로 인터페이스 기반 프록시를 제안하지만, **Spring Boot는 설정 프로퍼티에 따라 클래스 기반 프록시를 기본으로 활성화할 수 있다.**"*

**Boot 문서는 확정적이다**: *"**기본적으로 Spring Boot의 자동 구성은 Spring AOP가 CGLib 프록시를 사용하도록 구성한다.** JDK 프록시를 쓰려면 `spring.aop.proxy-target-class`를 `false`로 설정한다."*

| 환경 | 인터페이스가 있을 때 기본 |
|---|---|
| 순수 Spring Framework | **JDK 동적 프록시** |
| **Spring Boot (자동 구성)** | **CGLIB 프록시** |

**왜 바꿨나 — 실용적인 이유다**:

> **인터페이스 유무에 따라 프록시 타입이 달라지면 같은 코드가 클래스 구조를 바꿨다는 이유만으로 다르게 동작한다. 인터페이스를 하나 추가하는 순간 캐스팅이 깨지는 식이다. CGLIB로 통일하면 그 변동이 사라진다.**

```text
[Framework 기본]
  인터페이스를 하나 추가한다  → 프록시 타입이 JDK 로 바뀐다
                              → 기존 캐스팅 코드가 런타임에 깨진다
                              → 리팩터링이 무서워진다

[Boot 기본]
  인터페이스를 추가해도 CGLIB 그대로 → 동작이 안 바뀐다
```

**그래서 Q1의 `ClassCastException`은 Boot 프로젝트에서는 대개 안 난다.** 같은 코드가 **순수 Framework 설정에서만 터진다.**

**§5의 오해**: **"인터페이스를 만들면 JDK 프록시"는 가장 널리 퍼진 오해다.** 순수 Framework에서는 맞지만 **Boot에서는 틀린다.** 그 설명을 외운 채 Boot에서 실험하면 **재현이 안 된다.**

## Q5. 지금 내 빈이 어떤 프록시인지 확인하는 방법 둘

**① 클래스 이름을 찍는다**

```java
System.out.println(materialService.getClass().getName());
// jdk.proxy2.$Proxy142                        → JDK
// com...MaterialServiceImpl$$SpringCGLIB$$0   → CGLIB
```

**이름 자체가 정체를 말한다** — `$Proxy`로 시작하면 JDK, `$$SpringCGLIB$$`가 들어가면 CGLIB다.

**② `AopUtils`로 판정한다**

```java
AopUtils.isCglibProxy(bean)        // CGLIB 인가
AopUtils.isJdkDynamicProxy(bean)   // JDK 인가
AopUtils.isAopProxy(bean)          // 프록시이기는 한가
```

**세 번째가 특히 유용하다** — [[02-advisor-pointcut-and-auto-proxy-creation]]에서 다루는 **"프록시가 아예 아닌 경우"**를 먼저 걸러 낸다. 프록시가 아니라면 종류를 따질 이유가 없다.

**§6의 경고**: **프록시 타입을 코드 동작의 전제로 삼지 않는다.** **`getClass()` 결과로 분기하는 코드는 설정에 결합된다.** 위 방법들은 **진단용**이지 프로덕션 로직에 넣을 것이 아니다.

**설정을 바꾸는 자리**(§2.4):

```properties
spring.aop.proxy-target-class=true    # Boot 기본값. false 면 JDK 로 돌아간다
```

```java
@EnableTransactionManagement(proxyTargetClass = true)
@EnableAspectJAutoProxy(proxyTargetClass = true)
```

**XML의 함정**: `<tx:annotation-driven/>`, `<aop:aspectj-autoproxy/>`, `<aop:config/>` 중 **어느 하나에 `proxy-target-class="true"`를 쓰면 셋 모두에 CGLIB가 강제된다.** **한 곳만 바꿨다고 생각했는데 전역이 바뀌는 종류의 설정이다.**

## Q6. `@Transactional`이 안 먹을 때 CGLIB로 바꾸는 것이 헛수고인 이유

**대부분의 경우 원인이 자기 호출이고, 자기 호출은 프록시 종류와 무관하게 깨지기 때문이다.**

| 축 | **프록시 타입 (이 노트)** | **자기 호출** |
|---|---|---|
| 무엇이 문제 | **어떤 클래스가 만들어지는가** | **호출이 프록시를 지나는가** |
| CGLIB로 바꾸면 | 캐스팅·비인터페이스 메서드 **해결** | **해결 안 됨** |
| 해결 방법 | `proxyTargetClass=true` | **구조 변경** |

**왜 무관한가**:

```text
JDK 프록시:    this.method()  → 프록시를 안 지난다 ❌
CGLIB 프록시:  this.method()  → 프록시를 안 지난다 ❌
                 ↑ 둘 다 "프록시를 지나야 동작한다"는 전제 위에 있다
```

**프록시 종류는 "프록시가 어떻게 생겼는가"의 문제이고, 자기 호출은 "프록시를 거치는가"의 문제다.** 다른 축이다.

**그럼 CGLIB로 바꿔서 해결되는 것은 무엇인가**:

| 증상 | CGLIB로 해결? |
|---|---|
| `ClassCastException`으로 구현체 캐스팅 실패 | **✅** |
| 인터페이스에 없는 메서드에 AOP가 안 걸림 | **✅** |
| **자기 호출로 `@Transactional`이 무효** | **❌** |
| **`private` 메서드에 `@Transactional`이 무효** | **❌** |
| **`final` 메서드에 AOP가 안 걸림** | **❌ (오히려 CGLIB에서만 생기는 문제)** |

**마지막 줄이 아이러니다** — CGLIB로 바꾸면 **`final` 관련 제약이 새로 생긴다**(Q7). 문제를 해결하려다 다른 문제를 얻는 경로다.

**진단 순서**: 먼저 **`AopUtils.isAopProxy()`로 프록시이기는 한지**, 그다음 **호출 경로가 프록시를 지나는지**를 본다. 프록시 종류는 **그 둘이 다 맞은 뒤에** 따질 문제다.

## Q7. `final` 클래스에 `@Transactional`을 붙이면

**CGLIB가 상속할 수 없어 프록시가 만들어지지 않는다.**

```text
CGLIB 는 "대상 타입을 상속한 하위 클래스"를 만든다
  → final 클래스는 상속할 수 없다
  → 프록시를 만들 수 없다
```

**어떻게 드러나는가는 상황에 따라 다르다**:

| 상황 | 결과 |
|---|---|
| **인터페이스가 있고 JDK 프록시** | **동작한다** — 상속이 필요 없다 |
| **인터페이스가 없거나 Boot 기본(CGLIB)** | **프록시 생성 실패 또는 애노테이션 무효** |

**§6**: **`final` 클래스에 `@Transactional`을 붙이지 않는다.** **Kotlin에서 클래스가 기본 `final`이라 자주 걸린다.**

**Kotlin이 특히 위험한 이유** — 자바에서는 `final`을 **의식적으로 붙여야** 하지만, **Kotlin에서는 아무것도 안 붙이면 `final`이다.** 그래서 **평범하게 작성한 서비스 클래스가 전부 프록시 불가**가 된다.

**같은 제약이 메서드에도 있다** — `final` 메서드는 오버라이드할 수 없으므로 **그 메서드만 어드바이스가 안 걸린다.** 클래스와 달리 **프록시는 만들어지고 그 메서드만 조용히 원본이 호출된다** — 더 찾기 어렵다.

**이 모든 제약이 한 문장에서 나온다**([[03-why-final-private-and-self-invocation-break]]):

> **"상속해서 오버라이드한다"**

**§6의 관련 경계 — 프록시가 답이 아닌 경우**: **생성자·필드 접근·`private` 메서드에 개입해야 한다면 프록시로는 불가능하다. AspectJ 위빙이 필요한 자리다.**

## Q8. 프록시가 들고 있는 것이 "로직"이 아니라 "참조"라는 말

**프록시는 실제 일을 하지 않는다. 타깃 객체를 필드로 들고 호출을 위임할 뿐이다.**

```text
프록시 (JDK 든 CGLIB 든)
┌────────────────────────────┐
│ private Object target;     │  ← 원본 MaterialServiceImpl 인스턴스
│                            │
│ findAll() {                │
│   어드바이스 앞부분         │  ← 트랜잭션 시작
│   target.findAll();        │  ← 실제 로직은 여기 있다
│   어드바이스 뒷부분         │  ← 커밋 / 롤백
│ }                          │
└────────────────────────────┘
```

**§2.2의 5단계**: *"어느 쪽이든 **타깃 객체를 필드로 들고 호출을 위임한다.** 실제 로직은 원본에 있고 **프록시는 앞뒤로 어드바이스만 끼우는 역할**이다."*

**이 사실에서 여러 결과가 따라 나온다**:

| 결과 | 왜 |
|---|---|
| **원본 객체가 별도로 존재한다** | 프록시가 참조를 들고 있으니까 |
| **원본의 필드는 프록시에 없다** | 프록시는 값을 복사하지 않는다 — [[03-why-final-private-and-self-invocation-break]]의 필드 문제 |
| **원본 안의 `this`는 원본이다** | 프록시가 아니다 → 자기 호출 문제 |
| **프록시를 여러 겹 쌓을 수 있다** | 프록시가 다른 프록시를 타깃으로 들면 된다 |

**"로직을 복사한다"였다면 어떻게 달랐을까** — 필드도 복사되고 `this`도 프록시가 되어 자기 호출 문제가 없었을 것이다. **대신 원본과 프록시의 상태가 갈라지고**, 상속·리플렉션·직렬화가 전부 어긋난다. **참조 위임이 훨씬 단순하고 안전한 대신, 이 챕터의 모든 함정을 만든다.**

## Q9. `$Proxy142`의 "동적"과 CGLIB의 "Code Generation"

**둘 다 "클래스를 실행 시점에 만든다"를 가리키지만, 강조점이 다르다.**

**JDK 동적 프록시의 "동적(dynamic)"**:

> **클래스가 컴파일 시점이 아니라 실행 시점에 만들어진다는 뜻이다.**

**`$Proxy142`의 숫자는 그 JVM에서 몇 번째로 생성된 프록시인지를 나타낸다** — **소스에 없는 이름이 스택 트레이스에 찍히는 이유**다.

```text
$Proxy142
 ↑     ↑
 │     └── 이 JVM 에서 142번째로 생성된 프록시
 └──────── JDK 가 붙이는 접두어
```

**CGLIB = Code Generation Library**:

**이름 그대로 바이트코드를 생성하는 라이브러리**다. 지금은 **Spring이 자체적으로 재패키징해 내장**하고 있고, 그 흔적이 생성 클래스 이름에 남는다:

```text
MaterialServiceImpl$$SpringCGLIB$$0
        ↑              ↑
        원본 클래스    Spring 이 재패키징한 CGLIB 임을 표시
```

**두 이름의 차이가 관점을 보여 준다**:

| | 이름이 강조하는 것 |
|---|---|
| **"동적 프록시"** | **언제 만드는가** (실행 시점) — JDK는 이것을 **프록시 기능**으로 제공한다 |
| **"Code Generation Library"** | **무엇을 하는가** (바이트코드 생성) — CGLIB는 **범용 도구**이고 프록시는 그 용도 중 하나다 |

**그래서 CGLIB는 AOP 밖에서도 쓰인다** — [[04-configuration-class-cglib-enhancement]]에서 보듯 **`@Configuration` 클래스 강화**가 같은 기술을 **AOP가 아닌 목적**에 쓰는 사례다.

**실무 함의**: **스택 트레이스에 `$Proxy`나 `$$SpringCGLIB$$`가 보이면 프록시를 지나고 있다는 증거다.** 반대로 그런 프레임이 **없으면 프록시를 안 지났다** — 자기 호출을 진단하는 실마리가 된다.
