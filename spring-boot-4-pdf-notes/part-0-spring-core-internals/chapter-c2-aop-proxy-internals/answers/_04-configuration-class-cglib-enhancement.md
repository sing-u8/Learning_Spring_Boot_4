## Q1. full 모드에서 `@Bean` 메서드가 다른 `@Bean` 메서드를 부르면

**호출이 가로채여, `new`를 실행하는 대신 컨테이너에 이미 있는 빈을 돌려준다.**

```text
materialCache() 안의 statistics() 호출
  → 평범한 자바 메서드라면 return new CacheStatistics() 가 실행된다
  → 그런데 강화된 하위 클래스가 statistics() 를 오버라이드해 뒀다
  → "이 이름의 빈이 컨테이너에 이미 있으면 그걸 돌려준다"로 동작
  → 같은 싱글턴이 반환된다 ✅
```

**공식 문서의 목적 설명**: `@Bean` 메서드를 `@Configuration` 클래스 안에 선언하면 완전한 설정 클래스 처리가 적용되어 **메서드 간 참조가 컨테이너의 생명주기 관리로 리다이렉트**되며, 이는 *"같은 `@Bean` 메서드가 **평범한 자바 메서드 호출을 통해 실수로 호출되는 것을 막아**, 추적하기 어려운 미묘한 버그를 줄인다."*

**즉 이 강화는 기능 추가가 아니라 실수 방지 장치다** — "자바 문법대로 동작하면 틀린다"는 상황을 프레임워크가 막아 준다.

**`proxyBeanMethods = false`면 반대가 된다** — 공식 문서 표현대로 *"**컨테이너에 가로채이지 않으며** 따라서 평범한 메서드 호출처럼 동작해, 해당 빈의 기존 싱글턴 인스턴스를 재사용하는 대신 **매번 새 인스턴스를 만든다.**"*

## Q2. 그 가로채기를 무엇으로 구현하고, 그래서 생기는 제약

**CGLIB 하위 클래스로 구현한다. 그래서 `final`·`private` 제약이 그대로 붙는다.**

**강화의 5단계**:

1. **`@Configuration` 클래스의 빈 정의가 등록된다** — 설정 클래스도 결국 빈이다
2. **설정 클래스 후처리기가 `proxyBeanMethods` 값을 확인한다**
3. **`true`면 그 클래스를 상속한 CGLIB 하위 클래스를 만들고 빈 정의의 클래스를 그것으로 교체한다** — **`@Bean` 메서드를 오버라이드해야 호출을 가로챌 수 있다**
4. **하위 클래스의 각 `@Bean` 메서드는 "컨테이너에 이 빈이 있으면 그걸 반환, 없으면 원본 메서드 실행"으로 동작한다**
5. **설정 클래스 인스턴스(=강화된 하위 클래스)가 만들어지고 `@Bean` 메서드가 호출되어 빈들이 등록된다**

**3번이 [[03-why-final-private-and-self-invocation-break]]의 제약을 그대로 물려받는다**:

| 제약 | 이유 |
|---|---|
| **`@Configuration` 클래스가 `final`이면 안 된다** | 상속할 수 없다 |
| **`@Bean` 메서드가 `final`이면 안 된다** | 오버라이드되지 않아 가로채기가 안 된다 |
| **`@Bean` 메서드가 `private`이면 안 된다** | 같은 이유 |
| **설정 클래스에 상태(필드)를 두면 혼란** | 강화된 하위 클래스 인스턴스가 만들어진다 |

**§6**: **`@Configuration` 클래스를 `final`로 만들지 않는다. Kotlin에서는 `kotlin-spring` 플러그인을 확인한다.** 그리고 **`@Configuration` 클래스에 상태를 두지 않는다** — **설정 클래스는 팩터리 메서드의 모음으로만 쓴다.**

**속성 이름이 이미 답을 말한다**(§2.5): **`proxyBeanMethods`는 문자 그대로 "빈 메서드를 프록시할 것인가"다.** **가로채기의 정체가 프록시라는 것을 이름이 요약하고 있다.**

## Q3. `proxyBeanMethods = false`로 바꾸면 정확히 무엇이 달라지나

**CGLIB 하위 클래스가 만들어지지 않고, `@Bean` 메서드가 평범한 자바 메서드가 된다.**

| | **full 모드** | ****lite 모드**** |
|---|---|---|
| 조건 | `@Configuration` (기본 `proxyBeanMethods = true`) | `@Configuration(proxyBeanMethods = false)`, 또는 **`@Bean`이 `@Configuration` 아닌 클래스에 있을 때** |
| **CGLIB 하위 클래스** | **생성됨** | **생성 안 됨** |
| **`@Bean` 메서드 직접 호출** | **가로채여 싱글턴 반환** | **평범한 호출 — 새 인스턴스** |
| 오버헤드 | 클래스당 하위 클래스 생성 | **없음** |
| 문서의 성격 규정 | 완전한 설정 클래스 처리 | *"특별한 런타임 처리 없는 **범용 팩터리 메서드 메커니즘**"* |

**달라지지 않는 것도 정확히 알아야 한다**:

- **`@Bean` 메서드가 빈을 등록하는 것**은 그대로다 — 컨테이너가 각 메서드를 한 번씩 부른다
- **의존성 주입**도 그대로다 — 메서드 인자로 받으면 주입된다
- **오직 "메서드끼리 직접 호출할 때"만 달라진다**

**즉 코드에 `statistics()` 같은 직접 호출이 없으면 두 모드가 동일하게 동작한다**(Q7).

## Q4. 출발 장면에서 `CacheStatistics`가 세 개가 된 경로

```text
proxyBeanMethods = false  →  강화 없음  →  statistics() 는 평범한 자바 메서드

① 컨테이너가 statistics() 를 부른다
     → new CacheStatistics()  #1  → 컨테이너에 "statistics" 빈으로 등록

② 컨테이너가 materialCache() 를 부른다
     → 그 안의 statistics() 는 평범한 호출
     → new CacheStatistics()  #2  → MaterialCache 가 이것을 들고 간다

③ 컨테이너가 substanceCache() 를 부른다
     → 또 평범한 호출
     → new CacheStatistics()  #3  → SubstanceCache 가 이것을 들고 간다

결과: 인스턴스 3개
  지표를 노출하는 쪽은 ①(컨테이너에 등록된 것)을 읽는다
  기록은 ②③에 쌓인다
  → ①은 아무도 기록하지 않는 빈 객체다
  → 히트율이 실제의 절반 이하로 나온다
```

**`proxyBeanMethods = false`를 지우면 세 참조가 전부 같은 객체가 된다** — 오버라이드된 `statistics()`가 ②③에서 **컨테이너의 ①을 돌려주기 때문**이다.

> **애노테이션 속성 하나가 싱글턴 보장을 껐다.**

**주목할 점 — `statistics()`가 자바 문법대로 동작한 것이 문제다.** `return new CacheStatistics()`가 새 객체를 주는 것은 **정상**이다. **비정상은 full 모드 쪽**이고, 그 비정상이 우리가 기대하는 동작이다.

## Q5. 이 버그가 조용히 지나가는 이유

**타입이 맞고, `null`도 아니고, 메서드도 다 동작하기 때문이다. 그저 다른 객체일 뿐이다.**

**비유와 그 한계 — 회사 대표번호와 개인 휴대폰**: 대표번호로 "회계 담당자"를 찾으면 교환원이 **항상 같은 담당자에게 연결**한다(full 모드). 교환원을 없애면(lite 모드) "회계 담당자"라고 외칠 때마다 **새 직원을 채용해서 데려온다.** 매번 다른 사람이고 **앞사람이 처리한 내용을 모른다.**

→ **깨지는 지점**: **새 직원을 채용하면 누구나 이상하다는 걸 알아챈다.** 새 `CacheStatistics`는 **아무도 못 알아챈다.**

**어느 단계에서도 신호가 없다**:

| 단계 | 왜 안 걸리나 |
|---|---|
| **컴파일** | 타입이 맞다 |
| **시작** | 빈이 정상 등록된다. 예외 없음 |
| **기능 테스트** | 캐시는 정상 동작한다 — 히트도 미스도 맞게 처리된다 |
| **런타임 예외** | 없다. 모든 메서드가 정상 동작한다 |

**드러나는 것은 오직 "지표가 이상하다"는 형태**이고, **그것도 한참 뒤에** 드러난다. 그리고 **지표가 절반이라는 사실만으로는 원인을 짐작할 수 없다** — 캐시 로직을 먼저 의심하게 된다.

**이것이 c1·c2 전반의 반복되는 패턴이다** — **프록시 관련 실패는 예외가 아니라 부재로 나타난다.** `@PostConstruct`의 `@Transactional`도, `private` 메서드의 AOP도, 여기의 싱글턴 파괴도 전부 **"아무 일도 안 일어남"**이다.

## Q6. lite 모드에서 공식 문서가 요구하는 작성 방식

**메서드 인자로 협력자를 받는다.**

공식 문서: 런타임 프록시가 없는 클래스의 `@Bean` 메서드는 *"애초에 **인터-빈 의존성을 선언하도록 의도된 것이 아니며**"*, 대신 **자기가 속한 컴포넌트의 필드**나 **팩터리 메서드가 선언한 인자(자동 주입된 협력자)**로 동작해야 한다.

```java
@Configuration(proxyBeanMethods = false)
public class CatalogCacheConfig {

    @Bean
    public CacheStatistics statistics() {
        return new CacheStatistics();
    }

    @Bean
    public MaterialCache materialCache(CacheStatistics statistics) {   // ← 인자로 받는다
        return new MaterialCache(statistics);
    }

    @Bean
    public SubstanceCache substanceCache(CacheStatistics statistics) { // ← 인자로 받는다
        return new SubstanceCache(statistics);
    }
}
```

**메서드 인자로 받으면 컨테이너가 주입해 주므로 항상 같은 싱글턴이다. 강화가 필요 없다.**

**규칙 하나로 요약된다**:

> **`@Bean` 메서드 안에서 다른 `@Bean` 메서드를 호출하지 않는다.**

**그러면 `proxyBeanMethods` 값이 무엇이든 코드가 같게 동작한다.**

**§6**: **`@Bean` 메서드끼리 직접 호출하지 않는다.** **이 규칙 하나면 이 노트의 문제 전체가 사라진다.**

## Q7. 인자 주입이 두 모드 모두에서 옳은 이유

**인자 주입은 컨테이너가 해석하므로, 가로채기가 있든 없든 같은 싱글턴이 온다.**

```text
[full 모드]
  materialCache(CacheStatistics statistics)
    → 컨테이너가 "statistics" 빈을 찾아 주입
    → 강화가 개입할 일이 없다 (메서드 호출이 아니니까)
    → 싱글턴 ✅

[lite 모드]
  materialCache(CacheStatistics statistics)
    → 컨테이너가 "statistics" 빈을 찾아 주입
    → 똑같다
    → 싱글턴 ✅
```

**직접 호출은 모드에 의존하지만, 인자 주입은 모드와 무관하다.**

**§5의 판단**:

> **"full 모드니까 직접 호출해도 된다"는 맞지만, 인자 주입으로 쓰면 모드에 무관하게 옳다. 나중에 누군가 `proxyBeanMethods = false`를 붙여도 안전하다. 습관으로 인자 주입을 쓰는 편이 낫다.**

**"나중에 누군가"가 핵심 근거다** — 지금 full 모드라고 해서 직접 호출을 쓰면, **그 코드는 설정 한 줄에 의존하는 상태**가 된다. 그리고 그 설정을 바꾸는 사람은 **자기가 무엇을 깨뜨리는지 모른다**(Q5의 조용함).

**c2-01 Q10과 같은 논리다** — **"프록시 타입에 의존하는 코드를 쓰지 않는다"**와 같은 원칙이 여기서는 **"모드에 의존하는 코드를 쓰지 않는다"**로 나타난다.

**추가 이득**: 인자 주입은 **의존성이 시그니처에 드러난다.** `materialCache(CacheStatistics statistics)`를 보면 무엇이 필요한지 즉시 안다. 직접 호출은 **메서드 본문을 읽어야** 안다.

## Q8. Spring Boot 자동 구성이 lite 모드를 쓰는 이유 둘

**Spring Boot의 자동 구성 클래스들은 `@AutoConfiguration`을 쓰는데, 이 애노테이션은 `@Configuration(proxyBeanMethods = false)`를 메타 애노테이션으로 포함한다.**

**① 규모 — 시작 시간과 메모리**

**애플리케이션 하나가 수십~수백 개의 자동 구성 클래스를 평가하는데, 그 전부에 CGLIB 하위 클래스를 만들면 시작 시간과 메모리가 누적된다.**

공식 문서 표현으로 lite 모드의 *"긍정적 부수 효과는 **런타임에 CGLIB 하위 클래스를 적용할 필요가 없어 오버헤드와 메모리 사용이 줄어든다**는 것"*이다.

**② 네이티브 이미지**

Boot 문서가 적듯 **CGLIB 프록시 클래스는 네이티브 이미지에서 빌드 시점에 생성돼야** 하므로, **애초에 만들 필요가 없으면 그만큼 단순해진다.**

**Ch15의 "빌드 시점으로 이동"(방향 ④)과 이어진다** — 런타임 동적 생성을 줄이는 것이 네이티브 이미지 지원의 일반적 방향이다.

**중요한 단서**(§2.4):

> **우리가 쓰는 애플리케이션 설정 클래스에는 이 논리가 그대로 적용되지 않는다.**

| | 자동 구성 | 내 설정 클래스 |
|---|---|---|
| 개수 | **수십~수백** | **몇 개** |
| 강화 비용 | **누적되면 유의미** | **미미** |
| 실수의 대가 | 라이브러리 저자가 규칙을 안다 | **출발 장면처럼 크다** |

**§6**: **애플리케이션 설정 클래스에 습관적으로 `proxyBeanMethods = false`를 붙이지 않는다.** **라이브러리·스타터를 만들거나 시작 시간을 실제로 측정해 문제를 확인했을 때만 끈다.**

## Q9. AOP 프록시와 설정 클래스 강화의 차이 셋과 공통점 하나

| 축 | **AOP 프록시** | **설정 클래스 강화** |
|---|---|---|
| **① 목적** | **횡단 관심사 삽입**(트랜잭션·캐시) | **`@Bean` 메서드의 싱글턴 보장** |
| **② 대상 판정** | **포인트컷 평가** | **`@Configuration` 애노테이션 유무** |
| **③ 만드는 주체** | **자동 프록시 생성기**(빈 후처리기) | **설정 클래스 후처리기** |
| 끄는 방법 | 애노테이션 제거 | `proxyBeanMethods = false` |
| **공통점** | **둘 다 CGLIB 상속 → `final` 불가** | **같음** |

**마지막 행이 요점이다**:

> **목적이 달라도 물리적 수단이 같아서 제약도 같다.**

**②의 차이가 특히 중요하다** — 설정 클래스 강화는 **[[02-advisor-pointcut-and-auto-proxy-creation]]의 포인트컷 평가를 거치지 않는 별도 경로**다. 어드바이저가 하나도 없어도 `@Configuration`이면 강화된다.

**③도 다르다** — AOP 프록시는 **빈 후처리기**(c1-02)가 만들고, 설정 클래스 강화는 **설정 클래스 후처리기**가 만든다. **시점도 다르다** — 강화는 **빈 정의 단계**(c1-01)에서 일어나고, AOP 프록시는 **빈 생성 후**(c1-03의 6단계)다.

**그래서 "왜 이 빈이 프록시인가"에 답하려면 두 경로를 구분해야 한다**:

```text
클래스 이름에 $$SpringCGLIB$$ 가 있다
  ├ @Configuration 클래스인가?      → 설정 클래스 강화
  └ AOP 애노테이션이 있는가?         → AOP 프록시
     (둘 다일 수도 있다)
```

## Q10. `@Component`에 `@Bean` 메서드를 두면 어느 모드인가

**lite 모드다.**

**§2.1의 정의**: lite 모드의 조건은 두 가지다 —

1. `@Configuration(proxyBeanMethods = false)`
2. **`@Bean`이 `@Configuration` 아닌 클래스(`@Component` 등)에 있을 때**

**두 번째를 놓치기 쉽다.**

> **`@Component`에 `@Bean` 메서드를 쓰면 그것만으로 이미 lite 모드다.**

**§5**: **`proxyBeanMethods`를 명시하지 않았어도 그렇다.** `@Configuration`이 아닌 클래스에 `@Bean`을 쓰면 **강화가 없다.** **`@Component`에 `@Bean` 메서드를 두고 그 안에서 다른 `@Bean` 메서드를 부르면 출발 장면과 같은 문제가 난다.**

**왜 특히 위험한가** — **`proxyBeanMethods = false`는 눈에 보인다.** 누군가 명시적으로 적은 것이니 검토 대상이 된다. **`@Component`에 `@Bean`을 둔 것은 그냥 평범해 보인다.** 아무도 "이건 lite 모드다"라고 생각하지 않는다.

```java
@Component                    // ← @Configuration 이 아니다
public class SomeComponent {

    @Bean
    CacheStatistics statistics() { return new CacheStatistics(); }

    @Bean
    MaterialCache cache() {
        return new MaterialCache(statistics());   // ← 새 인스턴스가 나온다
    }
}
```

**이 코드에는 `proxyBeanMethods`라는 단어가 없다.** 그래도 lite 모드다.

**대응은 같다** — **인자 주입을 쓴다**(Q6·Q7). 그러면 **어느 애노테이션이 붙어 있든 옳다.**

**덤 — `private` `@Bean` 메서드**(§5): Spring 6.x부터 **`private` `@Bean` 메서드 자체는 lite 모드에서 지원**되지만, **full 모드의 가로채기는 여전히 불가능**하다(오버라이드할 수 없으니까). **헷갈릴 여지를 만들지 않는 것이 낫다.**
