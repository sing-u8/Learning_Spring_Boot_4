## Q1. 내 패키지 밖의 클래스가 빈을 등록하는 메커니즘

**컴포넌트 스캔이 아니라 임포트 파일이다 — 라이브러리가 자기 목록을 신고한다.**

```text
"내가 스캔해서 찾는다"  →  "라이브러리가 자기 목록을 신고한다"

각 JAR 이 자기 안에
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
를 넣어 두고
Boot 가 클래스패스의 모든 JAR 에서 그 파일을 읽어 모은다
```

**`@ComponentScan`은 `@SpringBootApplication`이 붙은 클래스의 패키지와 그 하위만 훑는다.** `DataSource`·`EntityManagerFactory`·`ObjectMapper`·`DispatcherServlet`은 전부 **`org.springframework.boot.*` 패키지의 JAR 안**에 있으므로 **스캔으로는 절대 발견되지 않는다.**

**비유와 그 한계 — 호텔 컨시어지의 제휴 업체 목록**: 컨시어지가 **도시를 직접 돌아다니며 식당을 찾는 것(스캔)이 아니라**, 제휴 업체들이 **자기 정보를 등록해 둔 바인더**를 넘겨본다. **새 업체가 제휴하면 바인더에 한 줄이 추가될 뿐, 컨시어지의 절차는 그대로다.**

→ **깨지는 지점**: 바인더에 실린 업체는 **영업 중이면 곧바로 안내할 수 있다.** 자동 구성 후보는 **목록에 있어도 대개 적용되지 않는다.** 수백 개 중 수십 개만 조건을 통과한다. **목록은 "가능한 것"의 목록이지 "적용될 것"의 목록이 아니다**(Q6).

## Q2. 컴포넌트 스캔으로 찾는다면 무너지는 것 셋

```java
@ComponentScan({"com.cosmoroute", "org.springframework.boot.autoconfigure"})   // 이렇게?
```

| 무너지는 것 | 내용 |
|---|---|
| **① 조건부 적용** | 그 패키지의 `@Component`가 **조건 없이 전부 등록**된다. **조건부 적용이라는 자동 구성의 핵심이 무너진다** |
| **② 시작 성능** | **클래스패스의 수천 개 클래스를 스캔하고 애노테이션을 읽어야** 한다 |
| **③ 유지보수** | **의존성을 추가할 때마다 스캔 목록을 손봐야** 한다. 라이브러리마다 패키지 이름이 다르다 |

**그리고 무엇보다 순서 문제가 있다**:

> **컴포넌트 스캔으로 발견된 빈은 사용자 빈과 뒤섞여 등록되므로, "사용자가 이미 만들었는가"를 판정할 안정된 시점이 없어진다.** [[02-conditional-evaluation-and-backoff]]에서 볼 back-off가 성립하지 않는다.

**이것이 네 번째이자 가장 근본적인 문제다** — ①②③은 불편이지만, 순서 문제는 **back-off라는 메커니즘 자체를 불가능하게** 만든다.

**c1-01 Q3에서 본 것과 같은 논리다** — **"사용자 빈이 있는지"를 알려면 전체 목록이 다 모인 뒤여야 한다.** 자동 구성이 사용자 빈과 뒤섞여 발견되면 그 시점을 특정할 수 없다.

## Q3. 임포트 파일의 경로와 형식

**경로**:

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

```text
spring-boot-autoconfigure-4.0.3.jar
 └── META-INF/
      └── spring/
           └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

**형식 — 클래스 이름 한 줄씩**:

```text
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.DispatcherServletAutoConfiguration
...
```

**공식 문서의 규정**: Boot는 발행된 JAR 안에 이 파일이 있는지 확인하며, 파일에는 **한 줄에 클래스 이름 하나씩** 설정 클래스들을 나열해야 한다.

**파일 이름이 긴 이유**(§2.5): **애노테이션의 정규화된 이름 자체가 파일 이름**이라, **다른 종류의 임포트 목록이 생겨도 충돌하지 않는다.**

**§5의 이력**: **`spring.factories`는 옛 방식이다.** Boot **2.7 이전**에는 `META-INF/spring.factories`의 `EnableAutoConfiguration` 키에 목록을 적었다. **지금은 `AutoConfiguration.imports`가 표준**이다. **오래된 블로그나 예제를 볼 때 이 차이를 알아두면 혼란이 준다.**

**§6**: **`spring.factories`를 새로 쓰지 않는다.**

## Q4. 공식 문서가 금지하는 세 가지 — 세 번째가 특히 중요한 이유

**공식 문서가 연달아 금지한다**:

1. **자동 구성은 임포트 파일에 이름이 적히는 것으로만 로드되어야 한다**
2. **특정 패키지 공간에 정의해 컴포넌트 스캔의 대상이 절대 되지 않도록 해야 한다**
3. **자동 구성 클래스 자신이 추가 컴포넌트를 찾기 위해 컴포넌트 스캔을 켜서도 안 된다**

**세 번째가 특히 중요한 이유**:

> **자동 구성이 스캔을 켜면 그 스캔이 사용자 패키지까지 훑을 수 있고, 그러면 사용자 빈이 예상 밖의 시점에 등록되어 [[02-conditional-evaluation-and-backoff]]의 순서 보장이 깨진다.**

```text
자동 구성이 스캔을 켠다
  → 스캔 범위가 사용자 패키지를 포함할 수 있다
  → 사용자 빈이 자동 구성 처리 도중에 등록된다
  → "사용자 빈이 이미 있는가" 판정이 타이밍에 따라 달라진다
  → back-off 가 불안정해진다
```

**①②는 "이 자동 구성이 잘못 등록되는" 문제**이고, **③은 "다른 모든 자동 구성의 판정이 흔들리는" 문제**다. **영향 범위가 다르다.**

**실무 함의**:

> **자동 구성 클래스를 실수로 스캔 범위 안에 두면 조건과 무관하게 등록될 수 있다. 스타터를 직접 만든다면 자동 구성 클래스를 애플리케이션 패키지와 확실히 분리해야 한다.**

**§6**: **자동 구성 클래스를 애플리케이션 패키지 안에 두지 않는다.** **자동 구성 클래스에서 컴포넌트 스캔을 켜지 않는다.**

## Q5. `@SpringBootApplication`의 세 구성 요소

| 구성 애노테이션 | 하는 일 | 이 챕터와의 관계 |
|---|---|---|
| **`@SpringBootConfiguration`** | 이 클래스가 **설정 클래스**임을 표시 | — |
| **`@ComponentScan`** | **내 패키지 아래**를 스캔 | **자동 구성과 무관** |
| **`@EnableAutoConfiguration`** | **임포트 파일 기반** 후보 수집 | **이 챕터의 주제** |

**요점**:

> **두 발견 메커니즘이 완전히 분리돼 있다는 것이 요점이다. 내 빈은 스캔으로, 라이브러리의 빈은 목록 파일로 온다.**

```text
com.cosmoroute.**           →  @ComponentScan 이 찾는다
org.springframework.boot.** →  @EnableAutoConfiguration 이 목록에서 읽는다
                               둘은 서로 관여하지 않는다
```

**`@SpringBootConfiguration`의 역할**은 c2-04와 이어진다 — **`@Configuration`을 메타 애노테이션으로 포함**하므로 이 클래스도 **설정 클래스 강화 대상**이다.

**진단에 쓰인다**: "왜 이 빈이 등록됐지?"라는 질문에 **두 갈래로 답이 나뉜다** — 내 패키지 아래면 스캔, 아니면 자동 구성이다. **어느 쪽인지에 따라 확인할 곳이 완전히 다르다.**

## Q6. "후보 목록에 있다"와 "적용된다"의 차이

**후보는 수백 개이고 적용은 수십 개다.**

```text
클래스패스의 모든 imports 파일    →  후보 목록 (수백 개)
        ↓ exclude 로 제거
        ↓ 순서 결정
        ↓ 조건 평가              ←  여기서 대부분이 탈락한다
   실제 적용 (수십 개)
```

**§5**: **가장 흔한 오해다.** **"그 자동 구성 클래스가 JAR에 있는데 왜 안 되지?"라는 질문의 답은 거의 항상 조건 불통과**이며, 그 이유는 [[04-condition-evaluation-report]]에서 확인한다.

**왜 후보를 많이 두는가** — **어떤 조합의 라이브러리를 쓸지 Boot가 미리 알 수 없기** 때문이다. **가능한 모든 조합을 후보로 두고, 실제 클래스패스를 보고 걸러낸다.**

**그래서 후보 목록이 길다는 것은 정상이다**(c4-04 Q5) — **`spring-boot-autoconfigure` 하나가 수백 개를 신고**하고, 그중 **내 프로젝트에 해당하는 것만 통과**한다.

**비유의 한계가 여기서 나온다**(Q1) — 바인더의 업체는 **영업 중이면 안내할 수 있지만**, 자동 구성 후보는 **목록에 있어도 대개 적용되지 않는다.**

**다음 노트가 이 질문을 이어받는다** — **이 노트가 "무엇이 후보인가"까지, [[02-conditional-evaluation-and-backoff]]가 "후보 중 무엇이 적용되는가"를 답한다.**

## Q7. 후보를 목록에서 빼는 세 방법과 백오프와의 차이

**세 방법**:

```java
// ① 클래스가 클래스패스에 있을 때
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
```

```java
// ② 클래스가 클래스패스에 없을 때 — 문자열로
@SpringBootApplication(excludeName = { "org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration" })
```

```properties
# ③ 프로퍼티로 — 환경별로 다르게 할 수 있다
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
```

**공식 문서는 ②를 클래스가 클래스패스에 없을 때의 방법으로 명시**하고, **애노테이션 수준과 프로퍼티 양쪽에서** 제외를 정의할 수 있다고 적는다.

**백오프와의 차이**(§5):

| 축 | **exclude** | ****백오프**** |
|---|---|---|
| 하는 일 | 후보 목록에서 **제거** | 조건 평가에서 **불통과** |
| **시점** | 조건 평가 **전** | 조건 평가 **중** |
| 트리거 | **명시적 지정** | **사용자 빈의 존재** |
| 쓸 때 | **기능 자체가 없어야 할 때** | **기본값만 바꾸고 싶을 때** |

> **제외는 대개 마지막 수단이다.** 자동 구성은 백오프로 물러나도록 설계돼 있으므로, **사용자 빈을 정의하는 것만으로 대체되는 경우가 대부분이다.**

**제외가 필요한 경우**: **"이 기능 자체가 아예 없어야 하는" 경우** — 예를 들어 **데이터베이스를 안 쓰는데 JPA 스타터가 전이 의존성으로 딸려 온 상황.**

**§6**: **`exclude`를 습관적으로 쓰지 않는다.**

## Q8. "옵트인"이라는 성격이 뜻하는 바

**명시적으로 켜지 않으면 아무 일도 일어나지 않는다.**

> **공식 문서 표현으로 자동 구성은 옵트인이다.**

**§2.1의 지적**:

> **1번의 "옵트인"이 자주 잊힌다.** `@SpringBootApplication`이 **세 애노테이션의 묶음**이라 **자동으로 되는 것처럼 보일 뿐**, 실제로는 **명시적 활성화**다.

**무엇이 달라지는가**:

| | 옵트인 | 항상 켜짐이었다면 |
|---|---|---|
| `@EnableAutoConfiguration` 없는 앱 | **자동 구성 없음** | 끌 방법이 없다 |
| 테스트 슬라이스 | **필요한 것만 켠다** | 전부 켜진다 |
| 라이브러리로 쓰일 때 | **소비자가 결정** | 강제된다 |

**두 번째가 실무에서 크다** — `@WebMvcTest`·`@DataJpaTest` 같은 **테스트 슬라이스가 가능한 이유**가 자동 구성이 옵트인이기 때문이다. **필요한 자동 구성만 켜서 컨텍스트를 가볍게** 만든다.

**그리고 "켜는 것"과 "무엇이 켜지는가"가 다르다** — `@EnableAutoConfiguration`은 **평가를 시작하라**는 뜻이지 **전부 적용하라**는 뜻이 아니다(Q6).

**c1-01의 사전 인스턴스화와 대비된다** — 그쪽은 **기본이 켜짐**(끄려면 `lazy-initialization=true`)이고, 이쪽은 **기본이 꺼짐**(켜려면 애노테이션). **어느 쪽이 안전한 기본값인가**로 정해진 차이다.

## Q9. `imports`라는 이름이 "스캔"과 대비해 말하는 것

**"스캔해서 발견"이 아니라 "명시적으로 가져옴"이다.**

> **Spring의 `@Import` 애노테이션이 설정 클래스를 명시적으로 가져오는 것과 같은 어법이며, 실제로 이 목록은 `@Import` 메커니즘 위에서 처리된다.**

```text
scan   : "찾아 나선다"  — 어디 있는지 모르고 뒤진다
                          범위를 정해야 하고, 넓으면 느리다
import : "가져온다"     — 무엇을 가져올지 이미 안다
                          목록에 적힌 것만, 정확히
```

**두 단어의 대비가 Q2의 문제들을 예고한다**:

| | 스캔 | 임포트 |
|---|---|---|
| 대상 결정 | **범위(패키지)** | **명시적 목록** |
| 비용 | 범위에 비례 | 목록 크기에 비례 |
| 예측 가능성 | **패키지에 무엇이 있느냐에 달렸다** | **목록에 적힌 대로** |
| 라이브러리 추가 시 | 스캔 설정을 고쳐야 할 수 있다 | **JAR을 넣으면 끝** |

**마지막 줄이 이 설계의 핵심 이득이다** — **의존성 하나를 추가하면 그 JAR의 목록이 자동으로 합쳐진다.** 사용자가 할 일이 없다.

**그리고 이름이 실제 구현과 일치한다** — 목록은 `@Import` 메커니즘 위에서 처리되므로, **이름이 비유가 아니라 사실**이다.

**Spring의 이름 규약을 읽는 훈련**(c3-03 Q10과 같은 종류): **`imports`라는 파일 확장자 하나가 "이것은 스캔이 아니다"를 말하고 있다.** 이름을 정확히 읽으면 **메커니즘의 절반을 이미 안 것**이다.
