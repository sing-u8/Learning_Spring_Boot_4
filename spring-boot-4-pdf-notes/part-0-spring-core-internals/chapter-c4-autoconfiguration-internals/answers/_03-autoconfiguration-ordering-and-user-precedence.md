## Q1. `@AutoConfigureAfter`가 정하는 것과 정하지 않는 것

**정하는 것: 정의 순서. 정하지 않는 것: 생성 순서.**

공식 문서: *"표준 `@Configuration` 클래스와 마찬가지로, 자동 구성 클래스가 적용되는 순서는 **그 빈들이 정의되는 순서에만 영향을 준다.** 그 빈들이 이후에 **생성되는 순서는 영향받지 않으며**, 각 빈의 의존성과 `@DependsOn` 관계가 결정한다."*

| 단계 | 무엇이 일어나나 | 무엇이 순서를 정하나 |
|---|---|---|
| **정의 단계** | 빈 정의가 레지스트리에 등록됨 | ****자동 구성 순서**** |
| **인스턴스 단계** | 실제 객체가 만들어짐 | **의존성**과 `@DependsOn` |

**c1에서 본 두 단계 구분이 그대로 적용된다.**

**출발 장면의 두 요구가 각각 다른 단계다**:

```text
① DataSource 를 주입받고 싶다        → 정의 단계 문제
   DataSource "정의"가 먼저 있어야 조건이 통과하고 주입 대상을 찾는다
   → after 가 효과가 있었다 ✅

② 초기화 순서를 정하고 싶다          → 인스턴스 단계 문제
   → after 는 여기에 아무 영향이 없다 ❌
```

**비유와 그 한계 — 책의 목차 순서와 읽는 순서**: 목차에서 3장이 5장보다 앞에 있다는 것은 **편집 순서**를 말할 뿐, **독자가 반드시 3장을 먼저 읽는다는 뜻은 아니다.**

→ **깨지는 지점**: 책은 **독자가 마음대로 순서를 정하지만**, 빈 생성 순서는 **의존 관계가 강제한다.** 즉 **"아무렇게나"가 아니라 "다른 규칙이 지배한다"**가 정확한 표현이다. **그래서 해법도 명확하다 — 생성 순서를 원하면 의존성으로 표현하면 된다.**

## Q2. 생성 순서는 무엇이 정하는가

**각 빈의 의존성과 `@DependsOn` 관계다.**

```java
@Bean
public PoolMetricsCollector poolMetrics(DataSource dataSource) {
    return new PoolMetricsCollector(dataSource);
}
```

**이 시그니처 자체가 생성 순서를 강제한다** — `PoolMetricsCollector`를 만들려면 **`DataSource` 인스턴스가 필요**하므로, 컨테이너가 **`DataSource`를 먼저 만든다.**

**§2.4의 선택지 넷**:

| 방법 | 어떻게 | 언제 |
|---|---|---|
| **의존성으로 표현** | 필요한 빈을 **생성자 인자로 받는다** | **대부분의 경우 — 정석** |
| `@DependsOn` | **이름으로** 선행 빈을 지정 | 의존성이 코드에 안 드러나는 경우(정적 초기화 등) |
| `SmartLifecycle` | 컨테이너 시작 후 **단계별 실행** | 컨테이너 전체가 준비된 뒤여야 할 때 |
| `ApplicationRunner` | **모든 빈 완성 후** 1회 실행 | 시작 작업 |

**출발 장면의 두 번째 요구는 첫 번째 방법으로 이미 해결돼 있었다** — 생성자로 `DataSource`를 받으므로 **그 순서는 이미 보장된다.**

**그럼 무엇이 문제였나**(§2.4):

> **초기화 시점에 커넥션을 여는 것 자체가 위험한 설계다.** c1에서 봤듯 **초기화 콜백은 프록시 이전이고, 다른 빈의 완성 상태를 가정할 수 없다.** **그런 작업은 `ApplicationRunner`로 옮기는 것이 맞다.**

**c1-03 Q8과 같은 결론이다** — **"시작할 때 한 번"은 `ApplicationRunner`다.**

## Q3. 정의 순서가 필요한 이유 — 조건 평가와 연결해

**빈 조건이 "지금까지 처리된 것"을 기준으로 평가되기 때문이다.**

```java
@AutoConfiguration
@ConditionalOnBean(DataSource.class)          // DataSource 정의가 이미 있어야 통과
public class CosmoRouteMetricsAutoConfiguration { ... }
```

```text
[순서가 틀리면]
  CosmoRouteMetricsAutoConfiguration 이 먼저 평가된다
    → DataSource 정의가 아직 없다
    → "없다" → 불통과
    → 기능이 통째로 사라진다

  클래스패스도 프로퍼티도 문제없는데 순서 하나로 사라진다. 그것도 조용히.
```

> **그래서 순서 지정이 필요하고, 그 순서는 정의 단계에서만 의미가 있다. 조건 평가가 정의 단계에 일어나기 때문이다.**

**즉 순서와 조건이 한 쌍이다**:

```text
순서가 조건 평가의 입력이 된다
  → 순서가 바뀌면 조건 결과가 바뀐다
  → 조건 결과가 바뀌면 어떤 빈이 등록되는지가 바뀐다
```

**c4-02 Q3의 "빈 조건만 순서에 민감하다"가 여기서 실무 문제가 된다** — **클래스·프로퍼티 조건만 쓴다면 순서 지정이 필요 없다.**

**"조용히"가 이 문제의 성질이다** — 조건 불통과는 **예외를 내지 않는다.** 그냥 빈이 없고, 나중에 **"빈을 찾을 수 없다"**로 나타난다([[04-condition-evaluation-report]] Q1).

## Q4. 순서를 정하는 세 수단과 각각의 상황

**① `@AutoConfiguration`의 속성**

```java
@AutoConfiguration(after = DataSourceAutoConfiguration.class)
```

공식 문서: 설정이 특정 순서로 적용돼야 하면 **`before`·`beforeName`·`after`·`afterName`** 속성을 쓴다.

**이유**: **자동 구성 선언과 순서 선언을 한 자리에 두어 흩어지지 않게 하기 위해서다.**

**② 전용 애노테이션 `@AutoConfigureBefore`·`@AutoConfigureAfter`**

**같은 역할**이며, **애노테이션을 분리해 쓰는 기존 스타일을 유지**하기 위한 것이다.

**③ `@AutoConfigureOrder`**

문서 표현으로 **서로를 직접 알지 못하는** 자동 구성들의 순서를 정할 때 쓰며, **일반 `@Order`와 같은 의미이되 자동 구성 전용 순서**를 제공한다.

**언제 필요한가**: **상대 클래스 이름을 참조할 수 없는 경우** — **순환 의존이 되거나 클래스패스에 없을 수 있는 경우**에도 순서를 표현해야 한다.

**정리**:

| 수단 | 쓰는 상황 |
|---|---|
| `@AutoConfiguration(after=...)` | **상대를 알고 클래스 참조가 가능** — 기본 |
| `@AutoConfigureAfter` | 같음. 스타일 차이 |
| `afterName`(문자열) | **상대 클래스가 클래스패스에 없을 수 있을 때**(Q5) |
| `@AutoConfigureOrder` | **상대를 모를 때** — "나는 그냥 늦게" |

## Q5. `beforeName`·`afterName`이 문자열을 받는 이유

**상대 클래스가 클래스패스에 없을 수 있기 때문이다.**

```java
// 클래스 참조 — 그 클래스가 없으면 NoClassDefFoundError
@AutoConfiguration(after = SomeOptionalAutoConfiguration.class)

// 이름 참조 — 없어도 안전
@AutoConfiguration(afterName = "com.example.SomeOptionalAutoConfiguration")
```

**c4-02 Q4의 같은 문제다** — **애노테이션 값이 `Class` 객체인데 그 클래스가 없으면 읽는 순간 터진다.**

**자동 구성 순서에서 이 상황이 흔한 이유**:

```text
내 스타터가 "Redis 자동 구성 뒤에" 놓이고 싶다
  → 그런데 사용자가 Redis 를 안 쓸 수도 있다
  → RedisAutoConfiguration 이 클래스패스에 없다
  → 클래스 참조를 쓰면 내 스타터가 통째로 못 뜬다
  → 이름으로 지정하면 "없으면 그 제약이 없는 것으로" 처리된다
```

**즉 선택적 순서 제약을 표현하는 수단이다** — **"있으면 그 뒤에, 없으면 상관없이"**.

**c4-01 Q7의 `excludeName`과 같은 이유다** — **클래스가 클래스패스에 없을 때는 문자열로.** Boot 전반에서 반복되는 패턴이다.

**§2.3의 클래스 조건 처리와도 같은 원리다** — **애노테이션 메타데이터를 바이트코드에서 문자열로 읽는다.** 이름 기반 지정은 그 처리 방식과 자연스럽게 맞는다.

## Q6. 사용자 빈이 먼저 처리된다는 보장이 없으면

**백오프가 성립하지 않는다.**

```text
① @ComponentScan 으로 발견된 사용자 빈 정의
② @Configuration 클래스의 @Bean 정의
   ─────────── 여기까지가 사용자 영역 ───────────
③ 자동 구성 후보들 (자기들끼리는 @AutoConfigureBefore/After 순서)
```

**공식 문서가 이를 보장으로 명시한다** — 빈 조건을 자동 구성 클래스에만 쓰라고 권하는 근거가 *"자동 구성 클래스는 어떤 사용자 정의 빈 정의든 추가된 **뒤에** 로드되는 것이 보장되기 때문"*이다.

**보장이 없다면**:

```text
자동 구성이 먼저 처리될 수도 있다
  → @ConditionalOnMissingBean 이 "없다"로 통과
  → 자동 구성 DataSource 가 등록된다
  → 그 뒤에 사용자 DataSource 도 등록된다
  → 빈이 둘이 된다 → NoUniqueBeanDefinitionException
  → 또는 실행마다 결과가 달라진다
```

**즉 백오프의 전제가 이 경계다** — **"내가 평가할 때는 사용자 빈이 이미 다 와 있다"**가 보장돼야 `@ConditionalOnMissingBean`이 의미를 갖는다.

**반대 방향도 이 그림으로 설명된다**(c4-02 Q6):

> **사용자 코드에서 같은 조건을 쓰면 ①·② 단계라 자동 구성 것이 아직 없어 의미가 없다.**

**§6**: **애플리케이션 코드의 `@Configuration`에 `@AutoConfigureAfter`를 붙이지 않는다.** **자동 구성 클래스 전용이며, 사용자 설정은 이미 자동 구성보다 먼저 처리된다.**

## Q7. 생성 순서를 강제해야 할 때의 선택지 넷과 정석

**Q2의 표 그대로이고, 정석은 "의존성으로 표현"이다.**

| 방법 | 어떻게 | 언제 |
|---|---|---|
| **의존성으로 표현** | **생성자 인자로 받는다** | **대부분 — 정석** |
| `@DependsOn` | 이름으로 선행 빈 지정 | **의존성이 코드에 안 드러나는 경우**(정적 초기화 등) |
| `SmartLifecycle` | 컨테이너 시작 후 단계별 실행 | 컨테이너 전체가 준비된 뒤여야 할 때 |
| `ApplicationRunner` | 모든 빈 완성 후 1회 실행 | **시작 작업** |

**왜 의존성이 정석인가**:

- **코드에 드러난다** — 시그니처를 보면 무엇이 먼저 필요한지 안다
- **컴파일러가 돕는다** — 타입이 맞아야 한다
- **추가 애노테이션이 없다** — 이미 있는 메커니즘을 쓴다
- **순환이면 즉시 실패한다**(c1-04) — 잘못된 설계가 기동에서 잡힌다

**`@DependsOn`이 필요한 경우**: **의존성이 코드에 안 드러날 때.** 예를 들어 A가 정적 초기화 블록에서 B가 설정한 시스템 프로퍼티를 읽는다면, **타입 의존이 없는데 순서 의존은 있다.** 그때만 이름으로 지정한다.

**`SmartLifecycle`과 `ApplicationRunner`는 층이 다르다** — **빈 생성 순서가 아니라 "컨테이너가 완성된 뒤 무엇을 언제 할지"**다.

**§6**: **초기화 콜백에서 다른 빈의 완성 상태를 가정하지 않는다. 시작 작업은 `ApplicationRunner`로 옮긴다.**

## Q8. `@Order`와 `@AutoConfigureOrder`를 구분해야 하는 이유

**대상이 다르고, 자동 구성 클래스에 `@Order`를 붙이면 의도한 효과가 안 난다.**

| 축 | **`@Order`** | **`@AutoConfigureOrder`** |
|---|---|---|
| 대상 | **같은 타입 빈들의 정렬** | **자동 구성 클래스의 처리 순서** |
| 예 | **인터셉터·필터·`BeanPostProcessor`** | 자동 구성 후보 |
| 단계 | 주로 **사용 시점** | **정의 단계** |

**§5**: **자동 구성 클래스에 `@Order`를 붙이면 의도한 효과가 안 난다. 접두어가 붙은 쪽을 쓴다.**

**이름을 나눈 이유**(§2.5):

> **이름을 나누지 않았다면 한 클래스에 붙은 `@Order`가 두 가지 의미로 해석될 수 있었다. 접두어가 그 모호함을 없앤다.**

```text
자동 구성 클래스도 결국 빈이다
  → @Order 를 붙이면 "빈으로서의 정렬 순서"로 해석될 수 있다
  → 그런데 우리가 원하는 것은 "자동 구성으로서의 처리 순서"다
  → 두 의미를 한 애노테이션이 감당할 수 없다
  → 이름을 나눈다
```

**`@AutoConfigureBefore`/`@AutoConfigureAfter`의 접두어도 같은 역할이다** — **`AutoConfigure` 접두어가 범위를 말한다.**

**c1-02 Q8과 이어진다** — 거기서도 `Ordered`가 **어떤 경우에는 무시된다**(프로그래밍 방식 등록). **순서 애노테이션은 "어느 메커니즘의 순서인가"를 항상 확인해야 한다.**

**§6**: **`@Order`와 `@AutoConfigureOrder`를 혼용하지 않는다. 층이 다르다.**

## Q9. `@AutoConfigureAfter`와 `@DependsOn`이 답하는 질문

| 축 | **`@AutoConfigureAfter`** | **`@DependsOn`** |
|---|---|---|
| **정하는 것** | **정의 순서** | **생성 순서** |
| 대상 | **자동 구성 클래스** | **빈** |
| 지정 방식 | 클래스·이름 | **빈 이름** |
| **조건 평가에 영향** | **있다** | **없다** |

**§5의 판별 문장**:

> **"내 빈이 저 빈보다 나중에 만들어져야 한다"면 `@DependsOn`(또는 그냥 의존성)이고, "내 조건이 저 자동 구성의 결과를 봐야 한다"면 `@AutoConfigureAfter`다.**

**두 질문을 다르게 물어야 한다**:

```text
@AutoConfigureAfter : "내가 평가될 때 저것의 빈 정의가 있어야 하는가?"
                      → 조건 평가를 위한 것
@DependsOn          : "내가 만들어질 때 저것이 이미 존재해야 하는가?"
                      → 초기화 순서를 위한 것
```

**"조건 평가에 영향" 행이 결정적이다** — `@DependsOn`은 **정의가 이미 다 끝난 뒤**의 이야기이므로 **조건 결과를 바꾸지 못한다.** 조건이 불통과해서 빈이 없다면 `@DependsOn`을 아무리 붙여도 소용없다.

**출발 장면이 이 혼동이었다** — `@AutoConfigureAfter`로 **초기화 순서**를 정하려 했다. **답하는 질문이 다르다.**

## Q10. 순서를 지정했는데 조건이 불통과라면

**순서 문제가 아닐 가능성이 크다. 클래스 조건이나 프로퍼티 조건에서 이미 걸렸을 수 있다.**

**§5**:

> **추측하지 말고 [[04-condition-evaluation-report]]로 확인한다 — 어느 조건이 왜 불통과했는지 문장으로 나온다.**

**§6의 우선순위**:

> **순서로 해결하려 하기 전에 조건을 의심한다. 대부분의 "왜 안 되지"는 순서가 아니라 조건 불통과다.**

**확인 순서**:

```text
1. 보고서의 negativeMatches 에서 그 자동 구성을 찾는다
2. condition 값을 본다
     OnClassCondition    → 클래스패스 문제. 의존성을 확인한다
     OnPropertyCondition → 프로퍼티 문제. 설정을 확인한다
     OnBeanCondition     → 여기서야 순서 문제일 수 있다
3. OnBeanCondition 이 아니면 순서는 원인이 아니다
```

**순서가 원인일 때만 순서를 고친다.** 클래스 조건에서 걸렸는데 `@AutoConfigureAfter`를 아무리 조정해도 **아무것도 안 바뀐다.**

**또 하나의 가능성 — 순환 순서**(§5):

> **A가 B 뒤에, B가 A 뒤에 오라고 하면 순서를 정할 수 없다.** c1의 순환 참조와 같은 형태의 문제이며, **대개 공통 부분을 제3의 자동 구성으로 빼는 것이 답이다.**

**c1-04 Q8의 해법과 같다** — **추출이 정석이다.**

**§6의 예방**: **순서 지정을 촘촘히 쌓지 않는다.** **자동 구성 간 순서 제약이 늘수록 스타터를 조합했을 때 순환이 생기기 쉽다.**
