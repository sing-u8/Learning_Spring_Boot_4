## Q1. 내 `DataSource` 빈을 만들면 자동 구성 것이 사라지는 과정 — "우선순위" 없이

**`DataSourceAutoConfiguration`의 `@Bean` 메서드에 `@ConditionalOnMissingBean`이 붙어 있고, 조건 평가 시점에 이미 `DataSource` 타입의 빈 정의가 있었으므로 조건이 불통과했다. 그래서 그 `@Bean` 메서드는 빈 정의로 등록조차 되지 않았다.**

```text
① 사용자 설정의 빈 정의가 먼저 등록된다   → DataSource 정의 있음
② 자동 구성 후보를 순서대로 처리한다
③ DataSourceAutoConfiguration 의 @Bean 에 @ConditionalOnMissingBean
   → 지금까지 등록된 정의에 DataSource 가 있다
   → 조건 불통과
④ 그 @Bean 메서드는 빈 정의로 등록되지 않는다
   → 애초에 하나만 만들어진다
```

**공식 문서는 이 성질을 자동 구성의 정체성으로 규정한다** — 자동 구성은 **비침습적(non-invasive)**이며, **자기 `DataSource` 빈을 추가하면 기본 내장 데이터베이스 지원이 물러난다.**

**비유와 그 한계 — "우산이 없으면 사 온다"는 규칙**: 집에 우산이 있으면 안 사 온다. **이건 "집에 있는 우산을 더 좋아해서"가 아니라 조건문이 그렇게 생겼기 때문이다.** **규칙에는 우산의 품질을 비교하는 부분이 아예 없다.**

→ **깨지는 지점**: 사람은 **집 우산이 부러진 걸 보면 규칙을 어기고 새로 산다.** 조건 평가에는 그런 판단이 없다 — **내 `DataSource`가 잘못 설정돼 있어도 자동 구성은 그대로 물러난다.** **조건은 "있는가"만 보고 "쓸 만한가"는 보지 않는다**(Q10, §5).

**설계의 우아함**(§1): **조건 하나로 "기본값 제공"과 "사용자 우선"을 동시에 표현한다**:

- **자동 구성의 관점**: "없으면 내가 만들어 준다" → **편의성**
- **사용자의 관점**: "내가 만들면 넌 빠져라" → **제어권**

> **같은 한 줄이 둘 다다. 별도의 override 메커니즘도, 우선순위 설정도 필요 없다.**

## Q2. 빈이 두 개 생겼다가 하나가 선택되는 것이 아니라는 증거

**"우선순위"가 있으려면 두 빈이 모두 존재하고 그중 하나를 고르는 단계가 있어야 하는데, 그런 단계가 없다.**

**확인 방법 셋**:

| 방법 | 무엇을 보나 |
|---|---|
| **`ApplicationContext`의 `DataSource` 타입 빈 개수** | **1개다.** 2개였다가 하나가 선택된 게 아니다 |
| **[[04-condition-evaluation-report]]** | `negativeMatches`에 `DataSourceAutoConfiguration#dataSource`가 **불통과 이유와 함께** 나온다 |
| **`@Primary`가 필요 없다** | 두 개면 필요했을 것이다(§5) |

**"우선순위 모델"이었다면 나왔어야 할 것들이 없다**:

- **우선순위를 적는 곳이 없다** — 어디에도 "사용자 빈이 우선"이라는 설정이 없다
- **`NoUniqueBeanDefinitionException`이 안 난다** — 두 개면 났어야 한다
- **자동 구성 빈을 이름으로 꺼낼 수 없다** — 존재하지 않으니까

**§5의 진단 규칙**:

> **`@Primary`가 필요하다는 것은 대개 백오프가 안 됐다는 신호다. 자동 구성이 물러났다면 애초에 하나뿐이라 `@Primary`가 필요 없다.**

**즉 `@Primary`를 붙이고 싶어졌다면 "왜 백오프가 안 됐는가"를 먼저 물어야 한다** — 대개 **타입이 다르거나**(Q9), **사용자 설정이 자동 구성보다 나중에 처리되는 구조**(c4-03)다.

## Q3. 조건 애노테이션 중 순서에 민감한 것

**빈 조건(`@ConditionalOnBean`, `@ConditionalOnMissingBean`)이다.**

| 무리 | 애노테이션 | 무엇을 보나 | **순서에 민감한가** |
|---|---|---|---|
| 클래스 | `@ConditionalOnClass`, `@ConditionalOnMissingClass` | 클래스패스 | **아니다** |
| **빈** | **`@ConditionalOnBean`, `@ConditionalOnMissingBean`** | **지금까지 등록된 빈 정의** | **매우 그렇다** |
| 프로퍼티 | `@ConditionalOnProperty` 등 | `Environment` 값 | 아니다 |
| 리소스 | `@ConditionalOnResource` | 파일·클래스패스 리소스 | 아니다 |
| 웹 | `@ConditionalOnWebApplication` 등 | 애플리케이션 타입 | 아니다 |
| 표현식 | `@ConditionalOnExpression` | SpEL 결과 | **경우에 따라** |

**왜 빈 조건만 민감한가**:

> **등록된 빈 정의는 평가하는 시점마다 달라진다.**

**공식 문서의 경고**: *"빈 정의가 추가되는 순서에 매우 주의해야 한다. 이 조건들은 **지금까지 처리된 것을 기준으로** 평가되기 때문이다."*

**그래서 순서 보장이 필요하고**, 그것이 [[03-autoconfiguration-ordering-and-user-precedence]]의 주제다.

**`@ConditionalOnExpression`이 "경우에 따라"인 이유** — SpEL 안에서 무엇을 참조하느냐에 달렸다. 프로퍼티만 보면 무관하고, 빈을 참조하면 민감해진다. **§6은 이 애노테이션 자체를 남용하지 말라고 한다** — **SpEL은 컴파일 시점 검증이 없어 오타가 런타임까지 간다.**

## Q4. 클래스 조건이 순서와 무관한 이유

**클래스패스는 시작 내내 바뀌지 않으므로 언제 평가하든 답이 같다.**

```text
빈 정의   : 처리가 진행되면서 계속 늘어난다  → 시점에 따라 답이 다르다
클래스패스: 시작 시 고정된다                → 언제 물어도 같은 답
```

**그래서 클래스 조건은 자동 구성의 첫 관문으로 쓸 수 있다**:

```java
@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
public class DataSourceAutoConfiguration { ... }
```

**이 조건이 없다면** — JDBC를 안 쓰는 애플리케이션에서도 이 클래스가 로드되면서 **`DataSource` 타입을 참조하려다 `NoClassDefFoundError`가 난다.**

**여기에 닭과 달걀이 있다**(§2.3):

> **조건을 읽으려면 애노테이션을 읽어야 하고, 애노테이션 값이 `Class` 객체인데 그 클래스가 없다면? 리플렉션으로 읽는 순간 터진다.**

**Spring의 해법 — 애노테이션 메타데이터를 바이트코드에서 읽는다**:

> **애노테이션에 적힌 값을 `Class` 객체가 아니라 클래스 이름 문자열로 꺼내므로, 없는 클래스를 참조해도 읽는 단계에서는 아무 일도 일어나지 않는다. 그다음 그 이름이 클래스패스에 있는지만 확인한다.**

**정확한 표현**: **"아무것도 로드하지 않는다"가 아니라 "자동 구성 클래스 자신을 로드하지 않고도 판정할 수 있다"**이다. **조건이 불통과하면 그 설정 클래스는 끝까지 로드되지 않고, 그래서 `NoClassDefFoundError`가 나지 않는다.**

**이 성질이 만드는 경험**:

> **스타터를 추가하는 것 = 클래스패스에 클래스가 생기는 것 = 클래스 조건이 통과하는 것.**

## Q5. 빈 조건을 자동 구성 클래스에만 쓰라는 이유 — 시간축으로

**공식 문서**: *"이런 이유로 `@ConditionalOnBean`과 `@ConditionalOnMissingBean` 애노테이션은 **자동 구성 클래스에만** 사용할 것을 권한다 — 자동 구성 클래스는 **어떤 사용자 정의 빈 정의든 추가된 뒤에** 로드되는 것이 보장되기 때문이다."*

**시간축**:

```text
①  사용자 설정의 빈 정의가 전부 등록된다
     @Component 스캔, @Configuration 의 @Bean
     ↑ 여기서는 자동 구성이 아직 아무것도 등록하지 않았다

②  자동 구성 후보들이 순서대로 처리된다
     ↑ 여기서는 사용자 빈 정의가 전부 확정돼 있다

③  각 후보의 조건을 평가한다 — 빈 조건은 이 시점까지 등록된 정의를 본다

④  통과한 것의 @Bean 메서드가 빈 정의로 등록된다

⑤  모든 정의가 확정된 뒤에야 인스턴스가 만들어진다  ← c1 의 정의/인스턴스 구분
```

**②에 있으면 안전하고, ①에 있으면 위험하다.**

**조건 평가가 두 국면으로 나뉜다**(노트의 추가 설명):

> Spring은 조건 평가 시점을 두 국면으로 구분한다 — **설정 클래스를 파싱하는 국면**과, **빈 정의를 등록할지 판정하는 국면**이다. **`OnBeanCondition`은 뒤쪽 국면에서만 평가된다** — 어떤 빈 정의가 모였는지 알아야 "없다"를 판정할 수 있기 때문이다. **클래스·프로퍼티 조건은 앞쪽에서도 평가될 수 있다.**

**이 구분이 "지금까지 처리된 것을 기준으로"에 구체적인 이름을 준다.** 책 트랙 `chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans`가 이 두 국면을 이름으로 짚는다.

## Q6. 사용자 코드의 `@ConditionalOnMissingBean`이 항상 통과하는 이유

**사용자 설정은 ①단계에 처리되는데, 그때는 자동 구성이 아직 아무것도 등록하지 않았기 때문이다.**

```java
// 사용자 코드 — 의도: "자동 구성이 만든 게 없으면 내가 만들겠다"
@Configuration
class MyConfig {
    @Bean
    @ConditionalOnMissingBean          // ❌ 항상 통과한다
    DataSource dataSource() { ... }
}
```

```text
① 사용자 설정 처리 중
   → 이 시점에 DataSource 정의가 있는가?
   → 자동 구성은 아직 시작도 안 했다
   → 없다 → 조건 통과 → 내 빈이 등록된다

② 자동 구성 처리
   → 내 DataSource 가 이미 있다
   → 자동 구성이 백오프한다

결과: 항상 내 빈이 이긴다. 조건은 아무 역할도 안 했다.
```

> **"자동 구성이 만든 빈이 없으면 내가 만들겠다"는 의도로 쓰면 항상 조건이 통과해 의도와 반대로 동작한다.**

**"반대로"가 정확한 표현이다** — 의도는 **"자동 구성을 존중하겠다"**였는데, 실제로는 **"항상 자동 구성을 밀어낸다"**가 된다.

**§6**: **사용자 코드에 `@ConditionalOnMissingBean`을 쓰지 않는다.**

**그럼 "자동 구성이 만든 게 없을 때만"을 어떻게 표현하나** — **표현할 필요가 없다.** 백오프가 이미 그 일을 한다. **내 빈을 그냥 정의하면 자동 구성이 물러난다.** 조건을 붙이는 것 자체가 **메커니즘을 오해한 결과**다.

## Q7. 클래스 레벨 조건과 메서드 레벨 조건의 차이

**공식 문서**: *"`@ConditionalOnBean`과 `@ConditionalOnMissingBean`은 `@Configuration` 클래스가 **생성되는 것 자체를 막지는 않는다.** 클래스 레벨에서 이 조건을 쓰는 것과 포함된 각 `@Bean` 메서드에 애노테이션을 붙이는 것의 **유일한 차이는, 전자는 조건이 맞지 않을 때 `@Configuration` 클래스가 빈으로 등록되는 것을 막는다**는 점이다."*

| 위치 | 효과 | 언제 |
|---|---|---|
| **클래스 레벨** | 조건 불통과 시 **설정 클래스 자체가 빈으로 등록 안 됨** | **그 설정 전체가 무의미할 때** |
| **메서드 레벨** | **그 `@Bean`만** 등록 안 됨 | **일부만 대체 가능하게 할 때** |

**Boot가 메서드 레벨을 많이 쓰는 이유**:

> **사용자가 `DataSource`만 직접 만들고 나머지(트랜잭션 매니저 등)는 자동 구성에 맡기는 부분 대체가 가능해야 하기 때문이다.**

```text
[클래스 레벨이었다면]
  DataSource 를 직접 만든다
  → DataSourceAutoConfiguration 전체가 물러난다
  → 트랜잭션 매니저, 초기화 스크립트 실행 등도 함께 사라진다
  → 전부 직접 만들어야 한다

[메서드 레벨]
  DataSource 를 직접 만든다
  → dataSource() 메서드만 물러난다
  → 나머지는 그대로 등록된다
  → 내 DataSource 를 받아서 동작한다 ✅
```

**이것이 "비침습적"의 실제 내용이다** — **필요한 것만 바꾸고 나머지는 그대로 쓸 수 있다.**

## Q8. 백오프·`@Primary`·`exclude`가 각각 만드는 빈 개수

| 축 | **백오프** | **`@Primary`** | **`exclude`** |
|---|---|---|---|
| **빈이 몇 개 생기나** | **1개** | **2개 이상** | **1개(내 것)** |
| 언제 작동 | 조건 평가 **중** | **주입 시점** | 후보 수집 **직후** |
| 자동 구성이 | **물러남** | **그대로 등록됨** | **목록에서 제거됨** |
| 쓸 때 | **기본값 대체** | 여러 개가 정말 필요할 때 | **기능 자체 제거** |

**`@Primary`만 2개 이상인 것이 핵심이다**:

```text
백오프  : 자동 구성 빈이 애초에 안 만들어진다        → 1개
@Primary: 자동 구성 빈도 만들어지고 내 것도 만들어진다 → 2개
          주입할 때 @Primary 붙은 쪽을 고른다
exclude : 자동 구성 후보가 목록에서 빠진다           → 1개
```

**`@Primary`의 대가**(§6):

> **`@Primary`로 백오프를 대체하지 않는다. 빈이 둘 생겨 자원이 낭비되고, 어느 것이 쓰이는지 추적이 어려워진다.**

**`DataSource`가 둘이면** — **커넥션 풀이 둘 열린다.** 안 쓰는 쪽도 커넥션을 잡고 있다.

**세 층이 서로 다른 시점에 작동한다는 점도 중요하다**:

```text
후보 수집 → [exclude] → 순서 결정 → [백오프] → 정의 등록 → 인스턴스화 → [@Primary]
```

**앞쪽일수록 근본적이다** — `exclude`는 평가조차 안 하고, 백오프는 평가해서 물러나고, `@Primary`는 만들고 나서 고른다.

## Q9. 빈 이름이 달라도 백오프가 되는 이유

**`@ConditionalOnMissingBean`의 기본 판정 기준이 타입이기 때문이다.**

```java
@Bean
public DataSource myConnectionPool() { ... }   // 이름이 dataSource 가 아니다
```

**그래도 백오프가 일어난다** — 조건은 **"`DataSource` 타입의 빈 정의가 있는가"**를 묻지 **"`dataSource`라는 이름의 빈이 있는가"**를 묻지 않는다.

**§5**: **`name` 속성으로 이름 기준 판정을 지정할 수도 있지만 기본은 타입이다.**

**왜 타입이 기본인가** — **자동 구성은 사용자가 어떤 이름을 쓸지 알 수 없다.** 이름 기준이라면 **"`dataSource`라는 이름으로 만들어야 백오프됩니다"**라는 규약을 문서화해야 하고, 사용자가 그것을 지켜야 한다. **타입 기준이면 규약이 필요 없다.**

**c3-01 Q5의 **특수 빈 타입**과 같은 원리다** — **타입으로 찾으면 이름이나 위치에 의존하지 않는다.**

**대가**: **타입이 정확히 맞아야 한다.** 내가 `HikariDataSource`를 반환 타입으로 선언하면(구현 타입), `DataSource` 조건이 여전히 매칭될지는 **선언된 타입을 어떻게 해석하느냐**에 달린다. **반환 타입을 인터페이스로 선언하는 것이 안전하다.**

**백오프가 안 될 때 첫 번째로 확인할 것이 이것이다**(Q2) — **타입이 정말 같은가.**

## Q10. "back off"라는 이름이 만드는 오해

**"물러난다"는 말이 행위자가 판단해서 양보한다는 인상을 준다. 실제로는 아무도 판단하지 않는다 — 조건문의 결과일 뿐이다.**

> **back off는 "물러서다·손을 떼다"라는 뜻의 일상 표현이다. 공식 문서가 쓰는 *"backs away"*도 같은 뉘앙스다. 싸워서 진 것이 아니라 자리를 비켜 준다는 어감이다.**

**오해가 만드는 잘못된 질문들**(§1의 세 질문):

| 오해에서 나오는 질문 | 조건 모델의 답 |
|---|---|
| "그 우선순위는 어디에 적혀 있나?" | **우선순위가 없다.** 조건 하나다 |
| "이름이 달라도 물러나나?" | **타입 기준이므로 물러난다**(Q9) |
| "내 빈이 `@Lazy`거나 prototype이면?" | **존재하면 불통과다.** 성질을 안 본다 |

**§5**: **조건은 품질을 보지 않는다.** **그 빈이 잘못 설정돼 있어도, `@Lazy`여도, prototype이어도 존재하면 조건은 불통과**한다. **자동 구성이 "더 나은 대안"으로 다시 들어오는 일은 없다.**

> **이름이 은유이고 메커니즘은 조건이라는 것을 구분해야 앞의 세 질문에 답할 수 있다.**

**이 챕터 전체의 교훈이기도 하다** — **Spring의 이름들은 대개 좋은 은유이지만**(c3-03 Q10의 `Resolver`/`Handler`, c4-01 Q9의 `imports`), **은유는 메커니즘이 아니다.** 이름이 **어디까지 맞고 어디서 틀리는지**를 아는 것이 정확한 이해다.

**§6의 마지막 줄이 실무 처방이다**:

> **조건이 왜 불통과했는지 추측하지 않는다. [[04-condition-evaluation-report]]가 이유를 문장으로 알려 준다.**
