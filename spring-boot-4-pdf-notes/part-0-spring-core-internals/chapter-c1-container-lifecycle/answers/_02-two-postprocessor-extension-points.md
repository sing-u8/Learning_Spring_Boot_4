## Q1. 확장점이 두 개여야 하는 이유 — "고치는 대상"으로

**고치는 대상이 다르고, 대상이 다르니 개입할 수 있는 시점도 다르기 때문이다.**

| | **`BeanFactoryPostProcessor`** | **`BeanPostProcessor`** |
|---|---|---|
| **고치는 대상** | **빈 정의 (메타데이터)** | **빈 인스턴스 (객체)** |
| 언제 | **어떤 빈도 만들어지기 전** | **빈이 만들어진 직후** |
| 몇 번 | 컨테이너당 한 번, **정의 전체**에 | **빈 하나마다** |
| 대표 예 | `PropertySourcesPlaceholderConfigurer` | AOP 자동 프록시 생성기 |
| 할 수 있는 일 | 정의 추가·삭제·**값 교체** | **감싸기**·검사·교체 |

**하나로 둘 수 없는 이유**:

```text
${jdbc.url} 치환    → 생성자 인자로 쓰이기 전에 끝나야 한다
                       → 객체가 없는 시점에 개입해야 한다

@Transactional 프록시 → 감쌀 대상 객체가 있어야 한다
                       → 객체가 생긴 뒤에 개입해야 한다

  두 요구가 시간축의 반대편에 있다. 한 확장점으로는 둘 다 못 한다.
```

**"고치는 대상"이 시점을 결정한다** — **정의를 고치려면 정의만 있으면 되고(객체는 없어야 한다), 객체를 고치려면 객체가 있어야 한다.**

**이름이 그 구분을 담고 있다**(§5): **`Factory`가 붙은 쪽이 "공장을 손본다" = 정의를 손본다**로 읽으면 갈린다.

| 축 | `BeanFactoryPostProcessor` | `BeanPostProcessor` |
|---|---|---|
| 이름의 뜻 | 빈 **팩터리**를 후처리 | **빈**을 후처리 |
| 인자로 받는 것 | `ConfigurableListableBeanFactory` (**전체**) | `Object bean, String beanName` (**하나**) |
| 호출 횟수 | 컨테이너당 1회 | **빈 개수만큼** |
| 반환 | `void` | **`Object` — 바꿔치기 가능** |

## Q2. `${}` 치환이 `BeanFactoryPostProcessor`인 이유

**치환된 값이 생성자 인자로 쓰이므로, 객체가 만들어지기 전에 확정돼야 하기 때문이다.**

**BFPP의 계약**(공식 문서):

> *"컨테이너가 **`BeanFactoryPostProcessor` 인스턴스 외의** 어떤 빈도 인스턴스화하기 전에, 설정 메타데이터를 읽고 잠재적으로 변경할 수 있게 해 준다."*

**"BFPP 외의"라는 단서가 핵심이다** — **후처리기 자신은 만들어져야 일을 할 수 있으니 예외가 된다.**

**5단계**:

1. **컨테이너가 빈 정의를 전부 모은다** — 일부만 모인 상태에서 고치면 **뒤에 올 정의를 못 본다**
2. **BFPP 타입의 빈만 먼저 만든다** — 정의를 고칠 주체 자신은 **객체여야 일할 수 있다**
3. **각 BFPP에 레지스트리를 통째로 넘긴다** — 개별 빈이 아니라 **정의 전체**를 봐야 "이 이름이 이미 있는가" 같은 판단이 가능하다
4. **BFPP가 정의를 고친다** — `${jdbc.url}` 자리를 실제 값으로. **그 값이 생성자 인자로 쓰이기 전에 확정돼야** 한다
5. **그다음에야 나머지 빈을 만든다** — **확정된 정의로만** 객체를 찍기 위해

**만약 BPP였다면** — 빈이 이미 만들어진 뒤에 받는다. 생성자에는 이미 `"${jdbc.url}"`이라는 **글자 그대로의 문자열**이 들어가 있고, `final` 필드라면 바꿀 수도 없다.

**공식 문서의 금지 사항**: BFPP 안에서 `BeanFactory.getBean()`으로 빈 인스턴스를 다루는 것이 *"기술적으로는 가능하지만, **이른 빈 인스턴스화를 유발해 표준 컨테이너 생명주기를 위반한다**"*. **Q3의 함정이 정확히 이 위반의 결과다.**

## Q3. `@Transactional`이 붙었는데 트랜잭션이 안 열리는 시나리오

**두 사실을 이어 붙이면 나온다.**

**① `@Transactional` 프록시는 빈 후처리기가 만든다**

공식 문서: *"AOP 자동 프록시 생성 자체가 `BeanPostProcessor`로 구현돼 있다."* **프록시는 마법이 아니라 "만들어진 빈을 받아서 감싼 것을 대신 돌려주는" 후처리 작업이다.**

**② 후처리기는 남들보다 먼저 만들어져야 한다**

공식 문서: *"모든 `BeanPostProcessor` 인스턴스와 **그것이 직접 참조하는 빈들**은 `ApplicationContext`의 특수한 시작 단계의 일부로 시작 시점에 인스턴스화된다."*

**순서를 따라가면**:

```text
① BFPP 를 만들고 실행한다                    — 정의를 확정하려고
② BPP 타입의 빈을 전부 만든다                — 나머지를 후처리하려면 먼저 존재해야
③ BPP 가 생성자로 참조하는 빈도 딸려 만들어진다
     ↑ SchemaSanityChecker 가 MaterialService 를 생성자에서 받는다
     ↑ MaterialService 가 여기서 만들어진다 — AOP 후처리기가 아직 등록되기 전에
④ BPP 들을 정렬해 등록한다
⑤ 이제부터 만들어지는 모든 빈이 등록된 BPP 전체를 거친다
     ↑ ③에서 딸려 만들어진 MaterialService 는 이 줄에 서지 못했다
```

**만들 사람이 아직 자리에 없으니 프록시가 씌워질 수 없다.**

공식 문서: *"`BeanPostProcessor` 인스턴스도, **그것이 직접 참조하는 빈도** 자동 프록시 대상이 될 수 없고 따라서 애스펙트가 위빙되지 않는다."*

**그리고 일반화한 문장도 있다**: *"더 일반적으로, **이 이른 단계에서 인스턴스화되는 어떤 빈이든** 모든 `BeanPostProcessor` 인스턴스에 의한 완전한 후처리 대상이 되지 못한다."*

**비유와 그 한계 — 개찰구를 설치하러 온 작업자**: 개찰구를 설치하려면 작업자가 **역 안에 먼저 들어가야** 한다. 작업자와 **작업자가 데리고 들어간 조수**는 개찰구를 통과하지 않은 채 안에 있게 된다.

→ **깨지는 지점**: 실제 역이라면 **나중에 한 번 나갔다 들어오면** 개찰구를 통과할 수 있다. 빈은 못 한다 — **싱글턴은 한 번 만들어지면 그것으로 끝이고, 나중에 다시 감쌀 기회가 없다.** 그래서 이 문제는 **"순서를 놓쳤다"가 아니라 "영구히 프록시 없이 산다"**가 된다.

## Q4. `is not eligible for getting processed by all BeanPostProcessors` 경고

**"이 빈은 특수 시작 단계에서 앞당겨 만들어졌고, 그래서 AOP 프록시를 받지 못했다"는 뜻이다.**

```text
Bean 'materialService' of type [com.cosmoroute.MaterialService] is not eligible
for getting processed by all BeanPostProcessors (for example: not eligible for auto-proxying)
```

**무엇을 의심해야 하나 — 세 가지를 순서대로**:

1. **이 빈이 어떤 `BeanPostProcessor`의 생성자 의존성인가?** — 가장 흔한 원인
2. **이 빈이 `BeanFactoryPostProcessor` 안에서 `getBean()`으로 꺼내졌는가?** — 공식 문서가 금지한 그것
3. **이 빈에 AOP 애노테이션이 붙어 있는가?** — 붙어 있다면 **그 애노테이션이 전부 무효**다

**3번이 실제 피해다** — `@Transactional`, `@Async`, `@Cacheable`, `@Validated`, 커스텀 애스펙트가 **전부 조용히 동작을 멈춘다.**

**이 로그가 특히 위험한 이유**:

> **에러가 아니라 정보 로그다. 대부분 그냥 지나간다. 그런데 이 한 줄이 "당신의 `@Transactional`은 지금 아무 일도 하지 않는다"는 뜻이다.**

**`INFO` 레벨이라 필터링에도 잘 걸리지 않고, 시작 로그의 다른 줄들 사이에 섞인다.** 그리고 **애노테이션은 소스에 그대로 있으므로 코드 리뷰에서도 안 보인다.**

**대응**: 원인이 1번이면 Q7의 `ObjectProvider`, 2번이면 `getBean()` 제거, 그리고 **애초에 후처리기가 필요한지부터 다시 묻는다**(§6).

## Q5. `BeanPostProcessor`의 반환 타입이 `Object`인 것이 결정적인 이유

**받은 빈과 다른 객체를 돌려줘도 되기 때문이다. 그게 프록시가 가능한 유일한 통로다.**

```java
public interface BeanPostProcessor {
    Object postProcessBeforeInitialization(Object bean, String beanName);
    Object postProcessAfterInitialization(Object bean, String beanName);
}
```

**`void`였다면 무엇이 불가능한가**:

```text
[반환 void]  후처리기는 받은 객체를 "고칠" 수만 있다
             필드를 세팅하거나 검사하거나 로그를 찍는다
             → 프록시로 감쌀 수 없다. 감싼 것을 돌려줄 통로가 없다

[반환 Object] 후처리기가 다른 객체를 돌려줄 수 있다
             → 컨테이너는 그때부터 원본이 아니라 그것을 그 이름의 빈으로 취급한다
             → 다른 빈에도 그것을 주입한다
```

**공식 문서의 표현대로 후처리기는 *"빈을 프록시로 감쌀 수 있다"*.**

> **이 반환값 하나가 **자동 프록시 생성기**가 존재할 수 있는 이유다.**

**`@Transactional`·`@Async`·`@Cacheable`이 전부 이 경로로 동작한다.** 어떻게 프록시를 만드는지는 c2의 주제다.

**§5의 대비 — 후처리기 vs 초기화 콜백**:

> 결정적 차이는 **누구의 코드인가**다. 초기화 콜백은 **그 빈 자신의 메서드**이고 자기 자신만 손댄다. 후처리기는 **제3자**이고 컨테이너의 모든 빈에 개입한다. **그래서 프록시로 감싸는 일은 후처리기만 할 수 있다 — 자기가 자기를 감쌀 수는 없다.**

**"자기가 자기를 감쌀 수 없다"가 왜 그런가** — 감싼다는 것은 **호출자에게 다른 객체를 주는 것**인데, 자기 자신은 **호출자에게 무엇을 줄지 결정하는 위치에 있지 않다.** 그 위치에 있는 것이 컨테이너이고, 컨테이너에 개입하는 통로가 후처리기의 반환값이다.

## Q6. `postProcessBeforeInitialization`의 "Before"는 무엇의 앞인가

**초기화 콜백의 앞이다. 빈 생성의 앞이 아니다.**

```text
빈 인스턴스화
   ↓
의존성 주입
   ↓
postProcessBeforeInitialization        ← 여기
   ↓
초기화 콜백 (@PostConstruct · afterPropertiesSet() · init 메서드)
   ↑ 이것이 "Initialization" 이다
   ↓
postProcessAfterInitialization         ← 그리고 여기
```

**두 메서드 다 빈이 이미 만들어진 뒤에 불린다.** 의존성 주입까지 끝난 객체를 받는다.

**§5**: **빈 생성 전이 아니다. 이미 만들어지고 의존성까지 주입된 빈을 받는다. 앞뒤의 기준은 초기화 콜백이다.**

**헷갈리면 무엇이 어긋나나** — "Before가 생성 전"이라고 읽으면 **"후처리기에서 객체가 만들어지는 것을 막을 수 있다"**고 생각하게 된다. 실제로는 **이미 만들어진 뒤**라 막을 수 없다. 그리고 **`bean` 인자에 객체가 들어온다**는 시그니처 자체가 이미 그 사실을 말하고 있다.

**정확한 위치는 [[03-bean-creation-and-lifecycle-callbacks]]에서 전체 순서와 함께 본다.**

**왜 두 지점인가** — `Before`는 **초기화가 아직 안 된 원본**을 보고, `After`는 **초기화가 끝난 완성품**을 본다. **프록시는 `After`에서 씌운다** — 초기화 콜백이 프록시가 아니라 원본에서 실행돼야 하기 때문이다.

## Q7. `ObjectProvider`가 함정을 피하는 원리

**참조를 들고 있을 뿐 즉시 만들지 않기 때문이다.**

```java
@Component
public class SchemaSanityChecker implements BeanPostProcessor {

    private final ObjectProvider<MaterialService> materialServiceProvider;   // 지연 조회

    public SchemaSanityChecker(ObjectProvider<MaterialService> provider) {
        this.materialServiceProvider = provider;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // 실제로 필요한 순간에 꺼낸다 — 그때는 이미 프록시가 씌워진 뒤다
        // materialServiceProvider.getObject().check(...)
        return bean;
    }
}
```

**Q3의 3단계를 피한다**:

```text
[생성자로 직접 주입]
  후처리기를 만들려면 MaterialService 가 있어야 한다
    → 특수 시작 단계에서 딸려 만들어진다
    → 프록시 없음 ❌

[ObjectProvider]
  후처리기를 만들 때 필요한 것은 Provider 객체뿐이다
    → MaterialService 는 만들어지지 않는다
    → 정상 순서를 밟아 프록시를 받는다 ✅
    → 나중에 getObject() 로 꺼내면 프록시가 온다
```

**핵심은 "생성자에서 참조하지 않는 것"이다.** `@Lazy`를 붙이는 것도 같은 원리다 — 프록시를 주입해 두고 **실제 접근 시점에** 진짜 빈을 해석한다.

**§6**: **후처리기에서 애플리케이션 빈을 생성자로 주입받지 않는다.** 받는 순간 **그 빈이 프록시를 잃는다.**

**더 나은 선택은 대개 후처리기를 쓰지 않는 것이다**:

> **시작 시 한 번 무언가를 하고 싶은 것뿐이라면 `ApplicationRunner`나 `@EventListener(ApplicationReadyEvent.class)`가 맞는 자리다. 그 시점에는 컨테이너가 이미 완성돼 있어 어떤 함정도 없다.**

**판별 질문**: *"모든 빈에 개입해야 하는가, 아니면 시작할 때 한 번 하고 싶은 것인가?"* 후자면 후처리기가 아니다.

## Q8. `Ordered`가 무시되는 경우

**프로그래밍 방식으로 추가한 `BeanPostProcessor`다.**

공식 문서: *"**프로그래밍 방식으로 추가된** `BeanPostProcessor` 인스턴스는 `Ordered` 인터페이스를 **존중하지 않는다.** 여기서는 **등록 순서가 실행 순서를 결정한다.**"*

```java
context.getBeanFactory().addBeanPostProcessor(myProcessor);
// ↑ 이렇게 꽂으면 order 를 아무리 지정해도 무시되고 꽂은 순서대로 돈다
```

| 등록 방식 | `Ordered` |
|---|---|
| **`@Component` / `@Bean`으로 등록** | **존중된다** |
| **`addBeanPostProcessor(...)`로 직접 꽂기** | **무시된다 — 등록 순서가 이긴다** |

**왜 그런가** — 빈으로 등록된 것들은 **컨테이너가 전부 모아서 정렬한 뒤** 등록한다(Q3의 4단계). 직접 꽂은 것은 **이미 등록된 목록에 순서대로 추가**되는 것이라 정렬 기회가 없다.

**순서가 왜 중요한가**(Q3의 4단계): **순서가 결과를 바꾼다 — 감싼 위에 또 감싸는 일이 생긴다.** 프록시 A가 씌운 위에 프록시 B가 씌워지면, 호출은 B → A → 원본 순서로 흐른다. 반대면 반대다.

**§6**: **프로그래밍 방식으로 등록한 BPP에 `Ordered`를 기대하지 않는다.**

**실무 대응**: 순서가 중요하면 **`@Bean`으로 등록하고 `Ordered`를 구현한다.** 직접 꽂아야 하는 상황이라면 **꽂는 순서를 코드에서 명시적으로 관리**해야 하고, 그건 유지보수 부담이다.

## Q9. 초기화 콜백과 후처리기의 결정적 차이

**누구의 코드인가.**

| 축 | **초기화 콜백** | **후처리기** |
|---|---|---|
| **누구의 코드** | **그 빈 자신의 메서드** | **제3자** |
| 개입 범위 | **자기 자신만** | **컨테이너의 모든 빈** |
| 반환 | `void` | **`Object` — 바꿔치기 가능** |
| 언제 | 그 빈이 만들어질 때 한 번 | 빈 개수만큼 |

**그래서 프록시로 감싸는 일은 후처리기만 할 수 있다**:

> **자기가 자기를 감쌀 수는 없다.**

**두 이유가 겹친다**:

**① 위치의 문제** — 감싼다는 것은 **컨테이너가 다른 빈에게 무엇을 줄지 바꾸는 것**이다. 빈 자신은 그 결정을 하는 위치에 있지 않다. `@PostConstruct` 메서드가 `return proxy;`를 할 수 있어도 **아무도 그 반환값을 받지 않는다.**

**② 논리의 문제** — 프록시는 **원본을 감싼 다른 객체**다. 원본 안에서 자기를 감싸려면 **이미 완성된 자기 자신**이 필요한데, 초기화 콜백은 **아직 완성 중**인 지점이다.

```text
초기화 콜백:  "나는 준비를 마쳤다"        — 자기 상태에 대한 선언
후처리기:     "이 빈 대신 이걸 써라"      — 컨테이너에 대한 지시
```

**이 구분이 실무에서 갖는 의미** — [[03-bean-creation-and-lifecycle-callbacks]]에서 보듯, **`@PostConstruct` 안에서 `@Transactional`이 안 먹는 이유**가 여기서 이미 예고된다. 초기화 콜백은 **프록시가 씌워지기 전**에 실행되는 **자기 자신의 메서드**이므로, 자기가 자기를 부르는 것과 같다.
