## Q1. 생성자 주입 순환 참조에서 시작이 실패하는 이유 — 생성자 호출의 계약으로

**계약은 하나다 — "생성자를 부르려면 인자가 이미 준비돼 있어야 한다."**

```text
MaterialService 를 만들려면  → 완성된 SubstanceService 가 필요하다
SubstanceService 를 만들려면 → 완성된 MaterialService 가 필요하다

어느 쪽을 먼저 시작해도 상대를 요구받고, 상대는 다시 나를 요구한다
```

**공식 문서의 표현대로 "고전적인 닭과 달걀"이다.**

**컴파일은 통과한다는 점이 중요하다** — **Java 문법으로는 아무 문제가 없다.** 문제는 **"이 두 객체를 만들 수 있는 순서가 존재하지 않는다"**는 것이고, **그건 컴파일러가 볼 수 없는 영역**이다.

**컨테이너는 런타임에 감지한다** — 생성 스택에 이미 올라온 빈을 다시 요구받으면 ****순환 참조****로 판정하고 `BeanCurrentlyInCreationException`을 던진다.

**비유와 그 한계 — 서로에게 먼저 서명하라고 요구하는 두 계약서**: A 문서는 "B가 서명된 뒤에만 유효", B 문서는 "A가 서명된 뒤에만 유효". **둘 다 규칙을 어기지 않았지만 아무도 첫 서명을 할 수 없다.**

→ **깨지는 지점**: 계약서는 사람이 합의하면 **"동시에 서명"**이라는 편법이 통한다. **객체 생성에는 그런 동시성이 없다** — JVM에서 생성자 호출은 **반드시 한 번에 하나씩, 순서대로** 일어난다. Spring이 뒤에서 쓰는 우회로(**조기 노출**)도 **"동시에"가 아니라 "미완성인 채로 먼저 넘긴다"**는 전혀 다른 타협이다.

## Q2. `BeanCurrentlyInCreationException`이라는 이름이 말하는 것

**"이 빈은 지금 생성 중입니다"** — **만들어 달라고 요청받은 빈이 이미 자기 생성 스택에 올라와 있다**는 뜻이다.

```text
createBean(materialService)          ← 스택에 올린다
  → 의존성 substanceService 필요
  → createBean(substanceService)     ← 스택에 올린다
      → 의존성 materialService 필요
      → materialService 는 이미 "생성 중" 상태다
      → BeanCurrentlyInCreationException 💥
```

**"CurrentlyInCreation"이 상황의 두 가지를 동시에 말한다**:

1. **그 빈이 존재하기 시작했다** — 생성 시도가 시작됐다
2. **그런데 아직 완성되지 않았다** — 줄 수 있는 상태가 아니다

**이름이 왜 좋은 진단인가** — "찾을 수 없다"(`NoSuchBeanDefinition`)나 "만들 수 없다"(`BeanCreationException`)가 아니다. **빈은 있고 만들 수도 있는데, 하필 지금 만드는 중**이라는 것이다. 그 사실 자체가 **재귀를 가리킨다.**

**감지하지 않으면 무슨 일이 나나** — **무한 재귀로 스택이 터진다.** `StackOverflowError`는 원인을 전혀 알려 주지 않는다. **명시적 예외로 잡는 것이 훨씬 낫다.**

**그리고 Boot가 한 겹 더 얹는다** — 실패 분석기가 사이클을 **사람이 읽을 수 있는 그림**으로 바꾼다:

```text
┌─────┐
|  materialService defined in file [.../MaterialService.class]
↑     ↓
|  substanceService defined in file [.../SubstanceService.class]
└─────┘
```

**예외 스택만으로는 어느 빈들이 고리를 이루는지 알 수 없기 때문이다.**

## Q3. setter 주입에는 있고 생성자 주입에는 없는 "틈"

**1단계(인스턴스화)와 2단계(프로퍼티 주입) 사이다.**

```text
[생성자 주입]
  1. 인스턴스화 ─── 이 안에서 의존성이 필요하다
     new MaterialService(substanceService)
                        └── 없으면 이 줄을 실행조차 못 한다
  → 1단계와 2단계가 한 덩어리다. 틈이 없다.

[setter 주입]
  1. 인스턴스화        new MaterialService()        ← 의존성 없이 성공
       ▼  ◀── 여기가 틈이다. 미완성 객체가 이미 존재한다
  2. 프로퍼티 주입     setSubstanceService(...)
  → 1단계가 2단계 없이 먼저 끝난다.
```

**컨테이너가 이 틈을 이용한다** — `MaterialService`를 인스턴스화한 **직후, 아직 의존성이 안 채워진 그 객체를 내부 캐시에 등록**해 둔다. 이것이 ****조기 노출****이다.

**그다음**: `SubstanceService`를 만들면서 **그 미완성 참조를 넣어 주고**, 완성된 `SubstanceService`를 다시 `MaterialService`에 채운다.

**핵심은 "객체를 만드는 일과 의존성을 채우는 일을 분리하면 미완성 상태의 객체를 상대에게 먼저 건네줄 수 있다"는 것이다.**

**Boot의 기본값**: `SpringApplication.setAllowCircularReferences`의 기본값은 **`false`**(2.6.0부터)이며, 이 값이 컨텍스트 refresh 전에 빈 팩터리에 설정되어 **프레임워크가 조기 노출로 사이클을 깨려는 시도 자체를 할지**를 결정한다.

## Q4. 조기 노출이 감수하는 대가와 위험한 코드

**대가 — 한쪽은 완전히 초기화되기 전에 남에게 주입된다.**

공식 문서: 순환 의존이 있으면 *"두 빈 중 하나는 **자신이 완전히 초기화되기 전에** 다른 빈에 주입되도록 강요된다."*

```text
SubstanceService 가 잠시 들고 있는 MaterialService
  = 필드가 아직 비어 있는 객체
  → 그 시점에 메서드를 부르면 NullPointerException
```

**특히 위험한 코드 — 주입받은 상대의 메서드를 "만들어지는 중"에 부르는 것**:

| 위치 | 왜 위험한가 |
|---|---|
| **생성자** | 상대가 미완성인 그 순간이다 |
| **`@PostConstruct`** | [[03-bean-creation-and-lifecycle-callbacks]]의 5단계 — 상대가 아직 자기 초기화를 못 끝냈을 수 있다 |
| `InitializingBean.afterPropertiesSet()` | 같은 이유 |

**반대로 안전한 코드** — **요청을 처리할 때** 상대 메서드를 부르는 것. 그때는 두 빈 다 완성돼 있다.

**즉 위험은 "사이클이 있다"가 아니라 "미완성 구간에 상대를 쓴다"에 있다.** 사이클을 켜 두고도 오래 문제없이 도는 애플리케이션이 있는 이유이고, **어느 날 초기화 코드를 한 줄 추가하는 순간 터지는 이유**이기도 하다.

**§6**: **`spring.main.allow-circular-references=true`를 상시 설정으로 두지 않는다.** **켜야만 뜨는 상태는 설계 부채가 남아 있다는 표시다.**

## Q5. 이 실패가 시작 시점에 나는 것이 이득인 이유

**[[01-beandefinition-and-metadata-phase]]의 사전 인스턴스화 덕분이다.**

```text
1. 컨테이너가 빈 정의를 전부 모은다          — 전체를 봐야 의존 그래프를 그린다
2. 싱글턴을 하나씩 실제로 만들어 본다        — 정의 검증만으론 생성 시점 문제를 못 잡는다
3. 생성 스택에 이미 올라온 빈을 다시 요구받으면 사이클로 판정
                                             — 그대로 두면 무한 재귀로 스택이 터진다
4. Boot 의 실패 분석기가 사람이 읽을 그림으로 바꾼다
```

> **이 실패는 손해가 아니라 이득이다.**

**사전 인스턴스화가 없었다면**:

```text
시작 성공 → 배포 완료 → 트래픽 유입
  → 첫 요청에서 그 빈이 처음 만들어진다
  → 여기서 사이클 실패
  → 운영 환경에서, 사용자 요청 중에 드러난다 💥
```

**같은 결함인데 발견 시점이 "배포 전"과 "운영 중"으로 갈린다.**

**그래서 `spring.main.lazy-initialization=true`는 이 안전망을 약화시킨다** — **빈을 나중에 만들면 사이클도 나중에 발견된다.**

**§6**: **`lazy-initialization`으로 사이클 실패를 회피하지 않는다.** 시작은 성공하지만 **같은 문제가 첫 요청 시점으로 옮겨질 뿐이다.**

**일반화하면**: **시작 시점의 실패는 배포 파이프라인이 잡아 주는 실패**다. 개발자가 로컬에서, CI가 빌드에서, 배포가 헬스 체크에서 잡는다. **런타임 실패는 그 셋을 전부 통과한 뒤에 나온다.**

## Q6. Boot가 `allow-circular-references=true`를 "최후의 수단"이라 부르는 이유 셋

**① 미완성 객체가 돌아다닌다**

Q4 그대로 — **한쪽은 필드가 빈 상태로 주입된다.** 그 시점에 상대 메서드를 부르는 코드(생성자나 `@PostConstruct`)가 있으면 `NullPointerException`.

**② 프록시와 충돌할 수 있다**

[[02-two-postprocessor-extension-points]]에서 봤듯 **프록시는 초기화가 끝난 뒤 씌워진다.** 그런데 **조기 노출은 그 전에 참조를 내준다.** 그래서 **"원본을 이미 남에게 넘겼는데 나중에 프록시로 감싸졌다"**는 상태가 생길 수 있고, **이때 Spring은 시작을 실패시킨다.**

> **`@Transactional`이 붙은 빈이 사이클에 끼면 켜도 안 뜨는 경우가 여기서 나온다**(Q7).

**③ 사이클은 대개 책임 분리가 잘못됐다는 신호다**

**A와 B가 서로를 필요로 한다면, 둘이 공유하는 무언가가 제3의 클래스로 나와야 할 가능성이 높다.**

**그리고 setter로 푸는 것은 생성자 주입의 이점 셋을 전부 포기하는 것이다** — 공식 문서가 생성자 주입을 권하는 근거:

| 근거 | setter로 바꾸면 |
|---|---|
| **불변 객체로 만들 수 있다** | `final` 불가 |
| **필수 의존성이 `null`이 아님이 보장된다** | 보장 없음 |
| **완전히 초기화된 상태로 호출자에게 반환된다** | 미완성 구간이 생긴다 |

**§5의 방향 정정**:

> **생성자 주입이 사이클에서 실패하는 것은 결함이 아니라 기능이다.** 공식 문서가 생성자 주입을 권하는 근거가 **정확히 이 실패를 만들어 내는 성질**이다.

| | 생성자 주입 | setter 주입 |
|---|---|---|
| 사이클을 만나면 | **시작 실패** | 조용히 동작 |
| 그 결과 | **설계 문제를 즉시 안다** | **설계 문제가 숨는다** |

## Q7. `@Transactional` 빈이 사이클에 끼면 켜도 안 뜰 수 있는 이유

**조기 노출과 프록시 씌우기의 시점이 어긋나기 때문이다.**

```text
[정상 순서]
  1~5단계 → 6단계에서 프록시를 씌운다 → 7단계에서 프록시를 주입한다
             모두가 프록시를 받는다 ✅

[조기 노출이 끼면]
  1단계 직후 원본을 캐시에 넣는다
    → 사이클 상대가 그 원본 참조를 받아 간다
  … 5단계 …
  6단계에서 프록시를 씌운다
    → 이제 컨테이너의 정본은 프록시다
    → 그런데 상대는 이미 원본을 들고 있다
    → "내가 노출한 것과 최종 빈이 다르다"
    → Spring 이 이 불일치를 감지하고 시작을 실패시킨다 💥
```

**왜 실패시키는가 — 조용히 두면 더 나쁘다.** 같은 빈에 대해 **어떤 곳은 프록시를, 어떤 곳은 원본을 들고 있는** 상태가 된다. 그러면 **호출 경로에 따라 `@Transactional`이 켜지고 꺼진다** — c1-03 Q2의 문제가 **애플리케이션 전체에 무작위로 흩어진** 형태다.

**그래서 "켜면 뜬다"가 항상 참이 아니다**:

| 사이클 구성 | `allow-circular-references=true` |
|---|---|
| 평범한 빈끼리 | 대개 **뜬다** (대가는 Q4) |
| **AOP 대상 빈이 끼면** | **안 뜰 수 있다** |

**이 사실이 §6의 판단을 강화한다** — 켜는 것은 **임시방편으로도 신뢰할 수 없다.** 오늘 뜨더라도 **그 빈에 `@Transactional`을 붙이는 순간 안 뜬다.**

**§5의 `@Lazy` 평가도 같은 맥락**:

> **`@Lazy`를 붙이면 프록시가 대신 주입되어 사이클이 뚫린다. 동작은 한다. 하지만 그건 문제를 숨긴 것이지 푼 것이 아니다 — 여전히 두 클래스는 서로를 안다.**

## Q8. 사이클을 푸는 정석 세 가지와 대가

| 방법 | 언제 | 대가 |
|---|---|---|
| **공통 로직을 제3의 빈으로 추출** | **대부분의 경우 — 정석** | **클래스가 하나 는다** |
| **한쪽을 `ObjectProvider`로 지연 조회** | 한쪽이 상대를 **가끔만** 쓸 때 | 호출부가 `getObject()`로 **지저분해진다** |
| **이벤트로 방향을 끊는다** | 한쪽이 **"알리기만"** 하면 될 때 | **흐름 추적이 어려워진다** |

**① 추출이 정석인 이유** — Q6의 ③ 그대로다. **A와 B가 서로를 필요로 한다면 둘이 공유하는 무언가가 제3의 클래스로 나와야 한다.** 사이클이 **설계를 진단해 준 것**이므로, 그 진단을 따르는 것이 자연스럽다.

```text
[전]  A ⇄ B
[후]  A → C ← B      C 가 둘이 공유하던 로직
```

**② `ObjectProvider`가 맞는 경우** — **비대칭적일 때**다. A가 B를 항상 쓰고 B는 A를 예외 경로에서만 쓴다면, 추출할 공통 로직이 없을 수 있다. **그때는 B 쪽만 지연시킨다.**

**③ 이벤트가 맞는 경우** — **한쪽이 상대의 반환값을 필요로 하지 않을 때**다. "저장했다"를 알리기만 하면 되면 **의존 방향 자체를 없앨 수 있다.** 대가는 **컴파일 타임에 누가 듣는지 안 보인다**는 것.

**§6의 금지**: **`@Lazy`를 사이클 해결의 기본 도구로 쓰지 않는다.** **프록시가 하나 더 끼고 문제는 그대로다.** 세 정석 중 어느 것도 못 쓸 때의 임시방편이지 해법이 아니다.

## Q9. prototype 빈을 싱글턴에 주입했는데 항상 같은 객체인 이유

**주입이 싱글턴 생성 시점에 딱 한 번 일어나기 때문이다.**

공식 문서: *"prototype 스코프 빈을 싱글턴 스코프 빈에 의존성 주입하면, 새 prototype 빈이 하나 인스턴스화되어 싱글턴 빈에 주입된다. **그 prototype 인스턴스가 싱글턴 빈에 공급되는 유일한 인스턴스다.**"*

```text
싱글턴 생성 (딱 한 번)
  → 의존성 해석
  → prototype 인스턴스 하나 생성
  → 주입
  → 끝. 이후 다시 조회하지 않는다

싱글턴이 100번 호출돼도 들고 있는 것은 그때 받은 그 하나다
```

**§5의 정정**:

> **스코프는 "새로 만들 수 있다"를 뜻할 뿐, "주입 지점이 매번 다시 조회한다"를 뜻하지 않는다.**

**즉 `@Scope("prototype")`은 "요청받으면 새로 만든다"는 컨테이너 쪽 규칙이고, 싱글턴은 요청을 한 번밖에 안 한다.**

**해법 — 주입 지점을 `ObjectProvider<T>`로 선언하고 필요한 순간 `getObject()`를 부른다.**

```java
private final ObjectProvider<Worker> workerProvider;

void handle() {
    Worker w = workerProvider.getObject();   // 부를 때마다 새 인스턴스
}
```

**문서의 표현으로, 인스턴스를 붙들고 있거나 따로 저장하지 않고 필요할 때마다 현재 인스턴스를 가져오는 방식이다.**

**함정이 하나 더 있다**(§2.4, [[03-bean-creation-and-lifecycle-callbacks]]): **prototype에는 **소멸 콜백**이 불리지 않는다.** 컨테이너가 **건네준 뒤로는 기록을 갖지 않기** 때문이다.

**§6**: **prototype 빈에 자원 반납을 맡기지 않는다.**

## Q10. 엔티티끼리의 양방향 연관이 이 노트의 순환 참조와 다른 이유

**만드는 주체와 문제의 종류가 다르다.**

| 축 | **빈 순환 참조** | **엔티티 양방향 연관** |
|---|---|---|
| 누가 만드나 | **Spring 컨테이너** | **JPA(Hibernate)** |
| 언제 | **애플리케이션 시작 시** | **요청 처리 중** |
| 문제의 종류 | **생성 순서가 없다** | **순서 문제가 아니다** |
| 실패 형태 | **시작 실패** | (해당 없음) |

**§5**:

> **도메인 엔티티끼리 서로를 참조하는 것(예: `Material` ↔ `Substance` 연관)은 여기서 말하는 순환 참조가 아니다. 그건 컨테이너가 만드는 빈이 아니라 JPA가 만드는 엔티티이고, 생성 순서 문제가 아니다.**

**왜 엔티티에는 순서 문제가 없나** — **엔티티는 setter/필드로 채워지고, 식별자만 있으면 프록시로 대신할 수 있다.** j2에서 본 대로 `material.company`는 **프록시**이고, 그 프록시는 **회사를 만들지 않고도** 존재한다. **"완성된 상대가 있어야 나를 만들 수 있다"는 계약이 없다.**

**엔티티 양방향에는 다른 문제들이 있다** — 하지만 종류가 다르다:

| 엔티티 양방향의 실제 문제 | 어디서 다루나 |
|---|---|
| 양쪽 동기화 (주인만 외래 키를 쓴다) | j2-01 |
| JSON 직렬화 무한 루프 | (DTO 변환으로 회피) |
| `toString()`·`equals()` 무한 재귀 | (구현 시 주의) |

**이 중 어느 것도 "생성 순서를 정할 수 없다"가 아니다.**

**구분이 왜 중요한가** — 둘을 섞으면 **엔티티 양방향을 보고 "순환 참조니까 없애야 한다"**고 판단하게 된다. 실제로는 **j2-02에서 본 대로 컬렉션을 두는 것이 정당한 경우**가 있다. **진단명이 같다고 처방이 같지 않다.**

> **이 노트의 주제는 컨테이너가 빈을 만드는 순서에 국한된다.**
