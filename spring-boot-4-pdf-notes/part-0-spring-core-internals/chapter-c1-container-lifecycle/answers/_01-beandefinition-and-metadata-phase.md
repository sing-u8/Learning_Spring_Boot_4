## Q1. `@Component`가 객체가 되기까지 반드시 있어야 하는 단계

**빈 정의 단계다 — 클래스를 찾아낸 것을 곧바로 객체로 만들지 않고 "이런 객체를 이렇게 만들어라"라는 설명서로 바꿔 보관하는 단계.**

**세 단계로 나뉜다**:

1. **정의 수집** — `@Component` 스캔·`@Bean` 메서드·XML·자동 구성에서 읽은 것을 전부 **빈 정의** 객체로 바꿔 등록기(`DefaultListableBeanFactory`)에 담는다 → **아직 아무 객체도 만들지 않아야, 뒤에 올 정의까지 전부 모인 상태에서 판단할 수 있다**
2. **정의 가공** — 모인 정의를 훑으며 고친다. `${}` 치환이 여기서 → **객체 생성에 쓰일 재료를 재료가 쓰이기 전에 확정하려고**
3. **인스턴스화** — 확정된 정의대로 객체를 만들고 의존성을 채운다 → **이 시점에는 더 이상 정의가 바뀌지 않는다는 보장이 있어야, 만들어진 객체가 반쪽짜리 설정을 물고 태어나지 않는다**

**왜 이 단계가 "반드시" 필요한가 — 발견 즉시 생성하면 셋을 못 한다**:

- **`${}` 치환을 끼워 넣을 자리가 없다** — 발견 순간이 곧 생성 순간이라 **그 사이에 아무것도 낄 수 없다**
- **자동 구성의 back-off가 불가능하다** — "사용자 빈이 있는지"를 알려면 **전체 목록이 다 모인 뒤**여야 한다
- **프록시로 감쌀 기회가 없다** — 이미 원본 객체를 만들어 다른 곳에 넘겨 버린 뒤다

> **Spring이 실제로 이 셋을 다 해낸다는 사실 자체가, 발견과 생성 사이에 틈이 있다는 증거다.**

**비유와 그 한계 — 주문서와 완성품**: 주방에 붙은 주문서는 **고칠 수 있다.** 조리 전에 종이를 고치면 된다. **이미 나온 파스타는 못 고친다.**

→ **깨지는 지점**: 주문서는 **손님이 고치고 주방은 따르기만** 한다. 빈 정의는 **컨테이너 자신이 고용한 확장점**([[02-two-postprocessor-extension-points]])이 고친다 — **주방이 스스로 주문서를 고쳐 쓰는 셈**이다. 게다가 주문서는 요리가 나오면 역할이 끝나지만, **빈 정의는 컨테이너가 살아 있는 내내 남아** 스코프·소멸 메서드 같은 정보를 계속 참조당한다.

## Q2. `${}` 치환이 "객체 생성 전"에 끝나야 하는 이유 — 생성자 호출 순서로

```java
@Component
public class GithubClient {
    private final String token;

    public GithubClient(@Value("${cosmoroute.github.token}") String token) {
        this.token = token;
    }
}
```

**순서를 따져 보면 답이 나온다**:

```text
GithubClient 객체를 만들려면
  → 생성자를 불러야 한다
  → 생성자를 부르려면 token 문자열이 이미 준비돼 있어야 한다
  → 그런데 ${cosmoroute.github.token} 은 아직 글자 그대로의 문자열이다
  → 누군가 이 자리를 실제 값으로 바꿔치기해야 한다
  → 그 일은 객체가 만들어지기 전에 끝나 있어야 한다
```

> **객체를 만들면서 동시에 그 객체의 재료를 고칠 수는 없다.**

**생성자 인자는 "이미 값이어야 하는 것"이다.** 자바의 생성자 호출 규칙상 인자는 **호출 시점에 평가가 끝나** 있어야 하고, 그 뒤로는 바꿀 수 없다. **`final` 필드에 대입되면 더더욱** 그렇다.

**그래서 Spring의 해법**:

> **재료 목록을 먼저 만들어 두고, 그 목록을 손볼 시간을 준 다음, 마지막에 객체를 찍어낸다.**

**setter 주입이었다면 조금 다르다** — 객체를 만든 뒤에 값을 넣으므로 이론상 나중에 고칠 여지가 있다. **하지만 생성자 주입에는 그 여지가 없고, 생성자 주입이 권장 방식이다.** 그래서 **가장 엄격한 경우에 맞춰 단계를 나눈 것**이다.

**이것이 [[02-two-postprocessor-extension-points]]의 구분과 직결된다** — `${}` 치환이 `BeanFactoryPostProcessor`인 이유가 정확히 이 순서다.

## Q3. 자동 구성의 back-off가 "발견 즉시 생성" 방식에서 불가능한 이유

**"사용자가 같은 타입의 빈을 직접 만들었는가"를 알려면 전체 목록이 다 모인 뒤여야 하기 때문이다.**

```text
[발견 즉시 생성]
  자동 구성 클래스를 먼저 읽었다
    → DataSource 빈을 즉시 만든다
    → 그 뒤에 사용자의 @Bean DataSource 를 발견한다
    → 이미 만들어서 다른 곳에 주입까지 했다
    → 물러설 수가 없다

[정의를 먼저 모은다]
  자동 구성 + 사용자 정의를 전부 정의로 수집
    → 목록을 보고 "사용자 DataSource 정의가 있다" 판정
    → 자동 구성 정의를 등록하지 않는다
    → 아무것도 만들어지지 않았으므로 되돌릴 것도 없다
```

**핵심은 "판단에 필요한 정보가 언제 완성되는가"다.** back-off의 조건(`@ConditionalOnMissingBean`)은 **다른 정의의 존재 여부**를 본다. 그 정보는 **수집이 끝나야** 완성된다.

**그리고 순서에 의존하면 안 된다** — 사용자 설정 클래스를 자동 구성보다 먼저 읽도록 강제할 수도 있겠지만, 그러면 **읽는 순서가 곧 동작을 결정**한다. 패키지 이름 하나만 바뀌어도 결과가 달라진다.

**정의 단계를 분리하면 순서가 무관해진다** — 전부 모은 뒤에 판정하므로 **누가 먼저 스캔됐는지가 결과에 영향을 주지 않는다.**

**c4에서 이어진다** — 자동 구성이 항상 **사용자 정의보다 나중에 평가되도록** 순서를 잡는 것도 같은 목적이다.

## Q4. 빈 정의에만 있고 클래스 코드에는 없는 것

**`Scope`가 대표적이다. `Name`, `Lazy initialization mode`, `Autowiring mode`도 그렇다.**

**공식 문서의 아홉 항목**:

| 항목 | 무엇을 정하나 | 클래스 코드에 있나 |
|---|---|---|
| **Class** | 인스턴스화할 클래스 | — (이게 곧 클래스다) |
| **Name** | 컨테이너 안에서의 이름 | **없다** |
| **Scope** | singleton / prototype / request … | **없다** |
| Constructor arguments | 생성자에 넣을 값·참조 | 시그니처만 |
| Properties | setter로 넣을 값·참조 | 시그니처만 |
| **Autowiring mode** | 어떤 방식으로 짝을 찾을지 | **없다** |
| **Lazy initialization mode** | 시작 때 만들지, 요청 때 만들지 | **없다** |
| Initialization method | 준비 후 부를 메서드 | 메서드는 있으나 "언제"는 없다 |
| Destruction method | 종료 시 부를 메서드 | 위와 같다 |

**왜 중요한가 — `Class`와 `Scope`가 나란히 있다는 점이다**:

> **"무엇을 만들지"와 "몇 개를 만들지"가 같은 층의 메타데이터다.**

**그래서 같은 클래스를 서로 다른 스코프의 빈 두 개로 등록할 수 있다.** 클래스 코드는 자기가 몇 개 만들어질지 모른다.

**이것이 IoC의 구체적 형태다** — 클래스는 **"나는 이런 것이다"**만 말하고, **"어떻게 쓰일지"는 정의가 정한다.** 클래스가 자기 스코프를 하드코딩하고 있다면 그 클래스는 **재사용될 수 없다.**

**`Name`도 같다** — 같은 클래스가 서로 다른 이름의 빈 두 개가 될 수 있고, 주입 지점은 이름으로 지목한다. **클래스 안에 이름이 있었다면 하나밖에 못 만든다.**

## Q5. 싱글턴을 미리 다 만드는 것의 비용과 이득

**비용 — 시작 시간과 메모리. 이득 — 설정 문제를 시작 시점에 발견하는 것.**

**공식 문서의 단서가 핵심이다**:

> **"컨테이너가 만들어질 때 각 빈의 설정을 검증한다. 그러나 빈 프로퍼티 자체는 빈이 실제로 만들어지기 전까지는 설정되지 않는다."**

**즉 정의 단계의 검증만으로는 부족하다** — 정의는 멀쩡한데 **실제로 만들어 보면 터지는** 경우가 있다. 문서의 표현대로, **정상적으로 로드된 컨테이너가 나중에 객체를 요청받는 순간 예외를 낼 수 있다.**

**그래서 **사전 인스턴스화**가 기본이다**:

> **미리 만드는 데 드는 시간과 메모리를 지불하는 대신, 설정 문제를 나중이 아니라 `ApplicationContext`가 만들어지는 시점에 발견한다.**

**교환의 성격**: **비용은 확정적이고 예측 가능**(시작 몇 초, 힙 몇 MB)한 반면, **이득은 확률적이지만 값이 크다**(운영 중 특정 요청에서만 터지는 문제를 안 만난다).

**Boot의 스위치**: `spring.main.lazy-initialization=true`. Boot 공식 문서는 시작 시간이 줄어드는 대신 **"문제 발견이 늦어진다"**를 단점으로 명시하고, **그래서 기본값이 아니라고** 적는다. 웹 애플리케이션에서는 **많은 웹 관련 빈이 HTTP 요청이 들어올 때까지 초기화되지 않는다**는 점도 함께 경고한다.

## Q6. "정상 기동했다"가 보장하는 것과 보장하지 않는 것

**보장하는 것**:

> **"애플리케이션이 떴다"는 것은 "설정 파일이 문법에 맞다"가 아니라 "싱글턴 빈을 전부 실제로 만들어 봤고 하나도 안 터졌다"는 뜻이다.**

- 모든 싱글턴의 **생성자가 실제로 호출됐다**
- 모든 의존성이 **실제로 해석됐다** — 타입이 맞는 빈을 찾았다
- 모든 초기화 콜백이 **실제로 실행됐다**
- 순환 참조가 **없거나 해결됐다**

**보장하지 않는 것**(§5):

| 안 잡히는 것 | 왜 |
|---|---|
| **`@Lazy` 빈, prototype 빈** | **아직 안 만들어졌다** |
| **`lazy-initialization=true`인 경우** | **대부분이 안 만들어졌다** |
| **값이 주입됐지만 그 값이 틀린 경우** | **타입이 맞으면 컨테이너는 통과시킨다** |

**세 번째가 가장 자주 물린다** — `${cosmoroute.github.token}`이 오타로 빈 문자열이 들어와도, **`String` 타입이 맞으므로 컨테이너는 아무 말도 하지 않는다.** 실패는 그 토큰으로 API를 부르는 순간에 난다.

**그래서 기동 성공은 "구조가 성립한다"의 증거이지 "동작이 옳다"의 증거가 아니다.** 값의 유효성은 `@ConfigurationProperties` + 검증이나 `ApplicationRunner`의 헬스 체크 같은 **별도 장치**로 확인해야 한다.

## Q7. prototype 빈 100개가 만들어졌을 때 빈 정의는 몇 개인가

**하나다.**

| 축 | **빈 정의** | **빈** |
|---|---|---|
| 정체 | **메타데이터 객체** | **실제 인스턴스** |
| 개수 | **이름 하나당 하나** | 스코프에 따라 **0개~N개** |
| 언제 생기나 | 시작 초반, 스캔·파싱 직후 | 정의가 확정된 뒤 |
| 고칠 수 있는 시점 | **인스턴스화 전까지** | 만들어진 뒤엔 프록시로 감싸는 정도 |
| **`prototype`이면** | **정의는 하나** | **요청할 때마다 새로** |

**그 답이 뜻하는 바**:

> **"정의는 틀이고 빈은 결과물"이라는 관계가 여기서 눈에 보인다.**

**정의는 붕어빵 틀이고 빈은 붕어빵이다.** 틀 하나로 100개를 찍는다. 그리고 **틀을 고치면 그다음에 찍히는 것이 달라지지만, 이미 찍힌 것은 안 바뀐다** — Q1의 "주문서는 고칠 수 있지만 나온 파스타는 못 고친다"와 같은 말이다.

**싱글턴이면 헷갈리지 않는다** — 정의 1개, 인스턴스 1개라 1:1로 보인다. **prototype이 이 관계를 드러낸다.**

**그리고 0개인 경우도 있다** — `@Lazy` 빈을 아무도 요청하지 않으면 **정의는 있는데 인스턴스는 없다.** 정의의 존재가 인스턴스의 존재를 뜻하지 않는다.

**실무 함의**: "빈이 몇 개냐"는 질문이 **모호하다.** `getBeanDefinitionCount()`와 실제 살아 있는 객체 수는 다른 숫자다.

## Q8. `spring.main.lazy-initialization=true`의 대가

**문제 발견이 시작 시점에서 런타임으로 밀린다.**

```text
[기본 — 사전 인스턴스화]
  시작 시   싱글턴 전부 생성 → 여기서 터진다 → 배포가 실패한다 ✅
  운영 중   이미 검증됨

[lazy-initialization=true]
  시작 시   거의 안 만든다 → 빠르게 뜬다
  운영 중   첫 요청에서 만든다 → 여기서 터진다 💥
            → 이미 배포됐고 트래픽이 들어오는 중이다
```

**Boot 공식 문서가 명시하는 두 가지**:

1. **"문제 발견이 늦어진다"** — 그래서 기본값이 아니다
2. **웹 애플리케이션에서는 많은 웹 관련 빈이 HTTP 요청이 들어올 때까지 초기화되지 않는다**

**§6의 추가 경고**: **시작 시간 단축용으로 가볍게 켜지 않는다.** **시작 때 안 만들던 빈까지 결국 다 만들어지므로 힙 크기를 먼저 점검해야 한다.**

**즉 절약이 아니라 이연이다** — 총량은 같고 **시점만 옮긴다.** 그리고 옮긴 시점이 **하필 트래픽이 있는 때**다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 시작 시간 | **짧아진다** | — |
| 총 메모리 | 변화 없음 (결국 다 만든다) | 힙 피크 시점이 예측 불가 |
| **실패 시점** | — | **배포 전 → 운영 중** |
| 첫 요청 지연 | — | **길어진다** |

**켤 만한 경우**: 개발 중 재시작을 자주 하는 로컬 환경, 또는 빈 수가 매우 많고 그중 실제로 쓰이는 것이 일부인 배치 애플리케이션. **운영 웹 서비스에서는 얻는 것보다 잃는 것이 크다.**
