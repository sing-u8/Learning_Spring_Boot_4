## Q1. 컨트롤러 서른 개에 서블릿 하나인 구조

**컨트롤러는 서블릿이 아니다. `DispatcherServlet`이 호출하는 평범한 자바 메서드다.**

```text
서블릿 컨테이너가 아는 것        : DispatcherServlet 하나 (매핑 "/")
DispatcherServlet 이 아는 것     : 컨트롤러 서른 개
컨트롤러가 아는 것               : 자기 도메인 로직뿐
```

**요청이 `/materials`든 `/companies/42`든 같은 서블릿이 받는다.** 매핑이 `/`이므로 **그 아래 모든 경로가 이 하나로 들어온다.**

**공식 문서의 설계 규정**: *"Spring MVC는 ****프런트 컨트롤러**** 패턴을 중심으로 설계됐다. 중앙 `Servlet`인 `DispatcherServlet`이 **요청 처리를 위한 공유 알고리즘**을 제공하고, **실제 작업은 설정 가능한 위임 컴포넌트들이 수행한다.**"*

**중간층이 없다면 무엇을 해야 하나** — 컨트롤러마다 **경로 매칭, 쿼리 파라미터 파싱, JSON 역직렬화, 응답 직렬화, 상태 코드 결정, 예외 처리, 인코딩 설정**을 직접 해야 한다. **서른 개 컨트롤러에 같은 코드가 서른 번 복사된다.**

**비유와 그 한계 — 건물의 안내 데스크**: 방문객은 전부 **로비의 한 창구**로 들어온다. 안내원은 **용건별 담당 부서를 알지 못해도 된다** — 목록에서 찾아 연결하면 된다. **부서가 늘어나도 안내 절차는 그대로다.**

→ **깨지는 지점**: 안내원은 **연결한 뒤 손을 뗀다.** `DispatcherServlet`은 **끝까지 관여한다** — 담당자가 낸 결과물을 응답 형식으로 바꾸고, **사고를 치면(예외) 그것까지 수습한다.** **연결이 아니라 전 과정의 진행**을 맡는다.

## Q2. "컨트롤러가 서블릿이다"로 설명되지 않는 것 셋

| 관찰 | 서블릿이라면 |
|---|---|
| **① 메서드 시그니처가 제각각이다** | `service(HttpServletRequest, HttpServletResponse)` **하나로 고정돼야 한다** |
| **② `String` 반환이 뷰 이름도 되고 본문도 된다** | **서블릿에는 반환값 자체가 없다** |
| **③ 예외를 던지면 JSON 오류 응답이 나온다** | **그냥 500이 나가야 한다** |

> **이 셋은 전부 컨트롤러와 서블릿 컨테이너 사이에 무언가가 끼어 있다는 증거다.**

**§5의 대비표가 정리한다**:

| 축 | **서블릿** | **컨트롤러** |
|---|---|---|
| 등록 주체 | 서블릿 컨테이너 | **Spring 컨테이너(빈)** |
| 개수 | 보통 하나 | **여럿** |
| **시그니처** | **고정** | **자유** |
| **반환값** | **없음** | **있음** |
| 컨테이너가 아는가 | 안다 | **모른다** |

**세 번째·네 번째 행이 이 챕터 전체의 이유다.** 자유로운 시그니처와 반환값을 가능하게 하는 층이 [[03-argument-resolvers-and-return-value-handlers]]다.

**마지막 행도 중요하다** — **서블릿 컨테이너는 컨트롤러의 존재를 모른다.** Tomcat은 `DispatcherServlet` 하나만 알고, 그 안에서 무슨 일이 일어나는지 관여하지 않는다. w1에서 본 **"Spring MVC 전체가 컨테이너 눈에는 서블릿 하나"**가 이것이다.

## Q3. 공식 문서의 처리 6단계

1. **`WebApplicationContext`를 찾아 요청 속성으로 바인딩한다** — 처리 과정의 컨트롤러와 다른 요소들이 **컨테이너에 접근할 수 있어야** 한다
2. **로케일 해석기를 요청에 바인딩한다** — 뷰 렌더링·데이터 준비에서 **어떤 로케일을 쓸지** 각 요소가 결정할 수 있어야 한다
3. **멀티파트 해석기가 있으면 멀티파트 여부를 검사하고, 있으면 `MultipartHttpServletRequest`로 감싼다** — 뒤따르는 요소들이 **파일 파트를 일반 파라미터처럼** 다룰 수 있어야 한다
4. **적절한 **핸들러**를 찾는다.** 찾으면 그 핸들러와 연결된 ****실행 체인****(전처리기·후처리기·컨트롤러)이 실행되어 렌더링할 모델을 준비한다
5. **모델이 반환되면 뷰를 렌더링한다. 모델이 없으면 렌더링하지 않는다** — **전·후처리기가 요청을 가로챘다면** 이미 완료됐을 수 있다
6. ****예외 해석기**들이 처리 중 발생한 예외를 해석한다** — 예외를 그대로 컨테이너로 올려보내면 **프레임워크가 제어할 수 없는 오류 페이지**가 나간다

**뼈대는 모든 요청에 대해 항상 같고, 요청마다 달라지는 것은 각 단계에서 어떤 구현체가 선택되는지뿐이다.**

## Q4. 4단계의 "`HandlerAdapter` 안에서 응답이 렌더링될 수 있다"가 왜 중요한가

**`@RestController`는 5단계를 아예 거치지 않고, 4단계 안에서 응답이 완성되기 때문이다.**

문서의 단서: *"애노테이션 컨트롤러의 경우 **뷰를 반환하는 대신 (`HandlerAdapter` 안에서) 응답이 렌더링될 수 있다**"*

```text
[뷰 컨트롤러]
  4단계  핸들러 호출 → 모델 + 뷰 이름 반환
  5단계  뷰 렌더링 ← 여기서 응답 본문이 만들어진다

[@RestController]
  4단계  핸들러 호출 → 반환값을 HttpMessageConverter 가 본문에 쓴다
         ↑ 여기서 응답이 이미 완성된다
  5단계  모델이 없으므로 건너뛴다
```

**왜 중요한가 — 이 사실이 여러 함정의 원인이다**:

| 결과 | 어디서 |
|---|---|
| **`postHandle`에서 붙인 헤더가 사라진다** | [[05-exception-resolution-and-filter-vs-interceptor]] — **응답이 이미 커밋된 뒤** |
| `ViewResolver`가 아예 관여하지 않는다 | §5 — **REST API만 만든다면 5단계는 평생 안 쓴다** |
| 직렬화 예외가 200과 함께 나간다 | c3-05 — 상태 코드가 이미 나갔다 |

**§5**: **뷰 렌더링(5단계)이 일어나는 것은 모델이 반환됐을 때뿐이다.** `@ResponseBody`·`ResponseEntity`는 **4단계 안에서 응답을 완성**하므로 `ViewResolver`가 관여하지 않는다.

**즉 "6단계 파이프라인"이라는 그림이 REST API에서는 정확하지 않다** — 실제로는 **4단계가 부풀어 있고 5단계가 비어 있다.**

## Q5. 위임 대상을 찾는 방식과 커스터마이징의 연결

**타입 기반이다 — 정해진 인터페이스를 구현한 빈을 컨텍스트에서 찾는다.**

그 목록이 ****특수 빈 타입****이다.

| 타입 | 책임 |
|---|---|
| `HandlerMapping` | 요청을 핸들러에, **인터셉터 목록과 함께** 매핑 |
| `HandlerAdapter` | **핸들러가 실제로 어떻게 호출되는지와 무관하게** `DispatcherServlet`이 핸들러를 호출하도록 도움 |
| `HandlerExceptionResolver` | 예외를 해석해 핸들러·오류 뷰에 매핑 |
| `ViewResolver` | 논리적 뷰 이름을 실제 `View`로 해석 |
| `LocaleResolver`, `LocaleContextResolver` | `Locale`·시간대 해석 |
| `MultipartResolver` | 멀티파트 요청 파싱 추상화 |
| `FlashMapManager` | 리다이렉트를 가로질러 속성 전달 |

**커스터마이징과의 연결 — 이 표가 곧 확장 지점 목록이다**:

```text
동작을 바꾸고 싶다  →  해당 타입의 빈을 등록한다
아무것도 안 한다     →  Boot 자동 구성이 기본 구현을 넣는다
```

> **우리가 아무 설정 없이도 웹 애플리케이션을 쓸 수 있는 이유다.**

**타입 기반이라는 점이 왜 좋은가** — **이름이나 위치가 아니라 타입으로 찾으므로**, 내가 만든 구현이 **어느 패키지에 있든 어떤 이름이든** 등록만 되면 쓰인다. c4의 자동 구성 back-off와 같은 원리다.

**§6**: **`DispatcherServlet`을 직접 상속·수정하지 않는다.** **확장 지점이 이미 열려 있다.**

## Q6. REST API만 만들 때 안 쓰는 특수 빈 타입

**`ViewResolver`다.**

Q4에서 본 대로 **`@ResponseBody`·`ResponseEntity`는 4단계 안에서 응답을 완성**하므로 **5단계 뷰 렌더링에 들어가지 않는다.**

> **REST API만 만든다면 5단계는 평생 안 쓴다.**

**나머지 여섯은 쓸 수 있다**:

| 타입 | REST API에서 |
|---|---|
| `HandlerMapping` | **필수** |
| `HandlerAdapter` | **필수** |
| `HandlerExceptionResolver` | **필수** — `@RestControllerAdvice`가 이 층이다 |
| **`ViewResolver`** | **안 쓴다** |
| `LocaleResolver` | 오류 메시지 국제화에 쓸 수 있다 |
| `MultipartResolver` | **파일 업로드 API면 쓴다** |
| `FlashMapManager` | 리다이렉트를 안 쓰면 무관 |

**`LocaleResolver`에 대한 문서의 단서**: **로케일 해석이 필요 없으면 이 해석기도 필요 없다.**

**이 질문의 값** — "6단계를 전부 외운다"가 아니라 **"내 애플리케이션에서 실제로 도는 것은 어디까지인가"**를 아는 것이다. REST API라면 **파이프라인의 절반을 안 쓴다.**

## Q7. "공유 알고리즘"이 주는 이득 셋과 대가 하나

**공식 문서의 *"shared algorithm"*은 정확한 단어 선택이다** — **6단계 뼈대는 모든 요청에 대해 항상 같고**, 달라지는 것은 **각 단계에서 어떤 구현체가 선택되는지뿐**이다.

**이득 셋**:

| 이득 | 내용 |
|---|---|
| **① 일관성** | **모든 엔드포인트가 같은 순서로 처리된다.** `@RestController`든 뷰 컨트롤러든 **4단계까지는 동일**하다 |
| **② 횡단 관심사의 자리** | **로깅·인증·트랜잭션을 끼울 지점이 정해져 있다.** 컨트롤러마다 넣을 필요가 없다 |
| **③ 교체 가능성** | **단계마다 인터페이스가 있으므로 한 단계만 바꿔 끼울 수 있다** |

**대가 하나**:

> **호출 스택이 깊어지고, 디버깅할 때 내 코드가 아닌 프레임워크 프레임을 여럿 지나야 한다.**

**그리고 이 챕터의 실질적 값어치가 거기 있다**:

> **이 챕터가 그 프레임들의 이름을 알려 주는 것이 실질적인 값어치다.**

**즉 대가는 없앨 수 없고 감당할 수 있게 만드는 것이다** — 스택 트레이스에 `DispatcherServlet`, `HandlerAdapter`, `HandlerMethodArgumentResolver`가 보일 때 **그게 무엇인지 알면** 깊은 스택이 문제가 아니라 **지도**가 된다.

## Q8. 서블릿 컨테이너와 Spring 컨테이너

**이름이 둘 다 "컨테이너"라 섞이기 쉽다.**

| | **서블릿 컨테이너** | **Spring 컨테이너** |
|---|---|---|
| **담는 것** | **서블릿·필터·리스너** | **빈** |
| 예 | **Tomcat, Jetty** | **`ApplicationContext`** |
| 이 챕터에서 | **`DispatcherServlet`을 실행** | **`DispatcherServlet`이 위임 대상을 찾는 곳** |

```text
[서블릿 컨테이너 — Tomcat]
  소켓을 열고 HTTP 를 파싱한다
  등록된 서블릿(DispatcherServlet)의 service() 를 부른다
  ↓
[Spring 컨테이너 — ApplicationContext]
  DispatcherServlet 이 여기서 HandlerMapping·HandlerAdapter 등을 찾는다
  컨트롤러도 여기 있는 빈이다
```

**두 컨테이너가 만나는 지점이 정확히 `DispatcherServlet` 하나다** — 그 위는 서블릿 세계, 그 아래는 Spring 세계다.

**섞으면 무엇이 막히나**:

- **"Tomcat이 내 컨트롤러를 부른다"** → 아니다. Tomcat은 컨트롤러의 존재를 모른다
- **"필터에서 `@Autowired`가 되나?"** → 필터는 서블릿 층이지만 Spring이 등록한 필터 빈이면 된다. **층을 구분해야 답할 수 있다**
- **"인터셉터를 필터로 대체하면 되나?"** → 위치가 다르다([[05-exception-resolution-and-filter-vs-interceptor]])

**서블릿 층의 자세한 내용은 `part-0-web-foundations`의 `chapter-w1`이 원본이다.**

## Q9. "dispatch"라는 이름이 가리키는 동작

**"발송하다·파견하다"** — **들어온 요청을 받아 적절한 처리자에게 파견한다**는 동작이 그대로 이름이 됐다.

**같은 어원의 것들**:

| | 무엇을 파견하나 |
|---|---|
| `DispatcherServlet` | 요청 → 컨트롤러 |
| 서블릿 명세의 `RequestDispatcher` | 요청 → 다른 서블릿/JSP |
| 컨테이너의 **ERROR dispatch** | 오류 → 오류 페이지 |

**마지막이 c3-05에서 실제로 등장한다** — 아무도 처리 못 한 예외가 **컨테이너의 ERROR dispatch를 통해** Boot의 기본 오류 응답으로 간다.

**`Front controller`의 "front"**는 **건물 정면, 즉 모든 출입이 지나는 앞면**이다. **뒤쪽에 여러 방이 있어도 문은 하나**라는 구조를 가리킨다.

**두 이름이 함께 구조를 설명한다**:

```text
front   : 입구가 하나다        ← 서블릿이 하나인 이유 (Q1)
dispatch: 안에서 나눠 보낸다   ← 컨트롤러가 서른 개일 수 있는 이유
```

**이름만으로 이 노트의 결론에 도달할 수 있다** — 하나로 받아서 여럿에게 파견한다. **그게 프런트 컨트롤러 패턴의 전부이고, `DispatcherServlet`이라는 이름이 그것을 말하고 있다.**
