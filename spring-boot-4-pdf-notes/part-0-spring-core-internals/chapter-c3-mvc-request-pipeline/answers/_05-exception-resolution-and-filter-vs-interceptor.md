## Q1. `postHandle`에서 붙인 헤더가 사라지는 과정 — 커밋으로

**`@ResponseBody`·`ResponseEntity`의 응답은 핸들러 어댑터 안에서 쓰이고 커밋된다. `postHandle`은 그 뒤다.**

공식 문서의 경고: *"`@ResponseBody`와 `ResponseEntity` 컨트롤러 메서드의 경우, 응답이 **`postHandle`이 호출되기 전에** `HandlerAdapter` 안에서 쓰이고 커밋된다. 그것은 헤더 추가 같은 응답 변경을 하기에는 **이미 늦었다**는 뜻이다."*

```text
핸들러 어댑터
  ├ 인자 해석
  ├ 컨트롤러 실행
  └ 반환값 처리 → 본문 작성 → 커밋 ★
postHandle          ← 여기서 setHeader 를 해도 늦었다
```

**"커밋"이 무엇인가** — **HTTP 응답은 헤더가 먼저 나가고 본문이 뒤따른다. 본문 쓰기가 시작되는 순간 헤더는 이미 전송됐다.**

**커밋 후의 `setHeader`는 오류가 아니라 무시된다.**

**비유와 그 한계 — 편지를 부친 뒤 봉투에 도장을 찍으려는 것**: 도장 찍는 동작은 **아무 문제 없이 수행된다** — 다만 **대상 편지가 이미 우체통 안에 없을 뿐**이다.

→ **깨지는 지점**: 편지는 **없어진 것이 눈에 보인다.** HTTP 응답은 **커밋된 뒤에도 객체가 그대로 손에 남아 있다.** `res.setHeader(...)`가 **정상적으로 호출되고 반환된다.** **아무 신호도 없이 효과만 사라진다**는 점이 이 함정을 어렵게 만든다.

**대안**(공식 문서): *"**`ResponseBodyAdvice`**를 구현해 `@ControllerAdvice` 빈으로 선언하거나 `RequestMappingHandlerAdapter`에 직접 설정할 수 있다."* — **본문이 쓰이기 직전에 개입하는 지점**이다.

## Q2. 뷰 컨트롤러에서는 같은 코드가 동작하는 이유

**`postHandle` 이후에 뷰 렌더링(5단계)이 남아 있어 아직 커밋 전이기 때문이다.**

```text
[@RestController]
  어댑터 안에서 본문 작성 → 커밋
  postHandle             ← 이미 늦음 ❌

[뷰 컨트롤러]
  어댑터가 ModelAndView 반환 (아직 본문 없음)
  postHandle             ← 아직 커밋 전 ✅
  뷰 렌더링 → 본문 작성 → 커밋
```

**`postHandle`의 원래 설계 의도가 뷰 컨트롤러 쪽이다** — **모델을 보강할 마지막 기회**를 주는 자리다. `ModelAndView` 인자를 받는 시그니처가 그 사실을 말하고 있다.

**`@RestController`가 나중에 생기면서 그 전제가 깨졌다** — 어댑터 안에서 응답이 완성되는 경로가 추가됐는데, `postHandle`의 위치는 그대로다.

**그래서 진단이 어렵다**:

- **뷰 컨트롤러로 테스트하면 통과한다**
- **REST 컨트롤러에서만 실패한다**
- **코드는 동일하다**

**"어떤 컨트롤러에서 테스트했는가"가 결과를 바꾼다.**

**§6**: **`postHandle`에서 응답 헤더·상태 코드를 바꾸지 않는다.** **REST API에서는 무시된다. 필터나 `ResponseBodyAdvice`를 쓴다.**

## Q3. 그 함정에 예외도 로그도 없는 이유

**커밋 후의 `setHeader`는 오류가 아니라 무시되도록 서블릿 명세가 정하고 있기 때문이다.**

```java
res.setHeader("X-Elapsed-Nanos", "123");
// → 정상 호출. 예외 없음. 반환값도 없음(void)
// → 내부적으로 "이미 커밋됐으니 무시" 하고 끝
```

**왜 예외를 안 던지도록 했을까** — **커밋 여부를 호출자가 항상 알 수는 없기 때문**이다. 필터·인터셉터·어드바이스가 겹치면 **어느 시점에 커밋됐는지 추적이 어렵고**, 그때마다 예외가 나면 **정상 경로에서도 방어 코드를 써야** 한다.

**대신 확인할 방법은 있다** — `response.isCommitted()`가 `boolean`을 돌려준다. **묻지 않으면 알려 주지 않는 설계**다.

**이 함정이 c1·c2의 함정들과 같은 형태다**:

| 함정 | 공통점 |
|---|---|
| `@PostConstruct`의 `@Transactional` (c1-03) | 애노테이션은 있는데 **아무 일도 안 일어난다** |
| `private` 메서드의 AOP (c2-03) | **경고 없음** |
| `@Component`의 `@Bean` lite 모드 (c2-04) | **조용히 다르게 동작** |
| **`postHandle`의 `setHeader` (여기)** | **호출은 되는데 효과가 없다** |

**전부 "실패가 아니라 부재"다.** 그래서 **이 챕터들의 값어치가 "미리 알고 있는 것"에 있다.**

## Q4. 필터와 인터셉터의 위치 차이가 만드는 능력 차이 둘

**① 핸들러를 아는가**

| | **필터** | **인터셉터** |
|---|---|---|
| **핸들러를 아는가** | **모른다** | **안다** (`Object handler` 인자) |

**인터셉터는 `preHandle(req, res, Object handler)`로 어떤 컨트롤러 메서드가 선택됐는지 받는다.** 그래서 **메서드에 붙은 커스텀 애노테이션을 읽어 분기할 수 있다.**

**필터는 아직 **핸들러 매핑**이 실행되기 전이라 그 정보가 없다.**

**② 요청·응답을 래핑할 수 있는가**

| | **필터** | **인터셉터** |
|---|---|---|
| **요청·응답 래핑** | **가능** | **불가능** |

**필터는 `chain.doFilter(wrappedReq, wrappedRes)`로 감싼 객체를 넘길 수 있다.** 그래서 **응답 본문을 가로채 가공**하거나 **커밋을 지연**시킬 수 있다. 인터셉터는 **이미 정해진 객체를 받을 뿐**이다.

**전체 대비**:

| 축 | **서블릿 필터** | **핸들러 인터셉터** |
|---|---|---|
| 관리 주체 | **서블릿 컨테이너** | **Spring** |
| 위치 | `DispatcherServlet` **밖** | **안** |
| 정적 리소스 요청에도 적용 | **예** | 매핑된 경로만 |
| 예외 처리 | `try/catch`로 **전체 감쌈** | Spring 예외 해석 **뒤** |
| 적합한 일 | 인코딩·CORS·인증·응답 래핑 | 감사 로그·권한 세부 검사·모델 보강 |

**§5의 판별**: **"핸들러를 알아야 하는가"와 "응답을 손대야 하는가" 두 질문으로 대부분 갈린다.**

**Q1의 계측 헤더는 두 번째 질문에 걸린다** → **필터**다.

## Q5. 공식 문서가 인터셉터를 보안 계층으로 권하지 않는 이유

문서의 경고: *"인터셉터는 애노테이션 컨트롤러 **경로 매칭과 불일치할 가능성** 때문에 보안 계층으로 이상적이지 않다. 일반적으로 Spring Security를 쓰거나, 서블릿 필터 체인에 통합된 유사한 접근을 **가능한 한 이른 시점에** 적용할 것을 권한다."*

**핵심은 "불일치 가능성"이다**:

```text
인터셉터의 경로 패턴      : /admin/**
@RequestMapping 의 매칭   : 트레일링 슬래시, 인코딩, 매트릭스 변수 …

두 규칙이 완전히 같지 않다
  → 인터셉터가 걸리지 않는데 컨트롤러는 실행되는 조합이 생길 수 있다
  → 보안에서 그런 틈은 곧 우회 경로다
```

**"가능한 한 이른 시점"의 뜻**:

> **필터 체인의 앞쪽일수록 통과해야 할 관문이 많아진다.**

```text
요청 → [보안 필터] → [다른 필터들] → DispatcherServlet → 인터셉터 → 컨트롤러
        ↑ 여기서 막으면 뒤의 모든 경로가 보호된다

요청 → [필터들] → DispatcherServlet → [보안 인터셉터] → 컨트롤러
                                       ↑ 여기까지 오는 다른 경로가 있으면 새어 나간다
```

**보안의 원칙은 "빠뜨릴 수 없는 자리에 둔다"이고**, 필터 체인 앞쪽이 그런 자리다. **인터셉터는 매핑된 경로에만 적용**되므로 **매핑되지 않은 경로**나 **다른 서블릿**은 지나가지 않는다.

**§6**: **인터셉터로 인증·인가를 구현하지 않는다. Spring Security를 쓴다.**

## Q6. 인터셉터 세 콜백의 시점과 예외 시 호출 여부

| 콜백 | 시점 | 예외가 나면 |
|---|---|---|
| **`preHandle`** | 실제 핸들러 실행 **전** | (예외 전이므로 항상 불림) |
| **`postHandle`** | 핸들러 실행 **후**, 뷰 렌더링 전 | **건너뛰어진다** |
| **`afterCompletion`** | 요청 전체가 끝난 **후** | **불린다** |

**`preHandle`의 반환값 계약**: *"`true`를 반환하면 실행이 계속되고, **`false`를 반환하면 나머지 실행 체인이 건너뛰어지고 핸들러가 호출되지 않는다.**"* — **요청을 아예 막을 수 있어야** 하기 때문이다.

**짝짓기 규칙**:

> **`false`를 반환한 인터셉터가 있으면 그 앞에서 `preHandle`이 성공한 인터셉터들의 `afterCompletion`만 불린다.**

```text
인터셉터 A.preHandle → true
인터셉터 B.preHandle → true
인터셉터 C.preHandle → false   ← 여기서 중단
  → 핸들러 호출 안 됨
  → B.afterCompletion, A.afterCompletion 만 불린다 (역순)
  → C 자신은 안 불린다 (자기가 막았으니까)
```

**§5**: **`preHandle`에서 연 자원의 정리는 `postHandle`이 아니라 `afterCompletion`에 둔다** — **`postHandle`은 예외 시 건너뛰어진다.**

**실무 규칙**:

| 하려는 일 | 어디에 |
|---|---|
| 요청 차단 | `preHandle` (`false` 반환) |
| 모델 보강 | `postHandle` (뷰 컨트롤러 한정) |
| **자원 정리·계측 종료** | **`afterCompletion`** |
| **응답 헤더** | **필터** (Q1·Q4) |

## Q7. 예외 해석기가 `null`을 반환하는 것이 실패가 아닌 이유

**체인을 만들기 위한 계약이기 때문이다.**

| 반환값 | 의미 | 다음 해석기 |
|---|---|---|
| 오류 뷰를 가리키는 `ModelAndView` | 오류 페이지로 처리 | **중단** |
| **빈 `ModelAndView`** | **해석기 안에서 처리 완료** | **중단** |
| **`null`** | **미해결** | **시도한다** |

**`null`은 "나는 이 예외를 모른다. 다음 사람에게"라는 뜻이다.**

**이 계약이 가능하게 하는 설계 — 책임 연쇄**:

```text
ExceptionHandlerExceptionResolver     @ExceptionHandler 가 있나?  없으면 null
        ↓
ResponseStatusExceptionResolver       @ResponseStatus 가 붙었나?  없으면 null
        ↓
DefaultHandlerExceptionResolver       Spring MVC 표준 예외인가?   아니면 null
        ↓
(끝까지 null) → 서블릿 컨테이너로 올라간다
```

**각 해석기가 "자기가 아는 것만" 처리하고 나머지는 넘긴다.** 그래서 **새 해석기를 추가해도 기존 것을 안 고쳐도 된다.**

**내장 구현 넷**:

| 구현 | 언제 걸리나 |
|---|---|
| **`ExceptionHandlerExceptionResolver`** | `@ExceptionHandler` 메서드가 있을 때 — **우리가 주로 쓰는 것** |
| `ResponseStatusExceptionResolver` | 예외에 `@ResponseStatus`가 붙어 있을 때 |
| `DefaultHandlerExceptionResolver` | **Spring MVC 자신이 던지는 예외**(400·405·415·406 등) |
| `SimpleMappingExceptionResolver` | 예외 클래스명 → 오류 뷰 이름 매핑 |

**순서 규칙**: 여러 해석기를 빈으로 선언하고 `order` 속성을 조정할 수 있으며, **`order` 값이 클수록 나중에 놓인다.**

**빈 `ModelAndView`와 `null`의 차이가 헷갈리기 쉽다** — 빈 `ModelAndView`는 **"내가 처리했고 뷰는 필요 없다"**(예: `@ResponseBody` 오류 응답을 이미 썼다)이고, `null`은 **"처리 안 했다"**이다.

## Q8. 아무도 처리 못 한 예외는 어디로 가나

**서블릿 컨테이너로 올라가고, 컨테이너가 ERROR 디스패치를 한다.**

공식 문서: *"예외가 끝까지 남으면 **서블릿 컨테이너로 올라가는 것이 허용된다.**"*

```text
예외 해석기 체인이 전부 null 반환
  ↓
DispatcherServlet 이 예외를 서블릿 컨테이너로 던진다
  ↓
컨테이너가 설정된 URL(예: /error)로 ERROR 디스패치를 한다
  ↓  ← 컨테이너 내부에서 일어나는 두 번째 요청 처리다
그것이 다시 DispatcherServlet 에 의해 처리된다
  ↓
Boot 의 BasicErrorController 가 기본 오류 응답을 만든다
```

> **Spring Boot의 기본 오류 응답이 나오는 경로가 이것이다 — 같은 `DispatcherServlet`을 한 번 더 지나간다.**

**"한 번 더 지나간다"가 실무에서 갖는 의미**:

- **필터가 두 번 실행될 수 있다** — ERROR 디스패치도 필터 체인을 지난다(`OncePerRequestFilter`가 이것을 막는다)
- **`/error` 경로가 매핑돼 있어야 한다** — Boot가 `BasicErrorController`를 자동 등록한다
- **로그에 요청이 두 번 찍힐 수 있다**

**c3-01 Q9의 "dispatch"가 여기서 다시 등장한다** — `RequestDispatcher`, `DispatcherServlet`, **ERROR dispatch**가 같은 개념이다.

**그리고 이 경로를 커스터마이징하려면** `BasicErrorController`를 대체하거나 `ErrorAttributes`를 등록한다 — **`@ExceptionHandler`로는 여기까지 온 예외를 못 잡는다.**

## Q9. Spring Security의 인증 실패가 `@RestControllerAdvice`에 안 잡히는 이유

**필터에서 던진 예외는 `DispatcherServlet` 밖이므로 예외 해석기가 볼 수 없기 때문이다.**

```text
   ┌─ 필터 체인 ────────────────────────────────┐
   │  Spring Security 필터                       │
   │    인증 실패 → AuthenticationEntryPoint 로  │
   │                자체 응답을 만든다 ★         │
   │  ┌─ DispatcherServlet ──────────────────┐  │
   │  │  예외 해석기 체인                     │  │
   │  │    ↑ 여기는 도달하지 못한다           │  │
   │  └───────────────────────────────────────┘  │
   └─────────────────────────────────────────────┘
```

**§5**: **Spring Security의 인증 실패 응답이 `@RestControllerAdvice`에 안 잡히는 이유가 이것이다** — **그쪽은 필터 체인 안에서 자체 진입점(`AuthenticationEntryPoint`)으로 처리된다.**

**진단 원칙**:

> **"내 `@ExceptionHandler`가 안 걸린다"면 먼저 그 예외가 파이프라인 안에서 났는지 확인한다.**

**층별로 대응이 다르다**:

| 예외가 난 곳 | 잡는 것 |
|---|---|
| **컨트롤러·서비스** | `@ExceptionHandler` / `@RestControllerAdvice` |
| **인가 실패**(`AccessDeniedException`, 메서드 보안) | 경우에 따라 다르다 — 메서드 보안은 파이프라인 안이라 잡힐 수 있다 |
| **인증 실패**(필터) | **`AuthenticationEntryPoint`** |
| **필터의 다른 예외** | 필터에서 직접 `try/catch` |

**오류 응답 형식을 통일하려면 두 곳을 맞춰야 한다** — `@RestControllerAdvice`와 `AuthenticationEntryPoint`가 **같은 형식**(예: RFC 9457 Problem Details)을 내도록. **한쪽만 하면 인증 실패 응답만 형식이 다르다.**

**§6**: **필터에서 던진 예외를 `@ExceptionHandler`가 잡을 것으로 기대하지 않는다. 층이 다르다.**

## Q10. 직렬화 도중 예외가 나면 200과 깨진 본문이 나가는 이유

**응답이 이미 커밋된 뒤이기 때문이다 — 예외 해석기가 아무리 훌륭한 오류 응답을 만들어도 내보낼 자리가 없다.**

```text
반환값 처리기가 직렬화를 시작한다
  → 200 OK 헤더가 나간다 (커밋)
  → 본문을 쓰기 시작한다  {"id":"abc","company":
  → 여기서 프록시 초기화 실패 또는 순환 참조
  → 예외
  → 예외 해석기가 500 오류 응답을 만든다
  → 그런데 상태 코드는 이미 200 으로 나갔다
  → 헤더도 못 바꾼다
  → 클라이언트는 200 과 잘린 JSON 을 받는다
```

**§2.5**: **직렬화가 절반쯤 진행된 상태에서 예외가 나면, 응답은 이미 200 OK 헤더와 잘린 본문을 내보낸 뒤다.**

**클라이언트 입장에서 최악이다** — **HTTP 계층에서는 성공**이므로 재시도 로직도 오류 처리도 발동하지 않고, **파싱에서 정체불명의 실패**가 난다.

**실무 원칙**:

> **컨트롤러에서 반환하는 객체를 단순하게 유지한다.**

> **지연 로딩 프록시나 순환 참조가 있는 엔티티를 그대로 반환하면 실패가 하필 가장 나쁜 시점 — 커밋 이후 — 에 일어난다.**

**§6**: **엔티티를 그대로 반환하지 않는다. 직렬화 실패가 커밋 이후에 일어나 예외 해석기가 무력해진다.**

**이것이 c3-04 Q9·j3-05·j1-03과 같은 결론이다** — **네 챕터가 서로 다른 이유로 "DTO를 반환하라"를 가리킨다**:

| 챕터 | 이유 |
|---|---|
| j1-03 | 더티 체킹 비용, 의도치 않은 UPDATE |
| j3-05 | OSIV를 끄면 트랜잭션 밖 지연 로딩 실패 |
| c3-04 | 직렬화가 프록시·순환 참조에서 터진다 |
| **c3-05 (여기)** | **그 실패가 하필 커밋 이후라 복구가 불가능하다** |

**같은 규칙에 근거가 넷이면, 그건 취향이 아니라 원칙이다.**
