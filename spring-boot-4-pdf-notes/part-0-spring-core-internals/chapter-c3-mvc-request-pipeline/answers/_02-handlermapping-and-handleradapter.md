## Q1. `Ambiguous mapping`이 기동 시점에 나는 것이 알려 주는 것

**매핑 테이블이 시작할 때 이미 완성돼 있다는 것이다.**

```text
/materials 로 요청을 보내지도 않았는데 충돌을 발견했다
  → 요청이 올 때 애노테이션을 읽는 구조였다면 첫 요청에서야 알았을 것이다
  → 그런데 기동 시점에 터졌다
  → 경로 → 메서드 매핑 테이블이 시작할 때 만들어진다
```

**이것이 c1·c2에서 반복된 패턴이다** — **"판정은 시작할 때 한 번뿐"**(Q10).

**그리고 이 실패는 좋은 실패다** — **조용하지 않다.** 애플리케이션이 아예 안 뜨므로 **배포 파이프라인이 잡아 준다.** 런타임에 "둘 중 아무거나" 부르는 것보다 훨씬 낫다.

**§6**: **같은 경로에 조건 없이 두 메서드를 두지 않는다.** **다행히 조용하지 않은 실패라 발견은 쉽다.**

## Q2. 요청마다 애노테이션을 읽는 구조라면 무너지는 것 셋

| 무너지는 것 | 내용 |
|---|---|
| **① 성능** | 요청 하나마다 **컨트롤러 서른 개의 메서드 수백 개를 리플렉션으로 훑어야** 한다. **처리량이 무너진다** |
| **② 조기 발견** | **충돌을 런타임에야 알게 된다.** 잘 안 쓰는 경로라면 **배포 후 며칠 뒤에** 드러난다 |
| **③ 목록화** | **어떤 경로들이 존재하는지 목록을 만들 수 없다.** Actuator의 매핑 조회, **springdoc의 문서 생성**이 전부 불가능해진다 |

**③이 덜 알려져 있지만 실무에서 크다** — `/actuator/mappings`도, OpenAPI 문서 자동 생성도 **매핑 테이블이 있어야** 가능하다. 요청마다 판정하는 구조라면 **"지금 이 애플리케이션이 어떤 API를 제공하는가"에 답할 수 없다.**

**그래서 시작할 때 스캔해 테이블을 만들고, 요청이 오면 조회한다.**

## Q3. 찾는 일과 호출하는 일을 다른 인터페이스로 나눈 이유 — "차단"

**공식 문서가 존재 이유를 직접 밝힌다**:

> *"예를 들어 애노테이션 컨트롤러를 호출하려면 애노테이션을 해석해야 한다. **`HandlerAdapter`의 주된 목적은 `DispatcherServlet`을 그런 세부 사항으로부터 차단(shield)하는 것이다.**"*

**차단하지 않으면 무엇이 문제인가**:

```java
// 이것도 핸들러다
@GetMapping("/materials")
public List<MaterialSummary> findAll(@RequestParam int page) { ... }

// 이것도 핸들러다 (정적 리소스)
ResourceHttpRequestHandler

// 이것도 핸들러다 (함수형)
RouterFunction
```

**셋의 호출 방법이 전부 다르다** — 첫 번째는 **애노테이션을 해석해 인자를 채워야** 하고, 두 번째는 **파일을 찾아 스트림으로 쓰면** 되고, 세 번째는 **함수를 적용하면** 된다.

> **`DispatcherServlet`이 이 셋을 전부 알아야 한다면, 새로운 종류의 핸들러가 추가될 때마다 `DispatcherServlet`을 고쳐야 한다.**

**차단의 결과**: `DispatcherServlet`은 **`Object handler`를 들고 있을 뿐 그것이 무엇인지 모르는 채로 어댑터에게 넘긴다.**

| | `HandlerMapping` | `HandlerAdapter` |
|---|---|---|
| 답하는 질문 | **누가** 처리하는가 | **어떻게** 실행하는가 |
| 입력 | HTTP 요청 | 핸들러 객체 + 요청/응답 |
| 출력 | ****실행 체인**** | `ModelAndView` 또는 **`null`** |

**비유와 그 한계 — 콜센터의 접수와 처리**: 접수 담당자는 **"이 문의는 요금제 팀 소관"**이라는 것만 알면 되고, **요금제 팀이 어떤 시스템에 로그인해 무슨 절차를 밟는지는 몰라도 된다.** **팀이 새로 생겨도 접수 절차는 안 바뀐다.**

→ **깨지는 지점**: 콜센터에서는 접수 담당자가 **연결만 하고 빠진다.** `DispatcherServlet`은 어댑터를 통해 **결과를 돌려받아** 다음 단계(뷰 렌더링, 예외 해석)를 이어 간다. **위임이지 이관이 아니다.**

## Q4. 핸들러 매핑이 돌려주는 것

**핸들러 하나가 아니라 **실행 체인**이다 — 핸들러 + 그에 적용될 인터셉터 목록.**

공식 문서의 `HandlerMapping` 책임: *"요청을 핸들러에, **전·후처리를 위한 인터셉터 목록과 함께** 매핑한다"*

**왜 함께 돌려주는가** — **인터셉터는 경로별로 다르게 등록되므로 핸들러가 정해진 뒤에야 결정할 수 있다**(§2.2의 5단계).

```text
요청 /admin/materials
  → 핸들러: AdminMaterialController#list
  → 인터셉터: [인증 인터셉터, 감사 로그 인터셉터]     ← 경로 패턴으로 붙는다

요청 /public/materials
  → 핸들러: PublicMaterialController#list
  → 인터셉터: []                                       ← 붙는 것이 없다
```

**이것이 뜻하는 바**(Q9): **어떤 인터셉터가 적용될지는 컨트롤러가 정하지 않는다.**

## Q5. 매핑 조건에 경로 말고 무엇이 더 있나

**HTTP 메서드, `params`, `headers`, `consumes`, `produces`가 전부 조건이다.**

```java
@GetMapping(value = "/materials", params = "format=summary")
public List<MaterialSummary> summary() { ... }

@GetMapping(value = "/materials", produces = MediaType.APPLICATION_XML_VALUE)
public MaterialList asXml() { ... }
```

**두 메서드는 경로가 같아도 충돌하지 않는다. 조건이 다르기 때문이다.**

**반대로 출발 장면의 두 메서드는 경로·HTTP 메서드가 완전히 같아 충돌했다.**

**충돌 판정 규칙**: **조건의 조합 전체가 완전히 같을 때만** `Ambiguous mapping`이다. 하나라도 다르면 **다른 핸들러**로 취급된다.

**그리고 여럿이 맞을 때는 구체성 순으로 정렬해 고른다**(§2.2의 4단계) — `/materials/{id}`와 `/materials/new`가 둘 다 맞을 때 **후자가 이긴다.**

**`produces`가 조건이라는 사실이 특히 중요하다** — [[04-httpmessageconverter-and-content-negotiation]]과 이어진다:

> **클라이언트의 `Accept` 헤더가 어느 핸들러를 부를지까지 바꿀 수 있다.**

**§6의 경계**: **매핑 조건을 지나치게 정교하게 쓰지 않는다.** `params`·`headers` 조건으로 분기를 만들면 **어느 메서드가 불릴지 코드만 보고 알기 어려워진다.** 대개는 **경로를 나누는 편이 읽기 쉽다.**

## Q6. 404와 405의 구별 — 415·406은 무엇이 다른가

**405는 "경로는 맞다"는 신호다.**

```text
POST /materials 로 요청
  경로 /materials 가 테이블에 있다 (GET 으로 등록됨)
  HTTP 메서드 조건이 안 맞는다
  → 404 가 아니라 405 Method Not Allowed
```

**404가 나는 두 원인도 구별해야 한다**(§5):

| 원인 | 어디서 | 로그 |
|---|---|---|
| **매핑 테이블에 그 조건이 없다** | 핸들러 매핑 | `No mapping for GET /xxx` |
| **핸들러는 찾았는데 리소스가 없다** | 핸들러 내부 | 컨트롤러가 던진 예외 |

앞은 **경로·HTTP 메서드·`produces` 조건**을 봐야 하고, 뒤는 **컨트롤러 로직**을 봐야 한다. 매핑 목록은 **`/actuator/mappings`**로 확인한다.

**415·406은 사정이 다르다 — 원인이 둘이다**:

| 코드 | **원인 A — 매핑 단계** | **원인 B — 컨버터 단계** |
|---|---|---|
| **415** | `consumes` 조건 불일치 | **요청 `Content-Type`을 읽을 컨버터가 없음** |
| **406** | `produces` 조건 불일치 | **응답을 쓸 컨버터가 없음** |

**두 원인이 같은 예외로 수렴해 같은 상태 코드가 나간다.** 그래서 **415를 보고 `consumes`만 뒤지면 못 찾는 경우가 있다.**

**오히려 공식 문서가 명시하는 쪽은 컨버터다** — `DefaultHandlerExceptionResolver`의 javadoc은 415를 *"PUT 또는 POST된 컨텐츠에 대해 **메시지 컨버터를 찾지 못한** 경우"*, 406을 *"클라이언트가 (`Accept` 헤더로 표현한) 요구에 **맞는 메시지 컨버터를 찾지 못한** 경우"*로 적는다.

**진단 순서는 컨버터 먼저, `consumes`/`produces`는 그다음이 실용적이다** — **대부분의 프로젝트에는 `consumes`·`produces` 선언 자체가 없기 때문이다.**

## Q7. 어댑터가 `null`을 반환하는 경우와 그때 `DispatcherServlet`이 하는 일

**`@ResponseBody` 핸들러가 어댑터 안에서 응답을 다 쓰고 `null`을 반환한다. `DispatcherServlet`은 뷰 렌더링을 건너뛴다.**

```text
[뷰 컨트롤러]
  어댑터 → ModelAndView 반환 → DispatcherServlet 이 5단계에서 뷰 렌더링

[@ResponseBody]
  어댑터 안에서 HttpMessageConverter 가 본문을 이미 썼다
  어댑터 → null 반환
  → 돌려줄 모델이 없다
  → DispatcherServlet 이 뷰 렌더링을 건너뛴다
```

**§5**: **어댑터가 `null`을 돌려주는 것은 오류가 아니다. 이것이 정상이다.**

**이것이 [[01-dispatcherservlet-as-front-controller]]에서 본 "모델이 없으면 뷰를 렌더링하지 않는다"의 정체다.**

**`null`이 두 가지를 뜻할 수 있다는 점도 알아 둘 것**:

| `null`의 이유 | 상황 |
|---|---|
| **어댑터가 응답을 다 썼다** | `@ResponseBody`·`ResponseEntity` |
| **인터셉터가 요청을 가로챘다** | `preHandle`이 `false` 반환 — 문서의 *"보안상 이유로 요청이 이미 완료"* |

**둘 다 "더 할 일이 없다"는 신호**이고, `DispatcherServlet`은 어느 쪽인지 구별하지 않는다. **모델이 없으면 렌더링하지 않는다는 규칙 하나로 둘 다 처리된다.**

## Q8. `@RequestMapping`과 `HandlerMapping`의 층위 차이

**`@RequestMapping`은 개발자가 쓰는 선언이고, `HandlerMapping`은 그 선언들을 모아 테이블로 만들고 조회하는 전략이다.**

```text
@RequestMapping        선언 (메타데이터)
        ↓ 시작 시 스캔
매핑 테이블            자료구조
        ↓ 요청 시 조회
HandlerMapping         전략 인터페이스
```

**`RequestMappingHandlerMapping`이라는 긴 이름이 둘의 관계를 그대로 담고 있다**:

> **"`@RequestMapping`을 다루는 `HandlerMapping`"**

**섞으면 무엇이 막히나**:

- **`@RequestMapping`이 아닌 핸들러도 있다** — 정적 리소스는 `SimpleUrlHandlerMapping`이 다룬다. **`@RequestMapping`이 `HandlerMapping`의 전부가 아니다**
- **`HandlerMapping`은 여러 개 등록될 수 있다** — 순서대로 물어보고 처음 맞는 것이 이긴다
- **`@RequestMapping`을 고쳐도 테이블은 재생성되지 않는다** — 시작 시 한 번이다(Q1)

**이 구분이 [[01-dispatcherservlet-as-front-controller]] Q5와 이어진다** — `HandlerMapping`은 ****특수 빈 타입**** 중 하나이고, **타입 기반으로 찾아진다.** 내가 `HandlerMapping` 구현을 빈으로 등록하면 그것도 후보가 된다.

## Q9. 인터셉터 적용을 정하는 주체와 디버깅할 곳

**핸들러 매핑이 정한다. 디버깅할 곳은 `WebMvcConfigurer`의 `addInterceptors` 등록부다.**

> **어떤 인터셉터가 적용될지는 컨트롤러가 정하지 않는다. 컨트롤러 코드 어디에도 인터셉터에 대한 언급이 없고, 경로 패턴 기준으로 핸들러 매핑이 붙여 준다.**

```java
// 여기가 정본이다
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(auditInterceptor)
            .addPathPatterns("/admin/**")
            .excludePathPatterns("/admin/health");
}
```

**§6**: **인터셉터 적용 여부를 컨트롤러에서 찾지 않는다. 등록부에 있다.**

**왜 컨트롤러에 없는 것이 설계상 옳은가** — 인터셉터는 **횡단 관심사**다. 컨트롤러마다 "나는 인증 인터셉터를 받는다"고 적어야 한다면 **횡단 관심사를 분리한 의미가 없다.**

**대가는 "코드만 보고는 안 보인다"는 것이다** — 컨트롤러를 아무리 읽어도 **인증이 걸려 있는지 알 수 없다.** 그래서 **등록부를 함께 보는 습관**이 필요하다.

**AOP와 같은 구조다** — c2의 포인트컷도 **대상 클래스에 안 적혀 있다.** 둘 다 **"적용 규칙은 한곳에, 적용 대상은 모른다"**는 형태다.

## Q10. "시작 시점에 비싼 판정을 끝내고 런타임에는 조회만" 패턴

**c1·c2에서 반복된 것과 같은 패턴이다.**

| 챕터 | 시작 시점에 하는 것 | 런타임에 하는 것 |
|---|---|---|
| **c1-01** | 빈 정의 수집·가공, **싱글턴 사전 인스턴스화** | 이미 만들어진 빈을 꺼내 쓴다 |
| **c1-02** | 후처리기 등록·정렬 | 등록된 순서대로 실행 |
| **c2-02** | **포인트컷 평가**, 프록시 생성 여부 판정 | 프록시가 인터셉터 체인을 실행 |
| **c2-04** | `@Configuration` 강화 여부 판정 | 오버라이드된 메서드가 컨테이너 조회 |
| **c3-02 (이 노트)** | **매핑 테이블 구축**, 충돌 검사 | **테이블 조회** |

**공통 논리 세 가지**:

1. **비싼 일을 한 번만 한다** — 리플렉션·클래스 생성·조건 평가는 전부 시작 시점에
2. **실패를 앞당긴다** — `Ambiguous mapping`, 순환 참조, 빈 없음이 **전부 기동 실패**로 나온다
3. **런타임에는 조회만** — 예측 가능한 성능

**그리고 같은 대가를 공유한다**:

| 대가 | 예 |
|---|---|
| **시작 시간이 길어진다** | 사전 인스턴스화, 매핑 스캔 |
| **런타임 변경이 안 된다** | **매핑 테이블이 고정된다**(§6) — 동적 라우팅 불가 |

**§6**: **매핑 테이블이 시작 시 고정된다는 것은 런타임 경로 추가가 안 된다는 뜻이다.** 동적 라우팅이 필요하면 **하나의 핸들러 안에서 분기하거나 함수형 라우팅**을 고려한다.

**이 패턴을 알면 새로운 Spring 기능을 만났을 때 먼저 물을 것이 생긴다** — **"이 판정은 언제 일어나는가?"** 대개 답은 "시작할 때"이고, 그러면 **실패도 시작할 때 나온다**는 것을 예측할 수 있다.

1. 기동이 `Ambiguous mapping`으로 실패했다. 이 사실에서 구조에 대해 무엇을 알 수 있는가?
2. 요청마다 애노테이션을 읽는다면 무너지는 것 셋은? 그중 성능이 아닌 것은?
3. `HandlerAdapter`가 없다면 `DispatcherServlet`을 언제 고쳐야 하는가?
4. 핸들러 매핑의 반환값에 핸들러 말고 무엇이 더 있는가? 왜 함께 오는가?
5. 같은 경로의 두 메서드가 충돌하지 않을 수 있는가?
6. 415를 받았다. 무엇부터 확인하는가? 405와 무엇이 다른가?
7. 어댑터가 `null`을 반환했다. 오류인가? `null`의 두 가지 이유는?
8. `RequestMappingHandlerMapping`이라는 이름을 세 조각으로 나눠 설명하라.
9. 인증 인터셉터가 이 경로에 걸리는지 확인하려면 어느 파일을 보는가?
10. Spring의 새 기능을 만났을 때 "이 판정은 언제 일어나는가"를 묻는 것이 왜 유용한가?
