## Q1. 코드를 안 고쳤는데 응답이 XML로 바뀐 과정

**클래스패스에 XML 컨버터가 추가되면서 등록 순서가 바뀌었고, `Accept: */*`은 그 순서를 그대로 따랐기 때문이다.**

```text
[의존성 추가 전]
  등록된 컨버터: [Jackson(JSON), String, ByteArray, ...]
  Accept: */*  → 아무거나 좋다 → 순서대로 첫 번째 → JSON

[XML 의존성 추가 후]
  등록된 컨버터: [XML, Jackson(JSON), String, ...]   ← 순서가 바뀌었다
  Accept: */*  → 아무거나 좋다 → 순서대로 첫 번째 → XML
```

**컨트롤러 코드는 한 글자도 안 바뀌었다. 바뀐 것은 클래스패스뿐이다.**

**"`@RestController`니까 JSON이 나간다"고 알고 있으면 설명할 수 없다** — **실제로는 어디에도 "JSON으로 응답하라"는 지시가 없다.**

**컨트롤러는 `MaterialDetail` 객체를 반환할 뿐이고**, 그 객체가 바이트 스트림이 되려면 ****메시지 컨버터****가 직렬화해야 한다. 컨버터는 여럿이고 각자 **자기가 다룰 수 있는 미디어 타입 목록**을 갖는다. 그중 하나를 고르는 것이 ****콘텐트 협상****이다.

**비유와 그 한계 — 통역사 배정**: "한국어로 해 주세요"라면 한국어 통역사가 배정된다. **"아무 언어나 좋아요"라고 하면 접수처가 명단 순서대로 배정**하는데, **새 통역사가 명단 앞쪽에 들어오면 그날부터 다른 언어가 나온다.**

→ **깨지는 지점**: 사람은 **예상 밖의 언어가 나오면 즉시 알아채고 항의한다.** HTTP 클라이언트는 그러지 못한다 — **200 OK로 정상 응답이 온 것**이므로 **파싱 단계에 가서야 깨진다.** 게다가 **`Accept: */*`은 클라이언트 라이브러리의 기본값인 경우가 많아**, 개발자가 **명시적으로 선택한 적조차 없다.**

## Q2. `Accept: */*`이 위험한 이유 — 협상의 어느 성질 때문인가

**협상은 클라이언트가 선호를 제시하고 서버가 그중에서 고르는 구조인데, `*/*`은 선호를 포기하는 것이라 결정권이 통째로 서버에 넘어간다.**

> **일방적 지정이 아니라는 점이 핵심이다 — 그래서 클라이언트가 `*/*`처럼 선호를 포기하면 결정권이 통째로 서버에 넘어간다.**

**그리고 서버의 결정 근거가 안정적이지 않다**:

```text
Accept: application/json  → 답이 하나다. 클래스패스가 바뀌어도 JSON
Accept: */*               → 서버가 고른다 → 등록 순서가 이긴다
                            → 등록 순서는 자동 구성과 클래스패스에 달렸다
                            → 의존성 하나로 바뀐다
```

**세 겹으로 나쁘다**:

1. **클라이언트가 의도한 적이 없다** — 라이브러리 기본값인 경우가 많다
2. **서버도 의도한 적이 없다** — 등록 순서를 명시적으로 정한 사람이 없다
3. **실패가 200으로 온다** — HTTP 계층에서는 성공이고, **파싱에서야 깨진다**

**§5**: **컨버터 등록 순서에 의존하지 않는다.** **순서는 자동 구성과 클래스패스에 따라 정해지고, 의존성 하나로 바뀔 수 있다.**

**§6**: **`Accept: */*`을 보내는 클라이언트를 전제하지 않는다.** **서버가 형식을 고정해 주는 것이 양쪽 모두에게 안전하다**(Q7).

## Q3. 415와 406 — 방향·헤더·매핑 조건

| | **415 Unsupported Media Type** | **406 Not Acceptable** |
|---|---|---|
| **방향** | **읽기**(요청 본문) | **쓰기**(응답 본문) |
| **보는 헤더** | **`Content-Type`** | **`Accept`** |
| **매핑 조건** | **`consumes`** | **`produces`** |
| 의미 | **네가 보낸 걸 못 읽겠다** | **네가 원하는 걸 못 만들겠다** |
| 흔한 원인 | 클라이언트가 `Content-Type`을 안 붙임 | `Accept`가 서버 지원 형식과 불일치 |

**§5의 기억법**: **415는 "요청이 이상하다", 406은 "요구가 과하다"**로 기억하면 방향이 안 헷갈린다.

**읽기와 쓰기가 대칭이다**:

| 방향 | 트리거 | 하는 일 | 실패 시 |
|---|---|---|---|
| **읽기** | `@RequestBody`, `HttpEntity`, `@RequestPart` | 요청 본문 → 자바 객체 | **415** |
| **쓰기** | `@ResponseBody`, `ResponseEntity` | 자바 객체 → 응답 본문 | **406** |

**두 헤더를 혼동하면 415와 406을 반대로 진단하게 된다** — `Content-Type`은 **클라이언트가 보낸 형식**, `Accept`는 **클라이언트가 원하는 형식**이다.

**c3-02 Q6과 이어진다** — 415·406은 **원인이 둘**이다(매핑 조건 불일치 / 컨버터 없음). 공식 문서(`DefaultHandlerExceptionResolver` javadoc)가 명시하는 쪽은 **컨버터**이므로, **진단은 컨버터부터** 한다.

## Q4. `@RestController`가 JSON을 보장하지 않는 이유

**`@RestController`는 `@Controller` + `@ResponseBody`일 뿐이다.**

> **"본문에 직접 쓴다"는 뜻이지 "JSON으로 쓴다"는 뜻이 아니다. 형식은 협상 결과다.**

```text
@ResponseBody 가 결정하는 것 : 뷰를 거치지 않고 본문에 직접 쓴다
@ResponseBody 가 결정 안 하는 것 : 어떤 형식으로 쓸 것인가
                                    ↑ 콘텐트 협상이 정한다
```

**JSON이 나오는 것은 관례일 뿐이다** — 대부분의 프로젝트에서 **Jackson만 클래스패스에 있고 `Accept`가 JSON을 요구**하기 때문에 항상 JSON이 나온다. **조건이 바뀌면 결과도 바뀐다**(Q1).

**이 오해가 만드는 실제 문제**:

- **"JSON이니까 필드 이름이 그대로 나가겠지"** → XML 컨버터가 이기면 다른 규칙이 적용된다
- **"`@RestController`면 형식 걱정 없다"** → Q1의 사고가 난다
- **"406이 날 리 없다"** → `Accept`가 맞지 않으면 난다

**대응은 `produces` 명시다**(Q7).

**이름의 유래도 이 오해를 설명한다** — `Rest`는 **아키텍처 스타일 이름**이지 형식 이름이 아니다. REST는 **표현(representation)이 여럿일 수 있다**는 것을 전제하는 스타일이고, `@RestController`는 그 스타일을 지원하는 것이지 **JSON을 지정하는 것이 아니다.**

## Q5. 응답 형식이 결정되는 5단계

1. ****콘텐트 협상**이 클라이언트가 원하는 미디어 타입 목록을 구한다.** 공식 문서 기준 **기본적으로 `Accept` 헤더만 확인한다** — 어떤 형식을 만들어야 할지는 **클라이언트만 안다**
2. **핸들러의 `produces` 조건이 있으면 그것과 교집합을 낸다** — 서버가 만들 수 없다고 선언한 형식을 시도해 봐야 소용없다
3. **등록된 컨버터 중 그 미디어 타입과 반환 타입을 함께 지원하는 것을 순서대로 찾는다** — **미디어 타입만 맞아도 특정 자바 타입은 못 쓰는 컨버터가 있다**
4. **찾으면 그 컨버터로 직렬화하고 `Content-Type` 헤더를 설정한다** — 클라이언트가 **받은 것을 어떻게 파싱할지** 알아야 한다
5. **못 찾으면 406을 낸다** — **아무 형식으로나 내보내면 클라이언트가 파싱에 실패하고, 그것은 서버가 요구를 만족시키지 못했다는 사실을 감추는 일**이다

**1번의 "기본적으로 `Accept` 헤더만"이 출발 장면의 열쇠다** — **`*/*`은 "전부 수용 가능"이므로 1번에서 걸러지지 않고, 3번에서 등록 순서가 이긴다.**

**3번의 "반환 타입도 함께"가 덜 알려져 있다** — 미디어 타입이 맞아도 **그 자바 타입을 다룰 수 없으면** 그 컨버터는 후보에서 빠진다. 그래서 **`Accept: application/json`인데도 406이 날 수 있다** — Jackson이 그 타입을 직렬화할 수 없는 경우.

**5번의 판단이 중요하다** — **406을 내는 것이 "불친절"이 아니라 정직**이다. 아무거나 내보내면 **실패를 감춘다.**

## Q6. 공식 문서가 경로 확장자보다 쿼리 파라미터를 권하는 이유

| 전략 | 형태 | 공식 문서의 태도 |
|---|---|---|
| `Accept` 헤더 | `Accept: application/json` | **기본값** |
| **쿼리 파라미터** | `/materials/abc?format=json` | URL 기반이 꼭 필요하면 **이쪽을 권장** |
| **경로 확장자** | `/materials/abc.json` | **권장하지 않음** |

공식 문서: *"URL 기반 콘텐트 타입 해석을 꼭 써야 한다면, **경로 확장자보다 쿼리 파라미터 전략을 고려하라.**"*

**보안 이유다**:

> **경로 끝의 확장자를 형식 지정으로 해석하면 `/materials/report.html` 같은 요청이 의도치 않은 형식으로 처리될 수 있고, 이것이 RFD(Reflected File Download) 계열 공격의 표면이 된다.**

**접미사 매칭 자체가 현대 Spring에서 기본 비활성화된 것도 같은 흐름이다.**

**추가 문제들**:

| 문제 | 내용 |
|---|---|
| **경로의 일부를 형식으로 오인** | `/files/report.2024.json`의 `.2024`는? |
| **리소스 식별자와 섞인다** | 파일 이름에 점이 있는 리소스를 다룰 수 없다 |
| **캐시·라우팅과 충돌** | 프록시가 확장자로 판단하는 규칙과 부딪힌다 |

**쿼리 파라미터는 이 셋이 없다** — **경로는 온전히 리소스 식별자**이고, 형식은 **별도 축**에 있다.

**설정은 `ContentNegotiationConfigurer`로 한다**:

```java
@Override
public void configureContentNegotiation(ContentNegotiationConfigurer configurer) {
    configurer.mediaType("json", MediaType.APPLICATION_JSON);
    configurer.mediaType("xml", MediaType.APPLICATION_XML);
}
```

**§6**: **경로 확장자 전략을 쓰지 않는다.**

## Q7. `produces`를 명시하면 무엇이 고정되나 — 매핑에도 영향을 주는가

**응답 형식이 고정되고, 매핑 조건이기도 하다.**

```java
@GetMapping(value = "/materials/{id}", produces = MediaType.APPLICATION_JSON_VALUE)
public MaterialDetail findOne(@PathVariable UUID id) { ... }
```

**두 가지가 동시에 일어난다**:

| 층 | 효과 |
|---|---|
| **협상(2단계)** | `Accept: */*`이 와도 **교집합이 JSON뿐**이라 JSON이 나간다 |
| **매핑** | **`Accept: text/csv`인 요청은 매핑 단계에서 걸러진다** |

> **이렇게 두면 클래스패스에 무엇이 추가되든 응답 형식이 흔들리지 않는다.**

**매핑 조건이라는 사실의 함의**(c3-02 Q5):

```text
Accept: text/csv 로 요청
  → produces = JSON 인 핸들러는 후보에서 빠진다
  → 다른 후보가 없으면 406
  → 컨트롤러 메서드에 아예 들어오지 않는다
```

**즉 방어가 두 겹이다** — 핸들러가 안 불리고(매핑), 불려도 형식이 고정된다(협상).

**전역 설정도 가능하다** — 협상 설정에서 기본 타입을 못 박을 수 있다.

**§2.4의 판단**:

> **API 서버라면 형식을 고정하는 편이 예측 가능성 면에서 낫다 — 콘텐트 협상은 하나의 URL이 여러 표현을 갖는 하이퍼미디어 스타일에서 값어치가 있고, 형식이 하나뿐인 API에서는 위험만 남는다.**

**§6**: **형식이 하나뿐인 API에서 협상에 기대지 않는다. `produces`로 못 박는다.**

## Q8. 406과 500을 가르는 기준

**"고를 컨버터가 없다"(406)와 "골랐는데 그 안에서 터졌다"(500)이다.**

```text
406: 컨버터 선택 실패
     Accept 와 등록된 컨버터의 지원 타입이 겹치지 않는다
     → 직렬화를 시도조차 안 했다

500: 컨버터는 정해졌는데 그 안에서 실패
     순환 참조 · 알 수 없는 필드 · 날짜 포맷 문제
     → 직렬화를 시도했고 실패했다
```

**§5**: **직렬화 실패는 컨버터 선택 실패가 아니다.** **컨버터가 정해진 뒤 그 안에서 실패하는 경우가 있다.** 이건 **406이 아니라 500**이다.

**진단 시 무엇이 달라지나**:

| | 406 | 500 |
|---|---|---|
| 봐야 할 것 | **`Accept` 헤더, `produces`, 등록된 컨버터 목록** | **반환 객체의 구조** |
| 스택 트레이스 | 대개 없다 | **Jackson 예외가 찍힌다** |
| 재현 조건 | **요청 헤더**에 달렸다 | **데이터**에 달렸다 |

**마지막 줄이 중요하다** — 500은 **특정 데이터에서만** 날 수 있다. 순환 참조가 있는 엔티티가 하나뿐이면 **그 하나를 조회할 때만** 터진다.

## Q9. JPA 엔티티를 그대로 반환할 때 이 층에서 생기는 일

**직렬화 도중 두 가지가 터진다 — 지연 로딩 프록시와 양방향 연관의 무한 재귀.**

**§5**:

> **JPA 엔티티를 그대로 반환할 때 자주 겪는다. 지연 로딩 프록시를 Jackson이 직렬화하려다 실패하거나, 양방향 연관에서 무한 재귀에 빠진다.**

```text
[프록시 문제]
  Jackson 이 material.getCompany() 를 부른다
    → 프록시 초기화 시도
    → 트랜잭션이 이미 끝났으면 LazyInitializationException
    → OSIV 가 켜져 있으면 성공하지만 N+1 이 여기서 터진다

[무한 재귀]
  Material → Company → materials → Material → Company → ...
    → StackOverflowError 또는 무한히 커지는 JSON
```

**`part-0-jpa-foundations`의 프록시 내용과 이 층이 만나는 지점이다.**

**그리고 이것은 500이다**(Q8) — **컨버터는 정해졌고, 그 안에서 터졌다.**

**더 나쁜 경우가 있다** — **직렬화가 부분적으로 진행된 뒤 터지면**, 이미 나간 바이트가 있다. 그러면 **200 상태 코드와 깨진 본문**이 나간다(c3-05 Q10).

**§6**: **JPA 엔티티를 그대로 반환하지 않는다. 직렬화 시점에 지연 로딩·순환 참조 문제가 터진다. DTO로 변환한다.**

> **엔티티 대신 DTO를 반환하면 이 문제가 통째로 사라진다.**

**j3-05(OSIV)와 j1-03(DTO 조회)에서 이미 같은 결론에 도달했다** — **세 챕터가 서로 다른 이유로 같은 실무 규칙을 가리킨다**:

| 챕터 | 이유 |
|---|---|
| j1-03 | 더티 체킹·스냅샷 비용, 의도치 않은 UPDATE |
| j3-05 | OSIV를 끄면 트랜잭션 밖에서 지연 로딩 실패 |
| **c3-04 (여기)** | **직렬화가 프록시·순환 참조에서 터진다** |

## Q10. "협상"이라는 이름이 나누는 역할

**클라이언트가 선호를 제시하고, 서버가 그중에서 고른다.**

> **"negotiation(협상)"은 HTTP 명세의 용어다. 클라이언트가 선호를 제시하고(`Accept`) 서버가 그중에서 고른다는 구조가 협상이다. 일방적 지정이 아니라는 점이 핵심이다.**

```text
클라이언트의 역할 : 무엇을 받을 수 있는지 제시한다 (Accept)
                     — 요구가 아니라 제안이다
서버의 역할       : 제안 중 자기가 만들 수 있는 것을 고른다
                     — 못 고르면 406 으로 거절한다
```

**"일방적 지정이 아니다"가 두 방향으로 작동한다**:

| | 클라이언트가 | 서버가 |
|---|---|---|
| **강하게 제시하면** (`Accept: application/json`) | 선택지를 좁힌다 | **고를 여지가 없다** |
| **약하게 제시하면** (`Accept: */*`) | **결정권을 포기한다** | **전부 서버가 정한다** |

**그래서 Q2의 위험이 나온다** — 협상이라는 이름 자체가 **"양쪽이 관여한다"**는 뜻인데, `*/*`은 **한쪽이 관여를 그만두는 것**이다.

**`Message converter`의 "message"도 함께 보면 층이 정리된다**:

> **"message"는 HTTP 메시지, 즉 헤더와 본문으로 이뤄진 하나의 HTTP 단위를 가리킨다. 자바 객체와 HTTP 메시지 본문 사이를 오간다는 뜻이 이름 그대로다.**

**두 이름이 각각의 층을 말한다**:

```text
콘텐트 협상   : 어떤 형식으로 할지 정한다        ← 정책
메시지 컨버터 : 그 형식으로 실제 변환한다        ← 실행
```

**협상이 없으면 컨버터를 고를 수 없고, 컨버터가 없으면 협상 결과를 실행할 수 없다.** 둘이 짝이다.
