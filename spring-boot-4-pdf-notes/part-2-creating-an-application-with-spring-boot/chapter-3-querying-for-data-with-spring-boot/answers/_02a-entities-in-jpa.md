## Q1. record에 `@Entity`를 붙여도 안 되는 세 이유

```java
@Entity
record Video(@Id @GeneratedValue Long id, String name) {}   // 컴파일은 된다
```

1. **인자 없는 생성자가 없다.** record는 모든 컴포넌트를 받는 생성자만 만든다. **JPA는 행을 읽어 올 때 먼저 빈 객체를 만들고 나서 값을 채운다.** 채울 대상이 없으면 시작조차 못 한다.
2. **필드를 바꿀 수 없다.** record의 필드는 `final`이다. **JPA는 조회한 객체의 상태 변화를 추적해 반영하는 것이 일이다.** 바뀌지 않는 객체에는 추적할 것이 없다.
3. **`id`를 나중에 채울 수 없다.** 새 행의 키는 데이터베이스가 정한다. 즉 **객체를 만들 때는 `id`가 없고 저장한 뒤에 생긴다.** record는 그 "나중에 채우기"를 허용하지 않는다.

**컴파일은 통과하고 시작 시점에 실패한다**는 점도 중요하다. 애노테이션은 컴파일러에게 아무 의미가 없다.

## Q2. 세 이유가 나오는 하나의 사실

> **프레임워크가 이 객체를 관리하기 때문이다.**

책이 인과를 정확히 적는다: *"엔티티는 데이터 접근 프레임워크가 **관리하기 때문에**, 그 아래 저장소가 부과하는 특정 요구사항을 함께 갖는 경우가 많다."*

**관리한다는 것의 의미**를 풀면 세 요구가 전부 나온다.

```
관리한다 = 프레임워크가 이 객체를 대신 만들고(→ ①)
           상태 변화를 추적하고(→ ②)
           저장소와 동기화한다(→ ③)
```

- **대신 만든다** → 어떤 값을 넣을지 모르는 상태에서 인스턴스를 먼저 만들어야 한다 → **인자 없는 생성자**
- **변화를 추적한다** → 바뀔 수 있어야 추적할 것이 있다 → **가변 필드**
- **동기화한다** → DB가 만든 키를 객체에 돌려줘야 한다 → **`id` 나중 채우기**

**즉 임의의 제약이 아니라 "관리받는 대가"다.** 관리를 포기하면(순수 JDBC로 직접 매핑) 이 요구도 사라진다.

## Q3. `@Entity`가 엔티티의 정의가 아니라면 무엇인가

**JPA가 엔티티를 알아보는 방법이다.**

책이 범위를 넓힌다: *"엔티티라는 개념이 JPA에서 끝나는 것은 아니다. MongoDB 같은 다른 저장소에서 읽고 쓰는 데 쓰이는 클래스들도, **같은 애노테이션을 요구하지는 않지만** 역시 영속화된 도메인 데이터를 나타낸다. 실무적으로, **데이터 접근에 직접 참여하는 어떤 클래스든** 엔티티로 볼 수 있다."*

**판별 질문**: *"이 클래스가 데이터 접근에 직접 참여하는가?"*

| | 엔티티인가 | `@Entity`가 있는가 |
|---|---|---|
| JPA `VideoEntity` | ✔ | ✔ |
| MongoDB 도큐먼트 클래스 | ✔ | ✘ (`@Document`를 쓴다) |
| Redis에 저장하는 값 객체 | ✔ | ✘ |

**[[01a-using-spring-data-to-easily-manage-data]]의 방침이 여기서도 반복된다** — **개념은 공통이고 표시 방법은 저장소마다 다르다.** 공통 API를 만들지 않는 대신 관례를 공유한다.

## Q4. 인자 없는 생성자를 `protected`로 두는 이유

**프레임워크에는 열어 주고 일반 코드에는 닫는 절충이다.**

| 접근 제어자 | 결과 |
|---|---|
| `private` | **프레임워크가 못 만든다** — 조회 자체가 실패 |
| **`protected`** | **프레임워크는 만들 수 있고, 애플리케이션 코드는 못 만든다** |
| `public` | 동작하지만 **애플리케이션 코드가 필드가 다 비어 있는 엔티티를 아무 데서나 만들 수 있다** |

**`public`이 왜 나쁜가**: `new VideoEntity()`로 만든 객체는 `name`도 `description`도 `null`이다. 그런 객체가 저장 경로에 흘러 들어가면 **원인을 찾기 어려운 데이터**가 생긴다. 어디서 만들어졌는지 추적이 어렵고, 컴파일러도 막지 않는다.

**`protected`가 통하는 이유**: JPA 구현이 리플렉션으로 인스턴스를 만들 때 `protected`까지는 접근할 수 있다. 반면 같은 패키지 밖의 일반 코드에서는 호출할 수 없다.

**설계 원리**: [[02-dtos-entities-and-pojos]]에서 `Video`를 package-private으로 둔 것과 같은 판단이다 — **필요한 만큼만 열고, 넓히는 것은 나중에 할 수 있게 한다.**

## Q5. `save()`가 INSERT인지 UPDATE인지 결정하는 것

**메서드 이름이 아니라 `id`의 `null` 여부다.**

> **`id` 필드가 `null`이면 JPA에게 표에 새 행을 만들고 싶다는 뜻**이 된다.

그래서 `id`를 받지 않는 생성자에 `this.id = null;`을 **명시적으로 써 둔 것이 우연이 아니다.**

```java
VideoEntity(String name, String description) {
      this.id = null;          // ← 이 줄이 INSERT를 만든다
      this.description = description;
      this.name = name;
}
```

**실무 함정**: `id`를 직접 채운 객체를 `save()`하면 **UPDATE**가 된다. 그런데 그 키의 행이 실제로 없으면 의도와 다른 결과가 난다 — 구현에 따라 아무것도 안 하거나 예외가 나거나 새로 만든다.

**그래서 "저장"이라는 한 단어가 두 동작을 덮고 있다는 점을 의식해야 한다.** `save()`는 명령이 아니라 **"이 상태가 되게 하라"**에 가깝다.

## Q6. 저장 명령 없이 UPDATE가 나가는 메커니즘

**관리 상태의 엔티티는 프록시로 감싸여 상태 변화가 추적되고, flush 시점에 자동으로 UPDATE가 나간다.**

객체의 일생으로 보면 이렇다.

1. `new VideoEntity("제목", "설명")` — 아직 JPA가 모르는 평범한 객체. `id`는 `null`
2. `repository.save(...)` — `id`가 `null`이므로 **INSERT**. DB가 키를 만들고 **JPA가 그 값을 객체의 `id` 필드에 써넣는다**
3. 이후 이 객체는 **관리 상태**가 된다. 영속성 계층이 **프록시로 감싸 상태를 감시**한다
4. `entity.setName("새 제목")` — **저장 명령을 부르지 않았는데도 변경이 기록된다**
5. 트랜잭션이 끝나거나 관련 쿼리가 나가기 직전, 그 변경이 **flush**되어 **UPDATE 문이 실행된다**
6. 조회로 다시 꺼낼 때는 JPA가 빈 인스턴스를 만들고 컬럼 값을 채운다

**4→5가 질문의 핵심이다.** 프록시가 `setName()` 호출을 알고 있다가, flush 시점에 "이 객체가 바뀌었다"를 SQL로 바꾼다.

**요구 다섯 개가 전부 이 일생의 어느 한 단계에 대응한다** — 2단계에 `@GeneratedValue`와 가변 필드, 3단계에 프록시, 6단계에 인자 없는 생성자. **임의의 제약이 아니라는 증거다.**

## Q7. 자동 저장 편집기 비유가 깨지는 지점

**편집기의 자동 저장은 "몇 시 몇 분에 저장됨"이 화면에 표시라도 된다. JPA의 flush는 아무 흔적 없이 일어나고, 시점도 내가 정하지 않는다.**

| | 자동 저장 편집기 | JPA flush |
|---|---|---|
| 저장 사실 | **화면에 표시된다** | **흔적이 없다** |
| 시점 | 대개 주기적, 예측 가능 | 트랜잭션 커밋 시, 또는 **그 변경에 영향받는 쿼리 실행 직전**에 알아서 |
| 내가 아는가 | 안다 | **잊는다** |

**결과**: *"`setName()`만 불렀는데 `UPDATE` 문이 나갔다"*가 JPA를 처음 쓸 때 가장 놀라운 지점이 된다.

**더 근본적인 차이**: 편집기는 **저장을 내가 지시하지 않았다는 사실을 계속 인지시킨다.** JPA는 그 사실 자체를 잊게 만든다. 그래서 **"저장을 안 했으니 안 바뀌었겠지"가 성립하지 않는다** — 조회한 엔티티를 임시로 고쳐 화면에 쓰려다 DB까지 바뀌는 사고가 여기서 나온다.

## Q8. 다섯 요구를 일생 단계에 대응시키기

| # | 요구 | 대응하는 일생 단계 | 없으면 |
|---:|---|---|---|
| 1 | **`@Entity`** | **0단계** — 시작 시점에 관리 대상 목록을 만든다 | 매핑 메타데이터가 안 생기고, [[03-creating-repositories-and-declarative-queries]]의 쿼리 파생도 불가능 |
| 2 | **`@Id`** | **3·5단계** — "이 객체와 저 행이 같은 것"의 근거 | 변경을 **어느 행에** 반영할지 알 수 없다 |
| 3 | **`@GeneratedValue`** | **2단계** — DB가 키를 만들어 돌려준다 | 애플리케이션이 키를 정해야 하고 **동시 삽입 충돌을 스스로 처리**해야 한다 |
| 4 | **인자 없는 생성자(`protected`)** | **6단계** — 조회 시 빈 인스턴스를 먼저 만든다 | 조회 결과를 객체로 만들 수 없다 |
| 5 | **`id`를 받지 않는 생성자** | **1·2단계** — `id = null`이 INSERT 신호 | 새 행을 만들 방법이 모호해진다 |

**그리고 명시되지 않은 여섯 번째 요구**: **필드가 가변이어야 한다.** 2단계(DB가 준 키를 써넣는다)와 4단계(변경 추적)에 동시에 필요하다.

**이 대응표가 Q1~Q2를 완성한다** — record가 안 되는 이유(①②③)가 이 표의 4·5·"가변 필드"와 정확히 겹친다.
