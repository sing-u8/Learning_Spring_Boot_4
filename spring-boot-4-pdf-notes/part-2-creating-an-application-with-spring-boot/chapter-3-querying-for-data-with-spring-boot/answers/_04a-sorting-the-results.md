## Q1. `ORDER BY` 없이 조회하면

**어떤 순서로든 돌려줄 수 있다. 같은 쿼리를 두 번 실행해도 순서가 같다는 보장이 없다.**

**왜인가**: SQL 표준이 `ORDER BY` 없는 결과의 순서를 **정의하지 않기 때문이다.** 데이터베이스는 가장 빠른 방법으로 행을 읽고, 그 방법은 실행 계획·인덱스 선택·저장 구조·동시 갱신에 따라 달라진다.

**"삽입 순서로 나온다"는 착각이 위험한 이유**: 작은 표에서는 우연히 그렇게 보인다. 데이터가 늘거나 인덱스가 추가되어 **실행 계획이 바뀌는 순간** 달라진다. 그리고 그 변화는 **코드를 안 고쳤는데** 일어난다.

**규칙**: **순서가 의미 있다면 반드시 명시한다.**

## Q2. 받아서 Java로 정렬하면 걸리는 세 지점

```java
return repository.findByNameContainsIgnoreCase(keyword).stream()
        .sorted(Comparator.comparing(VideoEntity::getName))
        .toList();
```

1. **정렬을 위해 전부 가져와야 한다.** 상위 20건만 필요해도 **매칭된 전부**를 끌어온다. 데이터베이스가 인덱스로 **이미 정렬된 순서를 알고 있을 수도 있는데 그 정보를 버린다.**
2. **페이징과 결합되지 않는다.** "이름순 3페이지"를 요청하려면 정렬이 **데이터베이스 쪽에서** 일어나야 한다. 애플리케이션에서 정렬하면 페이지를 자르기 전에 이미 전부 가져온 뒤다.
3. **정렬 기준이 코드에 고정된다.** 사용자가 "조회수순"을 누르면 다른 `Comparator`를 골라 주는 분기가 또 생긴다.

**2번이 가장 구조적이다.** 정렬과 페이징은 **한 쪽에서 함께 일어나야** 의미가 있다. 나뉘면 페이징의 이득이 통째로 사라진다 — [[04b-limiting-query-results]].

## Q3. `OrderBy`와 `Sort`의 결정적 차이

> **순서를 정하는 주체가 리포지토리 작성자인가, 호출자인가.**

| | `OrderBy` (이름에 박기) | `Sort` 파라미터 (받기) |
|---|---|---|
| 순서를 정하는 주체 | 리포지토리 **작성자** | **호출자** |
| 바꾸려면 | **메서드를 새로 만든다** | 인자만 다르게 넘긴다 |
| 기준이 여럿이면 | 메서드가 기준 수만큼 생긴다 | **메서드는 하나** |
| 잘못된 컬럼 | **시작 시점에 실패** | **런타임에 실패** |
| 적합한 때 | 순서를 **미리 알 때** | **화면이 순서를 고를 때** |

**비유**: `OrderBy`는 메뉴판에 "매운맛"이 고정된 요리, `Sort`는 **주문할 때 맵기를 고르는** 요리다. 후자가 메뉴 수를 줄인다.

## Q4. 오타가 더 일찍 잡히는 쪽

**`OrderBy`다. 시작 시점에 잡힌다.**

**왜인가**: `OrderBy`는 [[04-using-custom-finders]]에서 본 **이름 파싱**을 거친다. 파서가 `@Entity` 매핑 메타데이터에서 그 필드를 찾고, 없으면 **애플리케이션이 시작조차 하지 않는다.**

`Sort`는 **문자열을 런타임에 받는다.** `Sort.by("nmae")`는 컴파일도 되고 시작도 된다. **그 코드가 실제로 실행될 때** 실패한다.

```
OrderByNmae…   → 시작 시 실패. 배포 전에 반드시 걸린다
Sort.by("nmae") → 그 검색 기능을 누군가 쓸 때 실패
```

**이것이 §2.1 표의 교환 조건이다** — 유연성을 얻으면 검증 시점을 잃는다.

**중간 지점이 `TypedSort`다** → Q6. `Video::getName`은 메서드 참조라 **컴파일 시점에** 잡힌다.

## Q5. `.and()`로 이은 순서의 영향

**선언 순서가 곧 우선순위다.**

```java
Sort.by("name").ascending().and(Sort.by("description").descending())

→ ORDER BY name ASC, description DESC
```

**`name`이 같은 행들끼리만 `description`으로 다시 줄 세운다.**

```
name        description
-----------------------
Spring A    zzz          ← name이 다르면 description은 아예 안 본다
Spring A    aaa
Spring B    yyy
```

**순서를 바꾸면 완전히 다른 결과가 된다.**

```java
Sort.by("description").descending().and(Sort.by("name").ascending())
→ ORDER BY description DESC, name ASC     ← 전혀 다른 정렬
```

책이 이 API를 **"fluent"**라 부르는 것도 이유가 있다. 각 메서드가 다시 `Sort`를 돌려주므로 점으로 이어 붙일 수 있고, **소리 내어 읽으면 그대로 "이름으로, 오름차순으로, 그리고 설명으로"가 된다.**

## Q6. `TypedSort`가 얻는 것과 치르는 대가

```java
TypedSort<Video> video = Sort.sort(Video.class);
Sort sort = video.by(Video::getName).ascending()
    .and(video.by(Video::getDescription).descending());
```

| | 문자열 방식 | **`TypedSort`** |
|---|---|---|
| **오타 발견** | 그 코드가 실행될 때 | **컴파일할 때** |
| **필드 이름 변경** | 문자열을 찾아 고쳐야 한다 | **IDE 리팩터링이 함께 바꾼다** |
| 코드 길이 | 짧다 | **준비 줄이 하나 더** 필요 |
| 읽기 | 간단하다 | 익숙해지면 의도가 더 분명 |

**얻는 것**: `Video::getName`은 메서드 참조다. **그런 메서드가 없으면 컴파일이 안 된다.** Q4의 "런타임에 실패"를 컴파일 시점으로 끌어온다.

**대가**: `Sort.sort(Video.class)` 준비 줄과 전반적인 길이. **정렬 기준이 하나로 고정된 짧은 코드라면 문자열이 읽기 쉬울 수 있다** — 항상 나은 것은 아니다.

## Q7. 웹 요청의 정렬 컬럼을 그대로 `Sort`에 넣으면

**두 가지가 위험하다.**

1. **성능**: 인덱스가 없는 컬럼으로 정렬을 요청받으면 데이터베이스가 **전체 정렬(full sort)**을 한다. 응답이 무너진다. 그리고 이건 **호출자가 마음대로 일으킬 수 있는 비용**이다.
2. **정보 노출**: 잘못된 컬럼 이름에 대한 오류 메시지가 **노출할 의도가 없던 컬럼 이름**을 드러낼 수 있다.

**비유가 깨지는 지점이 정확히 여기다.** 식당은 맵기 선택지가 늘어도 주방 일이 조금 늘 뿐이다. **`Sort`는 호출자가 아무 컬럼이나 넣을 수 있게 열어 준다.**

> **선택지를 열어 준다는 것은 나쁜 선택지까지 열어 준다는 뜻이다.**

**메뉴판에는 없는 요리를 손님이 주문할 수 없지만, `Sort`에는 그런 방어가 기본으로 없다.**

**대응**: **허용 목록(allow-list)으로 거른다.** 정렬 가능한 컬럼을 미리 정해 두고, 그 밖의 값이 오면 거부하거나 기본값으로 대체한다.

## Q8. 책의 `TypedSort` 예제가 컴파일되지 않는 이유

**도메인 타입과 접근자 이름이 둘 다 어긋난다.**

```java
TypedSort<Video> video = Sort.sort(Video.class);   // ①
video.by(Video::getName)                            // ②
```

| # | 문제 |
|---|---|
| ① | 이 장에서 만든 **엔티티는 `VideoEntity`**다. `Video`가 아니다 |
| ② | [[../chapter-2-creating-web-and-api-applications-with-spring-boot/04a-adding-demo-data-to-a-template|Chapter 2의 `Video`]]는 **getter가 없는 record**다. record는 `getName()`이 아니라 **`name()`**을 만든다 |

**②가 더 근본적이다.** [[02-dtos-entities-and-pojos]]에서 본 대로 record는 JavaBean 관례를 따르지 않는다.

**올바른 형태**:
```java
TypedSort<VideoEntity> video = Sort.sort(VideoEntity.class);
video.by(VideoEntity::getName)...
```

[[02a-entities-in-jpa]]의 `VideoEntity`에는 **getter/setter가 있으므로** 그대로 동작한다.

**어떻게 읽어야 하나**: **JavaBean 관례를 따르는 엔티티를 가정한 예시**로 읽는 것이 맞다. 책이 `TypedSort` 개념을 설명하려고 일반적인 이름을 쓴 것이지, 이 장의 코드에 붙여 쓰라는 뜻이 아니다.

**교훈**: 책의 코드 조각을 **문맥 없이 복사하면** 이런 어긋남이 생긴다. 특히 이 장은 `Video`(DTO)와 `VideoEntity`(엔티티)를 **의도적으로 나눠 놓았으므로** 어느 쪽 이야기인지 매번 확인해야 한다.
