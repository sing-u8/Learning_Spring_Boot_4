## Q1. 저장소 결정을 건너뛰면 무너지는 세 지점

1. **데이터 모델이 저장소를 따라간다.** 문서 저장소면 중첩 구조가 자연스럽고, 관계형이면 표로 쪼개 조인해야 한다. **나중에 바꾸면 도메인 클래스부터 다시 그린다.**
2. **보장의 수준이 달라진다.** "결제와 재고 차감이 동시에 되거나 동시에 안 된다"를 저장소가 보장해 주는지가 **애플리케이션 코드의 복잡도를 결정한다.**
3. **되돌리기가 가장 비싼 결정이다.** 웹 프레임워크도 템플릿 엔진도 바꿀 수 있다. **운영 중인 데이터를 다른 저장소로 옮기는 일은 별도 프로젝트가 된다.**

**3번이 다른 둘을 무겁게 만든다.** 1·2번의 실수는 그 자체로는 고칠 수 있지만, 3번 때문에 고치는 비용이 시간이 갈수록 기하급수로 는다.

## Q2. 애플리케이션 코드 복잡도에 직접 영향을 주는 근거

**강한 ACID 보장이다.**

네 근거(성숙도 / ACID / 풍부한 도구 / 약 80% 채택률) 중 나머지 셋은 **개발 환경과 팀의 문제**다. 도구가 많으면 편하고, 아는 사람이 있으면 빠르다. 하지만 **코드 자체는 안 바뀐다.**

ACID는 다르다. **없으면 "절반만 반영된 상태"를 애플리케이션이 직접 처리해야 한다.**

```
ACID 있음:  트랜잭션 경계만 열고 닫는다
ACID 없음:  "결제는 됐는데 재고는 안 줄었다"를
            감지하고 → 보정하고 → 재시도하고 → 그 재시도도 실패하면…
```

**그 보정 로직이 곧 복잡도다.** 그리고 그것은 없어도 되는 코드가 아니라 **저장소가 안 해 주면 반드시 누군가 써야 하는** 코드다.

## Q3. Redis·MongoDB·Cassandra가 각각 잘하는 일

**강점이 전부 데이터 모델에서 직접 나온다.**

| 저장소 | 모델 | 강점 | **그 강점이 나오는 이유** |
|---|---|---|---|
| **Redis** | 키-값 | 매우 빠름. TTL, 원자적 연산, 카운터 | **조회 경로가 "키 → 값" 한 단계뿐**이라 인덱스 탐색과 조인이 아예 없다 |
| **MongoDB** | 문서 | 중첩 문서 저장, 집계 파이프라인 | **함께 읽을 데이터가 한 문서 안에** 있어 조인 없이 한 번에 읽힌다 |
| **Cassandra** | 표 비슷한 구조 | **일관성을 성능과 맞바꾸는 제어권** | **데이터가 여러 노드에 복제**되어 있어 몇 개에게 물어볼지 요청마다 고를 수 있다 |

**즉 "무엇을 빼서 무엇을 얻었나"가 각각 다르다.** Redis는 검색 능력을 빼고 속도를 얻었고, MongoDB는 조인을 빼고 한 번 읽기를 얻었고, Cassandra는 단일 진실을 빼고 확장성과 조절 가능성을 얻었다.

**그래서 "NoSQL이 빠르다"는 말은 무엇에 대해 빠른지를 빼면 틀린다.** 여러 조건으로 검색하고 집계하는 작업이라면 잘 인덱싱된 관계형이 더 빠를 수 있다.

## Q4. Cassandra의 정족수 읽기와 "일관성은 눈금"

**일관성이 켜짐/꺼짐의 이분법이 아니라 요청마다 고를 수 있는 값이 된다.**

| 읽기 방식 | 속도 | 보장 |
|---|---|---|
| 단일 노드 읽기 | 가장 빠름 | 가장 약함 — 그 노드가 낡았을 수 있다 |
| **정족수(quorum) 읽기** | **중간** | **중간** — 과반이 동의한 값 |
| 모든 복제본 대기 | 가장 느림 | 가장 강함 |

정족수 읽기는 **모든 복제본을 기다리는 것보다 빠르면서도 단일 노드 읽기보다는 강한 보장**을 준다.

**핵심은 이 선택이 요청마다 가능하다는 것이다.** 같은 애플리케이션에서 "잔액 조회"는 강한 보장으로, "좋아요 수 표시"는 빠른 쪽으로 읽을 수 있다. 관계형에서는 이런 눈금이 아예 없다 — 애초에 데이터가 한 곳에 있으니 **그 문제가 생기지 않는다.**

**비유가 깨지는 지점이 여기다.** 회계 장부는 종이 한 권이라 느릴 것 같지만, 관계형이 느린 것이 아니다. **비싼 것은 "여러 대의 기계에 데이터를 흩어 놓고도 즉시 일치를 보장하는 일"**이고, 그건 장부가 한 권일 때는 생기지 않는 문제다.

## Q5. 스키마를 "보장의 출처"로 설명하기

스키마를 "번거로운 절차"로만 읽으면 **절반만 이해한 것**이다. 실제로 하는 일 셋:

1. **읽는 쪽이 구조를 가정할 수 있게 한다.** `name` 컬럼이 항상 있으니 조회 코드가 `null` 검사를 덜 한다.
2. **잘못된 쓰기를 데이터베이스가 거부한다.** **애플리케이션 버그가 데이터를 오염시키는 경로를 하나 막는다.** 코드는 여러 곳에서 쓰지만 제약은 한 곳에 있다.
3. **최적화의 근거가 된다.** 타입과 제약을 알아야 인덱스와 실행 계획을 제대로 세운다.

**즉 제약은 비용이자 동시에 보장의 출처다.** 스키마를 없애면 세 가지가 전부 애플리케이션 쪽으로 넘어온다 — 2번이 특히 뼈아프다. 데이터베이스가 안 막으면 **모든 쓰기 경로가 각자 막아야** 한다.

## Q6. "NoSQL이 관계형의 모든 기능을 흉내 내면 장점을 잃는다"

**빠름은 기능을 더 넣어서 얻은 것이 아니라 빼서 얻은 것이기 때문이다. 그래서 다시 넣으면 사라진다.**

책의 문장: *"NoSQL 저장소가 관계형 저장소의 모든 기능(일관성, 트랜잭션, 고정 구조)을 흉내 내려 든다면, 아마도 그것들을 더 빠르고 확장성 있게 만들어 준 바로 그 특징을 잃게 될 것이다."*

논리를 풀면 이렇다.

```
Redis가 빠른 이유    = 조회가 "키 → 값" 한 단계뿐이다
                       ↓ 그런데 조인과 다중 조건 검색을 넣으면?
                       인덱스 탐색이 생기고 한 단계가 여러 단계가 된다
                       → 더 이상 빠르지 않다

Cassandra가 확장되는 이유 = 노드 간 즉시 일치를 요구하지 않는다
                       ↓ 그런데 강한 일관성을 넣으면?
                       모든 쓰기가 노드 간 합의를 기다린다
                       → 더 이상 확장되지 않는다
```

**트레이드오프는 선택이지 결함이 아니다.** 그리고 트레이드오프의 정의상, **한쪽을 되찾으면 다른 쪽을 내놓는다.**

실제로 현대 NoSQL 대부분이 지금은 트랜잭션을 지원하지만 **범위·일관성 수준·성능에 제약이 따른다** — 정확히 이 논리대로다.

## Q7. "NoSQL은 스키마가 없다"가 부정확한 이유

**데이터베이스가 스키마를 강제하지 않는다는 뜻이지 스키마가 없다는 뜻이 아니다.**

읽는 코드는 **여전히 어떤 필드가 있을 것이라 가정하고 동작한다.** `doc.get("name")`을 쓰는 순간 "name이라는 필드가 있다"는 스키마를 가정한 것이다.

**스키마가 사라진 것이 아니라 데이터베이스에서 애플리케이션 코드로 옮겨 갔다.** 그래서 **"schema-on-read"**라는 표현이 더 정확하다 — 쓸 때는 안 따지고 읽을 때 따진다.

**옮겨 간 결과**:
- 강제하는 주체가 하나(DB)에서 여럿(모든 읽기 코드)이 된다.
- 위반이 쓰기 시점이 아니라 **읽기 시점에** 드러난다. 잘못된 데이터가 이미 저장된 뒤다.
- 필드가 있는 레코드와 없는 레코드가 섞이므로 **모든 읽기가 방어 코드를 쓴다.**

**Q5의 세 항목이 그대로 반대로 작용한다.**

## Q8. 관계형을 골랐는데도 NoSQL에 통한다는 근거

**Spring Data가 관계형과 비관계형을 아우르는 일관된 프로그래밍 모델을 제공하기 때문이다.**

책은 관계형을 고르면서 곧바로 경계를 긋는다 — *"이 장의 예제는 관계형을 쓰지만, 다루는 기능은 SQL 기반 시스템에 국한되지 않는다."*

**그런데 이 "일관됨"이 무엇인지는 정확히 알아야 한다.** 다음 노트가 그 구조를 밝힌다 — Spring Data는 **공통 API를 만들지 않는다.** 저장소마다 전용 모듈을 두되, 그 위의 **repository 층**에서 도메인 타입만으로 연산을 표현하게 한다.

그래서 통하는 범위도 그 층에 한정된다.

| | 옮겨 가는가 |
|---|---|
| repository 인터페이스 선언 방식 | **통한다** |
| 파생 finder의 이름 규칙 | **대체로 통한다** |
| template을 쓴 코드 | 안 통한다 |
| `@Entity` 같은 저장소 고유 애노테이션 | 안 통한다 |
| 트랜잭션 의미론 | 안 통한다 |

**Spring Data가 주는 것은 이식성이 아니라 일관된 학습 곡선에 가깝다** — [[01a-using-spring-data-to-easily-manage-data]].
