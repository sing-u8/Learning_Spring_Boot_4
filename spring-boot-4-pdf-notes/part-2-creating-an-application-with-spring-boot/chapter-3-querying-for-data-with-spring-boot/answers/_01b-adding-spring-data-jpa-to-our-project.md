## Q1. 좌표를 손으로 쓸 때 이번에 특히 어려운 이유

Chapter 2에서 본 문제가 돌아오되 **더 나쁘다.**

1. **한 개가 아니라 네 개다.** 넷의 groupId·artifactId·**scope**를 전부 맞혀야 한다. 틀릴 자리가 네 배다.
2. **Boot 4에서 이름이 바뀌었다.** Boot 3에서 통했던 좌표를 그대로 쓰면 없는 아티팩트가 된다. **`spring-boot-h2console`이 정확히 그런 경우다.**
3. **scope를 틀리면 조용히 잘못된다.** `h2`를 `runtime`이 아니라 기본 scope로 넣으면 **컴파일도 되고 실행도 된다.** 다만 애플리케이션 코드가 H2 클래스를 직접 참조할 수 있게 되어 나중에 다른 DB로 옮길 때 발목을 잡는다.

**3번이 가장 위험하다.** 1·2번은 빌드가 즉시 실패해 알려 주지만, 3번은 **몇 달 뒤 DB를 교체할 때** 드러난다 → Q3.

## Q2. 5단계를 `GENERATE`로 바꾸면

**별개의 새 프로젝트 ZIP이 내려온다.** 그것을 기존 폴더에 풀면 `.git`·소스·`pom.xml`이 **전부 덮인다.**

Chapter 2에서 세운 판별 질문이 그대로 적용된다 — **"내 작업 폴더가 이미 존재하는가?"** 존재하면 `EXPLORE`다.

**이 절차에서 `EXPLORE`가 핵심인 이유**: 우리가 원하는 것은 **좌표 계산 결과**뿐이다. 메인 클래스도 wrapper도 이미 있다. `GENERATE`는 필요 없는 것까지 전부 주면서 있는 것을 덮는다.

**2단계에서 "같은" artifact 정보를 넣는 이유도 같은 맥락이다** — 지금 내 프로젝트와 **같은 전제**(Boot 버전·Java 버전) 위에서 좌표가 계산되게 하려는 것이다.

## Q3. `h2`에 `runtime` scope를 주면 무엇이 막히나

**애플리케이션 코드가 `org.h2.*` 클래스를 직접 import하는 일이 원천적으로 막힌다.**

`runtime`은 **컴파일할 때는 안 보이고 실행할 때만 있다**는 뜻이다.

| scope | 컴파일 경로 | 실행 경로 |
|---|---|---|
| 기본(compile) | **있다** — 코드가 참조 가능 | 있다 |
| **`runtime`** | **없다** — 참조하면 컴파일 오류 | 있다 |

**즉 데이터베이스를 교체할 수 있는 상태를 컴파일러가 지켜 준다.**

이것이 왜 중요한가. H2는 **프로토타이핑용**이고 언젠가 PostgreSQL로 바꾼다. 그때 코드 어딘가에 `org.h2.jdbcx.JdbcDataSource`가 박혀 있으면 그 줄부터 고쳐야 한다. `runtime`은 **그런 줄이 애초에 생기지 못하게** 한다.

JDBC 드라이버는 원래 이 scope가 맞다 — 코드는 `java.sql.*` 표준 API만 쓰고, 실제 드라이버는 실행 시점에 발견되면 된다.

## Q4. 테스트 지원이 자동 포함되도록 바꾼 의도

**"테스트는 나중에 생각할 것"이라는 기본값을 뒤집는 것이다.**

책의 서술: *"Spring Data JPA를 추가하면 관련 테스트 지원 의존성이 새 자동 구성 모듈화의 일부로 **자동 포함된다.** 필요 없으면 제거해도 된다."*

**예전 흐름**: 테스트 슬라이스(`@DataJpaTest`)를 쓰려면 → 그런 게 있는지 알아야 하고 → 별도로 의존성을 찾아 넣어야 했다. **그 마찰이 곧 "테스트를 안 쓰는" 경로가 됐다.**

**바뀐 흐름**: 기본으로 있으니 **쓰는 것이 기본, 빼는 것이 선택**이다.

이것은 Boot 전체의 back-off 철학과 같은 형태다 — **흔히 원하는 것을 기본으로 주되 언제든 물러날 수 있게** 한다.

> ⚠ **좌표 주의**: 책은 `spring-boot-starter-data-jpa-test`로 적지만 ✅ Boot 4.1.0 공식 테스트 문서는 `@DataJpaTest`가 **`spring-boot-data-jpa-test` 모듈**에서 온다고 설명한다(문서는 이 계열을 `spring-boot-*-test` **모듈**로 부른다). 이름이 미묘하게 다르므로 **Initializr가 내주는 좌표를 그대로 복사하는 것이 확실하다** — 이 절차가 EXPLORE로 시작하는 이유가 여기에도 있다.

## Q5. H2를 드라이버와 콘솔로 나눈 것이 왜 보안과 관계있나

**운영 배포물에 웹 콘솔이 딸려 들어가는 것은 보안 표면을 늘리는 일이기 때문이다.**

H2 웹 콘솔은 **브라우저에서 데이터베이스 내용을 그대로 조회·수정할 수 있는 화면**이다. 개발 중에는 편리하지만 운영에 열려 있으면 그 자체가 취약점이다.

**Boot 3까지**: 드라이버를 넣으면 콘솔 지원이 함께 왔다. "안 켜면 되지"라고 하지만, **의존성이 클래스패스에 있다는 것 자체가** 조건부 자동 구성의 입력이 되고 설정 실수 하나로 켜질 수 있다.

**Boot 4**: 드라이버(`com.h2database:h2`)와 콘솔(`spring-boot-h2console`)이 **별도 의존성**이다. 콘솔을 안 넣으면 **애초에 클래스패스에 없다.** 설정 실수로도 켜지지 않는다.

**선택이 명시적으로 갈린다** — 내장 데이터베이스만 원하는가, 웹 콘솔까지 원하는가.

> ✅ **보강**: Boot 4.1.0의 `spring-boot-h2console` 모듈은 실제로 `com.h2database:h2`를 자기 api 의존성으로 이미 갖고 있다. 그러면 책이 `h2`를 **따로 또** 넣는 이유는? 두 가지다 — (1) 콘솔을 뺐을 때도 드라이버는 남아야 하므로 **의도를 명시적으로** 적어 두는 것, (2) **`runtime` scope를 직접 지정**해 컴파일 경로에서 H2를 밀어내기 위해서다(Q3). 콘솔 모듈을 통해 전이로 들어온 `h2`는 이 scope 제어를 받지 않는다.

## Q6. 세 변화의 방향이 하나인가

**그렇다. "숨은 동작에 대한 의존을 줄인다"가 셋을 관통한다.**

| 변화 | 이전 | Boot 4 |
|---|---|---|
| 테스트 지원 | 알아서 찾아 넣어야 함 | **기본으로 따라옴** (빼는 것이 선택) |
| H2 콘솔 | 드라이버를 넣으면 딸려 옴 | **명시적으로 골라야 함** |
| 영속성 기본값 | 자동 적용 | **일부는 명시적 설정 필요** |

**방향이 반대로 보이지만 아니다.** 하나는 더 주고 둘은 덜 주는데, 규칙은 하나다.

> **흔히 원하는 것은 기본으로, 사람마다 다른 것은 명시적으로.**

테스트 지원은 **거의 항상 원한다.** 웹 콘솔과 MongoDB 매핑 규칙은 **상황마다 다르다.** 그래서 앞의 것은 기본값이 되고 뒤의 것은 선택이 된다.

**"모듈화"라는 말의 실질**이 이것이다 — 덩어리를 쪼개면 무엇이 언제 켜지는지가 보인다.

> ✅ **보강**: 책은 `spring-boot-persistence`의 이름과 성격만 말한다. Boot 4.1.0에서 이 모듈에는 `PersistenceExceptionTranslationAutoConfiguration`이 들어 있고, `@Repository`가 붙은 빈의 저수준 예외를 Spring 공통 예외 계층으로 바꿔 주는 후처리기를 등록한다. `spring.persistence.exceptiontranslation.enabled`로 끌 수 있다. Note가 말한 "예외 변환 관련 프로퍼티 이름 변경"의 실체가 이것이다.

## Q7. JPA·Hibernate·Spring Data JPA를 패키지 이름으로

> **판별 질문: "이 타입이 어느 패키지에 있는가?"**

| 층 | 무엇인가 | 패키지 |
|---|---|---|
| **JPA** | **명세** — 무엇을 해야 하는지 | **`jakarta.persistence.*`** |
| **Hibernate** | 그 명세의 **구현** — 실제로 하는 것 | **`org.hibernate.*`** |
| **Spring Data JPA** | 그 위의 **repository 추상화** — 덜 쓰게 해 주는 것 | **`org.springframework.data.*`** |

`@Entity`는 `jakarta.persistence`, `@DynamicUpdate`는 `org.hibernate.annotations`, `JpaRepository`는 `org.springframework.data.jpa.repository`다.

**이름의 유래도 여기서 갈린다.** JPA는 원래 **Java** Persistence API였지만, Java EE가 Eclipse 재단으로 옮겨 **Jakarta** EE가 되면서 명세 이름도 Jakarta Persistence로 바뀌었다. Boot 4가 `jakarta.persistence` 패키지를 쓰는 이유이며 — [[../chapter-1-core-features-of-spring-boot/02-adding-portfolio-components-using-spring-boot-starters|Ch1의 Jakarta EE 논의]]와 같은 이관이다 — 책이 여전히 "JPA"라고 부르는 것은 관용적 표기다.

**실무적 의미**: `org.hibernate.*`를 import하는 순간 **JPA 표준을 벗어난다.** 되는 일이 많아지지만 구현 교체 가능성을 그만큼 잃는다.

## Q8. 책이 말하지 않은 전제

**표(테이블)가 어떻게 만들어지는지 말하지 않는다.**

이 절차대로 하면 예제가 도는 것은 **내장 데이터베이스일 때 JPA 구현이 스키마를 자동 생성해 주기 때문**이다. Boot가 임베디드 DB를 감지하면 `ddl-auto`를 `create-drop` 상당으로 두어, 시작할 때 엔티티에서 표를 만들고 종료할 때 지운다.

**실제 데이터베이스에서는 이 가정이 성립하지 않는다.**

- 운영 DB에 `create-drop`을 쓸 수는 없다 — 재시작마다 데이터가 사라진다.
- `update` 모드도 운영에서는 위험하다 — 무엇을 어떻게 바꿀지 예측할 수 없다.
- **스키마 관리(Flyway·Liquibase 같은 마이그레이션 도구)가 별도로 필요해진다.**

**다른 전제 하나 더**: **H2에서 통과한 쿼리가 PostgreSQL에서 다르게 동작할 수 있다.** SQL 방언, 함수, 타입 처리가 다르다. 책도 H2를 "프로토타이핑에 효과적"이라고만 하지 운영용이라고 하지 않는다. 실제 DB로 검증하는 방법은 Chapter 5의 Testcontainers에서 다룬다.

**이 두 전제가 "데모는 돌지만 운영은 다르다"의 실체다.**
