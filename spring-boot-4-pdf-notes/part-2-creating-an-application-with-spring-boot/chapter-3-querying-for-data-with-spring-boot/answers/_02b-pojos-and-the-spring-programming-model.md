## Q1. 프레임워크 클래스를 상속하면 테스트가 막히는 세 이유

1. **`new MyService()`가 성립하지 않는다.** 상위 클래스의 생성자가 프레임워크 컨텍스트, 설정 객체, 커넥션 따위를 요구한다.
2. **상위 클래스의 동작을 끊을 수 없다.** 내 메서드가 상위의 `protected` 메서드를 부르는데, 그것이 **실제 데이터베이스나 네트워크를 건드린다.** 상속 관계라 갈아 끼울 수도 없다.
3. **결국 프레임워크를 띄운다.** 테스트 하나에 컨테이너 기동 시간이 붙는다.

책의 표현: *"프레임워크에서 상속받은 요구사항 때문에 테스트 케이스를 쓰기에 적합하지 않았다. 사용자가 만든 코드가 제대로 도는지 확인하려면 **모든 것을 다 띄워야 하는** 경우가 잦았다."*

## Q2. "결국 프레임워크를 띄운다"가 왜 진짜 비용인가

**느린 테스트는 안 쓰는 테스트가 되기 때문이다.**

인과 사슬이 길지만 확실하다.

```
테스트 하나에 컨테이너 기동 시간이 붙는다
      ↓
테스트를 자주 안 돌리게 된다
      ↓
피드백 주기가 길어져 테스트의 값이 떨어진다
      ↓
테스트를 안 쓰게 된다
```

**1·2번은 "불편하다"이지만 3번은 "안 하게 된다"다.** 불편한 것은 참을 수 있지만, 안 하게 되는 것은 회복되지 않는다.

**그리고 이 비용은 눈에 안 보인다.** "테스트를 안 썼다"는 커밋 diff에 나타나지 않는다. 상속 강제가 만든 진짜 손실은 느린 테스트가 아니라 **없는 테스트**다.

## Q3. POJO라는 이름이 반어적으로 붙었다는 말

**"평범한 옛날 Java 객체"에 그럴듯한 이름이 없어서 사람들이 그것을 쓰기를 꺼린다고 보고, Martin Fowler와 동료들이 2000년경 일부러 거창한 약어를 붙인 것이다.**

**즉 이 용어는 새 기술의 이름이 아니라, 아무것도 안 하는 것에 이름을 붙여 선택지로 만든 것이다.**

당시 분위기를 생각하면 논리가 보인다. EJB, Struts 같은 이름이 붙은 것은 "제대로 된 엔터프라이즈 방식"으로 보이고, 그냥 클래스를 쓰는 것은 "아마추어"로 보였다. **이름이 없으면 선택지로 인식되지 않는다.**

**이름을 붙이자 비교가 가능해졌다** — "EJB로 할까 POJO로 할까"라는 문장이 성립하게 된 것이 이 작명의 성과다.

## Q4. 빈 등록이 왜 프록시의 전제 조건인가

> **내가 `new`로 만들면 아무도 감쌀 수 없기 때문이다.**

단계로 보면 2단계가 열쇠다.

1. 개발자가 아무것도 상속하지 않은 클래스를 쓴다 — 테스트에서 `new`로 만들 수 있게
2. **그 클래스를 컨테이너에 빈으로 등록한다** — 컨테이너가 **인스턴스 생성 시점을 통제**해야 그 자리에 다른 것을 끼워 넣을 수 있으므로
3. 컨테이너가 **원본 대신 프록시**를 만들어 등록한다 — 호출을 가로챌 지점이 필요하므로
4. 프록시가 호출 전후에 부가 동작을 하고 원본에 위임한다 — 원본 코드를 안 건드리고 기능을 더하려고
5. 주입받는 쪽은 **원래 타입으로** 받는다 — 호출 코드가 이 구조를 몰라도 되게

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04c-injecting-dependencies-through-constructor-calls|Chapter 2의 "누가 `new`를 부르는가"]]가 여기서 회수된다.** 거기서는 "인자를 누가 고르는가"가 요점이었는데, 여기서는 **"그 자리에 무엇을 놓을 수 있는가"**가 요점이다. 컨테이너가 생성을 통제하기 때문에 프록시를 놓을 수 있다.

바깥에서 붙이는 이런 기능을 **횡단 관심사**라 한다 — 트랜잭션, 보안, 로깅, 캐시.

## Q5. `VideoService`가 "트랜잭션을 알 필요조차 없다"

**`VideoService`의 소스 어디에도 트랜잭션이라는 말이 없는데 운영에서는 트랜잭션 안에서 돈다.**

책: *"이것이 `VideoService`를 **단위 테스트하기 쉽게** 만들었다. 서비스가 제 일을 하는지 확인하면서도, **트랜잭션 지원은 서비스가 알 필요조차 없는 구성 단계**가 되었다."*

**코드 수준에서 보면**:

```java
@Service
public class VideoService {          // 상속 없음. 트랜잭션 관련 코드 없음
    private final VideoRepository repository;
    public VideoService(VideoRepository repository) { ... }
    public Video create(Video v) { return repository.save(v); }
}
```

| | 운영 | 테스트 |
|---|---|---|
| 무엇이 만드나 | 컨테이너 → **프록시로 감싼다** | `new VideoService(fakeRepository)` |
| 트랜잭션 | **적용된다** | 적용 안 된다 (필요 없다) |
| 코드 | **똑같다** | 똑같다 |

**같은 클래스가 두 환경에서 다르게 동작하는데, 그 차이가 클래스 밖에 있다.** 이것이 "알 필요조차 없다"의 실체다.

**대비하면 명확하다** — 상속 방식이라면 `extends TransactionalServiceSupport` 같은 것이 소스에 박혀 있고, 테스트에서도 그 상위 클래스가 요구하는 것을 다 갖춰야 한다.

## Q6. self-invocation에서 `@Transactional`이 안 걸리는 이유

**그 호출이 프록시를 거치지 않기 때문이다.**

```
바깥 호출:   호출자 → [프록시] → 원본.methodA()      ✅ 트랜잭션 적용
자기 호출:            원본.methodA() → this.methodB()  ❌ 프록시를 안 지난다
```

프록시는 **바깥에서 들어오는 호출을 가로채는 껍데기**다. 원본 객체 안에서 `this.methodB()`를 부르면 그건 이미 껍데기 **안쪽**이라 가로챌 지점이 없다.

**비유가 깨지는 지점이 정확히 여기다.** 케이스는 눈에 보이고 손으로 떼어낼 수 있다. 하지만 프록시는 **호출하는 쪽이 그 존재를 모른다.** 그래서 안쪽에서 부르면 그냥 평범한 메서드 호출이 되고, **아무 경고도 없다.**

**같은 이유로 안 걸리는 것들**: `private` 메서드, `final` 클래스·메서드. 전부 "프록시가 감쌀 수 없는 자리"다.

**해법**: 메서드를 **다른 빈으로 옮기거나** 호출 경로를 바깥으로 돌린다. 주입 방식을 바꾸는 것으로는 해결되지 않는다 — 구조의 문제다.

## Q7. 애노테이션만 붙은 클래스가 POJO인가 — 책의 판단 기준

**책은 결론 대신 기준을 준다: "POJO로 쌓아 올린 애플리케이션을 검증할 수 있는가."**

책: *"**애노테이션만 붙인 것(다른 건 아무것도 없이)이 정말 POJO인지는 아마 논쟁의 여지가 있을 것이다.** 하지만 POJO로 쌓아 올린 애플리케이션을 검증한다는 발상은 우리 시스템에 대한 확신을 더 빨리 쌓게 해 준다."*

**양쪽 논리**:

| POJO가 아니다 | POJO다 |
|---|---|
| `@Transactional`은 결국 **프레임워크의 타입**이다 | 애노테이션은 **동작을 바꾸지 않는 메타데이터**다 |
| import되어 있으면 Spring 없이 의미가 없다 | `new`로 만들 수 있고, 메서드를 직접 불러 테스트할 수 있고, **상위 클래스 생성자 요구가 없다** |

**이 기준으로 보면 애노테이션이 붙은 클래스는 여전히 POJO 쪽이다.** 상속과 결정적으로 다른 점은 **테스트에서 프레임워크를 띄우지 않아도 된다**는 것이기 때문이다.

**같은 기준을 엔티티에도 적용할 수 있다.** [[02a-entities-in-jpa]]의 `VideoEntity`는 `@Entity`와 `protected` 생성자 요구를 받지만 **아무것도 상속하지 않으므로** `new VideoEntity("a", "b")`로 만들어 테스트할 수 있다. 순수성에서 한 걸음 물러났을 뿐 **상속 강제와는 성격이 다르다.**

## Q8. "애노테이션 자체는 아무것도 하지 않는다"와 테스트 용이성

**애노테이션은 표시일 뿐이고, 그것을 읽고 프록시를 만드는 컨테이너가 동작을 만든다.**

**그래서 컨테이너 밖에서 `new`로 만든 객체에 `@Transactional`이 붙어 있어도 아무 일도 일어나지 않는다.**

이 하나의 사실이 **정반대로 보이는 두 결과를 동시에 설명한다.**

| | 결과 |
|---|---|
| **테스트에서** | **좋다** — `new VideoService(fake)`로 만들면 트랜잭션도 프록시도 없이 순수 로직만 돈다. 컨테이너를 안 띄워도 된다 |
| **self-invocation에서** | **나쁘다** — 프록시를 안 지나면 애노테이션이 붙어 있어도 무시된다 (Q6) |

**같은 성질의 두 얼굴이다.** "애노테이션이 스스로 동작하지 않는다"가 테스트를 쉽게 만들고, 동시에 self-invocation 함정을 만든다.

**그리고 이것이 Q7의 논쟁에 답을 주는 방식이기도 하다.** 애노테이션이 동작을 바꾸지 않기 때문에 그 클래스는 **애노테이션이 없는 것처럼 테스트할 수 있고**, 그래서 POJO의 실질적 이득(빠른 검증)을 그대로 유지한다.

**경계**: "테스트가 쉽다"는 **단위 테스트**에 대한 이야기다. 트랜잭션 경계가 의도대로 걸리는지는 **컨테이너를 띄운 통합 테스트로만** 확인할 수 있다 — 애노테이션이 아무것도 안 하기 때문에, 그것이 제대로 읽혔는지는 실제로 읽는 쪽을 띄워 봐야 안다.
