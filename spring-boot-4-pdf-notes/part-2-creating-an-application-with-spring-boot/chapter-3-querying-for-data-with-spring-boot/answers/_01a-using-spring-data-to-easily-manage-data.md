## Q1. 공통 인터페이스를 만들면 API 밖으로 밀려나는 것

**모든 저장소가 공통으로 지원하는 것만 남고, 나머지가 전부 밀려난다.**

| 넣을 수 있는 것 | 밀려나는 것 | 왜 |
|---|---|---|
| `save(id, value)` | **Redis의 TTL(만료 시간)** | 관계형 표에는 행 만료 개념이 없다 |
| `findById(id)` | **MongoDB의 집계 파이프라인** | 키-값 저장소에는 파이프라인이 없다 |
| `delete(id)` | Cassandra의 요청별 일관성 수준 | 단일 노드 저장소에는 정족수가 없다 |
| | 관계형의 조인 | 문서 저장소는 조인을 전제하지 않는다 |

**예를 둘 들라면 TTL과 집계 파이프라인이다.** 둘 다 "다른 저장소에는 대응 개념 자체가 없어서" 공통 API에 들어갈 자리가 없다.

이 실패 패턴의 이름이 **최소공통분모 API**다.

## Q2. 밀려난 것들이 왜 하필 "그 저장소를 고른 이유"인가

**우연이 아니라 구조적으로 그렇다.**

논리를 뒤집어 보면 명확하다.

```
그 저장소를 고른 이유 = 다른 저장소에는 없는 무언가가 필요해서
                        ↓
"다른 저장소에는 없다" = 공통 부분집합에 속하지 않는다
                        ↓
공통 API는 정의상 공통 부분집합만 담는다
                        ↓
∴ 고른 이유는 반드시 API 밖에 있다
```

책의 진단: *"모든 저장소가 서로 다른 기능을 제공하므로, 우리가 어떤 저장소를 쓰고 싶게 만든 바로 그 예리한 특징들은 대개 그 공유 API에 없다!"*

**Redis를 고른 것은 TTL과 원자적 카운터 때문**이고, **MongoDB를 고른 것은 집계 파이프라인 때문**이다. 그것들이 API에 없으면 개발자는 인터페이스를 **캐스팅해 벗겨 내거나 별도 경로로 우회한다.**

**결과: 추상화가 있으나 마나 해진다.** 있는데 안 쓰거나, 쓰면서 계속 뚫고 나간다.

## Q3. `RedisTemplate`과 `MongoTemplate`이 공통 상위 타입 없이도 비슷하게 느껴지는 이유

**타입이 아니라 관례가 같기 때문이다.**

책이 못 박는다 — **"이 template 클래스들은 어떤 공통 API의 자손이 아니다."**

그런데도 비슷한 이유는 셋이다.

| | 공유되는 것 | 갈리는 것 |
|---|---|---|
| 무엇 | **생명주기, 자원 관리, 예외 처리 방식** | 실제 연산과 기능 |
| 형태 | **관례**(같은 이름·같은 사용감) | **타입**(공통 상위 인터페이스 없음) |
| 결과 | 새 저장소를 배울 때 **감이 온다** | 그 저장소의 고유 기능을 **다 쓸 수 있다** |

**이름이 다 `Template`으로 끝나는 것은 상속이 아니라 Spring의 오래된 명명 관례다.** `JdbcTemplate`, `RestTemplate`, `TransactionTemplate`이 같은 계열이고, 공통점은 타입이 아니라 **역할**이다 — 반복되는 자원 관리 절차(연결 열기, 오류 변환, 닫기)를 틀로 고정하고 달라지는 부분만 채우게 한다.

**실무적 귀결**: `Template t = condition ? redisTemplate : mongoTemplate;` 같은 코드는 **성립하지 않는다.** 이름의 공통점은 계약이 아니다.

## Q4. "관례로 묶고 타입으로는 안 묶는다"

**§1의 딜레마에 대한 Spring Data의 답이다.**

딜레마는 이랬다 — 타입으로 묶으면(공통 API) 고유 기능이 밀려나고, 아예 안 묶으면 저장소마다 처음부터 배워야 한다.

**Spring Data는 제3의 답을 골랐다.**

- **타입으로 안 묶는다** → 각 template이 그 저장소의 고유 기능을 **온전히** 노출한다. TTL도 집계 파이프라인도 그대로 있다.
- **관례로 묶는다** → 이름, 사용감, 생명주기, 자원 관리, 예외 처리가 같다. Redis를 써 본 사람이 MongoDB template을 열면 **어디를 봐야 할지 안다.**

**얻는 것**: 기능 손실 없이 학습 비용을 줄인다.
**포기하는 것**: 컴파일러가 지켜 주는 이식성. 저장소를 바꾸면 template 코드는 다시 쓴다.

**이것이 Q8의 "이식성이 아니라 일관된 학습 곡선"이라는 결론으로 이어진다.**

## Q5. repository가 도메인 타입만으로 동작하는 세 단계

1. **개발자가 도메인 타입을 기준으로 인터페이스를 선언한다.** — 저장소의 표 이름·컬럼 이름을 코드에 넣지 않기 위해
2. **Spring Data가 그 선언과 저장소 메타데이터를 읽는다.** — 도메인 필드가 저장소의 무엇에 대응하는지 알아야 하므로
3. **실제 쿼리를 만들어 실행하는 구현을 런타임에 제공한다.** — 개발자가 저장소별 API를 배우지 않아도 되게 하기 위해

**2번이 핵심이다.** 도메인 타입만으로 되는 것이 아니라, **도메인 타입 + 저장소 메타데이터**가 있어야 한다. `@Entity`나 매핑 정보가 그 메타데이터다.

**그래서 repository를 쓰는 코드는 저장소가 무엇인지 몰라도 읽힌다.** [[01-adding-spring-data-to-an-existing-application]]에서 "관계형을 골랐지만 SQL 기반에 국한되지 않는다"고 한 근거가 여기다.

## Q6. 접근 방법 사다리 네 칸

**"무엇으로 쿼리를 표현하는가" 기준이다.**

| 층 | 무엇으로 표현하나 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| repository 파생 쿼리 | 메서드 **이름** | 쿼리를 아예 안 쓴다 | 조건이 **작성 시점에 고정** |
| Query By Example | 부분적으로 채운 **객체** | 조건을 **런타임에 조립** | 동등·문자열 비교 위주로 제한 |
| Querydsl | 타입 안전한 **DSL 코드** | 복잡한 조건도 컴파일 검사 | 별도 라이브러리와 코드 생성 |
| 손으로 쓴 쿼리 | JPQL / SQL **문자열** | 완전한 제어 | 타입 검사·방언 독립성 상실 |

**위로 갈수록 편하고 아래로 갈수록 자유롭다.** 그리고 이 순서가 **Chapter 3 전체의 서술 순서**이기도 하다 — 파생 쿼리([[03-creating-repositories-and-declarative-queries]]·[[04-using-custom-finders]]) → QBE([[05-query-by-example-for-dynamic-search]]) → 손으로 쓴 쿼리([[06-writing-custom-jpa-queries]]).

**공통 설계 의도**: 네 층 모두 *"도메인 타입에 이미 존재하는 정보를 재사용해서"* 쿼리를 쓰고 유지하는 수고를 줄이도록 설계됐다. 위 세 층이 특히 그렇다.

## Q7. 아래 칸으로 내려가는 것이 왜 실패가 아닌가

**사다리의 존재 자체가 "한 층으로 다 된다"는 뜻이 아니기 때문이다.**

각 층은 **표현력과 편의의 교환비가 다른 도구**이지, 위 칸이 우월한 것이 아니다. 파생 쿼리로 표현할 수 없는 요구가 있다는 것은 파생 쿼리의 결함이 아니라 **설계된 범위**다.

**판단은 "무엇이 필요한가"로 한다.**

- 조건이 컴파일 시점에 고정 → 파생 쿼리로 충분하다
- **조건의 개수 자체가 런타임에 정해진다** → QBE가 필요하다 (파생 쿼리로는 **표현 불가능**)
- 4-JOIN 집계 → 손으로 쓴 쿼리 말고 답이 없다

**필요 이상으로 내려가지 않는 것**이 규율이고, **필요한 만큼 내려가는 것**은 정상 동작이다. 위 칸에 억지로 남으려고 finder 이름을 60자로 만드는 것이 오히려 실패다 — [[06-writing-custom-jpa-queries]]가 그 예로 시작한다.

## Q8. "저장소를 바꿔도 코드가 그대로"의 실제 범위

**repository 층에 한정된 이야기다.**

| | 옮겨 가는가 |
|---|---|
| repository 인터페이스 선언 | **대체로 통한다** |
| 파생 finder 이름 규칙 | 대체로 통한다 |
| **template을 쓴 코드** | **안 통한다** — 공통 타입이 없다 |
| **저장소 고유 애노테이션**(`@Entity` 등) | **안 통한다** |
| **트랜잭션 의미론** | **안 통한다** — 저장소마다 보장이 다르다 |

**세 번째 항목이 가장 크다.** 트랜잭션 의미론은 코드 모양은 같아 보여도 **동작이 다르다.** `@Transactional`을 붙인 코드가 관계형에서는 원자성을 보장하지만 어떤 NoSQL에서는 범위가 제한된다. **컴파일도 되고 실행도 되는데 보장이 다르다** — 가장 위험한 형태의 비이식성이다.

**정확한 표현**: **Spring Data가 주는 것은 이식성이 아니라 일관된 학습 곡선이다.**

**비유가 깨지는 지점**도 여기다. 전용 어댑터는 나라를 옮기면 통째로 새로 산다. Spring Data는 **두 층**이라 template 층은 갈리지만 repository 층은 모양이 상당히 유지된다. 실제 어댑터에는 이 이중 구조의 대응물이 없다.
