## Q1. 문법적으로 완벽한데 왜 문제인가

```java
findByMetricsActivityViewsLessThanOrEngagementLikesLessThan(Long minimumViews, Long minimumLikes);
```

**무너지는 것은 기계가 아니라 사람이다.**

[[04-using-custom-finders]]의 규칙대로 **파서는 정확히 해석하고 올바른 조인을 만든다.** 아무 문제가 없다.

책의 표현: *"쿼리 복잡도가 올라갈수록 **메서드 이름이 얼마나 빠르게 길어지고 읽기 어려워지는지**를 보여 준다."*

**독일어 합성어 비유가 깨지던 그 지점이다** — 독일어 합성어는 아무리 길어도 사람이 읽어 낸다. 파생 finder는 **사람이 못 읽는 지점이 기계보다 먼저 온다.**

**구체적 손실**:
- 코드 리뷰에서 **의도를 검증할 수 없다.** 이름을 세 번 읽어야 조건을 파악한다.
- **오타를 눈으로 못 잡는다.** `LessThan`을 `LessThen`으로 쓰면 시작 시점에 실패하지만, `Or`를 `And`로 쓰면 **잘 돌면서 틀린 결과**를 준다.
- 이름이 **"무엇을 하는지"만 말하고 "왜 하는지"를 말하지 않는다** → Q2

## Q2. `@Query`가 메서드 이름의 역할을 뒤집는다

| | 파생 finder | `@Query` |
|---|---|---|
| 메서드 이름은 | **쿼리 그 자체** | **문서** |
| 이름을 바꾸면 | **쿼리가 바뀐다** | 아무 일도 없다 |
| 이름에 담는 것 | 조건의 구조 | **연산의 의도** |
| 예 | `findByMetricsActivityViewsLessThan…` | `findVideosThatArentPopular` |

책: *"우리가 JPQL을 제공하므로 **메서드의 이름은 더 이상 중요하지 않다.** 이것은 필드 이름이나 finder 키워드에 제약받는 대신, **연산의 의도를 반영하는 이름**을 고를 기회다."*

**즉 "중요하지 않다"가 "아무렇게나 지어도 된다"가 아니다.** 기계가 안 보게 되었으니 **사람을 위해 쓸 수 있다**는 뜻이다.

`findVideosThatArentPopular`는 **왜 이 쿼리가 있는지**를 말한다. `findByMetricsActivityViews…`는 **어떻게 찾는지**만 말한다. 6개월 뒤 코드를 여는 사람에게 필요한 것은 전자다.

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/02-creating-a-spring-mvc-web-controller|Chapter 2]]의 "기계는 이름을 안 본다, 사람은 이름만 본다"가 여기서 다시 성립한다.**

## Q3. JPQL `@Query`에서도 `Sort`가 적용되는 이유

**`ORDER BY`는 쿼리 맨 뒤에 붙이면 되기 때문이다.**

책: *"`SORT` 절은 쿼리 끝에 덧붙일 수 있으므로, Spring Data JPA는 `Sort` 인자를 제공하면 그것을 적용하게 해 준다."*

**프레임워크가 우리 쿼리를 해석할 필요가 없다.** 문자열 뒤에 이어 붙이기만 하면 된다.

```
"select v from VideoEntity v where v.name = ?1"  +  " order by v.name asc"
```

**그런데 이것은 JPQL이기에 가능하다.** 프레임워크가 JPQL을 **이해하기 때문에** 끝에 안전하게 붙일 수 있다 — 이 쿼리가 서브쿼리로 끝나는지, 이미 `ORDER BY`가 있는지 등을 판단할 수 있다.

**네이티브 SQL은 임의의 문자열이라 그 조작이 위험해진다** → Q7.

**함께 유지되는 것**: `Pageable`도 그대로 쓸 수 있다. [[04a-sorting-the-results]]의 정렬과 [[04b-limiting-query-results]]의 페이징이 `@Query`와 함께 작동한다.

## Q4. 같은 타입 인자가 둘일 때 위치 파라미터가 위험한 이유

**순서를 바꿔도 컴파일되고 실행된다. 결과만 틀린다.**

```java
@Query("… where a.views < ?1 or e.likes < ?2")
List<VideoEntity> find(Long minimumViews, Long minimumLikes);
                       //     ↑ 둘 다 Long. 순서를 바꿔도 컴파일 OK
```

| | 위치 `?1` | 이름 `:minimumViews` |
|---|---|---|
| 짧다 | **예** | 아니오 (`@Param` 한 줄씩) |
| 인자 3개 이상 | **순서를 세어야 한다** | 이름으로 읽힌다 |
| **순서를 바꾸면** | **조용히 잘못된 결과** | **영향 없음** |
| 쿼리만 봐서 뜻이 통하나 | `?1`이 무엇인지 모른다 | **`:minimumViews`가 설명한다** |

**세 번째 줄이 실무에서 가장 아프다.** 타입이 다르면(`Long`, `String`) 순서를 바꿨을 때 컴파일 오류가 나서 잡힌다. **같은 타입이면 아무 신호가 없다.**

**그리고 리팩터링에 취약하다** — 파라미터 순서를 바꾸는 IDE 리팩터링은 `?1`/`?2`를 고쳐 주지 않는다.

**이름 있는 파라미터를 쓰면**: `@Param("minimumViews") Long minimumViews`. 한 줄 늘어나는 대신 **쿼리를 읽는 것만으로 의도가 파악된다.**

## Q5. 책의 Tip이 4-JOIN 예제에 내리는 결론

**저자는 그 예제에서도 여전히 커스텀 finder를 쓰겠다고 한다.**

> *"솔직히 말해 표 네 개를 조인하는 이 예제에서는 **나라면 여전히 커스텀 finder를 쓰겠다.** 그게 맞을 것이라고 알기 때문이다."*

**저자가 자기 예제에 대해 반대 결론을 내리는 것이 이 Tip의 값이다.** 네 개 조인짜리 예제조차 finder로 충분하다고 말한다.

**즉 `@Query`는 "복잡하면 쓰는 것"이 아니라 "이름으로 담을 수 없을 때 쓰는 것"이다.**

**판단 기준** — 책이 든 핵심 요인은 **`WHERE` 절의 개수**와 **복잡한(즉 외부) `JOIN` 절의 개수**다.

| 신호 | finder 쪽 | `@Query` 쪽 |
|---|---|---|
| `WHERE` 조건 개수 | 1~2개 | 3개 이상 |
| `JOIN` 종류 | 내부 조인 위주 | **외부 조인**이 섞임 |
| 메서드 이름 | 소리 내어 읽을 수 있다 | 세 번 읽어야 한다 |
| 서브쿼리·집계 | 없음 | 있음 |
| 확신 | **"이게 맞을 것이라 안다"** | "직접 보고 확인해야겠다" |

**마지막 줄이 저자의 기준이다** — *"단순한 이름으로 담아내기 어려워질수록 쿼리 전체를 직접 통제하는 편이 나아진다."*

## Q6. 네이티브로 내려갈 때 꺼지는 셋과 유지되는 둘

| | JPQL `@Query` | **네이티브 `@Query`** |
|---|---|---|
| **`Sort` 인자** | 적용된다 | **✘ 적용되지 않는다** |
| **`Pageable`** | 적용된다 | **△ 가능하되 `countQuery`를 직접 제공**해야 한다 |
| **방언 독립성** | 있다 | **✘ 없다** |
| **표·컬럼 이름** | 몰라도 된다 | **✘ 알아야 한다** |
| **연결 관리** | 유지 | **✔ 유지** |
| **트랜잭션 관리** | 유지 | **✔ 유지** |

**꺼지는 셋**: 동적 정렬, 방언 독립성, 이름 추상화. (페이징은 조건부로 살아 있다.)

**유지되는 둘**: **연결과 트랜잭션 관리.** 책이 이 절을 그렇게 닫는다 — *"이런 제약이 있어도 Spring Data JPA는 우리를 위해 **연결과 트랜잭션을 계속 관리하며**, 네이티브 쿼리도 여전히 Spring이 관리하는 데이터 접근 인프라 안에서 실행되도록 보장한다."*

**즉 수동 모드로 내려가도 완전히 맨손이 되지는 않는다.** 커넥션 풀, 트랜잭션 경계, 예외 변환은 그대로다.

**비유가 깨지는 지점이 여기다** — 자동차는 수동 모드로 바꿔도 ABS가 꺼지지 않는다. `@Query`의 네이티브 모드는 **안전장치 일부가 실제로 꺼진다.**

## Q7. JPQL에서 되던 동적 정렬이 네이티브에서 안 되는 이유

**JPQL은 프레임워크가 이해하는 언어이고, 네이티브 SQL은 임의의 문자열이기 때문이다.**

```
JPQL   : Spring Data가 파싱해서 구조를 안다
         → 끝에 ORDER BY 를 안전하게 붙일 수 있다

네이티브: 그냥 문자열이다
         → 어디가 끝인지, 이미 ORDER BY 가 있는지,
           서브쿼리로 끝나는지 판단할 수 없다
         → 붙이면 위험하다
```

책: *"그렇게 하려면 `SORT` 절을 붙이기 위해 **SQL을 조작해야** 할 것이다."*

**§2.2의 복선이 여기서 회수된다.** 거기서 "`ORDER BY`는 쿼리 맨 뒤에 붙이면 되기 때문"이라고 한 것이 **JPQL에 한정된 이야기였다.**

**페이징도 같은 이유로 반쪽만 된다**: 결과를 잘라 내는 것은 되지만, **전체 개수를 세는 쿼리는 프레임워크가 만들 수 없다.** 그래서 `@Query`의 `countQuery` 항목에 **개수를 세는 SQL을 직접 제공**해야 한다.

**일반 원리**: **프레임워크가 무언가를 자동으로 해 주려면 그것을 이해해야 한다.** 이해할 수 없는 것(임의 문자열)을 받으면 자동화도 함께 사라진다.

## Q8. `spring.aot.enabled=true`만으로 AOT 리포지토리가 생기지 않는 이유

**AOT 코드 생성은 빌드 시점에 일어나고, 그 프로퍼티는 실행 시점의 스위치이기 때문이다.**

✅ 책은 *"`spring.aot.enabled=true`로 켤 수 있다"*고만 적는데, **이는 절반이다.**

| 단계 | 무엇을 해야 하나 |
|---|---|
| **빌드 시점** | **Maven은 `-Pnative` 프로파일로, Gradle은 `org.springframework.boot.aot` 플러그인으로** AOT 코드를 생성한다 |
| **실행 시점** | 그렇게 만들어진 JAR을 `java -Dspring.aot.enabled=true -jar myapplication.jar`로 실행한다 |

**즉 빌드를 먼저 바꿔야 하고, 프로퍼티만 켠다고 없는 코드가 생기지는 않는다.**

**증상**: 프로퍼티만 켜면 아무 일도 안 일어난다. 오류도 없고 성능 개선도 없다. **"켰는데 왜 안 빨라지지"가 된다.**

**배경**: [[03-creating-repositories-and-declarative-queries]]에서 본 **런타임 프록시 생성**이 이 기능의 대상이다. 시작할 때마다 인터페이스를 읽고 구현을 만드는 작업을 **미리 해 두자**는 것이다.

**"디버깅 가능성이 높아진다"도 같은 이유다** — 생성된 코드가 **파일로 존재하면 들여다볼 수 있다.** 런타임 프록시는 중단점도 못 걸었다.

**지원 범위**: 집필 시점 기준 Spring Data JPA, JDBC, MongoDB, Cassandra.
