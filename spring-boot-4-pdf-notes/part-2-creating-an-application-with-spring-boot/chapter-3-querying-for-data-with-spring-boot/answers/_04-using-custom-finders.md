## Q1. 전부 가져와 Java로 거르는 방식이 나쁜 이유 — 숫자로

```java
return repository.findAll().stream()
        .filter(v -> v.getName().contains("SPRING"))
        .toList();
```

**행이 10건이면 잘 돈다. 10만 건이면 10만 건을 전부 메모리에 올린 뒤 아홉 건을 남긴다.**

| | DB가 할 때 | 애플리케이션이 할 때 |
|---|---|---|
| 읽는 행 | 인덱스로 **9건** | **10만 건** |
| 네트워크로 옮기는 양 | 9건 | **10만 건** |
| 메모리 | 9건 | **10만 건 전부 객체로** |
| 시간 | **0.001초** | 몇 초 |

**"데이터베이스가 인덱스로 0.001초에 할 일을 애플리케이션이 몇 초에 걸쳐 한다."**

**숫자 이상의 문제**: 10만 건을 객체로 만드는 것은 **GC 압박**도 만들고, 동시 요청이 몇 개만 겹쳐도 **힙이 터진다.** 그리고 이 문제는 **데이터가 늘면서 서서히 나타나므로** 개발·테스트에서 안 잡힌다.

## Q2. 이름 파싱 네 단계

1. **`findBy` 접두어 인식** — 리포지토리의 **모든 메서드를 쿼리로 볼 수는 없으므로** 파싱을 시작할 표식이 필요하다
2. **필드 이름 대조**(`Name`) — `@Entity` 매핑 메타데이터에 **그 이름의 필드가 실제로 있는지** 확인해야 하므로. **이 단계가 오타를 시작 시점에 잡는다**
3. **한정어 해석**(`Containing`, `IgnoreCase`) — 같은 필드에 대해 **정확 일치인지 부분 일치인지, 대소문자를 볼지**를 정해야 하므로
4. **인자 개수·타입 대조** — **조건 하나에 값 하나**가 필요하므로. 개수가 안 맞으면 역시 시작 시점에 실패

**2번과 4번이 안전장치다.** [[03-creating-repositories-and-declarative-queries]]에서 "사서 비유가 깨지는 지점"이라 한 그 융통성 없음이 여기서 값을 한다 — **오타가 런타임까지 살아남지 않는다.**

## Q3. 파라미터 이름은 바꿔도 되고 메서드 이름의 필드는 못 바꾸는 이유

> **Spring Data는 쿼리를 메서드 이름에서 파생하며, 파라미터 이름에서 파생하지 않는다. 파라미터 이름은 런타임에 값을 공급하는 데만 쓰인다.**

```java
List<VideoEntity> findByName(String name);       // 같은 쿼리
List<VideoEntity> findByName(String 아무거나);    // 같은 쿼리
```

**파라미터 이름은 값을 나르는 통로일 뿐 의미를 갖지 않는다.**

반대로 메서드 이름의 `Name`을 `Titel`로 바꾸면 `VideoEntity`에 그런 필드가 없으므로 **애플리케이션이 시작조차 하지 않는다.**

**설계 관점**: 어느 쪽에 의미를 실을지 골라야 했고, **메서드 이름을 골랐다.** 그 결과 파라미터 이름은 자유롭고(리팩터링해도 안전하고), 메서드 이름은 계약이 된다(못 바꾸는 대신 검증된다).

## Q4. 바인딩이 SQL 인젝션을 막는 원리 — "문법과 데이터"

**바인딩은 값을 문법이 아니라 데이터로 취급하게 만든다.**

```sql
-- 이어 붙이기: 입력이 문법의 일부가 된다
where v.name like '%' OR 1=1 --%'      ← 쿼리의 의미 자체가 바뀐다

-- 바인딩: 입력이 값의 자리에만 들어간다
where video.name = ?1
                   ↑ 여기에 ' OR 1=1 -- 이 들어가도
                     "그런 이름의 비디오를 찾아라"라는 뜻일 뿐이다
```

**결정적 차이**: 이어 붙이기는 쿼리 **문자열이 만들어지는 시점에** 입력이 섞인다. 그 시점 이후로는 파서가 어디까지가 개발자의 문법이고 어디부터가 사용자 입력인지 **구별할 수 없다.**

바인딩은 **쿼리 구조를 먼저 확정하고 값을 나중에 채운다.** 값은 파싱 대상이 아니므로 그 안에 무엇이 있든 문법이 되지 못한다.

책의 Tip: *"인자 바인딩은 훨씬 안전한 접근을 제공하며, 모든 사용자 입력이 데이터 저장소의 **정문으로** 들어와 쿼리 생성에 제대로 적용되도록 강제한다."*

**부수 효과**: 방언도 신경 쓸 필요가 없다. JPA가 MySQL·PostgreSQL의 특이점을 대체로 처리한다.

## Q5. `Containing`과 `Like` 중 언제 무엇을

> **판별 규칙: `%`를 직접 쓰기 시작하면 `Like`로 내려가고, 그렇지 않으면 한정어에 맡긴다.**

| | `Containing` / `StartsWith` / `EndsWith` | `Like` |
|---|---|---|
| 와일드카드 | **Spring Data가 대신 넣어 준다** | **내가 직접 넣는다** |
| 표현력 | 앞·뒤·양쪽 세 가지 | `%firstthis%thenthis%`처럼 자유롭게 |
| 안전성 | 사용자 입력에 `%`가 있어도 그대로 값 | 내가 `%`를 조립하므로 주의 필요 |
| 읽기 | 의도가 이름에 드러난다 | 패턴을 봐야 안다 |

**Note의 안내**: *"와일드카드를 앞에 붙이는 정도의 단순한 작업이라면 `StartsWith`를 쓰고 부분 토큰을 넘기면 된다 — Spring Data가 와일드카드를 대신 넣어 준다. … 더 복잡한 것이 필요하면 `Like`가 제어권을 준다."*

**같은 뜻에 이름이 세 개씩 있는 것**(`StartingWith`/`StartsWith`/`IsStartingWith`)은 **읽기 자연스러운 쪽을 고르라는 배려**다. 파서는 셋 다 같게 처리한다.

## Q6. `findByAddressZipCode`의 모호함과 밑줄

**`Person`에 `addressZip` 필드도 있다면 Spring Data는 관계 탐색보다 그 필드를 우선한다.**

파서가 이름을 쪼개는 순서:

```text
  후보 A:  addressZipCode  (필드 하나)      → 그런 필드는 없다
  후보 B:  addressZip + Code                → addressZip 필드가 있다면 여기서 멈춘다
  후보 C:  address → zipCode  (관계 탐색)    → 후보 B가 맞으면 여기까지 안 온다

  ▶ 파서는 "가장 긴 필드 이름부터" 맞춰 보고 맞으면 멈춘다.
```

**밑줄(`_`)은 "여기서 끊어라"를 사람이 직접 지시하는 것이다.**

```java
findByAddress_ZipCode(ZipCode zipCode)   // 관계 탐색을 강제
```

**왜 이 규칙인가**: 필드 우선이 **더 흔하고 더 싸기 때문**이다. 관계 탐색은 **join을 생성**한다. 파서가 join을 먼저 시도하면 의도치 않은 조인이 조용히 생길 수 있다.

**위험한 점**: 나중에 `addressZip` 필드를 **추가하는 순간** 기존 `findByAddressZipCode`의 의미가 바뀐다. 밑줄을 쓰면 그 변화에 영향받지 않는다.

## Q7. `hasText`로 거르지 않으면

**전부 매칭된다. 아무것도 안 나오는 것이 아니라 반대다.**

`Containing`에 **빈 문자열을 주면 `%%`가 되어** 모든 행이 걸린다.

```
name = ""  →  where name like '%%'  →  모든 행
```

**그래서 §1의 갈래 1 문제가 그대로 돌아온다** — 표 전체를 가져온다. 조건이 있는 척하면서 실제로는 없는 쿼리다.

`StringUtils.hasText`는 **텍스트를 갖고 있으며 비어 있지도 `null`도 아님**을 확인한다. 그래서 세 경우를 갈라 처리한다.

```java
if (hasText(name) && hasText(description)) { /* 둘 다 */ }
if (hasText(name))                          { /* 이름만 */ }
if (hasText(description))                   { /* 설명만 */ }
return Collections.emptyList();             // 둘 다 비었다
```

**마지막 줄에 `if`가 없는 것**도 의도적이다 — 앞의 세 경우가 아니면 남은 상태는 하나뿐이다.

**설계 판단**: "검색어가 없으면 빈 목록"이 맞는지 "전체 목록"이 맞는지는 **제품 결정**이다. 여기서는 빈 목록을 골랐고, 그 결정이 코드에 명시돼 있다.

## Q8. 필드가 4개로 늘면

**finder는 조합 수만큼, `if`도 그만큼 필요하다.**

| 필드 수 | 비어 있지 않은 조합의 수 | 필요한 finder |
|---:|---:|---:|
| 2 | 3 | 3 |
| 3 | 7 | 7 |
| **4** | **15** | **15** |
| 5 | 31 | 31 |

**2ⁿ − 1개다.** 4개면 **15개의 finder와 15갈래 분기**가 필요하다.

**게다가 각 finder는 이름이 계속 길어진다**:
```
findByNameContainsOrDescriptionContainsOrTagsContainsAllIgnoreCase...
```

**근본 원인**: **finder의 조건 조합이 작성 시점에 고정되기 때문이다.**

메서드 이름은 컴파일 시점에 확정된다. 그런데 **어떤 필드가 채워질지는 런타임에 정해진다.** 정적인 것으로 동적인 것을 표현하려니 **가능한 모든 경우를 미리 나열**하는 수밖에 없다.

**비유가 깨지는 지점과 이어진다**: 독일어 합성어는 아무리 길어도 사람이 읽어 낸다. 파생 finder는 **사람이 못 읽는 지점이 기계보다 먼저 온다.**
