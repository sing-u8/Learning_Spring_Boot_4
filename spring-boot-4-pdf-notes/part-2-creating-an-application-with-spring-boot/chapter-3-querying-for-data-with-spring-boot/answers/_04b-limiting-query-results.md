## Q1. 10만 행을 다 가져올 때 무너지는 네 지점

1. **메모리.** 객체 8만 개가 동시에 살아 있다. 요청이 몇 개만 겹쳐도 힙이 찬다.
2. **네트워크와 직렬화.** 데이터베이스에서 애플리케이션으로 8만 행이 흘러온다.
3. **응답 시간.** 첫 화면을 그리기 전에 **8만 건을 다 받아야** 한다.
4. **예측 불가능성.** **데이터가 늘어날수록 조용히 느려진다.** 어제 되던 것이 오늘 안 된다.

**가장 위험한 것은 4번이다.**

**왜인가**: 1~3번은 **지금 측정하면 보인다.** 부하 테스트를 하면 드러난다. 4번은 **코드는 그대로인데 데이터 증가만으로 장애가 난다.** 배포도 없었고 변경도 없었으므로 **원인을 찾을 실마리가 코드에 없다.**

그리고 개발·테스트 환경은 데이터가 적으므로 **끝까지 안 잡힌다.**

## Q2. 소방 호스 비유가 깨지는 지점

**밸브는 잠그면 물이 덜 나올 뿐 "어느 물인지"는 문제되지 않는다.**

`Top5`는 다르다 — **"어느 5건인가"를 정하지 않으면 무의미하다.**

정렬을 지정하지 않은 상위 5건은 **실행할 때마다 다른 5건일 수 있다.** [[04a-sorting-the-results]]에서 본 대로 `ORDER BY`가 없으면 순서가 보장되지 않기 때문이다.

> **개수 제한은 정렬과 짝을 이룰 때만 의미를 갖는다.**

**밸브 비유에는 "어느 물인가"라는 개념 자체가 없어서 여기서 멈춘다.**

**실무적 귀결**: `findTop5By…`를 쓸 때는 반드시 `OrderBy`를 붙이거나 `Sort`를 함께 넘긴다. "인기 상위 5개"라면 **무엇이 인기인지**를 정렬로 말해야 한다.

## Q3. `Top5`와 `Pageable`을 각각 언제

```text
findTop5ByName(name)          → 항상 앞의 5건. 6번째부터는 볼 방법이 없다.
                                 "이 조건의 대표 5개"

findByName(name, PageRequest.of(2, 5))
                              → 5건씩 끊었을 때의 3번째 묶음(11~15번째)
                                 "전체를 훑어 나가는 중"
```

> **고정된 상위 N개가 필요한가, 전체를 나눠 보고 싶은가로 갈린다.**

| | `Top5` | `Pageable` |
|---|---|---|
| 개수 | **컴파일 시점에 고정** | 런타임에 지정 |
| 그 뒤를 볼 수 있나 | **없다** | 있다 |
| 전형적 용도 | "최근 5건", "인기 3위까지" | 목록 화면의 페이지 넘김 |
| 정렬 | `OrderBy`로 이름에 박거나 `Sort` | **`Pageable`에 함께 담을 수 있다** |

마지막 줄이 실용적이다 — `Pageable`은 **페이지와 정렬을 한 객체로** 나른다. §1이 짚은 "어느 N건인가" 문제를 여기서 해결한다.

## Q4. `PageRequest.of(0, 20)`의 0

**페이지 번호이며, 0번이 첫 페이지다.**

크기가 20인 페이지 중 **첫 번째**를 요청한다.

**흔한 실수**: **`of(1, 20)`이 첫 페이지라고 생각하는 것.** 실제로는 **두 번째** 페이지(21~40번째)다.

**증상**: 첫 페이지가 통째로 안 보인다. 그런데 목록에 데이터는 나오므로 **"동작한다"고 보인다.** 데이터가 20건 이하면 빈 화면이 나와서 그제야 이상함을 느낀다.

**대응**: **사용자에게 "1페이지"로 보여 주려면 화면 쪽에서 1을 빼 줘야 한다.** 이 변환을 어디서 할지 팀에서 정해 두지 않으면 어떤 코드는 빼고 어떤 코드는 안 빼는 상태가 된다 — 전형적인 off-by-one의 근원이다.

## Q5. `existsBy`가 `findBy` + 비어 있는지 확인보다 나은 이유

**엔티티 객체를 만들지 않기 때문이다.**

```java
// 나쁨: 엔티티를 만들어 놓고 버린다
boolean exists = !repository.findByName(name).isEmpty();

// 좋음: 존재 여부만 확인한다
boolean exists = repository.existsByName(name);
```

| | `findBy` + `isEmpty()` | `existsBy` |
|---|---|---|
| DB가 하는 일 | 매칭 행을 **전부 읽어 반환** | 존재만 확인 (대개 1건만 찾고 멈춘다) |
| 네트워크 | 행 데이터 전부 | 참/거짓 |
| 애플리케이션 | **엔티티 객체 생성 → 버림** | 없음 |

**존재 여부만 알면 되는데 객체 생성 비용을 치르는 것**이 문제다. 매칭이 많으면 그 비용이 매칭 수만큼 곱해진다.

**같은 계열**: `countBy…`도 **엔티티를 하나도 만들지 않고** 정수만 돌려준다.

**그리고 이 셋(`countBy`, `existsBy`, `deleteBy`)은 `findBy`와 같은 조건 문법을 전부 지원한다.** `findByNameContainsIgnoreCase`가 되면 `countByNameContainsIgnoreCase`도, `deleteByNameContainsIgnoreCase`도 그대로 된다. **접두어만 바뀌고 뒤쪽 문법은 하나다.**

## Q6. 메서드 이름이 SQL이 되기까지의 번역

**두 번이다.**

```text
  메서드 이름              Spring Data가 파싱
  findByNameContains  ──────────────────────▶  JPQL
                                               select v from VideoEntity v
                                               where v.name like ?1
                                                      ▲ 엔티티 필드 이름

                        JPA(Hibernate 등)가 번역
                      ──────────────────────▶  SQL
                                               select v.id, v.name, v.description
                                               from video_entity v
                                               where v.name like ?
                                                      ▲ 실제 표·컬럼 이름
```

| 단계 | 이름의 정체 | 예 |
|---|---|---|
| 메서드 이름 | **Java 필드 이름의 CamelCase 조합** | `Name` |
| **JPQL** | **엔티티 필드 이름** | `v.name` |
| **SQL** | **실제 표·컬럼 이름** | `video_entity.name` |

**이것이 [[04-using-custom-finders]]에서 "표 이름·컬럼 이름을 몰라도 된다"고 한 이유다** — 두 단계의 번역이 그 간극을 메운다.

**실무적으로 왜 중요한가**: **"쿼리가 이상하다"고 할 때 어느 단계의 것인지 구분해야 원인을 제대로 짚는다.**
- **JPQL이 이상하다** → 파생이 잘못됨 (메서드 이름 문제)
- **SQL이 이상하다** → 방언·매핑 문제 (`@Entity` 설정 문제)

로그에 보이는 쿼리가 어느 것인지 먼저 확인해야 한다.

## Q7. 동적인 것 셋과 정적인 것 셋

| 요소 | 런타임에 바꿀 수 있나 | 근거 |
|---|---|---|
| 조건의 **값** (`"SPRING"`) | **✔ 동적** | 인자로 전달된다 |
| **정렬 기준** | **✔ 동적** | `Sort` 파라미터 — [[04a-sorting-the-results]] |
| **페이징** | **✔ 동적** | `Pageable` 파라미터 |
| 조건으로 쓸 **컬럼** | **✘ 정적** | **메서드 이름에 박혀 있다** |
| 조건들의 **결합 방식**(`And`/`Or`) | **✘ 정적** | 메서드 이름에 박혀 있다 |
| **한정어**(`Containing`, `IgnoreCase`) | **✘ 정적** | 메서드 이름에 박혀 있다 |

> **값은 유연하고 구조는 고정이다.**

책의 표현: *"인자를 통해 커스텀 기준을 줄 수 있고, 정렬과 페이징은 동적으로 조정할 수 있는 것도 사실이다. 그러나 **기준으로 삼을 컬럼과 그것들을 결합하는 방식**은 **우리가 쓰는 시점에 고정된다.**"*

**그래서 "이름으로 찾기"와 "이름 또는 설명으로 찾기"는 서로 다른 메서드여야 한다.**

**경계선의 논리**: 메서드 이름은 **컴파일 시점에 확정되는 문자열**이다. 그 안에 들어간 것은 전부 정적이고, 파라미터로 받는 것만 동적이다. **선이 명확하다.**

## Q8. 그 비대칭이 왜 조합 폭발로 이어지나

**정적인 것으로 동적인 것을 표현하려니 가능한 모든 경우를 미리 나열하는 수밖에 없기 때문이다.**

```
어떤 필드가 채워질지는 런타임에 정해진다   ← 동적
조건 구조는 메서드 이름에 박혀 있다        ← 정적
        ↓
런타임의 모든 경우에 대해 메서드를 미리 만들어 둔다
        ↓
2ⁿ − 1 개 (n = 검색 필드 수)
```

| 필드 수 | 필요한 finder |
|---:|---:|
| 2 | 3 |
| 3 | 7 |
| 4 | **15** |
| 5 | 31 |

**그리고 이름이 함께 길어진다**:
```
findByNameContainsOrDescriptionContainsOrTagsContainsAllIgnoreCase...
```

**이미 앞 절에서 드러났다.** 책이 가리킨다 — *"단지 `name`과 `description` 두 개의 파라미터를 갖는 것만으로도, 올바른 커스텀 finder를 고르기 위해 **일련의 `if` 절을 쓰는 길로** 들어섰다."*

**출구는 둘 중 하나다.**
- **구조를 런타임에 조립할 수 있게 만든다** → [[05-query-by-example-for-dynamic-search]]
- **이름 대신 쿼리를 직접 쓴다** → [[06-writing-custom-jpa-queries]]

이 절은 **문제를 선언할 뿐 해결하지 않는다.** 그것이 다음 노트의 존재 이유다.
