## Q1. `Video` 하나로 다 처리하면 왜 오래 못 가나

**이해관계자가 둘이기 때문이다** — 웹 계층과 영속성 계층.

처음에는 잘 돌아간다. 파일도 적고 변환 코드도 없다. **그게 함정이다.**

시간이 지나면 **양쪽에서 요구가 들어오고, 그 요구들이 서로 밀어낸다.** 한 클래스가 두 주인을 섬기면 한쪽을 만족시킬 때마다 다른 쪽이 흔들린다.

책의 진단: *"DTO이면서 동시에 엔티티이려고 하는 클래스는 길게 보면 관리하기 더 어렵다. 왜인가? **이해관계자가 둘이기 때문이다.**"*

**해법의 근거는 단일 책임 원칙(SRP)이다** — *"클래스가 딱 한 가지 일에 집중하려 할 때 유지하고 갱신하기 쉬워진다."*

---

## Q2. 양쪽 요구가 서로 밀어내는 구체적 예

**저장소 쪽 요구**
- 기본 키 `id`가 필요하다
- 감사 필드 `createdAt`·`createdBy`를 남겨야 한다
- JPA가 관리하려면 **인자 없는 생성자**가 필요하고 필드가 **바뀔 수 있어야** 한다 → **record로는 안 된다**

**웹 쪽 요구**
- `id`와 `createdBy`는 **외부에 노출하고 싶지 않다**
- JSON 키 이름을 `video_name`처럼 바꿔 달라
- 화면에는 **없는 계산 필드**(`durationText`)가 필요하다

**밀어내는 예 둘**:

1. **`createdBy` 추가 → API 응답에 새 필드가 생긴다.** 저장소 운영을 위한 필드가 공개 계약에 새어 나간다. [[../chapter-2-creating-web-and-api-applications-with-spring-boot/05-creating-json-based-apis|Chapter 2]]에서 본 "record 필드 하나가 계약을 바꾼다"가 그대로다.
2. **JSON 키 이름 변경 → 컬럼 매핑을 건드릴 위험.** 같은 클래스에 Jackson 애노테이션과 JPA 애노테이션이 겹쳐 붙으면, 한쪽을 고치다 다른 쪽 규칙을 바꾸게 된다.

**세 번째, 더 근본적인 충돌**: **불변성.** 웹은 불변 record를 원하고 저장소는 가변 객체를 요구한다. 이건 필드 하나의 문제가 아니라 **클래스의 형태 자체**가 양립하지 않는 경우다.

## Q3. 셋의 정의가 전부 "목적"으로 시작하는 이유

**생김새로 구분하려 들면 실패하기 때문이다.**

- DTO: 데이터를 **전송하는 것이 목적인** 클래스
- Entity: 데이터를 저장소에 **저장하고 꺼내는 것이 목적인** 클래스
- POJO: 프레임워크를 상속하지도 제약을 품지도 않은 클래스

**필드 두 개짜리 클래스는 셋 중 무엇이든 될 수 있다.** `record Video(String name)`을 보고 DTO인지 엔티티인지 알 방법이 없다. 알려면 **어디에 쓰이는지**를 봐야 한다.

**판별 질문은 언제나**: *"이 클래스는 무엇을 위해 존재하는가?"* 옮기려고면 DTO, 저장하려고면 엔티티다.

그리고 **POJO는 축이 다르다** — 역할이 아니라 **속박 여부**를 묻는다. 그래서 "DTO이면서 POJO"가 성립하고, 셋은 배타적이지 않다.

## Q4. 같은 record가 DTO에는 이상적이고 엔티티에는 부적합한 이유

> **옮기는 데이터는 도중에 바뀌면 안 되니 불변이 장점이고, 저장소가 추적하며 갱신해야 하는 데이터는 불변이면 곤란하다.**

**같은 성질이 원인이다** — 불변, 인자 없는 생성자 없음, 접근자만 있음.

| | DTO에서 | 엔티티에서 |
|---|---|---|
| 불변 | **장점** — 경계를 넘는 동안 값이 안 바뀐다 | **결격** — 영속성 계층이 필드를 갱신해야 한다 |
| 인자 없는 생성자 없음 | 상관없음 | **결격** — JPA가 인스턴스를 만들 수 없다 |
| 식별자 개념 없음 | 상관없음 | **결격** — 엔티티는 식별자에 의존한다 |

책의 서술이 정확히 갈린다 — DTO는 *"최신 Java에서는 record로 구현하는 경우가 많다"*, 엔티티는 *"식별자와 가변성에 의존한다. 그래서 record는 이 역할에 잘 맞지 않는다."*

**성질이 좋고 나쁜 게 아니라 목적이 다른 것이다.** [[../chapter-2-creating-web-and-api-applications-with-spring-boot/04a-adding-demo-data-to-a-template|Chapter 2에서 쓴 record]]가 DTO로 이상적이었던 바로 그 성질이 여기서 결격 사유가 된다.

## Q5. DTO가 "JSON을 위한 클래스"가 아니라는 Note의 요지

**DTO의 정의를 형식에서 떼어 놓는 것이다.**

Note: *"DTO가 JSON에만 국한된 것은 아니다. XML이든 다른 어떤 데이터 교환 형식이든 데이터의 형식을 제대로 갖춰야 할 필요는 똑같다."*

**DTO는 "경계를 넘기 위한 클래스"이고, 그 경계 너머가 JSON이든 XML이든 HTML이든 상관없다.**

**왜 이 구분이 중요한가**: DTO를 "JSON용 클래스"로 이해하면 두 가지 오해가 따라온다.
- HTML 템플릿에 넘기는 객체는 DTO가 아니라고 생각하게 된다 — **아니다.** 그것도 경계를 넘는다.
- Jackson 애노테이션이 붙어야 DTO라고 생각하게 된다 — **아니다.** 애노테이션은 형식 조정 도구일 뿐이다.

**JSON이 눈에 띄는 이유는 인기 때문이다.** *"JSON이 오늘날 업계에서 가장 인기 있는 형식일 뿐이며, 그래서 Spring Web을 고르면 Spring Boot가 Jackson을 기본으로 클래스패스에 올려 두는 것이다."*

## Q6. 엔티티에만 있고 DTO에는 없어야 할 필드 세 종류

| 필드 | 왜 DTO에 없어야 하나 |
|---|---|
| **`id` (기본 키)** | **내부 식별자를 노출하면 그것이 곧 API 계약이 된다.** 저장소를 바꾸면 깨진다 |
| **`createdAt`·`createdBy` (감사 필드)** | **저장소 운영의 관심사이지 소비자의 관심사가 아니다** |
| **스키마 제약을 반영한 타입** | 소비자에게는 **컬럼 길이나 nullable 여부가 의미 없다** |

**첫 번째가 가장 실질적이다.** DB 자동 증가 id를 API에 노출하면 소비자가 그것으로 URL을 만들고 저장한다. 그 순간 **"id는 순차 정수다"가 계약이 된다.** UUID로 바꾸거나 저장소를 옮기면 깨진다. (부수적으로 순차 id는 **총 레코드 수를 추측할 수 있게** 하는 정보 노출이기도 하다.)

**반대 방향도 성립한다** — DTO에는 있어도 엔티티에는 없어야 하는 것: 여러 엔티티를 합쳐 만든 **요약 필드**, 표시용으로 **가공한 문자열**. 엔티티에 넣으면 **저장할 것도 아닌 필드가 매핑 대상으로 끼어든다.**

**그리고 이 분리가 Chapter 2에서 남긴 문제의 해법이다** — 엔티티에 필드를 더해도 DTO를 안 건드리면 **계약은 그대로다.**

## Q7. "패러다임이지 코딩 구조가 아니다"

**컴파일러도 프레임워크도 이 구분을 강제하지 않는다는 뜻이다.**

`@Entity`가 붙은 클래스를 그대로 `@RestController`에서 반환해도 **아무 오류가 없다.** 같은 클래스에 `@Entity`와 Jackson 애노테이션을 함께 붙여도 컴파일되고 실행된다.

**비유가 깨지는 지점이 여기다.** 여권과 원부는 **발급 기관이 물리적으로 구분을 강제한다** — 여권에 원부의 모든 항목을 적어 넣을 수 없다. DTO와 엔티티는 **아무 도구도 강제하지 않는다.**

**실무에서 뜻하는 바**:
- **코드 리뷰와 팀 합의로만 유지된다.** "이 엔티티를 컨트롤러가 그대로 반환하고 있다"를 지적할 사람이 필요하다.
- **어기는 쪽이 항상 더 쉽다.** 매핑 코드를 안 쓰는 것이 쓰는 것보다 편하다. 규율이 없으면 자연히 무너진다.
- **검출 장치를 따로 두는 팀도 있다.** 아키텍처 테스트로 "웹 계층이 `@Entity` 타입을 반환하지 않는다"를 검사한다.

[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04b-building-our-app-with-a-better-design|Chapter 2의 계층 분리]]와 정확히 같은 성질이다 — 방향을 지키는 것은 컴파일러가 아니라 사람이다.

## Q8. 분리하지 않아도 되는 상황의 판단 기준

> **"이 코드가 오래 살 것인가?"**

책의 Tip이 원칙을 **적용 조건과 함께** 준다: *"Spring Boot를 제안하려고 CTO에게 보여 주는 그 데모는 어떤가? 그건 요점을 전달해야 하는 **단기 시나리오**다. 오래 갈 앱을 만드는 게 아니라 빠른 데모를 만드는 것이다. 그런 상황에서는 한 클래스가 DTO와 엔티티를 겸해도 괜찮다."*

**"항상 나눠라"가 아닌 이유**: 그 조언은 지키기도 어렵고 **왜 지키는지도 흐려진다.** 분리에는 실제 비용이 따른다 — 매핑 코드를 손으로 쓰거나 매핑 라이브러리를 도입해야 하고, **필드가 늘 때마다 두 곳을 고쳐야** 한다.

| 상황 | 판단 |
|---|---|
| CTO 데모, 프로토타입, 실험 | **겸해도 된다** |
| 운영에 올릴 것 | 나눈다 |
| 이 장의 예제 | **나눈다** — 데모라도 설명에 유리하므로 |

마지막 줄이 재미있다. 이 장은 데모인데도 `VideoEntity`(엔티티)와 `VideoSearch`·`UniversalSearch`(DTO)를 실제로 나눠 쓴다 — [[04-using-custom-finders]], [[05-query-by-example-for-dynamic-search]]. **가르치려는 목적이 또 하나의 "오래 사는 이유"인 셈이다.**
