## Q1. `EntityManager`로 직접 쓸 때 반복되는 세 문제

1. **배관 코드가 전부 같다.** `EntityManager` 얻고, 쿼리 만들고, 실행하고, 닫는다. **엔티티가 열 개면 이 뼈대가 열 번 복사된다.**
2. **쿼리 문자열이 코드 안에 흩어진다.** `"select v from VideoEntity v"`에서 엔티티 이름을 바꿔도 **컴파일러가 잡아 주지 않는다.** 실행해 봐야 안다.
3. **타입 안전성이 두 번 무너진다.** 쿼리 문자열은 검사되지 않고, 결과 타입도 `getResultList()`가 돌려주는 것을 믿어야 한다.

**가장 아픈 것은 1번이다.** 서로 다른 것은 **쿼리 한 줄**인데 같은 것이 **열 줄**이다. 신호 대 잡음비가 나쁘고, 그 잡음이 엔티티 수만큼 곱해진다.

**그래서 해법의 방향이 정해진다** — 책의 도발적 질문: *"최고의 쿼리는 무엇인가? **우리가 쓰지 않아도 되는 쿼리다!**"*

## Q2. "도메인 말"과 "쿼리 말"

책의 요약: *"애플리케이션은 리포지토리에 **도메인 말**로 이야기하고, 리포지토리는 다시 데이터 저장소에 **쿼리 말**로 이야기한다."*

| | 도메인 말 | 쿼리 말 |
|---|---|---|
| 예 | `findByName("SPRING")` | `select v.* from video_entity v where v.name = ?1` |
| 어휘 | 엔티티, 필드, 비즈니스 개념 | 표 이름, 컬럼 이름, 조인, 방언 |
| 아는 사람 | 애플리케이션 개발자 | 데이터베이스 |
| 바뀌는 이유 | 요구가 바뀔 때 | 스키마·DB 제품이 바뀔 때 |

**마지막 줄이 분리의 실익이다.** 두 말이 **서로 다른 이유로 바뀐다.** 섞어 두면 스키마를 바꿀 때 애플리케이션 코드를 뒤져야 한다.

**비유**: 리포지토리는 **도서관 사서**다. 나는 "『자바의 정석』 있나요?"라고 **내 말로** 묻고, 사서가 그것을 **청구기호와 서가 번호**로 옮긴다. 나는 청구기호 체계를 몰라도 된다.

**`repository`라는 이름 자체가 "보관소"**인 것도 맞물린다 — 데이터를 담아 두는 곳이 아니라 **그 데이터에 이르는 모든 경로를 한곳에 모아 둔 곳**이다.

## Q3. 몸통이 빈 인터페이스가 동작하는 다섯 단계

```java
public interface VideoRepository extends JpaRepository<VideoEntity, Long> {
}
```

1. **컴포넌트 스캔이 `Repository`를 상속한 인터페이스를 찾는다.** — 마커가 있어야 "이건 리포지토리다"를 기계가 판별할 수 있으므로
2. **제네릭 인자에서 도메인 타입과 키 타입을 읽는다.** — 어떤 엔티티를 다루는지 알아야 매핑 메타데이터를 찾으므로
3. **`@Entity` 매핑 메타데이터를 참조해 각 메서드가 어떤 쿼리가 될지 결정한다.** — 필드 이름과 컬럼 이름의 대응이 필요하므로
4. **그 인터페이스를 구현한 프록시를 런타임에 만들어 빈으로 등록한다.** — 인터페이스에 몸통이 없으므로 누군가 실제 실행을 맡아야 하므로
5. **주입받는 쪽은 `VideoRepository` 타입으로 받는다.** — 쓰는 코드가 이 과정을 몰라도 되게

**4단계가 [[02b-pojos-and-the-spring-programming-model]]의 프록시와 같은 발상이다** → Q5.

**3단계가 [[02a-entities-in-jpa]]에서 `@Entity`가 필요했던 이유를 회수한다** — 매핑 메타데이터가 없으면 쿼리 파생이 불가능하다.

## Q4. `Repository` 마커 인터페이스가 비어 있어야 하는 이유

**메서드가 하나라도 있으면 모든 리포지토리가 그 메서드를 갖게 되고, [[01a-using-spring-data-to-easily-manage-data]]에서 본 최소공통분모 문제가 재현된다.**

```
Repository에 findAll()을 넣는다면?
   → 모든 저장소의 리포지토리가 findAll()을 갖는다
   → 그런데 어떤 저장소는 "전체 조회" 개념이 없거나 위험하다
   → 결국 "다 지원하는 것"만 넣게 된다 = 최소공통분모
```

**아무것도 넣지 않았기 때문에 저장소별 하위 인터페이스가 자유롭게 갈릴 수 있다.** `JpaRepository`는 JPA에 맞는 연산을, MongoDB 리포지토리는 그쪽에 맞는 연산을 각자 정의한다.

**마커의 역할은 "판별"뿐이다** — Spring Data가 스캔에서 "이건 리포지토리다"를 알아보는 표식. 계약을 담지 않는다.

**Q3의 1단계와 이어 보면 완결된다**: 기계가 알아볼 표식은 필요하고(그래서 인터페이스가 존재하고), 계약을 강제하면 안 되므로(그래서 비어 있고).

## Q5. 두 프록시가 같은 것과 다른 것

| | [[02b-pojos-and-the-spring-programming-model]]의 프록시 | 이 노트의 프록시 |
|---|---|---|
| **원본** | **있는 클래스**(`VideoService`) | **없다** — 인터페이스뿐 |
| **하는 일** | 원본을 **감싸고** 호출 전후에 부가 동작 후 **위임** | **구현 자체를 만들어 낸다** |
| 목적 | 횡단 관심사(트랜잭션·보안) | 쿼리 실행 |
| **같은 점** | 컨테이너가 **생성을 통제**하기 때문에 가능 | 동일 |
| 같은 점 | 주입받는 쪽은 **원래 타입으로** 받고 이 구조를 모른다 | 동일 |

**한 문장으로**: 거기서는 **있는 클래스를 감쌌고**, 여기서는 **없는 구현을 만들어 낸다.**

**둘 다 "컨테이너가 `new`를 통제하기 때문에 가능한 일"이다** — [[../chapter-2-creating-web-and-api-applications-with-spring-boot/04c-injecting-dependencies-through-constructor-calls|Chapter 2]]에서 시작된 사슬이 여기까지 온다.

**부수 효과도 같다**: 디버거에서 **클래스 이름이 낯설고**, 그 클래스에 **중단점을 걸 수 없다.**

## Q6. `ID`, `T`, `S`

| 기호 | 뜻 | 예 |
|---|---|---|
| **`ID`** | 리포지토리의 **기본 키 타입** | `Long` |
| **`T`** | 리포지토리의 **직접적인 도메인 타입** | `VideoEntity` |
| **`S`** | **`T`를 상속하는 하위 타입.** 때로 **projection 타입**에 쓰인다 | `VideoEntity` 또는 그 부분 뷰 |

**`S`가 따로 있는 이유**가 중요하다. `save(S entity)`처럼 선언하면 **`T`의 하위 타입을 넣어도 그 타입 그대로 돌려받는다.** `T`로만 선언했다면 하위 타입을 넣어도 `T`로 받게 되어 다운캐스팅이 필요하다.

**projection 언급은 이 장 밖으로 이어지는 실마리다** — 도메인 타입 전체가 아니라 **필요한 필드만 담은 타입**으로 결과를 받을 수 있다는 뜻이며, [[02-dtos-entities-and-pojos]]의 DTO 분리와 맞닿는다.

## Q7. `List`가 아니라 `Iterable`을 요구하는 의도

**호출자가 전부를 한 번에 메모리에 올리지 않아도 되게 하기 위해서다.**

`Iterable`은 "순회할 수 있다"만 요구하고 **"모든 원소가 메모리에 완전히 실체화되어 있을 것"을 요구하지 않는다.** 스트림처럼 하나씩 흘려 보내는 구현도 넘길 수 있다.

```java
deleteAllById(Iterable<ID> ids)   // 100만 개 id를 List로 만들지 않아도 된다
```

**큰 데이터를 다룰 때 이 차이가 실제로 드러난다.** `List`로 선언했다면 호출자가 반드시 전부를 리스트로 만들어야 하고, 그 자체가 메모리 압박이 된다.

**물론 `List`를 넘겨도 된다** — `List`는 `Iterable`이다. 왜 굳이 상위 타입을 썼는지가 이 의도에 있다. **API가 요구를 최소로 두면 호출자의 선택지가 넓어진다.**

**같은 원리의 반대 예**: 반환 타입은 `List`가 흔하다. 돌려줄 때는 호출자가 크기를 알고 여러 번 순회할 수 있는 편이 낫기 때문이다. **받을 때는 느슨하게, 줄 때는 구체적으로.**

## Q8. `JpaRepository`로 "이름에 SPRING이 들어간 비디오"를 못 찾는 이유

**주어진 연산에 "조건"이라는 축이 없기 때문이다.**

| 묶음 | 되는 것 |
|---|---|
| 조회 | 전체(`findAll`), **정렬**(`findAll(Sort)`), **페이지**(`findAll(Pageable)`), **키로 하나**(`findById`) |
| 삭제·저장·집계 | 키 기준 또는 전체 기준 |

**`findAll()`은 전부 가져오고 `findById()`는 키로 하나 가져온다.** 그 사이가 없다. **페이징과 정렬은 되지만 조건은 안 된다.**

**왜 없나**: `JpaRepository`가 줄 수 있는 것은 **엔티티 타입만 알면 만들 수 있는 연산**뿐이다. "이름에 SPRING이 들어간"은 **어떤 필드를 어떤 방식으로 비교할지**를 알아야 하는데, 그 정보가 인터페이스 선언 어디에도 없다.

**그러면 그 정보를 어디에 적을 것인가** — 그것이 다음 노트의 답이다. **메서드 이름에 적는다** → [[04-using-custom-finders]].

책의 정리: *"이 모든 연산이 엄청난 힘을 주지만, 한 가지 빠진 것이 있다 — **더 구체적인 기준으로 질의하는 능력**이다."*
