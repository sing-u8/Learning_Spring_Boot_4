## Q1. 컨트롤러가 HTML 문자열을 직접 만들면 무너지는 세 지점

```java
return "<h1>Greetings...</h1>" + "<p>In this chapter...</p>";
```

돌아가긴 한다. 그리고 정확히 셋이 무너진다.

1. **HTML이 Java 문자열이 된다.** 따옴표 이스케이프, 줄바꿈 연결, 들여쓰기가 전부 사라진다. 에디터의 HTML 문법 검사도 자동 완성도 작동하지 않는다. 도구가 이걸 HTML로 보지 않기 때문이다.
2. **화면을 고치려면 Java를 다시 컴파일해야 한다.** 문구 하나 바꾸는 데 빌드 사이클이 돈다.
3. **디자이너와 협업할 수 없다.** HTML 파일이 **존재하지 않으니** 브라우저로 열어 볼 수도, 디자인 도구에 넣을 수도 없다.

**셋의 공통 뿌리는 하나다** — HTML이 파일이 아니라 코드 안에 있다. 그래서 해법도 하나다: **HTML을 파일로 두고, 컨트롤러는 "그중 어느 파일인지"만 이름으로 말한다.**

## Q2. `"index"`가 파일이 되기까지의 조립

접두사와 접미사를 붙이는 **단순한 문자열 조립**이다.

```text
컨트롤러가 돌려준 값:              "index"
                                      │
 앞에 기본 위치를 붙인다 ──────────▶  src/main/resources/templates/index
                                      │
 뒤에 엔진별 확장자를 붙인다 ───────▶  src/main/resources/templates/index.mustache
                                      │
 그 파일을 읽어 Mustache 엔진에 ───▶  렌더링된 HTML
```

- **접두사** `src/main/resources/templates/`는 Boot의 템플릿 엔진용 구성 프로퍼티 기본값이다.
- **접미사** `.mustache`는 엔진마다 다르다. Thymeleaf면 `.html`이다.
- 둘 다 **구성 프로퍼티로 바꿀 수 있다.**

이 조립을 하는 주체가 **뷰 해석**이고, 그것을 가능하게 한 것이 [[03-augmenting-an-existing-project-with-initializr]]에서 더한 스타터다. 스타터가 없으면 `"index"`는 **해석할 사람이 없는 문자열**로 남는다.

## Q3. 템플릿 파일 이름에 오타를 내면 언제 알게 되나

**애플리케이션은 아무 경고 없이 정상 시작하고, 누군가 실제로 그 URL을 요청하는 순간 500으로 터진다.**

**왜 그때인가**: 뷰 이름은 **런타임 문자열**이다. 컨트롤러는 그 파일이 존재하는지 모르고, 컴파일러도 그 문자열이 파일 이름이라는 사실 자체를 모른다. 파일 존재 확인은 **실제로 그 뷰를 해석하려 할 때** 처음 일어난다.

**비유가 깨지는 지점이 여기다.** 도서관 사서는 책이 없으면 *찾는 순간* "없습니다"라고 말해 준다. 뷰 해석은 그렇지 않다.

**이것이 관례의 대가다.** [[02-creating-a-spring-mvc-web-controller]] Q6에서 본 자유 — 템플릿 엔진을 바꿔도 컨트롤러가 안 바뀐다 — 와 **같은 성질의 뒷면**이다. 컨트롤러가 파일을 모르기 때문에 자유롭고, 모르기 때문에 컴파일러가 못 잡는다.

**대응**: 컨트롤러 테스트를 쓴다. 실제로 그 경로를 호출해 보는 테스트만이 이 오타를 빌드 단계에서 잡는다.

## Q4. "관례를 바꿀 수 있지만 따르는 편이 낫다"의 실질적 이유

**관례의 값은 규칙 자체가 아니라 "모두가 같은 규칙을 안다"는 데 있다.**

위치나 확장자를 바꾸면 기술적으로는 아무 문제가 없다. 문제는 사람 쪽에서 생긴다 — **그 프로젝트를 처음 여는 사람이 `templates` 폴더를 찾다가 못 찾는다.** 그리고 그 순간부터 팀의 모든 사람이 그 설정을 알고 있어야 한다.

바꿔서 얻는 것(내 취향에 맞는 경로)과 잃는 것(모두가 알던 공통 지식)을 비교하면 **얻는 것보다 잃는 것이 큰 경우가 많다.**

**일반화**: 관례 우선 설정에서 관례를 벗어나는 결정은 **"이 이득이 팀 전체의 학습 비용보다 큰가"**로 판단한다. 대부분은 아니다.

## Q5. `templates/`와 `static/`을 가르는 판별 질문

> **"이 파일에 서버 데이터를 끼워 넣어야 하는가?"**

그렇다면 `templates/`다.

| | `templates/` | `static/` |
|---|---|---|
| 접근 경로 | **URL로 직접 열 수 없다.** 컨트롤러를 거쳐 뷰 해석을 통해서만 | **컨트롤러를 거치지 않는다.** URL로 직접 서빙 |
| 처리 | 템플릿 엔진이 읽고 렌더링 | 파일 그대로 전달 |
| 예 | `index.mustache` | `app.js`, `style.css`, 이미지 |

이름이 둘 다 리소스 폴더라 섞기 쉽지만 **접근 경로 자체가 다르다.** `templates/index.mustache`를 브라우저에서 `/templates/index.mustache`로 열 수 없고, `static/app.js`는 컨트롤러 없이도 `/app.js`로 나온다.

이 구분은 뒤에서 다시 중요해진다 — [[07-bundling-javascript-with-nodejs]]에서 번들러가 결과물을 어디에 쓸지 정할 때 이 규칙이 근거가 된다.

## Q6. Mustache 문법이 하나도 없는데 스타터가 필요한 이유

**"Mustache 문법이 없다"와 "Mustache가 필요 없다"는 다른 말이다.**

`index.mustache`는 100% 순정 HTML5지만, 그 파일이 **엔진을 거치지 않는 것은 아니다.** 엔진은 여전히 파일을 읽고 처리하며, 단지 바꿀 자리표시자가 없을 뿐이다.

더 근본적으로, 스타터가 없으면 **`"index"`라는 문자열을 파일로 바꿀 주체 자체가 없다.** 뷰 해석 인프라가 등록되지 않으므로 컨트롤러의 반환값은 해석되지 않는다. 문법 사용 여부와 무관하게 **뷰 해석 경로 전체**가 스타터에 달려 있다.

**이 성질이 오히려 장점이다.** 템플릿이 순정 HTML로 남을 수 있다는 것 — 데이터 없이 브라우저로 열어 볼 수 있고 디자이너가 손대도 깨지지 않는다 — 이 로직 없는 템플릿 설계가 노린 바로 그 결과다. Mustache 템플릿은 "특수 문법으로 쓴 문서"가 아니라 **"HTML인데 필요할 때만 몇 글자가 더 있는 문서"**다.

## Q7. 컴포넌트 스캔과 자동 구성이 각각 기여한 것

**둘 다 빈을 만들지만 대상이 다르다.**

| | 무엇을 다루나 | 이 화면에 기여한 것 |
|---|---|---|
| **컴포넌트 스캔** | **내가 쓴 코드** | `@Controller`가 붙은 `HomeController`를 찾아 인스턴스로 만들고 요청 라우팅 인프라에 등록 |
| **자동 구성** | **Boot가 제공하는 구성 후보** | ① MVC 인프라(디스패처·핸들러 매핑) ② Mustache 클래스를 보고 **엔진을 뷰 인프라에 꽂는 빈** 등록 |

**두 번째 항목이 이 절의 핵심 기여다.** 자동 구성의 Mustache 부분이 없으면 `"index"`는 해석할 사람이 없는 문자열로 남는다. 그래서 [[03-augmenting-an-existing-project-with-initializr]]에서 스타터를 더한 것이 이 절의 전제였다.

**진단에도 그대로 쓰인다**: 컨트롤러가 안 걸리면 컴포넌트 스캔 범위(패키지 위치)를, 뷰가 해석 안 되면 자동 구성 조건(스타터가 클래스패스에 있는지)을 의심한다.
