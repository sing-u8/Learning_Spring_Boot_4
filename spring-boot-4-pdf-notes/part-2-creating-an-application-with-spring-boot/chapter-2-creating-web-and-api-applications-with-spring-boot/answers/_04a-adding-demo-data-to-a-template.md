## Q1. 컨트롤러에서 HTML 조각을 만들어 넘기면

```java
for (String name : videoNames) { html += "<li>" + name + "</li>"; }
model.addAttribute("listHtml", html);
```

1. **HTML이 다시 Java 문자열로 돌아온다.** [[04-leveraging-templates-to-create-content]]에서 템플릿 파일로 옮긴 이유가 통째로 무효가 된다.
2. **이스케이프가 사라진다.** ← **보안 측면**
3. **화면 구조를 바꾸려면 Java를 고쳐야 한다.** `<ul>`을 `<table>`로 바꾸는 일이 컨트롤러 수정이 된다.

**2번을 자세히.** 비디오 제목에 `<`가 들어오면 **그대로 태그로 해석된다.** 제목이 `<script>...</script>`라면 그 스크립트가 다른 사용자의 브라우저에서 실행된다. 사용자가 제목을 입력하는 순간 이건 XSS 구멍이다.

**템플릿을 쓰면 왜 안전한가**: `{{name}}`은 값을 **HTML 이스케이프해서** 출력한다. `<`는 `&lt;`가 되어 화면에 글자로 보인다. 이스케이프가 **기본값이고 opt-out이 명시적**이라는 것이 핵심이다 — 컨트롤러에서 문자열을 이어 붙이면 이 기본 안전장치를 통째로 건너뛴다.

## Q2. 값이 하나뿐인데도 `record Video(String name)`을 만드는 이유

**Mustache가 이름 있는 속성 위에서 동작하기 때문이다.**

만약 `List<String>`을 넘겼다면 템플릿에서 각 항목의 **이름을 부를 방법이 없다.** `{{name}}`이라고 쓸 대상이 없다. record가 `name`이라는 **이름을 만들어 준다.**

책은 두 가지 이유를 든다.

- 이름과 값을 가진 raw JSON을 손으로 쓸 수도 있지만 **record가 더 간단하다.**
- **더 강한 타입 안전성**을 준다. `Video` 타입이 템플릿에 넘길 데이터를 깔끔하게 감싼다.

**한 문장으로**: 값이 하나여도 그 값에는 **이름이 필요하고**, record는 그 이름을 만드는 가장 짧은 방법이다.

그리고 record 자체가 짧다 — `record Video(String name) {}` 한 줄로 생성자·접근자·`equals`·`hashCode`·`toString`이 전부 생긴다.

## Q3. `Model` 인스턴스는 누가 만들고 왜 요청마다 새로 만드나

**우리가 만들지 않는다. Spring MVC가 만들어 넘겨준다.**

`Model`은 Spring MVC가 웹 메서드에 선택적으로 붙일 수 있게 지원하는 여러 파라미터 타입 중 하나다. **파라미터로 요구하기만 하면** 프레임워크가 채워서 넘긴다.

1. Spring MVC가 `index` 메서드 시그니처를 보고 `Model` 타입 파라미터를 발견한다. — 호출 전에 무엇이 필요한지 알아야 하므로
2. **요청마다 새 `Model` 인스턴스를 만들어** 인자로 넘긴다. — **요청 간에 데이터가 섞이지 않게 하기 위해**
3. 우리 코드가 `addAttribute("videos", videos)`로 모델 속성 하나를 담는다.
4. 메서드가 뷰 이름을 반환하면 그 모델을 템플릿 엔진에 함께 넘긴다.

**2번이 질문의 핵심이다.** [[02-creating-a-spring-mvc-web-controller]]에서 본 그 문제 — 컨트롤러 빈은 하나이고 요청 스레드는 여럿 — 의 해법이 여기 있다. 컨트롤러 필드에 요청 데이터를 두면 섞이지만, **메서드 파라미터로 받은 `Model`은 그 호출에만 속하므로** 스레드마다 자기 것을 갖는다.

즉 `Model`이 파라미터인 것은 편의가 아니라 **스레드 안전성의 설계**다.

## Q4. `{{#videos}}`가 "반복"이 아니라 "섹션"인 이유

**같은 문법이 값의 종류에 따라 다르게 동작하기 때문이다.**

| `videos`의 값 | `{{#videos}}...{{/videos}}`의 결과 |
|---|---|
| 항목 3개짜리 목록 | 블록이 **3번 펼쳐진다** (반복) |
| 빈 목록 | 블록이 **사라진다** (조건) |
| `null` 또는 속성 자체가 없음 | 블록이 **사라진다** (오류 아님) |
| **단일 객체** | 블록이 **1번**, 그 객체를 문맥으로 펼쳐진다 |
| `false` | 블록이 사라진다 (조건) |

"반복"이라고 부르면 3~5행을 설명할 수 없다. 단일 객체일 때는 반복이 아니라 **문맥 전환**이고, `false`일 때는 **조건**이다.

**로직 없는 템플릿이 `if`와 `for`를 따로 두지 않고 이 하나로 처리하는 방식이다.** 문법은 줄었지만 대가가 있다 — **"이름을 틀렸을 때"와 "값이 비었을 때"가 화면에서 구별되지 않는다.** → Q5.

## Q5. `{{#video}}`(단수)로 잘못 쓰면

**화면에 아무것도 나타나지 않는다. 오류도 경고도 없다.**

Mustache는 `video`라는 속성을 찾고, 없으므로 위 표의 3행("속성 자체가 없음")에 해당해 **블록 전체를 조용히 삭제한다.**

**왜 오류가 아닌가**: 로직 없는 템플릿이 **"값이 없으면 안 그린다"를 정상 동작으로 정의**하기 때문이다. 이건 버그가 아니라 설계다 — 조건 분기를 별도 문법 없이 표현하려면 "없음"이 유효한 입력이어야 한다.

**그래서 이 조용함이 이 방식에서 가장 흔한 디버깅 함정이다.** 택배는 라벨을 잘못 쓰면 반송되거나 사고가 나서 **알게 되지만**, 여기서는 아무 일도 일어나지 않는다.

**진단 순서**: 화면이 비면 → ① 모델 속성 이름 철자 ② 실제로 `addAttribute`가 호출됐는지 ③ 값이 빈 목록인지. 셋의 증상이 **전부 같다.**

## Q6. record에 `getName()`이 없는데 `{{name}}`이 동작하는 이유

**Mustache가 두 형태를 모두 시도하기 때문이다.**

- 전통적인 JavaBean: `getName()`
- Java record가 컴파일러에서 만드는 것: **`name()`** (`getName()`이 아니다)

`{{name}}`은 **"필드를 직접 읽는다"는 뜻이 아니다.** 접근자 메서드를 호출해 값을 얻는다는 뜻이고, 그 메서드 이름이 `getName()`이든 `name()`이든 Mustache가 둘 다 찾아본다.

**이 성질이 record를 쓸 수 있게 만든 조건이다.** 그래서 record와 기존 JavaBean이 **한 템플릿 문법 아래 공존**한다. 데이터 타입을 record로 바꿔도 템플릿을 고칠 필요가 없다.

[[01-autoconfiguring-spring-beans]]의 "Spring bean과 JavaBean은 다른 기준"과 이어 보면 재미있다 — JavaBean 관례를 **실제로 요구하는 자리**가 따로 있는데, Mustache는 그 요구를 완화한 쪽이다.

## Q7. `model.addAttribute("clips", videos)`로 바꾸면

**템플릿의 `{{#videos}}`와 `{{/videos}}`를 `{{#clips}}`, `{{/clips}}`로 바꿔야 한다.** (안쪽 `{{name}}`은 그대로다 — 그건 `Video` 타입의 필드 이름이지 모델 속성 이름이 아니다.)

**왜인가**: `model.addAttribute("videos", videos)`에서 **왼쪽 문자열과 오른쪽 변수 이름이 우연히 같을 뿐**이다. 템플릿이 보는 것은 **왼쪽 문자열뿐**이다. Java 변수 이름은 템플릿에 전혀 전달되지 않는다.

**그 이름이 컨트롤러와 템플릿 사이의 유일한 계약이다.** 그리고 이 계약은 **컴파일러가 검사하지 않는다** — 한쪽만 바꾸면 Q5의 조용한 실패가 된다.

## Q8. `HomeController`가 동시에 맡고 있는 세 책임

```java
@Controller
public class HomeController {
    record Video(String name) {}        // ② 데이터의 형태를 정의한다
    List<Video> videos = List.of(...);  // ③ 데이터를 보관한다
    @GetMapping("/") ...                // ① HTTP 요청을 받는다
}
```

| # | 책임 | 원래 있어야 할 곳 |
|---|---|---|
| ① | HTTP 요청을 받는다 | **컨트롤러의 일** — 여기 있는 게 맞다 |
| ② | `Video`라는 데이터 형태를 정의한다 | **도메인의 일** |
| ③ | 비디오 목록을 보관한다 | **저장소의 일** |

세 책임의 **변경 주기가 다르다**는 것이 문제다. 웹 요구(①)는 자주 바뀌고, "비디오에는 이름이 있다"(②)는 사실은 그만큼 자주 바뀌지 않는다. **변경 주기가 다른 것을 한 파일에 두면 자주 바뀌는 쪽이 안 바뀌는 쪽을 계속 건드린다.**

그리고 ③은 즉각적인 실무 문제도 만든다 — **컨트롤러 빈이 하나이므로 이 필드도 하나다.** 애플리케이션 전체가 공유하는 상태다. 데모에서는 편리하지만 실제로는 잘못된 자리다.

이 상태가 왜 문제인지와 어떻게 나누는지는 [[04b-building-our-app-with-a-better-design]]에서 이어진다.
