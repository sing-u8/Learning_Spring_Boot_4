## Q1. 시그니처만 보고 답할 수 없는 두 질문

```java
Video getFirstVideosByName(String name) { ... }
```

1. **`name`에 `null`을 넘겨도 되나?** NPE가 날까, "전체 검색"으로 처리될까?
2. **반환값이 `null`일 수 있나?** 못 찾으면 `null`일까, 예외를 던질까?

**시그니처는 침묵한다.** 답을 알려면 구현을 읽거나, 문서를 찾거나, 실행해 봐야 한다. **세 번째가 가장 흔하다.**

**핵심 통찰**: **정보가 없었던 것이 아니라 정보가 코드에 적힐 자리가 없었던 것이다.** 서비스를 쓴 사람은 "못 찾으면 null"이라는 사실을 알고 있었다. 그저 그것을 시그니처에 쓸 방법이 없었을 뿐이다.

## Q2. NPE가 "런타임에 발견된다"의 네 단계

```java
Video v = videoService.getFirstVideosByName(query);
System.out.println(v.name());          // ← 여기서 NPE
```

1. **컴파일러는 아무 말도 안 했다.**
2. **테스트에 "못 찾는 경우"가 없었다면 통과했다.**
3. **운영에서 특정 검색어가 들어왔을 때** 처음 터진다.
4. **스택 트레이스는 `v.name()` 줄을 가리키지만, 진짜 원인은 `orElse(null)`을 쓴 서비스 쪽이다.**

**4번이 가장 나쁘다.** 증상이 나타나는 곳과 원인이 있는 곳이 다르다. 호출부를 아무리 봐도 답이 없고, 서비스 구현까지 거슬러 올라가야 한다.

**그리고 3번 때문에 발견이 늦다** — 특정 입력에서만 나므로 개발·스테이징을 통과한다.

## Q3. JSpecify가 표준화하려는 대상

**`@Nullable` 애노테이션의 "의미론"이다.**

책의 표현: *"Java에는 수년간 서로 경쟁하는 `@Nullable` 애노테이션 변종이 많았다. JSpecify의 목표는 nullness 애노테이션을 **잘 정의된 의미론으로 표준화하는 것**이다."*

**이름을 나열해 보면 문제가 보인다** — `javax.annotation.Nullable`(JSR-305), `org.jetbrains.annotations.Nullable`, `androidx.annotation.Nullable`, `org.springframework.lang.Nullable`… **같은 이름의 애노테이션이 최소 대여섯 개** 있었다.

**왜 문제였나**:
- 어떤 것은 **"이 필드가 null일 수 있다"**를, 어떤 것은 **"이 타입 사용이 null일 수 있다"**를 뜻해 미묘하게 달랐다.
- **도구마다 인식하는 것이 달랐다.** IntelliJ가 아는 것과 Eclipse가 아는 것이 달랐다.
- 라이브러리를 조합하면 **한 코드베이스에 여러 변종이 섞였다.**

**즉 문제는 "애노테이션이 없다"가 아니라 "너무 많고 뜻이 제각각이다"였다.** 표준화는 새 기능을 만드는 것이 아니라 **하나의 의미를 정하는 일**이다.

## Q4. 애노테이션 네 개를 두 축으로

| | **범위 전체의 기본값**을 정한다 | **개별 요소**를 지정한다 |
|---|---|---|
| null을 **금지** | **`@NullMarked`** | **`@NonNull`** |
| null을 **허용/미지정** | **`@NullUnmarked`** (미지정) | **`@Nullable`** (허용) |

- **왼쪽 열**은 패키지·클래스·모듈에 붙인다.
- **오른쪽 열**은 반환 타입·파라미터·필드·제네릭 인자에 붙인다.

**아래 행의 두 칸이 성격이 다르다는 점**에 주의한다. `@NullUnmarked`는 **"미지정"**(도구가 검사하지 않음)이고, `@Nullable`은 **"명시적 허용"**(null이 계약의 일부)이다. 전자는 마이그레이션용이고 후자는 설계 표현이다.

**`@NullUnmarked`의 용도**: 레거시나 서드파티 코드를 애노테이션 없이 두면서 팀이 **점진적으로** JSpecify를 도입할 수 있게 한다. "아직 안 봤다"를 명시하는 자리다.

## Q5. `@NullMarked` 안에서 `@NonNull`이 중복인데도 쓰는 이유

**중복이지만 무의미하지는 않다.** 세 가지 상황에서 쓴다.

1. **이해를 돕는다.** 특히 중요한 계약을 읽는 사람에게 명시적으로 보인다.
2. **`@NullUnmarked` 범위를 걷어낼 때.** 그 범위 안에서는 기본값이 없으므로 `@NonNull`이 실제 효력을 갖는다.
3. **혼합 작업·마이그레이션·레거시 코드에서 개별 값을 애노테이션할 때.** 패키지 전체를 `@NullMarked`로 못 만드는 상황에서 한 메서드씩 표시한다.

**책의 예제가 2·3번 상황이다.** `§2.2`의 `@NonNull Video getFirstVideosByName(@NonNull String name)`은 `package-info.java`를 아직 만들지 않은 시점의 코드다. `§2.3`에서 `@NullMarked`를 도입한 뒤에는 이 애노테이션들이 중복이 된다.

**설계 판단**: 기본값을 뒤집는 것(`@NullMarked`)이 개별 표시보다 낫다. *"애노테이션 잡음을 줄이고 nullability 규칙을 명확하고 구속력 있게 만든다."* 예외만 표시하면 되므로 **표시해야 할 것이 훨씬 줄어든다.**

## Q6. `@NonNull` 메서드가 `orElse(null)`을 반환해도 컴파일되는 이유

**`@NonNull`은 컴파일러에게 아무 강제력이 없다. 그저 메타데이터일 뿐이다.**

```java
@NonNull Video getFirstVideosByName(@NonNull String name) {
    return videos.stream().filter(...).findFirst().orElse(null);   // 컴파일된다
}
```

Java 컴파일러는 애노테이션을 **바이트코드에 기록하기만** 하고 그 의미를 해석하지 않는다. `@NonNull`이든 `@Deprecated`든 컴파일러 입장에서는 "붙어 있는 표시"다.

**잡아 주는 것은 정적 분석이다** — 프로그램을 실행하지 않고 소스나 바이트코드만 읽어 문제를 찾는 별도의 도구.

**이 사실이 왜 중요한가**: **애노테이션을 붙였다고 안전해지지 않는다.** 그것을 읽고 검사하는 도구가 있어야 한다. 그리고 그 도구가 IDE 경고 수준인지 빌드 게이트인지가 또 다른 문제다 → Q9.

**Java의 설계 선택이기도 하다.** 애노테이션을 컴파일러가 강제하게 만들면 언어 명세를 바꿔야 한다. 메타데이터로 두고 도구에 맡기면 **언어 변경 없이** 여러 검사 체계가 공존할 수 있다.

## Q7. 하위 패키지에서 검사가 안 되는 상황이 왜 알아채기 어려운가

**오류도 경고도 나지 않기 때문이다. 그냥 검사가 안 될 뿐이다.**

```text
com.learningspringboot4              ← package-info.java 에 @NullMarked  ✅
com.learningspringboot4.api          ← 별도 package-info.java 없음        ❌ 미지정
com.learningspringboot4.service      ← 별도 package-info.java 없음        ❌ 미지정
```

**패키지 수준 애노테이션은 하위 패키지에 상속되지 않는다.** 같은 규칙을 원하면 **각 하위 패키지가 자기 `package-info.java`를 정의해야** 한다.

**왜 알아채기 어려운가**:
- **아무 신호가 없다.** 경고가 줄어드는 것이 아니라 애초에 검사 대상이 아니다. "문제가 없다"와 "안 봤다"가 화면에서 같아 보인다.
- **패키지를 나누는 순간 조용히 사라진다.** 리팩터링으로 `service` 패키지를 만들면 그 안의 코드가 보호 밖으로 나간다. 리팩터링 diff에는 아무 흔적이 없다.
- **부분적으로 적용된 상태가 정상처럼 보인다.** 루트 패키지에서는 경고가 잘 뜨므로 "동작한다"고 믿는다.

**비유가 깨지는 지점이 여기다.** 건물 금연 규정은 상식적으로 별관에도 적용될 것 같지만, `@NullMarked`는 **층마다 따로 지정해야 하는** 규정에 가깝다.

**대응**: 패키지를 추가하는 체크리스트에 `package-info.java`를 넣거나, 아예 빌드에서 `@NullMarked` 없는 패키지를 검출한다.

## Q8. `List<@Nullable VideoV2>`의 세 층

**null이 허용되는 곳과 금지되는 곳이 세 층으로 나뉜다.**

```java
private List<@Nullable VideoV2> videosV2 = ...;
record VideoV2(String name, @Nullable String description) {}
```

| 층 | 대상 | 상태 | 근거 |
|---|---|---|---|
| ① **컬렉션 자체** | `videosV2` 변수 | **non-null** | 패키지가 `@NullMarked`이고 여기 `@Nullable`이 없다 |
| ② **컬렉션의 원소** | `List<...>`의 각 항목 | **nullable** | 제네릭 인자에 `@Nullable`을 붙였다 |
| ③ **원소 객체의 필드** | `VideoV2.name` / `.description` | `name`은 **non-null**, `description`은 **nullable** | 필드는 여전히 기본 non-null. `description`만 명시적 허용 |

**②와 ③이 독립적이라는 것이 핵심이다.** 책의 표현: *"컬렉션에 null 원소를 허용한다고 해서 **`VideoV2` 객체 내부의 null 값까지 자동으로 허용되는 것은 아니다.**"*

즉 `videosV2`에 `null`을 넣을 수는 있지만, 넣은 `VideoV2` 객체의 `name`이 `null`인 것은 여전히 계약 위반이다.

**이 세분성이 JSpecify가 `Optional`보다 표현력이 넓은 이유다** — `Optional<List<Optional<VideoV2>>>` 같은 것을 쓰지 않고도 각 층을 따로 말할 수 있다.

## Q9. IDE 경고와 NullAway — "경고"와 "게이트"

| | **IDE 검사** | **NullAway (빌드 강제)** |
|---|---|---|
| 언제 | 타이핑하는 동안 | **빌드할 때** |
| 누구에게 | **그 IDE를 쓰는 사람만** | **모든 사람과 CI** |
| 무시할 수 있나 | **예** — 노란 줄을 지나치면 그만 | **아니오** — 빌드가 실패한다 |
| 팀 일관성 | IDE·설정마다 다르다 | **저장소 전체에 동일** |

책의 Note: *"IDE 검사는 코드를 쓰는 동안 즉각적인 피드백을 주지만, **나중에 nullability 위반이 도입되는 것을 막지는 못한다.**"*

**핵심 차이는 "시간"이다.** IDE 경고는 **지금 이 코드를 쓰는 사람**에게만 작동한다. 6개월 뒤 다른 사람이 다른 IDE로 위반을 넣으면 아무도 모른다. **게이트는 시간에 걸쳐 작동한다.**

**NullAway는 Error Prone 위에서 돌며 JSpecify 계약 위반 시 빌드를 실패시킨다.** `https://github.com/uber/NullAway`, `https://errorprone.info`.

**일반 원리**: 팀 전체에 규칙을 적용하려면 **개인 도구가 아니라 공유 파이프라인**에 걸어야 한다. 코드 포맷터, 린터, 테스트 커버리지 전부 같은 구조다.

## Q10. JSpecify가 `Optional`을 대체하지 않는 이유

**적용 범위가 다르기 때문이다. 보완 관계다.**

| | `Optional` | JSpecify |
|---|---|---|
| **쓸 수 있는 자리** | **반환 타입에만** (필드·파라미터는 권장되지 않는다) | **반환·파라미터·필드·제네릭 인자** |
| **런타임 비용** | 객체를 하나 더 만든다 | **없다** (메타데이터일 뿐) |
| **강제력** | 타입 시스템이 강제 — 값을 꺼내려면 `get()`/`orElse()`를 거쳐야 한다 | 도구가 검사 (Q6) |
| **표현하는 것** | "이 **반환값** 하나가 없을 수 있다" | "이 **API 전반**의 null 규칙" |

책의 Note: *"`Optional`은 Java의 반환 타입 추상화다. JSpecify는 그것을 **보완**하며, 우리가 가장 적절한 추상화를 고를 수 있게 한다."*

**둘의 강점이 정반대다.**
- `Optional`은 **강제력이 있지만 범위가 좁다.** 파라미터에 `Optional`을 쓰면 호출부가 `Optional.of(...)`로 감싸야 해서 지저분해진다.
- JSpecify는 **범위가 넓지만 강제력이 약하다.** 도구가 없으면 아무 일도 안 한다.

**실무 조합**: "이 조회는 결과가 없을 수 있다"는 `Optional<Video>`로 반환 타입에 표현하고, "이 패키지의 모든 파라미터는 non-null이다"는 `@NullMarked`로 표현한다. **서로의 빈자리를 메운다.**

## 재출제 문항

1. `@NonNull` 메서드가 null을 반환하는 코드를 배포했다. 어느 단계도 막지 못했다면 무엇이 빠진 것인가?
2. 리팩터링으로 `service` 패키지를 새로 만들었다. null 검사에 무슨 일이 일어났고, 어떻게 알아챌 수 있는가?
3. `List<@Nullable Video>`에 `new Video(null)`을 넣었다. 계약 위반인가?
4. 팀원 절반이 IntelliJ, 절반이 VS Code를 쓴다. IDE 경고만으로 충분한가?
5. 파라미터에 `Optional`을 쓰는 것이 왜 권장되지 않는가? JSpecify라면 어떻게 표현하는가?
6. `@NullUnmarked`를 쓰는 상황을 하나 들어 보라. `@Nullable`과 무엇이 다른가?
