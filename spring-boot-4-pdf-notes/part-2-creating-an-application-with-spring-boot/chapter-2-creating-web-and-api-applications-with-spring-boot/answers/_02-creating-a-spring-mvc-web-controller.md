## Q1. 실행은 되는데 `localhost:8080`이 비어 있는 이유

**서버는 살아 있는데 `GET /`를 어떻게 처리하라고 말한 코드가 하나도 없기 때문이다.** Initializr가 준 것은 실행 환경이지 동작이 아니다.

두 층이 **둘 다** 필요하다.

| 층 | 하는 일 | 없으면 |
|---|---|---|
| **자동 구성** | MVC 클래스가 클래스패스에 있는 것을 보고 디스패처·핸들러 매핑 등 **인프라 빈**을 등록 | 요청을 받아 분배할 장치 자체가 없다 |
| **컴포넌트 스캔** | `@Controller`가 붙은 **내 클래스**를 찾아 그 인프라에 등록 | 인프라는 있는데 매핑할 대상이 없어 404 |

지금 상태는 **자동 구성만 끝나고 컴포넌트 스캔이 잡을 컨트롤러가 없는** 상태다. 그래서 서버 로그는 정상인데 페이지가 없다.

**진단에도 그대로 쓰인다**: `HomeController`가 안 걸리면 컴포넌트 스캔 범위(패키지 위치)를 의심하고, 디스패처가 없으면 자동 구성 조건을 의심한다.

## Q2. 서블릿을 직접 구현하면 무너지는 지점

1. **거대한 분기문.** 경로가 스무 개가 되면 `doGet` 하나가 `if-else` 덩어리가 된다. 경로 판단이 **선언이 아니라 실행 코드**에 들어간다.
2. **같은 경로가 흩어진다.** HTTP 메서드마다 `doGet`/`doPost`가 따로 있으므로 "같은 `/videos`의 GET과 POST"가 서로 다른 파일로 갈라진다. 응집이 경로 기준이 아니라 메서드 기준이 된다.
3. **배관 코드의 반복.** 요청 파라미터를 꺼내고, 타입을 바꾸고, 응답 형식을 정하는 **똑같은 코드가 모든 서블릿에 복제**된다.

**그래서 나온 해법**은 "경로와 HTTP 메서드에 따라 어느 Java 메서드를 부를지"를 프레임워크에 맡기고, 개발자는 **그 메서드 안의 결정만** 쓰는 것이다. 1번과 2번은 `@GetMapping` 같은 선언이, 3번은 프레임워크의 인자 바인딩과 메시지 변환이 흡수한다.

## Q3. `spring-boot-starter-web` → `spring-boot-starter-webmvc`

**이름만 보고도 아키텍처 선택이 드러나게 하려는 것이다.**

`web`은 "웹을 한다"는 말이라 **서블릿 기반인지 리액티브인지 구분하지 못한다.** Boot 4는 `webmvc`와 `webflux`로 갈라, 빌드 파일 한 줄이 **실행 모델의 선언**이 되게 했다.

✅ 이 이름 변경은 Boot 저장소에서 확인된다 — 옛 `spring-boot-starter-web`은 `spring-boot-starter-webmvc`를 위해 **deprecated**로 표시돼 있다.

이것은 Boot 4 전반의 방향과 같다. 자동 구성을 기술별 모듈로 쪼갠 것도, 테스트 스타터를 기술별로 나눈 것도 같은 판단이다 — **빌드 파일이 라이브러리 목록이 아니라 설계 선언이 되게 한다.**

## Q4. "Spring Web을 넣으면 Jackson이 딸려 온다"

**마법이 아니라 전이 의존성 한 줄이다.** ✅ `spring-boot-starter-webmvc`의 실제 구성:

| 묶인 모듈 | 무엇을 여는가 |
|---|---|
| `spring-boot-starter` | 코어·로깅·자동 구성 기반 |
| `spring-boot-starter-tomcat` | 내장 서블릿 컨테이너 |
| **`spring-boot-starter-jackson`** | **Java ↔ JSON 변환** |
| `spring-boot-http-converter` | HTTP 본문 ↔ 객체 변환기 |
| `spring-boot-webmvc` | Spring MVC 모듈과 그 자동 구성 |

세 번째 줄이 근거다. 내가 선언한 것은 한 줄이지만, 빌드 도구가 그 줄의 전이 의존성을 따라가 Jackson을 클래스패스에 올린다. 그리고 클래스패스에 Jackson이 있으면 자동 구성이 그것을 조건으로 읽어 메시지 변환기를 등록한다.

**이 사슬이 [[05-creating-json-based-apis]]의 전제다.** 거기서 `@RestController`가 객체를 JSON으로 바꿔 돌려줄 수 있는 이유가 지금 이미 갖춰져 있다.

## Q5. `@Controller`를 지우면 / `@GetMapping`을 지우면

**깨지는 단계가 다르다.**

| 지운 것 | 깨지는 단계 | 결과 |
|---|---|---|
| `@Controller` | **컴포넌트 스캔이 이 클래스를 발견하지 못한다** | 빈이 아예 만들어지지 않는다. 그냥 아무도 부르지 않는 평범한 Java 클래스가 된다 |
| `@GetMapping("/")` | 빈은 만들어지지만 **요청 매핑이 등록되지 않는다** | 컨텍스트에 컨트롤러 빈은 있는데 `GET /`로 갈 곳이 없다 |

**둘 다 404지만 원인 층이 다르다.** 전자는 "빈이 없다", 후자는 "빈은 있는데 경로가 안 붙었다". 그래서 진단 방법도 다르다 — 전자는 빈 목록을 보고, 후자는 매핑 목록을 본다.

**같은 계열의 세 번째 실패**도 있다. 애노테이션이 둘 다 맞는데 클래스가 **베이스 패키지 밖**에 있으면 스캔되지 않는다. "애노테이션은 맞는데 404"의 대표 원인이다.

## Q6. `return "index"`가 파일 경로가 아니라서 얻는 자유

`"index"`는 `"/templates/index.mustache"`의 줄임말이 **아니다.** 컨트롤러는 그 파일이 존재하는지도, 확장자가 무엇인지도 **모른다.**

**이 무지가 주는 자유**: 템플릿 엔진을 Mustache에서 Thymeleaf로 바꿔도 **컨트롤러 코드는 한 글자도 바뀌지 않는다.** 파일 확장자가 `.mustache`에서 `.html`로 바뀌어도 마찬가지다. 뷰 해석 규칙이 그 연결을 대신 맡기 때문이다.

**같은 구조를 다른 곳에서도 봤다.** `BookRepository`가 `DataSource` 계약에만 의존한 것, `server.port`가 Tomcat/Jetty 양쪽에 통하는 것과 **같은 형태**다 — 이름(계약)에만 의존하고 구현은 밖에서 정한다.

**대가**: 컴파일러가 잡아 주지 않는다. 오타는 실행 시점에야 드러난다. 자유의 값이다.

## Q7. "이름은 중요하지 않다"와 "의미 있게 지으라"가 모순이 아닌 이유

**겨냥하는 대상이 다르다.**

> **기계는 이름을 안 본다. 사람은 이름만 본다.**

`HomeController`를 `Foo`로, `index()`를 `bar()`로 바꿔도 **동작은 똑같다.** 프레임워크가 보는 것은 `@Controller`와 `@GetMapping`이다. 그래서 "이름은 중요하지 않다"가 참이다.

동시에, 6개월 뒤 이 코드를 여는 사람은 애노테이션보다 **이름을 먼저 읽는다.** `HomeController`는 "우리 사이트의 home 경로를 담당하는 컨트롤러"라는 뜻을 이름만으로 전달한다. 그래서 "의미 있게 지으라"도 참이다.

**두 문장은 각각 "무엇이 동작을 결정하는가"와 "무엇이 이해를 결정하는가"에 답한다.** 같은 질문에 다른 답을 하는 것이 아니다.

## Q8. 컨트롤러 필드에 이번 요청의 사용자 이름을 저장하면

**다른 요청의 값과 섞인다.**

Spring의 컨트롤러 빈은 기본적으로 **애플리케이션 전체에 딱 하나**만 만들어진다. 그런데 요청을 처리하는 **스레드는 여럿**이다. 여러 스레드가 그 하나의 인스턴스를 동시에 쓴다.

```
스레드 A: 필드에 "alice" 저장
스레드 B: 필드에 "bob" 저장     ← A가 아직 안 끝났다
스레드 A: 필드를 읽는다 → "bob"  ← 남의 값
```

**비유가 깨지는 지점이 정확히 여기다.** 식당 창구는 손님이 몰리면 사람을 더 세우지만, **컨트롤러는 한 명이 동시에 모든 손님을 받는다.**

**올바른 방법**: 요청마다 다른 값은 **메서드 지역 변수나 파라미터**로 다룬다. 지역 변수는 스레드마다 자기 스택에 있으므로 섞이지 않는다.

**증상이 나쁘다는 점도 알아 둘 만하다.** 개발 중에는 요청이 하나씩 오므로 **절대 재현되지 않는다.** 부하가 걸리는 운영에서만, 그것도 간헐적으로 터진다.
