## Q1. `RestClient`로 직접 호출하는 코드가 무너지는 네 지점

1. **버전이 문자열 리터럴로 호출부마다 흩어진다.** 헤더 이름을 `Api-Version`으로 오타 내면 **컴파일러는 아무 말도 안 하고, 서버는 default 버전으로 응답한다.** 조용한 실패다.
2. **base URL이 호출부마다 반복된다.** 환경이 바뀌면 모든 호출 지점을 찾아야 한다.
3. **응답 타입이 없다.** `String`을 받아 직접 파싱하거나 매번 타입을 지정해야 한다.
4. **버전 전략을 바꾸면 호출 코드를 전부 고쳐야 한다.** 서버가 헤더에서 쿼리로 옮기면 모든 `.header(...)`가 `.queryParam(...)`이 된다.

**4번이 [[08-versioning-apis-with-spring-boot-4]]가 지적한 문제의 클라이언트 쪽 절반이다** — *"버전 관리가 암묵적이었고 컨트롤러 매핑과 **클라이언트 코드** 여기저기에 흩어져 있었다."* 서버 쪽은 Boot 4가 `version` 속성으로 풀었고, 클라이언트 쪽을 이 절이 푼다.

---

## Q2. 구현 클래스가 없는데 동작하는 이유

**런타임에 프록시가 만들어지기 때문이다.**

`@ImportHttpServices(VideoClient.class)`가 Spring에게 이 인터페이스를 감지해 **HTTP 클라이언트 프록시**를 생성하라고 지시한다. 그 프록시는 Spring 빈으로 등록되어 `VideoClient` 타입이 필요한 곳에 주입된다.

**프록시가 하는 일 네 단계**:

1. **메서드 호출을 가로챈다.** — 인터페이스에 본문이 없으므로 누군가는 실제 동작을 해야 하기 때문
2. `@HttpExchange`의 기본 경로와 `baseUrl`을 합쳐 **최종 URL을 만든다.** — 계약(경로)과 환경(호스트)을 분리해 두기 위해
3. `@GetExchange(version = "…")`의 버전을 **`ApiVersionInserter`에게 넘겨** 요청에 싣게 한다. — 버전 전송 방식을 호출부가 아니라 **설정 한 곳**에서 정하기 위해
4. HTTP 요청을 보내고 응답 본문을 **메서드 반환 타입으로 역직렬화**한다. — 호출부가 JSON 파싱을 하지 않게 하기 위해

**인터페이스는 "무엇을 호출할지"의 계약만 담고, "어떻게 호출할지"의 절차는 프록시가 채운다.** 이것이 **선언적 클라이언트**다.

## Q3. `@GetExchange(version = "2")`가 말하지 않는 것

**"그 버전을 요청의 어디에 실을지"를 말하지 않는다.**

책의 표현: *"이 버전은 **URL에 박히지도 않고 헤더에 수동으로 설정되지도 않는다.** 클라이언트 설정이 처리하며, 구성된 전략에 따라 자동으로 전송된다."*

전송 방식은 별도 설정이 정한다.

```java
.apiVersionInserter(ApiVersionInserter.useHeader("API-Version"))
```

**이것이 Q1의 4번을 푸는 방식이다.** 전략을 바꾸려면 이 한 줄만 바꾼다. 호출부는 그대로다.

**그리고 서버 쪽과 정확히 대칭이다** → Q4.

---

## Q4. 서버의 `@GetMapping(version=...)`과 클라이언트의 `@GetExchange(version=...)`이 대칭이라는 것

**양쪽 모두 "논리 버전"만 선언하고, "그것을 요청의 어디에서 읽을지 / 어디에 실을지"는 별도 설정이 정한다.**

| | 서버 | 클라이언트 |
|---|---|---|
| **무엇을** (논리 버전) | `@GetMapping(version = "2")` | `@GetExchange(version = "2")` |
| **어디서/어디에** (전송 방식) | `spring.mvc.apiversion.use.header=API-Version` | `ApiVersionInserter.useHeader("API-Version")` |
| 전략을 바꾸면 | **프로퍼티 한 줄** | **configurer 한 줄** |
| 핸들러/호출부 코드 | **안 바뀐다** | **안 바뀐다** |

**같은 설계 판단이 양쪽에 적용됐다** — 버전이라는 **개념**과 그 **전송 형식**을 분리한다. Boot 4가 API 버전 관리를 일급 개념으로 만들면서 얻은 것이 이 대칭이다.

**실무적 귀결**: 서버 팀이 전략을 바꾸면 클라이언트 팀도 한 줄만 바꾸면 된다. 양쪽 다 호출/핸들러 코드는 손대지 않는다.

---

## Q5. 서버 전략과 클라이언트 전략이 어긋나면

**컴파일도 되고 시작도 되고, 실제 호출에서야 드러난다.**

증상은 전략 조합에 따라 다르다.

| 서버 전략 | 클라이언트 전략 | 증상 |
|---|---|---|
| 헤더 | 쿼리 파라미터 | 서버가 버전을 못 읽는다 → **default 버전 응답**이거나 매핑 실패 |
| 경로 | 헤더 | 클라이언트가 `/api/videos`로 보낸다 → **404** (경로 방식은 세그먼트가 필요) |
| 헤더 이름 불일치 | — | 서버가 못 읽는다 → **조용히 default** |

**가장 나쁜 것이 "조용히 default 버전으로 응답"하는 경우다.** 200이 오고 JSON도 오는데 **내용이 기대와 다르다.** 역직렬화가 통과하면(v2 필드가 `@Nullable`이면 특히) 오류 없이 잘못된 데이터가 흘러간다.

**이것이 §1의 비유가 깨지는 지점이다** — 메뉴판에 없는 것을 주문하면 그 자리에서 "없습니다"가 온다. 하지만 **인터페이스와 원격 계약이 어긋나도 컴파일 시점에는 아무 오류가 없다.**

**대응**: 통합 테스트로 실제 서버를 한 번 호출해 보는 것 외에 방법이 없다. 이것이 Chapter 5 테스트 장이 필요한 이유이기도 하다.

## Q6. "선언적이고 타입 안전하다"의 범위

**내 코드 안에서만 성립한다.**

**보장되는 것**:
- 반환 타입이 `List<Video>`인지 `List<VideoV2>`인지 **컴파일러가 지킨다.** v1 응답을 v2 타입 변수에 넣으려 하면 컴파일 오류다.
- 메서드 이름을 오타 내면 컴파일 오류다.
- 호출부가 JSON 파싱 코드를 쓰지 않는다.

**보장되지 않는 것**:
- **`@HttpExchange("/api/vidoes")`처럼 경로에 오타를 내도 빌드는 통과한다.** 실행해서 호출해 봐야 404로 드러난다.
- **내 인터페이스와 상대 서버의 실제 계약이 맞는지는 아무도 검사해 주지 않는다.** 서버가 필드 이름을 바꿔도 내 `Video` record는 그대로 컴파일된다.
- 버전 전략이 서버와 맞는지도 검사되지 않는다 (Q5).

**한 문장으로**: **타입 안전은 "내가 선언한 것과 내가 쓰는 것"의 일치를 보장하지, "내가 선언한 것과 상대가 제공하는 것"의 일치는 보장하지 않는다.**

이 경계를 아는 것이 중요하다. 선언적 클라이언트를 쓰면 "이제 안전하다"고 느끼기 쉽지만, **네트워크 건너의 계약은 여전히 런타임 문제다.**

## Q7. 경로 기반 전략만 다른 취급을 받는 이유

**버전이 URL의 일부이므로 "요청에 덧붙이는" 방식으로 처리할 수 없기 때문이다.**

헤더·쿼리 파라미터·미디어 타입은 전부 **요청이 이미 만들어진 뒤 덧붙이는** 것이다. `ApiVersionInserter`가 완성된 요청에 헤더 하나를 추가하면 끝난다.

**경로는 다르다.** 버전이 URL 문자열 자체에 들어가야 하므로, **URL을 만드는 시점**에 개입해야 한다. `@HttpExchange("/api/videos")`의 경로에 세그먼트를 끼워 넣는 일이다 — 덧붙이기가 아니라 재조립이다.

**같은 이유가 서버 쪽에서도 나타났다** — [[08-versioning-apis-with-spring-boot-4]]에서 **경로 방식에만 default 버전을 적용할 수 없었다.** 버전이 리소스 식별자의 일부이기 때문이다.

**일반화**: 버전을 **식별자에 넣느냐 메타데이터로 두느냐**가 갈림점이고, 그 선택이 서버·클라이언트 양쪽에서 예외를 만든다.

## Q8. `ApiClientController`에서 `version`이 두 층에 걸쳐 나타나는 흐름

**같은 이름의 값이 성격이 다른 두 자리에 있다.**

```text
① 브라우저 → 우리 서버:  이 컨트롤러가 받는 요청의 버전
                            (우리가 [[08-versioning-apis-with-spring-boot-4]]에서 설정한 서버 전략으로 읽힌다)
                                   │
                                   ▼
② 우리 서버 → 원격 API:   VideoClient가 호출할 때 싣는 버전
                            (ApiVersionInserter가 정한 방식으로 실린다)
```

**우리 서버가 동시에 두 역할을 한다** — 브라우저에게는 **제공자**이고, 원격 API에게는 **소비자**다.

그래서 같은 "버전 2"라도:
- ①에서는 **읽어내는** 대상이고 서버 전략(`spring.mvc.apiversion.use.*`)이 지배한다.
- ②에서는 **실어 보내는** 대상이고 클라이언트 전략(`ApiVersionInserter`)이 지배한다.

**둘이 반드시 같을 필요는 없다.** 우리 API는 경로 전략을 쓰면서 원격 API는 헤더 전략으로 호출할 수 있다. 두 설정이 독립적이기 때문이다.

**혼동하기 쉬운 지점**: 지금 예제는 우리 서버가 **자기 자신을** 호출하므로(`baseUrl("http://localhost:8080")`) 두 층이 같은 애플리케이션 안에 있다. 학습용으로는 편하지만, 실제로는 ②의 상대가 다른 팀·다른 회사의 서버인 경우가 보통이고 **그때 두 전략이 다를 수 있다는 점이 분명해진다.**

## 재출제 문항

1. `@HttpExchange`의 경로에 오타를 냈다. 언제 어떻게 알게 되는가? "타입 안전"이라는 말과 모순인가?
2. 서버는 헤더, 클라이언트는 쿼리 파라미터로 설정됐다. 200이 오는데 데이터가 이상하다. 무슨 일인가?
3. 원격 API가 필드 이름을 바꿨다. 내 코드는 컴파일되는가? 언제 깨지는가?
4. 경로 전략만 `ApiVersionInserter`로 처리하기 어려운 이유를 서버 쪽 default 버전 문제와 묶어 설명하라.
5. base URL을 환경마다 다르게 하려면 어떻게 하겠는가?
6. 우리 서버가 v2를 제공하면서 원격 API의 v1을 호출할 수 있는가?
