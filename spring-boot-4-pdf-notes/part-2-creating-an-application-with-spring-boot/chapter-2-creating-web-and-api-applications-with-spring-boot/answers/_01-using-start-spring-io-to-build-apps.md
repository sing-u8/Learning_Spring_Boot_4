## Q1. 네 방법이 전부 무너지는 지점

**정답의 유효기간이 짧다는 것이다.**

Stack Overflow, 레퍼런스 짜깁기, 전문가 블로그, 이전 프로젝트 복사 — 넷 다 **"어느 시점엔가 유효했던 버전 조합"의 스냅샷**이다. 그 사이 모듈 이름이 바뀌거나 사라졌다면 복사한 XML은 "빌드는 되는데 실행하면 클래스를 못 찾는" 상태가 된다.

책의 표현이 정확하다 — *"더 이상 존재하지 않거나 필요한 일을 하지 않는 설정 옵션을 적용하려 시도했을 수 있다."* **설정을 잘못 쓴 것이 아니라 그 설정이 있던 시절의 세계가 사라진 것이다.**

이것이 진짜 문제였다는 점도 같이 봐야 한다. 어려운 질문은 "무엇이 필요한가"(Spring, MVC, Tomcat, Jackson, 로깅, 테스트 — 목록은 알고 있다)가 아니라 **"이 여섯을 어느 버전 조합으로 써야 안 깨지는가"**였다.

## Q2. 복사가 "가장 빠른 시작"인데도 결국 더 느려지는 이유

**시작은 0초지만, 걷어내는 데 드는 시간이 뒤에 온다.**

이전 프로젝트에는 **그 프로젝트에만 필요했던** 의존성·설정·디렉터리가 들어 있다. 하나씩 지워야 하는데 문제는 **무엇을 지워도 되는지 모른다**는 것이다. 지워도 되는지 확인하려면 빌드하고 실행해 봐야 하고, 어떤 것은 특정 경로를 타야만 드러난다.

책의 저자는 이 정리에 **새 프로젝트를 처음부터 만드는 것보다 더 오래 걸린 적도 있다**고 말한다.

거기에 Q1의 문제가 겹친다. 이전 프로젝트가 6개월 전 것이라면 그 버전 조합 자체가 이미 낡았다. **불필요한 것을 걷어내는 일과 낡은 것을 갱신하는 일을 동시에** 해야 한다.

## Q3. 산출물 중 핵심 하나

**빌드 파일(`pom.xml` / `build.gradle`)이다.**

Initializr는 메인 클래스, 빈 `application.properties`, Maven/Gradle wrapper, 테스트 스켈레톤도 만들어 준다. 하지만 나머지는 **내가 5분이면 손으로 만들 수 있는 것들**이다. 메인 클래스는 세 줄이고 빈 설정 파일은 빈 파일이다.

빌드 파일만이 **내가 알 수 없는 정보**를 담는다 — 지금 이 순간 유효한 버전 조합. §1이 지적한 문제가 정확히 그것이었고, 그 문제를 푸는 것이 이 산출물 하나다.

**판별 방법**: 나머지를 다 지우고 `pom.xml`만 남겨도 프로젝트는 복구할 수 있다. 반대로 `pom.xml`만 없으면 아무것도 못 한다.

## Q4. JAR과 WAR이 가르는 것 — "누가 서버를 띄우는가"

| | JAR | WAR |
|---|---|---|
| **서버를 띄우는 주체** | **애플리케이션 자신** (내장 Tomcat) | **미리 설치된 외부 서블릿 컨테이너** |
| 실행 방법 | `java -jar ch2.jar` | 컨테이너 배포 디렉터리에 얹고 재시작 |
| Boot 팀의 지원 | first-class | 여전히 유효하나 부차적 |
| 언제 | 기본값 | 조직이 이미 운영 중인 컨테이너에 배포할 때 |

**JAR이 기본이 된 이유는 배포 환경을 보면 분명하다.** 컨테이너 이미지나 클라우드 플랫폼에 올릴 때, "이미지 안에 Tomcat을 미리 깔고 그 안에 WAR을 넣는" 2단계는 그대로 낭비다. 서블릿 컨테이너가 애플리케이션 안으로 들어오면 **배포 단위가 하나**가 된다.

> "Make JAR not WAR" — Josh Long

**흔한 오해**: WAR을 고르면 내장 서버가 사라지는 것이 **아니다.** 개발 중에는 내장 서버로 돌고 배포 시에만 외부 컨테이너에 얹히는 **이중 구성**이 된다. 즉 WAR 선택의 진짜 의미는 "내장 서버를 포기한다"가 아니라 **"외부 컨테이너에 배포할 수 있는 형태도 만든다"**다.

## Q5. Java 25를 골랐는데 운영이 Java 17이라면

**문제인 것과 문제가 아닌 것을 갈라야 한다.**

| | |
|---|---|
| **문제다** | 컴파일 타깃이 25면 그 바이트코드는 Java 17 JVM에서 **실행되지 않는다.** 25에서만 쓸 수 있는 언어 기능을 썼다면 되돌리는 데 코드 수정이 필요하다 |
| **문제가 아니다** | **Spring Boot 4 자체는 Java 17이면 충분하다.** Boot 4/Framework 7의 최소 요구가 17이다. Boot 버전을 낮출 필요가 없고, 고른 스타터 목록도 그대로다 |

**즉 이건 Boot 문제가 아니라 컴파일 타깃 문제다.** Java 버전 선택은 **컴파일 타깃**일 뿐이고, Boot 버전은 **다른 라이브러리 버전을 정렬하는 기준점**이다. 성격이 다르다. Java 25를 골랐다고 Boot 버전이 달라지지 않는다.

책도 경계를 분명히 한다 — 25는 "현재 LTS의 언어·JVM 개선을 쓰기 위한 책의 선택"이지 **요구사항이 아니다.**

**대응**: 빌드 파일의 Java 버전 속성만 17로 내리면 된다. 25 전용 문법을 안 썼다면 그것으로 끝이다.

## Q6. Spring Web 하나로 웹 컨트롤러를 쓸 수 있는 이유

**Spring Web은 라이브러리 하나가 아니라 스타터 하나로 번역되기 때문이다.**

체크박스 하나가 `spring-boot-starter-webmvc` 아티팩트가 되고, 그 스타터가 전이 의존성으로 나머지를 전부 끌고 온다. ✅ Boot 4 저장소의 실제 구성:

```groovy
spring-boot-starter          // 코어·로깅·자동 구성 기반
spring-boot-starter-jackson  // JSON
spring-boot-starter-tomcat   // 내장 서블릿 컨테이너
spring-boot-http-converter   // HTTP 본문 ↔ 객체 변환
spring-boot-webmvc           // MVC와 그 자동 구성
```

§1에서 "필요한 것은 여섯 개"라고 했던 그 여섯이 여기 다 있다. **Initializr가 푼 문제는 "무엇을 고를까"가 아니라 "그 여섯의 버전을 어떻게 맞출까"였고, 스타터가 그 답을 한 이름으로 포장한다.**

그리고 클래스패스가 바뀌면 자동 구성이 그것을 조건으로 읽어 디스패처와 핸들러 매핑을 등록한다. 체크박스 하나 → 스타터 하나 → 전이 의존성 다섯 → 클래스패스 변화 → 자동 구성 → 동작하는 웹 인프라.

## Q7. 스스로 갱신되는 성질이 흡수하는 문제

**§1의 "정답의 유효기간이 짧다"를 서비스 쪽이 대신 진다.**

블로그 글은 쓰인 날짜에 고정된다. 읽는 사람이 그 글이 낡았는지 판단해야 한다. **start.spring.io는 새 Boot 릴리스가 나오면 스스로 갱신되므로, 오늘 접속하면 오늘 유효한 조합이 나온다.**

책 스크린샷과 화면의 버전 목록이 다른 것은 **버그가 아니라 이 성질의 증거**다. 유효기간 관리의 책임이 개발자에서 서비스로 옮겨 갔다.

**대가도 있다**: 지원이 끝난 Boot 버전은 목록에서 **사라진다.** 오래된 버전을 유지해야 하는 프로젝트는 Initializr로 되살릴 수 없다. 항상 최신을 준다는 것과 과거를 재현해 준다는 것은 다르다.

## Q8. Initializr가 하지 않는 일

**판별 질문 하나**: *이 도구가 내 도메인을 아는가?* 모른다. 거기서 갈리는 것들이다.

1. **아키텍처를 정해 주지 않는다.** 패키지 구조, 계층 분리, 도메인 모델이 전부 빈 상태다. 그 빈자리를 직접 채우는 것이 [[04b-building-our-app-with-a-better-design]]이다.
2. **코드를 생성하지 않는다.** Rails `scaffold`나 JHipster처럼 엔티티에서 CRUD를 뽑아 주지 않는다. 만들어 주는 것은 빌드 파일, 메인 클래스 하나, 빈 설정 파일, wrapper까지다.
3. **지원 종료된 버전을 되살려 주지 않는다.**
4. **사내 저장소·표준 스타터를 반영하지 않는다.** 오픈소스라 사내 인스턴스를 띄울 수는 있지만 그건 별도 운영 대상이다.
5. **생성된 `pom.xml`은 최종본이 아니다.** Node 빌드 연동처럼 손으로 더하는 플러그인이 이 장 뒤에 나온다 — [[06-integrating-nodejs-with-a-spring-boot-web-app]].

이름 자체가 범위를 말한다. `Initializr`는 **"initialize"까지만** 한다. 표기가 `Initializer`가 아닌 것은 2000년대 후반 웹 서비스 표기 유행(Flickr, Tumblr)이지만, 범위는 정확히 그 단어대로다.
