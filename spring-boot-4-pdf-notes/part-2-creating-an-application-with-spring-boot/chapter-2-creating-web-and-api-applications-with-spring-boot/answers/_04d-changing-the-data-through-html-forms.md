## Q1. `videos.add(newVideo)`가 컴파일은 되는데 실행하면 터지는 이유

**타입과 런타임 구현이 다른 층이기 때문이다.**

| 층 | 무엇을 아는가 |
|---|---|
| **타입**(`List<Video>`) | `List` 인터페이스에 **`add()`가 선언돼 있다.** 컴파일러는 여기까지만 본다 → **통과** |
| **런타임 구현**(`List.of()`가 만든 불변 리스트) | `add()`를 구현하되 **`UnsupportedOperationException`을 던진다** → **실패** |

책의 표현이 정확하다 — *"이 불변 리스트는 Java의 `List` 인터페이스를 존중하므로 `add()` 메서드에 접근할 수 있게 해 준다. 그러나 실제로 쓰려고 하면 `UnsupportedOperationException`만 만들어 낼 뿐이다."*

**즉 불변성은 타입이 아니라 런타임 구현이 강제한다.** 컴파일러가 막아 주지 않는다. Java 컬렉션 API의 오래된 설계 특성이고, 이 절이 실제로 그 함정을 밟아 보여 준다.

**설계상 다른 선택도 가능했다** — 불변 리스트를 별도 타입으로 만들어 `add()` 자체를 없앨 수도 있었다. 그러면 컴파일 시점에 잡히지만, 대신 모든 `List` 자리에 불변 리스트를 넘길 수 없게 된다. 호환성을 택한 대가다.

## Q2. 폼의 `name="name"`에서 왼쪽과 오른쪽

**우연한 반복처럼 보이지만 서로 다른 것과 맞물린다.**

```html
<input type="text" name="name">
         ↑ HTML 문법      ↑ Video record의 컴포넌트 이름
```

- **왼쪽 `name=`** — HTML의 폼 필드 속성 이름이다. 브라우저가 이걸 키로 써서 `name=Learning+Spring+Boot+4` 형태로 보낸다.
- **오른쪽 `"name"`** — `record Video(String name)`의 **컴포넌트 이름**과 맞춘 값이다.

**이 값이 자동 변환을 가능하게 하는 유일한 연결고리다.** `@ModelAttribute`가 폼 키와 record 컴포넌트 이름을 **이름으로 매칭**하기 때문이다. 다르면 그 필드는 채워지지 않는다 — 그리고 **오류 없이 `null`이 된다.**

[[04a-adding-demo-data-to-a-template]]의 모델 속성 이름과 같은 성질이다. **컴파일러가 검사하지 않는 문자열 계약**이고, 틀리면 조용히 실패한다.

## Q3. POST 응답으로 HTML을 바로 돌려주면

**사용자가 새로고침하면 브라우저가 방금 한 POST를 그대로 다시 보낸다.**

같은 비디오가 하나 더 들어간다. **F5를 다섯 번 누르면 다섯 개가 더 생긴다.**

**왜인가**: 브라우저의 "현재 페이지"가 POST 요청의 응답이기 때문이다. 새로고침은 "이 페이지를 만든 요청을 다시 실행"이고, 그 요청이 POST면 POST를 다시 보낸다. (브라우저가 "재전송하시겠습니까?" 경고를 띄우기도 하지만, 사용자는 대개 확인을 누른다.)

**결제나 주문이라면 이건 중복 결제다.** 그래서 이 문제에 **PRG**(POST-Redirect-Get)라는 고유한 이름이 붙어 있다.

## Q4. 302와 301 중 302가 맞는 이유

| | **302 Found** | 301 Moved Permanently |
|---|---|---|
| 의미 | **임시 이동** | 영구 이동 |
| 원래 URL | **앞으로도 계속 쓸 수 있다** | 더 이상 유효하지 않다 |
| 브라우저 | 다음에도 **원래 URL로 먼저 온다** | 새 URL을 **기억하고 바로 간다** |

**`/new-video`는 다음 제출에도 그대로 쓴다.** 폼을 다시 제출하면 또 `POST /new-video`로 가야 한다.

301을 보내면 브라우저가 **"`/new-video`는 이제 `/`다"라고 캐시한다.** 다음에 폼을 제출하면 브라우저가 `/new-video`에 가지도 않고 곧바로 `/`로 갈 수 있다 — **POST가 아예 서버에 도달하지 않는다.** 그리고 이 캐시는 브라우저에 남아서, 서버 코드를 고쳐도 그 사용자에게는 계속 잘못 동작한다.

**한 문장으로**: 301은 "이 주소는 죽었다", 302는 "이번에는 저기로 가라". 여기서 죽은 주소는 없다.

## Q5. `create()`의 세 줄

```java
public Video create(Video newVideo) {
    List<Video> extend = new ArrayList<>(videos);   // ①
    extend.add(newVideo);                            // ②
    this.videos = List.copyOf(extend);               // ③
    return newVideo;
}
```

| 줄 | 하는 일 | 왜 필요한가 |
|---|---|---|
| ① | `List` 기반 생성자로 **가변** `ArrayList`를 만들고 기존 항목을 전부 복사 | **원본을 건드리지 않고** 작업할 공간이 필요하다 |
| ② | 이 `ArrayList`의 **쓸 수 있는** `add()`로 새 항목을 끝에 더한다 | **실제 변경이 일어나는 유일한 지점**이다 |
| ③ | `List.copyOf()`로 **다시 불변 리스트**로 만들어 필드에 대입 | 밖으로 새어 나간 참조가 변하지 않게 하기 위해 |

**③이 왜 필요한지가 핵심이다.** ②까지만 하고 `this.videos = extend`로 두면 가변 `ArrayList`가 필드에 들어간다. 그러면 [[04b-building-our-app-with-a-better-design]]에서 지적한 문제가 살아난다 — `getVideos()`가 그 참조를 그대로 돌려주므로 **호출자가 서비스 내부 상태를 직접 바꿀 수 있다.**

책이 정리하는 값: *"기존 데이터 사본이 메서드 호출로 인해 우연히 변경되는 일이 없도록 보장한다. 부작용이 방지되어 일관된 상태가 유지된다."*

**즉 불변이면 밖으로 나간 참조는 영원히 그 시점의 스냅숏이다.**

## Q6. "일관성은 있지만 thread-safe하지 않다"

**`List.copyOf`가 만든 목록 자체는 불변이라 안전하다. 안전하지 않은 것은 `create()`의 세 줄이 원자적이지 않다는 점이다.**

```text
스레드 A                          스레드 B
────────────────────────────      ────────────────────────────
videos 읽기 → [v1,v2,v3]
                                  videos 읽기 → [v1,v2,v3]
복사본에 A항목 추가
                                  복사본에 B항목 추가
this.videos = [v1,v2,v3,A]
                                  this.videos = [v1,v2,v3,B]   ← A가 사라졌다
```

**각 단계는 개별적으로 안전한데 전체가 하나의 원자적 연산이 아니라서** 마지막 쓰기가 앞의 쓰기를 덮는다. 이것이 **경쟁 상태**이고, 결과는 조용한 데이터 손실이다 — 예외도 로그도 없다.

**두 성질의 구분**:

| | 불변 컬렉션이 보장하는 것 | 보장하지 않는 것 |
|---|---|---|
| | 그 목록을 **여럿이 동시에 읽어도** 안전 | 그 목록을 가리키는 **필드를 여럿이 동시에 갈아 끼우는** 것 |

**대응**은 이 절의 범위 밖이다. 동기화, 원자적 참조(`AtomicReference`), 또는 애초에 트랜잭션을 지원하는 저장소가 필요하다. Chapter 3에서 실제 저장소로 넘어가는 이유이기도 하다.

## Q7. `redirect:`와 `forward:`를 바꿔 쓰면

**Q3의 새로고침 재전송 문제가 그대로 되살아난다.**

| | `redirect:` | `forward:` |
|---|---|---|
| 무엇을 보내나 | 브라우저에 **302**를 보낸다 | 아무것도 안 보낸다 |
| 요청 횟수 | **두 번** 오간다 | **한 번** |
| 브라우저가 아는 것 | "새 요청을 `/`로 보냈다" | "내가 보낸 요청은 `POST /new-video` 하나뿐" |
| 주소창 | `/`로 **바뀐다** | `/new-video` 그대로 |

`forward:`는 **서버 안에서 처리를 넘길 뿐**이라 브라우저는 자기가 보낸 요청이 POST 하나였다고 안다. 그래서 새로고침하면 **그 POST를 다시 보낸다.**

**PRG의 핵심이 정확히 이 지점이다.** 화면에 보이는 HTML이 POST의 응답이 아니라 **그 뒤에 이어진 GET의 응답**이어야 하고, 그러려면 브라우저가 **실제로 새 요청을 만들어야** 한다. 서버 내부 포워딩으로는 안 된다.

## Q8. 화면에 보이는 갱신된 HTML은 어느 요청의 응답인가

**리다이렉트 뒤에 이어진 `GET /`의 응답이다.** POST의 응답이 아니다.

전체 흐름 다섯 단계:

1. 브라우저가 `POST /new-video`를 보낸다.
2. `newVideo()`가 폼을 `Video`로 바인딩하고 `create()`를 호출한다.
3. 컨트롤러가 `/`로의 **리다이렉트(302)를 발행한다.** ← **POST의 응답은 여기서 끝. HTML이 아니다.**
4. 브라우저가 루트 경로로 되돌아가며 **새 GET 요청**을 보낸다.
5. 그 GET이 `index()`를 타고 갱신된 목록을 렌더링한다. ← **화면에 보이는 HTML**

**4번이 PRG의 핵심이다.** 이 상태에서 새로고침을 누르면 브라우저는 "현재 페이지를 만든 요청" — 즉 **GET** — 을 반복한다. POST는 반복되지 않는다.

**부수 효과 하나**: 주소창이 `/`가 되므로 사용자가 그 URL을 북마크하거나 공유해도 정상 동작한다. `/new-video`가 주소창에 남아 있었다면 그 링크는 POST 전용이라 GET으로 열면 405가 난다.

**PRG의 대가**: 리다이렉트 후 GET에서는 **"무엇이 저장됐는지"를 알 수 없다.** POST가 만든 결과 정보가 응답에 실려 오지 않기 때문이다. 성공 메시지 같은 것을 전달하려면 flash attribute 같은 별도 수단이 필요하다.
