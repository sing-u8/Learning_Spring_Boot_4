## Q1. `new HomeController(...)`를 아무도 안 부르는데 화면이 나오는 이유

**컨테이너가 대신 부르기 때문이다.** 다섯 단계다.

1. **컴포넌트 스캔**이 `@Controller`가 붙은 `HomeController`와 `@Service`가 붙은 `VideoService`를 후보로 모은다. — 관리할 대상 목록이 먼저 있어야 하므로
2. 각 후보에서 **주입 지점**을 찾는다. `HomeController`의 생성자 매개변수 `VideoService videoService`가 그것이다. — 무엇을 채울지 알아야 하므로
3. 그 타입의 빈이 있는지 본다. **없으면 먼저 만든다.** — 의존 대상이 준비된 뒤라야 안전하므로 → **Q3**
4. 찾은 인스턴스를 인자로 넣어 **생성자를 호출한다.** — 객체가 만들어지는 순간 필요한 것이 이미 채워져 있게 하려고
5. 완성된 컨트롤러를 컨텍스트에 등록하고 **Spring MVC 요청 라우팅에도 연결**한다. — 요청이 이 인스턴스에 도달해야 하므로

**3번의 부수 효과가 중요하다**: `VideoService` 빈은 **하나만** 만들어지고 `HomeController`와 `ApiController`가 **같은 인스턴스**를 받는다. [[04b-building-our-app-with-a-better-design]]에서 걱정한 "목록이 두 벌" 문제가 **구조적으로** 사라진다. 사람이 기억해서가 아니라 컨테이너의 기본 동작이라서.

## Q2. 조립 코드를 손으로 쓸 때 무너지는 세 지점

```java
VideoService videoService = new VideoService();
HomeController homeController = new HomeController(videoService);
ApiController apiController = new ApiController(videoService);
// 그리고 이 컨트롤러들을 요청 라우팅에 등록해야 한다
```

1. **조립 코드가 어딘가에 존재해야 한다.** 클래스가 늘수록 이 파일이 **애플리케이션에서 가장 자주 바뀌는 파일**이 된다. 클래스 하나를 추가할 때마다 여기가 함께 바뀐다.
2. **"같은 인스턴스를 공유해야 한다"를 사람이 기억해야 한다.** `ApiController`에 실수로 `new VideoService()`를 하나 더 넘기면 방금 없앤 "목록이 두 벌" 문제가 **그대로 돌아온다.** 그리고 이 실수는 컴파일러가 못 잡는다.
3. **자동 구성이 만든 빈은 아예 손에 잡히지 않는다.** Mustache 엔진 빈, Jackson 변환기처럼 Boot가 만든 객체를 우리 코드에 넘기려면 **그것들을 꺼낼 방법부터** 필요하다.

**3번이 결정적이다** → Q4에서 이어진다.

## Q3. `VideoService`가 `HomeController`보다 먼저 만들어져야 하는 이유

**생성자 주입이기 때문이다.** `HomeController`를 만드는 행위 자체가 `VideoService` 인스턴스를 **인자로 요구**한다. 없으면 생성자를 호출할 수 없다.

즉 순서는 컨테이너가 임의로 정한 것이 아니라 **의존 관계 선언에서 유도된다.** 개발자가 "이걸 먼저 만들어라"라고 쓴 적이 없는데도 순서가 결정된다.

**이것이 생성자 주입의 성질 중 하나다.** 필드 주입이라면 객체를 먼저 만들고 나중에 채우므로 이 강제가 약해진다. 생성자 주입은 **"완성되지 않은 객체가 존재하는 시간"을 없앤다** — 만들어지는 순간 이미 쓸 수 있는 상태다.

Chapter 1의 `@Bean` 메서드 매개변수와 같은 원리다. 매개변수가 곧 순서 선언이다.

## Q4. autowiring을 싫어하던 진영의 논리와, 무엇이 바꿨나

**반대 논리**: **"어느 구현이 어디에 들어가는지가 코드에 안 보인다."** 타입만 보고 컨테이너가 고르므로, 배선 결과를 확인하려면 **애플리케이션을 띄워 봐야** 한다.

그들이 대신 한 것: `@Configuration` 클래스를 만들고 `@Bean` 메서드를 써서, 반환된 인스턴스를 생성자나 setter로 **수동 배선**했다. 배선이 코드에 명시적으로 보인다.

**무엇이 바꿨나 — Spring Boot 자신이다.**

> "Spring Boot가 부상하고 자동 구성이 만들어 내는 빈들이 autowiring을 대규모로 활용하면서, autowiring은 거의 모두에게 받아들여지게 됐다."

이유는 Q2의 3번이다. **자동 구성이 만든 수십 개의 빈을 전부 손으로 배선하는 것은 애초에 가능한 선택지가 아니었다.** 수동 배선은 "빈이 열 개"일 때 성립하는 전략이었고, 자동 구성이 그 전제를 무너뜨렸다.

**논리 자체가 틀렸던 것은 아니다.** 명시성이 사라진다는 지적은 여전히 유효하고, 그래서 진단 도구(`--debug` 조건 평가 리포트, Actuator의 beans/conditions 엔드포인트)가 그 자리를 메운다.

## Q5. Option 1이 나머지 둘과 성격이 다른 이유

책의 세 옵션에는 **두 개의 다른 질문**이 섞여 있다.

| 질문 | 답하는 항목 | 성격 |
|---|---|---|
| 이 클래스가 애초에 **빈이 되는가?** | **Option 1** (`@Service` 등) | **전제** |
| 그 빈의 **어느 자리를 채울 것인가?** | Option 2 (`@Autowired`), Option 3 (단일 생성자) | **선택** |

**Option 1은 다른 둘과 나란한 선택지가 아니라 필수 전제다.** `@Autowired`만 붙이고 `@Service`를 안 붙이면, 그 클래스는 애초에 컨테이너가 만들지 않으므로 **아무 일도 일어나지 않는다.** 주입할 대상 객체 자체가 없다.

셋 중 하나를 고르는 것으로 읽으면 "Option 2만 쓰면 되지 않나"라는 잘못된 결론에 도달한다.

## Q6. `@Autowired`가 없는데 autowiring이 동작하는 이유

**Option 3 — 생성자가 하나뿐이면 Spring이 그것을 주입 지점으로 간주한다.** 애노테이션이 생략 가능할 뿐이다.

**중요한 구분**: `HomeController`에 `@Autowired`가 없다고 해서 **autowiring을 안 쓰는 것이 아니다.** autowiring은 작동하고 있다. **애노테이션의 유무와 동작의 유무는 다르다.**

**왜 이 규칙이 생겼나**: 생성자가 하나면 모호함이 없다. 컨테이너가 어느 생성자를 쓸지 고민할 필요가 없으므로 표시가 불필요하다. 생성자가 둘 이상이면 그때는 `@Autowired`로 어느 것인지 알려 줘야 한다.

부수 효과로 **클래스가 Spring 애노테이션에 덜 오염된다.** 생성자는 평범한 Java 생성자이고, 테스트에서 `new HomeController(가짜서비스)`로 그냥 부를 수 있다.

## Q7. 생성자 주입이 필드 주입보다 나은 세 가지

Spring 팀이 권장하는 것은 생성자 주입이고, 이유가 코드에 이미 드러나 있다.

| | 생성자 주입 | 필드 주입 |
|---|---|---|
| **`final`** | `private final VideoService`를 쓸 수 있다 → **주입 후 교체 불가**, 불변 보장 | `final`을 쓸 수 없다. 나중에 누군가 바꿀 수 있다 |
| **테스트** | 컨테이너 없이 `new HomeController(fake)` 가능 | 리플렉션이나 컨테이너가 있어야 채울 수 있다 |
| **순환 의존** | **시작 시점에 실패한다** → 설계 문제가 즉시 드러난다 | 객체를 먼저 만들고 나중에 채우므로 **숨는다** |

**세 번째가 가장 중요하다.** 순환 의존(`A`가 `B`를, `B`가 `A`를 요구)은 생성자 주입으로는 풀 수 없다 — 컨테이너도 무엇을 먼저 만들지 정할 수 없기 때문이다. 이때 **주입 방식을 바꿔 우회할 것이 아니라 설계를 다시 봐야 한다.** 필드 주입은 그 신호를 지워 버린다.

**추가로**: 필수 의존성이 **생성자 시그니처에 명시된다.** 이 클래스가 무엇을 필요로 하는지 한 줄로 읽힌다. 그리고 매개변수가 대여섯 개를 넘으면 그것은 주입 방식의 문제가 아니라 **그 클래스가 너무 많은 일을 한다는 신호**다 — 필드 주입으로 생성자를 짧게 보이게 만드는 것은 증상만 가린다.

## Q8. 같은 타입 빈이 둘일 때 실패하는 것이 왜 좋은 설계인가

**컨테이너가 임의로 고르는 것보다 사람이 명시하는 편이 안전하기 때문이다.**

**비유가 깨지는 지점이 정확히 여기다.** 콘센트는 규격만 맞으면 무엇이든 꽂힌다. Spring은 그렇지 않다 — **"규격이 맞으니 알아서 하나 골라 주겠지"가 통하지 않는다.**

만약 컨테이너가 임의로 골랐다면:

- **어느 것이 골라졌는지 코드로 알 수 없다.** 스캔 순서나 클래스 이름 순서 같은 우연에 달린다.
- **환경마다 다르게 동작할 수 있다.** 개발에서는 A가, 운영에서는 B가 선택될 수 있다.
- **실패가 늦게 나타난다.** 시작은 되고, 그 빈을 실제로 쓰는 코드 경로에서 이상한 결과가 나온다.

**시작 시점 실패는 이 셋을 전부 없앤다.** 문제를 배포 전에, 원인 지점에서, 명확한 메시지로 드러낸다.

**해결 방법도 명시적이다** — `@Primary`로 기본을 정하거나, `@Qualifier`로 지정하거나, 매개변수 이름을 빈 이름과 맞춘다. 셋 다 **코드에 의도가 남는다.**

같은 철학을 [[01-autoconfiguring-spring-beans]]에서도 봤다. `@ConditionalOnMissingBean` 백오프가 **빈을 두 개 만들고 순위로 고르는 대신 아예 안 만드는** 것도, "모호함을 만들지 않는다"는 같은 판단이다.
