## Q1. 순수 DOM 조작이 무너지는 세 지점

```js
ul.innerHTML = "";                       // 지우고
for (const v of videos) { ... }          // 새로 만들어 붙인다
```

1. **"지금 화면이 어떤 상태인지"를 DOM에서 읽어야 한다.** 데이터의 진짜 출처가 JS 변수인지 화면의 `<li>`들인지 **모호해진다.**
2. **모든 변화마다 "무엇을 지우고 무엇을 더할지"를 손으로 쓴다.** 조건에 따라 나타났다 사라지는 요소가 몇 개만 겹쳐도 이 코드가 폭발한다.
3. **갱신 누락이 조용히 생긴다.** 데이터는 바꿨는데 화면 갱신 코드를 빠뜨리면 **둘이 어긋난 채로 남는다.**

**셋의 공통 뿌리**: 상태가 두 곳(변수 + DOM)에 있고, 그 둘을 **사람이 손으로 동기화**한다.

**React의 해법**: 상태를 한 곳(`state`)에만 두고, 화면은 **그 상태의 함수**로 선언한다. 동기화를 사람이 안 한다.

## Q2. 스프레드시트 비유가 깨지는 지점

**스프레드시트는 셀 값이 어떻게 바뀌든 의존 관계를 엔진이 추적한다. React는 그렇지 않다.**

`setState()`를 **호출해야만** 다시 그린다. `this.state.data.push(newItem)`처럼 상태 객체를 직접 건드리면 **값은 바뀌지만 화면은 그대로다.**

**왜인가**: React는 "무엇이 바뀌었는지"를 **감시하지 않는다.** "바뀌었다고 알려 준 시점"에만 일한다. 감시는 비용이 크고, 알림은 싸다.

**초보자가 가장 자주 밟는 함정이 이것이다** → Q5에서 자세히.

## Q3. `constructor`에서 `state`를 빈 배열로 초기화하지 않으면

**`render()`가 `undefined.map`으로 터진다.**

순서를 보면 왜 필수인지 명확하다.

1. 생성자가 상태를 `{data: []}`로 초기화
2. **React가 `render()`를 부른다** ← 이 시점에 데이터는 아직 없다
3. 빈 `<ul>`이 DOM에 삽입된다 (**마운트**)
4. `componentDidMount()`가 호출된다
5. `fetch`로 데이터를 받는다
6. `setState()`
7. `render()` 재호출 → 항목 세 개

**2번이 5번보다 먼저다.** 첫 렌더는 **데이터가 도착하기 전에** 일어난다. 그래서 `render()`가 참조할 값이 반드시 있어야 한다.

**빈 배열이 좋은 초기값인 이유**: `[].map(...)`은 빈 배열을 돌려주므로 **오류 없이 빈 목록**이 그려진다. 데이터를 기다리는 동안에도 화면에 무언가는 있다.

## Q4. 네트워크 요청을 생성자가 아니라 `componentDidMount`에 두는 이유

**화면에 붙기 전에 요청을 걸면 응답이 와도 갱신할 대상이 없기 때문이다.**

| | 생성자 | `componentDidMount` |
|---|---|---|
| 시점 | **DOM에 붙기 전** | **붙은 직후** |
| 용도 | 상태 초기화 | **부수 효과**(네트워크, 구독, 타이머) |

응답이 아주 빨리 오면 컴포넌트가 아직 마운트되지 않은 상태에서 `setState()`가 호출될 수 있다. React가 갱신할 대상이 화면에 없다.

**더 근본적으로**: 생성자는 **순수해야 한다.** 객체를 만드는 일과 바깥 세계에 요청을 보내는 일은 다른 성격이다. React는 컴포넌트를 여러 번 만들었다 버릴 수 있고, 그때마다 네트워크 요청이 나가면 곤란하다.

**둘 다 "처음에 한 번"이지만 시점이 다르다** — 이 구분이 생명주기 메서드가 존재하는 이유다.

## Q5. `setState()` 대신 `this.state.data.push(x)`를 하면

**배열은 바뀌지만 화면은 안 바뀐다.**

**왜인가**: **`setState()`가 재렌더의 유일한 트리거이기 때문이다.** React가 값을 감시하는 것이 아니라 **알림을 기다린다.** 배열을 직접 밀어 넣으면 알림이 없으므로 React는 아무 일도 일어나지 않았다고 안다.

**증상이 나쁘다**: 오류도 경고도 없다. 데이터는 실제로 들어가 있어서 콘솔로 확인하면 멀쩡하다. **다음에 다른 이유로 재렌더가 일어나면 그때 갑자기 나타난다** — 그래서 "가끔 되고 가끔 안 된다"로 보인다.

**Q2의 비유가 깨지는 지점이 바로 이것이다.** 스프레드시트라면 값을 바꾼 것만으로 다시 계산된다.

**올바른 형태**: 새 배열을 만들어 통째로 교체한다.
```js
this.setState({ data: [...this.state.data, newItem] })
```
원본을 바꾸지 않는다는 점에서 [[04d-changing-the-data-through-html-forms]]의 **복사-후-교체**와 같은 발상이다.

## Q6. `bind(this)`가 필요한 이유

**JavaScript에서 `this`는 함수가 어떻게 **호출되는지**로 결정되지, 어디에 **정의됐는지**로 결정되지 않기 때문이다.**

클래스 메서드를 이벤트 핸들러로 넘기면 (`onSubmit={this.handleSubmit}`) 그 함수는 **컴포넌트 인스턴스와 분리되어** 전달된다. 나중에 이벤트 시스템이 그것을 부를 때 `this`는 컴포넌트가 아니다 — `undefined`이거나 다른 것이다. 그래서 `this.setState`가 터진다.

`bind(this)`는 **`this`를 지금의 인스턴스로 고정한 새 함수**를 만든다. 어떻게 호출되든 `this`가 바뀌지 않는다.

**이것은 React의 문제가 아니라 JavaScript의 성질이다.** Java에서 메서드 참조가 항상 자기 객체를 데리고 다니는 것과 대비된다.

**현대적 대안**: 화살표 함수(`onSubmit={() => this.handleSubmit()}`)나 클래스 필드 문법은 `this`를 어휘적으로 잡으므로 `bind`가 필요 없다. 문제 자체를 우회하는 방식이다.

## Q7. `event.preventDefault()`를 빼면

**브라우저의 기본 폼 제출 동작이 되살아난다** — 즉 **페이지 전체가 다시 로드된다.**

[[04d-changing-the-data-through-html-forms]]에서 봤던 그 왕복이다. 폼 submit → 브라우저가 요청을 보내고 → 응답 문서로 페이지를 갈아 치운다.

**그러면 이 절의 목적이 통째로 무효가 된다.** §1에서 SPA를 도입한 이유가 "항목 하나 추가하는데 화면 전체가 다시 그려진다"였는데, 그 동작이 그대로 돌아온다.

**부수 효과**: JavaScript로 `fetch`를 보내는 코드와 브라우저의 기본 제출이 **동시에** 일어난다. 요청이 두 번 나가고, 그중 하나가 완료되기 전에 페이지가 갈아 치워진다. 증상이 일관되지 않아 원인을 찾기 어렵다.

**한 문장으로**: `preventDefault()`는 "이 이벤트는 내가 처리한다, 브라우저는 손 떼라"는 선언이다.

## Q8. `react.mustache`가 `index.mustache`와 근본적으로 다른 점

| | `index.mustache` | `react.mustache` |
|---|---|---|
| 데이터를 넣는 주체 | **서버**(Mustache 엔진) | **브라우저**(React) |
| 서버가 보내는 것 | **완성된 HTML** | **빈 껍데기 + 번들 로드 태그** |
| 데이터가 오는 경로 | HTML에 이미 박혀 있다 | **별도 API 호출**(`/api/videos`) |
| 왕복 횟수 | 1 (HTML) | 3 (HTML → 번들 → API) |

`react.mustache`에는 **Mustache 자리표시자가 사실상 없다.** 서버가 채울 것이 없기 때문이다. 하는 일은 `<div id="app">`이라는 **마운트 지점**을 두고 `<script type="module">`로 번들을 부르는 것뿐이다.

**즉 `react.mustache`는 템플릿이라기보다 부트스트랩 문서다.** Mustache 엔진을 거치지만 채워 넣을 값이 없다.

**같은 데이터의 두 표현**: `/`는 서버가 완성해서 주고, `/react`는 브라우저가 조립한다. 하지만 **같은 `VideoService`, 같은 `/api/videos`를 쓰므로 데이터는 하나다** — [[05-creating-json-based-apis]]에서 만든 이중 표현 구조가 여기서 실제로 쓰인다.

## Q9. 책이 "shadow DOM"이라 부른 것

**정확한 이름은 virtual DOM이다.**

| | **virtual DOM** | **Shadow DOM** |
|---|---|---|
| 무엇 | React가 메모리에 두는 **가벼운 화면 표현** | 브라우저의 **웹 표준 API** |
| 무엇을 위한 것 | **효율적인 갱신 계산** | **캡슐화** |
| 어떻게 | 이전 가상 트리와 비교해 **변경분만** 실제 DOM에 반영 | 웹 컴포넌트가 자기 마크업과 스타일을 **바깥으로부터 격리** |
| 소속 | React 구현 세부 | 웹 컴포넌트 표준 |

**판별 질문**: *무엇을 위한 것인가?* **갱신 효율이면 virtual, 캡슐화면 shadow.**

이름이 비슷해 혼동하기 쉽지만 **목적이 다르다.** 책이 설명하는 동작(가상 노드로 변경분을 계산해 반영)은 명백히 **virtual DOM**이다.

**Shadow DOM이 실제로 푸는 문제**는 다른 것이다 — 내가 만든 컴포넌트의 CSS가 페이지의 다른 스타일과 충돌하지 않게 하는 것. React와는 무관하게 브라우저가 제공하는 기능이다.

## Q10. 이 절의 진짜 목표

**React 학습이 아니라 "JavaScript를 Spring Boot 웹 애플리케이션에 병합하는 방법"이다.**

책이 마지막에 직접 초점을 다시 맞춘다.

> "React 이야기는 이만하자. 이 절의 초점은 **JavaScript를 Spring Boot 웹 애플리케이션에 병합하는 방법**을 보여 주는 것이었다. Node.js를 설정하고, 패키지를 설치하고, 빌드 도구를 활용하는 이 기법들은 React를 쓰든 Angular, Vue.js, 그 무엇을 쓰든 상관없이 통한다."

**요지 한 줄**: **프런트엔드 프레임워크가 무엇이든 Spring Boot 쪽 인터페이스는 `static` 폴더 하나다.**

- **손으로 두는** 정적 파일(JS·CSS) → `src/main/resources/static`
- **빌드가 만드는** 파일(번들) → `target/classes/static`

이 둘이 최종적으로 같은 자리에 도착한다는 것이 [[07-bundling-javascript-with-nodejs]]에서 확인한 내용이고, 그것이 이 세 노트([[06-integrating-nodejs-with-a-spring-boot-web-app]] · 07 · 07a) 전체의 결론이다.

**그래서 React의 구체 문법(클래스 컴포넌트, `bind`)이 낡았다는 사실은 이 절의 가치를 떨어뜨리지 않는다.** 현재 React 문서는 함수 컴포넌트와 훅(`useState`, `useEffect`)을 기본으로 안내하지만, **개념(상태 → 재렌더)은 그대로이고 문법만 다르다.** 그리고 Spring Boot 쪽 인터페이스는 아무것도 안 바뀐다.
