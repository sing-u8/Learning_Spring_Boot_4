## Q1. 파트너에게 HTML을 그대로 주면

1. **표현과 데이터가 섞여 있다.** ← 질문이 지목한 항목
2. **타입이 없다.** 조회수를 숫자로 쓰고 싶어도 HTML에서 뽑은 것은 전부 문자열이다.
3. **모든 소비자가 같은 파싱 코드를 각자 쓴다.** 그리고 **각자 다르게 틀린다.**

**"화면 스타일 변경이 API 장애가 된다"를 구체적으로**: 파트너는 제목을 뽑으려고 `<li>` 태그를 찾는 코드를 쓴다. 우리가 디자인을 바꿔 `<ul>`을 `<table>`로 만드는 순간 그 코드는 `<li>`를 찾지 못한다.

여기서 무서운 것은 **우리 쪽에 아무 신호가 없다는 점**이다. 우리 입장에서는 CSS 리팩터링이고, 테스트도 전부 통과하고, 화면도 정상이다. **장애는 파트너 쪽에서만 발생한다.** 우리가 계약을 맺은 적이 없는데 계약이 존재했던 셈이다.

**JSON이 푸는 것이 정확히 이것이다** — 표현을 뺀 데이터만 내보내면, 표현을 바꿔도 데이터 계약이 안 바뀐다. 무엇이 계약이고 무엇이 아닌지가 **명시적**이 된다.

## Q2. "Spring Web을 넣으면 Jackson이 온다"

**마법이 아니라 의존성 그래프다.** ✅ `spring-boot-starter-webmvc`의 실제 구성에 `spring-boot-starter-jackson`이 들어 있다.

```
Spring Web 체크박스
  → spring-boot-starter-webmvc
      → spring-boot-starter-jackson   ← 여기
      → spring-boot-starter-tomcat
      → spring-boot-http-converter
      → spring-boot-webmvc
      → spring-boot-starter
```

그리고 클래스패스에 Jackson이 있으면 **자동 구성이 그것을 조건으로 읽어** Jackson 기반 메시지 변환기를 등록한다.

**두 단계다** — 빌드 시점에 클래스패스가 바뀌고, 시작 시점에 조건이 참이 되어 빈이 등록된다. 그래서 책 말대로 "API를 코딩하기 시작하는 데 손가락 하나 더 움직일 필요가 없다."

이 사슬을 [[02-creating-a-spring-mvc-web-controller]]에서 이미 확인해 뒀다. 지금은 그때 깔린 것을 쓰는 것뿐이다.

## Q3. `@RestController`가 `@Controller`와 다른 딱 한 가지

**반환값의 해석이다.**

> **`@RestController` = `@Controller` + "반환값은 뷰 이름이 아니라 응답 본문이다"**

**같은 점**: 컴포넌트 스캔에 걸려 빈이 되고, 컨텍스트에 등록되고, Spring MVC에 컨트롤러로 등록되어 웹 호출이 라우팅된다. 전부 같다.

**다른 점 하나**: 모든 웹 메서드를 **템플릿 기반에서 JSON 기반으로 전환한다.** 템플릿 이름을 반환하는 대신 결과를 Jackson으로 **직렬화**한다.

**이름에 대한 주의**: `Rest`는 REST 아키텍처 스타일에서 왔지만, 애노테이션이 실제로 강제하는 것은 **REST 원칙 전체가 아니라 본문 직렬화 하나**뿐이다. 이름이 기능보다 넓게 들린다.

**동등한 표현**: `@RestController`는 클래스의 **모든** 메서드에 `@ResponseBody`를 붙인 것과 같은 효과다. 그래서 한 클래스에서 HTML과 JSON을 섞으려면 `@RestController`를 쓸 수 없고 `@Controller` + 메서드별 `@ResponseBody`를 써야 한다.

## Q4. `return "index";`가 두 애노테이션에서 각각 어떻게 해석되나

| | `@Controller` | `@RestController` |
|---|---|---|
| 해석 | **논리적 뷰 이름** | **응답 본문 그 자체** |
| 결과 | `templates/index.mustache`를 찾아 렌더링한 HTML | `index`라는 **다섯 글자짜리** 응답 |
| Content-Type | `text/html` | `text/plain` 계열 |

**같은 코드 한 줄이 클래스 애노테이션 하나 때문에 완전히 다른 것이 된다.** 이 대비가 두 애노테이션의 차이를 가장 선명하게 보여 준다.

**실무에서의 함정**: `@Controller`를 `@RestController`로 바꾸면 기존 화면 메서드들이 **전부 뷰 이름 문자열을 그대로 뱉는다.** 500도 404도 아니고 200으로 `index`가 나오므로 원인을 찾기 어렵다. 클래스 단위 결정이라 **한 번에 전부** 바뀐다.

## Q5. safe와 idempotent

**같은 말이 아니다.**

- **safe** = **상태를 바꾸지 않는다**
- **idempotent** = **여러 번 해도 결과가 한 번 한 것과 같다**

| 동사 | safe | idempotent | 이유 |
|---|---|---|---|
| GET | ✔ | ✔ | 읽기만 한다 |
| **POST** | ✘ | **✘** | 보낼 때마다 **새로 생긴다** |
| **PUT** | ✘ | **✔** | **상태를 바꾸지만**, 같은 값으로 덮어쓰므로 최종 상태가 같다 |
| DELETE | ✘ | ✔ | 이미 지워진 것을 또 지워도 최종 상태가 같다 |

**PUT이 두 성질을 가르는 결정적 예다.** PUT은 서버 상태를 바꾸므로 **safe하지 않다.** 하지만 "이 리소스를 이 값으로 만들어라"이므로 열 번 보내도 한 번 보낸 것과 최종 상태가 같다 — **idempotent다.**

**POST가 위험한 이유**: 유일하게 **idempotent하지 않다.** 네트워크가 끊겨 응답을 못 받았을 때 클라이언트가 재시도하면 **중복 생성**이 된다. 요청이 서버에 도달했는지 아닌지를 클라이언트가 알 수 없기 때문에 이 상황을 피할 수 없다.

**이 구분이 재시도 정책을 정한다** — idempotent한 요청만 마음 놓고 재시도할 수 있다. [[04d-changing-the-data-through-html-forms]]의 PRG도 같은 성질에서 나온 대응이다. 브라우저 새로고침으로 인한 POST 재전송을 막는 것.

## Q6. `-H 'Content-type:application/json'`을 빼면

**415 Unsupported Media Type이 난다.**

**`@RequestBody`가 모르는 것은 "이 본문이 어떤 형식인가"다.** 애노테이션은 "본문을 객체로 바꿔라"라고만 말한다. 어떤 변환기를 쓸지는 **`Content-Type` 헤더가 결정한다.**

Spring은 등록된 메시지 변환기들 중 그 미디어 타입을 처리할 수 있는 것을 고른다. 헤더가 없거나 틀리면 **Jackson 변환기가 선택되지 않는다.** 본문에 완벽한 JSON이 들어 있어도 마찬가지다 — 내용을 들여다보고 추측하지 않는다.

**이것이 오히려 올바른 설계다.** 본문을 열어 보고 "JSON 같아 보이니 JSON으로 파싱하자"고 추측하면, 형식이 애매한 입력에서 예측 불가능해진다. **선언된 것만 믿는다.**

**나머지 옵션도 같은 방식으로 읽으면 된다**: `-X POST`가 없으면 GET으로 가고, `-d`가 없으면 본문이 없어 역직렬화가 실패한다. 각 옵션이 요청의 한 부분씩을 책임진다.

## Q7. curl verbose의 `>`와 `<`

- **`>`** = 우리가 **보낸** 것 (요청)
- **`<`** = 서버가 **돌려준** 것 (응답)

```text
> POST /api/videos HTTP/1.1        ← 우리가 보낸 요청 라인
> Content-type:application/json    ← 우리가 보낸 헤더
> Content-Length: 34
>
< HTTP/1.1 200                     ← 서버 응답 상태
< Content-Type: application/json   ← 서버 응답 헤더
{"name":"Learning Spring Boot 4"}  ← 응답 본문
```

**확인 포인트 넷**: ① 위쪽의 동사·URL·헤더가 의도대로인가 ② `HTTP 200` 성공 코드 ③ 응답이 `application/json`인가 ④ 본문에 방금 만든 항목이 있는가.

**이 도구가 디버깅에 중요한 이유**: 브라우저 개발자 도구와 달리 **우리가 보낸 것을 그대로 보여 준다.** "헤더를 넣었다고 생각했는데 실제로는 안 갔다" 같은 상황을 여기서 잡는다.

## Q8. `create()`가 인자를 그대로 돌려주도록 만든 이유

**HTTP 표준이 요구하는 것은 아니지만, 갱신 연산이 새로운·갱신된·삭제된 항목의 사본을 돌려주는 것은 흔한 동작이기 때문이다.**

**클라이언트에게 주는 이득**:
- **서버가 무엇을 만들었는지 확인**할 수 있다. 보낸 것과 저장된 것이 다를 수 있다.
- **서버가 채운 값**(생성 시각, 서버가 부여한 id 등)을 즉시 받는다. 지금 `Video`에는 그런 필드가 없지만, 실제 API에서는 이것이 핵심 이유다.
- **추가 조회 요청이 필요 없다.** 저장 → 다시 GET의 왕복 두 번이 한 번이 된다.

**응답 모양의 차이도 여기서 보인다**: `all()`은 `List<Video>`를 돌려주므로 JSON **배열**, `newVideo()`는 단일 `Video`를 돌려주므로 JSON **객체**다. 반환 타입이 그대로 응답 구조가 된다.

## Q9. `Video`에 필드를 하나 더하면

**자동으로 일어나는 일**: **JSON 키가 하나 는다.** record의 컴포넌트 하나가 JSON 키 하나에 대응하므로, 필드를 더하면 모든 응답에 그 키가 나타난다. 설정할 것이 없다.

**왜 위험한가**: **내부 필드 추가가 곧 공개 계약 변경이 된다.**

- 필드를 더하는 커밋은 **내부 리팩터링처럼 보인다.** 리뷰어도 API 변경으로 인식하지 않는다.
- 그런데 그 순간 모든 소비자의 응답이 바뀐다. 엄격한 파서를 쓰는 클라이언트는 **모르는 필드에서 실패**할 수 있다.
- 반대로 **필드를 지우거나 이름을 바꾸면** 확실히 깨진다. 그리고 그것도 record 한 줄 수정이다.
- 내부에만 쓰려던 필드(내부 상태 플래그, 계산용 값)가 **의도치 않게 공개**된다.

**Q1의 문제가 형태만 바꿔 돌아온 것이다.** 거기서는 "HTML 구조가 몰래 계약이었다"였고, 여기서는 "내부 데이터 클래스가 몰래 계약이다".

**실무의 대응 두 가지**: ① 응답 전용 타입(DTO)을 따로 두어 내부 모델과 공개 계약을 분리한다 ② 버전을 명시해 계약 변경을 드러낸다 — [[08-versioning-apis-with-spring-boot-4]]가 정확히 이 문제에서 출발한다.
