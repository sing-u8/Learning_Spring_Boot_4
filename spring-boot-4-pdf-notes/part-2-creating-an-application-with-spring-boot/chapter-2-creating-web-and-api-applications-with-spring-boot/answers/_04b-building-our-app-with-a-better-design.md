## Q1. 두 번째 컨트롤러가 생기는 순간의 세 가지 나쁜 선택지

비디오 목록이 `HomeController` 안에 있으므로, `ApiController`가 그것을 쓰려면:

1. **필드를 복사해 붙여 넣는다** → **목록이 두 벌**이 된다. 한쪽에 추가한 비디오가 다른 쪽에 안 보인다. 같은 데이터가 두 개의 진실을 갖는다.
2. **`ApiController`가 `HomeController`를 주입받는다** → **컨트롤러가 컨트롤러를 부르는** 기이한 구조가 된다. 웹 계층이 웹 계층에 의존하면 어느 쪽이 요청을 처리하는 주체인지 흐려진다.
3. **`HomeController.Video`로 밖에서 참조한다** → 데이터 타입의 이름이 **웹 계층에 영원히 묶인다.** 나중에 이 타입이 DB 엔티티가 되어도 이름은 여전히 컨트롤러 소속이다.

**셋의 공통 뿌리**: 데이터의 형태와 데이터 자체가 **웹 계층 안에 있다.** 어느 선택지를 골라도 그 근본은 안 바뀐다.

## Q2. 컨트롤러와 데이터 정의를 나누는 근거 — 변경 주기

**웹 요구는 자주 바뀌고, 데이터의 형태는 그만큼 자주 바뀌지 않는다.**

- 웹: URL이 바뀌고, HTML이 JSON이 되고, 폼이 REST가 되고, 응답 형식이 바뀐다. 이 장 안에서만 [[05-creating-json-based-apis]]와 [[08-versioning-apis-with-spring-boot-4]]가 웹 요구를 두 번 바꾼다.
- 데이터: "비디오에는 이름이 있다"는 사실은 그동안 한 번도 안 바뀐다.

> **변경 주기가 다른 두 가지를 한 파일에 두면 자주 바뀌는 쪽이 안 바뀌는 쪽을 계속 건드린다.**

책의 두 이유도 같은 말이다 — 컨트롤러는 "웹 호출에 응답하고 다른 서비스와 상호작용하는 것"이 일이고, **데이터까지 다루는 무거운 컨트롤러는 웹 요구가 바뀔 때 조정을 어렵게 만든다.**

실무적 증상은 **불필요한 diff와 불필요한 리뷰**다. 응답 형식만 바꾸는 커밋에 데이터 정의 파일이 딸려 오면, 리뷰어가 "이 record는 왜 바뀌었지"를 매번 확인해야 한다.

## Q3. `Video`를 자기 파일로 옮기는 것만으로 달라지는 것

**`Video`가 더 이상 `HomeController`의 소유물이 아니게 된다.**

코드는 "완전히 같은 코드이고, 자기 파일로 옮겨졌을 뿐"이다. 그런데:

- 이제 **같은 패키지의 누구든** 이 타입을 쓸 수 있다.
- **어느 컨트롤러에도 종속되지 않는다.** `HomeController.Video`가 아니라 그냥 `Video`다.
- Q1의 세 번째 나쁜 선택지가 **사라진다.** 밖에서 참조할 때 웹 계층 이름을 거칠 필요가 없다.

**한 줄도 안 바뀌었는데 의미가 바뀐 것**이 핵심이다. 소속(중첩 위치)이 곧 계약이었기 때문이다.

## Q4. `Video`에 `public`을 붙이지 않는 것이 왜 좋은가

`Video`는 Java의 **기본 가시성**인 **package-private**다. 같은 패키지(`com.learningspringboot4`, 즉 베이스 패키지) 안에서만 보인다.

**되돌리기 어려운 것은 "공개"다.**

한 번 `public`으로 열어 밖에서 쓰기 시작하면 **그 순간부터 그 타입은 계약이 된다.** 이름을 바꾸거나 필드를 없애면 밖의 코드가 깨진다. 좁게 시작하면 넓히는 것은 언제든 쉽지만, **넓게 시작하면 좁히는 것은 남의 코드를 깨는 일**이 된다.

> 기본값을 좁게 두면, 넓힐 때마다 "정말 밖에서 필요한가"를 **한 번 묻게 된다.**

그리고 이건 §1이 지적한 문제 — **계층 방향을 컴파일러가 강제하지 않는다** — 에 대한 부분적 대응이기도 하다. 가시성 제한이 그 약속을 **조금이나마 언어 수준으로 밀어 올린다.**

**주의**: `private`와 다르다. `private`는 **같은 클래스** 안에서만 보이므로, `Video`가 `private`였다면 `VideoService`조차 쓸 수 없다.

## Q5. `@Service`와 `@Component`가 기계적으로 같다면 왜 `@Service`인가

**기계에게는 같고 사람에게는 다르다.**

`@Service`는 `@Component`를 **메타 애노테이션으로 갖는 특수화된 형태**다. 컴포넌트 스캔이 발견해 빈으로 등록하는 동작은 완전히 같다.

차이는 **읽는 사람에게 남기는 정보**다. 클래스 목록만 훑어도 "이건 업무 동작을 담당한다"가 드러난다. 그래서 이런 애노테이션을 **stereotype**(정형화된 역할 표시)이라 부른다.

**판별 질문**: *이 클래스가 하는 일에 더 구체적인 이름이 있는가?* 있으면 그 stereotype(`@Service`, `@Controller`, `@Repository`), 없으면 `@Component`.

**단, 전부 "이름만"인 것은 아니다.** `@Controller`는 Spring MVC가 **추가 의미까지 부여한다** — 요청 매핑의 대상이 되고, 반환 문자열이 뷰 이름으로 해석된다. `@Repository`도 예외 변환 같은 부가 동작이 붙는다. `@Service`가 순수하게 의미 표시에 가까운 쪽이다.

## Q6. 계층의 화살표가 한 방향이어야 한다는 규칙은 누가 강제하는가

**아무도 강제하지 않는다. 사람이 지키는 약속이다.**

Spring의 계층은 **같은 JVM 안의 객체 참조**일 뿐이다. 서비스가 컨트롤러를 주입받는 코드도, 컨트롤러가 서비스를 건너뛰고 저장소를 직접 부르는 코드도 **잘 컴파일된다.**

**비유가 깨지는 지점이 정확히 여기다.** 실제 식당에서 홀 직원은 주방 냉장고에 마음대로 손을 넣을 수 없다 — **벽이 물리적으로 막는다.** Spring의 계층에는 그런 벽이 없다.

**거들어 주는 것들**은 있다.

- **가시성 제한** — `Video`가 package-private인 것이 그 시도다.
- **패키지 분리** — 프로젝트가 커지면 패키지를 나눠 import 자체를 눈에 띄게 만든다.
- 그 외 아키텍처 테스트 도구(ArchUnit 등)로 방향을 검사하는 방법도 있지만, 이 장의 범위 밖이다.

**핵심은 이것들이 전부 "거드는" 수준이라는 점이다.** 방향을 지키는 주체는 여전히 사람이다.

## Q7. 인메모리에서 DB로 바꿀 때 고쳐야 하는 파일

| | 리팩터링 **전** | 리팩터링 **후** |
|---|---|---|
| 고칠 파일 | **`HomeController`** (목록 필드가 거기 있으므로) + 그 목록을 쓰는 **모든 컨트롤러** | **`VideoService` 내부만** |
| 컨트롤러 | 저장 방식을 안다 → 함께 고쳐야 한다 | `videoService.getVideos()`만 부른다 → **손대지 않는다** |

**이것이 이 리팩터링의 진짜 값이다.** Chapter 3에서 인메모리 목록을 실제 저장소로 바꿀 때, 컨트롤러는 한 글자도 안 바뀐다.

값이 회수되는 시점도 분명하다. 책은 이 작업이 "약간 지루하게 느껴졌을지 모르지만 계속 살을 붙여 나가면서 값을 할 것"이라고 하는데, **이 장 안에서만 두 번 회수된다** — [[05-creating-json-based-apis]]에서 `ApiController`가 같은 서비스를 재사용하고, [[04d-changing-the-data-through-html-forms]]에서 추가 로직이 서비스 한 곳에만 들어간다.

## Q8. `getVideos()`가 내부 목록을 그대로 돌려주는 것

**지금 안전한 이유**: 그 목록이 `List.of()`로 만든 **불변 컬렉션**이기 때문이다. 호출자가 참조를 받아도 `add`를 부르면 예외가 난다. 내부 상태를 바꿀 방법이 없다.

**언제부터 위험한가**: 그 필드가 **가변 목록**이 되는 순간이다.

```java
private List<Video> videos = new ArrayList<>(...);
public List<Video> getVideos() { return videos; }   // ← 내부 참조를 그대로 넘긴다
```

이제 호출자가 `videoService.getVideos().add(...)`나 `.clear()`를 부를 수 있다. **서비스가 캡슐화한다고 믿었던 상태를 밖에서 직접 바꾼다.** 서비스 안에 검증이나 로깅을 넣어도 이 경로는 그것을 전부 우회한다.

**그리고 [[04d-changing-the-data-through-html-forms]]에서 실제로 가변 목록이 필요해진다.** 그때 이 점이 다시 문제가 된다.

**대응 선택지**: 방어적 복사(`List.copyOf(videos)`)를 돌려주거나, `Collections.unmodifiableList`로 감싸거나, 아예 조회 메서드가 필요한 형태만 돌려준다. 각각 비용(복사)과 이득(안전)의 균형이 다르다.
