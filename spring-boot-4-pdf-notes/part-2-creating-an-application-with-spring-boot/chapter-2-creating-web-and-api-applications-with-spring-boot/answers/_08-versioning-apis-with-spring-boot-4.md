## Q1. "계약"에 포함되는 것

**경로·요청 형식·응답 필드·타입·의미**가 모두 계약이다. 그리고 다음도 실질적으로 포함된다.

- **필드 이름** — `name`을 `title`로 바꾸면 파싱이 깨진다
- **필드 타입** — 문자열이던 것이 객체가 되면 깨진다
- **필드의 존재** — 지우면 확실히, 더해도 엄격한 파서에서는 깨진다
- **HTTP 상태 코드와 오류 형식**
- **값의 의미** — 같은 필드가 다른 뜻이 되면 타입이 같아도 깨진다

**핵심은 "우리가 계약이라고 선언한 적이 없어도 계약이 된다"는 점이다.** [[05-creating-json-based-apis]]에서 본 문제와 같다 — record에 필드를 더하는 **내부 리팩터링처럼 보이는 커밋**이 공개 계약을 바꾼다.

책의 진단: *"API를 개발하고 릴리스할 때 우리는 그 소비자들과 **계약**을 맺는 것이다. 계약에 사소한 변경만 생겨도 소비자들이 동작을 멈출 수 있다."*

---

## Q2. 이미 배포된 모바일 앱이 왜 버전 관리를 필수로 만드나

**우리가 고칠 수 없기 때문이다.**

웹 프런트엔드는 우리가 배포하므로 서버와 같이 바꿀 수 있다. 모바일 앱은 다르다 — 사용자의 기기에 있고, **사용자가 업데이트할 때까지 몇 주가 걸린다.** 업데이트를 안 하는 사용자도 있다.

그래서 상황이 이렇게 된다.

- 계약을 바꾸면 **구버전 앱 사용자 전원이 즉시 장애**를 겪는다.
- 우리 잘못이 아닌 것처럼 보이지만 **장애 신고는 우리에게 온다.**
- 롤백도 답이 아니다. 새 계약에 맞춘 신버전 앱이 깨진다.

**그렇다고 계약을 영원히 안 바꿀 수도 없다.** 요구는 계속 바뀐다.

**유일한 출구가 "여러 계약을 동시에 제공하는 것"이다.** 구버전 앱은 v1을, 신버전 앱은 v2를 부른다. 각자의 속도로 이동한다.

## Q3. 네 가지 전략과 각각의 대가

| 전략 | 형태 | 장점 | **대가** |
|---|---|---|---|
| **URI(경로)** | `/api/v1/videos` | 말이 되고 테스트가 간단하다 | **버전이 모든 링크에 박힌다** |
| **요청 헤더** | `API-Version: 2.0` | URL이 깨끗하다. 웹·모바일·파트너가 서로 다른 버전을 쓸 때 잘 맞는다 | URL만 보고는 버전을 알 수 없다 |
| **쿼리 파라미터** | `?api-version=2.0` | 단순하고 갖고 놀기 쉽다 | 지저분해지기 쉽고 **공개 API에는 대체로 선호되지 않는다** |
| **미디어 타입** | `Accept: application/vnd.myapp.v2+json` | 가장 REST 순수주의적 | **가장 장황하고 실무에서 다루기 어렵다** |

**URI 방식의 대가가 실무에서 가장 뼈아프다.** 응답 본문 안에 다른 리소스의 URL을 담는 API라면, 버전을 올릴 때 **본문 속 URL까지 전부 바뀐다.**

**미디어 타입 방식**이 기대는 것은 **콘텐츠 협상**이다 — 클라이언트가 `Accept`로 원하는 표현을 알리고 서버가 맞춰 고른다. "버전도 결국 같은 리소스의 다른 표현"이라는 관점에서 **가장 이론적으로 일관된 자리**다. 다만 이론적 일관성과 실무 편의가 반대 방향이다.

## Q4. Boot 4 이전에 없었던 것

**헤더·파라미터 조건 매칭은 있었다. 없었던 것은 "버전"이라는 개념 자체다.**

```java
@GetMapping(value = "/api/videos", headers = "API-Version=1")   // 조건을 손으로
public List<Video> allV1() { ... }

@GetMapping(value = "/api/videos", params = "version=2")        // 다른 엔드포인트는 다른 전략
public List<VideoV2> allV2() { ... }
```

조건은 다 있었지만 **그것들이 "버전을 나타낸다"는 사실은 개발자 머릿속에만 있었다.**

책의 표현: *"버전 관리는 암묵적이었고 컨트롤러 매핑과 클라이언트 코드 여기저기에 흩어져 있었으며, 각 엔드포인트가 서로 다른 전략을 써서 엉망이 될 수 있었다."*

**결과 세 가지**:
- 전략이 엔드포인트마다 달라져도 **아무도 못 막았다.**
- 전략을 바꾸려면 **모든 매핑을 찾아 고쳐야** 했다.
- 클라이언트 쪽에도 같은 문자열이 흩어졌다 — [[09-calling-versioned-apis-with-http-service-clients]].

**Boot 4가 한 일은 새 기능을 만든 것이 아니라 흩어진 개념에 이름을 준 것이다.** 일급 개념이 되면서 통일된 API가 생겼다.

## Q5. `use.path-segment=1`의 `1`

**경로 세그먼트의 색인이다. 버전 번호가 아니다.**

```text
   /api/v2/videos
    │    │    │
    │    │    └── segment 2 = "videos"
    │    └─────── segment 1 = "v2"      ← use.path-segment=1
    └──────────── segment 0 = "api"
```

**0부터 세는 색인**이다.

**흔한 오해**: "`1`이니까 버전 1을 쓰라는 뜻"으로 읽는 것. 아니다. **"경로의 몇 번째 조각에서 버전을 찾을지"**를 말한다. `/api/v2/videos`든 `/api/v99/videos`든 이 설정은 그대로 `1`이다.

**그리고 파싱까지 프레임워크가 한다**: Spring이 세그먼트 `v2`를 읽어 **논리 버전 2**에 매칭하고, 그것이 `version = "2"`로 선언된 handler에 대응한다. 우리가 `version = "v2"`가 아니라 `version = "2"`라고 쓴 이유다 — `v` 접두사를 벗기는 일은 프레임워크 몫이다.

## Q6. 헤더에서 쿼리로 전략을 바꿀 때 컨트롤러는 얼마나 바뀌나

**한 줄도 안 바뀐다.** 프로퍼티만 바꾼다.

```properties
# 이 한 줄만 교체
spring.mvc.apiversion.use.path-segment=1
→ spring.mvc.apiversion.use.header=API-Version
→ spring.mvc.apiversion.use.query-param=api-version
```

**왜인가**: 컨트롤러의 `version = "2"`는 **논리 버전만** 말한다. **그 버전을 요청에서 어떻게 읽어낼지는 전혀 적혀 있지 않다.**

```java
@GetMapping(value = "/api/{version}/videos", version = "2")   // "무엇" 만 있다
```

**두 관심사가 분리돼 있다** — 컨트롤러는 *무엇을*, 프로퍼티는 *어디서 읽을지*. Boot 4 이전에는 이 둘이 한 애노테이션에 뒤엉켜 있었고(Q4), 그래서 전략을 바꾸면 모든 매핑을 고쳐야 했다.

**같은 구조를 클라이언트 쪽에서도 본다** — [[09-calling-versioned-apis-with-http-service-clients]]의 `@GetExchange(version = "2")`도 "어디에 실을지"는 모르고, `ApiVersionInserter`가 정한다. **정확히 대칭이다.**

## Q7. 경로 방식에 default 버전을 적용할 수 없는 이유

**매핑 자체가 성립하지 않기 때문이다.**

헤더나 쿼리 파라미터 방식에서는 버전이 없어도 **경로는 완전하다.** `/api/videos`로 요청이 도착하고, 서버가 "버전 정보가 없네, 기본값을 쓰자"고 판단할 수 있다.

경로 방식은 다르다. 버전이 **경로의 일부**다.

```text
/api/v2/videos   ← 매핑된다
/api/videos      ← 세그먼트 수가 다르다. 애초에 이 매핑에 안 걸린다
```

**요청이 handler에 도달하지도 못한다.** "버전이 없으니 기본값을 쓰자"고 판단할 지점 자체가 없다 — 그 판단은 매핑이 성립한 **뒤에** 일어나는 일인데, 매핑이 성립하지 않는다.

**일반화**: 버전을 **리소스 식별자의 일부**로 만들면, 버전 없는 요청은 **다른 리소스를 가리키는 요청**이 된다. 헤더·쿼리 방식은 버전을 리소스에 대한 **메타데이터**로 두므로 생략이 가능하다.

## Q8. 전략을 애플리케이션당 하나로 제한하는 이유

**Q4에서 지적한 문제를 구조적으로 막기 위해서다.**

이전에는 엔드포인트마다 다른 전략을 쓸 수 있었고 *"각 엔드포인트가 서로 다른 전략을 써서 엉망이 될 수 있었다."*

**하나로 제한하면**:

- **소비자가 규칙 하나만 배우면 된다.** "이 API는 헤더로 버전을 준다"가 전부다. 엔드포인트마다 문서를 뒤질 필요가 없다.
- **클라이언트 설정도 하나면 된다.** [[09-calling-versioned-apis-with-http-service-clients]]의 `ApiVersionInserter`가 클라이언트 전체에 하나로 붙는 이유다.
- **전략 변경이 프로퍼티 한 줄이 된다** (Q6). 엔드포인트마다 다르면 이 단순함이 불가능하다.

**대가**: 특정 엔드포인트만 다른 전략을 쓰고 싶어도 못 한다. 하지만 **그런 요구 자체가 대개 설계 문제의 신호**다.

## Q9. 버전을 나눴을 때 새로 생기는 비용

**핵심은 "유지 비용이 보이지 않게 쌓인다"는 것이다.**

**비유가 깨지는 지점이 정확히 여기다.** 벽의 콘센트는 두 벌을 설치하면 **눈에 보이는 자리를 차지한다.** 그래서 언젠가 "이 옛 콘센트 아직 쓰나?"라는 질문이 자연히 나온다. **API의 옛 버전은 코드베이스 안 handler 메서드 하나일 뿐이라 아무도 안 본다.**

**구체적 비용**:

- **모든 버그 수정을 여러 곳에 반영**해야 한다. v1, v2, v3가 있으면 세 곳이다. 하나를 빠뜨리면 "특정 버전에서만 나는 버그"가 생긴다.
- **테스트가 버전 수만큼 곱해진다.**
- **서비스 계층에도 번진다.** `getVideos()`와 `getVideosV2()`가 따로 생긴다 — 계약이 다르니 불가피하지만, 그만큼 중복이 는다.
- **문서가 버전마다 필요**하고, 어느 것이 최신인지 소비자가 헷갈린다.

**그래서 결론은 하나다** — **버전 관리에는 폐기 계획이 함께 있어야 한다.** 언제 v1을 끄는지, 소비자에게 어떻게 알리는지, 남은 사용량을 어떻게 측정하는지를 **버전을 만드는 시점에** 정해 둔다. 나중에 정하려 하면 아무도 지우자고 말하지 않는다.
