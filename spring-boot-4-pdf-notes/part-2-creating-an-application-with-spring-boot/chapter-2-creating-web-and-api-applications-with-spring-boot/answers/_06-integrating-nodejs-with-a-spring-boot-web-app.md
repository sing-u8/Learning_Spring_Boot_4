## Q1. 각자 Node를 설치해 빌드하는 방식이 무너지는 네 지점

1. **개발자마다 Node 버전이 다르다.** 한 사람은 20, 다른 사람은 24. 어떤 패키지는 이 차이에서 다르게 동작한다.
2. **CI 서버에는 Node가 아예 없다.** 빌드 이미지에 넣는 별도 작업이 생기고, 그 버전이 또 개발자 PC와 다르다.
3. **"복사"를 사람이 기억해야 한다.** JS를 고치고 빌드한 뒤 복사를 잊으면 **옛 파일이 배포된다.**
4. **빌드가 하나가 아니다.** `mvn package` 하나로 배포 산출물이 안 나오므로 배포 문서에 "그전에 이걸 하세요"가 붙는다.

**1~2의 공통 뿌리**는 "빌드 환경이 코드에 기록되지 않았다"이고, **3~4의 공통 뿌리**는 "빌드가 하나의 명령이 아니다"다. 두 뿌리 모두 `frontend-maven-plugin`이 해결한다 — 버전을 `pom.xml`에 박고, 실행을 Maven 생명주기에 얹는다.

## Q2. Node를 프로젝트 안에 설치하는 이유

**개발자 PC의 설치 상태에 빌드가 좌우되지 않게 하기 위해서다.**

`<nodeVersion>v24.10.0</nodeVersion>` 한 줄이 **버전을 코드로 고정한다.** 그러면 내 PC, 동료 PC, CI가 전부 같은 Node로 빌드한다. 재현 가능성이 사람의 설치 습관이 아니라 파일에서 나온다.

**비유와 그 한계**: 원청이 하청에게 **현장 공구**를 지정해 그것만 쓰게 하는 것과 같다. 기사가 자기 집 공구를 가져오면 사람마다 달라진다.

→ 그런데 **건설 하청은 공정이 끝나면 공구를 챙겨 철수한다.** `frontend-maven-plugin`이 내려받은 `node/`와 `node_modules/`는 프로젝트 폴더에 **그대로 남는다.** 수백 MB를 차지하고 실수로 커밋되기 쉬워 `.gitignore` 관리가 별도로 필요해진다 → Q5.

**부수 효과 하나**: 다운로드 URL에 `darwin-arm64` 같은 것이 붙는다. 플러그인이 **현재 OS·CPU에 맞는 배포판**을 고르므로 macOS·Linux·Windows에서 같은 `pom.xml`이 각자 맞는 Node를 가져온다.

## Q3. `generate-resources`에서 도는 것이 왜 중요한가

```text
validate → generate-sources → process-sources
        → generate-resources ← 여기
        → process-resources → compile → test → package
```

**`compile`과 `package`보다 앞이라는 점이 핵심이다.** 그래야 만들어진 JS 번들이 **최종 JAR에 함께 담긴다.**

**`package` 뒤였다면**: JAR이 이미 만들어진 다음에 번들이 생긴다. 번들은 `target/` 어딘가에 파일로 남지만 **JAR 안에는 없다.** 배포하면 JS가 404다.

그리고 그 실패는 **로컬에서 안 보인다.** IDE로 실행하면 클래스패스에 `target/classes/`가 그대로 들어가므로 번들이 잘 로드된다. **JAR로 패키징해 배포했을 때만** 문제가 드러난다 — 가장 늦게, 가장 나쁜 타이밍에.

## Q4. 콘솔 로그 세 구간

| 로그 구간 | 하는 일 | 왜 필요한가 |
|---|---|---|
| `Downloading … to ~/.m2/repository/…` | Node 배포판을 **Maven 로컬 저장소**에 받는다 | 다른 프로젝트에서도 **같은 파일을 재사용**하기 위해 |
| `Unpacking … into <프로젝트>/node/tmp` | **프로젝트 폴더 안**에 푼다 | 이 프로젝트 **전용** Node를 확보하기 위해 |
| `Copying node binary … Extracting NPM` | `node/node`와 npm을 **제자리에** 놓는다 | 이후 실행이 `node/npm` 경로로 **일정하게** 되기 위해 |

**첫 구간과 둘째 구간이 다른 위치인 것이 설계다.** 다운로드는 사용자 홈의 공유 캐시(`~/.m2`)에, 압축 해제는 프로젝트 안에. 그래서 여러 프로젝트가 같은 Node를 쓸 때 **다운로드는 한 번**이지만 **각자 자기 `node/`를 갖는다.**

셋째 구간이 [[07-bundling-javascript-with-nodejs]]의 `node/npm install`이 동작하는 근거다 — 경로가 일정해야 다음 execution이 그것을 부를 수 있다.

## Q5. `node/`·`node_modules/`는 커밋 안 하고 `package.json`은 커밋하는 기준

> **판별 질문: "이 파일이 빌드로 다시 만들어지는가?"** 그렇다면 **산출물**이지 소스가 아니다.

| | 다시 만들어지는가 | 커밋 |
|---|---|---|
| `node/` | 예 — `install-node-and-npm`이 만든다 | ✘ |
| `node_modules/` | 예 — `npm install`이 만든다 | ✘ |
| **`package.json`** | **아니오 — 사람이 결정한 기록이다** | **✔** |

`package.json`은 **어떤 의존성을 쓸지 사람이 내린 결정**이다. 이것이 없으면 `node_modules/`를 다시 만들 수 없다. 반대로 `package.json`만 있으면 나머지는 언제든 복원된다.

**왜 이 판단이 중요한가**: `node_modules`는 의존성 수에 따라 **수만 개 파일, 수백 MB**가 되는 것이 보통이다. 실수로 커밋하면 저장소가 급격히 무거워지고, **이미 커밋된 것을 되돌리는 일은 이력 재작성을 요구한다.**

그래서 실무 규칙 하나: **플러그인을 넣는 커밋과 `.gitignore`를 고치는 커밋을 함께 다룬다.** 순서가 어긋나면 첫 빌드에서 수만 개 파일이 스테이징된다.

## Q6. `static/`과 `templates/`를 가르는 기준

> **"이 파일에 서버 데이터를 끼워 넣어야 하는가?"** 그렇다면 `templates/`, 아니면 `static/`.

| | `templates/` | `static/` |
|---|---|---|
| 거치는 것 | 컨트롤러 → 뷰 해석 → 템플릿 엔진 | **아무것도 안 거침** |
| URL | 컨트롤러가 정한 경로 | **파일 경로 그대로** |
| 예 | `index.mustache` → `GET /` | `static/index.js` → `GET /index.js` |

JS 번들이 `static/`으로 가는 이유는 **그 파일에 서버 데이터를 끼워 넣을 일이 없기 때문**이다. 데이터는 [[05-creating-json-based-apis]]의 API로 따로 가져온다.

**보강**: 이 관례도 구성 프로퍼티로 조정할 수 있다. `spring.mvc.static-path-pattern`으로 서빙 경로를 바꾸거나, `spring.web.resources.chain.strategy.content.enabled=true`로 정적 파일 URL에 내용 해시를 붙이는 캐시 무효화를 켤 수 있다. **Chapter 1의 "기본값이 있고 명시하면 물러난다"가 여기도 그대로다.**

## Q7. 플러그인에는 버전을 쓰고 스타터에는 안 쓰는 이유

> **갈림점: Spring Boot BOM이 관리하는 아티팩트인가?**

| | `frontend-maven-plugin` | Boot 스타터 |
|---|---|---|
| BOM 관리 대상 | **아니다** (서드파티) | **그렇다** |
| `<version>` | **반드시 쓴다** | **쓰지 않는다** |
| 안 지키면 | 버전이 없어 빌드 실패 | BOM 정렬이 그 한 줄에서만 깨진다 |

Boot BOM은 자기가 아는 것만 관리한다. `com.github.eirslett`는 그 목록에 없으므로 **버전을 안 쓰면 Maven이 무엇을 받을지 알 수 없다.**

반대로 BOM이 관리하는 아티팩트에 버전을 박으면 [[03-augmenting-an-existing-project-with-initializr]]에서 본 함정에 빠진다 — **빌드는 성공하고 런타임에만 어긋난다.**

**한 문장으로**: 버전을 쓸지 말지는 취향이 아니라 **그 아티팩트를 누가 관리하느냐**로 결정된다.

## Q8. 이 방식이 적합하지 않은 상황

**프런트엔드가 커져서 Java 빌드에 얹는 것 자체가 병목이 될 때다.**

세 execution이 모두 `generate-resources`에서 도므로 **매 빌드마다 JS 빌드가 함께 돈다.** Java 한 줄만 고쳐도 번들링이 다시 돈다. 프런트엔드가 수백 개 모듈이 되면 이 비용이 매 빌드에 붙는다.

그 밖의 부적합 상황:

- **JavaScript 빌드가 아예 필요 없는 프로젝트** — 순수한 비용이다.
- **폐쇄망 CI** — 첫 빌드에 Node 배포판과 npm 패키지 다운로드가 필요하다. 사내 미러나 사전 캐시가 있어야 한다.
- **프런트엔드와 백엔드의 배포 주기가 다를 때** — 별도 저장소·별도 배포로 분리하는 편이 낫다.

**이 절의 접근이 유효한 조건**: **하나의 배포 단위로 유지하고 싶을 때.** 그 이득(배포 단순화, 버전 일치)이 비용(빌드 시간, 디스크)보다 클 때만 성립한다.
