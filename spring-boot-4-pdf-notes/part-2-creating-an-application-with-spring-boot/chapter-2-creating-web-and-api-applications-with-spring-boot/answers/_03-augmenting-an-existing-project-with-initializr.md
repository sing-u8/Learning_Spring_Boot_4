## Q1. 의존성 한 줄을 손으로 쓸 때 동시에 맞혀야 하는 세 가지

1. **groupId** — `org.springframework.boot`인가 `com.samskivert`인가? **Mustache 구현체 자체와 Boot 스타터는 좌표가 다르다.**
2. **artifactId** — `spring-boot-starter-mustache`인가 `spring-boot-mustache`인가? **Boot 4는 여러 모듈 이름을 바꿨다.**
3. **version** — 여기 버전을 써야 하나 말아야 하나?

셋 중 **하나만 틀려도** 결과는 "빌드가 안 되거나", 더 나쁘게는 "빌드는 되는데 런타임에 버전이 어긋나는" 상태다.

이건 새 문제가 아니다. [[01-using-start-spring-io-to-build-apps]]에서 정리한 옛 방식(Stack Overflow 검색, 블로그 복사)의 문제가 **기존 프로젝트 안으로 되돌아온 것**이다. 프로젝트를 Initializr로 시작했어도, 6개월 뒤 의존성을 더하는 순간 같은 함정이 다시 열린다.

## Q2. 왜 "버전을 쓸지 말지"가 특히 위험한가

**다른 둘은 즉시 실패하고, 이것만 조용히 통과하기 때문이다.**

| 틀린 항목 | 언제 드러나나 |
|---|---|
| groupId | **빌드 즉시** — 아티팩트를 못 찾는다 |
| artifactId | **빌드 즉시** — 아티팩트를 못 찾는다 |
| **version** | **빌드는 성공한다.** 런타임에, 그것도 특정 코드 경로를 탈 때만 |

Boot BOM이 관리하는 아티팩트에 버전을 직접 박으면 **BOM의 정렬이 그 한 줄에서만 깨진다.** 나머지 라이브러리는 Boot가 맞춰 준 버전인데 이 하나만 다른 세계에 있게 된다. 빌드 도구는 "요청한 버전이 존재한다"만 확인하므로 아무 불평도 하지 않는다.

증상은 그 라이브러리를 **실제로 호출하는 순간** `NoSuchMethodError`나 `ClassNotFoundException`으로 나타난다. 원인(빌드 파일 한 줄)과 증상(런타임 예외) 사이가 멀어서 추적이 어렵다.

**그래서 규칙은 단순하다** — Boot가 관리하는 아티팩트면 `<version>`을 **쓰지 않는다.** EXPLORE 결과에 버전이 없으면 그게 답이다.

## Q3. EXPLORE와 GENERATE를 가르는 판별 질문

> **"내 작업 폴더가 이미 존재하는가?"**

존재하면 **EXPLORE**다.

| | GENERATE | EXPLORE |
|---|---|---|
| 결과 | ZIP 다운로드 | 브라우저에서 프로젝트 내용 보기 |
| 상황 | 새 프로젝트 시작 | 기존 프로젝트 확장 |
| 가져오는 것 | 전부 | 필요한 조각만 |

**GENERATE로 받은 ZIP을 기존 폴더에 덮어쓰면** `.git`·소스·설정이 뒤섞인다. 이미 6개월치 커밋 이력과 배포 파이프라인이 묶여 있는 폴더에 새 프로젝트를 덮어쓰는 셈이다.

비유하면 EXPLORE는 **옷 가게의 피팅룸**이다. 계산대로 가서 사 오는(GENERATE) 대신 일단 입어 보고 필요한 부분만 확인한다.

## Q4. Mustache가 "가볍다"는 말의 정확한 뜻

**배워야 할 문법이 적다는 뜻이다.** 파일 크기나 실행 속도가 아니다.

Mustache는 **로직 없는 템플릿**을 표방한다 — 템플릿 안에 조건식·반복 카운터 같은 프로그래밍 구문을 두지 않는다. 그 결과 배울 것이 사실상 두 가지뿐이다.

- 값 넣기 (`{{name}}`)
- 섹션 열고 닫기 (`{{#videos}}` … `{{/videos}}`)

**이 설계가 주는 실질적 이득**은 [[04-leveraging-templates-to-create-content]]에서 드러난다. 문법이 적으니 템플릿이 **거의 순정 HTML**로 남고, 그래서 데이터 없이도 브라우저로 열어 볼 수 있고 디자이너가 손대도 깨지지 않는다.

**대가**: 템플릿에서 할 수 없는 일이 많다. 계산이나 조건 분기가 필요하면 **컨트롤러나 모델 쪽에서 미리 만들어 넘겨야** 한다. 이건 제약이자 동시에 "표현 계층에 로직을 두지 마라"는 강제이기도 하다.

이름의 유래도 문법의 단순함에서 온다 — 자리표시자 기호 `{{`가 옆으로 누우면 콧수염처럼 보인다.

## Q5. `pom.xml`에 스타터를 넣는 것과 Mustache가 켜지는 것

**서로 다른 시점의 서로 다른 일이다.**

| | 무엇을 하나 | 언제 |
|---|---|---|
| `pom.xml`에 줄 추가 | **클래스패스를 바꾼다** | 빌드 시점 |
| Mustache 뷰 해석이 동작 | 그 클래스패스를 본 **자동 구성의 조건이 참**이 된다 | 애플리케이션 시작 시점 |

`pom.xml`의 한 줄은 **기능을 켜는 명령이 아니다.** "Mustache 클래스들을 클래스패스에 올려라"라는 빌드 지시일 뿐이다. 실제로 Mustache가 Spring MVC의 뷰 인프라에 꽂히는 것은, 시작할 때 자동 구성이 그 클래스들의 존재를 조건으로 읽고 관련 빈을 등록하기 때문이다.

Chapter 1의 **"빌드 시점 → 시작 시점"** 구분이 여기서 그대로 반복된다. [[02-adding-portfolio-components-using-spring-boot-starters]]의 `starter → classpath → 조건 평가 → bean`이 같은 사슬이다.

**실무적 귀결**: 의존성을 넣었는데 기능이 안 돌면 두 층 중 어디가 문제인지 갈라야 한다. 클래스패스에 실제로 올라왔는지(`dependency:tree`)와 조건 평가가 통과했는지(`--debug`)는 다른 확인이다.

## Q6. `spring init` CLI가 웹 UI보다 나은 상황

**핵심은 "사람이 클릭하지 않아도 되는가"다.**

- **여러 마이크로서비스를 같은 규격으로 찍어낼 때.** 서비스가 스무 개면 웹 UI를 스무 번 클릭해야 하고, 그 과정에서 하나쯤 옵션을 다르게 고르는 실수가 난다. 스크립트는 실수하지 않는다.
- **사내 표준 프로젝트 템플릿을 배포할 때.** "우리 팀 새 서비스는 이 명령으로 만든다"를 한 줄로 공유할 수 있다.
- **CI나 자동화 파이프라인에 넣을 때.** 브라우저를 띄울 수 없는 환경이다.

한 문장으로: **웹 UI는 한 번 만들 때, CLI는 반복 가능해야 할 때.**

문서는 `https://docs.spring.io/spring-boot/cli/index.html`에 있다.

## Q7. EXPLORE가 보장해 주지 않는 것

**EXPLORE가 계산하는 것은 "빈 프로젝트 기준의 정답"이다.**

1. **내 프로젝트와의 충돌은 모른다.** 내가 이미 버전을 override했거나 사내 부모 POM을 쓰고 있으면, 복사한 조각이 그 설정과 충돌하는지는 **직접 확인해야 한다.** 피팅룸 거울은 옷이 *내 몸에* 맞는지 보여 주지만, EXPLORE는 그 조합이 *내 기존 프로젝트에* 맞는지는 보여 주지 않는다.
2. **그 기능을 어떻게 쓸지는 알려 주지 않는다.** 스타터 좌표만 정확할 뿐이다. Mustache를 넣어도 템플릿 파일을 어디에 두는지는 별도 지식이다 — [[04-leveraging-templates-to-create-content]].
3. **폐쇄망에서는 쓸 수 없다.** 사내에 Initializr를 띄우거나 CLI를 사내 미러로 설정해야 한다.

그리고 절차 자체의 위험도 있다. **의존성을 더하는 일은 되돌리기가 어렵다.** 클래스패스에 올라온 기술은 조건부 자동 구성을 켜서 예상 밖 동작을 만들 수 있다. "일단 넣고 본다"는 습관이 위험한 이유다.
