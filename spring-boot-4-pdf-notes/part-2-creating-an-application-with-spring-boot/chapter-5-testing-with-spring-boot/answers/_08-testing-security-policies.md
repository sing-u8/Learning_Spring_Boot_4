## Q1. 앞 절이 증명한 것과 증명하지 못한 것

**증명한 것 — "되는 것이 된다"뿐이다.**

```text
  indexPageHasSeveralHtmlForms  (@WithMockUser 있음)
  → "인증된 사용자는 홈 페이지를 볼 수 있다"

  postNewVideoShouldWork        (@WithMockUser 있음)
  → "인증된 사용자는 새 비디오를 만들 수 있다"
```

**증명하지 못한 것 — "안 되는 것이 안 되는가."**

**책이 이 질문에 스스로 답한다**: *"그렇기도 하고, **아니기도 하다.** … 하지만 우리는 **필요한 보안 경로를 전부 덮지 않았다.** 그리고 보안에서는 덮어야 할 경로가 흔히 아주 많다."*

**`@WithMockUser`를 썼다는 사실이 오해를 만든다** — 그것을 쓴 이유는 보안을 검증하려던 게 아니라 **`@WebMvcTest`가 보안 정책을 켠 채로 오기 때문에 통과시키려던 것**이었다([[03-testing-web-controllers-with-mockmvc]]). **같은 애노테이션이 거기서는 장애물을 넘는 도구였고, 여기서는 검증 대상이다.**

## Q2. `SecurityConfig`를 통째로 지우면

```text
  SecurityConfig 를 삭제한다
        │
        ▼
  indexPageHasSeveralHtmlForms  → 통과 ✅   (인증 요구가 없으니 당연히 200)
  postNewVideoShouldWork        → 통과 ✅
        │
        ▼
  테스트는 전부 초록. 애플리케이션은 완전히 열려 있다.
```

**실패하는 것**: 이 절의 **부정 경로 테스트**들 — `unauthUserShouldNotAccessHomePage`, `newVideoFromUnauthUserShouldFail`. 401을 기대했는데 200이 온다.

**통과하는 것**: **긍정 경로 전부.** 인증을 아예 요구하지 않으면 **인증된 사용자는 당연히 통과**한다.

> **그 사실이 뜻하는 바: 정책이 존재한다는 증거는 부정 경로뿐이다.**

**긍정 경로만 쌓은 테스트 스위트는 "보안이 있다"를 증명하지 않는다.** 그것이 증명하는 것은 **"보안이 있더라도 막지 않는다"**뿐이며, **보안이 아예 없을 때도 똑같이 통과**한다.

**이 성질이 커버리지 함정([[02-testing-domain-objects]] Q8)과 같은 모양이다** — **테스트가 있다는 사실이 검증됐다는 뜻이 아니다.** 여기서는 더 나쁘다. **없는 것이 안전하다고 믿게 만든다.**

## Q3. 자물쇠 비유가 깨지는 지점 · 격자의 세 축

**자물쇠는 물리적으로 상태가 하나다(잠김/열림). 하지만 보안 정책은 주체마다 다른 답을 낸다.**

**격자의 세 축**:

```
  주체        ×   경로        ×   HTTP 메서드
  ─────           ─────           ───────────
  미인증          /               GET
  ROLE_USER       /search         POST
  ROLE_ADMIN      /api/**         ...
                  /new-video
                  /delete/**
                  /login
```

> **그래서 "자물쇠 하나를 점검한다"가 아니라 (주체 × 경로 × 메서드) 격자를 점검하는 일이 된다.**

**책이 "역할마다 별도 테스트가 정말 필요하다"고 하는 이유이며, 자물쇠 비유로는 그 조합 폭발이 안 보인다.**

**실무적 귀결**: 격자를 다 채우면 테스트가 **빠르게 늘어난다.** 규칙이 많은 애플리케이션에서는 **파라미터화 테스트로 격자를 표현**하는 편이 현실적이다.

**비유가 맞는 부분은 남는다** — **열쇠로 열리는지만 확인하면 부족하고, 열쇠 없이 안 열리는지도 확인해야 한다**(Q2). 깨지는 것은 **차원의 수**이지 그 통찰이 아니다.

## Q4. 규칙 한 줄이 테스트 세 개를 부르는 이유

```java
.requestMatchers("/", "/search").authenticated()
```

**이 한 줄이 세 주체에 대해 각각 다른 약속을 한다.**

```text
        ├─▶ 미인증 → 거부되는가?              (부정 경로)
        ├─▶ ROLE_USER → 허용되는가?           (긍정 경로)
        └─▶ ROLE_ADMIN → 허용되는가?          (긍정 경로 · 다른 역할)

  규칙 한 줄 = 테스트 세 개
```

**`authenticated()`가 말하는 것**: **인증만 요구하고 특정 역할을 요구하지 않는다.** 책의 표현대로 *"`/`에 접근하려면 인증된 접근이 필요하고 **그 이상은 아니라는 것**"*.

**"그 이상은 아니다"가 검증돼야 하는 명제다.** `ROLE_ADMIN` 테스트가 그것을 검증한다 — **관리자도 막히지 않는다**는 것.

**그래서 정책을 먼저 읽는 것이 테스트 목록을 만드는 방법이다.** 테스트를 생각해 내는 것이 아니라 **규칙에서 기계적으로 유도**한다.

## Q5. 부정 경로에서 `@WithMockUser`가 없는 것이 "설정"인 이유

**애노테이션이 없다는 사실 자체가 미인증 사용자를 시뮬레이션하는 설정이다.**

> **이는 서블릿 컨텍스트에 인증 자격 증명이 저장되지 않는다는 뜻이고, 따라서 미인증 사용자를 시뮬레이션한다.**

**코드에 보이지 않는 것이 의미를 갖는 드문 경우다.**

**그래서 위험하다**: **실수로 `@WithMockUser`를 붙이면 이 테스트는 여전히 통과하지만 아무것도 검증하지 않게 된다.**

```
@WithMockUser 를 실수로 붙임
      ↓
get("/") 가 200 을 돌려준다
      ↓
isUnauthorized() 단언 실패 → 빨간불
```

**— 다행히 이 경우는 시끄럽게 실패한다.** [[07-testing-repositories-with-testcontainers]]의 `replace = NONE` 누락과는 반대다. 거기서는 **조용히 통과**했다. **단언이 부정형이라는 것이 방어가 된다.**

**방어 장치**: 메서드 이름이 그 역할을 한다 — `unauthUserShouldNotAccessHomePage`는 **기대를 아주 분명히 진술한다.** 책의 말대로 *"언젠가 깨졌을 때 이 테스트의 요점이 무엇이었는지 정확히 알 수 있고, 더 빨리 고칠 수 있다."*

> **참고 — 원문의 조판 오류**: 책 p.182의 리스팅은 `void () throws Exception {`으로 인쇄되어 **메서드 이름이 비어 있다.** 바로 다음 문단이 그 이름을 언급하므로 조판 사고다.

## Q6. 401과 403의 이름이 어긋난 지점

| 상황 | 개념 | HTTP 상태 | **이름의 문제** |
|---|---|---|---|
| **로그인을 안 했다** | **인증**(authentication) 실패 | **401 Unauthorized** | **이름은 "인가 안 됨"인데 실제로는 "인증 안 됨"** |
| **로그인은 했는데 권한이 없다** | **인가**(authorization) 실패 | **403 Forbidden** | **이름에 authorization이 없다** |

> **즉 401의 이름이 잘못 붙어 있다.**

**개념의 정의**:
- **인증** = **당신이 누구인지 증명하는 것**
- **인가** = **당신이 무엇을 할 수 있는지**

**책의 Note가 이것을 "용어가 다소 기묘하게 섞여 있다"고 인정한다.** **HTTP 초기 명세의 유산**이며, 지금 와서 바꿀 수 없어 그대로 남아 있다.

**실무적 함의**: **코드가 아니라 개념으로 골라야 한다.** "권한 없음이니까 Unauthorized"라고 생각하면 틀린다. 판별은 **"로그인은 했는가"**다:
```
로그인 안 했다  → 401
로그인은 했다   → 403
```

## Q7. `.with(csrf())`를 넣고도 401이 나야 하는 것이 더 강한 테스트인 이유

**CSRF 토큰이 없어서 실패하는 것이 아니라, 인증이 없어서 실패한다는 것을 증명하기 때문이다.**

**책의 못 박음**: *"**유효한 CSRF 토큰을 포함해 기대되는 값을 전부 제공해도 예상대로 실패한다.**"*

```
토큰을 안 넣었다면 → 실패 원인이 둘로 흐려진다
                     ("CSRF 때문인가, 인증 때문인가?")
토큰을 넣었는데도 실패 → 원인이 하나로 특정된다
```

**즉 실패 원인을 통제 변인으로 좁힌 것이다.** 이 장이 계속 해 온 **"원인 후보 줄이기"**([[02-testing-domain-objects]])가 보안 테스트에서 취하는 형태다.

**끄는 방식과의 차이**:
```text
  방법 A: CSRF 보호를 끈다
    → 테스트는 통과한다
    → 운영과 다른 설정으로 검증한 것이므로, CSRF 관련 회귀를 못 잡는다

  방법 B: .with(csrf()) 로 올바른 토큰을 공급한다
    → 테스트는 통과한다
    → 운영과 같은 설정으로 검증한 것이다

  ▶ 결과는 같아 보이지만 무엇을 증명했는지가 다르다.
```

**책의 Note가 그것을 명시한다** — *"HTML 페이지에 렌더링된 CSRF 토큰이 없는 테스트에서는, **CSRF를 끄지 않으려면** 이 값을 여전히 제시해야 한다."*

**[[03-testing-web-controllers-with-mockmvc]]에서 예고한 그 지점이다** — 거기서 `.with(csrf())`는 **정당한 요청을 통과시키는** 용도였고, 여기서는 **통과시켰는데도 막히는 것을 보이는** 용도다. **같은 도구, 반대 목적.**

## Q8. `is3xxRedirection()`이 `isFound()`보다 나은 이유

| 단언 | **무엇을 고정하나** | 언제 깨지나 |
|---|---|---|
| `status().isFound()` | **302 정확히** | **301·303·307로 바꾸면 깨진다** |
| `status().is3xxRedirection()` | **리다이렉트라는 사실** | **리다이렉트가 아니게 되면 깨진다** |

> **의도는 "리다이렉트한다"이지 "302다"가 아니다.**

**책의 근거**: *"**누군가 나중에 soft redirect에서 hard redirect로 바꿔도 테스트가 덜 깨지게** 만든다."*

**단언 수준의 원칙**: **의도 수준에서 단언하면 구현 변경에 덜 민감해진다.**

**같은 원칙이 이 장 곳곳에 있다**:
- [[05-testing-repositories-with-embedded-databases]]: **`id`를 단언하지 않는다** — 테스트가 통제하지 않는 값
- [[05-testing-repositories-with-embedded-databases]]: **순서를 단언하지 않는다** — `ORDER BY` 없이는 보장 없음
- [[04-testing-services-with-mocks]]: **목을 많이 쓰면 구현 세부에 묶인다**

**공통점**: **필요 이상으로 좁게 단언하면 가짜 실패를 생산한다.** 애플리케이션이 잘못되지 않았는데 빨간불이 뜨는 테스트는 결국 **무시되거나 삭제**된다.

**반대 방향의 한계도 있다** — 너무 넓히면(`status().isNot5xx()` 같은) 아무것도 검증하지 않게 된다. **"의도"의 수준을 찾는 것**이 판단이다. 여기서는 `redirectedUrl("/")`가 함께 있어서, **"리다이렉트한다 + 목적지는 `/`"**로 의도가 정확히 표현된다.

## Q9. `ROLE_USER`와 `ROLE_ADMIN` 테스트가 지금은 같은데도 둘 다 필요한 이유

**지금 통과하는 것이 목적이 아니라 미래의 변경을 감지하는 것이 목적이기 때문이다.**

```java
@WithMockUser(username = "alice", roles = "USER")   // 200 기대
@WithMockUser(username = "alice", roles = "ADMIN")  // 200 기대
//                            ↑ 유일한 차이
```

**정책이 `authenticated()`에서 `hasRole("USER")`로 바뀌는 순간 이 테스트만 빨갛게 된다.**

```
현재:  .requestMatchers("/").authenticated()
       → USER 통과 ✅  ADMIN 통과 ✅

변경:  .requestMatchers("/").hasRole("USER")
       → USER 통과 ✅  ADMIN 실패 ❌  ← 이 테스트가 잡는다
```

**그 변경이 의도된 것이면** 테스트를 고치면 되고, **의도되지 않은 것이면** 버그를 잡은 것이다. **어느 쪽이든 변경이 눈에 보인다.**

> **이 테스트들은 현재를 확인하는 것이 아니라 미래의 변경을 감지하는 장치다.**

**책의 표현**: *"미인증 사용자와 `ROLE_USER` 사용자만 우리 시스템의 사용자인 것은 아니다. **`ROLE_ADMIN`을 가진 관리자도 있다.** 그리고 **각 역할마다 보안 정책이 제대로 구성됐는지 확인하는 별도 테스트가 정말로 있어야 한다.**"*

**"중복 같은데 지워도 되나"에 대한 답**: 지우면 **관리자가 막히게 되는 변경을 아무도 모르게 된다.** 코드가 비슷하다는 것과 **검증하는 명제가 같다는 것**은 다르다 — 여기서는 **주체가 다르므로 명제가 다르다**(Q3의 격자).

**한 가지 주의**: `@WithMockUser(roles = "USER")`는 **내부적으로 `ROLE_` 접두어를 붙여** `ROLE_USER`를 만든다. `roles = "ROLE_USER"`라고 쓰면 **`ROLE_ROLE_USER`**가 되어 정책과 안 맞는다.
