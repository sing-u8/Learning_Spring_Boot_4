## Q1. 테스트 도구를 매번 직접 고르면 무너지는 것

1. **선택 자체가 마찰이 된다.** 무엇을 고를지 **조사하는 시간이 첫 테스트를 쓰기 전에** 소모된다.
2. **버전 조합이 또 하나의 위험이 된다.** [[../chapter-2-creating-web-and-api-applications-with-spring-boot/01-using-start-spring-io-to-build-apps|Ch2]]에서 본 그 문제가 **테스트 영역에서 반복**된다.
3. **가장 나쁜 결과 — 테스트를 안 쓰게 된다.**

> **마찰이 있으면 "나중에 하자"가 되고, 나중은 오지 않는다.**

**3번이 최악인 이유**: 1·2번은 **시간 손실**이지만 3번은 **손실이 안 보인다.** 없는 테스트는 커밋에도 diff에도 나타나지 않는다. **비용을 치르지 않은 것처럼 보이지만** 나중에 버그로 돌아온다.

**그리고 이것은 개인의 게으름이 아니라 구조의 문제다** — 마찰이 있으면 **누구나** 미룬다. 그래서 해법도 결심이 아니라 **마찰을 없애는 것**이다.

## Q2. "테스트를 하기로 선택할 필요조차 없다"의 설계 의도

> **테스트를 선택 사항이 아니라 기본값으로 만든다.**

책: *"우리는 올바른 테스트 키트를 찾아 헤맬 필요가 없고, **테스트를 하기로 선택할 필요조차 없다.** … **테스트는 Spring 팀에게 일급 관심사다.**"*

**"선택할 필요가 없다"의 두 층**:
- **결정을 안 해도 된다** — 무엇을 쓸지 고민할 필요가 없다
- **결정했다는 사실조차 기억할 필요가 없다** — "테스트 의존성 넣었나?"를 확인할 일이 없다

**Q1의 3번을 구조적으로 막는다** — 마찰이 0이면 미룰 이유가 없다.

**Boot 전반의 철학과 같다**: [[../../part-1-the-basics-of-spring-boot/chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1]]의 자동 구성도, [[../chapter-4-securing-an-application-with-spring-boot/02-adding-spring-security-to-the-project|Ch4]]의 "의존성 한 줄로 잠긴다"도 같다 — **흔히 원하는 것을 기본값으로 주고, 원치 않으면 빼게 한다.**

## Q3. 공구함 비유가 깨지는 지점

**공구함은 안 쓰는 공구가 들어 있어도 무겁기만 할 뿐 작업 결과를 바꾸지 않는다.**

**테스트 의존성은 그렇지 않다**:

> **클래스패스에 올라온 라이브러리는 자동 구성 조건을 켜고 테스트 컨텍스트에 빈을 추가한다. 즉 무게가 아니라 동작이 달라진다.**

**구체적으로 무엇이 바뀌나**:
- **테스트 컨텍스트가 켜는 빈이 늘어난다** → 시작이 느려진다
- **무엇이 왜 켜졌는지 읽기 어려워진다** → 웹 테스트인데 DB 인프라가 떠 있으면 원인 추적이 어렵다
- **의도치 않은 자동 구성이 테스트 결과를 바꿀 수 있다**

**이것이 Boot 4가 굳이 나눈 이유이며, 무게 비유로는 설명되지 않는 부분이다.**

**[[../../part-1-the-basics-of-spring-boot/chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1의 Boot 4 모듈화]]와 같은 논리다** — 클래스패스에 있다는 것이 **조건 평가의 입력**이므로, 목록이 좁을수록 무엇이 켜지는지가 명확해진다.

## Q4. AssertJ와 Hamcrest가 둘 다 필요한 이유

**문체가 다르고, 어떤 API는 특정 문체를 요구한다.**

| | **AssertJ** | **Hamcrest** |
|---|---|---|
| 문체 | **값을 받아 점으로 잇는다** | **조건을 객체로 만들어 넘긴다** |
| 예 | `assertThat(x).isEqualTo(y)` | `containsString("...")` |
| 강점 | 읽기 쉽고 실패 메시지가 자세하다 | **조건 자체를 값으로 다룰 수 있다** |

**구체적 API 예 — MockMvc**:

```java
.andExpect(content().string(containsString("alice")))
                            ↑ 조건을 인자로 요구한다 → Hamcrest
```

**`content().string(...)`은 matcher를 인자로 받는다.** AssertJ의 `assertThat(...)`은 **단언을 즉시 수행**하므로 여기에 넣을 수 없다. **조건을 인자로 요구하는 API를 만나면 Hamcrest다.**

**그래서 [[03-testing-web-controllers-with-mockmvc]]에서 한 테스트 메서드 안에 둘이 함께 나타난다** — MockMvc 체인에는 Hamcrest, 그 뒤 결과 객체 검증에는 AssertJ.

**중복이 아니라 역할 분담이다.**

## Q5. JUnit 5 → 6이 4 → 5보다 훨씬 싼 이유

> **JUnit 6이 같은 프로그래밍 모델과 패키지 구조를 유지하기 때문이다.**

| 전환 | 무엇이 바뀌었나 | 비용 |
|---|---|---|
| **4 → 5** | **패키지가 통째로** 바뀌고 `@Before`가 `@BeforeEach`가 됐다 | **높다** |
| **5 → 6** | **모델과 패키지가 유지된다** | **거의 없다** |

**4 → 5가 아팠던 이유가 정확히 그 반대였다** — `org.junit.Test`와 `org.junit.jupiter.api.Test`는 **다른 타입**이라 **import부터 바뀐다.**

**5 → 6은 그런 종류의 이동이 아니다.** *"JUnit 5용으로 작성된 대부분의 테스트는 수정 없이 계속 동작한다."*

**교훈**: **메이저 버전 번호가 비용을 말해 주지 않는다.** 무엇이 바뀌었는지를 봐야 한다.

**JUnit 4의 위치**: **레거시.** Boot 4에 **기본 포함되지 않으며** 필요하면 명시적으로 설정해야 한다.

## Q6. 스타터를 나눈 이유가 "배포물 크기"가 아닌 근거

**전부 `test` scope이기 때문이다.**

**`test` scope는 운영 산출물에 안 들어간다.** 그래서 **테스트 도구를 많이 넣는 것이 배포물을 무겁게 만들지 않는다.**

**진짜 이유는 Q3의 그것**:

> **테스트 컨텍스트가 무엇을 켜는지가 달라지기 때문이다.**

**웹 테스트에 데이터 접근 인프라까지 딸려 오면** 테스트가 느려지고, 무엇이 왜 켜졌는지 읽기 어려워진다.

**즉 나눈 목적은 "가볍게"가 아니라 "명확하게"다.** 배포 크기는 애초에 문제가 아니었다.

**대가**: **필요한 것을 안 넣으면 안 켜진다.** Boot 3에서 올라온 프로젝트가 **"예전엔 되던 슬라이스 애노테이션이 없다"**고 느끼는 원인이다.

## Q7. 네 관심사를 대표하는 애노테이션

| 관심사 | 애노테이션 | 등장 노트 |
|---|---|---|
| **웹 계층** | **`@WebMvcTest`** (+ `MockMvc`) | [[03-testing-web-controllers-with-mockmvc]] |
| **데이터 접근** | **`@DataJpaTest`** | [[05-testing-repositories-with-embedded-databases]] |
| **보안** | **`@WithMockUser`**, `csrf()` | [[08-testing-security-policies]] |
| **컨테이너** | **`@Testcontainers`**, `@ServiceConnection` | [[06-adding-testcontainers]] |

**앞의 둘은 "슬라이스 애노테이션"이다** — 애플리케이션의 **한 층만 띄운다.**

**뒤의 둘은 성격이 다르다** — 보안 도구는 **테스트 실행 문맥**(누구로 요청하는가)을 조작하고, Testcontainers는 **외부 자원**(진짜 DB)을 붙인다.

**이 넷이 이 장의 지도다** — 도메인([[02-testing-domain-objects]]) 다음으로 바깥으로 나가며 각 층을 다룬다.
