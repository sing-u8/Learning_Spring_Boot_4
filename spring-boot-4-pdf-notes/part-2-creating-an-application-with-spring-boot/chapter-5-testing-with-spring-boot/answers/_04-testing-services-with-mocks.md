## Q1. 원문 제목이 오해를 부르는 이유

**원문 제목은 *Testing data repositories with mocks*(목으로 데이터 리포지토리 테스트하기)인데, 실제로 테스트하는 대상은 리포지토리가 아니라 `VideoService`이고 리포지토리는 모킹되는 쪽이다.**

```
제목이 읽히는 대로:   테스트 대상 = 리포지토리,  도구 = 목
실제:                테스트 대상 = VideoService, 목이 되는 것 = 리포지토리
```

> **대상과 도구가 뒤바뀌어 읽힌다.**

**이 노트의 파일 이름이 `04-testing-services-with-mocks`인 이유**가 그것이다. 원문 제목을 그대로 따라가면 **"리포지토리를 테스트했으니 쿼리도 검증됐다"**는 잘못된 결론에 이르기 쉽고, 그것이 정확히 Q8이 부정하는 것이다.

**진짜 리포지토리 테스트는 [[05-testing-repositories-with-embedded-databases]]와 [[07-testing-repositories-with-testcontainers]]에 있다.**

## Q2. 진짜 `VideoRepository`를 쓰면 무너지는 세 지점

1. **느려진다.** [[02-testing-domain-objects]]의 **49밀리초**가 **수백 밀리초 또는 수 초**가 된다.
2. **실패 원인이 넓어진다.** 빨갛게 되면 **서비스 로직인지, 쿼리인지, 연결인지** 알 수 없다.
3. **환경에 의존한다.** **데이터베이스가 떠 있지 않은 CI**에서는 아예 못 돌린다.

> **`VideoService` 빈을 단위 테스트 방식으로 테스트하려면 바깥 영향으로부터 격리해야** 하고, 그 방법이 **모킹**이다.

**2번이 이 장 전체를 관통하는 원리다** — [[02-testing-domain-objects]]에서 "안쪽부터 테스트해 원인 후보를 지운다"고 했고, [[03-testing-web-controllers-with-mockmvc]]에서 `controllers=`로 슬라이스를 좁혔다. **여기서는 협력자를 가짜로 바꿔 좁힌다.** 같은 목표의 세 번째 수단이다.

## Q3. 스턴트 대역 비유가 깨지는 지점

**스턴트 대역은 실제로 그 동작을 수행한다. 다만 다른 사람이 할 뿐이다.**

**그런데 목은 아무것도 수행하지 않고 미리 정해 둔 답만 돌려준다.**

> **그래서 "대역이 잘 해냈다"가 "진짜도 할 수 있다"의 근거가 되지 못한다.**

**책의 Note가 경고하는 것이 정확히 이 지점이다** — *"주어진 테스트 케이스가 **목 자신 말고는 아무것도 테스트하지 않을 위험**."*

**구체적으로**: `when(repository.findAll()).thenReturn(List.of(v1, v2))`는 **내가 정한 값**이다. 진짜 `findAll()`이 그 값을 준다는 보장이 **전혀 없다.** 쿼리가 틀렸어도, 매핑이 틀렸어도, 방언이 틀렸어도 **이 테스트는 초록이다.**

**"목을 썼으니 이 테스트는 믿을 만하다"는 정확히 반대의 위험을 안는다.**

## Q4. Spring 컨텍스트가 하나도 없는 것이 가능한 이유

**생성자 주입 덕분이다.**

```java
@BeforeEach
void setUp() {
    this.service = new VideoService(repository);   // ← 그냥 new
}
```

**`@SpringBootTest`도, 슬라이스 애노테이션도, 애플리케이션 컨텍스트도 없다.**

[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04c-injecting-dependencies-through-constructor-calls|Ch2]]에서 **"테스트에서 `new HomeController(가짜서비스)`로 만들 수 있다"**고 한 것이 **여기서 실제로 회수된다.**

> **필드 주입이었다면 이 한 줄이 성립하지 않는다.** — 리플렉션으로 필드를 채워 줄 컨테이너가 필요해진다.

**그리고 컨텍스트가 없다는 것이 장점이다**:
- **가장 빠르다** — 컨텍스트 기동 비용이 0
- **실패 범위가 가장 좁다** — Spring 설정이 원인일 가능성이 없다

**"Spring이 안 나오는데 Spring 테스트인가"** — 이 테스트가 검증하는 것은 **Spring이 아니라 내 비즈니스 로직**이다. **Spring을 안 쓰고도 테스트할 수 있게 만들어 준 것 자체가 Spring의 설계가 준 이점**이다.

## Q5. `given`·`when`·`then`이 읽기 쉬운 것 외에 주는 이득

**테스트 냄새를 드러내는 틀이 된다.**

책의 Tip이 그것을 말한다:

> **단언이 너무 많고 방향이 너무 여러 갈래로 뻗는다면, 그 테스트를 여러 메서드로 쪼개야 한다는 신호일 수 있다.**

```
// given   ← 상황을 만든다 (스텁 설정, 데이터 준비)
// when    ← 딱 한 가지 행동
// then    ← 기대를 단언

▶ `when` 이 두 개면 이미 테스트가 두 개다.
▶ 주석 자리를 못 정하겠으면 그 테스트는 초점이 흐린 것이다.
```

**책은 그 이유도 밝힌다** — *"테스트 케이스를 사방으로 흩어지게 쓸 때가 있다. 메서드를 given·when·then으로 흐르게 만들면 **더 조리 있고 초점이 분명해진다**."*

**읽기 쉬움 자체도 개발자만의 이득이 아니다** — *"소프트웨어 개발자만이 아니라, **코드 작성보다 고객 의도를 포착하는 데 집중하는 비즈니스 분석가나 다른 팀원들**도 읽을 수 있다."*

**[[02-testing-domain-objects]]의 "쪼개는 이유"와 이어지되 근거가 다르다**:
- 거기서는 **실패가 가려진다** (기술적 근거)
- 여기서는 **의도가 흐려진다** (가독성 근거)

## Q6. `any(VideoEntity.class)`가 필요한 이유

**서비스가 내부에서 `NewVideo`를 `VideoEntity`로 변환해 저장하므로, 테스트가 그 인스턴스를 미리 손에 쥘 수 없다.**

```java
given(repository.saveAndFlush(any(VideoEntity.class)))
    .willReturn(new VideoEntity("alice", "name", "des"));

service.create(new NewVideo("name", "des"), "alice");
//      ↑ 인자는 NewVideo 다.
//        VideoEntity 는 서비스 안에서 만들어지므로
//        테스트에는 그것을 가리킬 참조가 없다
```

**정확히 같은 객체를 지정할 수 없으니 "그 타입이면 무엇이든"으로 넓힌다.**

**대가가 있다** — **잘못된 인자로 불려도 통과한다.** 서비스가 `username`을 안 넣어도, `name`과 `description`을 바꿔 넣어도 `any(VideoEntity.class)`는 일치한다.

> **인자를 특정할 수 있으면 특정하는 편이 낫다.**

**여기서는 어떻게 보완했나**: **반환값을 단언**했다 — `getName()`, `getDescription()`, `getUsername()` 세 줄. 인자를 못 좁히는 대신 **결과를 확인**한 것이다. `ArgumentCaptor`로 실제 인자를 붙잡는 방법도 있다.

## Q7. `delete()` 테스트에서 상태 검증이 불가능한 이유

**`service.delete(1L)`가 아무것도 돌려주지 않기 때문이다.**

```
단언할 반환값이 없다.
그리고 리포지토리가 목이므로 실제로 지워지지도 않는다.

▶ "삭제가 일어났다"의 유일한 증거는
   repository.delete(entity) 가 불렸다는 사실이다.
```

**책의 설명**: *"**서비스의 동작이 더 복잡하므로 미리 정해 둔 데이터로는 안 된다.** 대신 서비스 내부에서 **호출된 메서드들을 검증**하는 쪽으로 전환해야 한다."*

**`verify`가 두 줄인 것도 의미가 있다**:

```java
verify(repository).findById(1L);   // 먼저 찾고
verify(repository).delete(entity); // 그다음 지운다
```

**이 서비스의 절차가 두 단계**이므로 **두 단계가 모두 일어났는지**를 각각 확인한다.

**판별 기준**:
```
반환값이 있는가?
   ├─ 예 → 상태 검증  (when(...).thenReturn(...) + assertThat(결과))
   └─ 아니오 → 행위 검증  (verify(...))
```

[[03-testing-web-controllers-with-mockmvc]]의 POST 테스트도 **같은 이유**로 `verify()`였다 — 리다이렉트만 돌려주므로 단언할 것이 없었다.

**그리고 이 둘은 배타적이지 않다** — 책의 Note: *"**한 가지 테스트 전략만 고를 필요는 없다.**"* 같은 `VideoRepository` 목이 어떤 테스트에서는 **스텁 용법**(반환값 단언), 다른 테스트에서는 **목 용법**(호출 검증)이다. **판별은 객체의 종류가 아니라 그 테스트가 무엇을 단언하는가에 있다.**

## Q8. 전부 통과해도 여전히 모르는 것

**쿼리가 옳은지 전혀 모른다.**

**목이 돌려주는 값은 내가 정한 값**이므로 다음이 전부 검증 밖이다:
- `findByNameContainsIgnoreCase`가 **엉뚱한 SQL**을 만들고 있어도 통과
- 엔티티 **매핑**이 틀렸어도 통과
- 운영 데이터베이스의 **방언**에서 안 도는 쿼리여도 통과
- 데이터베이스 **연결 설정**이 아예 없어도 통과

> **그래서 이 장이 여기서 멈추지 않는다.**

**책의 Note가 그 지도다**:

| | **단위 테스트** | **통합 테스트** |
|---|---|---|
| 속도 | **빠르다** — 외부 영향이 전부 정해 둔 답으로 바뀐다 | **그만큼 빠르지 않다** |
| 확신 | **목 자신 말고는 아무것도 테스트하지 않을 위험** | **높인다** — 더 현실에 가깝다 |
| 비용 | 낮다 | **설계와 준비가 더 든다** |

**"둘 중 하나를 고르는 문제가 아니다" — 어느 쪽만 쌓아도 확신에 구멍이 남는다.**
- **단위만** → 쿼리·매핑·방언이 틀려도 전부 초록
- **통합만** → 느려서 안 돌리게 되고, 실패해도 원인이 안 좁혀진다

**남는 대가 하나 더**: 목을 많이 쓸수록 테스트가 **구현 세부에 묶인다.** `verify(repository).findById(1L)`은 서비스의 내부 절차를 **고정**하므로, **동작이 같아도 구현을 바꾸면 테스트가 깨진다.**
