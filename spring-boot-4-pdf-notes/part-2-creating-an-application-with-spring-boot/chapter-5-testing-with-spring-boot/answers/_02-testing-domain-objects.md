## Q1. 컨트롤러부터 테스트하면 곤란해지는 것

**실패했을 때 원인 후보가 너무 많다.**

```
컨트롤러 테스트 실패
      ├─ 요청 매핑이 틀렸나?
      ├─ 보안 정책에 막혔나?
      ├─ 서비스 호출이 잘못됐나?
      ├─ 리포지토리 쿼리가 틀렸나?
      └─ 도메인 객체의 생성자가 필드를 잘못 넣었나?  ← 이게 원인이어도 여기서는 안 보인다
```

> **가장 안쪽이 틀렸는데 가장 바깥에서 발견하면 원인까지 거슬러 올라가는 데 시간이 든다.**

**반대로 도메인 테스트가 먼저 통과해 있으면 그 후보가 목록에서 지워진다.** 후보를 하나씩 지우는 것이 디버깅이고, **안쪽부터 테스트하는 것은 그 지우기를 미리 해 두는 일**이다.

**그리고 도메인 테스트는 가장 싸다** — **49밀리초.** 컨테이너도 컨텍스트도 없이 `new`로 만들어 확인한다.

**이 장 전체의 순서가 그래서 안에서 바깥이다** — 도메인 → 컨트롤러 → 서비스 → 리포지토리 → 보안.

## Q2. 콘크리트 강도 시험 비유가 깨지는 지점

**콘크리트 강도는 한 번 재면 그 값이 변하지 않는다. 도메인 객체는 기능이 늘 때마다 바뀐다.**

**이 장의 `VideoEntity`가 그 증거다** — [[../chapter-3-querying-for-data-with-spring-boot/02a-entities-in-jpa|Ch3에서 만든 것]]과 **이미 다르다.**

```
Ch3:  VideoEntity(name, description)
Ch4:  VideoEntity(username, name, description)   ← 보안 요구가 도메인을 바꿨다
```

> **한 번 하고 끝나는 검사가 아니라 코드와 함께 자라는 검사이며, 그래서 책이 "테스트는 결코 끝나지 않는다"고 말한 것이다.**

**실무적 귀결**: 도메인 테스트는 **가장 자주 고치는 테스트**이기도 하다. 필드가 늘면 단언도 늘어야 한다. **그 유지 비용을 감수할 만큼 값이 있는가**가 판단 기준이고, 답은 "있다" — Q1의 후보 지우기 때문이다.

## Q3. `assertThat(entity.getId()).isNull()`이 검증하는 것

**단순한 초기값이 아니라 "이 객체가 아직 저장되지 않았다"는 JPA의 계약이다.**

[[../chapter-3-querying-for-data-with-spring-boot/02a-entities-in-jpa|Ch3]]에서 본 대로 **`id`가 `null`이면 `save()`가 INSERT를 낸다.** `null`이 아니면 UPDATE다.

**이 한 줄이 검증하는 것**:
- 새로 만든 엔티티가 **INSERT 경로로 간다**
- 생성자가 `id`를 **실수로 채우지 않았다**
- `@GeneratedValue`가 채울 자리를 **비워 두었다**

**틀리면 무슨 일이 생기나**: 생성자가 `id`에 무언가를 넣으면 **모든 새 객체가 UPDATE로 처리된다.** 그 키의 행이 없으므로 **아무것도 저장되지 않거나 예외가 난다.** **증상이 저장 실패로 나타나므로** 생성자를 의심하기 어렵다.

**나머지 세 단언은 다른 일을 한다** — **생성자 인자가 올바른 필드에 들어갔는가.** 3-인자 생성자에서 `username`과 `name`의 순서가 바뀌는 것은 **컴파일러가 못 잡는 실수**다(둘 다 `String`).

## Q4. 49밀리초라는 숫자가 왜 중요한가

**자주 돌릴 수 있다는 뜻이다.**

**테스트의 가치는 실행 빈도에 비례한다.** 아무리 좋은 테스트도 **안 돌리면 0**이다.

| 실행 시간 | 실제 행동 |
|---|---|
| **49ms** | **파일을 저장할 때마다** 돌려도 부담이 없다 |
| 5초 | 커밋 전에 한 번 |
| 5분 | CI에 맡기고 로컬에서는 안 돌린다 |

**피드백 주기가 짧을수록 실수와 발견 사이의 거리가 짧다.** 방금 고친 줄이 원인이라는 것을 안다.

**왜 이렇게 빠른가**: **컨테이너도 컨텍스트도 없다.** **Spring이 전혀 관여하지 않는다.**

**대비**: [[07-testing-repositories-with-testcontainers]]에서 볼 숫자는 **401ms / 35ms / 24ms**다 — 첫 테스트가 컨테이너 기동을 포함한다. **두 자릿수 밀리초와 세 자릿수는 다른 종류의 테스트**다.

## Q5. 테스트 이름에 `should`를 넣으면

**이름이 명세 문장이 된다.**

```
toStringShouldAlsoBeTested        → "toString 도 테스트되어야 한다"
newVideoEntityShouldHaveNullId    → "새 VideoEntity 는 null id 를 가져야 한다"
```

> **실패 목록만 봐도 "무엇이 지켜지지 않았는가"가 읽힌다.**
> **반대로 `testToString1` 같은 이름은 실패했을 때 코드를 열어 봐야 한다.**

**차이가 나타나는 순간**: CI가 **"3개 실패"**를 보고할 때. 이름이 명세면 **보고서만 보고 무엇이 깨졌는지** 안다.

**`should`가 문법 장식이 아닌 이유**: 그 단어가 **주어와 서술어를 강제**한다. **무엇이 어떠해야 하는지**가 문장 구조로 나온다.

**테스트 메서드 이름은 기술적 요구가 아니라 정보를 담을 기회다** — 컴파일러는 이름을 안 본다. **오직 사람을 위한 것**이므로 최대한 유용하게 짓는다.

## Q6. 단언을 여러 메서드로 쪼개는 기술적 근거

**JUnit은 단언이 실패하면 그 메서드를 즉시 중단하기 때문이다.**

```java
@Test void everything() {
    assertThat(a).isEqualTo(1);   // ← 여기서 실패하면
    assertThat(b).isEqualTo(2);   // ← 이 줄은 실행조차 안 된다
    assertThat(c).isEqualTo(3);   // ← 이것도
}
```

> **한 실패가 다른 실패를 가리지 않게 하기 위해.**

**결과**: 한 번 돌려서 **문제를 하나만 알게 된다.** 세 개가 틀렸으면 **세 번 왕복**해야 한다.

**쪼개면**: 한 번 돌려서 **세 개가 전부 실패로 보고**된다. **문제의 전체 크기를 즉시 안다.**

**부수 이점**: 메서드마다 이름이 붙으므로 Q5의 명세 효과도 함께 온다.

**대안도 있다** — AssertJ의 `SoftAssertions`나 JUnit의 `assertAll`은 한 메서드에서 여러 단언을 모아 실행한다. 다만 **이름이 하나뿐**이라 명세 효과는 잃는다.

## Q7. 단언 없는 테스트가 100% 커버리지를 내는 이유

**커버리지는 "이 줄이 실행됐다"만 측정하기 때문이다.**

```java
@Test void 아무것도검증하지않는테스트() {
    VideoEntity e = new VideoEntity("a", "b", "c");
    e.getId(); e.getName(); e.getUsername(); e.getDescription();
    e.toString();
    // 단언 없음
}
▶ 커버리지: 초록 (전부 실행됨)
▶ 검증된 것: 없음 (예외만 안 나면 통과)
```

**커버리지 도구는 "실행 여부"를 세지 "기대와 비교했는가"는 세지 않는다.**

> **커버리지는 "테스트가 닿지 않은 곳"을 찾는 데 좋다. "테스트가 충분하다"의 근거로 쓰면 틀린다.**

**올바른 사용법**: **빨간 줄을 찾는 도구**다. "여기는 아무 테스트도 안 지나간다"는 **확실한 정보**다. 초록은 **"지나갔다"까지만** 말한다.

**책의 예도 그렇게 쓰인다** — `VideoEntity`가 **`protected` 무인자 생성자만 빼고 전부 커버**됐고, **그 빨간 줄이 다음에 쓸 테스트를 알려 준다.**

## Q8. 커버리지를 목표 숫자로 관리하면

**숫자를 올리는 가장 싼 방법이 "단언 없는 테스트를 쓰는 것"이 된다.**

```
"커버리지 80% 이상" 이라는 목표
      ↓
가장 빠른 달성 방법 = 검증하지 않고 실행만 하는 테스트 (Q7)
      ↓
숫자는 오르고 안전성은 그대로
      ↓
그리고 이제 "테스트가 있다"고 믿게 된다   ← 목표 전보다 나쁘다
```

**마지막 줄이 핵심이다.** 없는 테스트는 **없다는 것을 알지만**, 검증하지 않는 테스트는 **있다고 믿게 만든다.**

**다른 왜곡들**:
- **테스트하기 쉬운 코드만 테스트한다** — getter/setter 커버리지를 올리고 복잡한 분기는 둔다
- **커버리지가 낮은 코드를 지운다** — 결과는 좋을 수 있지만 동기가 이상하다

**Goodhart의 법칙의 사례다** — 측정치가 목표가 되면 좋은 측정치이기를 그친다.

**대안**: 커버리지는 **보고 참고하는 지표**로 두고 **빨간 줄을 볼 때** 쓴다. 게이트로 쓰려면 **"내려가지 않게"** 정도가 안전하다.
