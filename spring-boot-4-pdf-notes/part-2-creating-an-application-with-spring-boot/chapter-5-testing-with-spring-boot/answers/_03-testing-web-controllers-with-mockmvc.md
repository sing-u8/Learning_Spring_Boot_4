## Q1. 컨트롤러를 `new`로 만들어 직접 부르면 검증 안 되는 것

| 검증 안 되는 것 | 왜 |
|---|---|
| **`@GetMapping("/")`이 실제로 그 경로에 매핑되는가** | 메서드를 직접 부르면 **매핑을 안 거친다** |
| **HTTP 상태 코드가 200인가** | 반환값은 **뷰 이름 문자열**일 뿐 |
| **뷰 이름이 실제 HTML로 렌더링되는가** | **템플릿 엔진을 안 거친다** |
| **보안 정책이 이 경로를 막는가** | **필터 체인을 안 거친다** |
| **폼 파라미터가 객체로 바인딩되는가** | 인자를 **내가 직접 만들어 넘겼다** |
| **`redirect:/`가 302로 나가는가** | 문자열 비교로 끝난다 |

> **즉 애노테이션이 하는 일 전부가 검증 밖에 있다.**

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/02-creating-a-spring-mvc-web-controller|Ch2]]에서 "중요한 부분은 애노테이션이다"라고 했는데, 직접 호출은 정확히 그 부분을 건너뛴다.**

**책의 표현**: *"우리가 원하는 것의 일부는 **Spring MVC의 기계를 통과하는 것**이다."*

## Q2. 비행 시뮬레이터 비유가 깨지는 지점

**좋은 시뮬레이터는 공기역학까지 흉내 내지만, MockMvc는 네트워크 계층을 아예 통과하지 않는다.**

**검증되지 않는 것**: 실제 소켓 연결, HTTP 텍스트 파싱, 서블릿 컨테이너의 **타임아웃·커넥션 한도·헤더 인코딩.**

> **"서버를 안 띄운다"는 장점과 "서버를 안 띄운다"는 한계가 같은 사실이다.**

| | 장점 | 한계 |
|---|---|---|
| 서버를 안 띄운다 | **빠르다**(1초 미만), 포트 충돌 없음, 병렬 실행 가능 | **네트워크 계층 문제를 못 잡는다** |

**그래서 MockMvc가 전부 통과해도 실제 배포에서 다르게 동작할 수 있다.**

**필요하면 다른 도구를 쓴다** — `@SpringBootTest(webEnvironment = RANDOM_PORT)`와 실제 HTTP 클라이언트. **더 느리지만 네트워크를 거친다.**

## Q3. `@WebMvcTest(controllers = ...)`에서 `controllers`를 지정하는 이유

**이 스위트를 `HomeController` 하나로 제한하기 위해서다.**

**안 하면**: **애플리케이션의 모든 컨트롤러와 웹 인프라를 다 띄운다.**
- **느려진다**
- **실패 원인도 넓어진다** — 다른 컨트롤러의 문제가 이 테스트를 깨뜨릴 수 있다
- **협력자를 전부 채워야 한다** — 모든 컨트롤러의 의존성에 `@MockitoBean`이 필요하다

**이것이 테스트 슬라이스다** — 애플리케이션 전체가 아니라 **특정 계층만, 그 안에서도 지정한 것만** 띄운다.

**[[02-testing-domain-objects]]의 원리가 이어진다** — **원인 후보를 좁히는 것**이 테스트 설계의 목표다. 슬라이스는 그 좁히기를 **컨텍스트 수준에서** 한다.

> **Boot 4 주의**: `@WebMvcTest`는 이제 **`org.springframework.boot.webmvc.test.autoconfigure`**에서 import한다. 모듈 세분화의 결과다.

## Q4. 컨트롤러는 진짜인데 왜 `@MockitoBean`이 필요한가

**컨트롤러가 진짜이기 때문에 협력자를 요구한다.**

> **MockMvc가 컨트롤러를 mock한다 → 아니다. 컨트롤러는 진짜다. mock되는 것은 서블릿 컨테이너 쪽이다.**

**이름 때문에 가장 자주 오해되는 지점이다.**

**슬라이스는 웹 계층만 켠다** → **진짜 `VideoService` 빈이 없다** → **없으면 컨트롤러 생성 자체가 실패한다.**

```
@WebMvcTest 가 켜는 것:  DispatcherServlet, 컨트롤러, 필터 체인, 템플릿 엔진
안 켜는 것:              서비스, 리포지토리, 데이터소스
                          ↑ 그런데 HomeController 생성자가 VideoService를 요구한다
```

**`@MockitoBean`이 가짜를 만들어 컨텍스트에 넣는다** — 이것이 **빈 오버라이드**다.

> **Boot 4 주의**: `@MockBean`은 **제거됐다.** 이름만 바뀐 것이 아니라 **Spring Framework의 빈 오버라이드 모델로 옮겨 갔고**, `@Configuration` 클래스에는 못 쓴다는 제약이 붙는다.

## Q5. Hamcrest와 AssertJ가 한 메서드에 함께 있는 이유

**API가 요구하는 형태가 다르기 때문이다.**

```java
.andExpect(content().string( containsString("Username: user") ))
                             └──────┬──────┘
                              Hamcrest matcher
                     "조건을 객체로 만들어 인자로 넘긴다"
                     → andExpect 가 matcher 를 요구하기 때문

assertThat(html).contains("<form action=\"/logout\"", ...)
└──────┬──────┘
     AssertJ
"값을 받아 점으로 잇는다"
→ 이미 문자열을 손에 넣은 뒤라 자유롭게 쓸 수 있다
```

**갈림점은 "값이 손에 있는가"다.**
- **MockMvc 체인 안** — 값이 아직 없다. **조건을 미리 만들어 넘겨야** 한다 → Hamcrest
- **`.andReturn()` 이후** — 문자열을 받았다. **바로 단언할 수 있다** → AssertJ

**[[01-junit-6-and-focused-test-starters]]에서 "둘은 중복이 아니다"라고 한 이유가 이 코드에 그대로 있다.**

**세 번째 문체도 이 파일에 있다** — `verify(videoService).create(...)`는 **Mockito**다. **값이 아니라 호출을 본다** → Q7.

## Q6. `@WithMockUser`를 빼면

**401이 나온다.**

> **`@WebMvcTest`는 Spring Security 정책을 켠 채로 온다.**

이 애노테이션이 없으면 **요청이 필터 체인에 막혀** 컨트롤러에 도달하지 못한다. **인증을 시뮬레이션해야** 통과한다.

**"`@WebMvcTest`는 보안을 끈다"는 오해가 흔하다** — **켠다.** 그래서 `@WithMockUser` 없이 요청하면 **"왜 200이 아니지?"**로 헤매게 된다.

**`@WithMockUser`가 만드는 것**: 사용자 이름 `user`, 권한 `ROLE_USER`(기본값)로 **로그인한 사용자를 시뮬레이션**한다. 그래서 이 절의 테스트가 `"Username: user"`와 `"Authorities: [ROLE_USER]"`를 단언할 수 있다.

**반대로 이 성질을 정면으로 이용하는 것이 [[08-testing-security-policies]]다** — **`@WithMockUser`를 일부러 빼서** "막히는지"를 검증한다. 같은 성질이 한쪽에서는 함정이고 다른 쪽에서는 도구다.

## Q7. POST 테스트에서 `verify()`를 쓰는 것이 맞는 이유

**컨트롤러가 리다이렉트만 돌려주기 때문이다.**

```
POST /new-video
      ↓
컨트롤러가 videoService.create(...) 호출  ← 여기가 이 메서드의 전부
      ↓
302 리다이렉트

▶ 응답 본문에 저장이 일어났다는 증거가 없다.
▶ 그리고 videoService는 가짜이므로 진짜로 저장되지도 않는다.
```

> **"위임이 제대로 일어났는가"가 이 컨트롤러 메서드의 전부이고, 그것을 확인할 방법은 `verify()`뿐이다.**

**이것이 행위 검증이다** — **반환값 대신 어떤 메서드가 어떤 인자로 불렸는지** 확인한다.

**`verify(videoService).create(new NewVideo("new video", "new desc"), "user")`가 한 번에 검증하는 것**:
- 서비스가 **불렸다**
- **폼 파라미터가 `NewVideo`로 바인딩됐다** — MockMvc가 넣어 준 값이 그대로 왔다
- **`@WithMockUser`의 사용자 이름이 인자로 전달됐다** — [[../chapter-4-securing-an-application-with-spring-boot/06b-taking-ownership-of-data|Ch4의 소유권 흐름]]이 동작한다

**앞 테스트와 성격이 다르다** — 거기서는 **응답 내용**을, 여기서는 **협력자 호출**을 본다. 자세한 구분은 [[04-testing-services-with-mocks]].

## Q8. `.with(csrf())`가 CSRF를 끄는 것이 아니라는 말

> **반대다. CSRF 보호를 켠 채로 올바른 토큰을 공급하는 것이다.**

**끄는 것과 통과하는 것은 다르다.**

| | 끈다 | **토큰을 공급한다** |
|---|---|---|
| CSRF 필터 | 동작 안 함 | **동작한다** |
| 검증하는 것 | 없음 | **정당한 요청이 통과하는가** |
| 놓치는 것 | **CSRF 설정이 깨져도 모른다** | — |

**즉 `.with(csrf())`는 "공격이 아니라 정당한 요청임을 시뮬레이션"한다.** 실제 브라우저가 폼의 hidden input으로 보내는 그 토큰을 테스트가 대신 넣는 것이다.

**끄는 방식이었다면 무엇을 잃나**: CSRF 설정을 실수로 망가뜨려도 **테스트가 통과한다.** 방어가 있는 것처럼 보이지만 검증되지 않는다.

**이 차이는 [[08-testing-security-policies]]에서 다시 나온다** — 거기서는 **`.with(csrf())`를 넣고도 401이 나야 하는** 테스트가 등장한다. 토큰이 있어도 **인증이 없으면 막힌다**는 것을 증명하려는 것이고, 그것이 더 강한 테스트다.
