## Q1. 자동화 이전에 실제 DB 테스트가 얼마나 비쌌나

> **실제 데이터베이스를 상대로 테스트하는 것은 늘 시간과 자원 양쪽에서 비쌌다.**

**책이 그린 절차**:
1. **애플리케이션을 띄우고**
2. **손으로 쓴 스크립트를 손에 쥐고**
3. **애플리케이션의 여러 페이지를 클릭해 가며** 동작을 확인한다

**그리고 그것이 직업이었다** — *"**이런 테스트 문서를 쓰고, 변경이 나올 때마다 갱신하고, 따로 마련된 테스트 랩에서 애플리케이션에 실행하는 것만이 일인 테스트 엔지니어 팀**을 둔 회사들이 있다."*

> **새 기능이 이 체계를 통과하기를 일주일 기다린다고 상상해 보라.**

**이 숫자가 [[02-testing-domain-objects]]의 49밀리초와 대비되는 지점이다.** 같은 "검증"인데 **일주일 대 밀리초**다. 그 차이가 **얼마나 자주 검증할 수 있는가**를 결정하고, 그것이 곧 **얼마나 빨리 고칠 수 있는가**다.

**자동화가 판을 바꿨지만 문제가 남았다** — **여전히 진짜 데이터베이스와 대화해야 했다.** *"솔직히 말해 **물리적인 데이터베이스와 이야기하지 않으면 테스트가 진짜가 아니기** 때문이다."* 그래서 나온 것이 **SQL을 말하면서도 로컬에서, 메모리 안에서 도는 데이터베이스**다.

## Q2. "인메모리"가 뜻하는 것

**애플리케이션과 같은 메모리 공간에서 돈다 = 별도 프로세스가 아니다.**

**책이 Note를 따로 둔 이유**:

> **데이터베이스는 다 메모리에서 도는 것 아닌가? 운영급 데이터베이스 시스템은 메모리에서 돈다.** 서버에는 데이터베이스 서버를 받치기 위한 거대한 메모리와 디스크가 붙는다. **하지만 우리가 말하는 것은 그게 아니다.**
> 애플리케이션 관점에서 인메모리 데이터베이스란 **여러분의 애플리케이션과 같은 메모리 공간에서 도는 데이터베이스**다.

```
운영 PostgreSQL:   [내 앱 프로세스]  ←네트워크→  [postgres 프로세스]
HSQLDB 인메모리:   [ 내 앱 프로세스 · 그 안에 DB 엔진이 함께 산다 ]
```

**핵심은 "메모리를 쓴다"가 아니라 "별도 프로세스가 아니다"이다.**

**그래서 따라오는 성질들**: 설치가 없다 · 네트워크가 없다 · 포트 충돌이 없다 · **프로세스가 죽으면 데이터도 사라진다** · 그리고 **엔진이 다르다**(→ Q3).

## Q3. 리허설 비유가 깨지는 지점

**리허설 극장과 본 공연장의 차이는 음향이나 동선처럼 눈에 보이는 것들이다. 하지만 HSQLDB와 PostgreSQL의 차이는 눈에 안 보이는 곳에 있다.**

**차이가 나는 항목**: **SQL 방언, 인덱싱 동작, 대소문자 처리, 트랜잭션 처리.**

> **그래서 리허설을 완벽히 마쳐도 본 공연에서 처음 드러나는 것이 남는다.**

**하필 이 절의 어떤 테스트와 직결되는가 — `IgnoreCase` 테스트다.**

```java
repository.findByNameContainsIgnoreCase("SpRinG bOOt 4")
```

**대소문자 처리는 데이터베이스마다 다른 대표적인 항목이다.** 이 절이 방금 통과시킨 바로 그 동작이 **PostgreSQL에서는 다르게 돌 수 있다.** 검증했다고 믿는 것이 실은 검증되지 않은 것이다.

**책의 진단이 그대로다**:
> **SQL이 표준화되어 있긴 하지만 그 표준들에는 빈틈이 있다.** 각 데이터베이스 엔진은 그 빈틈을 자기 방식으로 메우고, 종종 명세를 넘어서는 추가 기능을 제공한다. 결과적으로 **방언의 특이점, 인덱싱 동작, 대소문자 민감성, 트랜잭션 처리**가 내장 데이터베이스에서는 되던 코드를 PostgreSQL에서 실패하게 만들 수 있다.

**이 문단이 이 절이 끝이 아닌 이유 전부다** → [[06-adding-testcontainers]].

**참고로 앞 절과 성격이 다르다**: [[04-testing-services-with-mocks]]의 목은 **대역**이었고, 여기는 **본인의 리허설**이다 — **진짜 SQL 엔진이 실제로 쿼리를 실행한다.** 그래서 "쿼리를 아예 모른다"에서 "쿼리를 다른 엔진에서 확인했다"로 한 단계 올라간 것이고, 그 한 단계만큼만 올라간 것이다.

## Q4. `hsqldb`에 `runtime` scope를 주는 것이 막는 것

**애플리케이션 코드가 HSQLDB 클래스를 직접 import하는 일을 원천적으로 막는다.**

```xml
<dependency>
     <groupId>org.hsqldb</groupId>
     <artifactId>hsqldb</artifactId>
     <scope>runtime</scope>
</dependency>
```

> **이것은 `runtime` 의존성이며, 우리 코드의 어떤 것도 이것을 상대로 컴파일할 필요가 없다는 뜻이다. 애플리케이션이 실행될 때만 필요하다.**

**컴파일 경로에서 밀어냈으므로**, 실수로 `org.hsqldb.*`를 import하면 **컴파일이 안 된다.** 즉 **컴파일러가 규율을 강제한다.**

**왜 그 규율이 필요한가**: 특정 DB 클래스를 직접 쓰기 시작하면 **다른 DB로 갈아탈 수 없게 된다.** JDBC/JPA라는 추상화를 두는 이유가 사라진다.

**[[../chapter-3-querying-for-data-with-spring-boot/01b-adding-spring-data-jpa-to-our-project|Ch3에서 H2를 넣을 때와 같은 이유]]다.** 그리고 이 성질 덕분에 **[[06-adding-testcontainers]]에서 PostgreSQL로 바꿔도 애플리케이션 코드는 한 줄도 안 고친다.**

## Q5. 세 테스트 중 가장 가치가 낮은 것

**`findAllShouldProduceAllVideos`다.**

**책이 기준을 명시한다**:
> 우리가 **Spring Data JPA가 동작하는지 확인하는 데 초점을 두는 것이 아니라는** 점을 이해하는 것이 중요하다. 그것은 **프레임워크를 검증하는 일**이며 우리 범위 밖이다. 아니다 — 우리는 **우리가 올바른 쿼리를 썼는지** 검증해야 한다.

| 테스트 | 검증 대상 | 누가 만든 것인가 |
|---|---|---|
| `findAll()` 크기 3 | `JpaRepository`의 기본 메서드 | **Spring Data JPA가 만든 것** |
| `findByNameContainsIgnoreCase` | 메서드 이름에서 파생된 쿼리 | **우리가 이름 지어 만든 것** |
| `findByNameContainsOrDescriptionContainsAllIgnoreCase` | 두 필드 OR + IgnoreCase | **우리가 만든 것** |

**`findAll()`은 사실상 Spring Data JPA를 테스트하는 것에 가깝다.**

**다만 절대적이지는 않다** — [[07-testing-repositories-with-testcontainers]]에서 **같은 테스트가 스모크 테스트라는 다른 이름과 다른 목적을 얻는다.** 거기서는 "쿼리가 맞나"가 아니라 **"컨테이너가 뜨고 연결되고 스키마가 만들어졌나"**를 확인하는 첫 신호다. **같은 코드의 가치가 문맥에 따라 달라진다.**

## Q6. `"SpRinG bOOt 4"`가 우연이 아닌 이유

**대소문자를 일부러 뒤섞어 `IgnoreCase` 한정어가 실제로 작동하는지를 증명한다.**

```
저장된 것:  "Need HELP with your SPRING BOOT 4 App?"
입력:       "SpRinG bOOt 4"
            ↑ 원문과도 다르고 소문자와도 다르다
```

**만약 `"spring boot 4"`나 `"SPRING BOOT 4"`로 넣었다면**, `IgnoreCase`가 **동작하지 않아도 통과할 수 있다** — 한쪽이 우연히 맞아떨어질 여지가 있다. **뒤죽박죽으로 만들면 그 여지가 사라진다.**

> **이것이 "우리가 만든 것을 검증한다"(Q5)의 구체적 모습이다.** 테스트 데이터는 **한정어를 실제로 시험하도록** 고른 것이다.

**같은 설계가 두 번째 검색 테스트에도 있다** — `"CoDe"`와 `"YOUR CODE"`. 하나는 **부분 문자열 + 섞인 대소문자**, 하나는 **공백 포함 + 전부 대문자**다. `Contains`와 `IgnoreCase`가 **둘 다** 필요해야만 통과한다.

**단언 쪽도 마찬가지다** — `hasSize(1)`로 끝내지 않고 `extracting(VideoEntity::getName).containsExactlyInAnyOrder(...)`로 **어느 것이 걸렸는지**까지 본다. 크기만 보면 **엉뚱한 하나가 걸려도 통과**한다.

## Q7. `id`와 결과 순서를 단언하지 않는 이유가 같은 원칙인가

**그렇다 — 둘 다 "테스트가 통제하지 않는 값은 단언 대상에서 뺀다"이다.**

| | 왜 통제 밖인가 |
|---|---|
| **`id`** | **`setUp()`의 `saveAll()`이 채운다.** 값이 몇인지 테스트가 정하지 않았다 |
| **결과 순서** | **`ORDER BY`가 없으면 관계형 데이터베이스가 삽입 순서로 돌려줄 의무가 없다** |

**`id`에 대한 책의 말**:
> 실제 데이터베이스와 대화하는 테스트에서 이것을 피하는 이유는 **`id` 필드가 `saveAll()`로 채워지기 때문**이다. 동적으로 다룰 방법을 궁리해 볼 수도 있지만 **기본 키를 확인하는 것이 결정적으로 중요하지는 않다.** 대신 **애플리케이션 관점에서** 검증하는 데 집중하라.

**순서에 대한 책의 말**:
> **의도적으로 순서는 확인하지 않는데, `ORDER BY` 절이 없으면 관계형 데이터베이스가 삽입 순서로 결과를 돌려줄 의무가 없기 때문**이다.

**둘 다 단언하면 어떤 테스트가 되는가**: **"지금은 통과하지만 언제든 깨질 수 있는" 테스트**가 된다. 그리고 깨졌을 때 **애플리케이션이 잘못된 게 아니다.** 즉 **가짜 실패를 생산하는 테스트**다.

**"순서를 단언하지 않는 것은 게으른 것"이라는 오해가 있는데 반대다** — `ORDER BY` 없이 순서를 단언하면 **틀린 것을 검증하는** 테스트가 된다. 지금 통과하는 것이 **우연**이다. 순서가 중요하다면 **`ORDER BY`를 쿼리에 넣고 나서** 단언해야 한다([[../chapter-3-querying-for-data-with-spring-boot/04a-sorting-the-results|Ch3]]).

**`containsExactlyInAnyOrder()`가 정확히 이 원칙의 도구다** — **순서는 중요하지 않지만 구체적 내용은 중요할 때** 딱 맞는 연산자다.

## Q8. 필드 주입이 테스트 클래스에서만 괜찮은 근거

**테스트 클래스를 만들고 파괴하는 생명주기를 우리나 Spring Framework가 아니라 JUnit이 관리하기 때문이다.**

**필드 주입이 위험한 이유의 뿌리**:
```
누군가 new HomeController() 로 만들면
   → @Autowired 필드가 채워지지 않는다
   → 첫 호출에서 NullPointerException
```

**컨테이너를 거치지 않는 생성 경로가 존재한다는 것**이 위험의 정체다.

**테스트 클래스에서는 그 경로가 없다**:
```
VideoRepositoryHsqlTest 인스턴스를 만드는 것은 JUnit 뿐이다.
JUnit → Spring TestContext → @Autowired 필드 주입
▶ 내가 new 로 만들 일이 없다.
```

> **"나쁘다"가 아니라 "그 위험이 있는 곳에서 나쁘다"이다.**

**책도 그렇게 정리한다** — *"필드 주입은 보통 `NullPointerException`으로 이어질 수 있는 위험으로 여겨지지만, **테스트 클래스에서는 괜찮다.**"*

**흥미로운 대비**: [[04-testing-services-with-mocks]]는 정반대 방향으로 같은 사실을 이용했다 — 거기서는 **운영 코드가 생성자 주입이라서** 테스트가 `new VideoService(repository)` 한 줄로 조립할 수 있었다. **운영 코드는 생성자 주입, 테스트 클래스는 필드 주입** — 두 선택이 각각 그 자리에서 맞다.
