## Q1. `@AutoConfigureTestDatabase(replace = NONE)`을 빼면

**Boot가 클래스패스에서 내장 데이터베이스를 발견하면 설정된 `DataSource`를 그것으로 갈아 끼운다.**

**즉 컨테이너를 띄우는 비용만 치르고 검증은 하나도 못 얻는다.**

```text
  컨테이너 기동  ✅  (초 단위 비용 지불)
  테스트 실행    ✅
  테스트 통과    ✅
  실제 쓴 DB     ❌  내장 DB
  방언 검증      ❌  아무것도

  ▶ 빨간불이 하나도 안 뜨는데 목적만 사라진다.
```

> **왜 발견하기 어려운가 — 아무 오류도 안 나기 때문이다.**

**실패는 눈에 띈다. 통과는 안 띈다.** 컴파일 오류도, 예외도, 경고도 없다. **스스로 의심하지 않으면 발견할 방법이 없다.**

**이 자동 교체 자체는 선의다** — 테스트를 **빠르고 격리되게** 만들려는 것이다. 그런데 이 절의 목적은 정확히 그 반대다. [[05-testing-repositories-with-embedded-databases]]가 끝에서 지적한 **방언 문제**를 잡으려고 진짜 PostgreSQL을 띄운 것이다.

**확인하는 법**: 로그에서 실제 JDBC URL을 본다. `jdbc:postgresql://localhost:<임의포트>/testdb`가 아니라 `jdbc:h2:mem:...`이면 갈아 끼워진 것이다.

## Q2. 눈치 빠른 조수 비유가 깨지는 지점

**사람 조수는 한 번 거절하면 다음부터 기억한다. 하지만 `@AutoConfigureTestDatabase(replace = NONE)`은 테스트 클래스마다 다시 말해야 한다.**

> **그리고 말하는 것을 잊어도 조수는 아무 말 없이 자기 판단대로 한다 — 오류도, 경고도 없다.**

**이 비대칭이 사람 조수 비유에는 없다**:
```
사람 조수:  거절 → 기억함 → 다음부터 안 물어봄
애노테이션: 거절 → 그 클래스에서만 유효 → 새 클래스에서 침묵으로 되돌아감
```

**거절을 잊으면 조용히 목적을 잃는다.**

**설계상 왜 그런가**: 애노테이션은 **클래스 단위 선언**이지 세션 상태가 아니다. 프로젝트 전체에 걸린 규칙이 아니라 **이 테스트 클래스에 대한 지시**다. 그래서 잊기 쉽고, 잊었을 때 알려 주는 장치가 없다.

**실무적 방어**: 이런 테스트의 **베이스 클래스**를 만들어 애노테이션 네 개를 거기 몰아 두고 상속시키면, 새 클래스가 그것을 빠뜨릴 여지가 줄어든다.

## Q3. 여섯 애노테이션 각각이 없으면 깨지는 것

| 애노테이션 | 하는 일 | **없으면** |
|---|---|---|
| **`@Testcontainers`** | Testcontainers `junit-jupiter` 모듈이 **JUnit 6 생명주기에 훅**을 건다 | **컨테이너가 자동으로 뜨고 지지 않는다** |
| **`@DataJpaTest`** | 엔티티와 Spring Data JPA 리포지토리를 스캔 | **리포지토리 빈이 없다** |
| **`@AutoConfigureTestDatabase(replace = NONE)`** | 내장 DB로의 자동 교체를 막는다 | **컨테이너 대신 내장 DB로 조용히 통과** (Q1) |
| **`@TestPropertySource(ddl-auto=create-drop)`** | 컨텍스트 시작 시 **스키마 생성**, 종료 시 **삭제** | **표가 없어 전부 실패** |
| **`@Container`** | 이 컨테이너를 **JUnit 생명주기로 제어**할 대상으로 표시 | **컨테이너 객체는 있으나 기동되지 않는다** |
| **`@ServiceConnection`** | 컨테이너를 **Spring 컨텍스트에 자동 바인딩** | **접속 정보를 손으로 넘겨야 한다** (Q4) |

**`@Container`와 `@ServiceConnection`의 구분이 특히 헷갈린다**:
```
@Container         → 컨테이너를 띄우고 내린다        (Testcontainers 쪽)
@ServiceConnection → 그 접속 정보를 Spring 에 알린다  (Spring Boot 쪽)

▶ 앞의 것만 있으면 컨테이너는 뜨지만 애플리케이션이 그걸 모른다.
```

**이 대응이 [[06-adding-testcontainers]]의 의존성 넷과 맞물린다** — `testcontainers-junit-jupiter`가 `@Testcontainers`/`@Container`를, `spring-boot-testcontainers`가 `@ServiceConnection`을 준다. **다리와 본체가 각각 자기 애노테이션을 낸다.**

**실패의 종류도 다르다**: `@DataJpaTest`·`@TestPropertySource`·`@Container`를 빠뜨리면 **시끄럽게 실패**한다(빈 없음·표 없음·연결 거부). **`@AutoConfigureTestDatabase`만 조용히 통과**한다 — 그래서 유일하게 위험하다.

## Q4. `@ServiceConnection`이 없던 시절

**컨테이너가 뜬 뒤 접속 정보를 읽어 Spring 프로퍼티로 등록해야 했다.**

```java
@DynamicPropertySource
static void props(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url",      database::getJdbcUrl);
    registry.add("spring.datasource.username", database::getUsername);
    registry.add("spring.datasource.password", database::getPassword);
}
```

> **문제의 뿌리는 컨테이너의 포트가 실행할 때마다 달라진다는 것이다.**

**왜 포트가 달라지는가**: **충돌을 피하려고 임의 포트를 쓴다.** 5432를 고정하면 로컬에 이미 PostgreSQL이 떠 있거나 CI에서 병렬 실행할 때 부딪힌다.

```
고정된 설정 파일로는 표현할 수 없다
        ↓
"컨테이너가 뜬 뒤 값을 읽어 프로퍼티로 등록" 하는 단계가 필요했다
        ↓
@ServiceConnection 은 컨테이너 타입을 보고 그 일을 알아서 한다
```

**`Supplier` 형태(`database::getJdbcUrl`)로 넘긴 것도 같은 이유다** — 등록 시점에는 **아직 값이 없다.** 컨테이너가 뜬 뒤에 호출돼야 한다.

**`@ServiceConnection`이 하는 일**: 필드의 **타입**(`PostgreSQLContainer`)을 보고 **어떤 연결 설정을 채워야 하는지 안다.** 그래서 애노테이션 한 줄로 끝난다. 같은 원리가 Redis·Kafka·MongoDB 컨테이너에도 적용된다.

## Q5. 컨테이너는 `static`인데 데이터는 `@BeforeEach`인 이유

**비싼 것은 한 번, 싼 것은 매번.**

```text
  테스트 클래스 시작
        │
        ├─▶ 컨테이너 기동 (static · 클래스당 1회)     ← 비싸다 (400ms)
        │   스키마 생성 (ddl-auto=create-drop)
        │
        ├─▶ 테스트 1 ─ @BeforeEach: 데이터 3건 ─ 실행 ─ 롤백   ← 싸다
        ├─▶ 테스트 2 ─ @BeforeEach: 데이터 3건 ─ 실행 ─ 롤백
        ├─▶ 테스트 3 ─ @BeforeEach: 데이터 3건 ─ 실행 ─ 롤백
        │
        └─▶ 컨테이너 종료 · 스키마 삭제
```

**책의 근거**: *"각 테스트 메서드가 **깨끗한 데이터베이스에서 시작**하므로 내용을 미리 채워야 한다."*

**"`static`이면 데이터가 섞이지 않나" — 섞이지 않는다.** **컨테이너 공유와 데이터 격리는 별개로 처리된다**:
- **공유**: 컨테이너·스키마 (`static`)
- **격리**: `@DataJpaTest`가 각 테스트를 **트랜잭션으로 감싸 롤백**하고, `@BeforeEach`가 **매번 다시 채운다**

**이 분담이 컨테이너 기동의 초 단위 비용을 감당 가능하게 만든다** → Q6의 숫자.

**다른 데이터 시나리오가 필요하면**: 책은 **테스트 클래스를 하나 더 쓰라**고 하고, 그것이 안전한 이유도 준다 — Testcontainers가 JUnit과 긴밀히 통합되어 있어 **한 테스트 클래스의 정적 인스턴스가 떠돌며 다른 클래스를 망가뜨릴 걱정을 하지 않아도 된다.**

## Q6. 401ms / 35ms / 24ms가 말해 주는 것

**비용이 첫 테스트에 몰려 있다.**

| 테스트 | 시간 | 무엇을 포함하나 |
|---|---:|---|
| `findAllShouldProduceAllVideos()` | **401ms** | **컨테이너 기동 마무리 + 스키마 생성 + 첫 연결** + 실제 쿼리 |
| `findByName()` | 35ms | 데이터 적재 + 쿼리 |
| `findByNameOrDescription()` | 24ms | 데이터 적재 + 쿼리 |
| **합계** | **460ms** | |

**두 가지를 동시에 말한다**:

**① `static` 컨테이너 설계가 옳았다는 증거.** 두 번째부터는 **[[03-testing-web-controllers-with-mockmvc]]의 MockMvc 테스트와 비슷한 수준**이다. **메서드마다 컨테이너를 띄웠다면 세 테스트가 모두 400ms대**였을 것이다.

**② 그래도 싸지 않다.** [[02-testing-domain-objects]]의 **49밀리초와 비교하면 약 열 배**다.

> **이 장이 "각 전술에 트레이드오프가 있다"고 반복하는 것이 이 숫자에 있다.**

**실무적 함의**: 테스트 **메서드**가 늘어나는 것은 싸지만 테스트 **클래스**가 늘어나는 것은 비싸다 — **클래스마다 400ms가 다시 붙는다.** 그래서 **싱글턴 컨테이너 패턴**(전체 스위트에 컨테이너 하나를 공유)이 필요해지는 지점이 온다.

**그리고 이 비용이 [[02-testing-domain-objects]]의 원칙과 충돌한다** — 모든 테스트를 이 방식으로 쓰면 전체 스위트가 느려져 **"자주 돌린다"가 무너진다.** 이 장이 세 전략(목·인메모리·컨테이너)을 다 보여 주는 이유다.

## Q7. 같은 `findAll()` 테스트가 다른 평가를 받는 이유

**목적이 달라졌다.**

| | [[05-testing-repositories-with-embedded-databases]] | **이 절** |
|---|---|---|
| 이름 | 그냥 첫 테스트 | **스모크 테스트** |
| 검증하려는 것 | 쿼리가 옳은가 | **컨테이너가 뜨고 스키마가 생기고 접속이 되는가** |
| 평가 | **가치가 낮다** — 사실상 Spring Data JPA를 테스트 | **필요하다** — 관문 역할 |

**책이 이 절에서 솔직하게 다시 말한다**:
> `findAll()`이 Spring Data JPA가 제공하는 것임을 생각하면 **우리 코드가 아니라 Spring Data JPA를 테스트하는 것에 가깝다.** 하지만 때로는 **모든 것이 제대로 설정됐는지 확인하기 위해** 이런 종류의 테스트가 필요하다. 이것을 때로 **스모크 테스트**라고 부른다.

**즉 평가가 뒤집힌 게 아니라, 이 절에서는 검증할 설정이 훨씬 많아졌다** — 컨테이너 기동, Docker 연결, 임의 포트 바인딩, `@ServiceConnection` 주입, `ddl-auto` 스키마 생성. **이 중 하나만 어긋나도 `findAll()`이 먼저 실패한다.** [[05-testing-repositories-with-embedded-databases]]에는 그 층이 없었다.

**이름의 유래**: `smoke test`는 전자 기기에 처음 전원을 넣고 **연기가 나는지 보던** 관행에서 왔다. **성능을 재는 것이 아니라 "타지 않는가"를 본다.**

**Q6의 숫자가 이것을 뒷받침한다** — **401ms 중 대부분이 그 설정 층**이다. 그 층을 통과했다는 사실 자체가 정보다.

## Q8. Testcontainers가 인메모리 대체물보다 확장성이 큰 이유

**Docker Hub 이미지를 찾을 수 있다면 무엇이든 엮을 수 있기 때문이다.**

> **이 전술은 다른 많은 곳에서도 통한다** — RabbitMQ, Apache Kafka, Redis, Hazelcast, 무엇이든. **Docker Hub 이미지를 찾을 수 있다면 Testcontainers로 코드에 엮을 수 있다.** 때로는 단축 애노테이션이 있고, 때로는 방금 우리가 한 것처럼 컨테이너를 직접 만들면 된다.

**인메모리 대체물에는 이 확장성이 없다**:
```
인메모리 DB   ← 누군가 "Java 로 도는 SQL 엔진"을 따로 구현해 줘야 성립
              (HSQLDB · H2 · Derby 가 그래서 존재한다)

Testcontainers ← 운영에서 쓰는 그 이미지를 그대로 띄운다
              (구현을 새로 만들 필요가 없다)
```

**인메모리 Kafka나 인메모리 Redis를 진짜와 같게 만들 방법이 마땅치 않다.** 프로토콜·파티셔닝·복제·만료 정책을 전부 다시 구현해야 하는데, 그러면 **또 다른 방언 문제**가 생긴다.

**근본 차이**: 인메모리 대체물은 **모방**이고, Testcontainers는 **진짜를 격리해 실행**하는 것이다. 그래서
- 모방은 **대상마다 누군가 만들어야** 하고 **차이가 남는다**
- 격리 실행은 **이미지가 있으면 되고 차이가 없다**

**대가는 Q6과 [[06-adding-testcontainers]]가 말한 것들이다** — **Docker가 전제**이고, **초 단위 비용**이 붙고, **이미지 태그가 운영 버전과 맞아야** 의미가 있다.

**남는 한계 하나**: `ddl-auto=create-drop`은 **엔티티 매핑에서 스키마를 만든다.** 운영 스키마가 마이그레이션 도구로 관리된다면 이 테스트는 **엔티티가 옳은지**는 검증해도 **실제 운영 스키마와 일치하는지**는 검증하지 않는다.

## 재출제 문항

1. Testcontainers 테스트가 전부 통과한다. 실제로 PostgreSQL을 썼다는 것을 어떻게 확인하는가?
2. 새 테스트 클래스를 만들었더니 검증 효과가 사라졌다. 무엇을 잊었는가?
3. `@Container`는 있는데 `@ServiceConnection`이 없다. 어떤 오류가 나는가?
4. 컨테이너 포트가 매번 달라지는데 왜 그렇게 만들었는가?
5. 컨테이너를 `static`이 아닌 인스턴스 필드로 바꾸면 Figure 5.6의 숫자가 어떻게 변하는가?
6. 테스트 클래스를 30개로 늘렸다. 무엇이 문제가 되는가?
7. 같은 `findAll()` 테스트가 앞 절에서는 가치가 낮고 여기서는 필요하다. 무엇이 달라졌는가?
8. Kafka를 쓰는 코드를 테스트하려 한다. 인메모리 방식과 Testcontainers 중 어느 쪽이고 왜인가?
