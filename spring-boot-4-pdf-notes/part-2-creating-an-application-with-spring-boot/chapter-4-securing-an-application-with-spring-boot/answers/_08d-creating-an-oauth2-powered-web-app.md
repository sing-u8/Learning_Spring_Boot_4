## Q1. 썸네일과 설명 길이 문제의 뿌리가 같은 이유

**둘 다 로직리스 템플릿이라 템플릿에서 판단할 수 없기 때문이다.**

| 문제 | 필요한 것 | Mustache에 있나 |
|---|---|---|
| **썸네일** — `Map<String, SearchThumbnail>`에서 `default`만 | **맵에서 특정 키 골라내기** | **✘** |
| **설명 길이** — 수백 자를 잘라야 | **조건문 + `substring`** | **✘** |

**Mustache 문법이 하는 일은 셋뿐이다** — 값 출력, 배열 반복, 점 중첩 접근. **고르기도 자르기도 없다.**

> **두 문제의 뿌리가 같다. 로직리스 템플릿이라서다.**

**해법도 하나다**: **판단을 모델 쪽으로 옮긴다** → Q3.

## Q2. Mustache가 `if` 없이 반복과 출력을 구분하는 규칙

> **타입을 보고 동작을 정한다 — 배열이면 반복, 값이면 출력.**

| 표기 | 값의 타입 | 결과 |
|---|---|---|
| `{{값}}` | 무엇이든 | **값 하나를 출력** |
| `{{#배열}}` … `{{/배열}}` | **배열/컬렉션** | **안쪽 HTML을 항목마다 반복** |
| `{{#값}}` … `{{/값}}` | 단일 객체 | 1번, 그 객체를 문맥으로 |
| `{{#값}}` … `{{/값}}` | `null`/빈 컬렉션/`false` | **사라진다** |

`{{#channelVideos.items}}`가 반복인 이유는 **`items`가 `SearchResult[]` 배열이기 때문**이다.

**`if`가 없어도 되는 이유가 이 규칙이다** — "없으면 안 그린다"가 조건문 역할을 하고, "배열이면 반복"이 루프 역할을 한다. **하나의 문법이 두 일을 한다.**

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04a-adding-demo-data-to-a-template|Ch2에서 `{{#videos}}`를 "섹션"이라 부른 이유]]가 이것이다** — 반복이라 부르면 나머지 경우를 설명할 수 없다.

**대가**: **이름을 틀려도 조용히 사라진다.** 오류가 아니라 빈 화면이다.

## Q3. 판단을 record로 옮겼을 때의 부수적 이점

**테스트 가능해진다.**

> **`shortDescription()`은 단위 테스트를 쓸 수 있지만 템플릿 안의 `{{#if}}`는 그렇지 않다.**

```java
record SearchSnippet(..., String description, Map<String, SearchThumbnail> thumbnails, ...) {
    String shortDescription() {
        if (this.description.length() <= 100) return this.description;
        return this.description.substring(0, 100);
    }
    SearchThumbnail thumbnail() { /* default 키를 고른다 */ }
}
```

> **템플릿에 로직을 넣을 수 없는 것이 제약처럼 보이지만, 결과적으로 "화면이 필요로 하는 계산"이 테스트 가능한 자바 코드로 남는다.**

**다른 이점 셋**:
- **재사용된다** — 다른 화면이나 API 응답에서도 같은 계산을 쓴다
- **타입 검사를 받는다** — 템플릿 문자열은 컴파일러가 안 본다
- **IDE 리팩터링이 따라온다** — 메서드 이름을 바꾸면 호출부가 함께 바뀐다(템플릿은 예외 → Q4)

**제약이 설계를 좋게 만든 사례다.** 할 수 있었다면 템플릿에 넣었을 것이고, 그러면 테스트할 수 없는 로직이 화면에 쌓였을 것이다.

**남는 결합**: **화면이 바뀌면 record 정의를 고치게 된다** → Q8.

## Q4. `{{snippet.shortDescription}}`이 실제로 부르는 것

**`shortDescription()` 메서드다.**

> **Mustache가 `{{snippet.shortDescription}}`을 만나면 필드를 먼저 찾고 없으면 같은 이름의 메서드를 부른다.**

`SearchSnippet` record에는 **`shortDescription`이라는 컴포넌트가 없다.** 그래서 메서드를 찾아 호출한다.

**"필드 접근이다"라는 오해가 흔하다** — 표기가 필드처럼 생겼기 때문이다. **필드처럼 쓰이지만 실제로는 계산이 일어난다.**

**`{{snippet.thumbnail.url}}`도 같다** — `thumbnail()`을 호출하고, 그 결과에서 `url`을 읽는다.

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04a-adding-demo-data-to-a-template|Ch2에서 record의 `name()`이 `{{name}}`으로 동작한 것]]과 같은 규칙이다** — Mustache는 `getX()`와 `x()` 둘 다 찾는다. 여기서는 그 성질을 **의도적으로 활용**한다.

**주의**: 이 연결은 **문자열 매칭**이라 컴파일러가 안 본다. 메서드 이름을 바꾸면 **템플릿이 조용히 빈 값을 출력**한다.

## Q5. `style.css`를 서빙하는 데 쓴 설정 코드는 몇 줄인가

**0줄이다.**

**파일을 `src/main/resources/static/style.css`에 두면 끝이다.**

**왜인가**: Spring MVC가 **그 디렉터리 아래를 정적 자원으로 자동 서빙**한다. **설정도 컨트롤러도 필요 없다.**

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/06-integrating-nodejs-with-a-spring-boot-web-app|Ch2의 `static/` 관례]]가 그대로다** — 판별 질문은 **"이 파일에 서버 데이터를 끼워 넣어야 하는가"**이고, CSS는 아니므로 `static/`이다.

**이것이 관례 우선 설정의 값이다** — 흔한 요구(정적 파일 서빙)에 **기본값을 두어 코드가 0줄**이 된다. [[../chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1]]에서 본 그 원리다.

**바꿀 수는 있다** — `spring.mvc.static-path-pattern` 같은 프로퍼티로 조정 가능하다. 다만 **관례를 따르면 0줄**이고, 벗어나면 그 설정을 팀 전체가 알아야 한다.

## Q6. 채널 선택 프롬프트가 뜨는 인과 — 스코프로

**`youtube.readonly` 스코프를 요청했기 때문이다.**

```
스코프에 youtube.readonly 포함
   → Google이 "이 앱에 YouTube 읽기 권한을 준다"는 동의를 받아야 한다
   → 그런데 한 Google 계정에 YouTube 채널이 여럿일 수 있다
   → "어느 채널에 대한 권한인가"를 물어야 한다
   → 채널 선택 프롬프트
```

> **"채널 선택 프롬프트는 Google이 늘 보여 준다"** → **아니다. 기본 스코프였다면 뜨지 않는다.**

**즉 우리가 요청한 권한이 화면에 그대로 나타난다** — [[07-understanding-oauth-2-1]]에서 본 **"스코프가 동의 화면에 그대로 나타난다"**의 구체적 사례다.

**그리고 앱 이름도 나타난다** — [[08a-creating-a-google-oauth-application]]의 13–14단계에서 설정한 동의 화면 이름이 **"to continue to YouTube Manager"**로 보인다.

**설정과 화면이 이어져 있다는 것이 이 흐름의 관측 가능한 증거다.**

## Q7. Figure 4.8에서 CSS가 부분적으로만 먹은 것을 어떻게 아는가

**테두리는 적용됐는데 열 너비는 균등하기 때문이다.**

```css
table { border: 3px solid #039E44; }   /* ✅ 적용됨 — 테두리가 보인다 */
thead th:nth-child(1) { width: 30%; }  /* ❌ 안 먹음 — 열이 균등하다 */
```

**원인**: **CSS 선택자가 `thead th`인데 템플릿의 헤더는 `<td>`다.**

```html
<thead>
<tr>
    <td>Id</td>     ← th가 아니라 td
```

**`th:nth-child`는 `<th>`를 찾는다. 없으므로 아무것도 선택되지 않는다.**

**진단이 가능한 이유**: **`table` 선택자는 태그가 맞으므로 먹고, `thead th`는 안 먹는다.** 둘의 결과가 화면에서 갈리므로 **"선택자 문제"임을 좁힐 수 있다.**

**"CSS가 적용됐으니 열 너비도 맞을 것"이라는 오해**가 여기서 깨진다 — **CSS 파일이 로드된 것과 모든 규칙이 적용된 것은 다르다.**

**고치는 법**: 템플릿의 `<td>`를 `<th>`로 바꾸거나(의미상으로도 헤더 셀이 맞다), 선택자를 `thead td`로 바꾼다. **전자가 옳다** — 헤더 행에는 `<th>`가 표준이다.

## Q8. 조리대 비유가 깨지는 지점

**누가 손질을 하느냐를 흐린다.**

비유는 여기까지 맞는다 — **요리사가 손질까지 끝낸 재료만 받는 조리대.** 조리대(템플릿)에서는 **썰거나 고르지 않고 담기만** 한다.

**깨지는 지점**:

> **여기서는 손질하는 주방이 따로 있는 게 아니라 재료 자신(record)이 손질 방법을 들고 있다.**

> **재료에 "나를 이렇게 썰어 내라"는 메서드가 붙어 있는 셈이라, 화면이 바뀌면 재료 정의를 고치게 된다는 결합이 남는다.**

**구체적으로**: 화면이 설명을 100자가 아니라 200자로 보여 주기로 하면 **`SearchSnippet` record를 고쳐야** 한다. **API 응답을 표현하는 타입이 화면 요구에 따라 바뀐다.**

**[[../chapter-3-querying-for-data-with-spring-boot/02-dtos-entities-and-pojos|Ch3의 DTO/엔티티 분리]] 기준으로는 냄새다** — 한 타입이 **"API 응답의 형태"**와 **"화면이 필요로 하는 계산"** 두 주인을 섬긴다.

**대안**: 화면 전용 DTO를 따로 두고 변환한다. **대가는 매핑 코드**이고, 이 규모에서는 과할 수 있다 — Ch3의 Tip이 말한 **"이 코드가 오래 살 것인가"**로 판단할 자리다.
