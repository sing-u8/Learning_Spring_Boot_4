## Q1. 부모 인터페이스의 메서드에 규칙을 걸려면

**자식 인터페이스에서 다시 선언(재선언)한다.**

```java
public interface VideoRepository extends JpaRepository<VideoEntity, Long> {
    @PreAuthorize("#entity.username == authentication.name")
    @Override
    void delete(VideoEntity entity);
}
```

**자바 인터페이스는 부모의 메서드를 자식에서 다시 선언할 수 있다.** **동작은 그대로**이고, **다른 애노테이션을 붙일 자리**가 생긴다.

**왜 필요한가**: `delete`는 **내가 쓴 적이 없다.** `JpaRepository`를 상속하는 순간 딸려 온 것이고, **부모 인터페이스는 Spring Data가 배포한 라이브러리 코드라 내가 고칠 수 없다.**

> **남이 만든 메서드에 내 규칙을 붙여야 하는 상황.**

재선언은 그 상황의 표준 해법이다. 몸통도 구현도 없고 **선언만 반복**한다.

## Q2. `@Override`를 빼면 생기는 버그와 그것이 조용한 이유

**시그니처 오타가 "새 메서드 추가"가 되어 규칙이 아무 데도 안 걸린다.**

```java
@PreAuthorize("...")
void delte(VideoEntity entity);   // 오타. @Override가 없으면 컴파일된다
```

**이렇게 되면**:
- `delte`라는 **새 메서드가 하나 추가**되고 거기에 규칙이 걸린다
- **진짜 `delete`는 무방비로 남는다**
- **컴파일은 된다.** 파생 질의 파싱에도 안 걸릴 수 있다

**왜 조용한가**: **아무도 `delte`를 부르지 않으므로** 규칙이 평가될 일이 없다. 오류도 경고도 안 난다. 그리고 **`delete`는 원래대로 잘 동작한다** — 검사만 없다.

> **`@Override`는 문서용 표시가 아니라 안전장치다.**

부모에 정말 그 시그니처가 있는지 **컴파일러가 검사**한다. 오타면 **컴파일 에러**다.

**이 장의 다른 조용한 실패들과 같은 계열이다** — [[06e-enabling-method-level-security]]의 스위치 누락, [[05-securing-web-routes-and-http-verbs]]의 규칙 순서. **보안 실패는 대개 신호를 남기지 않는다.**

## Q3. `#entity`와 `authentication`의 출처

**좌변은 데이터, 우변은 요청자.**

| 조각 | **어디서 오나** | 무엇을 하나 |
|---|---|---|
| `#entity` | **메서드 인자** | `#` 접두사는 **"파라미터를 이름으로 참조하라"** |
| `.username` | 그 객체 | **`getUsername()`을 호출한다** |
| `authentication` | **보안 컨텍스트** | Spring Security가 표현식에 **미리 넣어 주는 루트 객체** |
| `.name` | 그 객체 | `getName()`. 현재 로그인한 사용자 이름 |

**`#`이 붙고 안 붙고가 출처를 가른다.** `#`은 **메서드 인자**를 가리키고, 접두사 없는 이름은 **표현식 루트**에 이미 있는 값이다. 그래서 `#authentication`이라고 쓰면 안 된다.

> **이 둘을 나란히 놓고 비교할 수 있다는 것이 메서드 레벨 보안의 전부다.**

**[[05-securing-web-routes-and-http-verbs]]의 URL 규칙에는 좌변에 해당하는 것이 없었다** — 요청만 보고는 데이터를 알 수 없다.

**`#entity`의 이름은 파라미터 이름과 같아야 한다.** 파라미터가 `videoEntity`면 `#videoEntity`다.

## Q4. `.username`이 `getUsername()`을 부른다는 사실이 중요한 이유

**SpEL은 필드를 직접 읽는 게 아니라 접근자 메서드를 통하기 때문이다.**

**그래서 [[06a-updating-our-model]]이 "getters and setters"를 남겨 둔 것이 여기서 필요해진다.** getter가 없으면 **표현식이 런타임에 실패한다** — 컴파일은 통과하고 실행할 때 터진다.

**실무적 귀결 셋**:
1. **엔티티에서 getter를 지우면 보안 규칙이 깨진다.** 리팩터링 도구는 문자열 안의 `.username`을 못 본다.
2. **getter에 로직을 넣으면 보안 판정이 그 로직을 탄다.** 예를 들어 `getUsername()`이 소문자로 변환해 돌려주면 비교도 소문자로 일어난다.
3. **record는 `getUsername()`이 아니라 `username()`을 만든다** — 그래서 엔티티에 record를 못 쓰는 이유가 하나 더 늘어난다.

**문자열 표현식의 근본 한계이기도 하다**: `#entity.usernme`처럼 오타를 내도 **컴파일은 통과하고 런타임에 평가가 실패한다.** 그래서 이 규칙에는 **성공·실패 두 경로 모두** 테스트가 필요하다.

## Q5. 이 규칙이 URL 규칙으로 표현될 수 없는 근본 이유

**판정 재료의 절반이 요청 안에 없기 때문이다.**

```
#entity.username == authentication.name
      ↑ 데이터 (DB 조회 필요)    ↑ 요청 (보안 컨텍스트에 있다)
```

**우변은 URL 규칙도 알 수 있다.** 좌변이 문제다 — **7번 동영상의 소유자는 조회해야 안다.**

그리고 **필터는 컨트롤러보다 먼저 실행되므로** 그 시점에는 **아직 조회가 일어나지 않았다** — [[06-securing-spring-data-methods]] Q1.

**그래서 검사 위치를 옮겼다**: 엔티티를 **손에 넣은 뒤**, `repository.delete(entity)` **호출 직전**. 그 자리에서만 좌변이 존재한다.

**증거가 코드 형태에 남아 있다**: [[06c-adding-a-delete-button]]에서 `deleteById(id)` 대신 `findById(id)` → `delete(entity)`를 고른 이유가 바로 이것이다. **`entity`라는 파라미터가 있어야 규칙을 쓸 수 있다.**

## Q6. alice가 bob의 동영상을 지우려 할 때 403인 이유

**alice가 누구인지는 서버가 정확히 알기 때문이다.**

| 코드 | 뜻 | 이 상황에 맞나 |
|---|---|---|
| 401 | "**당신이 누구인지 모르겠다.** 먼저 밝혀라" | ✘ — alice는 로그인해 있다 |
| **403** | "**당신이 누구인지는 안다.** 그런데 이건 안 된다" | **✔** |

**401 계열 처리(로그인 화면으로 보내기)를 하면** alice는 **"이미 로그인했는데 왜?"**라며 혼란에 빠진다. 로그인해도 같은 결과가 나오므로 **무한 루프처럼 느껴진다.**

**[[01-spring-security-filter-chain-foundations]]의 인증/인가 구분이 여기서 실전으로 쓰인다** — 실패의 **종류**를 구분하는 것 자체가 기능이다.

**사용자가 보는 화면**:
```
Access to localhost was denied
You don't have authorization to view this page.
HTTP ERROR 403
```

**그리고 뒤로 가서 자기 동영상을 지우면 정상 동작한다** — **같은 버튼, 같은 코드 경로, 다른 데이터 → 다른 결과.** 이것이 데이터에 근거한 판정의 모습이다.

## Q7. 사물함 비유가 깨지는 지점

**사물함 앞에 서기 위해 이미 사물함을 열어 본 셈이다.**

비유는 여기까지 맞는다 — 사물함을 열기 전에 **이름표와 학생증을 대조한다.**

**깨지는 지점 둘**:

1. **소유자를 알기 위해 엔티티를 먼저 읽어야 했다.** 실제 사물함은 **밖에 이름표가 붙어 있어** 열지 않고도 확인된다. 여기서는 **DB에서 꺼내야** 소유자를 안다. **그 읽기는 검사 전에 일어난다.**
2. **읽기와 쓰기의 권한이 다를 수 있다는 점을 표현하지 못한다.** 사물함은 열면 다 되지만, 여기서는 **"조회는 되고 삭제는 안 되는"** 상태가 정상이다. alice는 bob의 동영상을 **목록에서 볼 수 있다.**

**1번의 실무적 귀결**: **거절되더라도 `findById`는 실행됐다.** 권한 없는 사용자가 **조회를 유발할 수 있다**는 뜻이고, 조회 자체가 비싸다면 **앞단에서 한 번 더 거르는 편이 낫다.**
