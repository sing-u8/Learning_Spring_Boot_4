## Q1. 자바 코드를 안 바꿨는데 앱이 잠기는 이유

**조건부 자동 설정이다. 다섯 단계.**

1. 앱이 뜰 때 Spring Boot가 **classpath를 훑는다.**
2. Spring Security 클래스가 보인다 → **보안 자동 설정을 켠다.**
3. 자동 설정이 **기본 `SecurityFilterChain`을 등록한다.** 내용은 "모든 요청에 인증 필요 + 폼 로그인 + HTTP Basic".
4. 사용자 정보를 줄 빈이 필요한데 내가 만든 게 없다 → **임시로 `user` 한 명을 메모리에 만들고 비밀번호를 랜덤 생성한다.**
5. 그 비밀번호를 **콘솔에 찍는다.** 안 찍으면 아무도 들어갈 수 없으니까.

**4단계가 핵심이다.** Spring Boot는 **"사용자가 없으니 보안을 끄자"가 아니라 "사용자가 없으니 임시로 하나 만들자"를 골랐다.** 방향이 **잠그는 쪽**이다 — [[01-spring-security-filter-chain-foundations]]의 "안전한 기본값"이 여기서 구체적으로 나타난다.

## Q2. 랜덤 비밀번호가 "좋은 것이자 나쁜 것"

| | 좋은 상황 | 나쁜 상황 |
|---|---|---|
| **언제** | **CTO 시연** — "의존성 한 줄로 애플리케이션을 잠급니다" | **개발을 계속하려는 순간** |
| 왜 | 5초 만에 끝나는 시연. 설정 없이 안전한 상태가 된다 | 재시작마다 값이 바뀐다 |

**나쁜 쪽을 구체적으로**:

| 상황 | 무슨 일 |
|---|---|
| 코드를 고치고 재시작 | 비밀번호가 **새로 생성된다.** 콘솔을 다시 뒤진다 |
| 하루에 30번 재시작 | 30번 복사·붙여넣기 |
| 팀원과 화면 공유 | **상대의 값은 내 것과 다르다** |
| 자동화된 통합 테스트 | 실행할 때마다 값이 달라 **테스트에 적을 수가 없다** |
| **역할 구분** | 사용자가 `user` **하나뿐**이라 "관리자만" 규칙을 시험할 수 없다 |

**마지막 줄이 결정적이다.** 이 장의 목표는 "관리자만 동영상을 추가할 수 있다" 같은 규칙인데, **사용자가 한 명이면 그 규칙이 동작하는지 확인할 방법이 없다.**

## Q3. `spring.security.user.password`를 책이 접는 세 이유

```properties
spring.security.user.name=admin
spring.security.user.password=password
spring.security.user.roles=ADMIN
```

재시작해도 유지된다. 그런데 책은 **"확장되지 않는다"**며 접는다.

1. **사용자가 여전히 한 명이다.** 이 프로퍼티는 **"그 하나뿐인 기본 사용자"의 값을 바꿀 뿐**, 두 번째 사용자를 만들 수단이 없다. alice와 bob이 서로의 동영상을 못 지우게 하려면 **최소 두 명**이 필요하다.
2. **비밀번호가 설정 파일에 평문으로 남는다.** 그리고 이 파일은 **보통 형상 관리에 들어간다.**
3. **다음 단계로 이어지지 않는다.** 결국 사용자는 데이터베이스에서 와야 하는데, 프로퍼티 방식은 **그 방향으로 한 걸음도 나아가지 않는다.**

**3번이 책의 실제 논거다** — *"비슷한 노력으로 더 현실적인 출발점에 설 수 있다."* 같은 시간을 들여 `UserDetailsService`를 만들면 [[04-spring-data-backed-users]]로 바로 이어진다.

**그리고 이건 랜덤 비밀번호보다 덜 안전하다.** 값이 고정이고 평문으로 남는다. **개발 편의를 위한 것이지 보안 개선이 아니다.**

## Q4. 두 스타터의 scope가 다른 이유

| 아티팩트 | scope | 하는 일 | 없으면 |
|---|---|---|---|
| `spring-boot-starter-security` | **(기본)** | 런타임에 필터 체인을 켠다 | 앱이 잠기지 않는다 |
| `spring-boot-starter-security-test` | **`test`** | `@WithMockUser`, `csrf()` 같은 테스트 지원 | **보안 규칙을 테스트할 수 없다** |

**`test` scope는 "이 라이브러리를 최종 배포물에 넣지 말라"는 지시다.**

**`test`를 빼면(= 기본 scope로 넣으면) 생기는 위험**: 테스트 도구가 **운영 배포물에 함께 들어간다.** 그것들은 운영에서 실행될 일이 없고, **오히려 들어 있으면 공격 표면만 넓힌다.** `@WithMockUser` 같은 것은 인증을 우회하는 도구다.

[[../chapter-3-querying-for-data-with-spring-boot/01b-adding-spring-data-jpa-to-our-project|Ch3의 `h2`에 `runtime` scope를 준 것]]과 같은 판단이다 — **필요한 단계에만 있게 하는 것이 보안이자 설계다.**

**처음부터 함께 넣는 이유**: 보안 규칙은 **성공 경로와 실패 경로를 둘 다** 시험해야 완성이다. "막히는지"의 확인은 **테스트로만 반복 가능하다.**

## Q5. 랜덤 비밀번호가 사라지는 메커니즘의 이름

**자동 설정 백오프(auto-configuration back-off)다.**

`UserDetailsService` 타입의 빈을 내가 만들면, **같은 역할의 빈이 이미 있으므로 자동 설정이 물러선다.** 임시 사용자를 만들던 그 코드가 실행되지 않고, 따라서 랜덤 비밀번호도 생성되지 않고 콘솔에도 안 찍힌다.

**[[../chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1에서 본 `@ConditionalOnMissingBean`]]이 그 실체다.**

**[[01-spring-security-filter-chain-foundations]]의 `SecurityFilterChain` 백오프와 같은 메커니즘이다.** 두 곳 모두 **"기본값에 얹는" 게 아니라 "대체한다".**

## Q6. 임시 자물쇠 비유가 깨지는 지점

**이 비유는 "열쇠가 매일 바뀐다"는 이상한 부분을 설명하지 못한다.**

비유는 여기까지 맞는다 — 새 집에 임시 자물쇠를 달아 준다. **문은 확실히 잠기고 열쇠도 하나 준다.**

**깨지는 지점**: 실제 자물쇠는 **열쇠가 그대로다.** Spring Boot의 랜덤 비밀번호는 **재시작할 때마다 바뀐다.**

**더 정확한 비유는 "매번 새 비밀번호를 발급하는 임시 출입증"이다.** 그래서 **오래 쓸 수 없다는 점이 핵심**이고, 그것이 이 절이 여기서 끝나지 않고 [[03-creating-users-with-userdetailsservice]]로 이어지는 이유다.

**한 가지 더 깨지는 점**: 자물쇠는 **밖에서 보면 잠겼는지 알 수 없다.** 이 비밀번호는 **콘솔에 평문으로 찍힌다.** 그 사실 자체가 **"보안 기능이 아니라 편의 기능"이라는 증거다.**
