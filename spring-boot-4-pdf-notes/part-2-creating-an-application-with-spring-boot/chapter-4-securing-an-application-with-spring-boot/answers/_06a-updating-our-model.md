## Q1. 보안 정책이 데이터 모델을 바꾸게 만드는 상황의 일반화

> **보안 규칙은 데이터 모델에 요구사항을 만든다.**

"소유자만 지울 수 있다"는 **순수한 정책 문제처럼 보이지만**, 실현하려면 **스키마에 컬럼이 하나 늘어야 한다.**

```
정책:  "alice는 자기 동영상만 지운다"
   ↓
필요:  "이 동영상이 누구 것인가"를 저장해야 한다
   ↓
결과:  VideoEntity.username 필드 추가 = 스키마 변경
```

**일반화하면**: **판정에 필요한 사실이 데이터에 없으면 그 규칙은 쓸 수 없다.** 정책은 **데이터가 뒷받침할 수 있는 만큼만** 표현된다.

**실무적 귀결**:
- 보안 요구사항은 **설계 초기에 나와야** 한다. 나중에 나오면 스키마 마이그레이션이 따라온다.
- "감사 로그가 필요하다", "승인자를 기록해야 한다" 같은 요구도 **전부 같은 형태**다.
- 반대로, **데이터 모델을 보면 표현 가능한 정책의 한계가 보인다.**

## Q2. `username`을 `@ManyToOne` 대신 문자열로 둔 이유와 대가

**이유: 비교 대상이 문자열이기 때문이다.**

보안 컨텍스트에서 꺼내는 값(`authentication.getName()`)은 **문자열**이고, 규칙은 이렇게 쓰인다.

```
#entity.username == authentication.name
```

**연관관계였다면 판정할 때마다 사용자 엔티티를 추가로 로딩해야 한다.** 삭제 한 번에 조회가 하나 더 붙는다.

**대가 — 참조 무결성이 없다**:
- **존재하지 않는 사용자 이름을 넣어도 DB가 막아 주지 않는다.**
- **사용자 이름이 바뀌면 동영상의 `username`은 옛 값으로 남는다.** 소유자를 잃는다.
- 사용자를 삭제해도 그 동영상들이 남는다.

**트레이드오프의 성질**: **읽기 성능과 단순함**을 얻고 **일관성 보장**을 잃었다. 소유권 판정이 **매우 자주** 일어나고 사용자 이름 변경은 **거의 없다면** 좋은 거래다.

**대안**: 사용자 이름을 불변으로 만들거나(변경 불가 정책), 변경 시 관련 데이터를 함께 갱신하는 절차를 둔다.

## Q3. 사용자를 두 명 이상으로 늘려야 하는 이유 — 테스트 관점

> **"막혀야 하는 경로"를 시험하려면 막힐 사람이 필요하다.**

| 사용자 수 | 시험할 수 있는 것 | **시험할 수 없는 것** |
|---|---|---|
| 1명 (`user`) | 자기 것 삭제 | **남의 것 삭제 거부** — **남이 없다** |
| 2명 (`alice`, `bob`) | 둘 다 | — |
| 3명 (+ `admin`) | 둘 다 + 역할 기반 규칙 | — |

**보안 규칙은 "통과"와 "거절" 두 경로가 다 맞아야 완성이다.** 통과만 확인하면 **"아무나 통과하는" 규칙도 테스트를 통과한다.**

**구체적으로**: `alice`만 있으면 "alice가 자기 동영상을 지운다"는 확인되지만, **"bob이 alice 것을 못 지운다"는 확인할 수 없다.** 그런데 **후자가 이 규칙의 존재 이유다.**

**[[02-adding-spring-security-to-the-project]]에서 랜덤 비밀번호를 접은 이유와 같다** — *"사용자가 한 명뿐이면 그 규칙이 동작하는지 확인할 방법이 없다."*

## Q4. alice와 bob이 같은 역할인데도 서로를 못 건드리는 근거

**판정 기준이 역할이 아니라 데이터이기 때문이다.**

```
역할 기반:  hasRole("USER")          → alice도 bob도 통과. 구분 불가
데이터 기반: #entity.username == authentication.name
                    ↑ 이 동영상의 소유자    ↑ 지금 요청한 사람
```

**둘 다 `ROLE_USER`지만 `authentication.name`이 다르다.** alice의 요청에서는 `"alice"`, bob의 요청에서는 `"bob"`이다.

**즉 역할은 "무엇을 할 수 있는 종류의 사람인가"를 말하고, 소유권은 "어느 것에 대해 할 수 있는가"를 말한다.** 두 축이 직교한다.

| | 묻는 것 | 판정 재료 | 어디서 |
|---|---|---|---|
| 역할 | **어떤 종류의 사람인가** | 보안 컨텍스트 | **URL 규칙**으로 충분 |
| 소유권 | **이 데이터에 대해 그런가** | 데이터 + 컨텍스트 | **메서드 보안** 필요 |

**[[06-securing-spring-data-methods]]가 메서드 보안을 도입한 이유가 바로 이 두 번째 축이다.**

## Q5. `protected` 무인자 생성자가 여전히 필요한 이유

**JPA가 리플렉션으로 객체를 만들 때 무인자 생성자를 요구하기 때문이다.**

필드가 하나 늘었어도 이 요구는 그대로다 — **JPA는 조회 결과를 만들 때 빈 객체를 먼저 만들고 값을 채운다** ([[../chapter-3-querying-for-data-with-spring-boot/02a-entities-in-jpa|Ch3]]).

**`protected`인 이유**: **애플리케이션 코드가 실수로 쓰지 못하게** 한다. `public`이면 `new VideoEntity()`로 **필드가 다 `null`인 엔티티**를 아무 데서나 만들 수 있고, 그런 객체가 저장 경로에 흘러 들어가면 **소유자 없는 동영상**이 생긴다.

**보안 맥락에서 이 점이 더 무거워진다**: `username`이 `null`인 동영상은 **누구의 것도 아니다.** 소유권 검사가 `null == "alice"`가 되어 항상 거짓 — 아무도 지울 수 없는 유령 데이터가 된다.

**`this(null, null, null)` 위임**: 무인자 생성자가 3인자 생성자를 부른다. **초기화 로직이 한 곳에만 있게 된다** — 필드가 늘어도 한 곳만 고친다.

## Q6. Alice/Bob 관례가 A/B보다 나은 실질적 이유

**읽을 때 헷갈리지 않는다.**

- **`A`와 `B`**는 시각적으로 비슷하고, 문장 안에서 **변수처럼 읽힌다.** "A가 B의 것을 지우려 한다"는 두 번 읽어야 방향이 잡힌다.
- **`alice`와 `bob`**은 **첫 글자도 길이도 다르고**, 문장에서 **사람으로 읽힌다.** "alice가 bob의 것을 지우려 한다"는 한 번에 읽힌다.

**그리고 관례가 이미 있다.** 암호학·보안 문헌에서 Alice와 Bob은 **수십 년간 통신 참여자를 가리키는 표준 이름**이다. 배경 지식이 있는 독자는 **설명 없이도 역할을 안다** — Alice는 보내는 쪽, Bob은 받는 쪽, Eve는 도청자, Mallory는 능동적 공격자.

**테스트 코드에서의 실익**: 실패 메시지에 `alice`와 `bob`이 찍히면 **어느 시나리오가 깨졌는지** 바로 안다. `user1`, `user2`면 다시 코드를 봐야 한다.

## Q7. 이름표 비유가 깨지는 지점

**이름표는 사람에게 붙지만, 여기서는 데이터에 붙는다. 그리고 그 이름표가 사람과 끊어질 수 있다.**

비유는 여기까지 맞는다 — 물건마다 소유자 이름표를 붙여 두고, 가져가려는 사람의 이름과 대조한다.

**깨지는 지점 셋**:

1. **이름표가 실제 사람을 가리킨다는 보장이 없다.** Q2의 참조 무결성 문제다. 문자열이므로 **존재하지 않는 사람의 이름**을 적어도 막히지 않는다.
2. **사람 이름이 바뀌면 이름표는 그대로다.** 현실의 이름표는 다시 붙이지만, 여기서는 **동영상의 `username`이 옛 값으로 남는다.** 소유자를 잃는다.
3. **이름표를 확인하려면 물건을 먼저 꺼내야 한다.** 창고에서 물건을 보면 이름표가 보이지만, 여기서는 **DB에서 조회하기 전에는 아무것도 모른다** — [[06-securing-spring-data-methods]] Q7의 금고 비유와 같은 한계다.
