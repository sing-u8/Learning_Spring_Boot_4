## Q1. 등록부터 해야 하는 이유 — 인가 서버의 네 질문

| Google이 알아야 하는 것 | **모르면** |
|---|---|
| **이 요청을 보낸 앱이 누구인가** | **아무나 사용자 동의를 요구할 수 있다** |
| **인증 후 사용자를 어디로 돌려보내나** | **공격자가 지정한 주소로 인가 코드를 보내게 된다** |
| **이 앱이 요청할 수 있는 권한은 어디까지인가** | **아무 데이터나 요구할 수 있다** |
| **누가 이 앱을 쓸 수 있나** | **개발 중인 앱이 전 세계에 열린다** |

**이 네 질문에 미리 답해 두는 것이 등록이다.**

**흐름의 첫 줄이 근거다** — *"클라이언트가 사용자를 인가 서버로 리다이렉트한다."* 그 순간 Google은 **누가 무엇을 요구하는지 모르는 상태**다. 요청에 담긴 것만으로는 판단할 수 없으므로 **미리 등록된 정보와 대조**한다.

**15단계의 묶음이 네 질문에 대응한다**:

| 묶음 | 단계 | 답하는 질문 |
|---|---|---|
| 프로젝트 만들기 | 1–3 | (준비) |
| **API 활성화** | 4–6 | 권한 범위 |
| **자격 증명 발급** | 7–12 | 앱이 누구인가 + 어디로 돌려보내나 |
| **사용자 제한** | 13–15 | 누가 쓸 수 있나 |

## Q2. Client ID가 공개여도 되는 근거

**그것만으로는 아무것도 못 하기 때문이다.**

| | **Client ID** | **Client secret** |
|---|---|---|
| 비밀인가 | **아니다** | **그렇다** |
| 어디에 실리나 | **인가 요청 URL에 그대로** | **서버 대 서버 토큰 교환에만** |
| 브라우저가 보나 | **본다** | 보면 안 된다 |
| 유출되면 | 큰 문제 없음 | **우리 앱을 사칭할 수 있다** |
| 비유 | **가게 이름** | **가게 금고 열쇠** |

**Client ID로 할 수 있는 최대**: 인가 요청을 흉내 내는 것. 그런데 **인가 코드는 등록된 redirect URI로만 간다**(Q3) → 공격자에게 도달하지 않는다.

**그리고 코드를 토큰으로 바꾸려면 시크릿이 필요하다**([[07a-oauth-vs-openid-connect]]).

**두 방어가 겹쳐 있다** — 코드가 엉뚱한 데로 안 가고, 가더라도 교환이 안 된다. **그래서 ID는 공개해도 된다.**

**시크릿이 소스나 형상 관리에 들어가면 안 되는 이유**: **시크릿 하나로 우리 앱 행세를 할 수 있다.**

## Q3. redirect URI 사전 등록이 없다면 가능한 공격

**공격자가 인가 코드를 가로챈다.**

```
1. 공격자가 인가 요청 URL을 만든다
   .../authorize?client_id=우리앱ID&redirect_uri=https://attacker.example/steal
                              ↑ 공개값이라 안다      ↑ 아무 주소나 넣는다
2. 피해자에게 그 링크를 클릭시킨다
3. 피해자는 진짜 Google 화면을 본다 → 도메인이 맞으므로 의심하지 않는다
4. 동의한다
5. Google이 인가 코드를 attacker.example 로 보낸다
6. 공격자가 그 코드로 토큰을 받는다 (시크릿도 알고 있다면)
```

**3번이 이 공격의 핵심이다** — 피해자가 보는 화면은 **진짜 Google**이다. 주소창 검사로는 걸러지지 않는다.

**사전 등록이 막는 지점**: Google이 **등록된 목록에 없는 `redirect_uri`를 거절한다.** 1번에서 이미 실패한다.

**즉 "코드는 등록된 주소로만 간다"가 [[07a-oauth-vs-openid-connect]]의 Authorization Code Flow가 성립하는 전제다.** 그 전제가 없으면 코드/토큰 분리도 무의미하다.

## Q4. 왜 정확한 일치여야 하는가

**부분 일치나 와일드카드를 허용하면 Q3의 공격이 되살아나기 때문이다.**

```
등록:  https://our-app.example/login/oauth2/code/google

접두사 일치 허용 시:
  https://our-app.example.attacker.com/...    ← 도메인이 다른데 접두사가 맞을 수 있다
  https://our-app.example/login/oauth2/code/google/../../redirect?to=attacker
                                              ← 경로 조작

와일드카드 허용 시:
  https://*.our-app.example/...                ← 서브도메인 하나만 장악하면 끝
```

**공격자가 필요한 것은 "등록 패턴에 걸리는 주소 하나"다.** 패턴이 넓을수록 그런 주소를 찾기 쉽다.

**서브도메인 위험이 특히 현실적이다** — 회사가 쓰는 여러 서브도메인 중 **하나만 장악하거나 사용자 콘텐츠를 호스팅하는 곳이 있으면** 와일드카드가 통째로 뚫린다.

> **이 엄격함이 인가 코드 탈취를 막는 장치다.**

**대가**: **운영 배포 시 redirect URI를 다시 등록해야 한다.** `localhost:8080`은 개발용이고, **실제 도메인과 HTTPS 주소를 추가로 등록**해야 한다. **잊으면 배포 직후 로그인이 전부 실패한다.** 불편하지만 그 불편이 곧 안전장치다.

## Q5. API 활성화 단계를 건너뛰면

**스코프를 요청해도 거절된다.**

6단계에서 **YouTube Data API v3를 켜 두는 것**은, 우리 앱이 그 API에 대한 **스코프를 요청할 수 있게 하는 준비**다.

**즉 두 겹의 허가가 필요하다**:
1. **프로젝트 수준**: 이 API를 쓸 수 있는가 (활성화)
2. **사용자 수준**: 이 사용자가 동의했는가 (스코프)

**둘 다 있어야** 실제 호출이 된다.

**왜 나뉘어 있나**: **관심사가 다르다.** 활성화는 **개발자의 결정**(이 앱은 YouTube를 쓴다)이고, 동의는 **사용자의 결정**(이 앱에 내 YouTube를 열어 준다)이다. 개발자가 안 켠 API를 사용자가 동의할 수는 없다.

**증상**: 로그인은 되는데 **API 호출에서 실패**한다. 스코프 요청 단계에서 걸리거나 토큰이 그 API에 대해 무효다. **로그인이 되므로 원인을 찾기 어렵다.**

## Q6. test mode의 기본값이 다른 기본값들과 같은 방향인 이유

| | **test mode** | 게시(published) 후 |
|---|---|---|
| 로그인 가능한 사람 | **등록한 test users만** | 누구나 |
| Google 심사 | 불필요 | 민감한 스코프면 필요 |
| 개발 중 위험 | **없다 — 남이 못 들어온다** | — |

> **잘못 설정하면 열리는 게 아니라 닫힌다. 등록을 잊으면 나만 못 들어가고, 남이 들어오는 사고는 나지 않는다.**

**[[01-spring-security-filter-chain-foundations]]의 "안전한 기본값"과 같은 방향이다.** 그리고 [[05-securing-web-routes-and-http-verbs]]의 `denyAll()`, Spring Boot의 랜덤 비밀번호도 같다.

**이 장 전체를 관통하는 패턴이다**: **실수했을 때 덜 나쁜 쪽으로 실패하게 만든다.**

**흔한 오해**: **"test mode는 기능 제한이다"** → **기능은 같고 접근 가능한 사람만 제한된다.** 개발 중에는 **오히려 안전장치**다.

## Q7. 다른 제공자를 붙일 때도 찾아야 할 네 가지

| 공통 항목 | Google에서의 대응 |
|---|---|
| **애플리케이션 정의** | 프로젝트 + OAuth Client ID 생성 |
| **승인된 플랫폼 API** | YouTube Data API v3 활성화 |
| **지원 사용자** | test users 등록 |
| **우리 앱으로의 콜백** | Authorized redirect URIs |

**Google이든 GitHub이든 Okta든 이 넷이 필요하다.**

> **메뉴 위치와 이름만 다를 뿐 구조는 같다. 한 번 이해하면 다른 제공자에서도 어디를 찾아야 하는지 안다.**

**Q1의 네 질문과 정확히 대응한다** — 앱이 누구인가(정의), 권한 범위(API), 누가 쓸 수 있나(사용자), 어디로 돌려보내나(콜백).

**이것이 이 절을 배우는 진짜 이유다.** Google 콘솔의 메뉴 위치를 외우는 것이 아니라, **어느 제공자에서든 이 넷을 찾을 수 있게 되는 것**이다.

## Q8. 입주 신고 비유가 깨지는 지점

**호수를 잘못 적었을 때의 결과를 가볍게 보이게 한다.**

비유는 여기까지 맞는다 — **이름을 등록하고, 출입 카드를 받고, 택배를 받을 호수를 지정한다.**

**깨지는 지점**:

> **잘못된 주소로 배달되는 것이 남의 인가 코드이고, 그것을 받은 사람은 사용자를 사칭할 수 있다.**

> **택배 오배송이 아니라 열쇠 오배송에 가깝다.**

**택배는 잘못 가도 물건 하나를 잃는다.** 인가 코드가 잘못 가면 **그 사용자의 계정 전체**가 넘어간다. 그리고 **피해자는 자기가 무엇을 잘못했는지 모른다** — 진짜 Google 화면에서 동의했을 뿐이다(Q3).

**두 번째로 깨지는 점**: 실제 입주 신고는 **한 번 하면 끝**이지만, redirect URI는 **환경마다 다시 등록해야** 한다. 개발·스테이징·운영이 각각 다른 주소이고, **하나라도 빠지면 그 환경에서 로그인이 안 된다.**
