## Q1. 비밀번호를 암호화가 아니라 해시로 저장하는 근본 이유

> **우리가 비밀번호 원문을 알아야 할 이유가 없다.**

로그인할 때 하는 일은 **"제출된 값이 저장된 값과 같은가"를 판정하는 것뿐**이다.

> **복호화가 필요 없다면 복호화가 불가능한 편이 낫다.**

**암호화의 문제**: 복호화가 가능해야 하고, 그러려면 **키를 어딘가에 보관**해야 한다. **그 키가 같은 서버에 있으면 DB를 턴 공격자가 키도 가져간다.**

**즉 암호화는 "키를 어디에 둘 것인가"라는 새 문제를 만든다.** 해시는 **그 문제 자체를 없앤다** — 지킬 키가 없다.

**보안 원칙의 형태**: [[08-leveraging-google-to-authenticate-users]]의 **"없는 데이터는 유출될 수 없다"**와 같은 계열이다. **방어를 강화하는 대신 방어할 대상을 없앤다.**

**저장 중 데이터 보호의 전제**: **저장소가 통째로 유출된 상황을 전제로 설계한다.** "유출되지 않게 하자"가 아니라 "유출돼도 쓸모없게 하자"다.

## Q2. 잊은 비밀번호를 이메일로 보내 준다면

**해시하지 않았다는 뜻이다.**

**서버조차 사용자의 비밀번호를 모른다.** 저장된 것은 해시뿐이고 **되돌릴 수 없다.**

> **그래서 "비밀번호를 잊었다"에 대한 답이 "알려 드리겠습니다"가 아니라 "재설정하세요"인 것이다.**

**알려 줄 수 있다는 것은**:
- 원문을 그대로 저장했거나
- 복호화 가능한 형태로 저장했다 → **키가 서버에 있다** → Q1의 문제

**둘 다 유출 시 계정이 즉시 끝난다.**

**사용자가 확인할 수 있는 신호다** — 서비스가 원문을 보내 준다면 **그 서비스의 저장 방식을 의심할 근거**가 된다. 그리고 **이메일 자체가 평문 채널**이라는 문제도 겹친다.

**피해가 그 서비스에서 끝나지 않는다**: **사용자들이 다른 사이트에서도 같은 비밀번호를 쓴다.** 한 곳의 유출이 **남의 서비스 침해로 번진다.**

## Q3. 솔트가 막는 공격과 반복 라운드가 막는 공격

| | **솔트** | **반복 라운드** |
|---|---|---|
| 막는 것 | **레인보우 테이블** | **무차별 대입 공격** |
| 공격의 형태 | **미리 계산해 둔 표**에서 찾는다 | 가능한 값을 **하나씩 대입**한다 |
| 왜 막히나 | **사용자마다 다른 값**이 섞여 미리 만든 표가 무력해진다 | **해시 한 번이 느려져** 초당 시도 횟수가 급감한다 |

**솔트가 없으면**: `password`, `123456` 같은 값의 해시는 **이미 다 계산돼 있다.** 그리고 **같은 비밀번호를 쓴 사용자들은 해시도 같아서 한 번에 드러난다.**

**솔트만 있으면**: 표는 무력해지지만 **계정 하나를 골라 집중하면** 뚫린다. **현대 GPU는 초당 수십억 번 해시를 계산한다.**

**반복이 바꾸는 것**: **정상 로그인은 0.1초쯤 걸리지만 공격자의 초당 시도 횟수는 수십억에서 수백으로 떨어진다.**

**두 방어가 다른 축이다** — 솔트는 **사전 계산**을, 반복은 **실시간 계산 속도**를 막는다. **하나만으로는 부족하다.**

**"BCrypt가 느린 건 단점이다"는 오해**: **의도된 설계다.**

## Q4. 솔트를 별도 컬럼에 저장하지 않아도 되는 이유

**BCrypt가 만드는 값이 솔트와 반복 횟수를 자기 안에 담기 때문이다.**

```text
$2a$10$N9qo8uLOickgx2ZMRZoMye...
 │   │  └─ 솔트 + 해시
 │   └─ 반복 횟수 (2^10)
 └─ 알고리즘 식별자
```

**검증할 때 저장값에서 솔트와 라운드를 읽어 같은 조건으로 다시 계산한다.**

**"솔트는 비밀이어야 한다"는 오해**: **비밀이 아니다.** 저장값에 **그대로 들어 있다.** 역할은 **숨기는 게 아니라 미리 계산한 표를 무력화**하는 것이다.

**이 설계의 실용적 이점**:
- **컬럼이 하나면 된다** — 스키마가 단순하다
- **알고리즘과 라운드가 값에 기록돼 있다** → Q5의 마이그레이션이 가능해진다
- **값 하나를 옮기면 검증에 필요한 것이 전부 따라간다**

## Q5. "적응형"이 몇 년 뒤에 가능하게 하는 것

> **반복 횟수를 설정으로 올릴 수 있어서, 하드웨어가 빨라져도 같은 알고리즘으로 난이도를 따라 올릴 수 있다. 몇 년 뒤에 알고리즘을 갈아엎지 않아도 된다.**

**문제의 성질**: 하드웨어는 계속 빨라진다. **오늘 0.1초 걸리는 계산이 5년 뒤에는 0.01초**가 된다. **방어가 시간이 갈수록 약해진다.**

**적응형이 아니라면**: 알고리즘 자체를 바꿔야 한다 → **모든 사용자의 비밀번호를 다시 해시해야 하는데, 원문이 없으므로 불가능하다.** 로그인할 때 하나씩 갈아 끼우는 점진적 마이그레이션밖에 방법이 없고, 그동안 두 알고리즘을 동시에 지원해야 한다.

**적응형이면**: **라운드 수만 올린다.** 그리고 Q4 덕분에 **각 저장값이 자기 라운드를 기록하고 있으므로**, 옛 값도 그대로 검증되고 **새로 저장되는 것만 새 라운드**를 쓴다. **혼재가 자연스럽게 처리된다.**

**경계**: `new BCryptPasswordEncoder()`는 **기본값을 쓴다.** 운영에서는 **자기 하드웨어에서 목표 지연 시간을 측정해 정하는 편이 낫다.**

## Q6. `withDefaultPasswordEncoder()`를 그대로 두면

**이미 해시된 값을 또 인코딩해 검증이 깨진다.**

```java
// 저장할 때:  encoder.encode("password")  →  $2a$10$N9qo...  (해시)
// 조회할 때:  withDefaultPasswordEncoder()가 그 해시를 또 인코딩
//             → 검증 대상이 "해시의 해시"가 된다  →  로그인 실패
```

| | `withDefaultPasswordEncoder()` | **`withUsername()`** |
|---|---|---|
| 비밀번호를 어떻게 다루나 | **자체적으로 인코딩**(사실상 평문) | **손대지 않는다** |
| 검증은 누가 | 그 자체 규칙 | **등록된 `PasswordEncoder` 빈** |

**`asUser()`에서 딱 한 줄 바뀐다** — `User.withDefaultPasswordEncoder()` → `User.withUsername()`.

**"스타일 차이"라는 오해**: **동작이 달라진다.**

**증상**: **모든 로그인이 실패한다.** 그런데 **오류 메시지는 "아이디 또는 비밀번호가 틀립니다"**이므로, **비밀번호를 잘못 입력했다고 생각**하게 된다. 인코더 설정 문제라는 신호가 없다.

**이 장 내내 남겨 둔 빚이 여기서 청산된다** — [[03-creating-users-with-userdetailsservice]]에서 경고하고, [[04-spring-data-backed-users]]에서 미뤘던 것.

## Q7. 같은 원문을 쓴 세 사용자의 저장값이 다른 이유

**솔트가 매번 새로 만들어지기 때문이다.**

```java
repository.save(new UserAccount("alice", encoder.encode("password"), ...));
repository.save(new UserAccount("bob",   encoder.encode("password"), ...));
repository.save(new UserAccount("admin", encoder.encode("password"), ...));
//                                        ↑ 같은 원문인데 결과가 셋 다 다르다
```

**`encode()`를 부를 때마다 BCrypt가 새 랜덤 솔트를 만들어 섞는다.**

> **이것이 레인보우 테이블 방어가 실제로 동작하는 모습이다.**

**왜 이것이 중요한가**:
- **유출된 테이블을 봐도 "누가 같은 비밀번호를 쓰는지" 알 수 없다.** 솔트가 없으면 **해시가 같은 행끼리 묶여** 그 정보가 드러난다.
- **표에서 한 번 찾으면 그 비밀번호를 쓰는 모두가 뚫리는 일**이 없다. **계정마다 따로 공격해야 한다.**

**부수 효과**: 같은 원문으로 `encode()`를 두 번 부르면 **다른 값이 나오므로**, 검증할 때 **문자열 비교로는 안 된다.** 반드시 `matches(원문, 저장값)`를 써야 한다 — 그것이 저장값에서 솔트를 읽어 같은 조건으로 재계산한다(Q4).

## Q8. 파쇄기 비유가 깨지는 지점

**같은 문서인지 확인할 수 있다는 핵심을 담지 못한다.**

비유는 여기까지 맞는다 — **되돌릴 수 없고, 같은 문서는 늘 같은 모양으로 잘린다.**

**깨지는 지점**:

> **진짜 파쇄기는 조각을 보고 원본을 대조할 수 없지만, 해시는 새 문서를 같은 파쇄기에 넣어 조각이 일치하는지 볼 수 있다.**

> **그 비교 가능성이 없으면 로그인이 성립하지 않는다.**

**해시의 가치는 "되돌릴 수 없음"과 "비교할 수 있음"이 동시에 성립한다는 것이다.** 하나만 있으면 쓸모없다 — 되돌릴 수 있으면 안전하지 않고, 비교할 수 없으면 로그인을 못 한다.

**두 번째로 깨지는 점**: 파쇄기는 **같은 문서를 늘 같은 모양으로** 자르지만, **솔트 때문에 같은 비밀번호도 매번 다른 값**이 나온다(Q7). **"같은 입력 → 같은 출력"이 성립하지 않는다** — 솔트를 고정해야만 성립한다.

**세 번째**: 파쇄기는 **빠를수록 좋지만** BCrypt는 **느릴수록 좋다**(Q3). 도구의 목표가 반대다.
