## Q1. 보안 검사를 필터에 두면 좋아지는 세 가지

| 컨트롤러 안에 둘 때의 문제 | 실패 시나리오 | 필터가 주는 해결 |
|---|---|---|
| **빠뜨리면 조용히 뚫린다** | 컨트롤러 메서드를 새로 추가하면서 검사 두 줄을 잊는다. **컴파일도 되고 테스트도 통과한다.** 그 엔드포인트만 무방비 | 필터는 **모든** 요청을 통과시키므로 새 엔드포인트도 **자동으로** 검사를 받는다. 기본값이 "막힘"이고 **여는 것이 명시적 선언**이다 |
| **정책이 코드 전체에 흩어진다** | "관리자만 들어갈 수 있는 경로가 뭐지?"에 답하려면 **컨트롤러를 전부 읽어야** 한다 | 규칙이 `SecurityFilterChain` 빈 **한 곳**에 모인다. 그 파일 하나로 정책 전체가 보인다 |
| **너무 늦다** | 위조된 요청(CSRF)이 이미 비즈니스 로직에 들어와 서비스·리포지토리를 건드린 뒤 거절된다 | 컨트롤러·서비스·리포지토리가 **아직 실행되기 전**이라 거절해도 **아무 부작용이 남지 않는다** |

**첫 번째가 가장 무섭다** — 실패가 **아무 신호를 남기지 않는다.** 나머지 둘은 불편이지만 이건 사고다.

## Q2. 401과 403을 잘못 돌려주면

| 상황 | 올바른 코드 | 뜻 |
|---|---|---|
| 로그인하지 않았다 | **401** (또는 로그인 화면) | "당신이 **누구인지 모르겠다.** 먼저 밝혀라" |
| 로그인했지만 권한이 없다 | **403** | "당신이 누구인지는 **안다.** 그런데 이건 안 된다" |

**뒤바꾸면**:
- **401인데 로그인 화면을 안 띄우면** → 사용자는 **막힌 채로 남는다.** 무엇을 해야 할지 알 방법이 없다.
- **403인데 로그인 화면을 띄우면** → **이미 로그인한 사용자에게 다시 로그인하라고** 한다. 로그인해도 같은 화면으로 돌아오는 무한 루프처럼 느껴진다.

**그래서 실패의 "종류"를 구분하는 것 자체가 기능이다.**

> **401의 이름은 역사적 사고다.** 실제 뜻은 "Unauthenticated"에 가깝지만 HTTP 규격에 `Unauthorized`로 굳어 버렸다. **이름만 보고 "인가 실패"로 읽으면 정확히 반대로 이해하게 된다.**

## Q3. 인가를 인증보다 먼저 할 수 없는 이유

**인가는 인증 결과를 재료로 쓰기 때문이다.**

- **인증** = **누구인가?**
- **인가** = **(그 누구가) 무엇을 해도 되는가?**

두 번째 질문은 첫 번째의 답을 **입력으로 요구한다.** 신원이 확정되지 않은 상태에서 "이 사람이 관리자인가"를 물을 수 없다 — 물을 대상이 없다.

**네 단계 순서가 전부 같은 논리다**:

| 단계 | 하는 일 | 왜 이 순서인가 |
|---|---|---|
| 1 | **인증 정보 추출** | 판정하려면 **먼저 재료가 있어야** 한다 |
| 2 | **인증 수행** | 재료가 진짜인지 확인해야 이후 판정이 의미를 갖는다 |
| 3 | **인가 규칙 적용** | **신원이 확정된 뒤에야** "해도 되는가"를 물을 수 있다 |
| 4 | **CSRF 등 방어** | **인증된 사용자를 노리는** 공격이 있으므로, 인증 성공만으로 통과시키면 안 된다 |

**4번이 3번 뒤인 것도 같은 이유다** — CSRF는 "로그인한 사용자의 브라우저를 이용하는" 공격이므로 인증이 끝난 뒤에야 문제가 된다.

## Q4. 기본값이 "전부 인증 필요" vs "전부 허용"

**설정을 잊었을 때 일어나는 일이 정반대다.**

| 기본값 | 설정을 잊으면 | 증상 |
|---|---|---|
| **"전부 잠김"** (Spring Security의 선택) | **전부 막힌다** | 즉시 눈에 띈다. 아무도 못 들어온다 |
| "전부 허용" | **전부 뚫린다** | **아무도 모른다.** 데이터가 새는 동안 애플리케이션은 정상으로 보인다 |

**핵심은 "실패의 방향"이다.**

> **잘못된 쪽으로 실패해도 데이터가 새지는 않는다.**

막히는 실패는 **개발 중에 즉시 발견된다** — 화면이 안 뜨니까. 뚫리는 실패는 **사고가 난 뒤에야** 발견된다.

**이것이 안전한 기본값(secure by default) 설계의 정의다** — 잘못될 때 **덜 나쁜 쪽으로** 잘못되게 만든다.

## Q5. `SecurityFilterChain` 빈을 정의했더니 로그인 화면이 사라진 이유

**자동 설정 백오프가 일어나 기본 정책이 통째로 대체됐기 때문이다.**

기본값은 세 가지를 켜 준다:
- 모든 요청 인증 요구
- **폼 로그인**과 **HTTP Basic**
- CSRF 방어

내가 `SecurityFilterChain` 빈을 하나 정의하면 **같은 역할의 빈이 있으므로 자동 설정이 물러선다.**

> **"기본값에 내 규칙을 얹는" 게 아니라 "기본값을 통째로 대체한다."**

그래서 내 정책에서 `formLogin()`을 다시 켜지 않으면 **로그인 화면 자체가 없다.** 인증은 요구하는데 인증할 방법이 없는 상태가 된다.

**[[../chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1의 `@ConditionalOnMissingBean` 백오프]]와 같은 메커니즘이다.** 거기서 본 대로 **"아무 일도 일어나지 않는 것이 정상 동작"**이라 조용하다.

**그래서 [[05-securing-web-routes-and-http-verbs]]에서 이 장의 모든 정책이 `formLogin`과 `httpBasic`을 매번 다시 적는다.**

## Q6. 검색대 비유가 깨지는 지점

**검색대는 건물 입구에만 있지만, Spring Security의 검사는 방마다 다시 놓을 수 있다.**

비유는 여기까지 잘 맞는다 — 신분증 확인(인증) → 출입증 등급 확인(인가) → 들여보냄.

**깨지는 지점**: 비유는 **입구를 통과한 뒤에는 검사가 없다**는 인상을 준다. 실제로는 **통과한 뒤에도 메서드 호출마다 다시 검사할 수 있고**, 이 장 후반부가 정확히 그 이야기다 — [[06-securing-spring-data-methods]], [[06e-enabling-method-level-security]].

**왜 두 겹이 필요한가**: 입구 검사(필터)는 **URL과 HTTP 메서드**만 본다. "이 동영상의 소유자인가"처럼 **데이터를 봐야 답이 나오는** 규칙은 URL만으로 표현할 수 없다 → Q7.

## Q7. 필터만으로 표현할 수 없는 규칙

**"이 동영상의 소유자인가"** 같은 규칙이다.

**왜 안 되나**: 필터는 요청이 **컨트롤러에 닿기 전에** 실행된다. 그 시점에는 **아직 데이터를 조회하지 않았다.**

```
GET /videos/42/delete

필터가 아는 것:  경로 "/videos/42/delete", 메서드 GET, 로그인한 사용자 "alice"
필터가 모르는 것: 42번 동영상의 소유자가 누구인가   ← DB를 봐야 안다
```

URL에 `42`가 있지만 **그것이 alice의 것인지는 조회해야** 알 수 있다. 그리고 조회는 **필터가 아니라 서비스·리포지토리가 하는 일**이다.

**같은 계열의 다른 예**:
- "이 사용자의 잔액이 충분한가"
- "이 문서가 이미 승인되었는가"
- "요청한 수량이 재고 이하인가"

**전부 "데이터에 답이 있는" 규칙이다.**

**그래서 [[06-securing-spring-data-methods]]의 메서드 레벨 보안이 따로 필요하다** — 데이터를 다루는 지점에서 다시 검사한다. 두 층은 경쟁 관계가 아니라 **볼 수 있는 정보가 다른** 두 자리다.
