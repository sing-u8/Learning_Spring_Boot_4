## Q1. 액세스 토큰만으로 사용자를 식별하면 가능한 공격

**남의 계정으로 로그인하는 공격이다.**

**"토큰으로 프로필 API를 부르면 되지 않나?"** — 실제로 그렇게들 했고, **그게 문제였다.**

```
공격자가 다른 앱을 위해 발급된 토큰을 손에 넣는다
   → 그 토큰을 우리 앱에 들이민다
   → 우리 앱이 그 토큰으로 프로필 API를 부른다
   → 프로필 API는 순순히 답한다 (그 토큰은 유효하니까)
   → 우리 앱은 그 사용자로 세션을 만든다
   → 공격자가 남의 계정으로 로그인했다
```

**핵심 결함**: 프로필 API로 얻은 정보에는 **"이 토큰이 정말 우리 앱을 위해 발급된 것인가"를 확인할 수단이 없다.**

**공격자가 그런 토큰을 얻는 경로**: 자기가 만든 악성 앱에 피해자가 동의하게 하면, **그 앱을 위한 유효한 토큰**을 얻는다. 그것을 우리 앱에 들이민다.

> **신원 확인은 형식을 갖춰야 한다.**

## Q2. ID 토큰의 어떤 필드가 그 공격을 막나

**수신 대상(audience) 필드다.**

**"이 토큰은 클라이언트 ID `xyz`를 위해 발급됐다"가 토큰 안에 적혀 있고, 인가 서버의 서명으로 위조가 막혀 있다.**

**우리 앱은 그 값이 자기 클라이언트 ID와 같은지 확인한다.** 다른 앱용 토큰을 들이밀면 **여기서 걸린다.**

| | 액세스 토큰 | **ID 토큰** |
|---|---|---|
| 내용 | **불투명해도 됨** | 사용자 식별자·발급자·**수신 대상**·만료가 담긴 **검증 가능한 구조** |
| 검증 | 자원 서버가 한다 | **우리 앱이 서명을 검증한다** |

**두 가지가 함께 필요하다**: **수신 대상 필드**(무엇을 검사할지)와 **서명**(그 값을 위조 못 하게).

**OIDC는 OAuth를 대체하지 않는다. 위에 얹는다.** 더하는 것은 **ID 토큰 하나**다. 흐름은 OAuth 그대로이고 **스코프에 `openid`가 들어가는 것**이 "OIDC로 동작하라"는 신호다.

## Q3. 코드와 토큰을 나눈 이유 — "브라우저를 지나는 값"

**브라우저 리다이렉트는 주소창·히스토리·리퍼러·서버 로그에 값을 남긴다.**

```
그 자리에 토큰을 두면  → 새어 나가고 즉시 악용된다
그 자리에 코드를 두면  → 새어도 코드만으로는 교환이 안 된다
```

**4단계 흐름**:

| 단계 | 일어나는 일 | 이유 |
|---|---|---|
| 1 | 사용자를 인가 서버로 리다이렉트 | 비밀번호를 우리가 안 받으려면 |
| 2 | 사용자가 인가 서버에서 인증 | 비밀번호가 인가 서버에만 머문다 |
| 3 | **인가 코드**를 돌려줌 | **이 값은 브라우저를 거치므로 노출된다. 그래서 토큰이 아니라 코드여야 한다** |
| 4 | 코드를 **액세스 토큰**과 교환 | **서버 대 서버**로, 클라이언트 시크릿과 함께 |

**두 성질**:
1. **액세스 토큰이 브라우저에 노출되지 않는다.** 브라우저를 지나는 것은 코드뿐이고 **코드만으로는 아무것도 못 한다.**
2. **토큰 교환이 서버 대 서버로 일어난다.** 그래서 **서버 사이드 웹 애플리케이션에 권장**된다.

**코드가 안전한 이유**: 교환하려면 **클라이언트 시크릿**이 필요하다. 코드를 가로챈 사람은 그것이 없다 — **다만 시크릿이 노출된 경우가 문제다** → Q4.

## Q4. PKCE가 막는 상황과 원래 모바일용이었던 이유

**막는 상황**: **코드가 가로채졌고 클라이언트 시크릿까지 알려져 있을 때.**

Q3의 방어는 "시크릿이 있어야 교환된다"에 기댄다. **시크릿이 새면 그 방어가 무너진다.**

**모바일용이었던 이유**: **모바일 앱이나 SPA는 시크릿을 숨길 수 없다.** **앱을 디컴파일하면 시크릿이 나온다.** 서버와 달리 코드가 사용자 기기에 있다.

**PKCE의 동작**:

| 단계 | 클라이언트 | 인가 서버 |
|---|---|---|
| 1 | **코드 검증자**(매 요청 새로 만드는 랜덤 비밀값) 생성 | — |
| 2 | 그것을 **해시한 코드 챌린지**를 인가 요청에 실어 보냄 | 챌린지를 코드와 함께 기억 |
| 3 | 코드를 교환할 때 **원본 검증자**를 제시 | 받은 검증자를 해시해 **기억한 챌린지와 비교** |
| 4 | — | 일치하지 않으면 **거절** |

**이름을 풀면** "Proof Key for Code Exchange" — **코드 교환을 위한 증명 키**다. **이름이 곧 하는 일이다.**

**OAuth 2.1은 모든 클라이언트에 PKCE를 의무화했다.** 시크릿을 잘 숨긴 서버 클라이언트라도 **방어가 한 겹 더 있어서 나쁠 게 없다**는 판단이다. Spring Security는 공개 클라이언트에 **자동으로** 켠다.

## Q5. 코드 검증자가 네트워크에 나가지 않는다는 사실이 결정적인 이유

**공격자가 코드를 가로채도 검증자를 모르기 때문이다.**

```
네트워크에 나간 것:  코드 챌린지 (= 검증자의 해시)
클라이언트 메모리에만: 코드 검증자 (원본)
```

**해시는 되돌릴 수 없으므로 챌린지에서 원본을 만들어 낼 수 없다.**

**그래서 공격자가 가진 것으로는 부족하다**:
- 코드 ✔ (가로챘다)
- 클라이언트 시크릿 ✔ (디컴파일로 얻었다)
- **코드 검증자 ✘** ← 여기서 막힌다

**그리고 매 요청마다 새로 만든다.** 한 번 알아내도 다음 요청에는 못 쓴다.

**설계의 우아함**: **추가 인프라가 필요 없다.** 서버에 비밀을 더 저장하지도, 새 통신 채널을 열지도 않는다. **한쪽만 아는 값을 만들고 그 해시를 미리 맡겨 두는 것**만으로 성립한다.

## Q6. Implicit Flow가 당시 합리적이었던 이유와 지금 제거된 이유

**제거된 이유**: **코드 대신 토큰 자체를 브라우저 리다이렉트로 돌려주었기 때문에** 토큰이 **주소창·히스토리·리다이렉트 URI 처리 과정에 그대로 노출**됐다 — Q3이 피하려던 바로 그 자리다.

**당시에는 이유가 있었다**:
- **브라우저 자바스크립트가 서버 대 서버 교환을 할 수 없던 시절**이었다
- **CORS가 지금처럼 정리되기 전**이었다

**즉 코드를 받아도 그것을 토큰으로 바꿀 방법이 브라우저에 없었다.** 토큰을 직접 받는 것 말고 선택지가 없었다.

**그 제약이 사라지자 존재 이유도 사라졌고, Authorization Code Flow + PKCE가 그 자리를 대신했다.**

**교훈의 형태**: **보안 규격의 "나쁜 설계"가 처음부터 나빴던 것은 아니다.** 환경 제약이 만든 타협이었고, 제약이 사라지면 타협도 걷어내야 한다. **그런데 이미 쓰이고 있는 것을 걷어내는 데는 시간이 걸린다** — 그것이 2.1까지 걸린 이유다.

## Q7. OAuth 2.1이 "새 기능이 아니라 정리"인 이유 — 네 항목

| 한 일 | 내용 |
|---|---|
| **제거** | **Implicit Flow** |
| **의무화** | **모든 클라이언트에 PKCE** |
| **승격** | **Authorization Code Flow를 표준 방식으로** |
| **명확화** | **보안 권고사항 정리** |

**네 항목 어디에도 "새로 만든 것"이 없다.** 전부 **이미 있던 것을 빼거나, 필수로 만들거나, 기본으로 올리거나, 문서에 명시**한 것이다.

> **흩어져 있던 모범 사례를 규격 본문으로 끌어들였다.**

**왜 이것이 의미 있나**: 2.0 시절에는 **"이렇게 하는 게 좋다"는 별도 문서**에 있었다. 규격만 읽고 구현하면 **낡은 방식으로 만들 수 있었다.** 2.1은 **규격을 읽으면 바로 안전한 것을 만들게** 한다.

**결과 — 권장이 단순해진다**: **사용자 로그인은 Authorization Code Flow + PKCE, 서비스 간 통신은 Client Credentials Flow.** 흐름이 여러 개처럼 보이지만 **실질적으로 둘이다.**

## Q8. 출입증/신분증 비유가 깨지는 지점

**신분증을 보여 주는 상대를 흐린다.**

비유는 여기까지 맞는다 — **출입증(액세스 토큰)은 문을 열어 주고, 신분증(ID 토큰)은 내가 누구인지 말해 준다.**

**깨지는 지점**:

> **ID 토큰은 자원 서버가 아니라 우리 앱에게 보이는 것이고, 우리 앱이 서명을 검증한 뒤 버린다.**

> **밖에 들고 다니는 물건이 아니라 입국 심사대에서 한 번 확인하고 회수하는 서류에 가깝다.**

**실제 신분증은 여러 곳에서 반복해 제시한다.** ID 토큰은 **한 번 검증하고 끝**이다. 이후 요청은 우리 앱이 만든 세션으로 처리한다.

**그래서 경계가 하나 나온다**: **ID 토큰을 API 호출에 쓰지 마라.** ID 토큰은 **우리 앱을 향한** 신분증이고, **자원 서버를 향한** 것은 액세스 토큰이다. 바꿔 쓰면 자원 서버가 거절하거나, **더 나쁘게는 받아 주면서 검증 모델이 무너진다.**

**두 번째로 깨지는 점**: 비유에는 **리프레시 토큰**에 해당하는 것이 없다. 그리고 그것이 **가장 위험하다** — 수명이 길어 유출되면 오래 악용된다. **서버에만 두어야 한다.**
