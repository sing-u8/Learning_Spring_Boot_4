## Q1. "자기 동영상만 삭제"를 URL 규칙으로 쓸 수 없는 이유

**판정에 필요한 재료가 요청 안에 없기 때문이다.**

| 재료 | URL 규칙이 볼 수 있나 | 왜 |
|---|---|---|
| 경로 `/delete/videos/7` | ✔ | **요청 줄에 그대로 있다** |
| HTTP 메서드 `POST` | ✔ | 요청 줄에 그대로 있다 |
| 현재 사용자가 alice라는 것 | ✔ | 보안 컨텍스트에 있다 |
| **7번 동영상의 소유자** | **✘** | **데이터베이스를 읽어야 안다** |

넣을 수 있는 규칙이 하나도 없다:
- `authenticated()` → alice와 bob **모두 통과.** 서로의 것을 지운다
- `hasRole("USER")` → 같은 결과
- `hasRole("ADMIN")` → **alice가 자기 것도 못 지운다**

**그리고 필터는 컨트롤러보다 먼저 실행된다.** 아직 **아무 조회도 일어나지 않은 시점**이다. 요청 안에 있는 것은 `7`이라는 숫자뿐이고, 그것이 누구 것인지는 조회해야 안다.

## Q2. 필터가 직접 DB를 조회하게 만들면

**두 가지가 나빠진다.**

1. **같은 조회를 두 번 한다.** 필터가 7번 동영상을 조회해 소유자를 확인하고, 통과하면 서비스가 **다시** 조회해 삭제한다. 요청 하나에 불필요한 왕복이 는다.
2. **보안 설정 파일에 데이터 접근 코드가 들어간다.** `SecurityConfig`가 리포지토리를 주입받게 되고, 정책 파일이 도메인 지식을 갖게 된다. **"정책을 한곳에 모아 읽기 쉽게"라는 [[05-securing-web-routes-and-http-verbs]]의 이점이 사라진다.**

**더 근본적으로**: 필터는 **모든 요청**을 통과시킨다. 특정 경로의 소유권 검사를 위해 필터에 조회 코드를 넣으면, **그 경로인지 판별하는 분기**부터 필터에 들어간다. 필터가 라우팅 지식까지 갖게 된다.

**옳은 방향**: **검사를 재료가 갖춰지는 자리로 옮긴다** — 엔티티를 손에 넣은 뒤, `repository.delete(entity)` 호출 직전.

## Q3. 메서드 보안을 컨트롤러에 남발하면

**"한 방식을 다른 방식으로 바꾼 것뿐"이 된다.**

컨트롤러 메서드마다 `@PreAuthorize("hasRole('ADMIN')")`을 붙이는 것은 **URL 규칙을 애노테이션으로 옮겨 적은 것**에 지나지 않는다.

**그러면 [[05-securing-web-routes-and-http-verbs]]가 지적한 문제가 그대로 돌아온다** — **정책이 코드 전체에 흩어진다.** "관리자만 갈 수 있는 경로가 뭐지?"에 답하려면 **컨트롤러를 전부 읽어야** 한다.

**판단 기준**:

| 규칙의 성격 | 어디에 | 이유 |
|---|---|---|
| "이 경로는 관리자만" | **URL 규칙** | **요청 정보만으로 판정된다.** 한곳에 모여야 읽기 쉽다 |
| "이 데이터의 소유자만" | **메서드 보안** | **데이터를 봐야 판정된다.** URL로는 불가능 |
| "인증한 사람만" | **URL 규칙** | 가장 넓은 그물은 가장 앞에 |

> **메서드 보안의 존재 이유는 "더 세밀한 잠금"이지 URL 규칙의 대체가 아니다. 둘은 같이 쓴다.**

## Q4. 애노테이션이 메서드 실행을 막는 메커니즘의 이름

**AOP 프록시다.**

Spring이 `VideoRepository`를 주입할 때 실제로 주는 것은 **원본이 아니라 프록시**다. **호출자는 그 사실을 모른다.**

```
VideoService --delete 호출--> [프록시] --권한 검사--> 진짜 구현
                                  └─ 실패 --> AccessDeniedException
```

**프록시가 먼저 권한을 검사하고, 통과하면 진짜 구현에 넘기고, 아니면 예외를 던진다.**

**[[../chapter-3-querying-for-data-with-spring-boot/02b-pojos-and-the-spring-programming-model|Ch3의 POJO 프록시]]와 같은 메커니즘이다.** 거기서 트랜잭션이 붙던 자리에 여기서는 권한 검사가 붙는다.

**중요한 성질**: **프록시를 거치지 않는 호출은 검사되지 않는다** → Q5.

---

## Q5. 자기 메서드를 부르면 검사가 안 되는 이유

**`this.delete(...)`는 프록시를 지나가지 않기 때문이다.**

```
바깥에서:  호출자 → [프록시] → 원본.methodA()        ✅ 검사됨
자기 호출:           원본.methodA() → this.delete()   ❌ 이미 프록시 안쪽
```

프록시는 **바깥에서 들어오는 호출을 가로채는 껍데기**다. 원본 객체 안에서 자기 메서드를 부르면 **껍데기를 지나지 않는다.**

**그리고 아무 경고가 없다.** 애노테이션은 붙어 있고 컴파일도 되고 실행도 된다. **검사만 안 된다.**

**같은 이유로 안 걸리는 것들**: `private` 메서드, `final` 클래스·메서드.

**[[../chapter-3-querying-for-data-with-spring-boot/02b-pojos-and-the-spring-programming-model|Ch3의 `@Transactional` self-invocation]]과 정확히 같은 함정이다.** 프록시 방식을 쓰는 모든 기능이 이 경계를 공유한다.

## Q6. URL 보안과 메서드 보안 중 하나만 고르면

**어느 쪽을 버려도 잃는 것이 크다.**

**URL 보안만 남기면**:
- **소유권 규칙을 표현할 수 없다** (Q1)
- 데이터에 답이 있는 모든 규칙이 불가능

**메서드 보안만 남기면**:
- **인증되지 않은 요청도 서비스 계층까지 들어와 조회를 일으킨 뒤에야 거절된다.** 낭비이고 **공격 표면도 넓어진다**
- **정책이 흩어진다** (Q3)
- 거절된 요청이 **부작용을 남길 수 있다** — [[01-spring-security-filter-chain-foundations]]의 "아무 부작용이 남지 않는다"가 사라진다

> **넓은 그물을 앞에, 촘촘한 그물을 뒤에.**

**두 층은 볼 수 있는 정보가 다르고 거절 비용도 다르다.** URL 층은 싸게 많이 거르고, 메서드 층은 비싸게 정확히 거른다.

## Q7. 금고 비유가 깨지는 지점

**금고 문 앞에 서기 전까지는 그 금고가 누구 것인지 알 수 없다.**

비유는 여기까지 맞는다 — URL 보안이 건물 입구 검색대라면, 메서드 보안은 **금고 앞에서 다시 하는 확인**이다. 입구를 통과했더라도 금고를 열려면 **이 금고가 내 것인지 다시 본다.**

**깨지는 지점**: 실제 금고는 **번호가 붙어 있고 명부를 보면 소유자를 안다.** 여기서는 **대상을 손에 넣기 전에는 판정할 재료가 없다.**

> **실제로는 그게 핵심이다 — 대상을 손에 넣기 전에는 판정할 재료가 없다.**

**그래서 부수 효과가 하나 생긴다**: **거절 시점이 늦다.** 소유자를 알려면 **조회가 먼저 일어나야** 하므로, **권한 없는 요청도 DB 조회 한 번은 유발한다.** URL 규칙처럼 "아무것도 실행하지 않고 거절"은 불가능하다.
