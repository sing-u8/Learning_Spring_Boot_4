## Q1. 보안의 네 축과 그 순서

| 축 | 하는 일 | **왜 이 순서인가** |
|---|---|---|
| 1. **사용자 출처 정의** | 누가 존재하는지 | **존재하지 않는 사용자에게 권한을 줄 수는 없다** |
| 2. **접근 규칙 생성** | 각 사용자가 뭘 할 수 있는지 | **사용자 목록이 있어야 역할을 붙일 수 있다** |
| 3. **앱의 각 부분과 규칙 연결** | 어느 경로에 어느 규칙을 | **규칙이 있어야 배치할 수 있다** |
| 4. **정책을 전 영역에 적용** | 웹·메서드·데이터 전부 | **한 군데라도 빠지면 우회로가 된다** |

**각 단계가 앞 단계의 산출물을 입력으로 쓴다.** 순서를 뒤집을 수 없다.

**이 장의 지도이기도 하다**: 이 절이 **1번**, [[05-securing-web-routes-and-http-verbs]]가 **2·3번**, [[06-securing-spring-data-methods]]가 **4번**이다.

**4번이 특히 중요한 이유**: 웹 경로만 막고 메서드를 안 막으면, **다른 경로로 같은 메서드에 도달하는 순간 뚫린다.** 보안은 **가장 약한 지점**의 수준이다.

## Q2. 메서드가 하나뿐인 것이 왜 강점인가

```java
UserDetails loadUserByUsername(String username) throws UsernameNotFoundException;
```

**`String`을 받아 `UserDetails`를 돌려준다. 그게 전부다.**

**이 좁은 계약이 하는 일**: **"사용자가 어디 있는가"와 "인증이 어떻게 동작하는가"를 완전히 떼어 놓는다.**

```
바뀌는 쪽 (구현)              계약                안 바뀌는 쪽 (Spring Security)
메모리 맵      ─┐
JPA 리포지토리  ─┼─→  loadUserByUsername  ─→  인증 필터 → 비밀번호 비교 → 컨텍스트 저장
LDAP           ─┘
```

**왼쪽을 통째로 바꿔도 오른쪽 코드는 한 줄도 안 바뀐다.** [[04-spring-data-backed-users]]에서 실제로 왼쪽만 갈아 끼운다.

**메서드가 많았다면**: 구현할 것이 늘어 새 저장소를 붙이기 어려워진다. LDAP에는 대응 개념이 없는 메서드가 있으면 **[[../chapter-3-querying-for-data-with-spring-boot/01a-using-spring-data-to-easily-manage-data|최소공통분모 문제]]**가 재현된다.

**"메서드가 하나"는 구현 비용을 최소로 만든다** — 새 사용자 출처를 붙이는 데 필요한 것이 **함수 하나**다.

## Q3. `UserDetailsService`와 `UserDetails`의 차이

> **`UserDetailsService`는 "찾아 주는 것", `UserDetails`는 "찾아진 것"이다.**

| | `UserDetailsService` | `UserDetails` |
|---|---|---|
| 무엇 | **서비스** — 조회 동작 | **데이터** — 사용자 정보의 표준 모양 |
| 개수 | 애플리케이션당 보통 하나 | 사용자마다 하나 |
| 내가 구현하는 것 | **어디서 가져올지** | 대개 Spring이 준 구현을 쓴다 |
| 비유 | 안내 데스크 직원 | 그 직원이 건네주는 **신원 카드** |

**`UserDetails`가 담는 것**: 사용자 이름, (인코딩된) 비밀번호, 권한 목록, 계정 잠김·만료 여부.

**Spring Security는 `UserDetails`만 본다.** 그것이 어느 저장소에서 왔는지 모르고 알 필요도 없다 — Q2의 분리가 여기서 완성된다.

## Q4. 이 빈을 만들면 랜덤 비밀번호가 사라지는 이유

**자동 설정 백오프다.**

Spring Security가 켜지면 **반드시 있어야 하는 빈이 `UserDetailsService`**다. 그래서:

- **내가 안 만들면** → Spring Boot가 임시로 하나 만든다(`user` + 랜덤 비밀번호) — [[02-adding-spring-security-to-the-project]]
- **내가 만들면** → **같은 역할의 빈이 있으므로 자동 설정이 물러선다.** 임시 사용자를 만드는 코드가 실행되지 않는다

**중요한 것은 "타입"이다.** 메서드 이름이 아니라 **반환 타입이 `UserDetailsService`**라서 백오프가 일어난다. 타입이 안 맞으면 빈은 만들어져도 백오프가 일어나지 않는다.

**[[../chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1의 `@ConditionalOnMissingBean`]]이 그대로다** — 검사 대상은 이름이 아니라 타입.

## Q5. `withDefaultPasswordEncoder()`를 쓰면서 동시에 금지하는 이유

**교육적 목적과 실무적 위험이 정면으로 부딪히기 때문이다.**

- **쓰는 이유**: 비밀번호를 **평문 그대로** 둔다. 예제 코드에서 `"password"`라고 쓰면 로그인할 때도 `"password"`를 친다. **인코딩이라는 주제를 이 절에서 다루지 않고 넘어갈 수 있다.**
- **금지하는 이유**: **비밀번호가 메모리와 코드에 평문으로 존재한다.** 소스에 남고, 힙 덤프에 남고, 형상 관리에 들어간다.

**이 메서드 자체가 `@Deprecated`로 표시되어 있다** — 만든 쪽도 "쓰지 말라"고 말하고 있다. **IDE가 취소선을 그어 준다는 것이 그 경고의 전달 방식이다.**

**교훈의 형태**: 책은 **작동하는 코드를 보여 주되 그것이 운영용이 아님을 명시**한다. 실무에서는 `BCryptPasswordEncoder` 같은 **단방향 해시**를 쓴다 — 저장된 값에서 원본을 복원할 수 없어야 한다.

**같은 패턴을 이 책의 다른 곳에서도 본다** — [[../chapter-3-querying-for-data-with-spring-boot/01b-adding-spring-data-jpa-to-our-project|Ch3의 H2]]도 "프로토타이핑용"이라고 못 박고 쓴다. **작동함과 적합함은 다른 문제다.**

## Q6. `.roles("ADMIN")`이 실제로 저장하는 문자열

**`ROLE_ADMIN`이다.** 접두사 `ROLE_`이 자동으로 붙는다.

**왜 이 구분이 중요한가**: 인가 규칙을 쓸 때 **두 가지 API의 기대가 다르다.**

| API | 넘기는 값 | 실제 비교 대상 |
|---|---|---|
| `.roles("ADMIN")` | `"ADMIN"` | `ROLE_ADMIN` (접두사 자동) |
| `.hasRole("ADMIN")` | `"ADMIN"` | `ROLE_ADMIN` (접두사 자동) |
| `.hasAuthority("ADMIN")` | `"ADMIN"` | **`ADMIN`** (접두사 없음) |
| `.hasAuthority("ROLE_ADMIN")` | `"ROLE_ADMIN"` | `ROLE_ADMIN` |

**전형적 실수**: `.roles("ADMIN")`으로 만들고 `.hasAuthority("ADMIN")`으로 검사하면 **안 맞는다.** 저장된 것은 `ROLE_ADMIN`인데 찾는 것은 `ADMIN`이다.

**증상이 나쁘다**: 오류가 아니라 **403이 난다.** "권한이 없다"로 보이므로 **권한 설정을 의심하지 문자열 불일치를 의심하지 않는다.**

**규칙**: **`role` 계열끼리, `authority` 계열끼리 짝을 맞춘다.**

## Q7. 안내 데스크 비유가 깨지는 지점

**안내 데스크 직원은 방문자를 보고 판단하지만, `UserDetailsService`는 이름만 받는다.**

비유는 여기까지 맞는다 — 이름을 대면 명부에서 찾아 신원 카드를 건네준다.

**깨지는 지점 셋**:

1. **비밀번호를 검증하지 않는다.** `loadUserByUsername`은 **사용자를 찾아 주기만** 하고, **비밀번호 비교는 Spring Security가 따로 한다.** 안내 데스크 직원이라면 "본인 맞나요?"까지 확인하겠지만 이 인터페이스는 그 일을 안 한다. **찾기와 검증이 분리돼 있다.**
2. **사용자가 없으면 예외를 던진다.** 직원이라면 "그런 분 없습니다"라고 답하고 끝이지만, 여기서는 `UsernameNotFoundException`이 **인증 실패 흐름을 촉발한다.**
3. **한 번 발급하면 관여하지 않는다.** 안내 데스크는 방문자가 나갈 때까지 지켜볼 수 있지만, `UserDetailsService`는 **로그인 시점에만 불린다.** 이후 요청의 인가는 보안 컨텍스트에 저장된 정보로 판단한다 — 그래서 **역할을 DB에서 바꿔도 이미 로그인한 세션에는 즉시 반영되지 않는다.**

**3번이 실무에서 가장 자주 문제가 된다.**
