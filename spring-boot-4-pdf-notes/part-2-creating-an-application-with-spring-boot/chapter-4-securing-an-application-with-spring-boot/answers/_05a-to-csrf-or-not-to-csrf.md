## Q1. CSRF가 인증·인가를 모두 통과하는 이유

**정당한 사용자를 도구로 쓰기 때문이다. 아무것도 뚫지 않는다.**

**요청 하나의 흐름**:

1. alice가 우리 사이트에 **로그인해 둔다.** 세션 쿠키가 브라우저에 저장된다.
2. alice가 다른 탭에서 낚시 링크를 연다. 그 페이지에 숨은 폼이 우리 사이트로 **자동 제출**된다.
3. **브라우저가 alice의 세션 쿠키를 자동으로 함께 실어 보낸다.** 쿠키는 "이 도메인으로 가는 요청"이면 **출처가 어디든** 붙는다.
4. 서버가 받는다 — **alice의 세션**이고, **alice는 7번 동영상의 소유자**다.

| 방어 수단 | 막나 | 이유 |
|---|---|---|
| 인증 | ✘ | **alice는 정말로 로그인해 있다** |
| 경로 인가 | ✘ | 규칙에 걸리지 않는 **정상 경로**다 |
| 메서드 보안(소유권) | ✘ | **alice는 정말로 그 동영상의 소유자**다 |
| **CSRF 방어** | **✔** | **"이 요청이 우리가 내려준 화면에서 출발했는가"**를 따로 묻는다 |

> **앞의 세 방어는 전부 "누가 보냈는가"를 묻는다. CSRF 방어만 "어디서 출발했는가"를 묻는다.**

**질문이 다르기 때문에 다른 방어가 필요하다.** 3번 줄이 특히 중요하다 — 소유권 검사까지 통과한다.

## Q2. nonce가 공격자에게 노출되지 않는 근거

**브라우저의 동일 출처 정책 때문이다.**

**다른 도메인의 페이지는 우리 사이트의 HTML을 읽을 수 없다.**

> **요청을 보낼 수는 있어도 응답을 읽을 수는 없다.**

이 비대칭이 전부다. 공격자의 페이지는 우리 사이트로 POST를 **보낼** 수 있지만(그래서 CSRF가 성립한다), 우리 사이트의 HTML을 **읽을** 수는 없다(그래서 폼 안의 토큰을 가져갈 수 없다).

**그리고 값이 요청마다 바뀐다** — 한 번 알아내도 다음에 못 쓴다. *"값이 요청마다 바뀌므로 다른 사이트가 캐시하거나 예측할 방법이 없다."*

**흔한 오해**: **"CSRF 토큰은 비밀번호처럼 숨겨야 한다."** 아니다 — **HTML 소스에 그대로 보인다.** **비밀이라서가 아니라 다른 출처에서 읽을 수 없어서** 안전하다.

## Q3. GET에 CSRF 방어를 걸지 않는 두 이유

1. **GET은 원래 데이터를 바꾸면 안 된다.** 규격상 **안전한 메서드**다. **GET으로 삭제를 구현했다면 CSRF 이전에 그 설계가 문제다.**
2. **GET에 토큰을 요구하면 링크가 전부 깨진다.** 북마크, 검색 엔진, 다른 사이트에서 걸어 준 링크가 **모두 토큰 없이** 온다.

**2번이 실용적 이유이고 1번이 원리적 이유다.**

**1번을 뒤집어 보면**: GET으로 상태를 바꾸는 설계라면 CSRF 방어를 GET에 거는 것이 답이 아니라 **그 엔드포인트를 POST로 바꾸는 것**이 답이다. 방어를 늘리는 대신 **문제의 전제를 없앤다.**

[[../chapter-2-creating-web-and-api-applications-with-spring-boot/05-creating-json-based-apis|Ch2의 safe/idempotent]] 논의가 여기서 실전으로 쓰인다 — **safe한 메서드는 CSRF 방어가 필요 없다**는 것이 그 성질의 직접적 귀결이다.

## Q4. Thymeleaf와 Mustache의 차이가 코드량으로

| | Thymeleaf | **Mustache** |
|---|---|---|
| 필요한 작업 | **없다** — 자동으로 hidden input을 끼워 넣는다 | 프로퍼티 한 줄 + **모든 폼에 hidden input 직접 추가** |
| 이유 | Spring Boot와 **통합이 깊다** | **가볍다 = 프레임워크를 잘 모른다** |

**Mustache에서 해야 하는 것**:

```properties
spring.mustache.servlet.expose-request-attributes=true
```

```html
<input type="hidden" name="{{_csrf.parameterName}}" value="{{_csrf.token}}">
```

**이 두 줄을 모든 상태 변경 폼에 빠짐없이 넣어야 한다.**

**파라미터 이름까지 서버에서 받아 오는 이유**: **설정에 따라 파라미터 이름이 달라질 수 있어서다.** 하드코딩하면 설정을 바꿀 때 깨진다.

**대가의 성질**: **하나라도 빠뜨리면 그 폼만 403이 된다.** 그리고 이 부담은 [[06c-adding-a-delete-button]]과 [[06f-displaying-user-details-on-the-site]]에서 **폼이 늘어날 때마다 반복된다.**

**"가볍다"의 실제 의미가 여기서 드러난다** — 배울 문법이 적은 대신 **프레임워크와의 통합도 적다.** [[../chapter-2-creating-web-and-api-applications-with-spring-boot/03-augmenting-an-existing-project-with-initializr|Ch2에서 "무엇이 적어서 가벼운가"]]를 물었던 것의 다른 얼굴이다.

## Q5. 제목이 "결정"인 이유 — 경로별로 할 수 없는 것

**CSRF를 끄면 그 효과가 앱 전체에 걸리기 때문이다.**

```java
.csrf(csrf -> csrf.disable());
```

**이 한 줄은 경로별로 켜고 끌 수 없다.** 그런데 우리 앱은 **성격이 다른 둘을 함께 서빙한다.**

| | HTML 웹 페이지 | JSON API |
|---|---|---|
| 세션 쿠키를 쓰나 | **예** | 아니오(토큰 방식) |
| 브라우저가 자동으로 붙이나 | **예** | 아니오 |
| CSRF 공격이 성립하나 | **예** | 아니오 |
| CSRF 토큰이 필요한가 | **필요** | **불필요하고 오히려 방해** |

**켜면 API가 막히고, 끄면 웹이 뚫린다.** 한쪽을 고르는 수밖에 없으므로 **"결정"**이다.

**책의 아키텍처 판단**: 두 성격이 한 앱에 섞인 게 원인이므로 **애플리케이션을 둘로 나눠야 한다.**
- 웹 애플리케이션 → CSRF **켠 채로**
- 무상태 REST API → **끈다**

**이 책의 선택**: `ApiController`를 **이 앱에서 덜어 내고 CSRF를 켠 채로** 간다. JSON API는 "다른 애플리케이션에 있다고 치자"고 가정한다.

> ⚠ **책의 서술 오류**: 책은 새 정책이 "직전 정책과 거의 같고 **뒤에서 둘째 줄만 다르다**"고 하지만, 실제로는 `.requestMatchers("/admin").hasRole("ADMIN")` 규칙도 **함께 사라졌다.** `.csrf(...)` 한 줄만 바뀐 게 아니다.

## Q6. 무상태 REST API에서 CSRF 방어가 불필요한 이유

**공격의 전제가 무너지기 때문이다.**

**CSRF는 "브라우저가 쿠키를 자동으로 붙인다"는 성질을 이용한다.**

```
웹:  브라우저가 세션 쿠키를 자동 첨부      → 공격자 페이지도 인증된 요청을 만든다  ← 성립
API: 클라이언트가 토큰을 명시적으로 첨부   → 공격자 페이지는 그 토큰을 모른다      ← 불성립
```

**매 요청에 토큰을 명시적으로 실어 보내는 API 클라이언트에는 그 자동 첨부가 없다.** 공격자의 페이지가 우리 API로 요청을 보내도 **인증 정보가 붙지 않는다.** 그냥 익명 요청이다.

**즉 CSRF 방어가 "불필요"한 것이 아니라 "공격 자체가 성립하지 않는다."**

**오히려 켜 두면 해가 된다**: API 클라이언트가 **토큰을 얻을 방법이 없어** 모든 POST가 403이 된다. 토큰을 받으려면 먼저 HTML 페이지를 받아야 하는데, API 클라이언트는 그러지 않는다.

## Q7. 번호표 비유가 깨지는 지점

**번호표는 순번을 관리하지만 nonce는 출처를 증명한다.**

비유는 여기까지 맞는다 — 창구에서 번호표를 받고, 그 번호를 제시해야 처리된다. 번호표가 없으면 거절.

**깨지는 지점 셋**:

1. **번호표는 남에게 넘길 수 있다.** 누가 들고 오든 유효하다. **nonce는 세션에 묶여 있어** 다른 사람의 것을 써도 통하지 않는다 — 서버가 **그 세션에 보관한 값과 대조**한다.
2. **번호표는 창구에서 눈에 보이게 받는다.** nonce는 **HTML 소스에 그대로 보이지만** 다른 출처에서는 **읽을 수 없다.** "보이는데 못 가져간다"는 상태가 물리 세계에는 없다.
3. **번호표는 순서를 위한 것이지 신원을 위한 것이 아니다.** nonce는 순서와 무관하고 **"우리가 내려준 화면에서 왔는가"만** 증명한다.

**2번이 이 방어의 본질이다** — 비밀이 아니라 **접근 경로의 제약**이 안전성을 만든다.
