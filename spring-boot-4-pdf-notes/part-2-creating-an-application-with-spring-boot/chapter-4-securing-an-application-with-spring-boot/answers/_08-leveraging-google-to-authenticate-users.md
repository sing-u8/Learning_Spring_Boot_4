## Q1. 직접 만들 때 필요한 기능 다섯 개 이상

| 필요한 것 | **왜 어려운가** |
|---|---|
| **회원 가입** | 이메일 소유 확인, 중복 검사, **봇 차단** |
| **비밀번호 저장** | 적절한 해시 알고리즘, **솔트**, 반복 횟수 조정 |
| **비밀번호 재설정** | **안전한 일회용 링크**, 만료, 재사용 방지 |
| **비밀번호 정책** | 최소 길이, **유출된 비밀번호 목록 대조** |
| **계정 잠금** | **무차별 대입 탐지**, 잠금 해제 흐름 |
| **2단계 인증** | TOTP 또는 하드웨어 키 지원 |
| **세션 관리** | 만료, 동시 로그인 제한, 강제 로그아웃 |
| **감사 로그** | 누가 언제 로그인했는지, 누가 권한을 바꿨는지 |

> **이 목록 전체가 우리 앱의 본업(동영상 목록)과 아무 관련이 없다. 그런데 하나라도 잘못하면 사고가 난다.**

**두 가지가 겹쳐 어렵다**: ① **본업이 아니다** — 투자할 이유를 찾기 어렵다 ② **실패 비용이 크다** — 잘못하면 계정 탈취다. **동기와 위험이 반대 방향**이다.

## Q2. "없는 데이터는 유출될 수 없다"

**우리 DB가 털려도 거기에 비밀번호가 없다.**

**위임하면 비밀번호가 우리 시스템을 한 번도 지나가지 않는다** — [[07-understanding-oauth-2-1]]에서 본 그대로다. 저장할 것이 없으므로 **유출될 것도 없다.**

**구체적 귀결**: [[09b-securing-data-at-rest]]에서 배울 **비밀번호 해싱조차 필요 없어진다.** 보관할 비밀번호가 아예 없기 때문이다. 해시 알고리즘 선택, 솔트, 반복 횟수 — 그 전체 주제가 사라진다.

**보안 전략으로서의 형태**: 대부분의 방어는 **"공격을 어렵게 만든다"**인데, 이것은 **"공격 대상을 없앤다"**다. **더 강한 종류의 방어다** — 방어를 뚫는 새 기법이 나와도 영향받지 않는다.

**같은 사고방식의 다른 예**: 필요 없는 데이터를 수집하지 않는 것, 로그에 개인정보를 남기지 않는 것. **가지고 있지 않은 것은 잃을 수 없다.**

## Q3. 위임하면 얻는 것과 잃는 것

**얻는 것**:

| 이득 | 구체적으로 |
|---|---|
| **보안 위험 감소** | 우리 DB가 털려도 **거기에 비밀번호가 없다** |
| **사용자 관리 단순화** | Q1의 목록 전체가 **우리 일이 아니게 된다** |
| **검증된 플랫폼 활용** | **수억 명이 쓰며 다듬어진** 시스템을 쓴다 |

**잃는 것**:

| 대가 | 구체적으로 |
|---|---|
| **가용성 통제** | **Google이 내려가면 우리 로그인도 내려간다** |
| **개발 환경 독립성** | **네트워크가 없으면 로그인 테스트를 못 한다** |
| **테스트 사용자 통제** | **실제 Google 계정이 필요**하다 |
| **사용자 범위** | **Google 계정이 없는 사용자를 배제**한다 |
| **정책 통제** | 스코프·토큰 정책이 **제공자가 정한 범위** 안이다 |

> **위임은 책임을 넘기는 대신 통제권도 넘기는 거래다.**

**대안**: [[07a-oauth-vs-openid-connect]]에서 본 흐름을 **직접 운영**할 수 있다 → Q4.

## Q4. Spring Authorization Server가 개발 환경에서 유용한 세 이유

| 축 | 외부 제공자 (Google) | **직접 운영** |
|---|---|---|
| **테스트 사용자** | 실제 Google 계정이 필요 | **내가 정의한다** |
| **개발 시 네트워크** | 외부 호출 필요 | **불필요** |
| **자동화 테스트** | 외부 서비스에 의존 | **로컬에서 완결** |
| 스코프·토큰 정책 | 제공자가 정한 범위 | 내가 통제 |
| 운영 부담 | 없음 | 서버 하나를 더 운영 |

**세 이유**:
1. **테스트 사용자를 마음대로 만든다.** alice·bob·admin 같은 시나리오를 실제 Google 계정 없이 구성한다.
2. **외부 네트워크 없이 테스트가 완결된다.** CI에서 외부 의존이 사라진다.
3. **자동화 테스트가 남의 서비스에 의존하지 않는다.** Google이 느리거나 rate limit을 걸면 우리 빌드가 깨진다 — 그 위험이 없다.

**책의 결론은 "상황에 따라 고르라"**다. **운영에서는 외부 제공자가 대체로 낫고, 개발과 통제된 환경에서는 로컬 인가 서버가 매우 유용하다.**

**"직접 인가 서버를 운영하는 건 무모하다"는 오해**: 개발·테스트 환경에서는 **오히려 실용적**이다.

## Q5. 외부 제공자를 써도 우리가 해야 하는 보안 작업

**인증만 넘어간다. 인가는 여전히 우리 몫이다.**

> **"이 사용자가 이 동영상을 지워도 되는가"는 Google이 답해 주지 않는다.**

**여전히 우리 일인 것들**:
- **[[06d-locking-down-access-to-the-owner]]의 소유권 규칙** — 그대로 필요하다
- **[[05-securing-web-routes-and-http-verbs]]의 경로별 인가** — 그대로 필요하다
- **[[05a-to-csrf-or-not-to-csrf]]의 CSRF 방어** — 세션을 쓰는 한 그대로
- **역할 부여** — Google은 우리 앱의 역할 체계를 모른다
- **사용자 테이블** — 대개 **여전히 필요하다.** 우리 앱만의 정보(역할, 설정, 소유한 동영상)를 저장해야 하고, **Google 식별자를 열쇠로 그 행을 찾게 된다**

**흔한 오해 둘을 정리하면**:
- **"외부 제공자를 쓰면 보안을 신경 쓸 필요가 없다"** → **인증만 넘어간다**
- **"Google 로그인을 붙이면 사용자 테이블이 필요 없다"** → **대개는 여전히 필요하다**

## Q6. 책이 Google을 고른 예제상의 이유

**YouTube 데이터까지 함께 다루기 위해서다.**

OAuth와 OIDC를 지원하는 곳은 많다 — Google, GitHub, Microsoft, 상용 신원 서비스들. **그냥 로그인만 보여 줄 거라면 어느 제공자나 비슷하다.**

**Google을 쓰면 로그인에 더해 "위임받은 권한으로 남의 API를 호출하는" 부분까지 한 예제로 보여 줄 수 있다.**

[[07-understanding-oauth-2-1]]에서 설명한 **위임 인가가 실제로 무엇을 가능하게 하는지**가 그 부분에서 드러난다. 로그인만 보면 OAuth와 OIDC의 차이가 안 보이지만, **YouTube API를 부르는 순간** 액세스 토큰과 ID 토큰이 **다른 일을 한다**는 것이 눈에 보인다.

**즉 교육적 이유다.** 한 예제로 **인증(OIDC)과 인가(OAuth) 둘 다** 보여 줄 수 있다.

## Q7. 여권 심사대 비유가 깨지는 지점

**심사대가 우리 건물 밖에 있다는 점을 흐린다.**

비유는 여기까지 맞는다 — **우리는 여권을 발급하지도, 진위를 판별하지도 않고, 심사대의 결과만 신뢰한다.**

**깨지는 지점 둘**:

1. **심사대가 문을 닫으면 우리 건물에는 아무도 들어올 수 없다.** 실제 심사대는 건물 안에 있고 우리가 운영을 통제하지만, **Google은 밖에 있고 우리 통제 밖이다** → Q3.
2. **심사대는 "이 사람이 누구인지"만 알려 줄 뿐 "이 사람이 우리 건물의 어느 층에 갈 수 있는지"는 여전히 우리가 정해야 한다** → Q5.

**2번이 이 절 전체의 요지이기도 하다.** 위임의 범위가 **인증까지**이고 **인가는 넘어가지 않는다.**

**세 번째로 깨지는 점**: 실제 여권 심사대는 **누구나 통과 대상**이지만, Google 로그인은 **Google 계정이 있는 사람만** 대상이다. 계정이 없는 사람은 심사대 앞에 설 수조차 없다 — 그래서 실제 서비스는 보통 **여러 제공자를 함께 지원한다.**
