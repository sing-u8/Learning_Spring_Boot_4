## Q1. 삭제를 GET 링크로 만들면 벌어지는 사고 셋

```html
<a href="/delete/videos/{{id}}">Delete</a>
```

1. **GET이 데이터를 지운다.** HTTP 규격상 GET은 **안전한 메서드**여야 한다. **브라우저·프록시·검색 봇은 GET을 마음대로 재시도하거나 미리 가져와도 된다고 전제한다.**
2. **크롤러가 목록을 훑으면 전부 사라진다.** **실제로 일어났던 유명한 사고다.** 검색 봇이 페이지의 모든 링크를 따라가면서 삭제를 실행한다.
3. **CSRF 방어가 GET에는 걸리지 않는다.** 그래서 공격자가 **`<img src="/delete/videos/7">` 한 줄로** 남의 데이터를 지울 수 있다. 이미지 태그는 자동으로 GET을 보낸다.

**셋의 공통 뿌리**: **"GET은 안전하다"는 전제 위에 인터넷 전체가 돌아간다.** 그 전제를 깨면 **브라우저·프록시·봇·보안 계층이 전부 잘못 동작한다.** 내가 만든 것이 아닌 것들까지.

**그래서 삭제는 반드시 상태 변경 요청, 즉 POST 계열로 보내야 한다.**

## Q2. HTML 폼으로 DELETE를 보낼 수 없는 이유와 우회 방법

**HTML 표준 폼은 `method` 속성에 `get`과 `post`만 받는다.**

`method="delete"`라고 쓰면 **브라우저는 그냥 GET으로 처리한다.** 오류도 안 난다 — 인식할 수 없는 값이므로 기본값으로 떨어진다.

**REST 관점에서는 `DELETE /videos/7`이 맞다.** 하지만 표준 폼으로는 불가능하다.

**선택지**:

| 방법 | 가능한가 | 이 장의 선택 |
|---|---|---|
| `method="delete"` | ✘ GET이 된다 | — |
| JavaScript `fetch` | ✔ | **이 장은 JS 없이 간다** |
| **POST + 경로에 의도** | ✔ | **✅ 책의 선택** |
| 숨은 `_method` 파라미터 | ✔ (프레임워크 지원 필요) | — |

**책의 선택**: **POST로 보내고 경로에 의도를 담는다** — `/delete/videos/{id}`.

**즉 HTTP 동사가 표현하지 못하는 의도를 경로가 대신 표현한다.** REST 순수주의로는 아쉽지만, **JS 없이 순수 폼으로 간다는 제약** 아래서는 이것이 가장 단순하다.

## Q3. `"redirect:/"`가 없으면

**사용자가 새로고침할 때 브라우저가 방금 한 POST를 그대로 다시 보낸다.**

삭제가 **한 번 더 실행된다.** 이미 지워진 것을 또 지우려 하므로:
- 운이 좋으면 아무 일도 안 일어난다 (`Optional`이 비어 있어 그냥 통과)
- 운이 나쁘면 **예외**가 난다
- 그리고 **브라우저가 "재전송하시겠습니까?" 경고를 띄운다** — 사용자를 불안하게 한다

**[[../chapter-2-creating-web-and-api-applications-with-spring-boot/04d-changing-the-data-through-html-forms|Ch2의 PRG 패턴]]이 그대로 적용된다.**

**핵심**: 브라우저의 "현재 페이지"가 **POST 응답이면** 새로고침이 POST를 반복하고, **GET 응답이면** GET을 반복한다. 리다이렉트는 그 사이에 **GET 한 번을 끼워 넣어** 마지막 요청을 GET으로 만든다.

**부수 효과**: 주소창이 `/`가 되므로 **북마크하거나 공유해도 정상 동작**한다. `/delete/videos/7`이 남아 있었다면 그 링크는 POST 전용이라 GET으로 열면 405다.

## Q4. `return true`가 있는 이유 — `Optional.map`의 계약

**`Optional.map`은 "값이 있으면 변환, 없으면 빈 Optional"이므로 변환 함수가 무언가를 돌려줘야 한다.**

```java
return repository.findById(videoId)
        .map(entity -> {
            repository.delete(entity);
            return true;              // ← 없으면 컴파일 안 된다
        })
        .orElse(false);
```

**`map`의 시그니처가 `Function<T, R>`을 요구한다.** 람다가 값을 돌려주지 않으면 **함수가 아니다.**

**`delete`는 `void`를 돌려주므로** 그것만 쓰면 람다가 반환값이 없다. 그래서 **`true`를 명시적으로 돌려준다.**

**`true`/`false`가 의미하는 것**: **"실제로 지웠는가"**다. 없는 id를 주면 `findById`가 빈 `Optional`을 돌려주고, `map`이 실행되지 않고, `orElse(false)`가 `false`를 준다.

**대안**: `ifPresent`를 쓰면 반환값이 필요 없지만 **"지웠는지 여부"를 호출자에게 알릴 수 없다.** 그 정보가 필요하면 `map` + `orElse`가 맞다.

## Q5. `deleteById(id)` 대신 `findById(id)` → `delete(entity)`를 고른 진짜 이유

**메서드 보안이 엔티티를 봐야 하기 때문이다.**

```java
// 이러면 소유권을 검사할 수 없다
repository.deleteById(videoId);        // 인자가 Long. 소유자를 모른다

// 이러면 검사할 수 있다
repository.findById(videoId)
    .map(entity -> { repository.delete(entity); ... })
                              ↑ 인자가 VideoEntity. username 필드가 있다
```

**[[06-securing-spring-data-methods]]의 결론이 여기서 코드 형태를 결정한다** — *"대상을 손에 넣기 전에는 판정할 재료가 없다."*

`@PreAuthorize`가 `#entity.username == authentication.name` 같은 규칙을 쓰려면 **`entity`라는 파라미터가 있어야** 한다. `deleteById(Long)`에는 그런 파라미터가 없다.

**즉 "조회 후 삭제"는 비효율처럼 보이지만 보안 요구가 만든 형태다.** 조회 한 번이 추가되는 대가로 **소유권 검사가 가능해진다.**

**[[06-securing-spring-data-methods]]에서 예고한 "거절 시점이 늦다"의 실체이기도 하다** — 권한 없는 요청도 **조회 한 번은 유발한다.**

## Q6. `_csrf` hidden input을 빼면

**403 Forbidden이 온다.**

이 앱은 CSRF 방어가 **켜져 있고**([[05a-to-csrf-or-not-to-csrf]]에서 켠 채로 가기로 했다), POST는 **상태 변경 요청**이므로 토큰 검사 대상이다.

토큰이 없으면 **필터가 컨트롤러에 도달하기 전에 거절한다.** 삭제는 실행되지 않는다.

**증상이 헷갈리는 이유**: 403은 **"권한이 없다"**로 읽힌다. 그래서 **소유권 규칙이나 역할 설정을 의심하지** CSRF 토큰을 의심하지 않는다. 로그인도 되어 있고 자기 동영상인데 403이 나므로 더 혼란스럽다.

**Mustache의 대가가 여기서 반복된다** — 폼마다 두 줄을 **빠짐없이** 넣어야 하고, **하나라도 빠뜨리면 그 폼만 403**이 된다. Thymeleaf였다면 자동이다.

**진단 방법**: 브라우저 개발자 도구로 요청 본문에 `_csrf` 파라미터가 실렸는지 본다. 없으면 템플릿 문제다.

## Q7. POST-Redirect-GET 비유가 깨지는 지점

**"영수증을 받고 목록으로 돌아간다"는 비유는 리다이렉트 후 GET이 무엇을 잃는지 담지 못한다.**

비유는 여기까지 맞는다 — 계산(POST)을 하고, 영수증 대신 **"목록으로 가세요"라는 안내(302)**를 받고, 목록을 다시 본다(GET).

**깨지는 지점 둘**:

1. **영수증이 없다.** 실제 계산에서는 **무엇을 샀는지 적힌 종이**를 받는다. PRG에서는 **POST의 결과 정보가 응답에 실려 오지 않는다.** "7번 동영상을 지웠습니다"를 화면에 띄우려면 **flash attribute 같은 별도 수단**이 필요하다.
2. **돌아간 목록이 방금 그 목록인지 알 수 없다.** GET은 **새 요청**이므로 그 사이에 다른 사람이 무언가를 바꿨을 수 있다. 비유의 "목록"은 정지해 있지만 실제 데이터는 그렇지 않다.

**1번이 실무에서 자주 부딪힌다.** 성공/실패 메시지를 보여 주려면 PRG를 유지하면서 정보를 나르는 방법을 따로 마련해야 한다.
