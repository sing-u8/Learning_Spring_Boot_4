## Q1. 이 애노테이션을 빠뜨렸을 때의 실패가 특별히 위험한 이유

**뚫리는 방향으로 실패하기 때문이다.**

| | `denyAll()` 누락 | **`@EnableMethodSecurity` 누락** |
|---|---|---|
| 결과 | **막힌다** | **뚫린다** |
| 발견 | 사용자가 **즉시 불평**한다 | **아무도 불평하지 않는다** |
| 언제 알게 되나 | 개발 중 | **사고가 날 때까지 모른다** |
| 신호 | 403 화면 | **없음** — 예외도, 경고도, 로그도 |

**애노테이션은 분명히 거기 있는데 동작하지 않는다.** `@PreAuthorize`가 붙은 코드를 읽으면 **보안이 걸려 있다고 믿게 된다.** 코드 리뷰도 통과한다.

> **이것이 보안에서 가장 위험한 실패 모양이다.**

**[[01-spring-security-filter-chain-foundations]]의 "안전한 기본값"과 정면으로 어긋나는 지점**이기도 하다. Spring Security 전체가 **잠기는 쪽으로 실패**하도록 설계됐는데, 이 스위치만은 **꺼진 상태가 기본**이다 → Q2.

## Q2. 자동으로 켜지지 않는 세 이유

**메서드 보안을 켠다는 것은 모든 후보 빈을 프록시로 감싼다는 뜻이고, 이것은 공짜가 아니다.**

| 비용 | 내용 |
|---|---|
| **성능** | **모든 메서드 호출이 프록시를 한 겹 더 지난다** |
| **동작 변화** | **`this.method()` 같은 내부 호출과 프록시 호출의 동작이 갈린다** |
| **디버깅** | **스택 트레이스에 프록시 프레임이 끼어든다** |

**메서드 보안을 안 쓰는 앱에 이 비용을 강제할 수는 없다.**

**두 번째가 특히 무겁다.** 프록시를 씌우면 **같은 코드의 동작이 호출 경로에 따라 달라진다.** 메서드 보안을 안 쓰는 앱에서도 이 변화가 일어나면 예상 못 한 버그가 생긴다.

> **그래서 켜는 쪽을 명시적 선언으로 만들었다. 대가로 "켜는 걸 잊으면 조용히 무력해진다"는 함정이 생겼다.**

**트레이드오프의 성질**: 안전한 기본값과 비용 없는 기본값이 **충돌할 때** 후자를 골랐다. 이 선택 자체가 옳고 그름의 문제라기보다 **어느 쪽 실수를 더 흔하게 볼 것인가**의 판단이다.

## Q3. `@PreAuthorize`를 기본으로 켜고 `@Secured`를 끄는 판단의 근거

**표현력이 가장 큰 것을 기본으로, 나머지는 필요할 때 켠다.**

| | `@EnableGlobalMethodSecurity` (옛) | `@EnableMethodSecurity` (새) |
|---|---|---|
| `@PreAuthorize`·`@PostAuthorize` | 옵션으로 켜야 함 | **기본으로 켜짐** |
| `@Secured` | 옵션 | **기본으로 꺼짐** (`securedEnabled = true` 필요) |
| `@RolesAllowed` (JSR-250) | 옵션 | **기본으로 꺼짐** (`jsr250Enabled = true`) |

**근거**: `@PreAuthorize`는 **표현식**을 받아 `@Secured`나 `@RolesAllowed`가 **표현할 수 없는 조건까지** 쓸 수 있다.

```java
@PreAuthorize("#entity.username == authentication.name")   // 가능
@Secured("ROLE_ADMIN")                                      // 역할만. 소유권 비교 불가
```

**우리가 [[06d-locking-down-access-to-the-owner]]에서 쓴 규칙이 정확히 그런 예다.** `@Secured`로는 **좌변(데이터)을 참조할 방법이 없다.**

**즉 이 기본값 변경은 "이 장에서 하는 일"을 기본으로 만든 것이다.** 역할 기반 검사만 필요하면 URL 규칙으로 충분하고, **메서드 보안을 굳이 켜는 이유는 대개 표현식이 필요해서**다.

## Q4. metadata source + decision voter → `AuthorizationManager`

**두 부분으로 나뉘어 있던 판정 구조가 하나의 함수형 타입으로 합쳐졌다.**

**옛 구조**:
- **metadata source**: 애노테이션을 읽어 "이 메서드에 어떤 조건이 붙어 있는가"를 수집
- **decision voter**: 그 조건들을 놓고 투표해 최종 판정

**두 단계로 나뉘어 있으면**:
- 확장하려면 **양쪽을 다 이해**해야 한다
- 조건과 판정이 분리돼 있어 **흐름을 따라가기 어렵다**
- 투표 방식(만장일치·과반 등)이 **또 하나의 설정 축**이 된다

**새 구조 — `AuthorizationManager`**:
- **하나의 함수형 타입**이 조건 읽기와 판정을 함께 담당
- **조합 가능하다** — [[05-securing-web-routes-and-http-verbs]]에서 본 `AuthorizationManagers.allOf`·`anyOf`·`not`
- **직접 구현하기 쉽다** — 함수 하나

**핵심 이득은 조합성이다.** 옛 구조에서 커스텀 규칙을 만들려면 voter를 만들고 등록하고 투표 정책을 조정해야 했다. 이제는 **람다 하나로 만들어 `allOf`에 넣으면 된다.**

## Q5. URL 보안과 메서드 보안이 같은 추상을 공유하는 것의 의미

**두 층이 같은 어휘를 쓰게 되어 배운 것이 이전되고 조합이 가능해진다.**

**전에는**: URL 보안은 `AccessDecisionManager` 계열, 메서드 보안은 별도 구조. **같은 "인가"인데 확장 방법이 달랐다.**

**지금은**: 둘 다 `AuthorizationManager`다.

**이득 셋**:
1. **커스텀 규칙을 한 번 만들면 양쪽에서 쓴다.** URL 규칙에 쓰던 `AuthorizationManager`를 메서드 보안에도 넣을 수 있다.
2. **배우는 개념이 하나다.** "인가는 `AuthorizationManager`가 한다"로 통일된다.
3. **조합 API가 공유된다** — `allOf`·`anyOf`·`not`이 양쪽에서 같게 동작한다.

**설계 관점**: **같은 문제(인가)에 두 개의 추상이 있었던 것이 이상했던 것**이고, 통합은 그 이상함을 없앤 것이다. [[06-securing-spring-data-methods]]에서 "둘은 경쟁이 아니라 볼 수 있는 정보가 다른 두 자리"라고 했는데, **자리는 달라도 판정 방식은 같아야 자연스럽다.**

## Q6. 스위치가 켜졌는지 코드만 보고 확인할 수 없다면

**실제로 막히는지 테스트로 확인한다.**

**코드로는 확인이 불충분한 이유**: `@EnableMethodSecurity`가 **다른 `@Configuration` 클래스**에 붙어 있을 수 있고, 라이브러리가 켜 줬을 수도 있다. **`@PreAuthorize`가 붙은 파일만 봐서는 알 수 없다.**

**확인 방법**:

| 방법 | 무엇을 확인 |
|---|---|
| **통합 테스트** | **권한 없는 사용자로 호출했을 때 실제로 `AccessDeniedException`이 나는가** ← 가장 확실 |
| Actuator `/actuator/beans` | 대상 빈이 **프록시로 감싸였는지** |
| 디버거 | 주입된 객체의 클래스 이름에 `$$SpringCGLIB$$` 등이 붙었는지 |
| 로그 | 시작 시 보안 관련 자동 설정 로그 |

**첫 번째가 답이다.** 그리고 이것이 [[02-adding-spring-security-to-the-project]]에서 **`spring-boot-starter-security-test`를 처음부터 넣은 이유**와 이어진다 — **보안 규칙은 "막히는지"를 확인해야 완성이고, 그 확인은 테스트로만 반복 가능하다.**

**"성공 경로만 테스트하면 아무 의미가 없다"**는 점도 같다. alice가 자기 것을 지우는 테스트는 **스위치가 꺼져 있어도 통과한다.** bob의 것을 지우려다 **막히는** 테스트만이 이 스위치를 검증한다.

## Q7. 경보기 비유가 깨지는 지점

**경보기는 꺼져 있으면 그 사실이 표시되지만, 이 스위치는 꺼져 있어도 아무 표시가 없다.**

비유는 여기까지 맞는다 — 센서(애노테이션)를 방마다 달아 두어도 **주 전원(스위치)이 꺼져 있으면 아무 일도 안 일어난다.**

**깨지는 지점 셋**:

1. **경보기 패널에는 "무장 해제됨" 표시등이 있다.** 여기에는 **아무 표시가 없다.** 로그도 경고도 없다 → Q1.
2. **경보기는 테스트 버튼이 있다.** 여기서는 **직접 침입해 봐야** 알 수 있다 — 권한 없는 호출을 실제로 해 보는 것 → Q6.
3. **센서를 달았다는 것과 작동한다는 것이 물리적으로 연결돼 있다.** 경보기 센서는 배선이 안 되면 **설치할 때 티가 난다.** 애노테이션은 **붙이는 것만으로 완결돼 보인다.**

**3번이 이 함정의 심리적 원인이다** — 애노테이션은 **선언이 곧 완성**처럼 보인다. 실제로는 **그것을 읽어 프록시를 만드는 쪽이 있어야** 한다. [[../chapter-3-querying-for-data-with-spring-boot/02b-pojos-and-the-spring-programming-model|Ch3의 "애노테이션 자체는 아무것도 하지 않는다"]]가 여기서 보안 사고로 나타난다.
