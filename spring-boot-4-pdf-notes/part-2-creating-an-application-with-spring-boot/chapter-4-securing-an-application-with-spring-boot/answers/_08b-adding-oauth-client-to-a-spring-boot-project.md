## Q1. OAuth 앱을 새 프로젝트로 시작하는 이유

**인증 모델이 근본적으로 다르기 때문이다.**

| | 지금까지의 앱 | **OAuth 앱** |
|---|---|---|
| 사용자 출처 | **우리 DB**(`UserDetailsService`) | **Google** |
| 비밀번호 | **우리가 보관** | **보지 않는다** |
| 로그인 화면 | Spring Security가 렌더링 | **Google로 리다이렉트** |
| 필요한 의존성 | `starter-security` + JPA | OAuth 2 Client + HTTP Client |
| 도메인 | `VideoEntity` | YouTube 검색 응답 |

> **둘을 한 앱에 섞으면 "어느 쪽으로 로그인해야 하는가"부터 정해야 하고, 그건 이 절이 가르치려는 것과 다른 주제다.**

**실무에서는 섞는 경우도 많다** — "아이디로 로그인 또는 Google로 로그인". 하지만 그러려면 **두 `UserDetailsService`를 조율**하고, **같은 사람이 두 방식으로 들어왔을 때 계정을 잇는** 문제까지 풀어야 한다. **별개의 주제다.**

> ✅ **좌표 주의**: Boot 4에서 이 스타터의 이름은 **`spring-boot-starter-security-oauth2-client`**다. Boot 3까지 쓰던 `spring-boot-starter-oauth2-client`는 **`spring-boot-starter-security-*` 접두사로 정리되며 자리를 넘겼다.**

## Q2. 엔드포인트를 하나도 안 적었는데 동작하는 이유

**`CommonOAuth2Provider`가 미리 채워 주기 때문이다.**

OAuth 흐름을 완성하려면 원래 주소가 여럿 필요하다 — **인가 엔드포인트, 토큰 엔드포인트, 사용자 정보 엔드포인트, JWK 세트 주소.** 우리 설정에는 하나도 없다.

✅ Spring Security 7.1.0의 `CommonOAuth2Provider` 열거형에는 상수가 정확히 **`GOOGLE`·`GITHUB`·`FACEBOOK`·`OKTA`** 넷이다. **등록 이름이 그 목록과 맞으면 나머지를 채워 준다.**

> **"기술적으로는 그것만으로 Google 인증이 된다."**

**우리가 `scope`를 추가로 적은 것은 순전히 YouTube API를 쓰려고**다. **기본 스코프만으로도 로그인은 된다.**

**경계**: **`CommonOAuth2Provider`에 없는 제공자**(사내 인가 서버 등)는 **엔드포인트를 직접 적어야 한다.**

## Q3. 등록 이름 `google`이 하는 두 가지 일

1. **redirect URI의 마지막 조각과 맞춘다** — `/login/oauth2/code/**google**` ([[08a-creating-a-google-oauth-application]]에서 등록한 값)
2. **`CommonOAuth2Provider.GOOGLE`의 기본값을 끌어온다** — 엔드포인트 네 개 (Q2)

**즉 하나의 문자열이 두 시스템을 잇는다** — 우리 설정과 Google의 등록, 그리고 우리 설정과 Spring Security의 내장 목록.

**다른 이름을 쓰면**: **엔드포인트를 직접 다 적고 redirect URI도 새로 등록해야 한다.** 둘 다 깨진다.

**경로 자체는 우리가 안 만든다**: **"경로 `/login/oauth2/code/google`을 내가 만들어야 한다"** → **Spring Security가 자동으로 처리한다.** 컨트롤러가 필요 없다. **마지막 조각만 맞으면 된다.**

## Q4. 스코프 네 개와 `.readonly`

| 스코프 | 요청하는 것 | **없으면** |
|---|---|---|
| **`openid`** | **OIDC로 동작하라는 신호.** ID 토큰이 발급된다 | **신원 확인이 형식을 갖추지 못한다** ([[07a-oauth-vs-openid-connect]]) |
| `profile` | 이름·프로필 사진 | 사용자 표시 이름을 알 수 없다 |
| `email` | 이메일 주소 | 이메일로 식별할 수 없다 |
| **`youtube.readonly`** | YouTube 데이터 **읽기** | [[08c-invoking-an-oauth-2-api-remotely]]의 API 호출이 **거절된다** |

**목적별로 나누면**: **앞의 셋은 로그인용, 마지막 하나는 데이터 접근용.**

> **한 번의 동의로 두 목적을 함께 처리한다는 것이 OAuth+OIDC 조합의 실용적 이점이다.**

**`.readonly`로 끝나는 이유**: **우리는 목록을 읽기만 하므로 쓰기 권한을 요구할 이유가 없다.**

> **필요한 최소만 요청하는 것이 스코프 설계의 원칙이다.**

**넓게 요청하면 두 가지를 잃는다**: ① **유출 시 피해가 커진다** ② **동의 화면에 그대로 나타나므로 사용자가 거절한다** — [[07-understanding-oauth-2-1]] Q4.

> **표기 참고**: 공식 정규 표기는 kebab-case인 `client-id`·`client-secret`이다. 책의 `clientId`가 동작하는 것은 **완화된 바인딩** 덕분이다 — [[../chapter-1-core-features-of-spring-boot/03a-creating-custom-properties|Ch1]]에서 본 그 규칙.

## Q5. 두 저장소 빈이 보관하는 것과 나뉜 이유

| 빈 | **무엇을 보관** | **왜 필요한가** |
|---|---|---|
| **`ClientRegistrationRepository`** | **제공자별 등록 정보**(clientId, secret, 스코프, 엔드포인트) | **여러 제공자를 동시에 지원**하려면 조회 창구가 필요 |
| **`OAuth2AuthorizedClientRepository`** | **발급받은 토큰**을 사용자·제공자별로 | **요청마다 다시 로그인시킬 수는 없다** |

**나뉜 이유 — 수명과 범위가 다르다**:

```
등록 정보: 애플리케이션 전체에 하나. 시작할 때 설정에서 읽고 안 바뀐다
토큰:      사용자마다, 제공자마다 다름. 계속 생기고 만료되고 갱신된다
```

**"여러 제공자" 이야기가 이 구조의 이유다.** Facebook·Twitter·Google·Apple 로그인을 동시에 제공하는 사이트에서는 **등록이 여러 벌**이고, **"지금 요청은 어느 제공자 것인가"를 이름으로 구분**해야 한다.

## Q6. `OAuth2AuthorizedClient`가 토큰 하나가 아니라 묶음인 이유

> **"누구의, 어느 제공자의, 어떤 스코프의 토큰인가"가 함께 묶여야 재사용할 수 있다.**

**토큰 문자열만 들고 있으면 답할 수 없는 것들**:
- **누구 것인가** — alice의 토큰을 bob 요청에 쓰면 안 된다
- **어느 제공자 것인가** — Google 토큰을 GitHub API에 보낼 수 없다
- **어떤 스코프인가** — YouTube 읽기 토큰으로 쓰기를 시도하면 실패한다
- **언제 만료되나** — 갱신 시점을 알아야 한다
- **리프레시 토큰이 있나** — 있어야 조용히 갱신할 수 있다

**즉 토큰은 문맥 없이는 쓸 수 없다.** 그 문맥을 함께 담은 것이 `OAuth2AuthorizedClient`다.

**부수 효과**: 이 묶음이 있으므로 **관리자 빈이 만료를 감지해 리프레시 토큰으로 조용히 갱신**할 수 있다 → Q8.

## Q7. 빌더의 세 provider가 대응하는 흐름

```java
OAuth2AuthorizedClientProviderBuilder.builder()
    .authorizationCode()      // ①
    .refreshToken()           // ②
    .clientCredentials()      // ③
```

| provider | 흐름 | 언제 쓰이나 |
|---|---|---|
| **`authorizationCode()`** | **Authorization Code Flow** | **사용자가 처음 로그인할 때.** 코드를 토큰으로 교환 |
| **`refreshToken()`** | **리프레시 토큰 흐름** | **액세스 토큰이 만료됐을 때.** 사용자를 다시 로그인시키지 않고 새 토큰 |
| **`clientCredentials()`** | **Client Credentials Flow** | **사용자 없이** 서비스가 자기 자격으로 |

**셋 다 [[07a-oauth-vs-openid-connect]]에서 본 흐름이다.**

**"세 개를 다 켜면 세 번 호출된다"는 오해**: **아니다. 상황에 맞는 것 하나가 선택된다.** 켜 둔다는 것은 **"이 흐름도 지원한다"**는 뜻이다.

**왜 직접 조립하나**: **"`OAuth2AuthorizedClientManager`도 자동 설정된다"** → 이 예제에서는 **직접 만든다.** 자동 설정에 맡길 수 있는 경우도 있지만, **어떤 흐름을 지원할지 명시하려면** 직접 조립한다.

## Q8. 사원증 비유가 깨지는 지점

**사원증이 매번 새로 발급된다는 점을 담지 못한다.**

비유는 여기까지 맞는다 — **출장 갈 회사의 주소록과 사원증을 미리 등록해 둔다.** `CommonOAuth2Provider`가 **주소록의 유명한 항목들을 미리 채워 준** 상태다.

**깨지는 지점**:

> **실제로 우리가 들고 있는 것은 사원증이 아니라 "사원증을 발급받을 수 있는 자격"이고, 실제 출입증(액세스 토큰)은 만료되면 관리자 빈이 조용히 새로 받아 온다.**

**우리가 보관하는 것**: clientId·secret = **발급 자격**
**실제로 쓰는 것**: 액세스 토큰 = **출입증**, 수명이 짧다

**실제 사원증은 한 번 받으면 몇 년 쓴다.** 액세스 토큰은 **수십 분**이고, 그 갱신이 **자동으로, 사용자 모르게** 일어난다 — `refreshToken()` provider가 하는 일이다(Q7).

**두 번째로 깨지는 점**: 사원증은 **회수하려면 돌려받아야** 하지만, 토큰은 **사용자가 원격으로 무효화**한다 — [[07-understanding-oauth-2-1]] Q7의 발레파킹 키와 같은 지점이다.

**보안 경계 하나 더**: **시크릿을 설정 파일에 그대로 두면 안 된다.** 책의 예제는 학습용이고, 실제로는 **환경 변수나 비밀 관리 도구에서 주입**해야 한다. **`application.yaml`은 보통 형상 관리에 들어간다.**
