## Q1. 서버를 바꿔도 `DispatcherServlet`이 영향을 받지 않는 이유

**Spring MVC 전체가 컨테이너 눈에는 서블릿 하나이고, 그 사이에 `jakarta.servlet` 계약이 있기 때문이다.**

**요청이 지나가는 길에서 계약이 지켜지는 지점**:

```text
소켓 바이트
   ↓ ⑥ 커넥터가 읽는다                      ← 제품마다 다르다
   ↓ ⑦ HttpServletRequest 로 만든다          ← 여기가 계약이다
   ↓ ⑧ 등록된 서블릿의 service() 호출        ← DispatcherServlet 하나
   ↓ ⑨ URL·메서드로 컨트롤러를 찾아 호출     ← 컨테이너는 이 안쪽을 모른다
   ↓ ⑩ 응답을 HTTP 로 직렬화                 ← 계약의 반대편 끝
```

**7단계가 핵심이다** — **제품이 무엇이든 `HttpServletRequest` 타입으로 만들어 주기로 약속했기 때문에 그 위의 코드가 제품을 몰라도 된다.**

**8~9단계가 "컨트롤러가 그대로인 이유"다**:

> **컨트롤러가 100개여도 컨테이너가 아는 것은 서블릿 하나뿐이다.**

`DispatcherServlet` 안쪽은 컨테이너에게 **"서블릿 하나가 알아서 하는 일"**일 뿐이다. **Spring의 개념(컨트롤러·`@GetMapping`)이 컨테이너에게 전혀 노출되지 않는다.**

**시작 시점에도 같은 원리가 한 겹 더 있다** — 2.1의 2~3단계:

- 웹 컨텍스트는 **`ServletWebServerFactory` 타입 하나만** 알면 된다 — **컨텍스트 코드 안에 제품별 분기가 들어가지 않게 하려고**
- 자동 구성이 **클래스패스에 실제로 있는 제품**을 보고 그에 맞는 팩터리를 등록한다 — **의존성 교체만으로 서버가 바뀌게 하려고**

**만약 이 층이 없었다면**: Spring MVC가 Tomcat 클래스를 직접 호출하는 구조라면 **세 줄 교체가 프레임워크를 다시 쓰는 일**이 된다. 사용자는 서버를 바꿀 때마다 코드를 고쳐야 하고, **Spring 팀은 지원하려는 서버 수만큼 MVC를 따로 만들어야 한다.**

## Q2. "내장 Tomcat"과 "외부 Tomcat"의 같은 점과 다른 점

**같은 것 — 제품 자체다. `spring-boot-starter-tomcat`이 끌어오는 것은 축소판이 아니라 진짜 Apache Tomcat 라이브러리다.**

**다른 것 — 시작 주체다.**

> **구분 기준 한 문장: `main()`을 누가 갖고 있는가.**

| | **외부 배포** | **내장 실행** |
|---|---|---|
| **`main()`을 가진 쪽** | **컨테이너** | **내 애플리케이션** |
| 배포 단위 | WAR (컨테이너는 미리 설치) | **실행 가능 JAR 하나** |
| 서버 설정 | 컨테이너의 `server.xml` 등 | **`application.properties`** |
| 버전 결정권 | 운영팀이 깐 서버 | **내 빌드 파일** |

**이 뒤집힘이 무엇을 바꾸는가** — **컨테이너 이미지·클라우드 배포에서 값을 한다.** 이미지 안에 Tomcat을 미리 깔고 그 안에 WAR를 넣는 **2단계가 통째로 사라진다.**

**버전 결정권의 이동도 크다** — 외부 배포에서는 애플리케이션이 **운영팀이 깐 Tomcat 버전에 맞춰야** 했다. 내장에서는 **빌드 파일이 정한다.** 같은 서버에 서로 다른 Tomcat 버전을 쓰는 앱을 나란히 띄울 수 있다.

**§5의 오해**: **"내장 Tomcat은 경량판이다" — 아니다.** 같은 라이브러리이고 바뀐 것은 시작 주체뿐이다.

**§6의 반대 방향 경계**: **외부 배포는 여전히 가능하다.** 패키징을 `war`로 바꾸고, 주 클래스가 `SpringBootServletInitializer`를 상속하고, 내장 컨테이너 의존성을 `provided`(Gradle은 `providedRuntime`)로 내려 배포 대상과 충돌하지 않게 한다. **"내장이 기본"이지 "내장만 가능"이 아니다.**

## Q3. Undertow 제거가 Spring 팀의 선호가 아닌 근거

**Undertow 자신이 밝히는 서블릿 지원 범위가 Boot 4의 기준선에 못 미치기 때문이다.**

```text
Undertow README 의 서블릿 지원 범위 : 4.0 ~ 6.0
Boot 4 의 서블릿 명세 기준선        : 6.1
                                      ↑ 못 맞춘다
```

> **계약을 못 맞추는 구현이 자동으로 탈락한 것이지, 선호로 뺀 것이 아니다.**

**"결정의 성격이 다르다"**(§5) — Spring 팀이 한 결정은 **"Jakarta EE 11에 정렬한다"**이고, Undertow 제거는 **그 결정의 결과**다.

**반사실 검사로 확인된다**: Undertow를 남기려면 **Servlet 6.1 기준선을 포기하거나 Undertow가 지원할 때까지 기다려야** 한다. 둘 다 **Undertow 하나 때문에 Jakarta EE 11 정렬 전체를 미루는 것**이다.

**근거의 출처가 Spring이 아니라는 점이 중요하다** — 지원 범위를 밝힌 것은 **Undertow의 README**다. Spring 팀의 판단이 아니라 **Undertow가 스스로 선언한 사실**이 근거다.

**Ch15의 같은 항목과 이어진다** — [[../../part-7-whats-new-in-spring-boot-4/chapter-15-whats-new-in-spring-boot-4/01-whats-new-in-spring-boot-4]]가 Undertow 제거를 "기능이 제거됨" 범주에 넣었다. **왜 "제거"였는지의 근거가 이 노트의 ①(계약)이다.**

**§6의 관련 사실 — 교체 가능성은 무한하지 않다.** Boot 4가 공식 지원하는 내장 서블릿 컨테이너는 **Tomcat 11.0.x와 Jetty 12.1.x**이며, 그 밖에는 *"Servlet 6.1+ 호환 컨테이너에 배포 가능"*이라는 형태로만 열려 있다. **메이저 버전이 기준선을 올리면 프로퍼티 호환성만으로 제품을 유지할 수 없다.**

## Q4. Nginx는 Tomcat의 대체재인가

**아니다. Nginx는 Tomcat의 앞단이다.**

**Tomcat은 두 역할을 한 제품에 담고 있다**:

```text
Tomcat = [커넥터: 소켓·HTTP 파싱]  +  [서블릿 컨테이너: 서블릿 호출]
              ↑ 웹 서버 역할              ↑ Nginx 에는 없다

Nginx  = [커넥터·정적 파일·리버스 프록시]
              ↑ 앞의 절반만. 서블릿을 모른다
```

**§5**: **Nginx·Apache httpd는 앞의 절반만 하고 서블릿을 모른다. 그래서 Nginx는 Tomcat의 대체재가 아니라 앞단이다.**

**역할 경계**:

| | **Nginx** | **Tomcat** |
|---|---|---|
| TLS 종료·정적 파일 | ✅ | (가능하지만 주 역할 아님) |
| 로드 밸런싱·리버스 프록시 | ✅ | ✗ |
| **서블릿 실행** | **✗** | **✅** |
| 자바 코드 호출 | ✗ | ✅ |

**"Tomcat은 웹 서버 아닌가?"의 답은 "둘 다다"**(§5). 그래서 이름만 보고 "웹 서버끼리는 대체 가능하다"고 묶으면 틀린다.

**전형적인 배치**:

```text
브라우저 → Nginx (TLS 종료·정적 파일·로드밸런싱) → Tomcat (서블릿 실행)
```

**둘 다 HTTP를 다루므로 겹쳐 보이지만, 겹치는 것은 "앞의 절반"뿐이다.** 자바 애플리케이션을 실행하는 능력은 Nginx에 없다.

## Q5. `server.port`는 공통인데 `server.tomcat.*`은 전용인 기준

**모든 제품이 공통으로 갖는 개념이냐, 특정 제품에만 있는 개념이냐다.**

**공통 프로퍼티가 통하는 메커니즘 — 2.1의 4단계**:

> **팩터리가 `server.port` 같은 공통 프로퍼티를 받아 그 제품의 설정 API로 번역하고 서버 객체를 만든다.**

```text
server.port=9000
   ↓
TomcatServletWebServerFactory  → tomcat.setPort(9000)
JettyServletWebServerFactory   → jetty 의 설정 API 로 번역
   ↑ 번역할 대상이 양쪽에 다 있으므로 공통 이름이 성립한다
```

**책 p.14가 말하는 *"어떤 컨테이너든 `server.port`가 적용된다"*의 실제 구현 지점이 여기다.**

**`server.tomcat.*`이 전용인 이유 — 번역할 대상이 Tomcat에만 있다**:

```text
server.tomcat.threads.max
   ↓
Tomcat  → 대응하는 설정이 있다
Jetty   → 스레드 모델 자체가 다르다. 번역할 대상이 없다
   ↑ 공통 이름으로 만들 수 없다
```

**억지로 공통화하면 무엇이 나쁜가** — 이름은 같은데 제품마다 **의미가 미묘하게 다른** 프로퍼티가 생긴다. 설정 파일이 이식 가능해 보이는데 실제 동작이 다르면, **Ch15가 말한 "기본값이 바뀜"과 같은 종류의 조용한 사고**가 된다.

**그래서 접두어가 곧 계약의 표시다**:

| 접두어 | 뜻 | 서버를 바꾸면 |
|---|---|---|
| **`server.*`** | **모든 제품에 통하는 개념** | **그대로 통한다** |
| **`server.tomcat.*`** | **그 제품에만 있는 개념** | **무시된다** |

**실무적 함의**: 서버 교체를 염두에 둔다면 `server.tomcat.*`을 쓸 때마다 **"바꾸면 이 설정이 사라진다"**를 인식해야 한다. 조용히 무시되므로 **경고도 없다.**

## Q6. 서블릿이라는 이름이 "혼자서는 못 돈다"를 드러내는 방식

**`servlet` = `server` + `-let`이다.**

**`-let`은 축소 접미사다** — **브라우저 안에서 도는 작은 프로그램을 애플릿(applet)이라 부른 것과 같은 조어**로, **서버 안에서 도는 작은 프로그램**이라는 뜻이다.

> **이름 자체가 "혼자서는 못 돈다"를 말하고 있다.**

**구체적으로 무엇이 없는가**:

```text
서블릿에 없는 것
  main()      → 스스로 시작할 수 없다
  소켓        → 요청을 직접 받을 수 없다
  스레드 관리 → 동시 요청을 스스로 배정할 수 없다

  → 요청을 받아서 대신 호출해 줄 무언가가 반드시 필요하다
```

**그 역할이 **서블릿 컨테이너**다** — 서블릿 명세를 구현해 **요청을 받아 서블릿을 대신 호출해 주는 제품.**

**"컨테이너"라는 이름도 같은 것을 말한다** — **무언가를 담아 두고 그것의 생명주기를 관리하는 것**이다. 서블릿은 담기는 쪽이다.

**이름이 관계를 정확히 담고 있는 드문 예다**:

```text
applet   : 브라우저 안에서 도는 작은 것
servlet  : 서버  안에서 도는 작은 것
                 ↑ "안에서"가 이미 의존을 말한다
```

**이 사실이 Q1과 연결된다** — 서블릿이 혼자 못 도는 대신, **컨테이너와의 접점이 `service(request, response)` 하나로 좁아진다.** 그 좁은 접점이 곧 **제품을 갈아 끼울 수 있는 이유**다. 의존이 강한 대신 **접촉면이 작다.**

**§5의 관련 정정**: **"Undertow는 서블릿 컨테이너다"는 절반만 맞다.** Undertow는 `undertow-core`(논블로킹 HTTP 핸들러 엔진)와 `undertow-servlet`(서블릿 지원)이 **별도 아티팩트**이고, **서블릿 없이 순수 HTTP 서버로도 쓴다.** Jetty도 마찬가지다.

> **"서블릿 컨테이너"는 제품의 정체성이 아니라 제품이 제공하는 역할 중 하나로 읽는 것이 정확하다.**
