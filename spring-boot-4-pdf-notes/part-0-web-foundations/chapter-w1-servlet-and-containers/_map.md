# chapter-w1 개념 지도 — 서블릿과 컨테이너

> 목차가 아니라 관계도다. 세션을 열 때와 닫을 때 항상 펼친다.
>
> 이 챕터가 답하는 한 문장짜리 질문: **"내 컨트롤러 코드는 한 글자도 안 바뀌는데, 어떻게 서버 제품을 통째로 갈아 끼울 수 있는가?"**

## 축 1: 층 — 무엇이 계약이고 무엇이 제품인가

이 축을 세우지 않으면 "Tomcat", "서블릿", "내장 컨테이너"가 전부 같은 높이의 말로 들린다. 나머지 축은 전부 이 구분 위에 얹힌다.

```text
  내 코드 (@RestController)
        │  붙어 있는 대상
        ▼
  ① 계약   jakarta.servlet · Servlet 6.1        ← 바뀌지 않는 것
        │  구현하는 제품
        ▼
  ② 구현   Tomcat 11 · Jetty 12.1 · (Undertow)  ← 갈아 끼우는 것
        │  실행 방식
        ▼
  ③ 배치   내장(java -jar) · 외부(WAR)          ← 별개의 축
```

- **핵심 질문**: 지금 말하는 "서블릿 컨테이너"는 계약인가, 제품인가, 배치 방식인가?
- **주요 노드**: [[01-servlet-and-embedded-containers]] §1.3
- ②를 바꿔도 ①이 그대로라서 내 코드가 안 바뀐다. ③은 ②와 **직교한다** — 같은 Tomcat을 내장으로도, 외부로도 쓴다.

## 축 2: 시점 — 언제 무엇이 정해지는가

같은 "서버 선택"이라도 빌드 시점의 이야기와 시작 시점의 이야기, 요청 시점의 이야기가 뒤섞이면 설명이 엉킨다.

| 시점 | 일어나는 일 | 노트 |
|---|---|---|
| 빌드 | 스타터 의존성으로 어떤 구현이 클래스패스에 놓일지 결정 | [[01-servlet-and-embedded-containers]] §2.1-1 |
| 시작 — 컨텍스트 | 자동 구성이 제품별 팩터리 빈을 등록 | §2.1-2·3 |
| 시작 — 서버 생성 | 팩터리가 `server.port`를 제품 API로 번역, 포트 열림 | §2.1-4 |
| 시작 — 등록 | `DispatcherServlet`이 컨테이너에 서블릿으로 등록 | §2.1-5 |
| 요청 | 커넥터 → 계약 → 서블릿 → 컨트롤러 | §2.2 |

- **핵심 질문**: "Jetty로 바꿨다"는 말이 실제로 효력을 갖는 시점은 언제인가?

## 축 3: 경계 — 이 설명이 닿지 않는 곳

| 경계 | 이 챕터의 설명이 깨지는 지점 |
|---|---|
| 리액티브 스택 | WebFlux의 Reactor Netty는 서블릿 컨테이너가 아니다. ①이 다른 계약이다 |
| 명세 버전 | 계약에 버전이 있어 제품이 탈락할 수 있다 (Undertow ↔ Servlet 6.1) |
| 순수 웹 서버 | Nginx는 ②가 아니라 ② 앞단이다. 서블릿을 모른다 |
| 제품 전용 설정 | `server.port`는 공통이지만 `server.tomcat.*`은 번역되지 않는다 |

## 축 4: 책과의 접점 — 어디서 이 층이 필요해지는가

이 트랙은 독립 챕터가 아니라 책의 빈칸을 메우는 층이다. 아래 노트를 읽다 막히면 이 챕터로 내려온다.

| 책의 노트 | 그 노트가 결론만 말하는 것 | 여기서 채우는 것 |
|---|---|---|
| Ch1 `02` 스타터 | "Servlet API는 컨테이너와 애플리케이션의 계약" | 그 계약의 양쪽 끝에서 실제로 벌어지는 일 |
| Ch1 `03` 구성 프로퍼티 | "컨테이너를 바꿔도 `server.port`가 통한다" | 통하게 만드는 팩터리 층 |
| Ch2 `01` Initializr | JAR/WAR 선택, 실행 가능 JAR | 그 선택이 축 1의 ③이라는 위치 |
| Ch15 `01` Boot 4 변경점 | "Undertow 제거" | 제거가 아니라 탈락인 이유 |
