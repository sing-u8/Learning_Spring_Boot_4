## Q1. 지연 로딩이 원인이 아닌 이유 — `EAGER`로 바꾸면 쿼리 수는?

**쿼리 수가 같다.**

```text
[LAZY]   SELECT material  × 1
         getCompany() 접근 시 SELECT company × 20        → 21번

[EAGER]  SELECT material  × 1
         각 원료의 company 를 즉시 로딩 SELECT × 20      → 21번
```

**`EAGER`는 읽는 시점을 앞당길 뿐이고, 여전히 원료마다 한 번씩 읽는다.**

**오히려 나빠지는 면도 있다** — **회사를 쓰지 않는 화면에서도 20번을 읽는다.** LAZY였다면 안 읽었을 것이다.

**그러니 원인은 로딩 시점이 아니다**:

> **"연관을 항목마다 별도 쿼리로 읽는다"는 구조가 원인이고, 로딩 전략은 그 쿼리가 언제 나가느냐만 정한다.**

**§5의 정리**:

| 축 | **N+1** | **지연 로딩** |
|---|---|---|
| 정체 | 쿼리가 갈라지는 **현상** | 언제 읽을지 정하는 **설정** |
| 즉시 로딩이면 | **그대로 발생** | 해당 없음 |
| 해결 방법 | **연관을 같은 쿼리에 넣기** | — |

**"LAZY라서 N+1이 났다"는 진단은 절반만 맞다.** 고쳐야 하는 것은 **어느 쿼리에 무엇이 포함되는가**다.

**§6의 규칙**: **`EAGER`로 바꿔서 "해결"하지 않는다.** 쿼리 수는 그대로이고, 그 연관을 안 쓰는 화면까지 비용을 떠안는다.

## Q2. 발생하는 세 가지 조건과 그중 핵심

1. **여러 건을 반환하는 조회가 있다** — 한 건만 읽으면 추가 쿼리도 한 번뿐이라 문제가 되지 않는다
2. **각 건이 연관을 갖고 있다** — 연관이 없으면 추가로 읽을 것이 없다
3. **그 연관이 같은 쿼리에 포함되지 않았다** — 포함됐다면 이미 메모리에 있어 추가 쿼리가 필요 없다

**3번이 핵심이다.**

**왜 3번인가** — 1번과 2번은 **바꿀 수 없는 요구사항**이다. 목록을 보여 주는 화면에서 여러 건을 안 읽을 수 없고, 회사 이름을 보여 주려면 연관이 있어야 한다. **3번만이 개발자가 고를 수 있는 것**이다.

**그리고 3번은 기본값이 나쁜 쪽이다**:

> **`join fetch`나 엔티티 그래프를 쓰지 않으면 JPA는 목록 쿼리에 연관을 넣지 않는다. 기본 동작이 곧 N+1이다.**

**아무것도 안 하면 N+1이 된다.** 실수해서 생기는 게 아니라 **명시적으로 막아야 안 생긴다.**

**비유와 그 한계 — 품목마다 따로 계산하기**: 20개를 사면서 계산대에 20번 간다. **물건은 정확히 다 샀고 금액도 맞다** — 오래 걸릴 뿐이다.

→ **깨지는 지점**: **계산대에 20번 가는 사람은 자기가 20번 갔다는 걸 안다.** 코드는 그렇지 않다 — `getCompanyName()` 한 줄만 보이고, **그 줄이 20번 실행된다는 것도, 매번 DB에 간다는 것도 소스에 적혀 있지 않다.**

> **이 비가시성이 문제의 본질이고, 그래서 "조심하자"로는 해결되지 않는다.**

## Q3. 연관이 중첩되면 쿼리 수가 어떻게 변하나

**곱해진다.**

원료 20건, 각 원료에 성분 연결이 평균 8개, 각 연결이 성분을 가리킨다면:

```text
SELECT material                                    1번
  → 원료마다 SELECT material_substance             20번
      → 연결마다 SELECT substance                  20 × 8 = 160번
                                            합계   181번
```

**한 단계 깊어질 때마다 곱해진다.**

**일반식**: 목록 N건, 각각 연관 M개, 그 아래 또 K개면 → `1 + N + N×M + N×M×K`

**그래서 발견 카탈로그 상세처럼 "원료 → 성분 → 성분 정보"를 타고 들어가는 화면이 가장 위험하다.**

**출발 장면의 계산도 같은 방식이다**:

```text
①  SELECT ... FROM material WHERE ...           1번
②  SELECT ... FROM company WHERE id = ?        20번   ← 원료마다
③  SELECT ... FROM material_substance WHERE material_id = ?
                                               20번   ← 원료마다
                                        합계   41번
```

**코드에는 `map` 하나뿐인데 SQL은 41개다.**

**여기에 앞 챕터의 사실 하나가 겹친다** — **영속성 전이가 컬렉션을 순회하면 지연 로딩이 무력화된다.** 읽지 않으려던 컬렉션이 **삭제 경로에서 전부 초기화된다.** 삭제 API도 N+1의 무대가 된다.

## Q4. 이 문제가 기능 테스트를 통과하는 이유

**결과 데이터가 완전히 정확하기 때문이다.**

```text
회사 이름   → 맞다
성분 개수   → 맞다
정렬 순서   → 맞다
누락        → 없다
```

**틀린 것이 없으니 어떤 단언도 실패하지 않는다.**

**N+1은 "잘못된 답"이 아니라 "비싼 답"이다.** 기능 테스트는 답이 맞는지만 본다.

**그리고 나머지 개발 과정도 전부 통과한다**:

| 단계 | 왜 안 걸리나 |
|---|---|
| **로컬 실행** | 시드 데이터 10건이면 쿼리 21번에 **20ms**. 아무도 이상하다고 느끼지 않는다 |
| **코드 리뷰** | `m.getCompany().getCompanyName()`은 **완벽하게 자연스러운 자바 코드**다. 이 줄이 SQL을 만든다는 사실이 **코드에 적혀 있지 않다** |
| **기능 테스트** | 결과가 정확하다 |
| **원인 추적** | **원인 지점과 증상 지점이 다르다** — 느린 것은 목록 API인데, 원인은 `Material` 매핑의 fetch 설정이거나 DTO 변환 코드다 |

> **정상적인 개발 과정을 전부 통과한 뒤 운영에서만 드러난다. 이것이 N+1을 별도로 공부해야 하는 이유다.**

## Q5. 1차 캐시가 개발 환경에서 문제를 가리는 메커니즘

**같은 회사에 속한 원료가 여러 건이면 두 번째부터는 1차 캐시에서 반환되어 SQL이 안 나간다.**

```text
원료 20건이 전부 같은 회사 소속이라면
  첫 번째 getCompany().getCompanyName()   → SELECT company    1번
  나머지 19번                              → 1차 캐시에서 반환  0번
                                                       합계   2번
```

**첫 챕터의 동일성 보장이 그대로 작동한 것이다** — 같은 식별자를 다시 조회하면 캐시의 인스턴스를 준다.

**이것이 문제를 더 어렵게 만드는 이유 — 데이터 분포에 따라 결과가 달라진다**:

| | 회사 수 | 원료 20건에 대한 쿼리 |
|---|---|---|
| **개발 시드** | 2~3개 | **3~4번** — 문제가 안 보인다 |
| **운영 데이터** | 다양함 | **21번** — 그대로 N+1 |

> **같은 코드가 데이터 분포에 따라 다르게 동작한다.**

**그래서 "로컬에서 빨랐는데"가 아무 증거가 되지 못한다.**

**§5의 경계**: 1차 캐시가 줄여 주는 것은 **중복 접근**뿐이고, **서로 다른 20개 회사를 읽는 것은 그대로 20번**이다. **개발 데이터에서 문제가 안 보이는 이유이지 해결책이 아니다.**

**§6**: **로컬 데이터로 성능을 판단하지 않는다.**

## Q6. 쿼리 카운트 검증이 필요한 이유 — "성능 회귀를 기능 회귀처럼 잡는다"

**기능 검증으로는 못 잡으므로, 나간 SQL 개수를 직접 세어 단언한다.**

```java
@Test
void 발견_카탈로그_목록은_쿼리를_두_번만_쓴다() {
    Statistics stats = entityManagerFactory.unwrap(SessionFactory.class).getStatistics();
    stats.setStatisticsEnabled(true);
    stats.clear();

    service.discoveryList();

    assertThat(stats.getPrepareStatementCount()).isEqualTo(2);
}
```

**"기능 회귀처럼"이 무슨 뜻인가**:

```text
[기능 회귀]   답이 틀리면 → 테스트가 빨간불 → PR 이 막힌다
[성능 회귀]   답은 맞는데 느려지면 → 아무도 모른다 → 운영에서 발견

쿼리 카운트 단언을 붙이면
[성능 회귀]   쿼리가 늘어나면 → 테스트가 빨간불 → PR 이 막힌다
              ↑ 기능 회귀와 같은 경로로 잡힌다
```

**구체적으로 무엇을 막는가**: **다음 사람이 DTO 변환에 연관 하나를 더 타고 들어가는 순간 테스트가 깨진다.** 그 사람은 자기가 무엇을 했는지 **그 자리에서** 안다.

> **N+1에 대해 실제로 작동하는 유일한 방어선이다.**

**왜 "유일한"인가** — Q4에서 본 대로 로컬 실행·코드 리뷰·기능 테스트가 전부 통과시킨다. **남는 것은 숫자를 직접 세는 것뿐이다.**

**CosmoRoute는 자리가 이미 마련되어 있다** — 실 PostgreSQL을 Testcontainers로 띄우고 있다. **`ModuleStructureTest`가 모듈 경계를 테스트로 강제하는 것과 같은 성격의 장치다**:

> **규율을 사람의 주의력이 아니라 테스트에 맡긴다.**

## Q7. 실행 계획 분석으로 N+1을 찾을 수 없는 이유

**개별 쿼리에는 아무 문제가 없기 때문이다.**

```text
SELECT * FROM company WHERE id = ?
  실행 계획: Index Scan using company_pkey
  비용: 1ms
  → 완벽하다. 고칠 것이 없다.

  이 쿼리가 20번 나갔다는 사실은 실행 계획에 없다.
```

**실행 계획은 "쿼리 하나가 어떻게 실행되는가"를 설명하는 도구다. "이 쿼리가 몇 번 나갔는가"는 그 도구의 관심사가 아니다.**

**§5의 대비**:

| | **느린 쿼리** | **N+1** |
|---|---|---|
| 정체 | 한 번의 실행이 오래 걸린다 | **각각은 빠른데 횟수가 많다** |
| 실행 계획에서 | **보인다** — Seq Scan, 잘못된 조인 | **안 보인다** — 인덱스를 잘 타고 1ms |
| 슬로우 쿼리 로그 | **걸린다** | **안 걸린다** — 임계값을 넘지 않는다 |

> **모니터링 지표가 달라야 보인다.**

**무엇을 봐야 하나**:

- **요청당 쿼리 수** — 이것이 N+1의 고유 지표다
- **같은 SQL 패턴의 반복 횟수** — APM이 "이 쿼리가 이번 요청에서 20번"이라고 알려 주면 즉시 보인다
- **테스트의 쿼리 카운트 단언**(Q6) — 운영에 가기 전에 잡는 유일한 방법

**흔한 오진**: 목록 API가 느려서 **인덱스를 추가**한다. 개별 쿼리가 0.8ms로 빨라지지만 **여전히 20번 나가므로** 체감 개선이 거의 없다. **원인을 안 짚고 증상을 손댄 것이다.**

## Q8. 쿼리 카운트 단언을 모든 테스트에 붙이면 안 되는 이유

**매핑을 조금만 바꿔도 무더기로 깨지기 때문이다.**

```text
Material 에 연관 하나를 추가했다
  → 그 연관을 읽는 모든 경로의 쿼리 수가 바뀐다
  → 쿼리 카운트 단언이 붙은 테스트가 전부 빨간불
  → 대부분은 "예상된 변화"인데 하나씩 숫자를 고쳐야 한다
```

**세 가지가 함께 나빠진다**:

1. **신호 대 잡음비가 떨어진다** — 매번 여러 개가 깨지면 **"또 그거네" 하고 숫자만 고치게 된다.** 진짜 회귀도 같은 방식으로 지나간다.
2. **리팩터링 비용이 커진다** — 매핑을 개선하는 PR이 테스트 20개를 함께 고치는 PR이 된다.
3. **단언이 의도를 잃는다** — "이 API는 쿼리 2번이어야 한다"는 **설계 의도**인데, 전부 붙이면 그냥 **현재 상태의 스냅샷**이 된다.

**§6의 기준**:

> **목록 API처럼 회귀가 실제로 아픈 경로에만 붙인다.**

**"실제로 아픈"의 판별**(§6): **모든 N+1을 없애야 하는 것은 아니다.** **상세 화면처럼 한 건만 읽는 경로에서 연관을 한두 번 더 읽는 것은 문제가 아니다.** **목록과 반복이 있는 곳만 본다.**

**같은 이유로 §6의 다른 경계도 함께 기억한다**: **쿼리 수를 줄이는 것이 항상 이득은 아니다.** 다음 노트에서 볼 **페치 조인은 쿼리를 1번으로 만들지만 결과 행을 부풀린다.** **교환이지 개선이 아니다** — [[02-fetch-join-entitygraph-batch-size]].
