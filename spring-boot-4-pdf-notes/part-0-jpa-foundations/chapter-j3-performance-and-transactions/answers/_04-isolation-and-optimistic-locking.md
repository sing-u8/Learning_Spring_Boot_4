## Q1. `READ COMMITTED`에서 덮어쓰기가 막히지 않는 이유

**A와 B 모두 격리 규칙을 하나도 어기지 않았기 때문이다.**

```text
시각  운영자 A                          운영자 B
 t1   SELECT material WHERE id=X        ← 커밋된 데이터를 읽었다 ✅
 t2                                    SELECT material WHERE id=X  ✅
 t3   material.rename("새 이름")
 t4                                    material.updateSource("새 URL")
 t5   커밋                              ← 정상
 t6                                    커밋  ← 정상. 그런데 A 의 이름이 사라진다
```

**`READ COMMITTED`가 보장하는 것은 "커밋되지 않은 데이터를 읽지 않는다"뿐이다.** 위 시나리오에서 **A와 B는 각각 커밋된 데이터를 정상적으로 읽었다.**

**진짜 문제는 "읽고 → 애플리케이션에서 고치고 → 쓰는" 세 단계 구조에 있다**:

```text
읽기 ────────── (여기서 다른 트랜잭션이 끼어든다) ────────── 쓰기
  t2                                                          t6
```

**DB는 그 사이에 무슨 일이 있었는지 판정할 근거가 없다** — **B가 보낸 UPDATE는 그 자체로 완벽하게 정상적인 문장**이다.

**두 사실이 겹쳐 최악이 된다**(앞 챕터):

1. **Hibernate의 기본 UPDATE는 바뀌지 않은 컬럼까지 전부 포함한다** — B의 UPDATE에 `name`도 들어 있다
2. **`Material`·`Company` 어디에도 `@Version`이 없다** — 판정할 근거가 없다

**그래서 B의 UPDATE가 A의 이름 변경까지 t2 시점의 옛 값으로 되돌린다. 아무 에러도 나지 않는다. A는 자기 변경이 저장됐다고 믿는다.**

**`REPEATABLE READ`로 올리면?** PostgreSQL은 실제로 이 충돌을 감지해 직렬화 실패로 거부한다. **그런데 격리 수준을 올리면 그 트랜잭션의 모든 읽기가 영향을 받고, 재시도 처리를 애플리케이션 전반에 넣어야 한다.** **특정 엔티티의 동시 수정을 막으려고 전역 규칙을 바꾸는 셈이다.**

## Q2. 낙관적 락이 실제로 잠그는 것

**아무것도 잠그지 않는다.**

> **락이라는 이름이 붙었지만 어느 단계에서도 아무것도 잠그지 않는다. 읽는 동안 다른 트랜잭션은 자유롭게 읽고 쓴다.**

**충돌은 막지 않고 탐지한다.**

**§5의 지적**:

> **이름 때문에 "읽는 동안 다른 사람이 못 건드린다"고 오해하기 쉽다. 실제로는 전부 자유롭게 읽고 쓰며, 충돌은 커밋 시점에야 드러난다. 이름이 오해를 부르는 대표적인 예다.**

**그럼 왜 "락"이라 부르는가** — **결과가 락과 같기 때문이다.** "두 트랜잭션이 같은 행을 동시에 성공적으로 고칠 수 없다"는 보장을 제공한다. **방법이 다를 뿐 목표가 같아서 같은 이름을 쓴다.**

**비유와 그 한계 — 위키 문서 편집**: **낙관적**은 저장할 때 *"그 사이 다른 사람이 이 문서를 고쳤습니다"*라고 알려 주는 방식이고, **비관적**은 편집을 시작하는 순간 **문서를 잠가** 다른 사람이 못 들어오게 하는 방식이다.

→ **깨지는 지점**: 위키의 잠금은 **사람이 풀 수도 있고 타임아웃도 있다.** DB의 비관적 락은 **그 트랜잭션이 끝날 때까지 무조건 유지된다.** 트랜잭션 안에 외부 API 호출 같은 느린 작업이 하나만 있어도, **그동안 그 행을 건드리려는 모든 요청이 멈춘다.** [[03-transactional-propagation-and-proxy-limits]]에서 "트랜잭션을 길게 잡지 말라"고 한 것이 **여기서 실제 비용이 된다.**

## Q3. `@Version`이 붙었을 때 UPDATE 문

```sql
UPDATE material
   SET name = ?, version = 8
 WHERE id = ?
   AND version = 7          -- ← 이 조건이 추가된다
```

**두 곳이 달라진다**:

| 위치 | 무엇이 |
|---|---|
| **`SET`** | `version = 읽은값 + 1` — 다음 트랜잭션이 이 변경을 감지할 수 있게 |
| **`WHERE`** | `version = 읽은값` — **"내가 읽은 그 상태인가"를 DB에게 묻는다** |

**다섯 단계 전 과정**:

1. **엔티티를 조회하면 버전 값도 함께 읽힌다** — 나중에 비교할 기준이 필요하다
2. **필드를 고친다** — 더티 체킹이 변경을 감지한다
3. **플러시 시점에 UPDATE를 만들면서 `WHERE`에 읽었던 버전을 넣는다**
4. **동시에 `SET version = 읽은값 + 1`을 넣는다**
5. **갱신된 행 수를 확인한다** — 1이면 성공, **0이면 예외**

```java
@Entity
public class Material {
    @Version
    @Column(name = "version", nullable = false)
    private long version;
}
```

**개발자가 쓰는 코드는 필드 하나뿐이다.** `WHERE` 조건도 버전 증가도 **JPA가 자동으로** 넣는다.

**§5의 관련 사실 — 버전은 실제 변경이 있을 때만 올라간다.** 조회만 한 엔티티는 버전이 그대로다. 그래서 **"읽기만 했는데 충돌했다"는 상황은 기본적으로 생기지 않는다.** 읽은 사실 자체로 버전을 올리려면 `OPTIMISTIC_FORCE_INCREMENT`를 명시해야 한다.

## Q4. 갱신된 행이 0건인 것이 왜 충돌의 신호인가

**`WHERE id = ? AND version = 7`에서 `id`는 반드시 맞는다. 그러니 0건이 나올 수 있는 이유는 버전이 7이 아니라는 것뿐이다.**

```text
내가 읽을 때        version = 7
누군가 먼저 커밋     version = 8 로 올라감
내 UPDATE           WHERE version = 7  → 매칭 0건
```

**그리고 버전은 UPDATE가 성공할 때만 올라간다.** 즉 **"버전이 바뀌었다" = "누군가 이 행을 성공적으로 고쳤다"**이다. 다른 해석의 여지가 없다.

**논리를 정리하면**:

```text
갱신 0건
  → id 는 맞는데 version 이 안 맞는다
  → 내가 읽은 뒤 누군가 version 을 올렸다
  → version 은 성공한 UPDATE 로만 올라간다
  → 내가 읽은 뒤 누군가 이 행을 고쳤다
  → 지금 내가 쓰면 그 변경을 덮어쓴다
  → 예외를 던진다
```

**"0건"이 예외가 되는 이유** — 일반적인 UPDATE에서 0건은 **"고칠 게 없었다"**는 정상 결과다. 하지만 여기서는 **`id`로 지정한 행이 분명히 존재한다는 것을 아는 상태**다(방금 읽었으니까). 그래서 0건은 **불가능한 결과**이고, 불가능한 결과에는 원인이 하나뿐이다.

> **0은 "그 사이 누군가 고쳤다"는 유일한 신호다.**

**이 방식의 우아함** — 별도의 조회도, 잠금도, 추가 왕복도 없다. **원래 보내야 할 UPDATE 하나에 조건 하나를 얹었을 뿐**인데 충돌 탐지가 된다.

## Q5. 충돌 탐지 후의 선택지 셋과 맞는 상황

**낙관적 락은 예외를 던지는 데서 끝난다. 그다음은 애플리케이션이 정해야 한다.**

| 선택지 | 무엇을 하나 | 맞는 상황 |
|---|---|---|
| **① 사용자에게 알린다** | *"다른 관리자가 이 원료를 수정했습니다. 새로고침 후 다시 시도하세요."* | **관리자 화면처럼 사람이 개입하는 경로** |
| **② 재시도한다** | 다시 읽고, 다시 고치고, 다시 쓴다 | **자동 처리 경로.** 단 **무한 재시도가 되지 않게 횟수를 제한**해야 한다 |
| **③ 병합한다** | A의 이름과 B의 URL을 **둘 다 살린다** | **가장 좋지만 도메인마다 규칙을 정해야 해서 비싸다** |

**①이 기본이다**:

> **"충돌을 조용히 덮어쓰지 않는다"는 것만으로 이미 큰 개선이고, 그것이 낙관적 락의 최소 목표다.**

**②를 고를 때 주의** — 재시도가 **의미 있으려면 재시도 후 결과가 달라져야** 한다. 사용자가 입력한 값을 그대로 다시 쓰는 재시도는 **결국 덮어쓰기와 같아진다.** 재시도는 **읽은 값을 기반으로 계산하는** 경우(재고 차감, 카운터 증가)에 맞는다.

**③이 비싼 이유** — "이름과 URL은 병합 가능하지만 이름과 이름은 불가능하다" 같은 판단을 **필드마다** 해야 한다. 그리고 그 규칙이 도메인 지식이라 자동화할 수 없다.

**§6의 금지**: **낙관적 락 예외를 삼키지 않는다.** `catch`하고 무시하면 **원래의 덮어쓰기와 결과가 같아진다** — 예외를 붙인 의미가 없어진다. **최소한 사용자에게 알려야 한다.**

## Q6. 낙관적과 비관적을 가르는 판별 질문

> **"충돌했을 때 사용자에게 다시 하라고 할 수 있는가?"**

**있으면 낙관적, 없으면 비관적**이다.

**"없는" 경우의 예** — 재고 차감처럼 **금액이 걸린 것.** "재고 차감에 실패했으니 다시 시도하세요"는 사용자 경험 문제가 아니라 **비즈니스 문제**다. 결제가 이미 진행됐다면 되돌릴 수 없다.

| 기준 | **낙관적** | **비관적** |
|---|---|---|
| 충돌 빈도 | **낮을 때** | **높을 때** |
| 잠금 | 없음 | **있음 (대기 발생)** |
| 실패 시점 | **커밋할 때** | **읽을 때 (대기 후)** |
| 사용자에게 | "다시 하세요" 가능해야 함 | **기다리게 함** |
| 읽기 성능 | 영향 없음 | **잠긴 동안 막힘** |
| 교착 위험 | **없음** | **있음** |

**"실패 시점"이 핵심 차이다** — 낙관적은 **일을 다 한 뒤에** 실패를 알리고, 비관적은 **시작하기 전에** 기다리게 한다. 그래서 **일이 헛되지 않는 쪽이 비관적**이고, **기다리지 않는 쪽이 낙관적**이다.

**빈도가 판단을 뒤집는다** — 충돌이 잦으면 낙관적 락은 **계속 실패하고 계속 재시도**하게 되어, 결국 비관적보다 느려진다. "낙관적"이라는 이름이 **가정을 말하고 있다**: 충돌은 드물다.

**비관적 락의 세부 모드**:

| 모드 | SQL | 뜻 |
|---|---|---|
| `PESSIMISTIC_WRITE` | `for update` | **배타적 잠금.** 읽기도 쓰기도 막는다 |
| `PESSIMISTIC_READ` | `for share` (지원 시) | 공유 잠금. 다른 읽기는 허용 |
| `PESSIMISTIC_FORCE_INCREMENT` | 위 + 버전 증가 | 변경이 없어도 버전을 올린다 |

**대기가 곤란하면**: Hibernate의 **`UPGRADE_NOWAIT`**는 이미 잠긴 행이면 **즉시 실패**하고, **`UPGRADE_SKIPLOCKED`**는 **잠긴 행을 건너뛴다** — 후자는 **작업 큐를 여러 워커가 나눠 가질 때** 쓰인다.

## Q7. `PESSIMISTIC_WRITE`와 `LockModeType.WRITE`가 다른 이유

**`WRITE`는 비관적 락이 아니라 낙관적 모드다.**

**Hibernate의 `LockMode`와 JPA의 `LockModeType`은 이름이 겹치지만 의미가 완전히 같지 않다**:

| JPA `LockModeType` | 실제 의미 (Hibernate 대응) |
|---|---|
| `READ` | **`OPTIMISTIC`** — 낙관적 |
| **`WRITE`** | **`OPTIMISTIC_FORCE_INCREMENT`** — **낙관적** |
| **`PESSIMISTIC_WRITE`** | **`for update`** — **비관적** |
| `PESSIMISTIC_READ` | `for share` — 비관적 |

**왜 이런 혼란이 생겼나** — JPA 초기의 `READ`/`WRITE`는 **낙관적 락만 있던 시절의 이름**이다. 나중에 비관적 락이 추가되면서 `PESSIMISTIC_` 접두어가 붙은 이름들이 생겼고, **옛 이름은 호환을 위해 남았다.**

**그래서 이름만 보고 고르면 정반대가 된다**:

```java
@Lock(LockModeType.WRITE)              // ❌ 낙관적이다. 아무것도 안 잠근다
@Lock(LockModeType.PESSIMISTIC_WRITE)  // ✅ select ... for update
```

**`WRITE`를 쓰고 "잠갔다"고 믿으면** Q1의 시나리오가 그대로 재현되는데, 이번에는 **락을 걸었다고 믿는 상태**라 더 찾기 어렵다.

**규칙**: **비관적으로 잠그려면 `PESSIMISTIC_`으로 시작하는 것만 쓴다.**

## Q8. `@Version` 도입이 세 문제를 함께 푸는 이유

**확인된 사실**:

- `Material`·`Company` 어디에도 **`@Version`이 없다**
- **스키마에도 `version` 컬럼이 없다**
- 관리자 큐레이션 경로는 **운영자가 여럿이고, 같은 원료를 동시에 열 가능성이 있다**
- 앞 챕터에서 본 대로 **`@DynamicUpdate`를 붙이려면 `@Version`이 선행**되어야 한다

**세 가지를 함께 푼다**:

| 푸는 문제 | 어떻게 |
|---|---|
| **① 덮어쓰기 방지** | Q1의 시나리오에서 B의 UPDATE가 **0건으로 실패**한다 |
| **② `@DynamicUpdate` 안전성 확보** | 바뀐 컬럼만 쓰면 **존재한 적 없는 조합**이 생길 수 있는데, 버전이 그걸 막는다 |
| **③ "누가 먼저 고쳤는가" 판정 근거** | 버전 값 자체가 **변경 순서의 기록**이 된다 |

**②가 특히 값지다** — `@DynamicUpdate`는 그 자체로 성능 개선(UPDATE 문이 짧아지고 인덱스 갱신이 줄어든다)인데, **`@Version` 없이는 위험해서 못 쓴다.** 하나를 도입하면 다른 하나가 **잠금 해제**된다.

**도입 비용도 명확하다**:

1. Flyway 마이그레이션으로 `version bigint NOT NULL DEFAULT 0` 추가
2. 엔티티에 `@Version` 필드 추가
3. 서비스에서 `OptimisticLockException`을 **읽을 수 있는 409로 변환**

**3번의 자리도 이미 있다** — **CosmoRoute가 이미 RFC 9457 Problem Details를 쓰고 있으므로 변환 자리가 마련되어 있다.**

## Q9. 그런데 지금 도입하지 않는 이유

**첫 슬라이스의 목표가 아니고, 동시 수정이 아직 실제로 발생한 문제가 아니기 때문이다.**

> **첫 슬라이스는 매핑과 N+1이 목표이고, 동시 수정은 아직 실제로 발생한 문제가 아니다.** *"이 문제 때문에 도입했다"*는 근거가 생겼을 때 하는 것이 순서고, **그때 ADR 하나가 나온다.**

**두 가지가 함께 걸려 있다**:

1. **근거 없는 도입은 ADR을 쓸 수 없다** — "왜 이걸 넣었는가"에 *"좋다고 해서"* 말고 답할 게 없다
2. **도입에는 지속 비용이 있다** — §6: **모든 엔티티에 `@Version`을 붙이지 않는다.** 붙이면 **모든 UPDATE에 조건이 하나 더 붙고, 배치 갱신에서 충돌이 잦아진다**

**"지금 안 한다"와 "필요 없다"는 다르다** — Q8에서 본 대로 **필요해질 이유가 셋이나 있다.** 다만 **그중 어느 것도 아직 실제 문제로 나타나지 않았다.**

**같은 판단이 이 트랙 곳곳에 있다**:

| 항목 | 판단 |
|---|---|
| `Persistable` 도입 (j1-04) | 대량 삽입 경로가 생기고 **쿼리 수를 측정한 뒤** |
| `@Version` (여기) | 동시 수정이 **실제 문제로 나타났을 때** |
| `default_batch_fetch_size` (j3-02) | **지금 켠다** — 설정 한 줄이고 나빠질 게 없다 |

**세 번째와의 대비가 기준을 보여 준다** — **비용이 거의 없고 되돌리기 쉬우면 지금**, **스키마 변경과 지속 비용이 따르면 근거가 생긴 뒤.**

**§6의 마지막 줄이 이 판단이다**: **지금 도입할 이유가 없으면 도입하지 않는다.**
