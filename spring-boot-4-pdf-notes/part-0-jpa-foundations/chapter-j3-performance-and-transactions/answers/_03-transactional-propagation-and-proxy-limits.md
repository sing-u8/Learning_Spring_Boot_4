## Q1. 자기 호출에서 `@Transactional`이 무시되는 이유

**`@Transactional`은 코드에 적힌 대로 실행되는 것이 아니라, Spring이 그 빈을 프록시로 감싸고 프록시가 호출을 가로채서 트랜잭션을 열고 닫는다. 자기 호출은 프록시를 지나가지 않는다.**

```text
[정상 — 외부에서 호출]
  Controller ──▶ 프록시 ──▶ 트랜잭션 시작 ──▶ 실제 서비스 객체
                                                     linkAll()

[문제 — 같은 객체 안에서 호출]
  linkAll() ──▶ this.linkOne()
                    ▲
                    └── 프록시를 거치지 않는다.
                        @Transactional 을 읽을 기회 자체가 없다.
```

**`linkAll` 안의 `linkOne(...)`은 사실 `this.linkOne(...)`이다.** 이미 실제 객체 안에 들어와 있으므로 **프록시를 지나갈 일이 없다.**

**프록시가 하는 일 5단계 중 4번이 결정적이다**:

1. Spring이 `@Transactional` 빈을 프록시로 감싼다
2. 다른 빈이 주입받으면 **실제 객체가 아니라 프록시**를 받는다
3. 프록시가 호출을 받으면 전파 규칙을 보고 트랜잭션을 시작하거나 참여한다
4. **실제 객체의 메서드를 호출한다** — **이 지점부터는 프록시 밖이다**
5. 반환되면 커밋하거나 롤백한다

> **실제 객체 안으로 들어간 뒤의 호출은 전부 프록시 밖이다.**

**Spring 공식 문서의 명시**:

> *"기본값인 프록시 모드에서는 **프록시를 통해 들어온 외부 메서드 호출만 가로채진다.** 자기 호출은 호출되는 메서드에 **애노테이션이 붙어 있어도** 트랜잭션을 유발하지 않는다."*

## Q2. 코드만 보고 알아채기 어려운 이유

**문제가 있다는 신호가 코드 어디에도 없기 때문이다.**

```text
로그        없음
경고        없음
컴파일 오류 없음
런타임 예외 없음 (당장은)

그런데 애노테이션은 소스에 버젓이 붙어 있다
  → 오히려 "적용되고 있다"는 인상을 준다
```

**비유와 그 한계 — 회사 정문의 보안 검색대**: 밖에서 들어오는 사람은 반드시 통과하지만, **이미 건물 안에 있는 사람이 다른 층으로 이동할 때는 거치지 않는다.**

→ **깨지는 지점**: **검색대를 안 거친 사람은 출입 기록이 없어서 나중에 확인할 수 있다.** 자기 호출은 **아무 흔적도 남기지 않는다.**

> **그래서 이 함정은 반드시 미리 알고 있어야만 피할 수 있다.**

**증상이 원인을 가리키지 않는 것도 문제다** — Q3에서 보듯 실제로 터지는 것은 **`UnexpectedRollbackException`**이고, 그 예외 메시지는 "커밋하려는데 rollback-only가 찍혀 있다"고만 말한다. **`linkOne`의 `REQUIRES_NEW`가 무시됐다는 정보는 어디에도 없다.**

**한 발 더 나쁜 형태**(§5): **`private` 메서드에 붙인 `@Transactional`** — 프록시는 인터페이스나 하위 클래스로 만들어지므로 `private` 메서드는 **애초에 가로챌 수 없다.** 같은 이유로 효과가 없고, **이쪽은 더 눈에 안 띈다**(Q9).

## Q3. `catch`로 잡았는데도 `UnexpectedRollbackException`이 나는 과정

```text
linkAll()  ── 트랜잭션 T 시작
  linkOne() ── REQUIRES_NEW 가 무시되고 T 에 그대로 있음
      예외 발생 → Spring 이 T 를 rollback-only 로 표시
  catch 로 예외를 잡음 → 애플리케이션은 "처리했다"고 판단
  ...나머지 39건 계속 처리...
linkAll() 반환 → 커밋 시도
  → T 는 이미 rollback-only → UnexpectedRollbackException
```

**순서대로**:

1. `linkAll`이 트랜잭션 T를 연다
2. `linkOne`이 자기 호출이라 **새 트랜잭션을 못 만들고 T에 그대로 있다**
3. 예외가 나면 Spring이 **T에 rollback-only 플래그를 찍는다**
4. `catch`가 예외를 잡는다 — **예외의 전파는 멈췄지만 플래그는 그대로다**
5. 나머지 39건이 계속 처리된다 — **이미 롤백이 확정된 트랜잭션 안에서**
6. 커밋 시도 → **rollback-only가 찍혀 있으므로 커밋을 거부하고 예외를 던진다**

**§5의 정리**:

> **`catch`는 예외의 전파를 막을 뿐 트랜잭션 상태를 되돌리지 않는다. 이미 rollback-only가 찍혔다면 커밋할 방법이 없다.**

**한 번 찍힌 플래그는 애플리케이션 코드로 되돌릴 수 없다.** 그게 설계다 — 되돌릴 수 있으면 "이 트랜잭션은 안전하지 않다"는 판정이 무의미해진다.

**5번이 특히 낭비다** — 이미 결과가 정해진 상태에서 39건을 더 처리한다. 시간도 락도 그대로 쓴다.

> **부분 성공이 필요하면 트랜잭션 자체를 나눠야 한다.**

## Q4. Spring의 기본 롤백 규칙과 checked 도메인 예외

**Spring은 unchecked 예외(`RuntimeException`·`Error`)에만 롤백하고, checked 예외는 롤백하지 않는다.**

```text
throw new RuntimeException(...)         → 롤백 ✅
throw new IllegalStateException(...)    → 롤백 ✅ (RuntimeException 하위)
throw new IOException(...)              → 커밋 ⚠️ (checked)
throw new MyCheckedException(...)       → 커밋 ⚠️
```

**도메인 예외를 checked로 만들면 무엇이 문제인가**:

```text
@Transactional
public void curate(...) {
    ...부분적으로 저장...
    if (중복) throw new CuratedCatalogRuleViolation(...);   // checked 라면
}
  → 예외가 났는데 트랜잭션은 커밋된다
  → 중간까지 저장된 데이터가 그대로 남는다
  → 사용자에게는 실패를 알리고 DB에는 절반이 남는다
```

**"예외 = 실패 = 롤백"이라는 직관이 깨진다.** 그리고 이건 조용하다 — 예외는 정상적으로 밖으로 나가고 API가 409를 반환한다. **DB에 뭐가 남았는지는 아무도 안 본다.**

**§2.3의 확인 항목**: **CosmoRoute의 `CuratedCatalogRuleViolation`이 unchecked인지 확인해 볼 만한 지점이다.**

**왜 Spring이 이런 기본값을 골랐나** — EJB의 관례를 따른 것으로, checked 예외는 **"호출자가 처리할 것을 예상한 정상 흐름의 일부"**로 보는 자바 관례를 반영한다. **처리될 것을 전제한 예외를 롤백 사유로 삼지 않는다**는 논리다.

**바꾸려면** `@Transactional(rollbackFor = ...)`로 명시할 수 있지만, **애초에 도메인 예외를 unchecked로 두는 편이 단순하다.**

## Q5. 자기 호출을 푸는 세 가지 방법과 대가

**① 다른 빈으로 분리한다 — 공식 문서가 권하는 방법**

```java
@Service
public class CuratedCatalogService {
    private final SubstanceLinker linker;   // 별도 빈 = 프록시로 주입된다

    @Transactional
    public LinkResult linkAll(UUID materialId, List<UUID> ids) {
        for (UUID id : ids) {
            try { linker.linkOne(materialId, id); }   // 프록시를 거친다
            catch (CuratedCatalogRuleViolation e) { ... }
        }
    }
}

@Service
public class SubstanceLinker {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void linkOne(UUID materialId, UUID substanceId) { ... }
}
```

**대가**: 클래스가 하나 늘어난다. (Q6에서 이게 대가가 아닌 이유를 다룬다.)

**② 자기 자신을 주입한다**

```java
@Lazy private final CuratedCatalogService self;   // 프록시가 주입된다
...
self.linkOne(materialId, id);
```

**대가**: **동작하지만 코드를 읽는 사람이 `self`의 정체를 알아야 한다.** `this.linkOne()`과 `self.linkOne()`이 다르게 동작한다는 것이 소스에 안 적혀 있다. **순환 참조라 `@Lazy`가 필요한 것도 신호다** — 언어가 "이건 자연스럽지 않다"고 말하고 있다.

**③ `AopContext.currentProxy()`**

**대가**: 공식 문서가 *"매우 권장되지 않는다"*고 적는다. **클래스가 Spring AOP에 결합되고 프록시 노출 설정이 필요하다.**

> **쓰지 않는다.**

**네 번째 선택지도 있다**(§5): **AspectJ 로드타임 위빙.** 바이트코드를 직접 고치므로 **자기 호출도 가로채진다.** 하지만 **설정이 무겁고, 대부분의 프로젝트는 분리로 해결하는 편이 낫다.**

## Q6. "다른 빈으로 분리"가 억지가 아니라 설계 신호인 이유

> **"트랜잭션 경계가 다르면 다른 책임"이라고 읽으면 이 분리가 억지가 아니라 설계 신호가 된다.**

**왜 그런가** — 트랜잭션 경계는 **"어디까지가 하나의 원자적 작업인가"**를 선언하는 것이다. `linkAll`과 `linkOne`이 **다른 경계**를 갖는다는 것은:

```text
linkAll  : "40건을 시도하고 결과를 집계한다"        ← 조율(orchestration)
linkOne  : "한 건을 원자적으로 연결한다"            ← 단위 작업(unit of work)
```

**이건 원래 다른 책임이다.** 하나는 **여러 번 실패해도 되는 흐름 제어**이고, 하나는 **성공 아니면 실패인 원자 단위**다. 같은 클래스에 있던 것이 오히려 우연이었다.

**그래서 프록시의 제약이 설계를 나쁘게 만드는 게 아니라 드러낸다** — "다른 트랜잭션 경계를 원한다"는 요구는 **이미 두 개의 책임이 있다는 증거**다.

**②·③과 비교하면 차이가 분명하다**:

| 방법 | 무엇을 하는가 |
|---|---|
| ① 분리 | **설계를 요구에 맞춘다** |
| ② `self` 주입 | **제약을 우회한다** — 설계는 그대로 |
| ③ `AopContext` | **제약을 우회한다** — 게다가 프레임워크에 결합된다 |

**②③은 "왜 이렇게 썼는지"를 나중에 설명해야 하지만, ①은 설명이 필요 없다.** 클래스 이름과 위치가 이미 의도를 말한다.

## Q7. `REQUIRES_NEW`를 반복문에서 쓸 때의 커넥션 위험

**항목마다 커넥션이 하나씩 더 필요하고, 바깥 트랜잭션의 커넥션은 그동안 계속 잡혀 있다.**

```text
linkAll  ── 트랜잭션 T (커넥션 1) ─────────────────── 40건 내내 점유
  linkOne #1 ── REQUIRES_NEW (커넥션 2) → 반납
  linkOne #2 ── REQUIRES_NEW (커넥션 2) → 반납
  ...
  linkOne #40
```

**동시에 두 개**를 쓴다. 한 요청이 커넥션 2개를 점유한다는 뜻이다.

**§5의 비교**:

| 축 | `REQUIRED` | `REQUIRES_NEW` |
|---|---|---|
| 진행 중인 것이 있으면 | 참여 | **멈추고 새로 시작** |
| 안쪽 실패 시 바깥 | **함께 롤백** | 바깥은 계속 가능 |
| **커넥션** | **하나** | **둘 (동시에 점유)** |
| 교착 위험 | 낮음 | **같은 행을 건드리면 있다** |

**동시 요청이 겹치면 계산이 나빠진다**:

```text
커넥션 풀 10, 동시 요청 6개
  각 요청이 2개씩 점유 = 12개 필요
  → 풀 고갈 → 대기 → 타임아웃
```

**교착 위험도 실재한다** — 바깥 T가 이미 잠근 행을 안쪽의 새 트랜잭션이 건드리려 하면, **자기 자신을 기다리게 된다.** 같은 요청 안에서 나는 교착이라 원인을 짐작하기 어렵다.

**§6**: **`REQUIRES_NEW`를 반복문 안에서 남발하지 않는다.** **40건이면 커넥션 압박이 실제로 발생한다.**

**함께 지킬 것**: **트랜잭션을 길게 잡지 않는다.** 외부 API 호출이나 파일 처리를 트랜잭션 안에 넣으면 그동안 **커넥션과 락이 묶인다.** **DB 작업만 있는 구간으로 좁힌다.** 그리고 **`@Transactional`을 컨트롤러에 붙이지 않는다** — 요청 처리 전체가 트랜잭션이 된다.

## Q8. 참여하는 트랜잭션에서 `readOnly = true`가 무시되면

**앞 챕터의 더티 체킹으로 이어진다** — [[../chapter-j1-persistence-context/03-dirty-checking-and-snapshots]].

**규칙**: **`readOnly`는 새 트랜잭션을 시작할 때만 의미가 있다.** 쓰기 트랜잭션 안에서 `readOnly = true` 메서드를 부르면(그리고 그것이 프록시를 거친다면) **바깥 트랜잭션의 설정이 이긴다.**

```text
[의도]
  listSuppliers()  @Transactional(readOnly = true)
    → FlushMode 를 MANUAL 로 → 더티 체킹 안 돎 → 실수로 만져도 안전

[실제 — 쓰기 트랜잭션에 참여했다면]
  curate()         @Transactional          ← 쓰기 트랜잭션 T 시작
    listSuppliers()  readOnly = true 무시  ← T 에 참여
      → FlushMode 는 T 의 것 (AUTO)
      → 더티 체킹이 돈다
      → 조회 결과 엔티티를 만지면 UPDATE 가 나간다
```

**§2.5의 진단**:

> **조회 전용이라고 믿고 있던 경로가 쓰기 트랜잭션에 참여하면, 그 안에서 만진 엔티티에 UPDATE가 나갈 수 있다.**

**이 사고가 나쁜 이유** — 앞 챕터에서 본 그대로다. **코드 어디에도 `save()`가 없는데 UPDATE가 로그에 찍힌다.** 게다가 여기서는 **`readOnly = true`가 붙어 있어서** 더 안전하다고 믿게 된다.

**§6**: **`readOnly = true`가 항상 적용된다고 믿지 않는다.** 참여하는 경우에는 바깥 설정이 이긴다.

**함께 볼 것 — 클래스 레벨 선언의 성질**(§2.5): `CuratedCatalogService`는 클래스 레벨에 `@Transactional`이 있고 조회 메서드에만 `readOnly = true`를 다시 붙였다. **클래스 레벨 선언은 public 메서드 전부에 적용되므로, 새 메서드를 추가하면 자동으로 트랜잭션 안에 들어간다.** 의도한 동작이지만 **트랜잭션이 필요 없는 메서드까지 포함된다.**

## Q9. `private` 메서드에 `@Transactional`을 붙이면

**프록시가 가로챌 수 없기 때문에 아무 효과가 없다.**

**프록시의 두 가지 구현 방식 모두 `private`을 다룰 수 없다**:

| 프록시 종류 | 만드는 방법 | `private` 메서드는 |
|---|---|---|
| JDK 동적 프록시 | **인터페이스를 구현**한다 | 인터페이스에 없다 → 가로챌 수 없다 |
| CGLIB | **하위 클래스를 만든다** | **오버라이드 불가** → 가로챌 수 없다 |

**둘 다 "메서드를 재정의해 앞뒤에 코드를 끼워 넣는" 방식**인데, `private`은 재정의 대상이 아니다.

**자기 호출과 같은 이유이지만 한 가지가 더 나쁘다**(§5):

> **이쪽은 더 눈에 안 띈다.**

**왜 더 안 띄는가**:

```text
[자기 호출]  linkOne() 은 public 이다
             → 다른 클래스에서 부르면 트랜잭션이 작동한다
             → 테스트에서 직접 부르면 통과할 수 있다
             → "어떤 경로에서는 된다"는 단서가 있다

[private]    어느 경로로도 절대 작동하지 않는다
             → 단서조차 없다
             → 애노테이션이 완전한 장식이다
```

**그리고 `private`은 애초에 밖에서 못 부르므로, 그 메서드를 부르는 것은 항상 자기 호출이다.** 두 문제가 겹쳐 있다.

**대응**: `private`으로 두고 싶은 로직에 트랜잭션 경계가 필요하다면, **그건 그 로직이 별도 책임이라는 신호다**(Q6). **다른 빈으로 분리한다.**
