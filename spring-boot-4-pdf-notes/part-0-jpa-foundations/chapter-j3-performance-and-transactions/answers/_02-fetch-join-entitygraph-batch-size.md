## Q1. `JOIN`과 `JOIN FETCH`의 차이 — SELECT 목록으로

**연관 테이블의 컬럼이 SELECT 목록에 들어가느냐 아니냐다.**

| 축 | **`JOIN`** | **`JOIN FETCH`** |
|---|---|---|
| 목적 | **조건에 쓰기 위해** | **연관을 함께 읽기 위해** |
| **SELECT 목록** | **연관 컬럼 없음** | **연관 컬럼 포함** |
| 조회 후 연관 접근 | **추가 쿼리 발생** | **이미 채워져 있음** |
| 결과 행 | 컬렉션이면 곱해짐 | 컬렉션이면 곱해짐 |

```sql
-- JOIN
SELECT m.id, m.name, m.company_id           ← material 컬럼만
  FROM material m JOIN company c ON ...
 WHERE c.homepage IS NOT NULL               ← 조인은 조건 평가용

-- JOIN FETCH
SELECT m.id, m.name, m.company_id,
       c.id, c.company_name, c.homepage     ← company 컬럼까지
  FROM material m JOIN company c ON ...
```

**왜 컬럼이 있어야 하는가** — **프록시가 아니라 실제 값을 채우려면 컬럼이 있어야 한다.** 조인만 걸고 컬럼을 안 가져오면 채울 값이 없으므로 **여전히 프록시**다.

**§5의 흔한 착각**:

> **`JOIN`만 쓰고 N+1이 해결됐다고 생각하는 것이 흔한 착각이다. 조인은 걸렸지만 연관은 여전히 프록시다.**

**증상이 특히 헷갈린다** — 쿼리에 `JOIN company`가 분명히 있는데 로그에는 `SELECT ... FROM company WHERE id = ?`가 20번 더 찍힌다. **조인을 걸었으니 됐다고 믿으면 원인을 찾지 못한다.**

## Q2. 컬렉션 페치 조인에서 결과 행이 몇 배가 되나

**자식 개수만큼 곱해진다.**

```text
원료 20건, 각각 성분 연결 8개

SELECT m.*, ms.*
  FROM material m JOIN material_substance ms ON ...

→ 결과 행 160개. 원료 하나가 8줄로 반복된다.
```

**JPA는 이 160행을 읽어 중복을 제거하고 원료 20개로 조립한다. 결과는 맞다.**

**하지만 DB에서 애플리케이션으로 오는 데이터가 8배다.** 그리고 반복되는 것은 `ms` 컬럼만이 아니라 **`m`의 모든 컬럼**이다 — 원료의 긴 설명 텍스트가 8번씩 실려 온다.

**컬렉션 둘 이상이면 곱의 곱이 된다**:

```text
성분 연결 8개 × 다른 컬렉션 5개 = 20 × 8 × 5 = 800 행
```

**`List` 타입 컬렉션 둘을 동시에 페치하면 Hibernate가 아예 예외를 던진다** — **중복 제거가 불가능해지기 때문이다.** 어느 조합이 원본인지 복원할 수 없다.

**여기서 규칙 하나가 나온다**:

> **단일 연관 페치 조인은 거의 항상 안전하고, 컬렉션 페치 조인은 항상 따져 봐야 한다.**

**단일 연관(`@ManyToOne`)이면 행이 늘지 않는다** — 원료 하나에 회사 하나이므로 20건은 그대로 20행이다. **페이징도 문제없다.**

**비유와 그 한계 — 택배 배송**: 한 트럭에 전부 싣거나(페치 조인), 열 개씩 묶어 여러 번 보내거나(배치 페칭), 송장에 따로 적어 두거나(엔티티 그래프).

→ **깨지는 지점**: 택배는 **어떻게 묶든 물건 개수가 그대로다.** 페치 조인은 **조인하는 순간 물건이 8배로 불어났다가 도착해서 다시 줄어든다.** 원료 20개를 받으려고 160행을 실어 나른다. **"묶어 보내면 효율적"이라는 직관이 여기서 뒤집힌다.**

## Q3. 페이징 + 컬렉션 페치 조인에서 Hibernate가 하는 일

**`limit`을 빼고 전부 읽은 뒤 메모리에서 잘라 낸다.**

Hibernate 소스의 판단:

```java
else if ( hasLimit && containsCollectionFetches ) {
    if ( !isPaginationPushedToDerivedTable() ) {
        errorOrLogForPaginationWithCollectionFetch();
    }
    return limitOmittingExecutionContext();   // limit 을 빼고 실행한다
}
```

**이 동작이 **메모리 페이징**이다.**

```text
원료 5만 건 중 20건을 요청
  → limit 을 뺀 SQL 이 나간다
  → 5만 건 × 성분 8개 = 40만 행을 읽는다
  → 중복 제거해 원료 5만 개로 조립
  → 메모리에서 앞 20개를 자른다
  → 20건 반환

로그: HHH90003004 경고
```

**왜 그렇게 하는가 — 대안이 틀린 답이기 때문이다**(Q4). Hibernate는 **틀린 답을 주는 대신 느린 답을 준다.**

**문제는 이것이 기본적으로 경고만 찍고 계속 돈다는 점이다**:

> **정확성 문제가 아니라 성능 문제로 조용히 남는다.**

**답이 맞으므로 테스트가 통과하고, 개발 데이터가 작으면 느리지도 않다** — [[01-n-plus-one-when-it-happens]] Q4와 정확히 같은 형태의 은폐다.

**대응**(§6): **`fail_on_pagination_over_collection_fetch`를 켜면 경고 대신 예외가 나서 즉시 드러난다.** 경고를 예외로 바꾸는 것이 이 문제에 대한 유일한 실효 조치다.

## Q4. `LIMIT`을 그대로 붙이면 왜 답이 틀리나

**행을 자르는데, 우리가 원하는 것은 원료를 자르는 것이기 때문이다.**

```text
원료 20건, 각 성분 8개 → 결과 160행

LIMIT 20 을 붙이면
  행 1~8    → 원료 A 의 성분 8개
  행 9~16   → 원료 B 의 성분 8개
  행 17~20  → 원료 C 의 성분 4개   ← 잘렸다

결과: 원료 3개, 그중 하나는 성분이 절반만 있다
```

**두 가지가 동시에 틀린다**:

1. **원료 개수가 틀리다** — 20개를 요청했는데 3개가 온다
2. **데이터가 불완전하다** — 원료 C는 성분 8개 중 4개만 있다. **그런데 애플리케이션은 그게 전부라고 믿는다**

**2번이 더 나쁘다.** 개수가 적은 건 눈에 띄지만, **성분이 잘린 원료는 정상처럼 보인다.** 화면에 "성분 4개"라고 표시되고 아무도 의심하지 않는다.

**그래서 Hibernate가 `limit`을 빼는 선택을 한다** — **느린 것과 틀린 것 중 느린 쪽을 고른 것이다.**

**근본 원인**: SQL의 `LIMIT`은 **결과 행** 단위로 작동하는데, 컬렉션 조인 후에는 **행과 엔티티가 1:1이 아니다.** `LIMIT`이 엔티티 개수를 셀 방법이 없다.

**그래서 해법이 "다르게 자르기"가 아니라 "조인하지 않기"다** — 페이징이 필요하면 **컬렉션을 조인에서 빼야 한다.** 그 자리를 배치 페칭이 메운다(Q6).

## Q5. 페치 조인과 엔티티 그래프의 차이는 SQL 수준인가

**아니다. SQL 수준에서는 거의 같다. 다른 것은 선언 위치다.**

```java
// 페치 조인 — 쿼리 문자열 안
@Query("SELECT m FROM Material m JOIN FETCH m.company WHERE ...")
List<Material> findDiscoveryMaterials();

// 엔티티 그래프 — 쿼리 문자열 밖
@EntityGraph(attributePaths = {"company"})
@Query("SELECT m FROM Material m WHERE " + CatalogVisibility.DISCOVERY)
List<Material> findDiscoveryMaterials();
```

**Hibernate는 엔티티 그래프를 left outer join으로 번역한다.** 한계도 같다 — **컬렉션을 넣으면 페이징이 깨진다.**

**§5의 정리**:

> **"무엇이 더 빠른가"는 잘못된 질문이고, "같은 쿼리를 여러 그래프로 재사용할 일이 있는가"가 맞는 질문이다.**

**그럼에도 엔티티 그래프를 쓰는 이유는 재사용성이다**:

```java
// 같은 쿼리, 다른 그래프
@EntityGraph(attributePaths = {"company"})
List<Material> findForList();

@EntityGraph(attributePaths = {"company", "substanceLinks"})
Optional<Material> findForDetail(UUID id);
```

**쿼리 문자열은 그대로 두고 호출 지점마다 무엇을 함께 읽을지만 바꾼다.**

**CosmoRoute와 특히 잘 맞는다** — `CatalogVisibility` 상수처럼 **조건이 공유되는 구조**에서는, 조건은 한 곳에 두고 **페치 전략만 경로별로** 다르게 할 수 있다. 페치 조인이라면 같은 조건을 쿼리마다 복사해야 한다.

**차이의 성격**: 이건 **성능 선택이 아니라 코드 구조 선택**이다. 그래서 벤치마크로 고를 수 없고, **"조건과 페치 전략이 독립적으로 변하는가"**로 고른다.

## Q6. 배치 페칭이 페이징과 함께 쓸 수 있는 이유

**목록 쿼리에 연관을 넣지 않으므로 결과 행이 부풀지 않기 때문이다.**

```text
[컬렉션 페치 조인]  목록 쿼리에 조인이 들어간다 → 행이 8배 → LIMIT 이 틀린다
[배치 페칭]         목록 쿼리는 그대로            → 행 20개  → LIMIT 정상 ✅
                    그 뒤 연관을 IN 절로 모아 읽는다
```

**세 단계**:

1. **지연 로딩을 그대로 둔다.** 목록 쿼리에 연관이 포함되지 않는다 — **결과 행을 부풀리지 않기 위해서다**
2. **첫 프록시에 접근하는 순간, 아직 초기화되지 않은 같은 종류의 프록시를 모은다** — 어차피 곧 다 필요해질 것이므로
3. **모은 식별자를 `IN` 절 하나로 묶어 읽는다** — 왕복 횟수를 나누기 위해

```sql
SELECT ... FROM company WHERE id IN (?, ?, ?, ..., ?)
```

**핵심은 "목록 쿼리를 건드리지 않는다"**이다. 페이징은 목록 쿼리에서 일어나고, 배치 페칭은 **그 뒤에** 작동한다. 두 단계가 분리되어 있으니 서로 간섭하지 않는다.

**§5의 대비 — 즉시 로딩과 다르다**:

| | 즉시 로딩 | **배치 페칭** |
|---|---|---|
| 쿼리 수 | **N번** | **`ceil(N/크기)`번** |
| 지연 로딩 유지 | 아니다 | **그렇다** |
| 접근하지 않는 연관 | **그래도 읽는다** | **안 읽는다** |

**세 번째가 중요하다** — 배치 페칭은 **접근이 일어나야** 작동한다. 그래서 회사를 안 쓰는 화면에서는 여전히 쿼리 1번으로 끝난다.

**설정 한 줄이다**:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

## Q7. 배치 크기 100에 항목 500개면 쿼리는 몇 번인가

**`ceil(500 / 100) = 5`번이다.**

```text
서로 다른 회사 500개
  IN (?, … 100개) × 5회
  → SELECT 5번
```

**비교**:

| 방식 | 쿼리 수 | 결과 행 | 페이징 |
|---|---|---|---|
| 아무것도 안 함 | **501번** | 500 | ✅ |
| 페치 조인 (단일 연관) | **1번** | 500 | ✅ |
| 페치 조인 (컬렉션) | 1번 | **부풀어남** | ❌ |
| **배치 페칭 (크기 100)** | **6번** (1+5) | 500 | ✅ |

> **1번으로 만들지는 못하지만 결과 행을 부풀리지도 않는다.**

**그것이 배치 페칭의 위치다** — **최선이 아니라 안전한 차선**이다. 501을 6으로 줄이면서 아무것도 깨뜨리지 않는다.

**크기를 무한정 키우면 안 되는 이유**(§6): **`IN` 절의 파라미터 수가 커지면 DB의 실행 계획 캐시가 갈라지고 파서 부담이 늘어난다.** 파라미터 개수마다 다른 쿼리로 취급되기 때문이다. **100 안팎이 흔한 출발점이다.**

**CosmoRoute의 현재 상태**: `application.yaml`에 `default_batch_fetch_size`가 없다. Hibernate 속성은 `jdbc.time_zone`만 있다 — **배치 페칭이 꺼져 있다.**

**그래서 §2.4의 판단**: **`default_batch_fetch_size`를 전역으로 켜는 것이 가장 값싼 조치다.** 매핑을 건드리지 않고 **설정 한 줄**이며, **켜서 나빠지는 경우가 거의 없다.** **첫 슬라이스에서 가장 먼저 시도할 것**이다.

## Q8. 목록과 상세에서 다른 전략을 고르는 근거

**페이징의 유무다.**

| 요구 | 결론 |
|---|---|
| 회사 이름을 보여 준다 (**단일 연관**) | **페치 조인** — 행이 늘지 않고 안전하다 |
| 성분 개수·목록을 보여 준다 (**컬렉션**) | **배치 페칭** — 페이징을 살려야 한다 |
| **페이징이 필요하다** | **컬렉션 페치 조인은 배제된다** |
| **상세 화면은 한 건만 읽는다** | 페이징이 없으므로 **컬렉션 페치 조인 가능** |

```java
// 목록 — 페이징 있음
@EntityGraph(attributePaths = {"company"})          // 단일 연관만
Page<Material> findDiscoveryPage(Pageable pageable);
// 성분 연결은 default_batch_fetch_size 가 처리한다

// 상세 — 한 건
@EntityGraph(attributePaths = {"company", "substanceLinks"})
Optional<Material> findDiscoveryDetail(UUID id);
```

**같은 컬렉션인데 목록에서는 배제되고 상세에서는 허용되는 이유**: Q3의 문제가 **`hasLimit && containsCollectionFetches`** 두 조건이 겹칠 때만 발생하기 때문이다. **한 건 조회에는 `limit`이 없으니 조건이 성립하지 않는다.**

> **하나를 고르는 문제가 아니라 경로마다 다르게 고르는 문제다.**

**§6의 관련 경계**: **모든 쿼리에 페치 조인을 기본으로 달지 않는다.** 그 연관을 쓰지 않는 호출부에서도 읽게 된다 — **즉시 로딩을 매핑 대신 쿼리로 옮긴 것에 지나지 않는다.**

**그리고 §2.5의 네 번째 선택지를 먼저 검토한다**:

```java
@Query("SELECT new com.cosmoroute.api.catalog.MaterialSummary(m.id, m.name, c.companyName)"
        + " FROM Material m JOIN m.company c WHERE ...")
Page<MaterialSummary> findDiscoverySummaries(Pageable pageable);
```

**여기에는 페치 조인이 없다 — 일반 `JOIN`이고, 필요한 컬럼만 SELECT해서 DTO 생성자에 넣는다.**

- 쿼리 **1번**, 컬럼은 **필요한 것만**
- **영속성 컨텍스트에 아무것도 담기지 않는다** — 1차 캐시도 스냅샷도 없다
- **프록시가 없으므로 N+1이 발생할 수 없다**

> **셋 중 무엇을 고를지 고민하기 전에 "엔티티가 정말 필요한가"를 먼저 묻는 것이 순서다.**

## Q9. `distinct`가 해결하는 것과 못 하는 것

**해결하는 것 — 애플리케이션 메모리에서의 중복 원료 제거.**

```text
컬렉션 페치 조인 결과 160행 (원료 20개 × 성분 8개)

distinct 없이 → List<Material> 에 같은 원료가 8번씩 들어간다 (160개)
distinct 있고 → 원료 20개
```

**못 하는 것 — DB로 나가는 행 수를 줄이지 못한다.**

```text
DB → 애플리케이션:  160행  ← distinct 를 붙여도 그대로
애플리케이션 안:     20개  ← 여기서만 줄어든다
```

**즉 전송량 문제는 그대로 남는다.** `distinct`는 **조립 결과를 정리할 뿐 조인의 부작용을 되돌리지 않는다.**

**그리고 못 하는 것이 하나 더 있다 — 페이징을 살리지 못한다.** Q3의 문제는 **행 수가 엔티티 수와 다르다**는 것이고, `distinct`는 읽어 온 **뒤에** 작동하므로 `LIMIT`에는 아무 영향이 없다.

**§5의 추가 사실**: **최신 Hibernate는 이 중복 제거를 기본으로 해 주므로 `distinct`를 적을 필요가 줄었다.** 예전에 습관처럼 붙이던 것이 지금은 대부분 불필요하다.

**정리**:

| | `distinct` |
|---|---|
| 중복 원료 제거 | ✅ (최신 Hibernate는 기본) |
| 전송량 | ❌ 그대로 160행 |
| 페이징 | ❌ 여전히 깨진다 |
| 쿼리 수 | ❌ 무관 |

**그래서 `distinct`는 "컬렉션 페치 조인을 안전하게 만드는 장치"가 아니다.** Q2·Q3의 문제는 그대로 남는다.
