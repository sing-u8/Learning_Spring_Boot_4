## Q1. Spring Boot에서 OSIV의 기본값과 확인 방법

**기본값은 켜짐(`true`)이다.**

Spring Boot 공식 문서:

> *"웹 애플리케이션에서 Spring Boot는 **기본적으로** `OpenEntityManagerInViewInterceptor`를 등록해 'Open EntityManager in View' 패턴을 사용하며, 뷰에서의 지연 로딩을 지원한다. 이 동작은 `spring.jpa.open-in-view`를 `false`로 설정해 끌 수 있다."*

**CosmoRoute의 `application.yaml`에는 `open-in-view`가 없다** — 그런데 **없다고 꺼져 있는 것이 아니다.**

**설정에 없을 때 확인하는 방법 — 시작 로그의 경고**:

애플리케이션을 띄우면 Spring Boot가 **이 설정이 켜져 있으니 명시적으로 지정해 경고를 없애라**는 내용의 경고를 남긴다.

> **이 경고가 존재하는 것 자체가 힌트다. 기본값인데 경고를 하는 설정은 흔치 않다.**

**Spring 팀이 경고를 넣은 이유** — 기본값을 바꾸면 기존 애플리케이션이 깨지므로 못 바꾸지만, **모르고 쓰는 상태를 그대로 두고 싶지도 않은** 것이다. **"검토한 결과 켠 것"과 "몰라서 켜진 것"을 구분하게 만드는 장치**다.

**그래서 §6의 규칙이 나온다**: **켜 두기로 했다면 명시적으로 적는다**(Q8).

## Q2. OSIV가 늘리는 것과 늘리지 않는 것

**늘리는 것 — 영속성 컨텍스트의 수명. 늘리지 않는 것 — 트랜잭션 경계.**

```text
[OSIV 꺼짐]
  요청 ─┬─ 컨트롤러 ─┬─ 서비스 @Transactional ─┬─ 응답 ─┐
        │            │  ├ 트랜잭션 시작        │        │
        │            │  ├ 컨텍스트 생성        │        │
        │            │  └ 커밋 · 컨텍스트 종료 │        │
        │            │                         └ 준영속 │
        └────────────┴─────────────────────────────────┘
                                    ▲ 여기서 지연 로딩 = 예외

[OSIV 켜짐]
  요청 ─┬─ 컨트롤러 ─┬─ 서비스 @Transactional ─┬─ 응답 ─┐
        │  컨텍스트 생성                        │        │
        │            │  ├ 트랜잭션 시작        │        │
        │            │  └ 커밋 (트랜잭션만 끝남)│        │
        └────────────┴─────────────────────────┴────────┘
             컨텍스트는 여기까지 살아 있다
                        ▲ 지연 로딩 성공. 단 변경은 저장되지 않는다.
```

| | OSIV | 트랜잭션 연장 |
|---|---|---|
| **늘어나는 것** | **영속성 컨텍스트 수명** | **트랜잭션** |
| 지연 로딩 | 가능 | 가능 |
| **변경 저장** | **안 된다** | 된다 |
| 커넥션 | (Q4 참고) | 트랜잭션 끝까지 |

**"OSIV가 트랜잭션을 늘린다"가 가장 자주 틀리는 것이다.** 두 수명이 원래 하나였다가 **OSIV가 그것을 분리**한 것이다.

**인터셉터가 하는 일 5단계**:

1. **요청이 들어오면 컨텍스트를 만들어 스레드에 바인딩** — 이후 어느 계층에서든 같은 컨텍스트를 쓰게
2. **서비스의 `@Transactional`이 그 컨텍스트에 트랜잭션을 붙인다** — 새로 만들지 않고 참여한다
3. **서비스가 끝나면 트랜잭션만 커밋되고 컨텍스트는 유지된다**
4. **컨트롤러·직렬화 단계의 지연 로딩이 성공한다** — 다만 **트랜잭션 밖이라 읽기만 가능**
5. **응답이 끝나면 인터셉터가 컨텍스트를 닫는다**

## Q3. OSIV가 켜져 있는데도 컨트롤러의 변경이 저장되지 않는 이유

**엔티티는 여전히 영속 상태라 더티 체킹 대상이지만, 커밋할 트랜잭션이 없기 때문이다.**

```text
서비스 반환 후
  트랜잭션    끝났다        ← 커밋할 것이 없다
  컨텍스트    살아 있다     ← 엔티티는 여전히 영속

컨트롤러에서 m.rename("새 이름")
  → 더티 체킹은 이 변경을 "감지할 수 있는" 상태다
  → 그런데 플러시를 유발할 트랜잭션 커밋이 없다
  → 아무 일도 일어나지 않는다
```

> **앞 챕터의 준영속 사고와 증상이 같은데 원인은 다르다.**

| | 준영속 사고 (j1-04) | OSIV 아래 |
|---|---|---|
| 엔티티 상태 | **준영속** | **영속** |
| 지연 로딩 | **예외** | **성공** |
| 변경 저장 | 안 됨 | **안 됨** |
| 원인 | 컨텍스트가 없다 | **트랜잭션이 없다** |

**"영속인데 저장이 안 된다"가 특히 헷갈린다** — 앞 챕터에서 "영속 상태면 더티 체킹이 작동한다"고 배웠는데, 여기서는 영속인데 작동하지 않는다. **정확한 조건은 "영속 상태 + 커밋되는 트랜잭션"**이고, OSIV는 앞 절반만 남긴다.

**§5의 진단**: **OSIV가 켜졌다고 컨트롤러의 변경이 저장되지는 않는다. 이걸 혼동하면 "왜 저장이 안 되지"에서 막힌다.**

**비유와 그 한계 — 도서관의 대출 창구와 열람실**: **대출 창구(트랜잭션)는 닫혔는데 열람실(컨텍스트)은 계속 열어 둔다.** 책을 더 꺼내 볼 수는 있지만 **빌려 갈 수는 없다.**

→ **깨지는 지점**: 열람실에서는 내가 책을 몇 권 더 꺼내 보든 **다른 사람에게 영향이 없다.** 여기서는 다르다 — 책을 꺼낼 때마다 **사서(커넥션)를 한 명 불러야 하고**, 사서는 열 명뿐이며 **모든 열람실이 그들을 공유한다.** 게다가 **언제 몇 번 부를지가 열람실 밖에서는 보이지 않는다.**

## Q4. "커넥션을 요청 끝까지 붙잡는다"가 부정확한 이유 — 대신 무엇이 비용인가

**현재 Spring Boot 기본값에서는 트랜잭션이 끝나는 순간 커넥션이 풀로 돌아간다.**

Hibernate 공식 문서(RESOURCE_LOCAL 트랜잭션):

> *"RESOURCE_LOCAL 트랜잭션에서는 커넥션을 **필요할 때 획득하고 트랜잭션이 끝난 뒤 반환한다.**"*

**Spring Boot의 JPA 구성이 RESOURCE_LOCAL이고 커넥션 처리 모드가 `DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION`이므로, 서비스 트랜잭션이 커밋되는 순간 커넥션은 풀로 돌아간다.**

> **OSIV가 늘리는 것은 영속성 컨텍스트이지 커넥션 임대가 아니다.**

**그럼 무엇이 비용인가 — 획득 횟수와 그 위치다**:

```text
[고전적 요약이 말하는 것]
  요청 하나 = 커넥션 하나를 길게 점유
  → 대응: 풀을 키운다

[실제로 일어나는 것]
  컨트롤러에서 프록시를 건드릴 때마다
    → 그 쿼리도 커넥션이 필요하다
    → 트랜잭션 밖이므로 그때 다시 빌린다
  → 요청 하나가 풀을 예측할 수 없는 시점에 여러 번 때린다
  → N+1 이 응답 변환에서 터지면 그 횟수만큼
```

**§5의 정리 — 바뀌는 것은 결론이 아니라 진단 방향이다**:

> **점유 시간이 문제라면 풀을 키우는 것이 임시방편이라도 되지만, 실제 문제가 획득 횟수와 그 위치라면 풀을 키워도 N+1은 그대로다. 고쳐야 할 것은 "어디서 몇 번 읽는가"이고, 그건 페치 전략의 문제다.**

**고전적 요약이 아주 틀린 것도 아니다** — **커넥션 처리 모드를 `*_AND_HOLD`로 바꾸거나 옛 Hibernate 기본값을 쓰면 실제로 요청 내내 점유한다.**

**그래서 "내 애플리케이션에서 확인할 것"으로 다뤄야 한다**:

- **`hibernate.connection.handling_mode`의 실제 값**
- **HikariCP의 `hikaricp.connections.active`·`hikaricp.connections.pending` 지표**

## Q5. OSIV를 끄면 나는 예외가 왜 "비용이 아니라 신호"인가

**끄면 지금까지 조용히 일어나던 것이 소리를 낸다.**

```yaml
spring:
  jpa:
    open-in-view: false
```

**서비스 밖에서 지연 로딩을 하면 즉시 예외가 난다.** 불편해 보이지만 이것은 **"어디까지 읽을지를 서비스 계층에서 정하라"는 강제**다.

**따라오는 것 세 가지**:

| 얻는 것 | 왜 |
|---|---|
| **페치 전략이 한곳에 모인다** | 페치 조인·엔티티 그래프·배치 페칭 선택이 **서비스 안에서** 결정된다 |
| **쿼리 수 검증이 실제로 유효해진다** | **서비스 메서드를 감싸면 그 안에서 모든 쿼리가 끝난다** |
| **엔티티가 계층 밖으로 새는 것이 예외로 드러난다** | **DTO 변환 경계가 강제된다** |

**켜 두면 이 셋이 전부 무력해진다**:

- 앞 노트의 N+1이 **서비스 계층 밖에서** 발생한다 — 쿼리 수를 세는 테스트는 서비스 메서드를 감싸는데 **실제 쿼리는 컨트롤러에서 나간다**
- 응답 직렬화가 getter를 전부 호출하므로, DTO 변환을 빠뜨리고 엔티티를 그대로 반환하면 **객체 그래프 전체가 조용히 로딩된다**
- **DB 쿼리가 트랜잭션 밖에서 나간다**

> **문제가 사라진 것이 아니라 보이지 않게 된 것이다.**

**§5의 관련 함정 — 예외가 안 나는 두 가지 이유**:

> 하나는 **OSIV가 켜져 있어서**, 다른 하나는 **필요한 것을 이미 페치해 뒀기** 때문이다. **후자가 맞는 이유이고, 전자는 문제를 가린 것이다.** 예외가 안 난다는 사실만으로 안심하면 안 되는 이유가 이것이다.

**§5의 또 다른 대비 — 끄기 vs 트랜잭션을 컨트롤러까지 넓히기**: 둘 다 예외를 없애지만 **정반대 방향**이다. 후자는 앞 노트의 문제(긴 트랜잭션, 락 유지, 커넥션 점유)를 **전부 키운다.**

> **예외를 없애는 것이 목표가 아니라 경계를 명확히 하는 것이 목표다.**

## Q6. CosmoRoute에서 꺼야 하는 이유 넷

**일반론이 아니라 이 저장소의 구조 때문이다.**

**① 서버 뷰가 없다**

**OSIV의 "View"는 서버가 HTML을 렌더링하는 단계**를 뜻한다. CosmoRoute의 프론트는 **Nuxt와 Vue SPA로 완전히 분리**되어 있고, 백엔드는 `contracts/openapi.yaml` 계약에 따라 **JSON만 반환**한다.

> **지연 로딩이 필요한 뷰 렌더링 단계 자체가 존재하지 않는다.**

**② 응답 타입이 이미 DTO다**

`CompanySummary`·`MaterialSummary`가 **모듈의 공개 타입으로 따로 있다.** **엔티티가 컨트롤러 밖으로 나갈 일이 설계상 없다.** 그렇다면 컨트롤러 단계의 지연 로딩도 필요 없다.

**③ 모듈 경계를 테스트가 검증하는 저장소다**

ADR-0008에 따라 `internal` 패키지와 경계 테스트로 계층을 강제한다. **OSIV는 그 경계를 흐리는 방향으로 작동한다** — 서비스가 반환한 것을 **컨트롤러가 더 파고들 수 있게** 해 주기 때문이다.

**④ 첫 슬라이스가 N+1을 다룬다**

OSIV가 켜져 있으면 **쿼리가 서비스 밖에서 나가므로**, 앞 노트에서 만든 **쿼리 카운트 검증이 실제 동작을 못 잡는다.**

> **이 저장소에서 OSIV는 얻는 것이 없고 잃는 것만 있다.**

**네 이유의 구조** — ①②는 **"켤 이유가 없다"**, ③④는 **"켜면 해롭다"**이다. 한쪽만으로도 충분한데 둘 다 성립한다.

## Q7. 끄면 DTO 변환을 어디서 해야 하나

**서비스의 트랜잭션 안이다.**

```java
@Transactional(readOnly = true)
public MaterialDetail detail(UUID id) {
    Material m = repository.findDiscoveryDetail(id).orElseThrow();
    // ↑ 엔티티 그래프로 company 와 substanceLinks 를 함께 읽어 둬야 한다
    return MaterialDetail.from(m);   // ← 변환도 이 트랜잭션 안에서
}
```

**왜 트랜잭션 안이어야 하나** — 변환 과정이 **연관을 건드리기** 때문이다. `m.getCompany().getCompanyName()`은 프록시 초기화이고, **컨텍스트가 살아 있어야** 한다. OSIV를 껐으면 컨텍스트는 트랜잭션과 함께 끝난다.

**변환을 컨트롤러로 미루면 OSIV 없이는 예외가 난다.**

**두 가지가 함께 규칙이 된다**:

1. **필요한 연관을 조회 시점에 명시적으로 페치한다** — 엔티티 그래프나 페치 조인
2. **DTO 변환을 트랜잭션 안에서 끝낸다**

**이 제약이 오히려 이득이다**:

> **"엔티티는 서비스 밖으로 나가지 않는다"는 경계를 코드로 강제해 준다.**

**규율을 사람의 주의력이 아니라 구조에 맡기는 것** — [[01-n-plus-one-when-it-happens]]의 쿼리 카운트 검증, `ModuleStructureTest`와 같은 성격이다.

**§6의 배포 전 확인**: **끄기 전에 DTO 변환 경계를 먼저 확인한다.** 엔티티를 그대로 반환하는 컨트롤러가 있으면 **끄는 순간 예외가 난다.** 그 예외가 고쳐야 할 지점을 알려 주지만 **배포 전에 확인해야 한다.**

**§2.4의 현재 상태**: 지금은 깨질 것이 **거의 없다** — 연관관계 매핑이 `Material.company` 하나뿐이고 서비스가 DTO를 반환한다. **첫 슬라이스에서 성분 연결 컬렉션이 생기면** 위 규칙이 실제로 필요해진다.

## Q8. 켜 두기로 했더라도 명시적으로 적어야 하는 이유

> **기본값에 의존하지 말고 `true`라고 적고 이유를 남긴다. 그래야 다음 사람이 "검토한 결과"인지 "몰라서 그런 것"인지 구분할 수 있다.**

**설정 파일에 없는 값은 두 가지를 뜻할 수 있고, 파일만 봐서는 구별되지 않는다**:

```text
open-in-view 가 없다
  ├ "검토했고 기본값이 맞다고 판단했다"
  └ "이런 설정이 있는 줄 몰랐다"
       ↑ 파일만 봐서는 구별 불가
```

**적어 두면 구별된다**:

```yaml
jpa:
  # SPA 전용 백엔드라 서버 뷰가 없고, 응답은 항상 DTO 다.
  # 지연 로딩이 서비스 밖에서 일어나면 쿼리 카운트 검증이 무력해진다. (ADR-00XX)
  open-in-view: false
```

**Spring Boot의 시작 경고가 정확히 이걸 요구한다**(Q1) — 기본값인데 경고를 내보내는 이유가 **"의식적으로 고르라"**는 것이다.

**이 프로젝트의 다른 설정들과도 일관된다**(§2.3): **`application.yaml`의 다른 항목들이 전부 "왜 이 값인지"를 주석으로 달고 있다.** `ddl-auto: validate`도, `jdbc.time_zone: UTC`도 그렇다.

**"켜 두기로 했다면"이 중요하다** — §6의 마지막 항목대로 **템플릿 엔진을 쓰는 프로젝트라면 판단이 달라진다.** Thymeleaf 뷰에서 지연 로딩이 실제로 필요하다면 **OSIV의 값이 있다.** 그때는 **뷰가 연관을 몇 번 건드리는지가 곧 풀 사용량**이므로, **렌더링 중 쿼리 수를 따로 봐야 한다.**

**즉 이 노트의 결론은 "끄라"가 아니라 "고르고 적으라"다.** CosmoRoute에서는 그 답이 `false`일 뿐이다.
