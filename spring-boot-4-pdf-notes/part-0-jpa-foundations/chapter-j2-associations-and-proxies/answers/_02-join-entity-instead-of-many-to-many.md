## Q1. `@ManyToMany`의 가정과 그것이 깨지는 세 곳

**가정: 조인 테이블에는 외래 키 두 개만 있고, 그 둘의 복합키가 기본 키다.**

`material_substance`는 이 가정을 세 군데서 벗어난다.

**① 자체 식별자가 있다**

```sql
id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
```

`@ManyToMany`는 조인 테이블의 기본 키를 **두 외래 키의 복합키**로 본다. **별도 `id` 컬럼은 매핑 대상이 아니라서 JPA가 읽지도 쓰지도 관리하지도 않는다.** DB 기본값이 값을 채워 주긴 하지만, **애플리케이션은 그 행을 식별자로 지목할 수 없다.**

**② 대상이 두 종류다**

```sql
canonical_id   text REFERENCES substance (canonical_id),
provisional_id uuid REFERENCES provisional_substance (id),
```

**`inverseJoinColumns`에는 컬럼 하나만 적을 수 있다.** 그래서 위 매핑으로는 **정식 성분 연결만 표현되고 잠정 성분 연결은 존재하지 않는 것이 된다.**

**③ 테이블에 제약이 걸려 있다**

```sql
CONSTRAINT material_substance_one_target
    CHECK (num_nonnulls(canonical_id, provisional_id) = 1)
```

INV-9는 **"둘 중 정확히 하나"**를 요구한다. **`@ManyToMany`는 이 규칙을 알지 못하고, 알 방법도 없다.**

**②가 결정적이다.** 잠정 성분은 곁다리가 아니다 — 운영자가 아직 정식 성분에 매칭되지 않은 성분을 임시 등재하는 경로이고, **INV-10이 *"발견 원료와 공급 원료가 이 조인을 공유한다"*고 못 박은 대상**이다.

**셋의 성격 차이**: ①③은 **표현이 부족**한 것이지만, ②는 **도메인의 절반을 삼킨다.** ①③은 불편이고 ②는 데이터 손실이다.

> **이 매핑은 문법이 틀려서가 아니라, 표현할 수 있는 범위가 도메인보다 좁아서 쓸 수 없다.**

## Q2. 그대로 쓰면 사라지는 도메인

**잠정 성분 연결이 통째로 사라진다.**

```text
도메인이 요구하는 것
  material_substance ── canonical_id ──▶ substance            (정식 성분)
                     └─ provisional_id ─▶ provisional_substance (잠정 성분)

@ManyToMany 로 매핑하면
  material ══════════════▶ substance                          (정식만)
                                                              (잠정은 없는 것이 된다)
```

**그리고 이건 "일부 기능이 안 된다" 수준이 아니다**:

- **운영자의 등재 경로가 막힌다** — 아직 정식 성분에 매칭되지 않은 성분을 임시로 올릴 방법이 없다
- **INV-10이 깨진다** — *"발견 원료와 공급 원료가 이 조인을 공유한다"*는 전제가 성립하려면 두 대상 모두 표현돼야 한다
- **DB에는 데이터가 있는데 애플리케이션이 못 읽는다** — `provisional_id`가 채워진 행을 JPA가 로딩하면, `canonical_id`가 `null`이라 매핑이 어긋난다

**"매핑이 도메인의 절반을 삼켜 버린다."**

**함께 잃는 것**(①③에서):

| 잃는 것 | 나중에 무엇이 막히나 |
|---|---|
| 연결 행의 식별자 | "이 연결의 출처가 무엇인가"에 답할 수 없다 |
| `CHECK` 제약의 표현 | 자바 쪽에서 "정확히 하나"를 강제할 자리가 없다 |

**세 번째 항목은 곧 실제 요구가 된다** — 발견 카탈로그는 **출처와 확인일을 노출하는 것이 INV-13의 핵심**인데, 그 정보가 연결 단위로 필요해지면 **연결에 식별자가 있어야 한다.**

## Q3. 승격하면 매핑 종류가 어떻게 바뀌고 왜 이득인가

**다대다 하나가 다대일 두 개가 된다.**

```text
[다대다로 볼 때]        Material ═══════多대多═══════ Substance
                                  (조인 테이블은 숨은 배관)

[연결 엔티티로 볼 때]   Material ◀──多대一── MaterialSubstance ──多대一──▶ Substance
                                             (이제 이름과 정체성을 가진 개념)
```

**왜 이득인가 — 특수 규칙이 사라지고 일반 규칙 하나만 남는다.**

**`@ManyToMany`는 자기만의 규칙 세트를 갖는다**: 조인 테이블의 기본 키 가정, `joinColumns`/`inverseJoinColumns`, 컬렉션에서 원소를 뺄 때의 삭제 동작, 부가 속성 불가. **전부 다대다에서만 통하는 이야기다.**

**승격하면 그게 전부 없어지고**, [[01-association-owner-and-mappedby]]의 **주인 규칙 하나**로 설명된다:

```java
@Entity
@Table(name = "material_substance")
public class MaterialSubstance {
    @Id
    private UUID id;                       // ② 자체 식별자를 JPA 가 알게 된다

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "material_id", nullable = false)   // ③ 외래 키를 가진 이쪽이 주인
    private Material material;
}
```

**다섯 가지 결정과 각각의 이유**:

1. **`@Entity`** — 이 테이블의 행 하나를 애플리케이션이 **지목하고 다룰 수 있어야** 하니까
2. **`id` 매핑** — 조인 테이블에 **이미 있는** 자체 식별자를 JPA가 알게 해야 하니까
3. **`material_id`를 `@ManyToOne`** — 주인 규칙 그대로. 외래 키를 가진 이쪽이 주인
4. **`fetch = LAZY` 명시** — `@ManyToOne`의 기본값이 **즉시 로딩**이라, 연결 하나를 읽을 때마다 원료를 통째로 끌고 온다([[04-proxies-and-lazy-loading]])
5. **`optional = false`** — DDL의 `NOT NULL`과 일치해야 `ddl-auto: validate`를 통과하고, Hibernate가 **조인 종류를 최적화**할 수 있다

**추가 이득**: 부가 속성을 **필드 하나 추가**로 붙일 수 있고, 행을 **식별자로 지목**할 수 있고, 삭제가 **그 행 하나만** 지운다.

## Q4. 원료 쪽 컬렉션이 이번에는 정당한 이유 둘

**앞 노트의 원칙은 "단방향으로 되면 단방향이 낫다"였다. 이번엔 반대편을 둘 이유가 두 개 있다.**

```java
// Material.java
@OneToMany(mappedBy = "material", cascade = CascadeType.ALL, orphanRemoval = true)
private List<MaterialSubstance> substanceLinks = new ArrayList<>();
```

**① 생명주기가 종속적이다**

**연결 행은 원료 없이 존재할 이유가 없다.** 원료가 지워지면 연결도 지워져야 하고, **실제로 DDL에 `ON DELETE CASCADE`가 이미 걸려 있다.** 이 관계를 매핑에 반영하려면 **부모 쪽 컬렉션이 필요하다** — 전이와 고아 제거는 컬렉션에만 걸 수 있다([[05-cascade-orphan-removal-vs-db-cascade]]).

**② 불변식이 컬렉션 전체를 봐야 성립한다**

"같은 원료에 같은 성분을 두 번 연결하지 않는다"는 **부분 유니크 인덱스로 DB가 막고 있지만**, 그 전에 **읽을 수 있는 오류로 걸러 내려면** 엔티티 안에서 기존 목록을 확인해야 한다.

```java
// Material.java
void link(MaterialSubstance link) {
    if (this.substanceLinks.stream().anyMatch(link::sameTarget)) {
        throw new CuratedCatalogRuleViolation("이미 연결된 성분");
    }
    this.substanceLinks.add(link);
    link.setMaterial(this);   // 외래 키를 만드는 줄
}
```

**CosmoRoute가 INV-8을 사전 검사와 DB 제약으로 이중 강제한 것과 같은 방식이다.**

**②가 특히 중요한 이유** — 컬렉션이 있으면 **도메인 규칙이 엔티티 안에 들어온다.** `Material.publish()`가 INV-13의 게이트인 것과 같은 패턴이다.

> **규칙이 서비스가 아니라 엔티티 안에 있다.**

**앞 노트의 원칙과 모순이 아니다** — 그 원칙은 *"탐색이 실제로 필요할 때만 추가한다"*였다. 여기서는 **탐색이 아니라 생명주기와 불변식**이라는 더 강한 이유가 있다. `Company.materials`에는 그 이유가 없었다.

## Q5. "부가 속성이 생기면 승격"이 아니라 "처음부터 승격"인 이유

**나중에 바꾸면 타입이 바뀌고, 타입이 바뀌면 그 컬렉션을 쓰던 코드가 전부 따라 바뀌기 때문이다.**

```text
[처음부터 연결 엔티티]
  나중에 함량이 필요해짐
    → MaterialSubstance 에 필드 하나 추가
    → 기존 코드는 그대로

[나중에 승격]
  나중에 함량이 필요해짐
    → List<Substance> → List<MaterialSubstance>
    → 이 컬렉션을 쓰던 코드가 전부 컴파일 오류
    → for 루프, stream, DTO 변환, 테스트 …
    → 게다가 삭제 동작도 함께 바뀐다
```

**"속성이 붙는 순간 파괴적이다."** 매핑 한 줄만 바뀌는 게 아니라 **컬렉션 원소 타입이 바뀌므로 사용처가 전부 바뀐다.**

**승격을 미루는 것이 비용을 미루는 게 아니라 키운다** — 코드가 그 컬렉션을 더 많이 쓸수록 전환 비용이 커진다. 그리고 **부가 속성이 필요해지는 시점은 대개 그 코드가 이미 많이 쌓인 뒤**다.

**비유와 그 한계 — 수강신청**: 학생과 과목은 다대다로 보이지만, 실제 도메인에는 **"수강"이라는 개념이 따로 있다.** 거기에 수강일·성적·재수강 여부가 붙는다. 학생과 과목 사이의 **선이 아니라 그 사이에 놓인 사물**이다.

→ **깨지는 지점**: **수강은 처음부터 이름이 있고 누구나 개념으로 인정한다.** `material_substance`는 그렇지 않다 — 처음에는 "그냥 연결"로 보이고, 함량·표시 순서·출처가 **나중에** 붙는다. **언제 승격해야 하는지가 미리 보이지 않는다.**

**그래서 규칙이 "판단"이 아니라 "기본값"이 된다** — 판단할 정보가 그 시점에 없으니, **판단하지 않아도 되는 쪽을 기본으로 삼는다.**

**함께 피하는 것**: `@ManyToMany`는 **삭제 동작도 직관과 다르다** — 컬렉션에서 하나를 빼면 Hibernate가 **조인 행 전체를 지우고 남은 것을 다시 넣는** 경우가 있다. 연결 엔티티면 **그 행 하나만** 지운다.

**단, `@ManyToMany`가 항상 틀린 것은 아니다**(§6) — 조인 테이블이 정말 두 외래 키뿐이고 **앞으로도 그럴 것이 확실한** 관계(사용자-권한 등)라면 쓸 수 있다. **다만 "앞으로도 그럴 것"에 대한 확신이 대개 틀린다는 것이 이 절의 요지다.**

## Q6. 연결 엔티티와 임베디드 타입을 가르는 기준

**자체 식별자가 있는가.**

| | **임베디드 타입** | **연결 엔티티** |
|---|---|---|
| **자체 식별자** | **없다** | **있다** |
| 정체성 | 소유 엔티티의 **일부** | **독립적으로 지목**된다 |
| 지목 방법 | 소유자를 통해서만 | **식별자로 직접** |
| 생명주기 | 소유자에 완전히 종속 | 종속시킬 수도, 아닐 수도 |

**`material_substance`에 `id`가 있다는 사실 자체가 이미 답을 정해 준다.**

**왜 식별자 유무가 결정적인가** — 식별자는 **"이것을 나중에 다시 가리킬 수 있는가"**를 뜻한다. 가리킬 수 있으면 그것은 **독립된 사물**이고, 못 가리키면 **다른 것의 속성**이다.

```text
"이 연결의 출처가 무엇인가?"
  → 연결을 가리킬 수 있어야 답할 수 있다
  → 가리키려면 식별자가 필요하다
  → 그러므로 엔티티다
```

**CosmoRoute에서는 이 질문이 곧 실제 요구가 된다** — 발견 카탈로그가 출처와 확인일을 노출하는 것이 INV-13의 핵심이고, 그 정보가 **연결 단위**로 필요해진다.

**덤 — 복합키 대신 대리키를 쓰는 이득**(§5): 식별자를 `(material_id, canonical_id)` 복합키로 잡을 수도 있다. 그러면 **`@IdClass`나 `@EmbeddedId`가 필요하고 코드가 늘어난다.** CosmoRoute는 **별도 `id` 대리키를 이미 갖고 있으므로 그 고민이 없다** — **스키마가 이미 더 단순한 쪽을 골라 뒀다.**

**판별을 흐리는 관찰**(§5): **"둘 다 여러 개를 가진다"는 관찰만으로 다대다로 결론 내리지 않는다.** **연결 자체에 의미가 있는지**를 물어야 한다.

## Q7. 승격이 스키마 변경을 요구하지 않는 이유

**테이블은 그대로다. 바뀌는 것은 그 테이블을 자바에서 어떻게 보느냐뿐이다.**

```text
DB 쪽
  material_substance ( id, material_id, canonical_id, provisional_id )
  ↑ 승격 전후로 한 글자도 안 바뀐다

자바 쪽
  [전] Material.substances : List<Substance>       ← 조인 테이블을 숨은 배관으로 본다
  [후] MaterialSubstance @Entity                   ← 같은 테이블을 엔티티로 본다
       Material.substanceLinks : List<MaterialSubstance>
```

**`@ManyToMany`도 연결 엔티티도 같은 테이블을 읽는다.** 차이는 **JPA가 그 테이블의 컬럼을 어디까지 매핑하느냐**다:

| | 매핑하는 컬럼 |
|---|---|
| `@ManyToMany` | `material_id`, `canonical_id` (둘뿐) |
| 연결 엔티티 | **`id`, `material_id`, `canonical_id`, `provisional_id` 전부** |

**승격은 "이미 있는 컬럼을 마저 매핑하는 것"이다.** 새 컬럼을 요구하지 않는다.

**CosmoRoute에서는 마이그레이션 없이 매핑만 추가하면 된다** — 스키마가 **처음부터 연결 엔티티에 맞게** 설계돼 있다. `id`도 `CHECK` 제약도 이미 있다.

**이것이 [[01-association-owner-and-mappedby]] Q8과 같은 종류의 사실이다** — 양방향도, 승격도 **객체 쪽 이야기**이고 DDL을 건드리지 않는다.

**그래서 역방향 진단도 같다**: 승격하는데 마이그레이션이 필요하다고 느낀다면, 그건 승격 자체가 아니라 **원래 스키마가 순수 조인 테이블이었다**는 뜻이다 — 그때는 `id` 컬럼을 추가하는 별도의 결정이 필요하고, 그건 승격의 비용이 아니라 **미리 승격하지 않은 비용**이다(Q5).

## 재출제 문항

1. `@ManyToMany`로 매핑했더니 `provisional_id`가 채워진 행이 이상하게 로딩된다. 왜인가?
2. 조인 테이블에 `id` 컬럼이 있다. 이 사실 하나에서 무엇이 결정되는가?
