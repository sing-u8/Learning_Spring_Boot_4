## Q1. 표준 JPA가 이 형태를 표현하지 못하는 이유 — "연관의 전제"

**JPA의 연관은 "이 필드는 정해진 한 타입의 엔티티를 가리킨다"를 전제한다.**

```java
@ManyToOne
private 성분무언가 substance;   // Substance 이거나 ProvisionalSubstance
                              // ← 이런 타입을 쓸 자리가 없다
```

**다형성은 지원한다. 단 상속 계층 안에서만이다.**

```text
[JPA 가 아는 다형성]              [material_substance 가 요구하는 것]

        Payment                    Substance      ProvisionalSubstance
        ╱     ╲                    (text PK)      (uuid PK)
 CardPayment  CashPayment                ╲          ╱
                                          공통 조상이 없다
 @ManyToOne Payment 로 충분          @ManyToOne ??? 로 쓸 타입이 없다
```

**전제를 정확히 말하면**: `@ManyToOne`은 **대상 테이블이 하나**여야 한다. 그래야 외래 키 컬럼 하나가 그 테이블을 가리킨다고 선언할 수 있다. **대상이 두 테이블이면 그 선언 자체가 성립하지 않는다.**

**"애노테이션을 못 찾는 게 아니라, JPA의 연관 모델이 애초에 이걸 전제하지 않는다."**

**이 형태의 이름이 **배타적 연관**이다** — 하나의 연관이 **서로 상속 관계가 아닌** 둘 이상의 타입 중 **정확히 하나**를 가리키는 형태.

**두 조건이 모두 필요하다**(§5): 상속 관계가 아니어야 하고, **"정확히 하나"라는 제약이 있어야** 한다. 제약이 없으면 그냥 **선택적 연관 두 개**이고, 둘 다 채우는 것도 정상이다. **`material_substance`에 `CHECK (num_nonnulls(...) = 1)`이 있다는 사실이 이것을 배타적 연관으로 만든다.**

## Q2. `Substance`와 `ProvisionalSubstance`를 상속으로 묶으면 안 되는 이유 셋

**① 식별자 타입부터 다르다**

```sql
canonical_id   text REFERENCES substance (canonical_id)
provisional_id uuid REFERENCES provisional_substance (id)
```

`text`와 `uuid`다. **공통 상위 엔티티는 `@Id`의 타입을 하나로 정해야 한다.** 어느 쪽을 골라도 다른 쪽이 어긋난다.

**② 소유 주체가 다르다**

정식 성분은 ADR-0001에 따라 **수집 시스템이 소유하고 앱은 저작하지 않는 투영**이다. 잠정 성분은 **운영자가 앱 안에서 만든다.** 하나는 읽기 전용 투영, 하나는 앱의 저작물이다.

**③ 생명주기가 다르다**

정식 성분은 **feed가 갱신**하고, 잠정 성분은 **승인되면 정식 성분으로 대체된다.** 하나는 외부 주기를 따르고, 하나는 종료 조건이 있다.

**억지로 묶으면 이 차이가 전부 뭉개진다** — 상위 타입에 "누가 소유하는가"·"어떻게 갱신되는가"를 표현할 자리가 없고, 하위에서 오버라이드할 수도 없다(그건 데이터가 아니라 정책이다).

> **상속이 없는 것이 설계 실수가 아니라 도메인의 사실이다.**

**§6의 경고와 같다**: **공통 상위 엔티티를 억지로 만들지 않는다.** 식별자 타입·소유 주체·생명주기가 다른 두 테이블을 상속으로 묶으면 **그 차이를 표현할 곳이 사라진다.**

**판별 질문**: *"이 둘이 정말 is-a 관계인가?"* 잠정 성분은 **성분의 한 종류**가 아니라 **아직 성분이 아닌 것**이다. 승인되면 정식 성분으로 **대체된다** — 상속이라면 대체될 이유가 없다.

## Q3. `@Any`가 외래 키 제약을 걸 수 **없는** 구조적 이유

**컬럼 하나가 상황에 따라 다른 테이블을 가리키므로, 그 컬럼에 외래 키 제약을 걸 대상 테이블을 하나로 정할 수 없다.**

```text
payment_id 컬럼의 값 42
  payment_type = 'CASH'   → cash_payment 테이블의 42
  payment_type = 'CREDIT' → credit_card_payment 테이블의 42

외래 키 제약은 "이 컬럼은 저 테이블의 PK 를 참조한다"를 선언한다
  → 저 테이블이 두 개다
  → 선언할 수 없다
```

**공식 문서의 표현**:

> *"복합 외래 키(외래 키 + 판별자)는 **개념적일 뿐이며 물리적 데이터베이스 제약으로 강제할 수 없다.** … `@Any` 매핑은 기능은 하지만 참조 무결성을 데이터베이스 수준에서 강제하기 어렵기 때문에 **일반적으로 선호되지 않는다.**"*

**"안 거는 것"과의 차이가 결정적이다**:

| | 안 거는 것 | **걸 수 없는 것** |
|---|---|---|
| 성격 | **선택** | **구조적 불가능** |
| 나중에 | 마이그레이션으로 **추가할 수 있다** | **영원히 못 건다** |
| 대안 | 지금은 미루고 나중에 | **없다** — 매핑을 바꾸는 수밖에 |

**"안 걸었다"면 부채이고, "걸 수 없다"면 그 데이터에 대한 DB의 보증이 **영구히** 없어진다.** 잘못된 `payment_id`가 들어가도 DB는 막지 않고, 나중에 검사할 기회도 없다.

**비유와 그 한계 — 배송 수취인 칸**: 수취인이 개인 회원일 수도 사업자일 수도 있는데 각각 다른 명부에 있다. **칸을 두 개 두고 하나만 채우게 하거나(A), 칸 하나에 "종류" 라벨을 붙이거나(B).**

→ **깨지는 지점**: 종이 양식은 사람이 **나중에** 명부와 대조할 수 있다. **DB의 외래 키 제약은 행이 들어오는 그 순간에만 작동하고, 나중에 검사할 기회가 없다.** 그래서 B를 고르면 **대조 능력을 영구히 잃는다.** 종이에서는 사소한 차이가 DB에서는 결정적인 이유다.

## Q4. 세 선택지 비교 — 물리 외래 키 · 객체 탐색 · 자바 쪽 강제

| 축 | **A — `@ManyToOne` 둘** | **B — `@Any`** | **C — 식별자만** |
|---|---|---|---|
| **물리 외래 키** | **두 개 유지** | **걸 수 없다** | **두 개 유지** |
| INV-9 CHECK | 그대로 작동 | 그대로 작동 | 그대로 작동 |
| `ddl-auto: validate` | 매핑과 스키마 대조됨 | 판별 컬럼이 없어 **마이그레이션 필요** | 대조됨 |
| **객체 그래프 탐색** | **가능** | **가능** | **불가능** |
| **자바 쪽 "둘 중 하나" 강제** | 도메인 메서드로 | **타입으로** | 도메인 메서드로 |
| 필드 수 | 2 | **1** | 2 |

**세 축이 각각 무엇을 뜻하는가**:

- **물리 외래 키** = **DB가 지켜 주는가.** 잘못된 참조를 넣는 순간 막히는가.
- **객체 탐색** = `link.getCanonical().getInciName()`이 되는가. 안 되면 조회가 **매번 두 단계**다.
- **자바 쪽 강제** = 잘못된 조합을 **컴파일러나 타입 시스템이** 막는가, 아니면 **런타임 규약**에 맡기는가.

**각 선택지가 정확히 하나씩 포기한다**:

```text
A: 자바 쪽 타입 강제를 포기   → 도메인 메서드로 갚는다 (Q6)
B: 물리 외래 키를 포기        → 갚을 방법이 없다 (Q3)
C: 객체 탐색을 포기           → 조회 코드가 매번 두 단계
```

**A와 C는 잃은 것을 코드로 메울 수 있고, B는 못 메운다.** 그게 셋을 가르는 선이다.

## Q5. CosmoRoute가 A를 고르는 근거 — 기존 결정과의 연결

**B가 자바 쪽에서 가장 우아하지만, 이 저장소에서는 고를 수 없는 선택지다.**

**① 설계 원칙과 정면으로 어긋난다**

이 저장소의 원칙은 *"도메인 불변식을 부분 유니크·CHECK로 **DB가 강제**한다"*이다. **외래 키를 포기하는 매핑은 그 원칙과 정면으로 어긋난다.**

**② 테스트 전략의 근거가 사라진다**

테스트가 **H2 대신 실 PostgreSQL**을 쓰는 이유가 *"불변식 상당수가 DB 제약으로 강제되므로 H2로는 통과해도 의미가 없다"*였다. **그 제약을 스스로 없애면 그 결정의 근거도 함께 사라진다.**

**③ 마이그레이션의 성격이 나쁘다**

`@Any`를 쓰려면 **판별 컬럼을 추가하는 마이그레이션**이 필요하다. 즉 **스키마를 바꿔서 제약을 약하게 만드는** 변경이다. **ADR을 쓸 만한 사안이면서 동시에 쓰기 어려운 사안**이다 — "무결성을 포기하기 위해 스키마를 고칩니다"라고 적어야 한다.

**세 근거가 같은 방향을 가리킨다** — ①은 원칙, ②는 그 원칙에서 파생된 **테스트 인프라 결정**, ③은 그 변경을 **문서화할 때 드러나는 자기모순**이다. ②가 특히 강한 근거인 이유는, **이미 비용을 치른 결정**(느린 실 DB 테스트)이 무의미해지기 때문이다.

**C를 안 고르는 이유**: **성분 이름을 보여 주는 것이 발견 카탈로그의 핵심 기능**이므로, C는 **조회 코드를 매번 두 단계로** 만든다.

> **그래서 A가 답이다. 자바 쪽 우아함을 조금 포기하고, DB가 지키는 것을 그대로 지킨다.**

**§6의 마무리**: **선택지가 셋이라는 사실 자체를 기록해 둔다.** 이 결정은 **ADR 감**이다 — 나중에 *"왜 필드를 두 개나 뒀는가"*를 묻는 사람에게 답이 남아야 한다.

## Q6. A의 대가를 정적 팩터리가 갚는 방식

**A가 포기한 것은 "자바 쪽에서 둘 중 하나가 타입으로 강제되지 않는다"였다. 정적 팩터리는 잘못된 상태를 만들 경로 자체를 없앤다.**

```java
private MaterialSubstance() {}   // JPA 용. 밖에서 못 부른다

static MaterialSubstance toCanonical(Material material, Substance canonical) {
    MaterialSubstance link = new MaterialSubstance();
    link.id = UUID.randomUUID();
    link.material = material;
    link.canonical = canonical;      // provisional 은 null 로 남는다
    return link;
}

static MaterialSubstance toProvisional(Material material, ProvisionalSubstance provisional) {
    ...
}
```

**핵심은 "막는다"가 아니라 "만들 방법이 없다"이다**:

| 접근 | 잘못된 상태를 |
|---|---|
| 검증 메서드 (`validate()`) | **만든 뒤에** 잡는다 — 부르는 걸 잊으면 통과 |
| **private 생성자 + 정적 팩터리** | **만들 수가 없다** — 두 필드를 함께 채울 진입점이 없다 |

**두 팩터리가 각각 정확히 한 필드만 채운다.** 밖에서는 이 둘 중 하나로만 객체를 얻으므로, **"둘 다 채워진" 또는 "둘 다 빈" 인스턴스가 존재할 수 없다.**

**그래서 DB의 CHECK는 마지막 방어선이 된다** — 평소에는 **팩터리가 규칙을 지키고**, CHECK는 JPA를 거치지 않는 경로나 미래의 실수를 위한 그물이다.

**CosmoRoute가 INV-8을 사전 검사와 부분 유니크 인덱스로 이중 강제한 것과 같은 구조다** — 읽을 수 있는 오류는 애플리케이션이, 최종 보증은 DB가.

**§6의 짝 규칙**: **두 필드를 public setter로 열지 않는다.** 잘못된 조합을 만들 수 있는 경로를 남기면 **CHECK 위반이 런타임에야 드러난다** — 그때는 이미 어느 코드가 그랬는지 찾기 어렵다.

## Q7. 읽는 쪽 분기를 엔티티 안에 가두지 않으면

**같은 분기가 호출부마다 복제되고, 그중 하나는 반드시 빠진다.**

```java
// 흘리면 이렇게 된다 — 서비스 여기저기에
if (link.getCanonical() != null) {
    name = link.getCanonical().getInciName();
} else {
    name = link.getProvisional().getRawName();
}
```

**무엇이 문제인가**:

1. **빠뜨린 곳이 `NullPointerException`을 낸다** — `else`를 안 쓰고 `getCanonical()`만 부른 코드는 잠정 성분 연결에서 터진다
2. **터지는 곳이 데이터에 달렸다** — 정식 성분만 있는 환경에서는 **테스트가 통과한다.** 운영에 잠정 성분이 하나 들어오는 순간 터진다
3. **규칙이 바뀌면 전부 고쳐야 한다** — 표시 이름 규칙이 바뀌면 복제된 만큼 수정한다

**가두면**:

```java
// MaterialSubstance 안에
boolean isCanonical() { return this.canonical != null; }

String displayName() {
    return this.canonical != null
            ? this.canonical.getInciName()
            : this.provisional.getRawName();
}
```

**호출부는 `link.displayName()`만 부른다. 분기가 엔티티 안에 한 번만 존재한다.**

**이것이 A의 대가를 실제로 갚는 방식이다** — Q6의 팩터리가 **쓰는 쪽**을 막았다면, 이건 **읽는 쪽**을 막는다. 둘이 짝이다:

```text
쓰기: 정적 팩터리    → 잘못된 상태를 만들 수 없다
읽기: displayName()  → 어느 쪽이 채워졌는지 호출부가 알 필요가 없다
      ─────────────────────────────────────────────
      밖에서는 "둘 중 하나"라는 사실이 아예 안 보인다
```

**`Material.publish()`가 INV-13을 안에 가둔 것과 같은 패턴이다** — **규칙이 서비스가 아니라 엔티티 안에 있다.**

## Q8. `@Any`와 상속 다형성에서 판별자가 저장되는 위치

**정반대다.**

| 축 | **`@Any`** | **`@Inheritance` 다형성** |
|---|---|---|
| 대상 타입 관계 | 상속 관계 **없음** | 공통 상위 타입을 상속 |
| **판별자 위치** | **참조하는 쪽**에 저장 | **참조되는 쪽** 테이블에 저장 |
| 외래 키 제약 | **걸 수 없다** | **걸 수 있다** |
| 쓸 상황 | 식별자 타입만 공유하는 무관한 엔티티들 | **진짜 is-a 관계** |

```text
[상속 다형성]                        [@Any]

 payment 테이블                       order 테이블
 ┌────┬──────────┐                   ┌────┬────────────┬──────────────┐
 │ id │ dtype    │ ← 자기 종류를     │ id │ payment_id │ payment_type │
 ├────┼──────────┤    자기가 적는다  └────┴────────────┴──────┬───────┘
 │ 1  │ CASH     │                                            │
 │ 2  │ CREDIT   │                          상대의 종류를 ────┘
 └────┴──────────┘                          내가 적는다

 order.payment_id → payment.id            cash_payment / credit_card_payment
 대상 테이블이 하나 → FK 가능              대상 테이블이 둘 → FK 불가능
```

**"판별자가 어느 쪽 테이블에 있느냐"가 결정적 차이다.**

**그리고 이 위치 차이가 곧 외래 키 가능 여부를 결정한다**:

- **상속 다형성**: 대상이 **한 테이블**(`payment`)이다. 그 안에서 `dtype`으로 갈릴 뿐이다. → **외래 키를 걸 대상이 하나이므로 걸 수 있다.**
- **`@Any`**: 판별자가 **참조하는 쪽**에 있다는 건, 대상 테이블이 **행마다 다르다**는 뜻이다. → **Q3의 구조적 불가능**이 여기서 나온다.

**그래서 판별자 위치는 우연한 구현 차이가 아니라, 두 방식의 능력 차이를 만드는 원인이다.**

**정리 — "JPA가 지원하지 않는다"와 "매핑할 수 없다"는 다르다**(§5):

> 표준 JPA에 전용 애노테이션이 없다는 것과, 이 스키마를 매핑할 수 없다는 것은 다르다. **A와 C 모두 표준 JPA만으로 완전히 매핑된다.** 없는 것은 **"둘 중 하나"를 타입 수준에서 표현하는 문법**뿐이고, **그건 도메인 메서드가 대신한다.**
