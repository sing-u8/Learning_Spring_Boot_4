## Q1. 두 장치가 작동하는 층과 그 차이

**JPA 전이는 애플리케이션 층(영속성 컨텍스트), DB 연쇄 삭제는 DB 층(외래 키 제약)에서 작동한다.**

```text
[JPA cascade = REMOVE]
  em.remove(material)
    → 컨텍스트가 컬렉션을 순회하며 각 연결에도 remove 를 전파
    → 플러시 시점에
         DELETE FROM material_substance WHERE id = ?   × 연결 수만큼
         DELETE FROM material WHERE id = ?
    → 애플리케이션이 삭제를 "알고" 있다

[DB ON DELETE CASCADE]
  DELETE FROM material WHERE id = ?
    → DB 가 자식 행을 알아서 지운다
    → SQL 한 번
    → 애플리케이션은 무슨 일이 일어났는지 모른다
```

**결과는 같아 보이지만 대가가 정반대다.**

| 축 | **JPA 전이** | **DB 연쇄 삭제** |
|---|---|---|
| **적용 경로** | **컨텍스트를 통과하는 연산만** | **모든 경로** |
| SQL 수 | **자식 수만큼 + 1** | **1** |
| 컨텍스트 인지 | **안다** | **모른다** |
| 컬렉션 초기화 | **일어난다** | 일어나지 않는다 |
| 벌크 삭제에서 | **적용 안 됨** | **적용됨** |

**각각만 믿으면 생기는 문제**:

- **JPA 쪽만**: 성분 40개짜리 원료를 지우면 **DELETE가 41번**이다. 게다가 컬렉션을 순회해야 하므로 **지연 로딩된 컬렉션이 초기화된다** — 읽지 않으려던 것을 읽는다.
- **DB 쪽만**: SQL은 한 번이지만 **컨텍스트가 이 삭제를 모른다.** 이미 로딩해 둔 연결 엔티티들이 **DB에는 없는데 컨텍스트에는 살아 있는** 상태가 되고, 건드리면 존재하지 않는 행에 UPDATE가 나갈 수 있다.
- **둘 다**: JPA가 먼저 자식을 하나씩 지우고 부모를 지운다. DB의 CASCADE는 **지울 자식이 이미 없어 아무 일도 하지 않는다.** 결과는 맞지만 **DB 규칙이 사실상 죽은 코드**가 되고 DELETE는 여전히 N번이다.

**비유와 그 한계 — 건물 철거와 집기**: "건물을 철거하면 집기도 처분한다"를 **계약서에 적을 수도**(JPA) 있고, **철거 업체가 알아서 밀어버리게** 둘 수도(DB) 있다.

→ **깨지는 지점**: 철거 업체가 밀어버려도 건물은 사라진 채로 끝이다. DB가 밀어버리면 **관리 대장(영속성 컨텍스트)에는 집기가 그대로 남는다.** 물리 세계에서는 "장부를 나중에 고치면 되는" 문제가, 여기서는 **그 트랜잭션이 끝날 때까지 계속 틀린 답을 주는** 문제다.

## Q2. JPQL 벌크 삭제에서 전이가 일어나지 않는 이유

**전이는 컨텍스트를 통과하는 연산에만 걸리는데, 벌크 삭제는 컨텍스트를 우회해 DB로 직행하기 때문이다.**

**전이의 5단계 중 1단계가 전제다**:

1. **`em.remove(parent)`를 부른다** — **컨텍스트가 이 연산을 알아야** 전파 대상을 찾을 수 있다
2. `cascade`에 `REMOVE`가 있는 연관을 찾는다
3. **컬렉션을 초기화한다** — 무엇을 지울지 알려면 목록을 실제로 읽어야 한다
4. 각 자식에도 삭제를 예약한다
5. 플러시 때 **자식 DELETE 먼저, 부모 DELETE 나중** — 외래 키 제약을 만족시키려면 참조하는 쪽이 먼저 사라져야 한다

```java
@Modifying
@Query("DELETE FROM Material m WHERE m.hiddenAt IS NOT NULL")
int purgeHidden();
```

**이 쿼리는 1번을 거치지 않는다.** 컨텍스트를 통과하지 않고 DB로 직행하므로 **전이가 전혀 일어나지 않는다.**

**그때 자식을 정리하는 것은 DDL의 `ON DELETE CASCADE`뿐이다.** DB 제약이 없었다면 **외래 키 위반으로 터졌을 것이다.**

**여기서 결론 하나가 나온다**:

> **DDL의 연쇄 삭제는 JPA 전이의 중복이 아니라, JPA를 우회하는 경로를 위한 안전망이다. 둘은 같은 층에 있지 않다.**

**§6의 규칙이 여기서 나온다**: **DDL 연쇄 삭제를 JPA 전이의 중복으로 보고 지우지 않는다.** 벌크 삭제와 **운영 중 직접 실행하는 SQL**이 그 규칙에 의지한다.

## Q3. `cascade = REMOVE`와 `orphanRemoval`의 발동 조건

**한 문장씩**:

- **`cascade = REMOVE`** — **부모가 삭제될 때** 자식에게도 삭제를 전파한다.
- **`orphanRemoval = true`** — **부모의 컬렉션에서 자식이 빠질 때** 그 자식을 삭제한다.

| 축 | `cascade = REMOVE` | `orphanRemoval = true` |
|---|---|---|
| **발동 시점** | 부모가 삭제될 때 | **컬렉션에서 자식이 빠질 때** |
| **부모의 상태** | 삭제된다 | **살아 있다** |
| 전형적 코드 | `em.remove(material)` | `material.getLinks().remove(link)` |
| 의미 | "부모가 사라지면 자식도 의미 없다" | **"부모에 속하지 않는 자식은 존재할 수 없다"** |

**판별 질문 하나**(§5):

> **"부모는 살아 있는가?"**
> 살아 있는데 자식이 사라져야 하면 **`orphanRemoval`**, 부모가 사라져서 자식도 사라지면 **`REMOVE`**.

**포함 관계는 한 방향이다**: `orphanRemoval = true`를 켜면 **`REMOVE` 전이도 함께 적용된다.** 반대는 성립하지 않는다.

**CosmoRoute에서 실제로 자주 일어나는 것은 후자다** — 운영자가 원료의 성분 목록에서 하나를 잘못 넣었다고 판단해 뺀다. **원료는 그대로 있고 연결만 사라져야 한다.**

```java
// Material.java
void unlink(UUID linkId) {
    this.substanceLinks.removeIf(l -> l.getId().equals(linkId));
    // orphanRemoval = true 이면 이것만으로 DELETE 가 나간다
}
```

## Q4. `orphanRemoval` 없이 컬렉션에서 자식을 빼면

**매핑 형태에 따라 두 가지로 갈린다.**

**① 양방향 `mappedBy` 컬렉션 (CosmoRoute의 경우) — 아무 일도 일어나지 않는다**

```java
material.getSubstanceLinks().remove(link);   // 아무 SQL 도 안 나간다
```

**이유는 [[01-association-owner-and-mappedby]] 2.1 그대로다** — 이 컬렉션은 `mappedBy`가 붙은 반대편이라 **외래 키 판정에서 제외된다.** 플러시가 아예 보지 않는다.

**결과**: **화면에서는 사라졌는데 데이터는 남아 있는** 상태가 된다. 다음 요청에서 다시 조회하면 **되살아난다.**

**② 단방향 `@OneToMany` + `@JoinColumn` — 다른 방식으로 실패한다**

그때는 **컬렉션이 주인**이라 외래 키를 갱신하려 한다:

```text
UPDATE material_substance SET material_id = NULL WHERE id = ?
  → material_id 는 NOT NULL 이다
  → 제약 위반 💥
```

**두 실패의 성격이 정반대다**:

| | 증상 | 언제 발견되나 |
|---|---|---|
| ① `mappedBy` | **조용히 무시** | 다음 조회에서 되살아날 때 — **한참 뒤** |
| ② `@JoinColumn` | **즉시 예외** | 그 자리에서 |

**①이 더 나쁘다.** 예외가 없으니 코드가 맞다고 믿게 되고, 테스트도 같은 트랜잭션 안에서는 통과한다(컬렉션에서는 실제로 빠져 있으니까).

**그래서 `orphanRemoval = true`가 필요하다** — 그것만이 "컬렉션에서 뺐다"를 "DELETE"로 번역한다.

## Q5. CosmoRoute에서 `cascade = REMOVE`가 거의 쓰이지 않는 이유

**원료를 하드 삭제하는 경로가 없기 때문이다.**

**이 저장소는 물리 삭제를 거의 하지 않는다** — `deleted_at`·`hidden_at`으로 **소프트 삭제**를 하고, 성분은 ADR-0001에 따라 *"출처가 삭제한 경우 앱은 **소프트 삭제만** 반영한다."*

**세 설정의 판단이 갈린다**:

| 설정 | 판단 | 근거 |
|---|---|---|
| **`orphanRemoval = true`** | **필요하다** | 성분 연결 해제는 **실제 운영 동작**이고, 연결 행은 소프트 삭제 대상이 아니다(연결에는 `deleted_at`이 없다). **물리적으로 지우는 것이 맞다** |
| **`cascade = PERSIST`** | **필요하다** | 원료와 연결을 **한 트랜잭션에서 함께 만든다.** 전이가 없으면 연결마다 `save()`를 따로 불러야 한다 |
| **`cascade = REMOVE`** | **거의 안 쓴다** | **원료를 하드 삭제하는 경로가 없다** |

```java
@OneToMany(mappedBy = "material",
           cascade = {CascadeType.PERSIST, CascadeType.MERGE},
           orphanRemoval = true)
private List<MaterialSubstance> substanceLinks = new ArrayList<>();
```

**`cascade = ALL`로 뭉뚱그리지 않는 이유**(§5): **`ALL`은 편해 보이지만 쓰지 않는 연산까지 켠다.** 특히 **`REMOVE`가 켜진 줄 모르고 부모를 지웠다가 자식이 함께 사라지는 사고**가 난다. **쓰는 것만 나열하는 편이 낫다.**

**§6의 더 근본적인 규칙**: **연관이 있다고 전이를 거는 것이 아니다.** 전이는 **"부분이 전체에 속한다"**는 관계에서만 맞다. **원료와 회사처럼 서로 독립적인 생명주기를 갖는 관계에 걸면, 원료를 지웠을 때 회사가 사라진다.**

## Q6. 성분 쪽 외래 키가 `RESTRICT`인 것과 ADR-0001

```sql
canonical_id   text REFERENCES substance (canonical_id) ON DELETE RESTRICT,
provisional_id uuid REFERENCES provisional_substance (id) ON DELETE RESTRICT,
```

**성분은 앱이 저작하지 않는 투영이므로, 연결이 남아 있는 성분을 앱이 지우는 일 자체가 없어야 한다.**

**ADR-0001의 내용**: 정식 성분은 **수집 시스템이 소유하고 앱은 저작하지 않는다.** 출처가 삭제하면 앱은 **소프트 삭제만** 반영한다.

**그래서 `RESTRICT`가 두 가지를 동시에 한다**:

1. **정책의 표현** — "앱은 성분을 지우지 않는다"를 DB 제약으로 못 박는다
2. **사고 방지** — 실수로 하드 삭제가 시도되면 **그 자리에서 막힌다.** 연결이 대량으로 사라지는 사고가 일어나지 않는다

**같은 테이블에서 방향이 갈린다**:

```text
material_id    → ON DELETE CASCADE   "원료가 사라지면 연결도 사라진다"
canonical_id   → ON DELETE RESTRICT  "연결이 있으면 성분을 못 지운다"
provisional_id → ON DELETE RESTRICT
```

**한쪽은 전파하고 한쪽은 막는다.** 원료는 **연결의 소유자**이고, 성분은 **연결이 참조하는 외부 사실**이기 때문이다.

> **`RESTRICT`는 전이의 반대편 — 전파하지 말고 막으라는 선언이다.**

**이것이 이 장 전체의 판단 기준을 보여 준다** — 삭제 규칙은 "편한 쪽"이 아니라 **"누가 그 데이터의 소유자인가"**에서 나온다. 소유하면 전파하고, 소유하지 않으면 막는다.

## Q7. `@OnDelete`가 아끼는 것과 잃는 것

```java
@OneToMany(mappedBy = "material")
@OnDelete(action = OnDeleteAction.CASCADE)
private List<MaterialSubstance> substanceLinks = new ArrayList<>();
```

**DB의 연쇄 삭제를 이미 걸어 뒀다면, 그 사실을 Hibernate에게 알려 개별 DELETE를 생략하게 한다.**

공식 문서는 이것을 *"외래 키를 이용해 자식 레코드를 제거하는 **DDL 수준 기능**"*으로 설명하고, 컬렉션에 붙이면 *"`@OneToMany` 컬렉션이 `CascadeType.ALL`을 쓰더라도 **외래 키 연쇄를 통해** 자식이 삭제되도록 보장한다"*고 적는다.

**아끼는 것**:

| | 없이 | `@OnDelete` |
|---|---|---|
| SQL 수 | **자식 수 + 1** (성분 40개면 41번) | **1번** |
| 컬렉션 초기화 | **일어난다** (무엇을 지울지 알아야 하니까) | **안 일어난다** |

**두 번째가 덜 알려져 있지만 중요하다** — [[04-proxies-and-lazy-loading]]에서 아껴 둔 쿼리가 **삭제 경로에서 되살아나는** 것을 막는다.

**잃는 것 — 영속성 컨텍스트가 그 삭제를 모른다.**

**Q1에서 본 낡은 엔티티 문제가 그대로 돌아온다**: 이미 로딩해 둔 연결 엔티티들이 **DB에는 없는데 컨텍스트에는 살아 있다.** 그 트랜잭션이 끝날 때까지 계속 틀린 답을 준다.

**판단**(§6): **`@OnDelete`는 부모 하드 삭제가 잦을 때만 검토한다.** **CosmoRoute처럼 부모 하드 삭제가 없는 곳에서는 도입할 이유가 없다** — 아낄 것이 발생하지 않는 경로에 대가만 지불하게 된다.

## Q8. 전이가 지연 로딩을 무력화하는 지점

**3번 단계다.**

```text
1. em.remove(parent) 를 부른다
2. cascade 에 REMOVE 가 있는 연관을 찾는다
3. 컬렉션을 초기화한다              ← 여기
   — 무엇을 지울지 알려면 목록을 실제로 읽어야 한다
   — 지연 로딩이었어도 여기서 SELECT 가 나간다
4. 각 자식에도 삭제를 예약한다
5. 플러시 때 자식 DELETE 먼저, 부모 DELETE 나중
```

**왜 초기화가 불가피한가** — 전이는 **"각 자식에게도 같은 연산을 한다"**는 것이다. **각 자식을 지목해야 하고, 지목하려면 목록이 있어야 한다.** 목록은 DB에만 있다.

**그래서 §6의 경고가 나온다**:

> **전이가 컬렉션을 초기화한다는 점을 잊지 않는다. 지연 로딩으로 아껴 둔 쿼리가 삭제 경로에서 되살아난다.**

**전형적인 시나리오**:

```text
평소:   원료 조회 → 연결 컬렉션은 지연 → SELECT 1번
삭제 시: em.remove(material)
         → 3번에서 연결 40건 SELECT      ← 아껴 둔 쿼리가 돌아온다
         → 5번에서 DELETE 41번
         합계 42 쿼리
```

**대안**(§6): 자식이 아주 많다면 **전이 대신 벌크 삭제와 DDL 연쇄를 조합**하는 편이 낫다 — Q2에서 본 대로 벌크 삭제는 컨텍스트를 우회하므로 **컬렉션을 초기화하지 않고**, DDL 연쇄가 자식을 정리한다.

**정리하면 세 층이 각각 다른 값을 가진다**:

| 상황 | 무엇을 쓰나 |
|---|---|
| 자식이 적고 컨텍스트가 알아야 함 | **JPA 전이** |
| 자식이 많고 부모 하드 삭제가 잦음 | **`@OnDelete`** 또는 **벌크 + DDL 연쇄** |
| JPA를 우회하는 경로 | **DDL 연쇄 삭제** (항상 켜 둔다) |

**마지막 줄이 §6의 규칙이다** — DDL 연쇄는 **어느 조합을 고르든 지우지 않는다.**

1. 원료 하나를 지웠는데 DELETE가 41번 나갔다. 무엇이 켜져 있고, 그 전에 무엇이 한 번 더 일어났는가?
2. `@Modifying` 벌크 삭제에서 자식이 정리되는 이유는? JPA 전이인가?
3. "부모는 살아 있는가?" 이 질문이 무엇을 가르는가?
4. `mappedBy` 컬렉션에서 자식을 뺐는데 아무 일도 안 일어난다. 왜이고, 단방향이면 무엇이 달랐을까?
5. `cascade = ALL`로 쓰자는 제안에 어떻게 답하겠는가?

7. `@OnDelete`로 DELETE를 41번에서 1번으로 줄였다. 무엇을 잃었는가?
