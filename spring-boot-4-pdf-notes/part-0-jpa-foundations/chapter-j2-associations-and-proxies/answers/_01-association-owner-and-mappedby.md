## Q1. 참조 둘 · 컬럼 하나에서 "주인"이 필요해지는 이유

**개수가 안 맞으면 충돌이 생기고, 충돌에는 판정 규칙이 필요하기 때문이다.**

```text
객체 세계    material.company        참조 1개
             company.materials       참조 1개      →  총 2개

테이블 세계  material.company_id     외래 키 1개   →  총 1개
```

**참조 두 개를 컬럼 하나로 매핑해야 한다.** 그러면 반드시 답해야 할 질문이 생긴다 — **둘이 어긋나면 어느 쪽을 믿을 것인가.**

```java
material.setCompany(companyA);         // 원료는 A 를 가리킨다
companyB.getMaterials().add(material); // 회사 B 는 이 원료를 갖고 있다고 주장한다
```

**`company_id`에 무엇을 쓸 것인가.** 둘 다 볼 수는 없고, 매번 개발자에게 물을 수도 없다.

**그래서 JPA는 어느 쪽을 볼지 미리 고정한다.** 그 정해진 쪽이 **연관관계 주인**이다.

**"고정한다"가 핵심이다** — 런타임에 "더 최근에 바뀐 쪽"이나 "둘 다 반영" 같은 규칙을 쓸 수도 있었지만, 그러면 **결과를 코드만 보고 예측할 수 없다.** 매핑 시점에 고정하면 항상 같은 답이 나온다.

**주인은 고를 수 있는 것이 아니다** — **외래 키 컬럼을 가진 테이블에 대응하는 엔티티가 주인**이다. 설계 취향이 아니라 스키마가 결정한다.

## Q2. `Material`과 `Company` 중 누가 주인인가

**`Material`이 주인이다. 근거는 `material` 테이블에 `company_id` 컬럼이 있다는 것이다.**

```java
// Material.java — 주인
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "company_id", nullable = false)   // ← 외래 키 컬럼을 지정한다
private Company company;

// Company.java — 반대편 (둔다면)
@OneToMany(mappedBy = "company")                     // ← 소유권 포기 선언
private List<Material> materials = new ArrayList<>();
```

**판정은 한 줄로 끝난다** — *"외래 키 컬럼이 어느 테이블에 있는가?"* `material`에 있으므로 `Material.company`가 주인이고, **`Company.materials`는 반대편일 수밖에 없다.**

**흔한 오답 — "부모가 주인"**(§5):

> **주인은 도메인의 부모·자식과 무관하다.** 개념적으로는 회사가 원료의 부모지만, **외래 키를 가진 쪽은 자식인 원료다. 그래서 자식이 주인이다.**

**"부모가 소유하니까 부모가 주인"이라고 읽으면 반대로 매핑하게 된다.**

**왜 자식이 외래 키를 갖는가** — 일대다에서 "다" 쪽이 컬럼을 가져야 행마다 하나의 값을 쓸 수 있다. 부모 쪽에 두려면 한 컬럼에 여러 자식 id를 넣어야 하는데, 관계형 모델이 그걸 허용하지 않는다. **그래서 이 규칙에는 선택의 여지가 없다.**

## Q3. `mappedBy`가 수동태라는 말

**`mappedBy`는 "내가 저것을 매핑한다"가 아니라 "나는 저것에 의해(by) 매핑된다"는 뜻이다.**

```java
@OneToMany(mappedBy = "company")
private List<Material> materials;
```

**읽는 법**: *"이 컬렉션의 외래 키는 `Material` 클래스의 `company` 필드가 관리한다."*

> **소유권 주장이 아니라 소유권 포기 선언이다.**

**이름이 헷갈리는 지점이 여기다.** `mappedBy`를 능동태로 읽으면 "내가 매핑을 담당한다"처럼 들려서, **주인 쪽에 붙여야 할 것 같은 착각**이 생긴다. 실제로는 정반대다 — **`mappedBy`가 붙은 쪽은 주인이 아니다.**

**값이 무엇인지도 함께 틀린다**(§5):

| | `mappedBy` | `@JoinColumn` |
|---|---|---|
| 붙는 쪽 | **반대편** | **주인** |
| 뜻 | "외래 키는 저 필드가 관리한다" | "이 필드는 이 컬럼에 매핑된다" |
| **값** | **상대 엔티티의 자바 필드 이름** | **DB 컬럼 이름** |
| 빠뜨리면 | JPA가 **조인 테이블**을 가정한다 | 컬럼 이름을 규칙으로 추론한다 |

**`mappedBy = "company_id"`가 아니라 `mappedBy = "company"`다.** 컬럼 이름이 아니라 **필드 이름**이다. 수동태로 읽으면 이것도 자연스럽다 — "나는 저 **필드**에 의해 매핑된다"이지 "저 **컬럼**에 의해"가 아니다.

## Q4. 컬렉션에 넣기만 했을 때 아무 SQL도 안 나가는 이유 — 플러시 단계로

**3번 단계에서 `mappedBy` 필드가 외래 키 판정에서 아예 제외되기 때문이다.**

**플러시 시점에 JPA가 보는 것**:

1. **플러시가 시작되고 더티 체킹이 돈다**
2. **연관 필드 중 주인 쪽만 검사한다** — `Material.company`를 본다. 외래 키 컬럼과 대응하는 필드가 그것뿐이니까
3. **`mappedBy`가 붙은 필드는 외래 키 판정에서 제외한다** — `Company.materials`는 **아예 보지 않는다.** 하나의 컬럼에 두 개의 진실이 생기는 걸 막으려고
4. **주인 필드가 가리키는 대상의 식별자를 외래 키 컬럼에 쓴다**
5. **주인 필드가 `null`이면 외래 키도 `null`이 된다** — 컬렉션에 무엇이 들어 있든 상관없다

**출발 장면이 실패한 이유가 5번이다**:

```java
company.getMaterials().add(material);   // 3번에서 무시된다
materials.save(material);
// material.company 는 여전히 null → company_id NULL → NOT NULL 제약 위반 💥
```

**"무시한다"가 버그처럼 보이지만 설계다.** 반대편도 봤다면 Q1의 충돌 문제가 되살아난다. **보지 않기로 한 것이 규칙의 전부다.**

**비유와 그 한계 — 등기부와 내 수첩**: 소유권의 진실은 등기부(외래 키)에 있다. 수첩에 "이 건물은 내 것"이라 적어도 등기는 안 바뀐다.

→ **깨지는 지점**: 수첩과 등기부가 달라지면 수첩이 **낡은 상태로 남는다.** 반대편 컬렉션은 다르다 — **커밋하고 트랜잭션을 새로 열면 DB에서 다시 읽어 와 저절로 맞아진다.** 어긋나는 것은 **같은 트랜잭션 안에서만**이다.

**그래서 이 사고는 다음 요청에서는 멀쩡해 보이고, 테스트에서도 잘 잡히지 않는다.** "낡은 사본"이 아니라 **"잠깐 어긋났다가 스스로 사라지는 불일치"**다.

## Q5. 편의 메서드의 두 줄 중 SQL을 만드는 줄

**두 번째 줄이다.**

```java
// Company.java
void addMaterial(Material material) {
    this.materials.add(material);   // ① 객체 그래프 탐색을 위해 — 메모리 안의 일관성
    material.setCompany(this);      // ② 외래 키를 위해 — 이 줄이 실제 저장을 만든다
}
```

| 줄 | 역할 | 빼면 |
|---|---|---|
| **① `materials.add()`** | **메모리 안의 일관성** | **저장은 된다.** 단 같은 트랜잭션에서 `getMaterials()`를 다시 읽으면 방금 붙인 원료가 없다 |
| **② `setCompany()`** | **외래 키** | **아무것도 저장되지 않는다** — 출발 장면 그대로 |

**Q4의 3번 단계가 그대로 답이다** — ①이 건드리는 필드는 플러시가 보지 않는다.

**그럼 ①은 왜 쓰는가** — DB에는 반영됐는데 **이미 메모리에 로딩된 컬렉션은 그대로**이기 때문이다. 같은 트랜잭션 안에서 그 컬렉션을 읽는 코드가 있으면 방금 붙인 원료가 안 보인다. ①은 **그 불일치를 미리 메워 두는 것**이다.

**§6의 짝 규칙**: **편의 메서드를 만들었다면 반대쪽 제거도 함께 만든다.** `addMaterial`만 있고 `removeMaterial`이 없으면 **제거 경로에서 같은 불일치가 다시 생긴다** — 컬렉션에서는 빠졌는데 `material.company`는 그대로다.

## Q6. CosmoRoute가 컬렉션 대신 리포지토리 쿼리를 쓰는 편이 나은 이유 셋

```java
// MaterialRepository
@Query("SELECT m FROM Material m WHERE m.company.id = :companyId AND " + CatalogVisibility.SUPPLY
        + " ORDER BY m.name ASC")
List<Material> findPublishedByCompany(UUID companyId);
```

**① 가시성 조건을 걸 수 있다.**

`company.getMaterials()`는 **숨김·삭제·미공개 원료까지 전부 가져온다.** INV-14·INV-15가 요구하는 필터를 **컬렉션에는 붙일 수 없다.** ADR-0002대로 가시성이 조회 시점에 계산되는 설계에서는, 컬렉션이 그 규칙을 **우회하는 통로**가 된다.

**② `CompanyRepository`의 철학과 일관된다.**

그 인터페이스는 *"필터 없는 조회를 공짜로 얻으면 주인 없는 큐레이션 제조사가 공급사 목록으로 샌다"*는 이유로 **`JpaRepository`를 상속하지 않는다.**

> **필터 없는 컬렉션을 엔티티에 다는 것은 같은 구멍을 다른 문으로 여는 일이다.**

**③ 원료가 많은 회사에서 전량 로딩이 일어나지 않는다.**

**컬렉션은 페이징이 어렵지만 쿼리는 자연스럽다.** 원료 5,000건인 회사를 열면 컬렉션은 5,000건을 다 올린다.

**세 이유의 성격이 다르다** — ①은 **정확성**, ②는 **설계 일관성**, ③은 **성능**이다. 하나만으로도 근거가 되는데 셋이 같은 방향을 가리킨다.

**원칙**: **단방향으로 되면 단방향이 낫다.** 양방향은 *"객체 그래프를 타고 탐색해야만 하는 이유"*가 실제로 생겼을 때 추가한다.

**단, 전부 단방향이 답은 아니다**(§2.4) — 부모가 자식의 생명주기를 소유할 때(전이·고아 제거), 자식 없이 부모가 성립하지 않을 때, **도메인 규칙이 컬렉션 전체를 봐야 할 때**는 반대편을 두는 값이 있다. 마지막이 [[02-join-entity-instead-of-many-to-many]]에서 실제로 등장한다.

## Q7. `mappedBy`를 지우면 부팅이 실패하는 이유

**`mappedBy`가 없으면 JPA가 이 `@OneToMany`를 "외래 키 없는 일대다"로 해석해 별개의 조인 테이블을 가정하기 때문이다.**

```text
@OneToMany(mappedBy = "company")   →  "외래 키는 Material.company 가 관리한다"
                                      → material.company_id 를 쓴다

@OneToMany                          →  "이 연관에 대한 정보가 나한테 없다"
                                      → 조인 테이블 company_materials 를 가정한다
                                      → 그런 테이블이 스키마에 없다
                                      → ddl-auto: validate 가 검증에 실패
                                      → 애플리케이션이 아예 안 뜬다 💥
```

**왜 조인 테이블을 가정하는가** — JPA 입장에서 `@OneToMany`만 있고 아무 힌트도 없으면, **외래 키가 어디 있는지 알 방법이 없다.** 상대 엔티티의 어느 필드가 나를 가리키는지도 모른다. **가장 일반적인 형태(조인 테이블)로 폴백**하는 것이다.

**§6의 경고**:

> **`mappedBy`를 지워서 문제를 "해결"하지 않는다.**

**`ddl-auto: validate`인 CosmoRoute에서는 부팅 실패로 즉시 드러난다** — 이건 오히려 다행이다. **`ddl-auto: update`인 환경에서는 Hibernate가 엉뚱한 조인 테이블을 실제로 만들어 버린다.** 그러면 애플리케이션은 뜨고, 데이터는 두 곳에 나뉘어 쌓이며, **한참 뒤에 발견된다.**

**같은 사고의 두 얼굴**: `validate`는 **빌드·기동 시점의 오류**로, `update`는 **런타임의 조용한 데이터 분열**로 나타난다. Ch15의 "기본값이 바뀜"과 같은 구조다 — **일찍 크게 터지는 쪽이 낫다.**

## Q8. 양방향으로 바꿔도 DDL이 안 바뀌는 이유

**양방향은 순전히 객체 쪽 이야기이고, 외래 키는 원래부터 하나뿐이기 때문이다.**

Hibernate 공식 문서: *"부모와 자식 양쪽에서 탐색할 수 있게 되지만, **데이터베이스에는 여전히 외래 키가 하나뿐이다.**"*

```text
[단방향]                          [양방향]
 material.company_id   ← 있음      material.company_id   ← 그대로 있음
                                   company 테이블        ← 아무것도 안 늘어남

 DDL 차이: 없음
```

**추가된 `@OneToMany(mappedBy = ...)`는 필드 하나일 뿐이다.** `mappedBy`가 있으니 **새 컬럼도, 새 테이블도 요구하지 않는다.** 이미 있는 `material.company_id`를 **반대 방향에서 읽는 뷰**를 자바에 하나 더 만든 것이다.

**그래서 §5의 역방향 진단이 성립한다**:

> **양방향으로 바꿨는데 스키마 마이그레이션이 필요하다고 느낀다면 매핑을 잘못 짚은 것이다.**

거의 항상 **`mappedBy`를 빠뜨린 것**이다(Q7) — 그러면 조인 테이블이 필요해지므로 "마이그레이션이 필요하다"는 감각이 생긴다.

**함께 정리되는 것 — 양방향의 이득과 대가**:

| | 얻는 것 | 치르는 것 |
|---|---|---|
| DB | **없음** | **없음** |
| 객체 | 그래프 탐색, 전이·고아 제거를 걸 자리 | **동기화 책임**, 필터 없는 전량 로딩 위험 |

**DDL이 안 바뀐다는 사실이 곧 "이건 편의 기능"이라는 증거다.** 편의의 대가로 동기화 책임이 생기므로, **§6대로 기본값으로 삼지 않는다.**

**덤 — 컬렉션 초기화도 연관과 무관하다**(§5): `new ArrayList<>()`는 `NullPointerException`을 막는 자바 관례일 뿐이다. **초기화했다고 컬렉션이 DB와 이어지지는 않는다.**

## 재출제 문항

1. `company.getMaterials().add(m)` 후 커밋했더니 `company_id`가 `NULL`이다. 어느 단계에서 무시됐는가?
2. 편의 메서드에서 한 줄만 남길 수 있다면 어느 줄인가? 나머지 줄을 빼면 무엇이 어긋나는가?
3. `mappedBy = "company_id"`라고 썼다. 무엇이 틀렸는가?
4. 회사가 원료의 부모인데 왜 원료가 주인인가?
5. `mappedBy`를 지웠더니 부팅이 안 된다. `ddl-auto: update`였다면 무슨 일이 났을까?
6. "이 회사의 공개 원료 목록"이 필요하다. 컬렉션과 쿼리 중 무엇을 쓰고 왜인가?
7. 양방향으로 바꾸는 마이그레이션 스크립트를 짜라는 요청을 받았다. 어떻게 답하겠는가?
