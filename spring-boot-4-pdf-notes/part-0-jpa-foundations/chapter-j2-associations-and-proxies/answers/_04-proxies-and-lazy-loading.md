## Q1. `getId()`는 SQL을 유발하지 않고 `getCompanyName()`은 유발하는 이유

**프록시가 식별자만 갖고 있고 나머지 필드는 없기 때문이다.**

```java
Company c = m.getCompany();
c.getClass()          // Company$HibernateProxy$... — Company 를 상속한 런타임 생성 클래스
c.getId()             // 갖고 있는 값을 그대로 반환 → SQL 없음
c.getCompanyName()    // 갖고 있지 않다 → 여기서 SELECT
```

**이 비대칭이 프록시 동작의 전부다.**

**여섯 단계**:

1. **원료를 조회한다** — `material` 행을 읽으면 `company_id`가 함께 들어온다
2. **`Company`를 상속한 프록시를 만들고 식별자를 넣는다** — 비워 두면 `null`이 되어 연관이 끊기고, 실제로 읽으면 그래프 전체가 딸려 온다
3. **`material.company`에 그 프록시를 넣는다** — 프록시가 `Company`의 하위 타입이라 타입 검사를 통과하므로 호출부는 차이를 모른다
4. **`getId()` → 갖고 있는 식별자를 그대로 반환** — 이미 아는 값을 위해 DB에 갈 이유가 없다
5. **다른 getter → 그때 SELECT** — 이것이 **초기화**다
6. **읽어 온 값을 내부 실제 인스턴스에 채우고 이후 호출은 거기로 위임** — 같은 프록시에 두 번 SELECT를 보내지 않으려고

**설계 의도**: **자리는 채우되 내용은 비워 둔다.** `null`로 두면 연관을 매핑한 의미가 없고, 실제로 읽으면 **객체 그래프를 하나 건드릴 때 연결된 것이 전부 딸려 올라온다.** Hibernate 문서가 프록시 도입 이유를 *"전체 객체 그래프를 한꺼번에 로딩하는 비효율을 피하기 위해"*라고 적은 것이 이것이다.

## Q2. 프록시가 식별자를 이미 아는 이유 — 외래 키가 어느 행에 있는지로

**외래 키가 원료 행 자체에 있기 때문이다.**

```text
material 행을 SELECT 하면

  id | name | company_id | ...
  ───┼──────┼────────────┼────
  42 | ...  |   c-7      | ...
                  ↑
        이 값이 곧 회사의 식별자다
        회사 테이블을 읽지 않아도 이미 손에 있다
```

**`material.company_id`를 읽는 순간 그 값이 곧 회사의 식별자다. 회사를 조회하지 않아도 식별자만은 공짜로 안다.**

**그래서 `getId()`에는 SQL이 필요 없다** — 프록시는 원료 행에서 이미 얻은 값을 들고 있을 뿐이다.

**이 사실은 [[01-association-owner-and-mappedby]]의 주인 규칙과 직결된다** — 주인 쪽(`@ManyToOne`)은 **자기 행에 외래 키가 있으므로** 상대의 식별자를 공짜로 안다.

**반대편은 그렇지 않다**: `Company.materials`는 회사 행 어디에도 원료 id가 없다. **컬렉션을 프록시로 만들면 "몇 개인지"조차 모른다** — `size()`도 SQL을 유발한다. 같은 지연 로딩이지만 공짜로 아는 정보의 양이 다르다.

**비유와 그 한계 — 도서관 대출 카드**: 카드에는 **청구기호만** 적혀 있다. 책 내용이 필요하면 그 번호로 서가에 가야 한다. **번호만 알면 되는 일**(반납 목록에 적기)은 서가에 가지 않고 끝난다.

→ **깨지는 지점**: 카드는 도서관이 닫혀도 손에 남고 **내일 다시 가면 된다.** 프록시는 다르다 — **영속성 컨텍스트가 닫히면 그 자리에서 예외를 던진다.** 나중에 다시 가는 선택지가 없다. **"나중에 읽으면 된다"가 아니라 "그 트랜잭션 안에서만 읽을 수 있다"**는 점에서 비유가 멈춘다.

## Q3. `LazyInitializationException`이 나는 조건

**초기화(5단계)에는 영속성 컨텍스트가 살아 있어야 한다. 트랜잭션이 끝나 엔티티가 준영속이 되면 프록시는 돌아갈 곳을 잃는다.**

```java
// 트랜잭션 안
Material m = service.findById(id);   // @Transactional 이 여기서 끝난다
                                     // → m 도 그 안의 프록시도 준영속
// 트랜잭션 밖
m.getCompany().getCompanyName();     // LazyInitializationException
```

**두 조건이 모두 필요하다**:

1. **프록시가 아직 초기화되지 않았다** — 이미 읽었으면 값이 내부에 있으므로 예외가 안 난다
2. **영속성 컨텍스트가 없다** — 읽으러 갈 곳이 없다

**그래서 같은 코드가 통과하기도 한다** — 앞에서 우연히 그 필드를 한 번 건드렸으면 이미 초기화돼 있다. **테스트에서 통과하고 운영에서 터지는 전형적인 형태다.**

Hibernate 문서: *"프록시는 엔티티가 **영속성 컨텍스트에 연결되어 있는 동안에만** 가져올 수 있다. 그렇지 않으면 `LazyInitializationException`이 던져진다."*

**예외가 나는 것이 안전한 쪽이다**:

> **조용히 `null`을 반환한다면 데이터가 없는 것인지 못 읽은 것인지 구분할 수 없다.**

**§5의 진단**: 예외는 **"데이터가 없다"가 아니라 "읽을 수 없는 자리에서 읽으려 했다"**는 뜻이다. **원인은 데이터가 아니라 트랜잭션 경계에 있다.** 예외를 잡아 `null`로 바꾸는 것은 **원인을 감추는 처리**다.

**§6의 대응**: **엔티티를 그대로 응답으로 내보내지 않는다.** 직렬화기가 **모든 getter를 호출**하므로 프록시가 전부 초기화되거나, 트랜잭션 밖이면 예외가 난다. **DTO로 변환하는 경계를 트랜잭션 안에 둔다.**

## Q4. 컨텍스트 없이 지연 로딩을 허용하는 설정이 위험한 이유

**지연 로딩 한 번에 커넥션 하나를 쓰기 때문이다.**

Hibernate에는 컨텍스트 없이 프록시를 만나면 **새 세션과 트랜잭션을 열어** 읽어 오는 설정이 있다. 소스의 동작을 보면 **프록시 하나를 초기화할 때마다**:

```text
세션 열기 → 트랜잭션 시작 → SELECT → 커밋 → 세션 닫기
```

**목록 조회에서 켜면 무슨 일이 나는가**:

```text
원료 200건을 읽고 각각 회사 이름을 찍는다
  → 프록시 200개 초기화
  → 세션 200개, 트랜잭션 200개, 커넥션 200번 획득
  → 커넥션 풀(보통 10~20)이 그대로 소진된다
  → 다른 요청까지 대기한다
```

**"예외를 없애 주는 것처럼 보이지만 문제를 옮기는 설정이다."**

**무엇에서 무엇으로 옮기는가**:

| | 설정 없이 | 설정 켜고 |
|---|---|---|
| 증상 | **예외** — 즉시, 명확 | **커넥션 고갈** — 부하가 걸려야 나타난다 |
| 원인 추적 | 스택 트레이스가 그 자리를 가리킨다 | **전혀 무관한 요청이 타임아웃난다** |
| 트랜잭션 일관성 | 한 트랜잭션 | **읽을 때마다 다른 트랜잭션** — 중간에 값이 바뀔 수 있다 |

**세 번째가 조용하고 나쁘다** — 같은 화면에 표시된 값들이 **서로 다른 시점의 스냅샷**이 된다.

**§6**: **컨텍스트 없이 지연 로딩을 허용하는 설정을 켜지 않는다.** 예외가 났다면 고칠 곳은 설정이 아니라 **트랜잭션 경계나 조회 전략**이다.

## Q5. `@ManyToOne`의 fetch 기본값과 목록 조회에서의 문제

**기본값은 즉시(EAGER)다.**

| 연관 | 기본 fetch |
|---|---|
| **`@ManyToOne`** | **즉시** |
| **`@OneToOne`** | **즉시** |
| `@OneToMany` | 지연 |
| `@ManyToMany` | 지연 |

**"하나를 가리키는" 연관이 즉시가 기본이다.** 하나쯤은 함께 읽어도 괜찮다는 가정인데 — **목록 조회에서는 그 하나가 행 수만큼 반복된다.**

```text
[즉시 로딩으로 원료 200건 조회]
  SELECT * FROM material WHERE ...          → 200건
  SELECT * FROM company WHERE id = ?        → 200번 (원료마다 한 번)

  화면에는 회사 이름만 필요한데 회사의 모든 컬럼을 200번 읽었다.
```

**그리고 쿼리 수만이 문제가 아니다** — **회사가 다시 다른 것을 즉시 로딩한다면 그것도 따라온다.** 객체 그래프를 하나 건드리면 **연결된 것이 전부 딸려 올라온다.**

**그래서 `Material.company`에 `fetch = FetchType.LAZY`가 명시되어 있다는 사실 자체가 의도적인 선택이다.**

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "company_id", nullable = false)
private Company company;
```

**안 적었다면 즉시 로딩이 됐을 것이고, 발견 카탈로그 목록에서 회사를 원료 수만큼 읽었을 것이다.**

**[[02-join-entity-instead-of-many-to-many]]의 연결 엔티티도 같은 이유로 명시했다** — `MaterialSubstance.material`을 기본값으로 두면 **연결 하나를 읽을 때마다 원료 전체가 딸려 온다.**

**§6**: **`@ManyToOne`에 `fetch`를 생략하지 않는다.** 기본값이 의도와 반대다. **CosmoRoute의 두 매핑처럼 항상 명시한다.**

## Q6. 엔티티 `equals()`를 `getClass()`로 구현하면 깨지는 것

**프록시와 실제 인스턴스가 서로 같지 않다고 판정된다.**

```java
// 흔한 IDE 생성 코드
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;   // ← 여기서 깨진다
    ...
}
```

```text
company     .getClass() → Company
companyProxy.getClass() → Company$HibernateProxy$abc123

  같은 회사 id 42 인데 getClass() 가 다르다 → equals 가 false
```

**언제 실제로 문제가 되는가**:

```java
Set<Company> set = new HashSet<>();
set.add(company);                    // 실제 인스턴스
set.contains(material.getCompany()); // 프록시 → false
```

**그리고 §5의 사실이 이걸 더 나쁘게 만든다**:

> **이미 1차 캐시에 실제 인스턴스가 있으면 프록시가 아니라 그 인스턴스가 들어온다**(동일성 보장 때문).

**그래서 같은 코드가 상황에 따라 프록시를 주기도 하고 실제 객체를 주기도 한다.** 조회 순서에 따라 `equals()`의 결과가 달라진다 — **재현이 안 되는 버그**가 된다.

**대응**:

| 방법 | 설명 |
|---|---|
| **`instanceof`로 쓴다** | 프록시가 하위 타입이므로 통과한다 |
| **`Hibernate.unproxy()`를 거친다** | 실제 인스턴스를 꺼내 비교 |
| **아예 구현하지 않는다** | 영속 상태 안에서만 비교한다면 **동일성 보장이 이미 `==`를 참으로 만든다** |

**세 번째가 §6의 권고다** — 준영속 객체끼리 비교할 일이 실제로 있을 때만 구현한다.

**같은 뿌리의 문제 하나 더**: Hibernate 문서가 *"다형적 연관에서 **타입 캐스트와 `instanceof` 검사가 올바르게 동작하지 않을 수 있다**"*고 경고한다. **[[03-exclusive-target-associations]]에서 `@Any`를 고르지 않은 이유가 하나 더 늘어난 셈이다.**

## Q7. "지연 로딩은 읽지 않는 것이 아니라 미루는 것" — 쿼리 수로

**미룬 것은 결국 읽힌다. 그것도 한 번에가 아니라 하나씩.**

```text
[즉시 로딩]  원료 200건 + 회사 200번   = 201 쿼리 (조회 시점에 한꺼번에)
[지연 로딩]  원료 200건                = 1 쿼리
             그 뒤 각각 회사 이름 접근 = 200 쿼리
             ─────────────────────────────────────
             합계                       = 201 쿼리  ← 똑같다
```

**쿼리 수가 줄지 않았다.** 나간 시점만 뒤로 밀렸다.

**이것이 N+1이다.** Hibernate 문서: *"지연 로딩은 주의하지 않으면 **N+1 select 문제**로 이어질 수 있다."*

**언제 실제로 이득인가** — **끝까지 접근하지 않을 때만**이다:

```text
원료 200건을 읽고 이름만 표시한다 (회사는 안 씀)
  즉시 로딩:  201 쿼리
  지연 로딩:    1 쿼리   ← 여기서만 이득
```

**§5의 경고**: **"LAZY로 바꿨으니 쿼리가 줄겠지"라고만 생각하면 N+1을 만나고 원인을 못 찾는다.** 매핑을 바꿨는데 쿼리 수가 그대로이니, 매핑을 의심하지 않게 된다.

> **지연 로딩이 즉시 로딩보다 항상 나은 것이 아니라, 문제를 다른 모양으로 옮긴 것이다.**

**옮긴 모양의 차이**:

| | 즉시 로딩 | 지연 로딩 |
|---|---|---|
| 쿼리가 나가는 시점 | 조회 시점에 몰린다 | **접근할 때마다 흩어진다** |
| 안 쓸 때 | **그래도 읽는다** | 안 읽는다 ✅ |
| 원인 추적 | 조회 코드 한 곳 | **접근 코드 여기저기** |

**진짜 해법은 셋 중 하나가 아니다** — 페치 조인·`@EntityGraph`·배치 사이즈로 **"미룬 것을 한 번에 읽는"** 것이고, 그 조건과 해법은 `chapter-j3`에서 다룬다.

## Q8. `getReference()`로 성분 40개를 연결할 때 아끼는 것과 잃는 것

**프록시는 피할 대상만이 아니라, 식별자만 필요할 때 SELECT를 아끼는 도구이기도 하다.**

```java
Material material = entityManager.getReference(Material.class, materialId);
Substance substance = entityManager.getReference(Substance.class, canonicalId);
MaterialSubstance link = MaterialSubstance.toCanonical(material, substance);
```

**아끼는 것 — SELECT 40번**

**외래 키를 채우는 데 필요한 것은 식별자뿐이다.** 성분 행의 다른 컬럼을 읽을 이유가 없다.

```text
[findById 로 40개]   SELECT × 40  →  값을 다 읽지만 쓰는 건 id 뿐
[getReference 로]    SELECT × 0   →  프록시 40개, 각각 id 만
```

**잃는 것 — 존재 검증**

> **존재하지 않는 식별자를 넘겨도 그 자리에서는 알 수 없다.**

**언제 드러나는가**:

```text
getReference(Substance.class, "없는-id")   → 통과. 프록시가 생긴다
link 을 만들고 save                        → 통과
커밋 시 외래 키 제약 위반                  → 여기서 터진다 💥
   또는 나중에 그 프록시의 필드에 접근할 때 EntityNotFoundException
```

**터지는 위치가 원인에서 멀다.** 어느 성분 id가 잘못됐는지 스택 트레이스가 알려 주지 않는다.

| 축 | **`find()`** | **`getReference()`** |
|---|---|---|
| SQL | 즉시 SELECT | **나가지 않는다** |
| 없는 식별자 | `null` / 빈 `Optional` | **그 자리에서는 모른다** |
| 반환 타입 | 실제 엔티티 (또는 1차 캐시의 것) | **프록시** |
| 쓸 상황 | **값을 읽어야 할 때** | **외래 키만 채울 때** |

**판단 기준**(§6): **`getReference()`를 존재 검증이 필요한 곳에 쓰지 않는다.** 검증이 목적이면 `findById()`다.

**CosmoRoute의 경우** — 성분 id는 정식 성분 목록에서 사용자가 고른 값이라 존재가 사실상 보장되고, 만에 하나 없으면 **외래 키 제약이 최종 방어선**이 된다. [[03-exclusive-target-associations]]에서 A를 고른 덕에 그 방어선이 살아 있다. **`@Any`를 골랐다면 `getReference()`의 대가를 갚아 줄 제약도 없었다.**
