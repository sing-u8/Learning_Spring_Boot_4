## Q1. 네 상태를 두 축으로 구분하기

| 상태 | **컨텍스트가 관리?** | **식별자가 있나?** | 어떻게 되는가 |
|---|:---:|:---:|---|
| **비영속 (transient)** | ✗ | **✗** (보통) | `new`로 막 만든 것. DB 행도 없다 |
| **영속 (managed)** | **✓** | ✓ | 1차 캐시·더티 체킹·지연 로딩이 **여기서만** 작동 |
| **준영속 (detached)** | ✗ | **✓** | 한때 영속이었다가 떨어져 나왔다 |
| **삭제 (removed)** | **✓** | ✓ | DELETE가 **예약**된 상태. 아직 관리 대상 |

**두 축이 각각 무엇을 결정하는가**:

- **"관리하는가"는 메커니즘의 작동 여부를 결정한다.** ✓면 더티 체킹·동일성 보장·지연 로딩이 살아 있고, ✗면 전부 죽는다.
- **"식별자가 있나"는 들여오는 방법을 결정한다.** 없으면 `persist()`, 있으면 `merge()`.

**두 축이 만드는 네 칸 중 세 칸만 쓰인다** — "관리하는데 식별자가 없는" 칸은 없다. 1차 캐시가 `(타입, 식별자)` 맵이라 **식별자 없이는 담을 수가 없기 때문이다.**

**함정 — 두 축이 겉보기로 구별되지 않을 때가 있다.** CosmoRoute처럼 **식별자를 애플리케이션이 직접 할당**하면, 방금 `new`한 객체도 id를 갖는다. **비영속인데 식별자가 있다.** 그래서 Spring Data가 상태를 오판하고, 그 오판이 Q5의 문제가 된다.

**감으로 판정하지 말 것**(§6) — `entityManager.contains(entity)`가 참이면 영속, 거짓이면 그 컨텍스트 밖이다.

## Q2. `return this.companies.save(company)`를 `return company`로 바꾸면

**준영속 객체를 반환하게 되고, 호출부가 그걸 고쳐도 아무 일도 일어나지 않는다.**

**왜 두 객체가 다른가 — 두 단계가 얽혀 있다.**

**① Spring Data의 `save()`는 무조건 `persist()`를 부르지 않는다**:

```java
// SimpleJpaRepository
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity);
        return entity;                        // 같은 객체
    } else {
        return entityManager.merge(entity);   // 다른 객체일 수 있다
    }
}
```

**② `Company.curated()`가 식별자를 직접 할당한다**:

`Company`에는 `@Version`이 없고 식별자는 `UUID`다. `UUID.randomUUID()`로 값을 이미 채웠으므로 **`isNew()`는 거짓**이다. → `merge()`가 호출되고, `merge()`는 **다른 인스턴스**를 돌려준다.

```text
Company.curated(...)              id = UUID.randomUUID()   → 비영속, 식별자 있음
companies.save(company)
  └ isNew(company)?               @Version 없음 · id != null  → false
  └ entityManager.merge(company)
       ① 식별자로 컨텍스트 조회 → 없음
       ② DB SELECT … WHERE id = ? → 행 없음     ← 여분의 SELECT 1회
       ③ 새 영속 인스턴스를 만들고 값 복사
       ④ 영속 인스턴스 반환 (원본과 다른 객체)
  └ 커밋 시점에 INSERT

return this.companies.save(company);   → 영속 인스턴스   ✅
return company;                        → 준영속 원본     ❌
```

**그래서 이 코드에서 반환값을 쓰는 것은 취향이 아니라 정확성이다.**

**무엇이 깨지는가** — 호출부가 받은 객체는 관리 대상이 아니므로:

- 필드를 고쳐도 **UPDATE가 안 나간다** (예외도 없다)
- 지연 로딩 연관을 건드리면 **초기화 실패**
- 같은 회사를 다시 조회한 결과와 **`==`가 거짓**

**단, "경우에 따라 다르다"** — `isNew()`가 참이면 `persist()`를 타고 **넘긴 그 객체가 영속**이 된다. 그때는 `return company;`도 맞다. **그러나 어느 쪽인지 코드만 보고는 알 수 없으므로, 항상 반환값을 쓰는 것이 안전하다.**

## Q3. `merge()`가 넘긴 객체를 영속으로 만들지 않는다는 것

**Hibernate 문서의 표현이 정확하다** — *"새 영속성 컨텍스트와 연결된 **구별되는(distinct)** 영속 인스턴스를 반환한다. 사실상 준영속 인스턴스를 같은 DB 행을 나타내는 영속 인스턴스와 **교환**하는 것이다."*

```text
        [내 손]                        [영속성 컨텍스트]

   detached 객체                       ┌────────────────────┐
   ┌──────────────┐                    │                    │
   │ id = 42      │  ── ② 없으면 ──▶  │  ② SELECT id=42    │
   │ name = "신"  │      DB 조회       │       ↓            │
   └──────────────┘                    │  ┌──────────────┐  │
          │                            │  │ id = 42      │  │
          └──── ③ 값만 복사 ─────────▶ │  │ name = "신"  │  │
                                       │  └──────────────┘  │
   여전히 detached ❌                  └────────┬───────────┘
   (컨텍스트에 등록된 적 없음)                  │
                                          ④ 이것을 반환 ✅
```

**다섯 단계**:

1. 넘어온 객체의 **식별자를 읽는다** — 어느 행에 값을 옮길지 정해야 하니까
2. 그 식별자로 **컨텍스트를 조회하고, 없으면 DB에서 SELECT** — 값을 받아 줄 영속 인스턴스가 필요하니까
3. 넘어온 객체의 **필드 값을 그 영속 인스턴스로 복사**
4. **영속 인스턴스를 반환** — 이후 더티 체킹은 이쪽에만 작동하니까
5. **넘어온 원본은 여전히 준영속** — 컨텍스트에 등록된 적이 없으니까

**"이동하는 것은 객체가 아니라 값이다."** 화살표를 "준영속 객체가 영속이 된다"로 읽으면 안 된다.

**비유와 그 한계 — 도서관 대출**: 책이 서가에 있으면 사서가 관리한다(영속). 빌려 나가면 관리 밖이다(준영속) — 집에서 밑줄을 그어도 목록은 안 바뀐다.

→ **깨지는 지점**: 도서관은 빌려 간 **그 책**을 그대로 반납받는다. `merge()`는 **내가 들고 온 책의 내용을 서가의 다른 책에 옮겨 적고, 그 서가 책을 돌려준다.** 내가 들고 온 책은 **여전히 내 손에 남아 관리 밖이다.**

**2번의 SELECT가 중요하다** — **`merge()`는 거의 항상 조회를 한 번 한다.** DB에 행이 없으면 그때 새 인스턴스를 만들어 INSERT로 이어진다.

## Q4. `persist()`에는 반환값이 없고 `merge()`에는 있는 이유

**반환할 것이 있느냐 없느냐가 다르다. 시그니처 자체가 동작의 차이를 말한다.**

| 축 | **`persist()`** | **`merge()`** |
|---|---|---|
| 대상 상태 | 비영속 | 준영속 (또는 비영속) |
| **반환값** | **없음 (`void`)** | **영속 인스턴스 — 넘긴 것과 다르다** |
| 넘긴 객체는 | **그 자체가 영속이 된다** | **준영속으로 남는다** |
| SELECT | 하지 않는다 | **거의 항상 한 번** |
| 식별자 | 없어도 된다 | 있어야 한다 |

**`persist()`에 반환값이 없는 이유**: **넘긴 그 객체가 영속이 된다.** 돌려줄 새 객체가 없다. 호출부는 이미 그 참조를 들고 있다.

**`merge()`에 반환값이 있는 이유**: **넘긴 객체는 영속이 되지 않는다.** 관리되는 것은 다른 인스턴스이고, 호출부가 그것을 모르면 잘못된 객체를 계속 쓴다.

> **`merge()`에 반환값이 있는 것 자체가 "다른 객체를 준다"는 신호다.**

**이건 API 설계에서 자주 쓰이는 신호다** — `void`는 "제자리에서 바꿨다", 반환값은 "새 것을 준다"는 관례. `String.trim()`이 새 문자열을 주는 것과 같은 이유다.

**그래서 `merge()`의 반환값을 버리는 코드는 거의 항상 버그다**:

```java
entityManager.merge(company);   // 반환값을 안 쓴다 → 무엇을 관리 중인지 모른다
company.rename("새 이름");       // 준영속 원본을 고쳤다 → 반영 안 됨
```

**`save()`는 둘 중 하나를 고르는 분기다**(§5) — JPA 메서드가 아니다. **"`save()` = `persist()`"로 외우면 왜 어떤 경우엔 반환값이 다른 객체인지 설명할 수 없다.**

## Q5. 식별자를 애플리케이션이 할당하면 `isNew()`가 거짓이 되는 이유와 그 결과

**기본 `isNew()`는 "식별자가 `null`인가"를 본다. 직접 할당하면 항상 값이 있으므로 항상 거짓이다.**

```text
Company.curated(...)  →  company.id = UUID.randomUUID()   ← 여기서 이미 채워진다
save(company)         →  isNew()?  id != null  →  false
                      →  merge() 로 분기
```

**늘어나는 것 — INSERT 한 건마다 SELECT가 한 번씩이다.**

```text
merge() ② DB SELECT … WHERE id = ?  → 행 없음   ← 이 SELECT 가 매번 추가된다
        ③ 새 인스턴스 생성 후 INSERT
```

**"없는 것을 확인하기 위한 SELECT"다.** 결과가 항상 비어 있는데도 매번 나간다.

**규모에 따라 다르다**:

| 경로 | 영향 |
|---|---|
| 회사 하나 등록 | SELECT 1회 추가 — **무시할 만하다** |
| 원료에 **성분 40개**를 한꺼번에 붙임 | **SELECT 40회 추가** |

**이건 CosmoRoute의 실수가 아니라 결정의 대가다.** 그 결정의 이득도 분명하다:

- `IDENTITY`와 달리 **쓰기 지연이 온전히 살아 있다**([[02-write-behind-and-flush]])
- **INSERT 전에 이미 식별자를 알아** 연관 객체를 함께 조립하기 쉽다

**같은 결정의 양면이다** — 쓰기 지연에는 이득, `save()` 경로에는 대가.

## Q6. `Persistable`이 그 문제를 푸는 방식

**"새것인가"의 판정 근거를 식별자에서 떼어 내, 엔티티가 직접 대답하게 한다.**

```java
@MappedSuperclass
public abstract class AbstractEntity<ID> implements Persistable<ID> {

    @Transient
    private boolean isNew = true;

    @Override
    public boolean isNew() { return isNew; }

    @PostPersist @PostLoad
    void markNotNew() { this.isNew = false; }
}
```

**두 장치가 각각 하는 일**:

| 장치 | 역할 |
|---|---|
| **`@Transient`** | 이 필드를 **DB에 저장하지 않는다.** 순수한 메모리 상 플래그다 — 컬럼을 추가하지 않고 문제를 푼다 |
| **`@PostPersist`** | 저장된 **직후** 플래그를 내린다 — 이제 이 객체는 DB에 행이 있다 |
| **`@PostLoad`** | 조회된 **직후** 플래그를 내린다 — DB에서 왔으니 새것일 리 없다 |

**초기값이 `true`인 것이 핵심이다.** `new`로 만든 객체는 두 콜백 중 어느 것도 거치지 않았으므로 `isNew()`가 참이다.

```text
new AbstractEntity()   isNew = true   (초기값)
  └ save()  →  isNew() 참  →  persist()  →  @PostPersist  →  isNew = false ✅
                                              여분의 SELECT 없음

find()      →  @PostLoad  →  isNew = false
  └ save()  →  isNew() 거짓 →  merge()   (이미 컨텍스트에 있으니 SELECT 없음)
```

**두 콜백이 정확히 "DB에 행이 생기는 두 경로"를 덮는다** — 내가 저장했거나, DB에서 읽어 왔거나. 그 밖에 행이 생기는 경로는 없다.

**§6의 판단 — 지금 도입할 변경이 아니다.** CosmoRoute의 등록 경로는 아직 건당 처리다. **대량 삽입 경로가 실제로 생기고, 쿼리 수를 측정해 근거가 생겼을 때** 도입한다. 여기서는 **왜 그 선택지가 존재하는지**를 아는 것으로 충분하다.

## Q7. `merge()`로 부분 수정을 하면 데이터가 지워지는 이유

**`merge()`는 넘어온 객체의 모든 필드를 복사한다. 채워지지 않은 필드는 `null`인 채로 복사된다.**

```java
// 화면에서 이름만 받아 만든 객체
Company partial = new Company();
partial.setId(existingId);
partial.setCompanyName("새 이름");
// homepage, contactEmail, primarySourceUrl … 전부 null

companies.save(partial);   // merge → 나머지 컬럼이 전부 null 로 덮인다
```

**`merge()`는 "무엇이 바뀌었는지" 모른다.** 넘어온 객체는 컨텍스트 밖에서 온 것이라 **스냅샷이 없다.** 비교할 원본이 없으니 **"전부 옮긴다"밖에 할 수 있는 게 없다.** `null`이 "안 바꿨다"는 뜻인지 "`null`로 바꿔라"는 뜻인지 구별할 방법이 없다.

**`update`라는 이름을 기대하고 쓰면 데이터가 지워진다.**

**정석 — 조회 → 도메인 메서드 → 더티 체킹**:

```java
@Transactional
public void rename(UUID id, String newName) {
    Company company = repository.findCuratedById(id).orElseThrow();  // 영속 상태
    company.rename(newName);                                          // 필요한 필드만
    // 더티 체킹이 바뀐 것만 알아서 UPDATE
}
```

**이쪽에는 스냅샷이 있다.** 조회 시점의 값과 비교하니 **정말 바뀐 것만** UPDATE에 들어간다.

**추가 이득**: 도메인 규칙을 **엔티티 안에 유지**할 수 있다. `Material.publish()`가 출처 없이는 공개를 거부하는 게이트로 존재할 수 있는 것도 이 방식 덕분이다. **요청 DTO를 그대로 엔티티로 바꿔 `save()`하는 방식은 편해 보이지만 이 함정을 그대로 밟고, 게이트도 우회한다.**

**CosmoRoute의 `CuratedCatalogService`가 조회 → 도메인 메서드 호출 방식을 쓰는 것이 이 정석에 해당한다.**

## Q8. 트랜잭션 밖 수정이 조용히 무시되는데도 테스트가 통과하는 이유

**테스트 메서드에 `@Transactional`이 붙어 있으면 컨텍스트가 살아 있어 더티 체킹이 작동해 버리기 때문이다.**

```java
// 운영 코드 — 트랜잭션 밖
Company company = service.findById(id);   // 트랜잭션은 이 안에서 끝났다
company.rename("새 이름");                 // 준영속 → 아무 일도 안 일어난다
// UPDATE 도 예외도 없다
```

```java
// 테스트
@Test
@Transactional          // ← 이것 때문에
void rename_works() {
    Company company = service.findById(id);   // 테스트의 트랜잭션이 아직 살아 있다
    company.rename("새 이름");                 // 영속 상태 → 더티 체킹 작동 ✅
    assertThat(...).isEqualTo("새 이름");      // 통과한다
}
```

**테스트의 `@Transactional`이 서비스 호출을 감싸면서, 운영에서는 끝났을 컨텍스트가 테스트에서는 살아 있다.** 상태가 준영속이 아니라 **영속**이라 메커니즘이 작동한다.

**이 실패의 성질이 특히 나쁜 이유**:

> **예외가 나면 차라리 낫다. 아무 일도 일어나지 않는 것이 이 실패의 성질이다.**

- **로그가 안 남는다** — 실패한 게 아니라 안 한 것이다
- **테스트가 통과한다** — 위와 같은 이유로
- **운영에서만 실패한다** — 그것도 "저장이 안 된다"는 증상으로만

**어떻게 막는가**:

| 방법 | 무엇을 잡는가 |
|---|---|
| **컨트롤러·응답 변환 계층에서 엔티티를 다루는 것 자체를 의심**(§6) | 준영속 수정이 일어날 자리를 없앤다 |
| 통합 테스트에서 `@Transactional`을 빼고 실제 경계를 재현 | 운영과 같은 상태로 검증한다 |
| `entityManager.contains(entity)`로 확인 | 애매할 때 상태를 직접 판정한다 |

**첫 번째가 근본적이다** — 계층 경계에서 DTO로 바꾸면 준영속 엔티티가 밖으로 나갈 일이 없다.

## Q9. CosmoRoute의 `deleted_at` 갱신이 삭제 상태와 무관한 이유

**`deleted_at`을 채우는 것은 평범한 필드 변경이고, 더티 체킹으로 처리된다. 삭제 상태 전이와는 아무 관계가 없다.**

| | **삭제 상태 (removed)** | **소프트 삭제 (`deleted_at`)** |
|---|---|---|
| 무엇으로 진입 | **`remove()` 호출** | **필드에 값 대입** |
| 어느 메커니즘 | 삭제 예약 → 플러시 때 DELETE | **더티 체킹** → 플러시 때 UPDATE |
| 나가는 SQL | **`DELETE FROM …`** | **`UPDATE … SET deleted_at = ?`** |
| DB 행 | **사라진다** | **남는다** |
| 상태 전이 | 영속 → 삭제 | **영속 → 영속** (전이 없음) |

**CosmoRoute는 물리 삭제 대신 소프트 삭제를 하므로 삭제 상태를 거의 쓰지 않는다.**

**둘을 같은 말로 쓰면 막히는 지점**(§5):

> **"삭제했는데 왜 DELETE 로그가 없지?"**

**로그에는 UPDATE만 있다.** 그게 정상이다 — 애초에 삭제한 적이 없고, 필드 하나를 채웠을 뿐이다.

**거꾸로도 알아 둘 것 — `remove()`도 즉시 삭제가 아니다.** `remove()`를 부르면 엔티티는 삭제 상태가 되지만 **여전히 컨텍스트가 관리하고 있고, DELETE는 플러시 시점에 나간다.** `remove()` 직후 DB를 들여다봐도 **행이 그대로 있다.**

**그래서 "삭제"라는 말이 세 가지를 가리킬 수 있다**:

1. `remove()` 호출 — **예약**
2. 플러시 — **DELETE 발송** (아직 롤백 가능)
3. 커밋 — **확정**

**CosmoRoute의 소프트 삭제는 이 셋 중 어디에도 해당하지 않는다.** 조회 쿼리가 `deletedAt IS NULL`로 거르기 때문에 **삭제처럼 보일 뿐이다.**
