## Q1. `save()` 직후 파생 쿼리가 방금 저장한 행을 찾는 이유

**`existsBy…`가 파생 쿼리 = JPQL이고, `AUTO` 모드에서 JPQL 실행 직전에 자동 플러시가 일어나기 때문이다.**

```text
save(A)                         INSERT 를 큐에 쌓는다. SQL 은 아직 안 나감
existsByNormalizedName(...)     ← 파생 쿼리 = JPQL
                                  실행 직전 자동 플러시 → 큐의 INSERT 가 먼저 나간다
                                → SELECT 는 A 가 이미 들어간 DB 를 본다 → true
throw CuratedCatalogRuleViolation
```

**왜 JPA가 이런 계기를 두는가** — 두지 않으면 **같은 트랜잭션이 자기가 방금 만든 데이터를 못 찾는다.** 성능 문제가 아니라 **논리적 모순**이다.

**자동 플러시가 없었다면 무슨 일이 났을까**:

```text
existsBy… → false (DB에는 아직 없으니까)
save(B)   → 통과
커밋      → DB 유니크 제약 위반 💥
```

**서비스가 던지려던 읽을 수 있는 409(`CuratedCatalogRuleViolation`) 대신, 정체를 알기 어려운 제약 위반 예외가 밖으로 나간다.**

> **자동 플러시는 편의가 아니라 정합성 장치다.**

**주의할 함정**: `save()`를 불렀다고 SQL이 나갔다고 단정하면 이 장면을 **반대로 예측**하게 된다. `save()`는 "지금 DB에 써라"가 아니라 **"영속성 컨텍스트에 등록하라"**는 뜻이다. INSERT가 나간 이유는 `save()`가 아니라 **그다음 줄의 JPQL** 때문이다.

## Q2. 쓰기를 지연해서 얻는 것 세 가지

**즉시 보내면 단순하고 예측 가능하다. 대신 이것들을 잃는다.**

**① 왕복 횟수 — JDBC 배치로 묶을 기회**

원료 하나에 성분 40개를 연결한다. 즉시 보내면 **INSERT 40번 = DB 왕복 40번**이다. 모아 두면 한 번에 보내 JDBC 배치로 묶을 수 있다. 네트워크 지연이 왕복당 1ms만 돼도 40ms 차이다.

**② 중복 UPDATE 제거**

한 메서드 안에서 같은 엔티티의 필드를 세 군데서 고친다. 즉시 보내면 **UPDATE 3번**. 모아 두면 **최종 상태 하나**만 보내면 된다. 중간 상태는 어차피 아무도 못 본다.

**③ 제약을 지키는 순서**

회사를 만들고 그 회사에 속한 원료를 만든다. **INSERT 순서가 뒤집히면 외래 키 제약에 걸린다.** 애플리케이션 코드의 호출 순서와 DB가 요구하는 순서가 **항상 같지는 않다.** 모아 두면 Hibernate가 타입별로 순서를 정해 내보낸다.

**④ (덤) 롤백 비용** — 즉시 보내면 취소할 것도 그만큼 많아진다.

**Hibernate 공식 문서는 영속성 컨텍스트를 아예 *"트랜잭션 단위의 write-behind 캐시"*라고 정의한다** — 쓰기 지연이 부가 기능이 아니라 정의의 일부라는 뜻이다.

**세 번째가 나머지와 성격이 다르다** — ①②는 성능이지만 ③은 **정확성**이다. 순서를 잘못 보내면 느린 게 아니라 **터진다.**

## Q3. 플러시와 커밋을 구분하는 판별 질문

> **"지금 롤백하면 없던 일이 되는가?"**

**답이 "예"면 플러시까지만 한 것이고, "아니오"면 커밋된 것이다.**

| 축 | **플러시** | **커밋** |
|---|---|---|
| 무엇을 하나 | 쌓인 변화를 SQL로 번역해 DB로 **보낸다** | 그때까지 보낸 것을 **확정한다** |
| 되돌릴 수 있나 | **있다** — 롤백하면 보낸 SQL도 취소 | **없다** |
| 다른 트랜잭션에 보이나 | **안 보인다** (격리 수준에 따름) | **보인다** |
| 영속성 컨텍스트는 | **그대로 유지** | 닫히고 1차 캐시가 사라짐 |

**한 방향으로만 함의가 성립한다**:

- **커밋은 항상 플러시를 동반한다** — 보내지 않은 변화를 확정할 방법이 없다
- **플러시는 커밋을 동반하지 않는다** — `flush()`를 불러도 확정된 게 아니다

**그래서 `saveAndFlush()`라는 이름이 오해를 부른다** — "저장 완료"처럼 읽히지만 **트랜잭션을 끝내지 않는다.** 여전히 롤백 가능한 상태다.

**실무에서 이 구분이 필요해지는 순간**: 통합 테스트에서 `saveAndFlush()`까지 하고 "DB에 들어갔다"고 판단했는데, 테스트 트랜잭션이 롤백되며 아무것도 남지 않는다. 판별 질문을 쓰면 예측된다.

## Q4. `FlushModeType.COMMIT`에서 출발 장면이 잘못 도는 방식

**`COMMIT` 모드는 플러시 계기 3개 중 2번(JPQL 실행 직전)을 없앤다.** 쿼리를 아무리 날려도 **커밋 전까지 플러시하지 않는다.**

```java
entityManager.setFlushMode(FlushModeType.COMMIT);
```

**그러면 출발 장면은 이렇게 된다**:

```text
save(A)                         INSERT 를 큐에 쌓는다
existsByNormalizedName(...)     플러시 안 함 → DB 는 A 를 모른다 → false ❌
save(B)                         통과 — 예외가 안 난다
커밋                            A, B INSERT 가 함께 나감
                                → DB 유니크 제약 위반 💥
```

**세 겹으로 나쁘다**:

1. **의도한 예외가 안 나간다.** `CuratedCatalogRuleViolation`(읽을 수 있는 409)이 아니라 `DataIntegrityViolationException`이 나간다.
2. **터지는 위치가 원인에서 멀다.** 중복 검사 줄이 아니라 **커밋 시점**에 터진다. 스택 트레이스에 `existsBy…`가 없다.
3. **조용히 틀린다.** 컴파일도 되고 대부분의 경로에서는 정상이다. **같은 트랜잭션 안에서 쓰기와 조건 검사가 섞이는 경로**에서만 어긋난다.

**얻는 것**: 쿼리마다 플러시 여부를 판정하는 비용이 사라져 **조회가 많은 경로**가 빨라질 수 있다.

**경계** — CosmoRoute처럼 **서비스 계층 사전 검사와 DB 제약이 짝을 이루는 설계**에서는 특히 위험하다. 사전 검사가 무력화되면 남는 건 DB 제약뿐이고, 그건 사용자에게 보여 줄 메시지를 만들지 못한다.

## Q5. `COMMIT` 모드에서 JPQL과 네이티브 SQL이 갈리는 이유

**Hibernate가 그 쿼리의 영향 범위를 판정할 수 있느냐가 갈림길이다.**

Hibernate 문서의 명시: `COMMIT` 모드에서 *"JPQL 쿼리를 실행할 때는 커밋 시점에만 플러시하지만, **네이티브 SQL 쿼리를 실행할 때는 플러시한다**"*.

| | JPQL | 네이티브 SQL |
|---|---|---|
| Hibernate가 아는 것 | **엔티티 모델을 파싱**해 어느 테이블·컬럼을 건드리는지 안다 | **불투명한 문자열**이다 |
| `COMMIT` 모드에서 | 플러시 안 함 | **플러시함** |
| 판단 근거 | "개발자가 `COMMIT`을 골랐고, 나는 위험 범위를 안다" | **"모르니까 안전한 쪽"** |

**네이티브 SQL은 뭐든 할 수 있다** — 조인, 서브쿼리, 뷰, 함수, 다른 스키마. Hibernate는 그 문자열이 어느 테이블을 읽는지 파싱하지 않는다. 그래서 **큐에 쌓인 변경이 그 쿼리 결과에 영향을 줄지 판정할 수 없고**, 판정할 수 없으면 **보수적으로 플러시**한다.

**실무적 함의 — 모드 하나로 전체 동작을 예측하면 어긋난다.**

```text
"COMMIT 모드로 바꿔서 조회 성능을 올렸다"
  → 그런데 리포트 쿼리 몇 개가 @Query(nativeQuery = true) 였다
  → 그것들은 여전히 플러시를 유발한다
  → 기대한 성능 개선이 안 나오고, 어디서 새는지 안 보인다
```

**거꾸로도 위험하다** — `COMMIT` 모드를 믿고 "플러시는 커밋에만 일어난다"고 가정한 코드가, 네이티브 쿼리가 하나 끼어드는 순간 예상 밖 시점에 SQL을 내보낸다.

## Q6. `IDENTITY`가 쓰기 지연을 무너뜨리는 이유 — "식별자를 언제 아는가"

**순환 의존이 생긴다.**

```text
영속성 컨텍스트에 넣으려면  →  식별자가 있어야 한다
                              (1차 캐시가 (타입, 식별자) 맵이니까)
식별자를 알려면            →  INSERT 를 보내야 한다
                              (auto-increment 값은 DB 가 만든다)
──────────────────────────────────────────────────────
따라서 persist() 시점에 INSERT 가 즉시 나간다. 지연할 수가 없다.
```

**전략별 비교**:

| 전략 | 식별자를 아는 시점 | 지연 가능? |
|---|---|---|
| **`IDENTITY`** | **INSERT 이후** (DB가 만든다) | **불가능** — `persist()`에서 즉시 INSERT |
| **`SEQUENCE`·`TABLE`** | INSERT와 **별개로 미리** 받아 온다 | 가능 — INSERT는 커밋까지 지연 |
| **애플리케이션 직접 할당** | **객체를 만들 때** | 온전히 가능 |

**Hibernate 문서가 커밋 시 자동 플러시 예제에 *"SEQUENCE와 TABLE 생성기에 유효하다"*고 단서를 단 이유가 이것이다** — `IDENTITY`에서는 그 예제가 성립하지 않는다.

**CosmoRoute는 세 번째다**:

```java
@Id
@Column(name = "id", nullable = false, updatable = false)
private UUID id;                       // @GeneratedValue 가 없다

static Company curated(String companyName, String normalizedName, UUID curatedByUserId) {
    Company company = new Company();
    company.id = UUID.randomUUID();    // 애플리케이션이 식별자를 만든다
    ...
}
```

스키마의 `DEFAULT gen_random_uuid()`는 **JPA를 거치지 않는 경로용 안전망**이고, 애플리케이션 경로에서는 항상 값이 먼저 정해진다.

**그래서 이 프로젝트는** INSERT를 커밋 직전까지 미룰 수 있고 배치로 묶을 여지도 남는다. **`IDENTITY`를 골랐다면 이 여지가 통째로 없었다.**

**대가도 있다** — 식별자를 직접 할당하면 Spring Data가 **"이 엔티티는 새것인가"**를 판정하는 방식이 달라진다. `isNew()`가 `id == null`을 보는데 id가 항상 있으니 거짓이 되고, `save()`가 `persist()` 대신 `merge()`를 타면서 **불필요한 SELECT가 늘어난다.** 자세한 것은 [[04-entity-lifecycle-and-detachment]].

## Q7. `flush()`만 부르고 `clear()`를 안 부르면 남는 것

**SQL은 나가지만 1차 캐시와 스냅샷은 그대로 쌓인다.**

```text
10만 건 INSERT 루프

[flush() 만]
  큐:        비워짐 ✅
  1차 캐시:  10만 건 그대로 ❌
  스냅샷:    10만 건 그대로 ❌
  → 메모리는 계속 증가. OOM 은 그대로 온다.
  → 게다가 플러시마다 10만 건을 더티 체킹 대상으로 훑는다.

[flush() + clear()]
  큐:        비워짐 ✅
  1차 캐시:  비워짐 ✅
  스냅샷:    비워짐 ✅
  → 메모리가 톱니 모양으로 유지된다.
```

**둘의 역할이 다르다**:

| | 무엇을 비우나 |
|---|---|
| **`flush()`** | **쓰기 지연 큐** — 쌓인 변경을 SQL로 내보낸다 |
| **`clear()`** | **영속성 컨텍스트** — 1차 캐시와 스냅샷을 통째로 비운다 |

**"flush 했으니 정리됐다"는 흔한 오해다.** 플러시는 **보내는** 것이지 **버리는** 것이 아니다. 보낸 뒤에도 그 엔티티는 여전히 영속 상태이고, 여전히 더티 체킹 대상이다.

**부작용 하나 더** — `clear()`를 부르면 그때까지 들고 있던 참조는 **전부 준영속**이 된다. 루프 밖에서 그 객체를 계속 쓰고 있었다면 **지연 로딩이 깨진다.** 그래서 `clear()`는 "이 배치에서 다 쓴 시점"에 불러야 한다.

**권장 형태**:

```java
for (int i = 0; i < items.size(); i++) {
    em.persist(items.get(i));
    if (i % 500 == 0) {          // 배치 크기에 맞춘다
        em.flush();
        em.clear();
    }
}
```

## Q8. `saveAndFlush()` 뒤에 예외가 나면 데이터는 어떻게 되나

**롤백된다. 아무것도 남지 않는다.**

**`saveAndFlush()`는 `save()` 뒤에 `flush()`를 이어 부르는 것뿐이다. 트랜잭션을 끝내지 않는다.**

```text
saveAndFlush(A)      INSERT 가 DB 로 나간다 — 하지만 트랜잭션 안이다
… 예외 발생 …
롤백                 그 INSERT 도 함께 취소된다
                     → DB 에 A 는 없다
```

**Q3의 판별 질문을 그대로 적용하면 된다** — "지금 롤백하면 없던 일이 되는가?" **예.** 그러니 플러시까지만 한 것이다.

**이름이 만드는 오해**: `saveAndFlush`는 "저장하고 확실히 밀어 넣었다"처럼 읽힌다. 그래서 **"이건 이미 DB에 있으니 안전하다"**고 착각하기 쉽다. 실제로는 **커밋 전 어느 시점에서든 통째로 사라질 수 있다.**

**그럼 왜 쓰는가 — 두 가지 목적이 있다**:

| 목적 | 왜 플러시가 필요한가 |
|---|---|
| **제약 위반을 이 자리에서 확인** | 커밋까지 미루면 예외 발생 위치가 원인에서 멀어진다 |
| **DB가 생성한 값을 즉시 읽기** | 시퀀스·트리거·`DEFAULT`가 채운 값은 INSERT 후에야 안다 |

**두 목적 모두 "확정"과는 무관하다** — 확정이 아니라 **시점을 앞당기는** 것이다.

**습관적으로 부르면 안 되는 이유**(§6): 배치로 묶을 기회를 없애고, **트랜잭션이 락을 잡는 구간을 앞당겨 길게 만든다.** 구체적 이유가 있을 때만 부른다.
