## Q1. `save()` 없이 UPDATE가 나가는 과정 — 스냅샷부터 플러시까지

**일곱 단계다.**

1. **조회 시점에 값을 복사한다.** 엔티티가 영속 상태가 되는 순간, 1차 캐시에 인스턴스를 넣으면서 **필드 값을 별도로 한 벌 더** 보관한다 — 나중에 비교할 원본이 필요하니까.
2. **애플리케이션이 필드를 바꾼다.** `material.publish(...)`가 `publishedAt`을 채운다. **이 시점에 JPA는 아무것도 하지 않는다** — 엔티티는 평범한 자바 객체라 값이 바뀌었다고 알려 줄 방법이 없다.
3. **플러시가 시작된다.** 커밋 직전이거나 쿼리 실행 직전.
4. **영속 상태 엔티티를 전부 순회한다** — 어느 것이 바뀌었는지는 비교해 보기 전엔 모른다. **여기서 "전부"가 비용의 근원이다.**
5. **각 엔티티의 현재 값과 스냅샷을 필드 단위로 비교한다.**
6. **달라진 것이 있으면 UPDATE를 만들어 쓰기 지연 큐에 넣는다** — 실제 전송은 플러시가 한다.
7. **UPDATE를 보낸 뒤 스냅샷을 현재 값으로 갱신한다** — 같은 트랜잭션에서 다시 플러시할 때 이미 반영한 변경을 또 보내지 않으려고.

**`save()`가 어디에도 없다.** 2번에서 필드를 바꾼 것이 곧 **"저장 요청"**이고, 4~6번이 그것을 SQL로 번역한다.

**여기서 나오는 불안한 질문이 정답이다** — "그럼 조회만 하고 필드를 만졌을 때도 나가는 것 아닌가?" **실제로 나간다.** 그래서 이건 편의 기능이 아니라 **반드시 이해하고 다뤄야 하는 동작**이다.

## Q2. setter 가로채기 대신 스냅샷 비교를 택해서 얻은 것

**엔티티가 평범한 자바 객체로 남는다.**

**택하지 않은 세 가지 길과 그 대가**:

| 길 | 대가 |
|---|---|
| **개발자가 매번 `save()`** | 한 번만 잊으면 데이터가 조용히 사라진다. 그리고 "무엇을 바꿨는지"는 여전히 모르니 결국 **모든 컬럼을 덮어쓴다** |
| **모든 setter 가로채기** | 정확하지만 엔티티가 평범한 객체가 아니게 된다 — **프록시로 감싸거나 바이트코드를 조작**해야 하고, `final` 필드·**생성자 기반 불변 객체와 잘 맞지 않는다** |
| **무조건 전부 UPDATE** | 비교 비용은 없지만 DB 쓰기가 폭증하고, **아무도 손대지 않은 행까지 락이 걸린다** |

**JPA가 고른 네 번째 길 — 조회하는 순간 값을 한 벌 복사해 두고 나중에 비교한다.**

**이 선택이 무엇을 가능하게 했는가**:

```java
// Material 은 JPA 를 위해
//   - 아무 인터페이스도 구현하지 않고
//   - 어떤 프레임워크 타입도 상속하지 않는다
public void publish(Instant now) {
    // 순수한 도메인 규칙
}
```

**CosmoRoute의 `Material.publish()`가 도메인 규칙을 담은 순수한 메서드로 존재할 수 있는 것이 이 덕분이다.** setter 가로채기를 택했다면 도메인 메서드가 프레임워크의 감시 대상이 되어야 했고, 불변 객체 스타일도 포기해야 했다.

**대가는 미룬 것이지 없앤 것이 아니다** — 언제 바뀌었는지 모르니 **플러시마다 전부 훑어야 한다.** 그게 Q5의 비용이다.

**비유와 그 한계**: **입장할 때 사진을 한 장 찍어 두는 것**. 나갈 때 대조해 달라진 곳을 찾는다. → **깨지는 지점**: 사진 대조는 사람이 필요할 때 눈으로 훑는 일이지만, JPA는 **플러시마다 영속 엔티티 전부를 자동으로 훑는다.** 하나만 고쳐도 200건이 담겨 있으면 200건을 비교한다.

## Q3. 기본 UPDATE에 바뀌지 않은 컬럼까지 들어가는 이유

**Hibernate가 부트스트랩 시점에 엔티티마다 UPDATE 문을 미리 하나 만들어 두고 재사용하기 때문이다.**

공식 문서: *"Hibernate는 부트스트랩 시점에 엔티티마다 **정적(static) INSERT·UPDATE 문**을 생성한다. 그래서 수정되지 않은 속성도 UPDATE에 포함된다."*

**왜 그 설계인가 — 만들지 않았을 때의 비용을 보면 된다**:

```text
컬럼이 10개인 엔티티에서 "바뀐 컬럼만" 쓰려면
  → 바뀐 조합마다 다른 SQL 문자열
  → 최악 2^10 = 1024 가지
  → 매번 문자열을 만들고
  → DB 의 실행 계획 캐시도 그만큼 갈라진다
```

**즉 "필요한 만큼만 쓴다"의 대가가 SQL 생성 비용과 계획 캐시 파편화다.** 정적 문 하나를 재사용하면 둘 다 없다.

**바꾸고 싶으면 `@DynamicUpdate`**:

```java
@Entity
@DynamicUpdate
public class Material { ... }
```

→ `UPDATE material SET published_at = ? WHERE id = ?`처럼 **바뀐 컬럼만** 나간다.

**단, 공식 문서가 곧바로 경고를 단다** — 그 내용이 Q4다.

## Q4. `@DynamicUpdate`를 `@Version` 없이 쓰면 무엇이 잘못되나

**어느 시점에도 존재한 적 없는 컬럼 조합이 만들어질 수 있다.**

공식 문서: *"엔티티에 version 속성이 없으면 `@DynamicUpdate`는 **컬럼 값의 불일치**를 낳을 수 있다. 동시에 실행되는 트랜잭션들이 같은 엔티티를 **선택적으로** 갱신할 수 있기 때문이다."*

**시나리오 — 관리자 두 명이 같은 원료를 동시에 연다. 한 명은 이름만, 한 명은 공개 여부만 바꾼다.**

```text
초기 상태:  name="구",  published=false

[기본 동작 — 모든 컬럼 UPDATE]
  A: SET name="신",  published=false   (자기가 읽은 값 전부)
  B: SET name="구",  published=true
  나중에 커밋한 B 가 이김
  결과: name="구", published=true
  → A 의 변경은 사라졌다. 하지만 이것은 "B 가 화면에서 본 그 상태"다.
     어느 한 시점에 실제로 존재했던 조합이다. ✅

[@DynamicUpdate — 바뀐 컬럼만]
  A: SET name="신"                     (published 는 안 건드림)
  B: SET published=true                (name 은 안 건드림)
  둘 다 성공
  결과: name="신", published=true
  → 이 조합은 A 도 B 도 본 적이 없다. ❌
```

**결정적 차이**:

| | 기본 동작 | `@DynamicUpdate` (버전 없이) |
|---|---|---|
| 무엇을 잃나 | **한쪽의 변경 전체** | 잃는 건 없는데 |
| 남는 상태 | **일관된 한 시점의 상태** | **존재한 적 없는 조합** |
| 진단 가능성 | "덮어썼구나" — 이해된다 | **왜 이런 값이 됐는지 설명이 안 된다** |

**둘 다 문제지만 성격이 다르다.** 기본 동작의 lost update는 **정상적인 동시성 문제**이고 낙관적 락으로 감지할 수 있다. `@DynamicUpdate`의 조합 오염은 **각 UPDATE가 개별적으로는 모두 성공**해서, 락 없이는 감지할 대상 자체가 없다.

**그래서 순서가 정해진다**: `@DynamicUpdate`는 **낙관적 락(`@Version`)과 짝을 이뤄야** 안전하다. 버전이 있으면 B의 UPDATE가 `WHERE version = ?`에서 걸려 실패한다.

**CosmoRoute의 현재 상태**: 엔티티에 아직 `@Version`이 없다. **지금 `@DynamicUpdate`를 붙이면 이 위험을 그대로 떠안는다.**

## Q5. 조회만 하는 트랜잭션에서도 비용이 발생하는 이유

**두 가지 — 메모리와 비교 연산이다. 그리고 세 번째로 위험이 있다.**

```java
@Query("SELECT c FROM Company c WHERE " + CatalogVisibility.SUPPLIER_COMPANY
        + " ORDER BY c.companyName ASC")
List<Company> findSupplierCompanies();     // 200건 반환
```

```text
영속성 컨텍스트에 남는 것
  1차 캐시    Company 인스턴스 200개      ← 동일성 보장용
  스냅샷      Company 필드값 사본 200벌   ← 변경 감지용
```

**① 메모리가 두 배로 든다.** 엔티티 하나를 읽을 때마다 인스턴스와 값 사본이 **함께** 만들어진다. 조회 전용 화면이어도 예외가 없다.

**② 플러시마다 200건 × 필드 수만큼 비교가 돈다.** 그리고 플러시는 **JPQL 실행 직전마다** 일어날 수 있으므로, 같은 트랜잭션에서 조회를 여러 번 하면 그때마다 반복된다.

> **조회만 하는 화면인데 그렇다. 아무것도 고칠 생각이 없어도 비용은 그대로 발생한다.**

**③ (비용은 아니지만 더 무서운 것) 위험이 함께 생긴다**

누군가 조회 결과의 엔티티를 **응답 변환 과정에서 무심코 손대면** 의도하지 않은 UPDATE가 나간다.

```java
// DTO 변환 중 "정규화" 한다고 필드를 만졌다
companies.forEach(c -> c.trimName());   // 조회 API 인데 UPDATE 가 나간다
```

**이 사고는 원인을 찾기 어렵다 — 코드 어디에도 `save()`가 없기 때문이다.** 로그에 UPDATE가 찍히는데 그걸 만든 줄이 없다.

**그래서 §6의 판단이 나온다**: 조회 전용 경로에 더티 체킹을 켜 둘 이유가 없고, **비용을 줄이는 것보다 의도치 않은 UPDATE를 구조적으로 막는 것이 더 큰 이득**이다.

## Q6. `@Transactional(readOnly = true)`가 더티 체킹을 끄는 메커니즘

**플러시 모드를 `MANUAL`로 낮춰 자동 플러시를 없앤다. 더티 체킹은 플러시 안에서 도는 것이므로 함께 멈춘다.**

```text
readOnly = true
  → Hibernate 가 FlushMode 를 MANUAL 로 낮춘다
  → 커밋 직전에도, JPQL 실행 직전에도 자동 플러시가 안 일어난다
  → 플러시가 없으니 스냅샷 순회·비교도 안 돈다
  → 실수로 필드를 만져도 UPDATE 가 나가지 않는다
```

**핵심은 "더티 체킹을 끄는 스위치"가 따로 있는 게 아니라는 점이다.** §5의 정리대로:

> **더티 체킹은 무엇을 보낼지 결정하고, 플러시는 보낸다. 플러시가 시작되면서 더티 체킹이 그 안에서 돌아간다.**

그래서 **"플러시가 안 일어나면 더티 체킹도 안 돌아간다"**가 성립하고, `readOnly = true`가 더티 체킹을 끄는 방식이 정확히 이것이다.

**주의 — DB 수준의 읽기 전용이 아니다**:

| 막는 것 | 못 막는 것 |
|---|---|
| 자동 플러시로 인한 UPDATE | **네이티브 쿼리로 직접 쓰기** |
| 실수로 만진 필드의 반영 | **명시적 `flush()` 호출** |

**"쓰기가 불가능해진다"고 이해하면 과신이다.** 안전장치이자 최적화지 **봉인은 아니다.** DB 커넥션을 읽기 전용으로 바꾸는지도 드라이버와 설정에 따라 다르다.

**더 근본적인 두 번째 방법 — 애초에 엔티티로 조회하지 않는다**:

```java
@Query("SELECT new com.cosmoroute.api.catalog.CompanySummary(c.id, c.companyName, c.homepage)"
        + " FROM Company c WHERE ...")
List<CompanySummary> findSupplierSummaries();
```

**영속성 컨텍스트에 아무것도 담기지 않는다. 1차 캐시도 스냅샷도 생기지 않는다.** 목록 화면처럼 "읽고 그대로 내보내는" 경로에는 이쪽이 더 정직하다 — **관리할 이유가 없는 객체를 관리 대상으로 만들지 않는 것.**

## Q7. 영속 상태 엔티티에 `save()`를 부르는 코드를 지워도 되는 이유

**영속 상태에서는 `save()`가 아무 효과도 없기 때문이다. 틀리지는 않지만 하는 일이 없다.**

| 축 | **더티 체킹** | **`save()`** |
|---|---|---|
| 대상 | **이미 영속 상태**인 엔티티 | **비영속·준영속** 엔티티 |
| 호출 필요 | **없다** — 필드를 바꾸면 끝 | 명시적으로 불러야 한다 |
| 언제 SQL이 되나 | 플러시 시점 | 마찬가지로 플러시 시점 |
| 안 부르면 | **그래도 반영된다** | 아무 일도 안 일어난다 |

**Spring Data의 `save()`가 영속 엔티티에 하는 일**: `isNew()`가 거짓이므로 `merge()`를 부른다. 그런데 **넘긴 객체가 이미 그 컨텍스트의 관리 대상**이라, `merge()`는 1차 캐시에서 같은 인스턴스를 찾아 **그대로 돌려준다.** 복사할 것도, 새로 등록할 것도 없다.

**그래서 이 두 코드는 같은 SQL을 만든다**:

```java
Material m = repository.findById(id).orElseThrow();
m.publish(now);
repository.save(m);     // ← 지워도 결과가 같다
```

**그 사실을 설명할 수 있어야 이 절을 이해한 것이다**(§5).

**다만 "지워도 된다"가 "지워야 한다"는 아니다** — 팀에 따라 의도를 드러내려고 남기기도 한다. 위험한 건 반대 방향이다: **`save()`를 불렀다는 이유로 "이제 저장됐다"고 믿는 것.** 실제로는 플러시 전까지 아무것도 나가지 않았고, `save()`를 안 불러도 나갔을 것이다.

**정말 조심해야 할 경우**: 엔티티가 **준영속**이면 이야기가 완전히 달라진다. 그때는 `save()`가 필수이고, 게다가 `merge()`의 반환값을 써야 한다 — [[04-entity-lifecycle-and-detachment]].

## Q8. 목록 조회를 DTO로 바꾸면 영속성 컨텍스트에서 사라지는 것

**전부 사라진다 — 애초에 담기지 않는다.**

```text
[엔티티로 조회]                      [DTO 로 조회]
 영속성 컨텍스트                      영속성 컨텍스트
 ┌────────────────────────┐          ┌────────────────────────┐
 │ 1차 캐시  200 인스턴스 │          │        (비어 있음)     │
 │ 스냅샷    200 값 사본  │          │                        │
 └────────────────────────┘          └────────────────────────┘
```

**구체적으로 사라지는 것 네 가지**:

| 사라지는 것 | 그래서 없어지는 것 |
|---|---|
| **1차 캐시 엔트리** | 메모리 절반 |
| **스냅샷** | 메모리 나머지 절반 + 플러시마다의 비교 연산 |
| **더티 체킹 대상** | **의도치 않은 UPDATE의 가능성** |
| **지연 로딩 가능성** | 프록시가 없으니 N+1도 없다 |

**세 번째가 이 선택의 진짜 값이다.** `readOnly = true`는 **자동 플러시를 막는** 방식이라 네이티브 쿼리나 명시적 `flush()`로 뚫린다. DTO 조회는 **쓸 대상 자체가 없다** — 뚫릴 구멍이 없다.

**함께 잃는 것도 있다**:

- **동일성 보장이 없다.** 같은 회사가 두 행에 나오면 서로 다른 DTO 인스턴스다. `==`로 비교하는 코드가 있으면 깨진다.
- **연관을 따라갈 수 없다.** `company.getMaterials()`가 없다. 필요한 것을 **쿼리에서 전부 지정**해야 한다.
- **쿼리와 DTO 생성자가 결합된다.** `new com.…CompanySummary(...)`의 인자 순서·타입이 생성자와 정확히 맞아야 하고, 어긋나면 **런타임에** 터진다.

**CosmoRoute가 `CompanySummary`·`MaterialSummary`를 모듈의 공개 타입으로 따로 둔 것은 모듈 경계를 위한 설계지만, 이 관점에서도 이득이 있다** — 경계용으로 만든 타입이 성능·안전성까지 함께 가져온 경우다.
