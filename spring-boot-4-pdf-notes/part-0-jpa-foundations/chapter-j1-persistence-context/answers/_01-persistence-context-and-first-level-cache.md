## Q1. 같은 식별자를 두 번 조회했을 때 `a == b`가 참인 이유

**1차 캐시가 `(타입, 식별자) → 인스턴스` 맵이고, 조회 경로가 무엇이든 반환 직전에 이 맵을 거치기 때문이다.**

```text
findCuratedById(id) 1회차   캐시 없음 → 인스턴스 생성 → 캐시 저장 → 반환   ┐
                                                                          ├ 같은 화살표
findCuratedById(id) 2회차   캐시 있음 → 캐시 인스턴스 반환                ┘
```

**두 번째 조회가 새 객체를 만들 기회가 없다** — 만들기 전에 캐시를 보고, 있으면 거기서 멈춘다.

**이 성질의 이름이 **동일성 보장**이다** — 같은 트랜잭션 안에서 같은 식별자로 조회하면 `==`가 참.

**왜 이게 필요한가 — 없으면 "어느 쪽이 진실인가"를 판정할 수 없다**:

```text
[컨텍스트가 없는 세계]
  a = SELECT … id=1  →  Company@1a2b
  b = SELECT … id=1  →  Company@3c4d
  a.rename("신")

  커밋 시점에 DB에 쓸 값은?
    Company@1a2b 는 name="신" 이라 주장
    Company@3c4d 는 name="구" 라 주장
  → 같은 행에 두 개의 진실. 판정 규칙이 없다.
```

**출발 장면의 답도 여기서 나온다** — `b`를 건드리지 않았는데 `b.getCompanyName()`이 새 이름인 이유는 **`b`가 `a`이기 때문**이다. "값이 전파됐다"가 아니라 "애초에 하나였다".

**노트가 지적하는 흔한 오답**: "1차 캐시가 있으니까 쿼리가 한 번만 나간다" — 이건 `find()`에서만 맞다. 출발 장면은 JPQL이라 **SELECT가 두 번 나간다.** 그래도 `a == b`다.

## Q2. `find()`와 JPQL이 캐시를 만나는 단계

**둘 다 캐시를 거치지만, 거치는 지점이 SQL의 앞이냐 뒤냐가 다르다.**

| | **`find()`** | **JPQL** |
|---|---|---|
| 캐시를 만나는 시점 | **SQL을 보내기 전** | **결과 행을 엔티티로 만들기 전** |
| 캐시에 있으면 | **SQL이 아예 안 나간다** | **SQL은 나가고, 읽어 온 행을 버린다** |
| 왜 그런가 | `(타입, 식별자)`가 곧 조회 조건이라 캐시만으로 답할 수 있다 | WHERE 조건 평가는 **DB만** 할 수 있다 |

**JPQL이 캐시를 조회 조건으로 못 쓰는 이유** — CosmoRoute의 쿼리를 보면 분명하다:

```java
@Query("SELECT c FROM Company c WHERE c.id = :id"
        + " AND c.origin = CompanyOrigin.OPERATOR_CURATED AND c.deletedAt IS NULL")
Optional<Company> findCuratedById(UUID id);
```

**1차 캐시는 식별자로 색인된 맵일 뿐이다.** `origin`이나 `deletedAt`으로 필터링하는 기능이 없다. 그 조건을 평가할 수 있는 건 DB뿐이라 **캐시에 뭐가 있든 SQL은 나간다.**

**JPQL의 5단계**:

1. JPQL → SQL 번역 후 DB로 나감 — 조건 평가는 DB만 가능
2. 결과 행마다 `(타입, 식별자)` 키를 만든다 — 이미 컨텍스트에 있는지 판정하려면 키가 필요
3. 그 키로 1차 캐시 조회 — 동일성 보장을 지키려고
4. **있으면 읽어 온 행 데이터를 버리고 캐시 인스턴스 반환**
5. 없으면 새 인스턴스를 만들어 캐시에 넣고 반환

**Hibernate 소스의 근거** — `StatefulPersistenceContext.getEntity(EntityKey)`의 주석: *"이미 관리 중이면 그 인스턴스를 반환한다. 같은 DB 행에 같은 자바 동일성이 쓰이도록 보장하기 위해서다."*

**결론**: 경로는 다르지만 **반환 직전에 캐시를 통과한다는 점이 같아서** 결과 인스턴스가 같다.

## Q3. 읽어 온 행을 버리는 이유 — 버리지 않으면 무엇이 깨지나

**버리지 않으면 이 트랜잭션에서 만든 변경이 사라진다.**

```text
a = findCuratedById(id)      → name="구"  (캐시 인스턴스 A)
a.rename("신")               → 캐시 안의 A.name = "신"
                                (아직 DB에는 안 나갔다 — 쓰기 지연)
b = findCuratedById(id)      → SELECT 나감 → DB는 여전히 name="구"

  [버린다]     A 를 그대로 반환 → b.name = "신"  ✅ 내 변경이 살아 있다
  [덮어쓴다]   A.name = "구" 로 갱신 → b.name = "구"  ❌ rename 이 증발
```

**핵심은 "DB가 옛날 값을 들고 있다"는 것이다.** 쓰기 지연 때문에 `a.rename()`은 아직 DB에 반영되지 않았다. 그 상태에서 DB를 읽으면 **내 변경 이전의 값**이 온다. 그걸로 덮어쓰면 조용히 되돌린 것이다.

**그리고 `a == b`이므로 되돌아가는 건 `b`만이 아니다** — `a`도 함께 옛 이름이 된다. 코드에는 되돌리는 줄이 없는데 값이 되돌아간다.

**노트의 한 줄 요약**:

> **정확성이 최신성을 이긴다.**

**대가**: 1차 캐시는 **DB 변화를 모른다.** 다른 트랜잭션이 그 행을 바꿔도 캐시 인스턴스는 옛 값을 들고 있다. 최신 값이 꼭 필요하면 **`refresh()`를 부르거나 락을 잡아야 한다.**

**이 대가가 왜 받아들일 만한가** — 최신성이 필요한 경우는 명시적으로 요청할 수 있지만(`refresh()`), 잃어버린 변경은 **되찾을 방법이 없다.** 기본값은 복구 불가능한 쪽을 막는 방향으로 정해진 것이다.

## Q4. 1차 캐시를 끄는 설정이 없는 이유

**끄면 JPA의 다른 기능들이 성립하지 않기 때문이다. 1차 캐시는 최적화가 아니라 전제다.**

| | 1차 캐시 | 2차 캐시 |
|---|---|---|
| **주 목적** | **동일성 보장** | 왕복 감소 |
| 켜고 끄기 | **끌 수 없다** | 기본 꺼짐, 명시적으로 켠다 |

**"본업이 캐싱이 아니다"를 풀어 쓰면**:

성능 장치라면 끄는 선택지가 있어야 한다. 메모리가 아쉬우면 끄고 왕복을 감수하면 되니까. **그런데 1차 캐시를 끄면 잃는 게 성능이 아니다**:

1. **동일성 보장이 사라진다** — `a == b`가 거짓이 되고, `Set`에 같은 회사가 두 번 들어간다
2. **더티 체킹이 불가능해진다** — 무엇을 감시할지 담아 둔 곳이 없다
3. **쓰기 지연이 불가능해진다** — 모아 둘 곳이 없다
4. **"어느 쪽이 진실인가" 문제가 되살아난다** — §1이 진단한 그 정확성 문제

**즉 캐시를 끄는 스위치는 "JPA를 끄는 스위치"에 가깝다.**

**캐싱 효과가 부수적이라는 증거 — 수명이 너무 짧다**:

```text
@Transactional 진입   → 컨텍스트 생성
메서드 실행           → 엔티티가 쌓임
커밋 직전             → 변경분 flush
컨텍스트 종료         → 1차 캐시 통째로 사라짐
```

**트랜잭션 하나 안에서, 같은 엔티티를 여러 번 만질 때만** 왕복이 준다. 진짜 캐시라면 이렇게 짧게 살지 않는다. 그리고 짧게 사는 게 **의도**다 — 다음 트랜잭션이 옛 데이터를 최신인 양 쓰는 걸 막아야 하니까.

**이름도 그 사실을 담고 있다** — "영속성 컨텍스트"는 *영속(persistent) 상태인 객체들이 사는 문맥(context)*이다. 안에 있으면 영속, 밖으로 나가면 아니다. **캐시라는 말이 이름에 없다.**

## Q5. 1차 캐시와 2차 캐시 — 범위·목적·수명

| 축 | **1차 캐시** | **2차 캐시** |
|---|---|---|
| **범위** | 영속성 컨텍스트 하나 = **트랜잭션 하나** | **`EntityManagerFactory` 단위**, 여러 트랜잭션이 공유 |
| **목적** | **동일성 보장** | **왕복 감소** |
| **수명** | 트랜잭션 종료와 함께 사라짐 | **만료 정책·명시적 무효화**까지 유지 |
| 켜고 끄기 | 끌 수 없다 (JPA의 전제) | 기본 꺼짐, 명시적으로 켠다 |

**세 축이 서로를 설명한다**:

- **범위가 좁으니 목적이 정확성일 수 있다.** 한 트랜잭션 안에서만 통하면 되니 다른 트랜잭션과의 정합성을 걱정할 필요가 없다.
- **목적이 정확성이니 끌 수 없다.** 성능은 포기할 수 있지만 정확성은 아니다.
- **수명이 트랜잭션이니 stale 문제가 작다.** 2차 캐시는 **공유되고 오래 살기 때문에** stale 데이터 관리(만료·무효화)가 본질적 과제가 된다.

**"캐시"라는 같은 말을 쓰는 게 함정이다.** 1차 캐시를 성능 장치로만 이해하면 **왜 끌 수 없는지 설명하지 못한다.** 그게 이해 여부를 가르는 지점이다.

**실무 판별**: 성능이 문제인데 1차 캐시를 손보려 하고 있다면 방향이 틀렸다. 왕복을 줄이려면 2차 캐시, 페치 조인, 배치 사이즈다.

## Q6. `@Transactional`을 빼면 동일성 보장이 사라지는 이유

**보장의 범위가 트랜잭션이고, 트랜잭션이 없으면 범위가 리포지토리 호출 하나로 쪼개지기 때문이다.**

```text
[@Transactional 있음]
  ┌─────── 트랜잭션 1개 = 컨텍스트 1개 ────────┐
  │  a = findById(1)  → 캐시에 저장            │
  │  b = findById(1)  → 캐시에서 반환          │
  └────────────────────────────────────────────┘
  a == b  ✅

[@Transactional 없음]
  ┌ 컨텍스트 A ┐   ┌ 컨텍스트 B ┐
  │ a = find   │   │ b = find   │
  └ 종료·소멸  ┘   └ 종료·소멸  ┘
  a 와 b 는 서로 다른 캐시에서 나왔다
  a == b  ❌
```

**Spring Data JPA의 리포지토리 메서드는 자체적으로 트랜잭션 경계를 갖는다.** 그래서 바깥에 `@Transactional`이 없으면 **호출마다 컨텍스트가 생겼다 사라진다.** 두 컨텍스트는 캐시를 공유하지 않는다.

**같이 사라지는 것들** — 동일성만 잃는 게 아니다:

| 잃는 것 | 결과 |
|---|---|
| 동일성 보장 | `a == b` 거짓, `Set` 중복 |
| 더티 체킹 | 반환된 객체를 수정해도 UPDATE가 안 나간다 (조용히) |
| 쓰기 지연 | 모아 보낼 대상이 없다 |
| 지연 로딩 | 컨텍스트가 닫혀 프록시 초기화 실패 |

**두 번째가 특히 위험하다** — 조회 후 setter를 부르는 코드가 **예외 없이 아무 일도 안 한다.**

**한 줄로**: 동일성 보장은 **"같은 컨텍스트 안에서"**의 보장이고, 트랜잭션이 컨텍스트의 경계다. 경계를 안 그으면 보장할 범위 자체가 없다.

## Q7. 수만 건 배치에서 영속성 컨텍스트가 비용이 되는 이유

**컨텍스트가 하는 일 두 가지가 그대로 두 가지 비용이 된다.**

**① 메모리 — 조회한 엔티티가 두 벌씩 남는다**

```text
영속성 컨텍스트
┌──────────────────────────────────────┐
│ 1차 캐시                             │
│   (Company, id=1) ──▶ Company@1a2b   │  ← 엔티티 본체
│   (Company, id=2) ──▶ Company@3c4d   │
│   …  50,000 건                       │
│                                      │
│ 스냅샷                               │
│   (Company, id=1) ──▶ {name="구",…}  │  ← 조회 시점 값 복사본
│   (Company, id=2) ──▶ {…}            │
│   …  50,000 건                       │
└──────────────────────────────────────┘
```

**엔티티 하나를 읽을 때마다 캐시와 스냅샷 양쪽에 들어간다.** 트랜잭션이 끝나기 전에는 **아무것도 해제되지 않는다** — 다 쓴 엔티티도 컨텍스트가 참조를 쥐고 있어 GC 대상이 아니다.

**② 플러시 비용 — 비교 대상이 전부 늘어난다**

플러시 때 Hibernate는 **컨텍스트 안의 모든 엔티티**를 스냅샷과 비교한다. 5만 건을 읽었으면 **한 건만 수정했어도 5만 건을 비교**한다. 그리고 플러시는 트랜잭션당 한 번이 아니라 **JPQL 실행마다** 일어날 수 있어, 배치 루프 안에서 조회가 섞이면 이 비용이 반복된다.

**③ (따라오는 비용) 컨텍스트가 커질수록 위 둘이 함께 악화된다** — 메모리 압박이 GC를 부르고, 그 GC가 살아 있는 5만 건을 매번 훑는다.

**대응 두 가지**:

| 방법 | 무엇을 없애는가 |
|---|---|
| **엔티티 대신 DTO로 조회** | 애초에 컨텍스트에 안 담긴다 — 캐시도 스냅샷도 생기지 않는다 |
| **주기적으로 `flush()` + `clear()`** | 담긴 것을 내보내고 비운다 |

**첫 번째가 더 근본적이다** — 읽기만 하는데 더티 체킹 대상으로 만들 이유가 없다. `@Transactional(readOnly = true)`도 같은 방향의 완화책이다.

**여기서 §4의 논지가 다시 확인된다** — 1차 캐시가 성능 장치라면 이런 배치에서 **가장 이득**을 봐야 한다. 실제로는 **가장 손해**다. 본업이 캐싱이 아니라는 증거다.

## 재출제 문항

1. JPQL로 두 번 조회했다. SELECT는 몇 번 나가고 `a == b`는 무엇인가? 왜 이 둘이 따로 노는가?
2. 방금 `rename()`한 엔티티를 다시 조회했더니 새 이름이 나온다. DB에는 옛 이름이 있는데도.
3. 1차 캐시를 끄는 설정이 왜 없는가? 없어서 곤란한 상황이 있는가?
4. 조회 후 setter를 불렀는데 UPDATE가 안 나간다. 무엇부터 확인하는가?
5. 5만 건 정산 배치가 OOM으로 죽는다. 원인 후보 두 가지와 각각의 대응은?
6. 다른 트랜잭션이 그 행을 바꿨다. 내 캐시 인스턴스는 어떻게 되는가?
