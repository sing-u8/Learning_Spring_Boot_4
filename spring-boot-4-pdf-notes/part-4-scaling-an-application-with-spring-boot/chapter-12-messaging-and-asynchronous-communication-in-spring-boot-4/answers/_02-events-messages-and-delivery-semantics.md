## Q1. 이벤트와 메시지

| | |
|---|---|
| **이벤트** | **무슨 일이 있었는가** — 비즈니스 사실 |
| **메시지** | **그 정보가 어떻게 전달되는가** — 기술적 컨테이너 |

> **언뜻 바꿔 써도 될 것 같지만 실제로는 목적이 조금 다르고, 그 구분을 이해하는 것이 신뢰할 만한 시스템 설계에 필수다.**

**이벤트의 예**: **직원이 생성됐다 / 직원의 급여가 갱신됐다 / 결제가 승인됐다.**

**세 문장의 공통점**: **전부 과거형이고, 도메인 안에서 의미를 갖는다.**

**이 구분이 실제로 작동하는 지점**: **무엇을 도메인 모델로 다루고 무엇을 인프라 관심사로 다룰지가 갈린다.**

```
도메인의 것:  이벤트 정의 (record), 이름, 필드
인프라의 것:  직렬화, 헤더, 키, 파티션 배정
```

**[[01a-core-components-of-event-driven-systems]]의 `Event (message)` 병기가 헷갈렸던 이유**: **같은 것의 두 국면**이다. **도메인에서는 이벤트, 인프라 위에서는 메시지.**

## Q2. 이벤트 이름이 과거형인 것과 디커플링

**이벤트는 "무엇을 해 달라"는 명령이 아니라 "무엇이 일어났다"는 사실이기 때문이다.**

> **그래서 producer가 소비자를 몰라도 되고, 소비자가 그 사실로 무엇을 할지는 자기가 정한다.**

```
EmployeeCreatedEvent     → 사실. 누가 무엇을 하든 producer 는 관심 없다
SendNotificationCommand  → 명령. producer 가 소비자의 행동을 지시한다
```

**"이벤트에 명령을 담지 않는다"**(§5) — **명령을 담으면 producer가 소비자의 행동을 지시하는 셈이라 [[01-asynchronous-and-event-driven-communication]]의 디커플링이 무너진다.**

**이름 하나가 아키텍처를 결정한다** — `SendNotificationCommand`를 발행하는 순간 **producer는 "알림을 보내야 한다"는 것을 알고 있다.** 그러면 **알림 요구가 바뀔 때 producer도 바뀐다.**

**"그냥 DTO 아닌가"라는 물음**(§5): **구조는 DTO와 같다. 다른 것은 의미다.** **DTO는 "이 데이터를 넘긴다"이고 이벤트는 "이 일이 일어났다"이다.** 그래서 이벤트는 **과거형 이름**을 갖고, **한번 발행되면 고칠 수 없다.**

## Q3. `employeeId`만 담으면 무너지는 것

**소비자가 다시 employee service를 호출하게 되어 결합이 돌아온다.**

> **소비자가 employee service에 되물을 필요가 없다 — 그러면 다시 결합이 생길 테니까.**

```
얇은 이벤트:  { employeeId: 42 }
              → consumer 가 GET /employees/42 를 호출한다
              → employee service 가 죽으면 알림도 못 보낸다
              → 비동기로 만든 의미가 절반 사라진다
```

**"이벤트를 얇게 만들면 결합이 돌아온다"**(§5).

**`EmployeeCreatedEvent`가 담는 것**:
| 필드 | 왜 |
|---|---|
| `employeeId` | **누구** |
| `name`·`email` | **무엇을 알림에 쓸지** |
| `createdAt` | **언제** |

> **이 구조는 처리에 필요한 데이터를 전부 담고 있다.**

**반대 방향의 경계도 있다**(§6): **이벤트를 너무 크게 만들지 않는다.** **전체 엔티티를 통째로 실으면 스키마 변경 위험이 커진다.**

**즉 기준은 "소비자가 처리에 필요한 만큼"**이지 "많을수록 좋다"가 아니다. 그리고 **민감 정보는 담지 않는다** — **broker에 보관되고 여러 소비자가 읽는다.**

## Q4. 이벤트 record에 프레임워크 애노테이션이 없는 것

**이벤트는 도메인의 것이고, 메시지로 만드는 일은 인프라의 몫이라는 뜻이다.**

```java
public record EmployeeCreatedEvent(
        Long employeeId, String name, String email, Instant createdAt) {}
```

> **특별할 것이 하나도 없다! 이벤트 정보를 나르는 평범한 데이터 구조일 뿐이다.**

**뜻하는 것**: **이벤트를 만들 때 프레임워크 애노테이션도, 상속도, 특별한 인터페이스도 필요 없다.** **그것을 메시지로 만드는 일(직렬화, 헤더, 키, 파티션 배정)은 Broker와 클라이언트 라이브러리의 몫이다.**

**얻는 것**:
- **도메인 타입이 인프라에 오염되지 않는다** — Kafka를 RabbitMQ로 바꿔도 이벤트 정의는 그대로
- **테스트가 쉽다** — 그냥 `new EmployeeCreatedEvent(...)`
- **Q1의 층 분리가 코드로 확인된다**

**다만 완전히 무관하지는 않다**(§5): **직렬화가 도메인에 영향을 준다.** **이벤트 자체는 평범한 record지만 JSON으로 오가므로 필드 타입 선택이 호환성 문제가 된다** → [[04a-defining-the-event-and-persistence-models]].

**비유로 보면** 신문 기사와 신문지 — **기사(이벤트)는 내용, 신문지(메시지)는 매체.** **깨지는 지점 둘**:
- **신문지는 배달되면 역할이 끝나지만 Kafka의 메시지는 보관돼 다시 읽힌다** — **매체가 저장소이기도 하다**
- **기사는 사람이 읽고 판단하지만 이벤트는 코드가 파싱한다** — **그래서 매체 층의 형식(JSON 직렬화)이 기사의 내용에 영향을 준다** — [[04b-implementing-the-employee-service]]에서 **`Instant`냐 `LocalDateTime`이냐가 문제가 되는 이유**다

**§6의 나머지**: **한번 정한 필드를 함부로 지우지 않는다** — **소비자가 어떤 필드를 쓰는지 producer는 모른다**(디커플링의 대가).
