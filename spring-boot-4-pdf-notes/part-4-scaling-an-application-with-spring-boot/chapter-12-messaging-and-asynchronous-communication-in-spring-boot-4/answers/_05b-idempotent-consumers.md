## Q1. 재시도가 없어도 중복이 생기는 경로

**① offset 커밋 직전에 consumer가 죽는 경우.**
> **consumer가 메시지를 처리하고 offset을 커밋하기 직전에 죽으면, 다시 뜬 뒤 같은 메시지를 또 받는다.**

**② 리밸런싱.** 인스턴스가 뜨거나 죽어 **partition이 재배정**될 때 같은 일이 생긴다.

**뿌리는 [[02a-delivery-semantics]]의 At-least-once**다 — **"처리했다"와 "처리했음을 기록했다" 사이에 창이 있고**, 그 창에서 죽으면 재처리된다.

**멱등성이 필요한 곳**: **consumer가 부수효과를 낼 때** —
- **이메일 발송**
- **레코드 삽입이나 갱신**
- **감사 항목 생성**
- **외부 시스템 호출**

> **우리 `NotificationService`가 정확히 첫 번째 경우다. 같은 알림이 두 번 가면 사용자가 알아챈다.**

**멱등 소비자의 정의**: **중복 이벤트를 처리하는 것이 한 번 처리하는 것과 같은 효과여야 한다.**

## Q2. 인메모리 Set의 세 한계 중 가장 치명적인 것

**인스턴스 간 조율이 없다는 것이다.**

| 한계 | **결과** |
|---|---|
| **재시작하면 사라진다** | 배포 직후 과거 이벤트가 재전달되면 **알림이 다시 간다** |
| **인스턴스 간 조율이 없다** | **인스턴스 A가 처리한 것을 인스턴스 B는 모른다. 확장하는 순간 멱등성이 깨진다** |
| **무한히 자란다** | 직원이 백만 명이면 Set에 백만 개. **메모리 누수** |

> **두 번째가 가장 치명적이다. [[03-apache-kafka-fundamentals]]에서 본 consumer group의 요점이 인스턴스를 늘려 확장하는 것인데, 이 구현은 인스턴스를 늘리면 멱등성을 잃는다.**

**즉 이 구현은 Kafka를 쓰는 이유 자체와 충돌한다** — 확장하려고 Kafka를 썼는데 **확장하면 멱등성이 사라진다.**

**책 자신이 인정한다**: **"이 인메모리 접근은 시연용으로만 유용하다."**

**§6의 지침**: **인메모리 Set을 production에 쓰지 않는다.** **세 한계 중 하나만으로도 충분한 이유다.**

## Q3. inbox 패턴의 "유니크 제약"이 `contains` + `add`보다 나은 이유

**원자적이기 때문이다.**

> **`contains` 후 `add`는 원자적이지 않다. 두 스레드가 동시에 같은 ID를 확인하면 둘 다 통과한다. `ConcurrentHashMap.newKeySet()`이 각 연산은 스레드 안전하게 만들지만 두 연산의 조합은 아니다.**

```
스레드 A: contains(42) → false
스레드 B: contains(42) → false     ← 둘 다 통과
스레드 A: sendNotification(...)
스레드 B: sendNotification(...)    ← 중복!
```

**유니크 제약은 DB가 원자적으로 판정한다** — **INSERT를 시도하고 제약 위반이면 이미 처리된 것**이다. **확인과 기록이 한 연산**이다.

**그리고 나머지 두 한계도 함께 푼다**:
| 한계 | **inbox 패턴** |
|---|---|
| 재시작하면 사라진다 | **영속 저장소** |
| 인스턴스 간 조율 | **모든 인스턴스가 같은 DB를 본다** |
| 무한히 자란다 | 정리 정책을 걸 수 있다(오래된 행 삭제) |

**책의 정리**:
> **inbox 패턴은 소비한 메시지 ID를 유니크 제약이 있는 영속 저장소에 담는다. 멱등성을 구현해 각 이벤트가 한 번만 처리되게 보장한다.**
>
> **outbox 패턴은 producer 쪽에 구현한다. 이벤트를 비즈니스 연산과 같은 트랜잭션의 일부로 데이터베이스에 저장해 신뢰성 있는 발행을 보장한다.**

**§6의 지침**: **`contains` 후 `add` 패턴을 쓰지 않는다.** **원자적 수단을 쓴다** — `add`가 `true`/`false`를 반환한다는 점을 이용하면 **인메모리에서도 한 번에 해결**된다.

**멱등 키 선택도 도메인 판단이다**(§5): **`employeeId`를 쓰면 "한 직원에게 알림은 평생 한 번"이 된다.** **직원 정보가 갱신돼 다시 알려야 한다면 이 키로는 안 된다.** **이벤트 ID를 쓰는 편이 일반적으로 안전하다.** §6도 같다 — **멱등 키를 도메인 ID로만 정하지 않는다.**

## Q4. 세 패턴이 각각 푸는 문제

| 패턴 | **푸는 문제** |
|---|---|
| **재시도** | **일시적 실패** — 몇 초 뒤면 성공할 것을 버리지 않는다 |
| **DLT** | **영구적 실패** — 절대 성공하지 않을 것이 흐름을 막지 않게 한다 |
| **멱등성** | **중복 처리** — 같은 이벤트가 두 번 와도 결과가 같게 한다 |

**셋이 순서대로 맞물린다**:
```
실패 발생
  → 재시도 (일시적이면 여기서 해결)
  → 3회 실패 → DLT (영구적이면 격리)
  → 그 과정에서 중복이 생기면 → 멱등성이 흡수
```

**§6의 지침**: **멱등성만으로 신뢰성을 확보했다고 보지 않는다.** **재시도·DLT와 함께여야 한다.** [[05-reliability-patterns-retries-dlt-idempotency]]도 같은 말을 한다 — **재시도만으로 신뢰성을 확보했다고 보지 않는다.**

> **참고 — 이 구현의 재시도/멱등 검사가 맞물리지 않는다**(§5): **ID를 Set에 추가하는 것이 `sendNotification` 성공 뒤**다. 그런데 **재시도는 `sendNotification`이 실패했을 때 도는 것**이라, **재시도가 도는 동안에는 아직 Set에 없다.** **즉 재시도가 만드는 중복은 이 검사가 막지 못한다.**
>
> **막는 것은 다른 종류의 중복이다** — **offset 커밋 실패나 리밸런싱으로 이미 성공적으로 처리한 메시지가 다시 온 경우**(Q1). **그것도 중요하지만, 절의 도입이 "재시도가 중복 위험을 높인다"로 시작하는 것과는 어긋난다.**

> **그리고 책이 outbox를 여기에 둔다**(§5) — **outbox는 producer 쪽 패턴인데 멱등성 절의 Note에 있다.** **정작 그것이 푸는 문제는 [[04b-implementing-the-employee-service]]의 코드에 있는데 두 자리가 연결되지 않는다.**
