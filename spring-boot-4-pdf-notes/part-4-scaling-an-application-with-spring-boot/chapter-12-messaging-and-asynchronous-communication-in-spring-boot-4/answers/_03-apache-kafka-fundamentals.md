## Q1. partition 3개에 consumer 인스턴스 5개

**2개가 논다.**

| consumer 인스턴스 수 | **배정** |
|---:|---|
| 1 | **3개 전부** 배정 |
| 2 | 하나가 2개, 다른 하나가 1개 |
| 3 | **각 1개씩 — 세 consumer에 걸쳐 병렬 처리** |
| **4 이상** | **추가 인스턴스는 논다 — 배정할 partition이 남지 않았다** |

> **인스턴스를 늘려도 partition 수를 넘으면 처리량이 늘지 않는다. 확장 계획을 세울 때 partition 수를 먼저 정해야 하는 이유다.**

**보장 하나**: **각 partition은 그룹 내에서 오직 하나의 consumer가 처리한다** — **중복 처리를 막는다.**

**§6의 경계**: **partition 수를 나중에 줄일 수 없다.** **초기 설계에서 신중히 정한다.** (늘리는 것은 가능하다.)

**partition이 있는 이유**: **병렬 처리·확장성·처리량.** **partition은 독립적으로 소비될 수 있어, 한 그룹의 여러 consumer가 서로 다른 partition을 동시에 읽으며 부하를 효율적으로 나눈다.**

## Q2. Kafka가 큐가 아니라 로그라는 사실

**읽어도 메시지가 남는다.**

> **전통적 큐는 소비되면 메시지가 사라지지만, Kafka는 읽어도 남아 있다.**

**가능해지는 것**:
- **여러 consumer group이 같은 topic을 각자의 속도로 읽을 수 있다** — notification service와 audit service가 **서로 방해하지 않는다**
- **필요할 때 메시지 재생(replay)** — **오프셋을 되돌리면 과거 메시지를 다시 읽는다.** **버그를 고친 뒤 과거 이벤트를 다시 처리**할 수 있다
- **실패 후 재개** — **어디까지 처리했는지 알므로 이어서 할 수 있다**
- **[[05a-dead-letter-topics]]에서 DLT가 "queue"가 아니라 "topic"인 이유**도 여기 있다

**Commit log**: **불변·순차 로그**로 저장하며 **설정된 기간 동안 보존**한다. **내구성**을 보장하고 **재처리**를 가능하게 한다.

**Offset**: **partition 안 각 메시지의 고유 위치.** **consumer는 처리하면서 자기 위치를 커밋한다.**

**offset은 consumer group마다 따로다**(§5) — **같은 topic을 두 그룹이 읽으면 각자의 offset을 갖는다.**

**§6의 경계**: **보존 기간을 확인한다.** **"언제나 재생 가능"이 아니다. 기간이 지나면 사라진다.** 비유의 깨짐이 그것이다 — **대장은 무한히 쌓이지만 Kafka는 설정된 기간만 보존**한다.

## Q3. 전체 순서를 보장하려면

**partition을 하나로 두어야 하고, 그러면 병렬성을 포기하는 것이다.**

> **Kafka에서 순서는 partition 단위이지 topic 단위가 아니다.**

```
partition 3개:  각 partition 안에서는 순서 보장. topic 전체 순서는 보장 안 됨
partition 1개:  topic 전체 순서 보장. 그런데 consumer 하나만 일한다 (Q1)
```

> **이 trade-off가 Kafka 설계의 핵심이다.**

**§6의 경계**: **전체 순서가 절대적으로 필요하면 partition 1개를 써야 하고, 그러면 Kafka를 쓰는 이유의 절반이 사라진다.**

**대부분의 도메인은 전체 순서를 요구하지 않는다** — 필요한 것은 **"한 엔티티에 대한 이벤트들의 순서"**이고, 그것은 키로 해결된다 → Q4.

**partition 3개 + 키 사용이 실무의 답이다** — **부하 분산과 (필요한 범위의) 순서 보장을 동시에** 얻는다.

## Q4. 특정 직원의 이벤트 순서를 지키려면

**`employeeId`를 메시지 키로 쓴다.**

| 조건 | **배정** |
|---|---|
| **키가 있다** | **같은 키는 항상 같은 partition으로 간다. 그 키 안의 순서가 보존된다** |
| 키가 없다 | **round-robin**으로 partition에 분산 |
| 커스텀 전략 | 필요하면 구현할 수 있다 |

> **이 메커니즘이 부하 분산과 순서 보장을 동시에 달성한다.**

**그러면 그 직원의 모든 이벤트가 같은 partition으로 가서 순서가 지켜진다.** **[[04b-implementing-the-employee-service]]가 `saved.getId().toString()`을 키로 넘기는 이유가 이것이다.**

**§6의 경계**: **키를 아무거나 쓰지 않는다.** **키가 편중되면 특정 partition에 부하가 몰린다.** 예를 들어 **부서 ID를 키로 쓰면** 큰 부서의 partition만 바빠진다.

**좋은 키의 조건**: **순서를 지켜야 하는 범위와 일치하고**, **값이 고르게 분포**한다. `employeeId`는 둘 다 만족한다.

**Kafka가 이벤트 주도 시스템의 중추인 이유 넷**:
- **서비스 간 느슨한 결합**
- **partitioning을 통한 높은 확장성**
- **복제와 consumer group을 통한 내결함성**
- **재생 가능한 이벤트 스트림을 통한 유연한 데이터 처리**

**consumer group의 회복력**: **consumer가 죽으면 Kafka가 그 partition을 다른 consumer들에게 재분배**해 연속성을 보장한다 — [[01a-core-components-of-event-driven-systems]]의 **"회복력"의 실체**다.

**비유의 나머지 깨짐**: 도서관 대장 — **사서를 늘리면 더 빨리 볼 수 있을 것 같지만 대장 권수를 넘으면 남는 사서는 논다**(Q1).
