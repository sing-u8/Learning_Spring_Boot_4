## Q1. 일시적 실패와 영구적 실패를 가르는 기준

> **재시도하면 성공할 수 있는가.**

| | **일시적 실패** | **영구적 실패** |
|---|---|---|
| 예 | **Kafka 서버가 몇 초 사용 불가 / DB 연결 타임아웃 / 서드파티 API의 간헐적 오류** | **잘못된 payload / 필수 필드 없음** |
| 재시도하면 | **몇 초 뒤 성공할 수 있다** | **없는 이메일은 재시도해도 생기지 않는다** |
| 맞는 대응 | **재시도** | **DLT** |

> **재시도가 도움이 되는 실패와 자원만 낭비하는 실패는 다르다.**

**책이 던지는 세 질문이 이 절과 다음 두 절의 목차다**:
- notification service가 **일시적으로 사용 불가**면? → 재시도
- **잘못된 데이터**로 처리가 실패하면? → [[05a-dead-letter-topics]]
- **같은 메시지가 두 번 이상** 전달되면? → [[05b-idempotent-consumers]]

**[[02a-delivery-semantics]]의 At-least-once가 여기서 실제 동작으로 나타난다.**

**§6의 지침**: **영구적 실패에 재시도를 걸지 않는다.** **자원 낭비이고 뒤를 막는다**(Q3).

## Q2. 재시도 로직을 리스너 안에 쓰지 않는 것이 나은 이유

**관심사가 분리되기 때문이다.**

```java
@Bean
public DefaultErrorHandler errorHandler() {
    FixedBackOff fixedBackOff = new FixedBackOff(2000L, 3L);
    return new DefaultErrorHandler(fixedBackOff);
}
```

> **우리는 재시도 로직을 리스너 안에 쓰지 않는다. `try-catch`도, 루프도 없다. 에러 핸들러 bean 하나를 등록하면 프레임워크가 리스너 바깥에서 그 정책을 적용한다.**

**얻는 것**:
- **리스너는 비즈니스 로직만 담는다** — 읽기 쉽다
- **정책이 한 곳에 모인다** — 모든 리스너에 같은 정책이 적용된다
- **정책을 바꿔도 리스너를 안 고친다** — `FixedBackOff`를 `ExponentialBackOff`로 교체
- **[[05a-dead-letter-topics]]의 DLT를 나중에 얹을 수 있다** — 같은 bean에 recoverer만 추가

**[[../chapter-11-virtual-threads-in-java-and-spring-boot/03-integrating-virtual-threads-with-taskexecutor|Ch11]]의 `TaskExecutor` 주입과 같은 원리다** — **실행 정책을 설정으로 밀어내고 코드는 몰라도 되게** 한다.

**설정 요소**:
| 요소 | 하는 일 |
|---|---|
| **`DefaultErrorHandler` bean** | **메시지 처리 실패 처리를 커스터마이즈** |
| **`FixedBackOff(2000L, 3L)`** | **2초마다, 최대 3회 재시도** |

> **이벤트를 버리지 않고 consumer에게 회복할 기회를 준다.**

## Q3. `FixedBackOff(2000L, 3L)` 동안 그 partition에서

**뒤 메시지가 6초 동안 대기한다.**

> **2초 × 3회 = 6초 동안 뒤가 막힌다.**

**왜 그런가**: **[[03-apache-kafka-fundamentals]]의 규칙 — 각 partition은 그룹 내에서 오직 하나의 consumer가 처리한다.** 그 consumer가 **한 메시지를 재시도하는 동안 같은 partition의 다음 메시지를 못 잡는다.**

**§6의 지침**: **재시도 횟수를 크게 잡지 않는다.** **partition이 그만큼 막힌다.**

**계산이 필요하다**: 간격 10초 × 5회면 **50초**다. 그동안 그 partition에 쌓이는 메시지가 **처리량 × 50초**만큼이다.

**비유의 깨짐이 이것이다** — **전화는 내가 다시 거는 동안 다른 일을 할 수 있지만, Kafka consumer는 재시도 중에 그 partition의 다음 메시지를 처리하지 못한다.**

**그리고 영구적 실패라면 이 6초가 통째로 낭비다** — 그래서 [[05a-dead-letter-topics]]가 필요하다.

**또 하나의 부작용**: **재시도가 중복을 만든다**(§5) — **처리가 절반쯤 진행된 뒤 실패해 재시도하면 앞부분이 두 번 실행된다.** **이메일이 두 번 갈 수 있다는 뜻**이고, 그래서 [[05b-idempotent-consumers]]가 필요하다.

**§6의 지침**: **부수효과가 있는 처리에 재시도를 걸 때는 멱등성을 먼저 확보한다.**

## Q4. 시뮬레이션 코드에서 `Math.random()` 줄의 위치

**메서드 맨 앞에 있어서, `email` 검사에 닿기 전에 절반이 일시적 실패로 빠진다.**

```java
if (Math.random() < 0.5) { throw ... }          // ← 맨 앞
if (event.email() == null || ...) { throw ... } // ← 여기까지 오려면 위를 통과해야
```

> **그래서 이메일이 없는 메시지도 재시도 3회를 다 쓰기 전에 우연히 "성공"할 수 있다 — 두 번째 검사에 도달하려면 세 번의 `random()`이 모두 0.5 이상이어야 하는데, 그럴 확률이 1/8이다.**

**두 실패 유형을 대비해 보여 주려는 의도와 실행이 어긋난다.**

**영구 실패 경로를 확실히 보려면 `Math.random()` 줄을 잠시 빼야 한다.**

**여기서 "성공"에 따옴표가 붙는 이유**: `email`이 `null`인데 `Math.random()`이 0.5 미만이면 **첫 줄에서 예외가 나고**, 재시도에서 통과하면 **두 번째 줄에서 예외**가 난다. 즉 **어느 쪽 예외인지 로그로만 구분**되고, **DLT 도달 확률이 낮아** 시연이 잘 안 된다.

**§5의 다른 지적 — 재시도는 예외 종류를 구분하지 않는다**: **이 설정은 모든 예외에 대해 3회 재시도한다. 영구 실패도 3회 도는 것이다.** **`DefaultErrorHandler`에는 특정 예외를 재시도 없이 바로 실패시키는 설정이 있지만 책은 다루지 않는다.**

**비유의 다른 깨짐이 이것이다** — **사람은 "없는 번호입니다" 안내를 듣고 재시도를 포기하지만, `DefaultErrorHandler`는 예외의 종류를 구분하지 않는다.** **실제로는 예외 타입별로 재시도 여부를 나눌 수 있고, 그게 실무의 다음 단계다.**

**§6의 마지막 지침**: **재시도만으로 신뢰성을 확보했다고 보지 않는다.** **DLT와 멱등성이 함께 있어야 한다.**
