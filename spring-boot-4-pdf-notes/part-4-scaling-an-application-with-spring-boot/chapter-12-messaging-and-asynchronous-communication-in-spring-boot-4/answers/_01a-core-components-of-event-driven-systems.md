## Q1. broker의 세 일 중 디커플링을 가능하게 하는 것

**저장이다.**

> **"수신·저장·전달"이 나란히 적혀 있지만 가운데가 결정적이다.**

- **수신만 한다면 그냥 중계기다**
- **저장하기 때문에 consumer가 죽어 있어도 producer가 계속 발행할 수 있다**
- **저장하기 때문에 나중에 붙은 새 consumer가 과거 이벤트를 읽을 수 있다**

> **[[01-asynchronous-and-event-driven-communication]]에서 본 디커플링의 물리적 근거가 이 "저장"이다. 그리고 그것이 Kafka의 commit log로 구체화된다** → [[03-apache-kafka-fundamentals]].

**네 구성 요소**:
| 요소 | 하는 일 |
|---|---|
| **Producer** | **의미 있는 일이 생겼을 때 이벤트를 방출** |
| **이벤트** | **하류 소비자에게 관련 있는 비즈니스 데이터**를 담는다. **일단 발행되면 메시징 인프라가 옮기는 메시지가 된다** |
| **Broker** | **받고, 저장하고, 전달.** **producer를 consumer로부터 분리** (Kafka, RabbitMQ) |
| **Consumer** | **이벤트를 구독하고 반응** |

**저장이 없으면 [[01-asynchronous-and-event-driven-communication]]의 이점 두 개가 통째로 사라진다** — "소비자가 죽어도 계속 발행"과 "새 소비자를 나중에 붙인다" **둘 다 저장에 의존**한다.

## Q2. "실패가 격리된다"와 "실패 진단이 어렵다"가 동시에 참인 이유

**앞의 것은 영향 범위, 뒤의 것은 원인 추적이다.**

> **장애가 덜 번지는 대신 어디서 났는지 찾기 어렵다.**

```
격리:   notification 이 죽어도 employee service 와 클라이언트는 멀쩡하다
진단:   그런데 "알림이 안 갔다"는 사실을 아무도 모른다
```

**어려워지는 것 셋**:
| 어려워지는 것 | **왜** |
|---|---|
| **서비스를 가로지르는 비즈니스 흐름 추적** | **한 요청이 여러 서비스에서 시차를 두고 처리된다** |
| **타이밍과 순서 추론** | **언제 처리될지 보장이 없다** |
| **실패 진단** | **실패가 원래 요청과 다른 시간·다른 서비스에서 난다** |

**세 번째가 핵심이다** — REST에서는 **실패가 호출 스택에 남지만**, 이벤트에서는 **다른 시간 다른 프로세스**에서 난다. **스택 트레이스로 이어지지 않는다.**

**같은 성질의 양면이다** — **경계를 끊었기 때문에 장애가 안 번지고, 경계를 끊었기 때문에 추적이 안 된다.**

**이점 쪽도 함께**: **새 consumer 추가, 여러 인스턴스에 부하 분산, 실패 격리** — 한 단어씩 뽑으면 **확장성·회복력·유연성·느슨한 결합**이다.

- **재시도**
- **중복 전달**
- **스키마 진화**
- **결과적 일관성**

> **이것들이 설계·운영 복잡도를 더한다.**

**각각이 이 장의 어느 절로 이어지는지**:
| 관심사 | 이어지는 곳 |
|---|---|
| 재시도 | [[05-reliability-patterns-retries-dlt-idempotency]] |
| 중복 전달 | [[05b-idempotent-consumers]] |

**책이 이 절을 닫는 문장**:
> **실무에서 이벤트 주도 시스템은 상당한 이점을 주지만, 이해 가능하고 신뢰할 만한 상태로 남으려면 신중한 모델링·모니터링·오류 처리 전략이 필요하다.**

**"모니터링"이 목록에 들어 있는 것이 우연이 아니다** → Q4.

**이 절이 이 장에서 유일하게 이벤트 주도의 단점을 정면으로 나열하는 자리다.**

## Q4. 관측이 선택이 아닌 이유

**흐름 추적이 어려워졌으므로 관측이 이 아키텍처의 전제 조건이 된다.**

```
REST:      실패가 호출 스택에 남는다 → 로그 한 곳에서 추적 가능
이벤트:    실패가 다른 시간·다른 서비스에서 난다 → 추적 도구 없이는 못 찾는다
```

**§6의 첫 지침이 그래서 강하다**: **관측 체계가 없다면 이벤트 주도로 가지 않는다.** **문제가 생겨도 어디서 났는지 알 수 없다.**

**즉 관측은 "있으면 좋은 것"이 아니라 "없으면 이 아키텍처를 쓸 수 없는 것"**이다. Q2의 세 가지 어려움이 **전부 관측으로만 완화**된다.

**이 책의 Chapter 13이 그 도구를 다루는데, 두 장이 명시적으로 연결되지는 않는다**(§5).

**§6의 나머지 경계**:
- **스키마를 통제할 수 없다면 위험하다** — **producer가 필드를 지우면 모든 consumer가 깨진다**
- **순서가 엄격히 중요한 흐름은 설계가 까다롭다** → [[03-apache-kafka-fundamentals]]의 **partition과 key**
- **팀이 하나이고 서비스가 둘이라면 복잡도만 는다**

**비유로 보면** 우체국 — **발신인은 수취인이 지금 집에 있는지 몰라도 된다.** **깨지는 지점 셋**:
- **편지는 한 사람에게 가지만 이벤트는 여러 consumer가 각자 읽는다**
- **우체국은 배달을 완료하면 편지를 없애지만 Kafka는 설정된 기간 동안 보관**해 **재생이 가능하다**
- **편지가 안 왔으면 발신인에게 물어보면 되지만, 이벤트가 처리되지 않은 것을 알아채는 일 자체가 어렵다** — 그것이 **[[05a-dead-letter-topics]]에서 DLT를 도입하는 이유**다
