## Q1. REST 흐름의 어느 지점이 문제인가

**3번 — employee service가 알림을 보내려고 notification service를 호출하는 단계다.**

```
1. 클라이언트 → employee service: 직원 생성 요청
2. 직원 생성
3. employee service → notification service 호출     ← 문제의 자리
4. 클라이언트에 응답 반환

▶ 이 모든 단계가 같은 요청 주기 안에서 일어난다.
```

> **알림 서비스가 느리거나 사용할 수 없으면 요청 전체가 영향을 받는다. 클라이언트는 직원이 만들어졌는지도 모른 채 타임아웃을 받는다.**

**왜 응답의 성공 조건이 아닌가**: **알림 발송이 직원 생성 응답의 성공 조건인가? 대부분의 도메인에서 아니다. 직원은 이미 저장됐고, 알림은 나중에 가도 된다.**

**즉 기술적 결합이 도메인의 요구를 넘어선 상태**다. 도메인은 "직원 생성"만 요구하는데 **구현이 "알림 성공"까지 묶어 놓았다.**

**이벤트로 바꾸면 순서가 갈린다**:
```
3. EmployeeCreated 이벤트를 Broker 에 발행
4. 클라이언트에 응답 반환           ← 알림 처리를 기다리지 않는다
5. notification service 가 비동기로 소비
```

## Q2. "클라이언트 상호작용은 여전히 동기"

**클라이언트는 여전히 employee service로부터 응답을 받는다. 비동기가 되는 것은 내부 워크플로다.**

```
클라이언트 ──동기(요청/응답)──▶ employee service
                                      │ 비동기(이벤트)
                                      ▼
                                notification service
```

> **바뀌는 것은 서비스 경계 안쪽이다.**

**"이벤트 주도로 바꾸면 API가 비동기가 된다"는 흔한 오해**이고, 책이 명시적으로 부정한다.

**왜 이 구분이 중요한가**:
- **API 계약이 안 바뀐다** — 클라이언트는 아무것도 고칠 필요가 없다
- **응답이 무엇을 보증하는지가 달라진다** — 이제 응답은 **"직원이 생성됐다"**만 보증하고 **"알림이 갔다"는 보증하지 않는다**

**두 번째가 실질적 변화다** — **"직원은 만들어졌는데 알림이 안 갔다"는 상태가 정상적으로 존재할 수 있고, 그것을 결과적 일관성이라 부른다.** **그 상태를 감당할 수 있는 도메인에만 쓴다.**

**§6의 경계가 그 판단이다**: **응답 전에 반드시 끝나야 하는 일에는 쓰지 않는다.** **결제 승인이나 재고 차감을 이벤트로 미루면 클라이언트에게 거짓말을 하게 된다.**

## Q3. 디커플링이 producer에게 몰라도 되게 해 주는 세 가지

- **어떤 서비스가 소비할지**
- **소비자가 몇 개나 있는지**
- **각 소비자가 언제 처리할지**

**그래서 두 가지가 가능해진다**:

**① 한 서비스의 변경이 다른 서비스의 즉각적 변경을 덜 요구한다.** **기존 이벤트에 반응하는 새 소비자를 producer 변경 없이 추가**할 수 있다. **감사 로그를 남기는 서비스를 붙이고 싶다면 그냥 구독하면 된다.**

**② 소비자가 일시적으로 죽어도 producer는 계속 발행한다.** **소비자는 살아난 뒤 나중에 처리한다.** **이것이 REST에서는 불가능하다 — 호출 대상이 죽으면 호출이 실패한다.**

**얻는 것 넷**:
| 이점 | 뜻 |
|---|---|
| **누가 소비하는지 알 필요가 없다** | 이벤트를 발행할 뿐 |
| **소비자가 독립적으로 진화** | producer를 건드리지 않는다 |
| **notification 실패가 클라이언트 요청에 영향 없음** | 경계가 갈렸다 |
| **실패가 격리되고 전파되지 않는다** | 장애가 시스템을 타고 번지지 않는다 |

**"디커플링 = 의존이 없다"는 오해다**(§5) — **코드 의존은 사라지지만 이벤트 스키마에 대한 의존이 생긴다.** **producer가 필드를 지우면 consumer가 깨진다.** 그게 **"스키마 진화"**라는 새 관심사다.

## Q4. 이벤트 주도가 들여오는 새 설계 관심사 다섯

- **이벤트 구조**
- **전달 보장**
- **순서**
- **재시도**
- **결과적 일관성**

> **이 목록이 이 장의 나머지 목차다.** [[02-events-messages-and-delivery-semantics]]가 **이벤트 구조와 전달 보장**을, [[03-apache-kafka-fundamentals]]가 **순서**를, [[05-reliability-patterns-retries-dlt-idempotency]]가 **재시도**를 다룬다.

**"REST는 낡았다"는 오해다**(§5) — **책의 첫 문단이 그 반대를 말한다.** **request-response는 현대 시스템 설계의 핵심으로 남아 있다.** **문제는 그것을 모든 상호작용에 쓰는 것**이다 → [[06-choosing-between-rest-and-messaging]].

**§6의 나머지 경계**: **강한 일관성이 요구되는 도메인**에는 맞지 않는다 · **서비스가 둘뿐이고 함께 배포된다면 복잡도만 는다** · **추적이 어려워진다는 대가**를 계산에 넣는다 → [[01a-core-components-of-event-driven-systems]].

**비유로 보면** 식당 주문과 영수증 — **주문을 접수하고 영수증을 바로 주고, 주방은 주문표를 보고 알아서 만든다.** **깨지는 지점 둘**:
- **식당에서는 손님이 음식을 받아야 거래가 끝나지만, 이벤트 주도에서는 응답을 준 뒤에 실패해도 클라이언트가 모른다** → [[05a-dead-letter-topics]]
- **주문표는 종이 한 장이지만 이벤트는 여러 소비자가 각자 읽는다** — **누가 읽었는지 추적하는 문제**가 새로 생기고, 그게 **offset과 consumer group**이다
