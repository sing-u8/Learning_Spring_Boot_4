## Q1. `Employee`에 있고 `EmployeeCreatedEvent`에 없는 필드

**`role`이다. 알림을 보내는 데 직무가 필요 없기 때문이다.**

| 필드 | `Employee` 엔티티 | `EmployeeCreatedEvent` |
|---|---|---|
| id / employeeId | `id` | `employeeId` — **이름이 바뀐다** |
| name | 있음 | 있음 |
| **role** | **있음** | **없음** |
| email | 있음 | 있음 |
| createdAt | 있음 | 있음 |

**이름도 바뀌었다** — `id` → `employeeId`. **이벤트를 읽는 쪽에서는 "무엇의 id인지"가 문맥에서 자명하지 않기** 때문이다. 엔티티 안에서는 `Employee.id`라 명확하지만, **이벤트는 홀로 떠다닌다.**

> **이 두 가지 차이가 원칙 하나를 보여 준다 — 이벤트는 엔티티의 복사본이 아니라 소비자를 위한 계약이다.**

**[[02-events-messages-and-delivery-semantics]]의 "처리에 필요한 데이터를 전부 담아야 한다"의 반대편에 "필요 없는 것은 담지 않는다"가 있다.**

**두 원칙이 함께 기준을 만든다** — **소비자가 처리에 필요한 만큼, 그 이상은 말고.**

## Q2. 엔티티를 그대로 발행하면 생기는 문제

1. **DB 컬럼 변경이 곧 이벤트 스키마 변경이 된다.** **내부 리팩터링이 다른 팀의 서비스를 깨뜨린다.**
2. **소비자가 필요 없는 데이터를 받는다.** **급여 같은 민감 필드가 섞여 들어갈 수 있다.**
3. **JPA 프록시·지연 로딩 같은 것이 직렬화에 끼어들 수 있다.**

**1번이 가장 무겁다** — **DB 스키마와 이벤트 계약이 묶여 한쪽을 바꿀 때마다 다른 쪽이 인질**이 된다(§5). **`role`을 `position`으로 이름만 바꿔도 모든 소비자가 깨진다.**

**2번은 보안 문제로 커진다** — **broker에 보존되고 여러 소비자가 읽는다**(§6). 한번 발행된 민감 정보는 **회수할 수 없다.**

**3번은 조용히 터진다** — 지연 로딩 프록시를 직렬화하면 **`LazyInitializationException`**이거나 **의도치 않은 추가 쿼리**다.

**"엔티티와 이벤트를 합치고 싶은 유혹"**(§5): **필드가 거의 같으니 하나로 쓰고 싶어진다. 지금은 편하지만** 위 세 문제가 따라온다.

**§6의 지침**: **엔티티를 이벤트로 그대로 발행하지 않는다** · **이벤트에 민감 필드를 담지 않는다** · **한번 발행한 필드를 함부로 지우지 않는다** — **누가 쓰는지 producer는 모른다.**

## Q3. 이벤트가 record이고 엔티티가 클래스인 이유

| | **엔티티** | **이벤트** |
|---|---|---|
| 타입 | **클래스** | **record** |
| 왜 | **JPA가 생명주기를 관리하는 가변 객체여야** | **한번 일어난 사실이라 바뀌지 않는다** |

> **Producer가 발행한 뒤 아무도 고칠 수 없어야 한다. 불변성이 이벤트의 의미와 맞아떨어진다.**

**[[../chapter-11-virtual-threads-in-java-and-spring-boot/02-using-virtual-threads-in-a-spring-boot-application|Ch11]]에서 본 것과 같은 이유다** — **JPA 엔티티는 영속성 컨텍스트가 변경을 추적해야 하므로 record를 쓸 수 없다.**

**그리고 이벤트 쪽은 [[02-events-messages-and-delivery-semantics]]의 "이벤트는 한번 발행되면 고칠 수 없다"와 타입 수준에서 일치한다.**

**즉 타입 선택이 의미를 표현한다** — 가변 클래스는 **"이것은 계속 변하는 상태"**, 불변 record는 **"이것은 일어난 사실"**이다.

**이 장이 JPA를 쓰는 것도 짚어 둘 만하다**(§5) — **[[../chapter-10-working-with-data-reactively/01-what-reactive-data-access-requires|Ch10]]이 JPA를 블로킹이라 배제했는데 여기서는 그대로 쓴다.** **메시징과 리액티브는 별개 선택**이며 **이 장은 리액티브가 아니다.**

## Q4. `Instant`와 `LocalDateTime`

**`Instant`(또는 `OffsetDateTime`)를 써야 한다. 시간대가 명확하기 때문이다.**

> **책 p.323의 개념 소개용은 `Instant createdAt`이고, p.330의 구현용은 `LocalDateTime createdAt`이다. 같은 이름의 타입이 필드 타입만 다른 두 버전으로 제시된다.**

**실제 문제가 되는 이유 — JSON 표현이 다르다**:
```
Instant:        2026-03-28T18:00:00Z      ← UTC 기준. 시간대 정보 있음
LocalDateTime:  2026-03-28T15:00:00       ← 시간대 정보가 없다
```

> **producer가 한쪽으로 직렬화하고 consumer가 다른 쪽으로 역직렬화하면 메시지 계층에서 깨진다.**

**근거**: **서비스들이 다른 시간대에서 돌 수 있다.** `LocalDateTime`은 **"어느 시간대의 15시인지"를 담지 않으므로**, producer가 서울에서 돌고 consumer가 UTC로 해석하면 **9시간이 어긋난다.**

**§6의 지침**: **시간 필드에 `LocalDateTime`을 쓰지 않는다.** **서비스가 다른 시간대에 있으면 어긋난다.**

**이것이 [[02-events-messages-and-delivery-semantics]]의 "직렬화가 도메인에 영향을 준다"의 구체적 사례다** — **이벤트 자체는 평범한 record지만, JSON으로 오가므로 필드 타입 선택이 호환성 문제가 된다.**

**비유로 보면** 병원 진료 기록과 진단서 — **진료 기록(엔티티)은 병원 내부용이라 온갖 정보가 들어 있고 계속 갱신**되지만, **진단서(이벤트)는 외부에 내보내는 문서라 필요한 항목만 담고, 한번 발급하면 고치지 않는다.**
