## Q1. 플랫폼 스레드가 비싼 세 이유

| 비용 | **구체적으로** |
|---|---|
| **메모리** | **스레드마다 스택이 할당된다**(보통 수백 KB~1MB) |
| **스케줄링** | **OS 커널이 문맥 교환을 한다** |
| **생성** | **시스템 콜이 필요하다** |

> **그래서 한 프로세스가 만들 수 있는 플랫폼 스레드는 현실적으로 수천 개 수준이다. 동시 접속이 수만이면 감당이 안 된다.**

**근원은 하나다** — **플랫폼 스레드는 운영체제 스레드에 1:1로 대응한다.** OS가 관리하므로 **OS의 비용이 그대로 붙는다.**

**요청 하나에 스레드 하나를 주면 코드가 단순하다**는 것이 전통적 답이었고, **그 단순함의 대가가 이 세 비용**이다.

## Q2. 기존 우회로 셋의 해결과 대가

| 대응 | **하는 일** | **대가** |
|---|---|---|
| **스레드 풀** | **생성 비용을 감춘다** | **개수 제한은 그대로. 풀이 마르면 대기** |
| **비동기 프로그래밍** | **콜백으로 기다림을 없앤다** | **콜백 지옥, 스택 트레이스 소실** |
| **리액티브 모델** | **적은 스레드로 많은 요청** | **코드를 쓰고 조합하고 이해하는 방식이 바뀐다** |

> **"효과적이지만 이 접근들은 추가 복잡도를 들여오고, 개발자가 코드가 어떻게 구조화되고 실행되는지를 다르게 생각하게 만든다."**

**셋의 공통 대가가 "생각하는 방식"이다** — 스레드 풀만 **비용 문제**를 남기고, 나머지 둘은 **코드 형태 자체**를 바꾼다.

**스레드 풀이 가장 약한 답인 이유**: **Q1의 세 비용 중 생성 비용만 감춘다.** 메모리와 문맥 교환은 그대로이고, **개수 상한도 그대로**다.

**[[../chapter-9-writing-reactive-web-controllers/01-reactive-programming-and-backpressure|Ch9]]와 [[../chapter-10-working-with-data-reactively/01-what-reactive-data-access-requires|Ch10]]이 리액티브 모델을 다뤘고, 이 장은 다른 답을 제시한다.**

## Q3. "블로킹처럼 쓰고 논블로킹처럼 확장한다"의 네 단계

```
1. 가상 스레드가 캐리어 위에서 실행 중
2. 블로킹 연산 도달 (DB 응답 · 네트워크 대기)
3. JVM 이 가상 스레드를 중단하고 캐리어에서 내린다 (unmount)
4. 캐리어는 다른 가상 스레드를 얹어 일을 계속한다
   → 응답 도착 → 가상 스레드가 다시 얹혀 이어서 실행된다
```

**핵심은 3~4단계다.**

> **블로킹 호출이 여전히 코드에는 블로킹으로 적혀 있지만, 자원 관점에서는 블로킹이 아니다. 기다리는 것은 가상 스레드이고 캐리어는 다른 일을 한다.**

**두 축**: **캐리어 스레드**(= 가상 스레드를 실제로 실행해 주는 플랫폼 스레드)와 **마운트**(= 가상 스레드가 캐리어 위에 얹히고 내려오는 것).

**책이 "핵심 이점"이라 부르는 것**:
> **단순하고 명령형이며 블로킹 스타일인 코드를 쓰면서도 높은 확장성을 얻는다.**

> **이것이 리액티브가 콜백으로 얻던 것을 언어 수준에서 얻는 방법이다.**

**"가상 스레드를 쓰면 블로킹이 사라진다"는 오해다**(§5) — **코드는 여전히 블로킹이다.** 사라지는 것은 **플랫폼 스레드가 묶이는 것**이다.

## Q4. 리액티브와 가상 스레드의 차이

| | **리액티브** | **가상 스레드** |
|---|---|---|
| **코드 모양** | **연산자 체인, 콜백** | **평범한 순차 코드** |
| **스택 트레이스** | **끊긴다** | **그대로 남는다** |
| 디버거 | **어렵다** | **평소처럼** |
| **try-catch** | **안 통한다** | **통한다** |
| 스레드가 기다리나 | 아무도 안 기다린다 | **가상 스레드가 기다린다(공짜로)** |

**실무적으로 가장 큰 차이는 스택 트레이스와 try-catch다** — [[../chapter-9-writing-reactive-web-controllers/01a-blocking-vs-non-blocking|Ch9]]가 **"학습 곡선이 아니라 영구적인 운영 비용"**이라 부른 것이 여기서 사라진다.

**Spring Boot에서의 의미**:
> **이 모델은 기존 프로그래밍 관행과 자연스럽게 맞는다.** Spring Web MVC로 만든 애플리케이션, 데이터 접근 계층, 전통적 서비스 컴포넌트가 **리액티브로 옮기지 않고도** 확장성을 얻는다.

**즉 마이그레이션 비용이 거의 0이다.** 리액티브는 **코드를 다시 써야** 하지만, 가상 스레드는 **설정 한 줄**이다([[02-using-virtual-threads-in-a-spring-boot-application]]).

## Q5. 가상 스레드가 리액티브를 대체하지 못하는 두 영역

| 리액티브가 여전히 필요한 곳 | **왜** |
|---|---|
| **논블로킹 데이터 파이프라인** | **스트림 변환·조합이 필요하다** |
| **세밀한 배압 제어** | **가상 스레드에는 이런 흐름 제어 개념이 없다** |

> **가상 스레드는 "스레드가 비싸다"는 문제를 푼다. 리액티브는 그것에 더해 "데이터 흐름을 조절해야 한다"는 문제까지 다룬다. 후자가 없으면 가상 스레드가 훨씬 단순한 답이다.**

**이것이 결정 기준이다**:
```
배압이 필요한가?
  ├─ 예   → 리액티브
  └─ 아니오 → 가상 스레드 (훨씬 단순)
```

**[[../chapter-9-writing-reactive-web-controllers/05b-crafting-a-thymeleaf-template|Ch9]]가 "두 선택지를 정면으로 비교하지 않는다"고 지적한 그 빈자리를 이 절이 부분적으로 메운다** — **적어도 "언제 리액티브여야 하는가"는 명확하다.**

**가상 스레드는 I/O 바운드에 특히 잘 맞는다** — **CPU 계산이 아니라 기다림이 시간을 차지하는 작업.**

---

## Q6. CPU 바운드 작업에 이득이 없는 이유

**계산이 시간을 쓰는 동안에는 캐리어가 풀려나지 않기 때문이다.**

```
블로킹 I/O:  기다린다 → JVM 이 unmount → 캐리어가 다른 일
CPU 계산:    실행 중  → unmount 할 지점이 없다 → 캐리어가 묶여 있다
```

> **가상 스레드를 아무리 많이 만들어도 코어 수 이상으로 빨라지지 않는다.**

**Q3의 3단계가 성립하지 않는다** — **unmount는 "기다릴 때" 일어난다.** 계산에는 기다림이 없다.

**이것이 리액티브와 같은 한계다** — [[../chapter-9-writing-reactive-web-controllers/01a-blocking-vs-non-blocking|Ch9]]도 **"CPU 바운드에는 이득이 없다. 없앨 기다림이 없다"**고 했다. **두 답이 같은 문제(기다림)를 풀기 때문에 한계도 같다.**

**"가상 스레드는 더 빠른 스레드다"라는 오해도 여기서 정리된다**(§5) — **하나하나가 빠른 게 아니라 많이 만들 수 있는 것**이고, **단일 작업의 실행 속도는 같다.**

**추가 함정**(§6): **`synchronized` 블록 안의 블로킹.** **가상 스레드가 캐리어에 고정(pinning)될 수 있어 이점이 사라진다.** **책은 다루지 않지만 실무에서 자주 만나는 함정이다.**

## Q7. 종업원 비유가 깨지는 지점

**비유**: 가상 스레드는 **"식당에서 주문을 받아 두고 다른 테이블을 보러 가는 종업원"**이다. **요리가 나올 때까지 서 있지 않는다.**

**깨지는 지점**: **손님 쪽에서는 아무것도 달라지지 않는다는 점을 흐린다.**

> **실제로는 가상 스레드 코드 자체가 "서서 기다리는" 형태로 쓰여 있고, 자리를 뜨는 주체는 코드가 아니라 JVM이다. 종업원이 스스로 판단하는 게 아니라 지배인이 종업원을 다른 테이블로 옮겨 붙이는 쪽에 가깝다.**

```
비유:  종업원이 스스로 "다음 테이블로 가자"고 판단한다
실제:  코드는 "여기서 기다린다"고 적혀 있고
       JVM 이 그 스레드를 캐리어에서 내린다
```

**이 구분이 왜 중요한가**: **개발자가 아무것도 안 바꿔도 된다**는 것이 이 장의 약속인데, 비유는 **종업원(코드)이 달라진 것처럼** 읽힌다. **달라진 것은 지배인(JVM)**이다.

**그리고 그것이 Q4의 "마이그레이션 비용이 0"과 이어진다** — **리액티브는 종업원을 다시 교육해야 하지만, 가상 스레드는 지배인만 바꾼다.**

**비유가 맞는 부분은 남는다** — **기다리며 서 있지 않는다**는 핵심. 깨지는 것은 **주체**다.
