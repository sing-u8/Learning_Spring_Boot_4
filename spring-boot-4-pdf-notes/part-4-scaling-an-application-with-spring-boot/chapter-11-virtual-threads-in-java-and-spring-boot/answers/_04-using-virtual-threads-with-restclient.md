## Q1. HTTP 호출이 가상 스레드의 이점이 가장 큰 이유

**I/O 바운드이기 때문이다 — 시간의 거의 전부가 네트워크 응답을 기다리는 데 쓰인다.**

```
플랫폼 스레드가 HTTP 호출
    → 300ms 동안 응답 대기
    → 그 300ms 내내 OS 스레드 하나가 묶여 있다
    → 동시 호출 100건이면 스레드 100개가 아무것도 안 하며 점유
```

> **이것이 리액티브 프로그래밍이 등장한 주된 이유였다. 그리고 가상 스레드가 훨씬 단순하게 같은 문제를 푼다.**

**[[01-understanding-virtual-threads]]의 "기다림이 없으면 없앨 낭비도 없다"의 정반대 경우다** — **기다림이 거의 전부이므로 없앨 낭비가 최대**다.

**해당하는 시나리오**: **알림 시스템, 감사 API, 서드파티 연동.**

## Q2. 블로킹 모델이 가상 스레드에서 장점이 되는 메커니즘

**가상 스레드는 블로킹 지점을 만나야 캐리어에서 내려오기 때문이다.**

> **코드가 "여기서 기다린다"고 말해야 JVM이 그 자리에서 스레드를 바꿔 끼울 수 있다.**

**책의 문장**: *"**블로킹 모델을 따르므로 가상 스레드와 자연스럽게 통합된다.**"*

```
1. 가상 스레드가 toBodilessEntity() 호출
2. 소켓 읽기에서 대기            ← 여기가 블로킹 지점
3. JVM 이 가상 스레드를 중단하고 캐리어에서 내린다
4. 캐리어는 다른 요청을 처리한다
5. HTTP 응답 도착 → 가상 스레드가 다시 얹혀 다음 줄부터 이어서 실행
```

> **코드 어디에도 콜백이 없다.** `restClient.post()...`가 반환되면 그다음 줄이 실행된다. **그런데 그 사이에 캐리어 스레드는 다른 일을 했다.**

**"블로킹 클라이언트는 나쁜 선택이다"는 오해다**(§5) — **가상 스레드에서는 오히려 맞는 선택**이다. **블로킹 지점이 있어야 JVM이 캐리어를 바꿔 끼울 수 있다.**

**역설이 여기 있다** — **논블로킹 코드를 쓰면 JVM이 개입할 지점이 없다.** 블로킹이 **협조 지점**이 된다.

## Q3. RestClient와 WebClient를 고르는 기준

| | **RestClient** | **WebClient** |
|---|---|---|
| 모델 | **동기·블로킹** | **논블로킹 리액티브** |
| 가상 스레드와 | **자연스럽다** | **`.block()`을 붙여야 하는데 리액티브 스타일을 우회한다** |
| 의도된 용도 | **명령형 애플리케이션** | **완전히 논블로킹인 리액티브 파이프라인** |

> **"명령형 애플리케이션에는 RestClient를 쓰고 WebClient는 리액티브 애플리케이션에만 쓰는 편이 일반적으로 낫다. 가상 스레드는 확장성을 위해 리액티브 모델이 필요할 일을 최소화한다."**

**"WebClient가 항상 더 확장성이 좋다"는 오해다**(§5) — **가상 스레드 위에서는 차이가 크게 줄고, 코드 복잡도는 WebClient가 훨씬 높다.**

**판별 요령**: **주변 코드가 명령형인가 리액티브인가.** 명령형 코드에서 WebClient를 쓰면 **`.block()`을 붙이게 되고**, 그것은 **두 모델의 나쁜 점만 합친 것**이다 — 리액티브의 복잡도에 블로킹까지.

**의존성도 Boot 4의 집중형 스타터 전략을 따른다**:
| 아티팩트 | 하는 일 |
|---|---|
| `spring-boot-starter-restclient` | **`RestClient` API** |
| `spring-boot-starter-restclient-test` | **HTTP 클라이언트 상호작용을 테스트에서 시뮬레이션·검증** |

**이름이 곧 범위이고, 런타임용과 테스트용이 짝을 이룬다** — [[../../part-2-creating-an-application-with-spring-boot/chapter-5-testing-with-spring-boot/01-junit-6-and-focused-test-starters|Ch5]]의 그 패턴.

## Q4. 세 단계 중 응답 시간을 붙잡는 것

| 단계 | **어디서** | **응답을 붙잡나** |
|---|---|---|
| 직원 저장 | 요청 스레드 | **예** (짧다) |
| 감사 | **`TaskExecutor`가 별도 가상 스레드로** | **아니다** |
| **알림** | **요청 스레드에서 블로킹 HTTP 호출** | **예** |

> **감사는 배경으로 넘겼는데 알림은 요청 스레드에서 그대로 기다린다. 그래서 알림이 300ms 걸리면 사용자도 300ms를 기다린다.**

**"알림 호출도 배경으로 돌고 있다"는 오해다**(§5) — **`TaskExecutor`에 넘기지 않았다.**

**책의 문장이 그 점을 정확히 좁힌다** — *"**알림 호출이 블로킹이더라도 가상 스레드에서 돌기 때문에 확장성을 제한하지 않는다.**"* **응답 시간이 아니라 확장성**을 말한 것이다.

**[[03-integrating-virtual-threads-with-taskexecutor]]에서 본 구분이 여기서 다시 필요하다** — **확장성과 응답 시간은 다른 축**이고, 이 절이 개선하는 것은 **확장성뿐**이다.

**응답 시간까지 줄이려면**: 알림도 `TaskExecutor`에 넘긴다. 그러면 [[03-integrating-virtual-threads-with-taskexecutor]]의 fire-and-forget 문제(예외가 갈 곳이 없다)가 따라온다 → [[06-error-handling-in-concurrent-tasks]].

## Q5. "확장성을 제한하지 않는다"와 "응답이 빨라진다"

| | **확장성** | **응답 시간** |
|---|---|---|
| 무엇을 재나 | **동시에 처리할 수 있는 요청 수** | **한 요청이 걸리는 시간** |
| 가상 스레드가 | **개선한다** | **그대로** |
| 개선하려면 | 가상 스레드 | **일을 응답 경로 밖으로** |

```
플랫폼 스레드:  100건 동시 호출 → 스레드 100개 점유 → 다른 요청을 못 받는다
가상 스레드:    100건 동시 호출 → 캐리어 몇 개만 → 다른 요청을 계속 받는다
                단, 각 호출은 여전히 300ms 걸린다
```

**"블로킹하지 않으므로 응답이 빨라진다"는 오해다**(§5) — **확장성이 좋아지지 응답 시간이 줄지는 않는다.**

**이 구분이 이 장 전체를 관통한다** — [[01-understanding-virtual-threads]]의 **"하나하나가 빠른 게 아니라 많이 만들 수 있는 것"**, [[03-integrating-virtual-threads-with-taskexecutor]]의 **"가상 스레드는 응답이 늦는 문제를 풀지 않는다"**가 같은 말이다.

## Q6. 로그 두 줄에서 "양쪽 다 가상 스레드"를 읽기

```text
Notification received ... VirtualThread[#72,http-nio-8080-exec-1]/runnable@ForkJoinPool-1-worker-1 | isVirtual: true
Notification sent ...     VirtualThread[#71,tomcat-handler-3]/runnable@ForkJoinPool-1-worker-2   | isVirtual: true
```

| 관찰 | **근거** |
|---|---|
| **클라이언트와 서버 양쪽 다 가상 스레드** | **두 줄 모두 `VirtualThread[…]`, `isVirtual: true`** |
| **스타일은 블로킹, 자원 사용은 아니다** | **코드에 콜백이 없는데 캐리어는 두 개(`worker-1`, `worker-2`)뿐** |
| 요청과 I/O가 **독립적으로** 확장 | **서로 다른 가상 스레드 번호(`#71`, `#72`)** |

> **두 번째 줄이 이 절의 제목이다 — "블로킹 스타일, 논블로킹 자원."**

**받는 쪽에서도 스레드를 찍는 설계 덕분이다** — `ApiNotificationController`가 **자기 스레드를 출력**하므로 **양쪽이 다 가상 스레드임이 드러난다.**

**"로그의 `ForkJoinPool-1-worker-N`이 다르면 다른 요청이다"는 오해다**(§5) — **캐리어일 뿐**이고, **요청을 구분하는 것은 `VirtualThread[#…]` 번호**다.

> **원문 불일치**: 수신 측 로그가 **`http-nio-8080-exec-1`**인데 **같은 애플리케이션의 다른 로그는 전부 `tomcat-handler-N` 형식**이다. **`http-nio-8080-exec-N`은 가상 스레드를 켜지 않은 Tomcat의 전통적 워커 이름**이라, **한 실행에서 두 명명 규칙이 섞여 나오는 것이 설명되지 않는다.**

## Q7. 자기 자신을 호출하는 구조가 플랫폼 스레드였다면 위험한 이유

**스레드 고갈로 교착될 수 있기 때문이다.**

```
플랫폼 스레드 풀 = 200개
요청 200건이 동시에 들어온다
  → 200개 스레드가 전부 요청 처리 중
  → 각자 자기 자신의 /notify 를 호출한다
  → 그 호출을 받아 줄 스레드가 없다
  → 전부 서로를 기다린다 = 교착
```

> **가상 스레드라 요청 스레드가 캐리어를 점유하지 않아 자기 호출 교착이 생기지 않는다.**

**역설적으로 이 예제 자체가 가상 스레드의 이점을 보여 주는 셈이다.**

**책이 이것을 설명하지 않는다** — `baseUrl("http://localhost:8080")`으로 **자기 자신을 호출**하는데 **왜 안전한지는 언급되지 않는다.**

**§6의 관련 경계들**:
- **자기 자신을 호출하는 구조는 예제용이다.** **실제로는 별도 서비스여야** 한다
- **타임아웃 설정이 없다.** **예제 코드에는 연결·읽기 타임아웃이 없어, 상대가 응답하지 않으면 가상 스레드가 무한히 매달린다.** **가상 스레드가 싸다고 해도 누수는 누수다**
- **리액티브 파이프라인 안에서는 WebClient가 맞다**

**타임아웃이 특히 실무적이다** — 가상 스레드는 **싸서 많이 만들 수 있는 만큼, 새는 것도 많아질 수 있다.**

## Q8. 보류음 비유가 깨지는 지점

**비유**: 가상 스레드 위의 블로킹 호출은 **"전화를 걸어 두고 보류음을 들으며 다른 서류를 처리하는 것"**이다.

**깨지는 지점**: **누가 서류를 처리하는지를 흐린다.**

> **실제로 다른 일을 하는 것은 전화를 건 사람(가상 스레드)이 아니라 책상(캐리어)이다. 전화를 건 사람은 그동안 통째로 자리를 비웠다가, 상대가 받으면 다시 그 책상에 앉는다.**

```
비유:  한 사람이 전화를 들고 서류도 본다  (한 주체가 두 일)
실제:  가상 스레드는 통째로 자리를 뜨고
       캐리어(책상)에 다른 가상 스레드가 앉는다  (주체가 교대)
```

**[[01-understanding-virtual-threads]]의 종업원 비유와 같은 결함이다** — **주체를 혼동시킨다.** 거기서도 **"자리를 뜨는 주체는 코드가 아니라 JVM"**이라고 했다.

**정확한 그림**: **캐리어가 자원이고, 가상 스레드는 그 위에 얹혔다 내렸다 하는 상태**다. 사람으로 치면 **책상이 귀하고 사람이 싼** 구조다.

**비유가 맞는 부분은 남는다** — **기다리는 동안 자원이 놀지 않는다**는 핵심(Q2). 깨지는 것은 **누가 무엇을 하는가**다.
