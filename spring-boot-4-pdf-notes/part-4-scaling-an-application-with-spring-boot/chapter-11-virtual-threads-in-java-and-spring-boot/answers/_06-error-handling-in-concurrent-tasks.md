## Q1. 배경 작업의 예외가 HTTP 응답에 영향을 주지 않는 이유

**예외 전파는 한 스레드 안에서만 일어나기 때문이다.**

```
동기 흐름 (같은 스레드):
  Repository → Service → Controller → Spring MVC 예외 처리기 → 500 응답

TaskExecutor (다른 스레드):
  작업 안에서 예외 → 이 스레드의 스택 최상단까지 → 여기서 끝. 넘어갈 곳이 없다
  (컨트롤러 스레드는 이미 응답을 보냈다)
```

> **컨트롤러 스레드는 `taskExecutor.execute(...)`가 반환된 순간 다음 줄로 갔다. 작업의 완료를 기다리지 않으므로, 그 작업에서 난 예외를 받을 방법이 없다.**

**책의 설명**: *"**작업이 다른 스레드에서 돌고 컨트롤러 스레드는 완료를 기다리지 않으므로, 예외가 원래 요청 컨텍스트로 전파되지 않는다.**"*

**실험 결과가 놀랍다** — **예외는 던져지는데 HTTP 응답은 정상적으로 반환된다.**

**[[03-integrating-virtual-threads-with-taskexecutor]]가 남긴 질문의 답이다** — fire-and-forget이면 **예외가 갈 곳이 없다.**

## Q2. 그 분리가 의도적이라는 근거

**감사 실패를 응답에 반영하면 더 나쁜 일이 생긴다.**

| 감사 실패를 | **결과** |
|---|---|
| **응답에 반영하면** | **저장은 됐는데 실패로 보인다. 사용자가 재시도해 중복 생성** |
| **응답과 분리하면** | **사용자는 성공을 본다. 감사 로그만 빈다** |

> **"비핵심 실패가 사용자의 응답에 영향을 주지 않게 하여, 애플리케이션이 응답성을 유지하면서 배경 오류를 독립적으로 다룰 수 있게 한다."**

**핵심 논리**: **직원은 이미 저장됐다.** 감사 로그 기록이 실패했다고 **직원 생성 자체가 실패한 것으로 처리하면** **일어난 일과 보고된 일이 어긋난다.**

**두 번째가 낫다. 다만 조건이 하나 붙는다 — 누군가는 그 실패를 알아야 한다.**

**"배경 작업의 예외가 안 보이는 건 버그다"는 오해다**(§5) — **의도적 설계**다. **"그러니 그냥 무시해도 된다"도 오해다** — **명시적으로 기록**해야 한다.

## Q3. `catch` 안에 반드시 있어야 하는 것

**무언가를 남기는 것 — 로깅과 모니터링.**

> **핵심은 `catch` 안에서 무언가를 남긴다는 것이다. 여기서는 `System.err`이지만 실제로는 로거와 메트릭이 들어가야 한다.**

**책의 원칙**: *"**오류는 작업 안에서 명시적으로 처리돼야 한다.**"*

> **try-catch 블록이 작업 안에서 오류를 지역적으로 처리해, 실패가 지역에서 다뤄지고 조용한 실패로 끝나지 않게 한다.**

**[[../../part-5-observing-spring-boot-4-applications/chapter-13-observing-spring-boot-4-applications/04b-adding-custom-business-metrics-with-micrometer|Ch13]]에서 알림 실패를 `outcome="failed"` 카운터로 세었던 것이 정확히 이 자리에 들어갈 것이다.**

**§6의 경고**: **`catch (Exception ex)`로 삼키기만 하면 안 된다.** **삼키기만 하는 catch는 예외가 없는 것보다 나쁘다** — 실패가 **일어났는데 흔적도 없다.**

**로깅만으로 부족한 이유**: 로그는 **사람이 봐야** 알고, 배경 작업 실패는 **아무도 안 본다.** **메트릭이 있어야 알림을 걸 수 있다.**

---

## Q4. `exceptionally`가 `try-catch`와 다른 점

**체인의 일부라는 것.**

> **여러 단계를 이어 붙인 뒤 마지막에 한 번 붙이면 앞의 어느 단계에서 난 예외든 여기로 온다.**

```java
CompletableFuture.runAsync(step1)
    .thenRun(step2)
    .thenRun(step3)
    .exceptionally(ex -> { ... });   // step1~3 어디서 난 예외든 여기로
```

**`try-catch`라면 단계마다 감싸거나 전체를 한 블록에 넣어야** 한다. **비동기 체인에서는 단계마다 스레드가 다를 수 있으므로 후자가 불가능**하다.

**`try-catch`가 충분한 경우**: **작업 하나.** [[03-integrating-virtual-threads-with-taskexecutor]]의 감사 로그가 그렇다.

**`CompletableFuture`가 필요한 경우** — 책이 드는 넷:
- **여러 서비스를 병렬로 호출**한다
- **그 응답들을 결합**한다
- **실패하면 폴백 로직**을 적용한다
- **모든 작업이 끝난 뒤에만** 후속 단계를 실행한다

**`exceptionally`**: **예외 시 실행될 대체 처리를 붙이는 메서드.** **실패를 명시적으로 다뤄 조용한 실패를 막는다.**

## Q5. 이 장의 `CompletableFuture` 예제가 가상 스레드에서 안 도는 이유

**`runAsync()`에 실행자를 주지 않았기 때문이다.**

```
taskExecutor.execute(...)          → Spring Boot 의 기본 실행자 = 가상 스레드
CompletableFuture.runAsync(...)    → ForkJoinPool.commonPool() = 플랫폼 스레드
```

> **`runAsync()`는 기본적으로 JVM의 공용 스레드 풀을 쓴다. Spring 애플리케이션에서는 가상 스레드를 백엔드로 하는 것 같은 커스텀 실행자를 넘겨 동시성 모델에 맞출 수 있다.**

**그런데 인쇄된 예제 코드는 실행자를 주지 않는다.**

**[[02-using-virtual-threads-in-a-spring-boot-application]]에서 켠 `spring.threads.virtual.enabled=true`가 이 코드에는 적용되지 않는다** — 그 프로퍼티는 **"Spring Boot가 자동 설정하는 인프라"**에만 미치고, **`CompletableFuture.runAsync()`는 애플리케이션이 직접 부르는 JDK API**다.

**`ForkJoinPool.commonPool()`은 기본적으로 `코어 수 - 1`개의 플랫폼 스레드를 갖는다.** **블로킹 작업을 여기 던지면 풀이 금방 마른다.**

> **원문의 공백**: 책이 "커스텀 실행자를 줄 수 있다"고 짚기는 하지만 **예제 코드는 주지 않은 채로 남는다.** **장의 주제가 가상 스레드인데 마지막 예제가 플랫폼 스레드에서 도는 셈**이고, **그 사실이 강조되지 않는다.**

**올바른 형태**: `runAsync(task, Executors.newVirtualThreadPerTaskExecutor())` 또는 **주입받은 `TaskExecutor`를 넘긴다.**

**이것이 [[02-using-virtual-threads-in-a-spring-boot-application]]의 "LED 교체 비유가 깨지는 지점"의 실제 사례다** — **입주자가 개인적으로 가져다 놓은 스탠드.**

## Q6. 가상 스레드와 `CompletableFuture`가 "층이 다르다"

| | **가상 스레드** | **`CompletableFuture`** |
|---|---|---|
| **푸는 문제** | **스레드가 비싸다** | **작업 조율이 어렵다** |
| 코드 모양 | **순차적** | **체인** |
| 여러 작업 결합 | **직접 해야 한다** | **`thenCombine`·`allOf`** |
| 예외 | **try-catch** | **`exceptionally`** |

> **하나는 실행 모델, 하나는 조율 API다. `runAsync`에 가상 스레드 실행자를 주면 둘을 함께 쓰는 것이다.**

**책의 정리**: *"**가상 스레드와 `CompletableFuture`는 서로를 보완한다. 가상 스레드는 블로킹 실행을 단순화하고, `CompletableFuture`는 비동기 워크플로에 대한 제어를 제공한다.**"*

**"층이 다르다"가 뜻하는 것**: **경쟁 관계가 아니라 조합 관계**다. **"둘 중 뭘 쓸까"가 아니라 "가상 스레드 실행자 위에서 CompletableFuture 체인"**이 답이다.

**[[05-using-interface-proxy-http-service-clients]]의 교훈과 같다** — **개선 항목을 층으로 분리해 생각한다.** 거기서는 **실행 모델과 API 표현**이었고, 여기서는 **실행 모델과 조율 API**다.

**책의 마지막 강조**: *"**배경 작업의 예외는 HTTP 응답에 영향을 주지 않으므로, 오류 처리는 명시적이어야 하며 적절한 로깅과 모니터링이 따라야 한다.**"*

## Q7. 구조적 동시성의 세 보장과 이름의 유래

| 보장 | **뜻** |
|---|---|
| **스코프를 벗어나기 전 모든 작업 완료** | **떠도는 작업이 남지 않는다** |
| **실패가 일관되게 전파** | **하나가 실패하면 정해진 방식으로 알려진다** |
| **관련 작업을 함께 취소** | **하나가 실패하면 나머지를 멈출 수 있다** |

**이름의 유래**:
> **프로그래밍에서 `goto`를 버리고 블록 구조를 택했듯, 동시 작업도 블록처럼 열고 닫히게 만든 것이다. 블록을 벗어나면 그 안에서 시작한 작업은 전부 끝나 있다.**

```
비구조적:  taskExecutor.execute(...)  → 어디로 갔는지, 끝났는지 모른다  (goto 같다)
구조적:    try (var scope = ...) { ... }  → 블록을 나가면 다 끝나 있다  (블록 같다)
```

**Q1의 문제가 근본적으로 해결된다** — **스코프가 완료를 보장하므로 예외를 받을 자리가 생긴다.**

**`TaskExecutor`와 `CompletableFuture`가 요구하는 것**: **명시적인 조율·오류 처리·생명주기 관리.** 구조적 동시성은 **그것을 언어 구조가 대신**한다.

**책의 판단이 신중하다** — **집필 시점에 아직 preview 기능**이라, 이 장의 예제는 **운영에서 검증되고 널리 지원되는** `TaskExecutor`와 `CompletableFuture`에 의존한다. 더 알아볼 곳으로 **JEP 505**를 가리킨다.

**"구조적 동시성을 지금 쓰면 된다"는 오해다**(§5) — **preview**다.

## Q8. 반송 편지 비유가 깨지는 지점

**비유**: 배경 작업의 예외는 **"우체통에 넣은 편지가 반송된 것"**이다. **보낸 사람은 이미 자리를 떴고 반송 사실을 모른다.**

**깨지는 지점**: **반송 편지가 어딘가에는 남는다는 인상을 준다.**

> **실제로 잡지 않은 예외는 아무 데도 남지 않고 사라진다. 반송함이 있는 게 아니라, 처리자를 만들어 두지 않으면 편지가 증발하는 쪽이다.**

```
우편:  반송 편지 → 반송함에 쌓인다 → 나중에 확인할 수 있다
예외:  잡지 않으면 → 아무 데도 없다 → 확인할 방법이 없다
```

**Q3의 "`catch` 안에 무언가가 있어야 한다"가 이 성질에서 나온다** — **기본 저장소가 없으므로 우리가 만들어야** 한다.

**정확한 그림**: **예외를 잡는 것은 "반송함을 확인하는 일"이 아니라 "반송함을 설치하는 일"**이다.

**비유가 맞는 부분은 남는다** — **보낸 사람이 모른다**(Q1). 깨지는 것은 **흔적의 유무**다.

**§6의 나머지 경계**:
- **반드시 처리돼야 하는 일은 배경 작업에 두면 안 된다** — **애플리케이션이 죽으면 사라진다.** **메시지 큐가 맞다** → [[../chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/05-reliability-patterns-retries-dlt-idempotency|Ch12]]
- **`runAsync`의 기본 풀에 블로킹 작업을 던지지 마라** — **공용 풀이 마르면 애플리케이션 전체가 영향을 받는다**(Q5)
