## Q1. 가상 스레드를 켰는데도 응답이 느릴 수 있는 이유

**가상 스레드는 스레드가 부족한 문제를 풀지, 응답이 늦는 문제를 풀지 않는다.**

```
동기:   저장 20ms → 감사 50ms → 알림 300ms → 응답 = 370ms
분리:   저장 20ms → 응답 = 20ms       (감사·알림은 뒤에서)
```

> **"동기적으로 실행하면 응답 시간이 불필요하게 늘어난다."**

**응답을 빨리 주려면 일을 응답 경로 밖으로 내보내야 한다.**

**대상이 되는 일의 성질**: **중요하지만 사용자에게 즉시 응답하는 것의 일부가 아니다** — **감사 로그, 알림, 외부 프로세스 트리거.**

**"가상 스레드를 켜면 응답이 빨라진다"는 오해다**(§5) — **가상 스레드는 동시 처리 수를 늘리지 개별 응답 시간을 줄이지 않는다.**

**두 축을 구분하는 것이 이 장 전체의 요령이다**:
```
확장성(동시 처리 수)  ← 가상 스레드
응답 시간             ← 일을 응답 경로 밖으로 내보내기
```

## Q2. `TaskExecutor` + 가상 스레드로 없어지는 튜닝 항목

**풀 크기 튜닝이다.**

| | **플랫폼 스레드 풀 + TaskExecutor** | **가상 스레드 + TaskExecutor** |
|---|---|---|
| 동시 배경 작업 수 | **풀 크기가 상한** | **사실상 무제한** |
| 풀이 마르면 | **작업이 큐에서 대기** | — |
| 작업이 블로킹하면 | **풀 스레드 하나가 묶인다** | **캐리어가 풀려난다** |
| **튜닝** | **풀 크기를 맞춰야 한다** | **거의 필요 없다** |

> **`TaskExecutor`가 가상 스레드와 결합하면 제출된 각 작업이 자기 가상 스레드에서 돈다.**

**풀 크기 튜닝이 어려운 이유**: **너무 작으면 대기가 생기고, 너무 크면 메모리와 문맥 교환 비용**이다. 그리고 **적정값이 워크로드마다 다르다.** 가상 스레드는 **그 문제 자체를 없앤다.**

**[[02-using-virtual-threads-in-a-spring-boot-application]]에서 켠 프로퍼티가 여기까지 미친다** — **Spring Boot의 기본 실행자를 쓰므로 자동으로 가상 스레드가 된다.**

**`TaskExecutor`**: **작업을 별도 스레드에서 실행해 주는 Spring의 추상.** 인터페이스가 단순하다 — **`execute(Runnable)` 하나로 호출자를 막지 않고 일을 넘긴다.**

## Q3. `AuditService`가 스레드를 모르는 것이 좋은 설계인 이유

**코드를 바꾸지 않고 실행 모델만 갈아 끼울 수 있기 때문이다.**

```java
public AuditService(TaskExecutor taskExecutor) { ... }
//                  └──────┬──────┘
//                   인터페이스. 어떤 구현인지는 설정이 정한다
```

> **`AuditService`는 자기 작업이 어느 스레드에서 돌지 모른다. 그것은 [[02-using-virtual-threads-in-a-spring-boot-application]]의 프로퍼티가 정한다.**

**얻는 것**:
- **프로퍼티 하나로 플랫폼 → 가상 전환** — 서비스 코드는 그대로
- **테스트에서 동기 실행자로 교체** 가능 — 배경 작업을 즉시 실행시켜 검증
- **실행 정책이 설정에 모인다** — 서비스마다 흩어지지 않는다

**[[../../part-1-the-basics-of-spring-boot/chapter-1-core-features-of-spring-boot/01-autoconfiguring-spring-beans|Ch1]]의 원칙과 같다** — **교체 가능한 경계를 만들고, 어느 구현을 등록할지 구성에서 결정한다.**

**"`TaskExecutor`가 곧 스레드 풀이다"는 오해다**(§5) — **인터페이스**이고, **가상 스레드가 켜져 있으면 작업마다 가상 스레드**다.

## Q4. 저장을 먼저 하고 감사를 나중에 부르는 순서의 의미

**저장된 엔티티(`employeeSaved`)를 감사에 넘기므로 DB가 채워 준 `id`가 로그에 들어간다.**

```java
Employee employeeSaved = repository.save(employeeToSave);
auditService.registerEmployeeCreation(employeeSaved);   // ← 저장된 것을 넘긴다
```

**순서를 바꾸면**: `employeeToSave`를 넘기게 되고 **`id`가 `null`**이다. 감사 로그에 **어떤 레코드인지 식별할 수단이 없어진다.**

**[[../chapter-10-working-with-data-reactively/03-creating-reactive-repositories-and-r2dbc-access|Ch10]]의 `save()` 반환값 이야기와 같은 지점이다** — **`save()`가 돌려주는 것이 `id`가 채워진 객체**다.

**그리고 `registerEmployeeCreation`이 즉시 반환**되므로 **`return "redirect:/"`가 곧바로 실행**된다. **감사 작업은 뒤에서 계속된다.**

**즉 이 순서는 "동기적으로 필요한 것 먼저, 비동기로 넘길 것 나중"이라는 일반 규칙의 사례**다.

## Q5. `task-1`과 `tomcat-handler-0`이 구분해 주는 것

**요청 스레드인가 배경 작업 스레드인가.**

| | **요청 처리** | **배경 작업** |
|---|---|---|
| 이름 | `tomcat-handler-0` | **`task-1`** |
| 종류 | `VirtualThread[#61,…]` | `VirtualThread[#67,…]` |
| 캐리어 | `ForkJoinPool-1-worker-1` | `ForkJoinPool-1-worker-2` |
| `isVirtual` | true | **true** |

**책이 짚는 세 관찰**:
1. **`task-1`** — **`TaskExecutor`에 제출된 작업임을 보여 준다. 요청 스레드가 아니다.**
2. **`VirtualThread[#…]`** — **배경 작업도 가상 스레드로 실행된다.**
3. **`isVirtual: true`** — **비동기 처리에도 가상 스레드가 쓰인다는 확인.**

> **"HTTP 요청뿐 아니라 배경 작업도 가상 스레드의 이점을 누릴 수 있어, 프로그래밍 모델을 단순하게 유지하면서 효율적으로 일을 덜어낼 수 있다."**

**이 로그가 두 가지를 동시에 증명한다** — **분리됐다**(이름이 다르다)와 **둘 다 가상이다**(`isVirtual: true`).

## Q6. `TaskExecutor`와 `AsyncTaskExecutor`를 고르는 기준

**결과나 완료를 알아야 하는가.**

| | **`TaskExecutor`** | **`AsyncTaskExecutor`** |
|---|---|---|
| 반환값 | **없음** | **`Future` / `CompletableFuture`** |
| 완료 추적 | **불가** | **가능** |
| 결과 회수 | 불가 | 가능 |
| 예외 처리 | **작업 안에서만** | **명시적으로 다룰 수 있다** |
| 쓰는 곳 | **fire-and-forget** | **조율이 필요한 작업** |

> **감사나 로깅 같은 단순 배경 작업에는 `TaskExecutor`가 더 단순하고 적절하고**, **완료를 추적하거나 결과를 회수하거나 예외를 명시적으로 다뤄야 할 때 `AsyncTaskExecutor`를 쓴다.**

**"`execute`가 반환되면 작업이 끝난 것이다"는 오해다**(§5) — **시작만 됐다.** **끝났는지 알려면 `AsyncTaskExecutor`가 필요하다.**

**단순한 쪽을 기본값으로 두는 것이 요점이다** — 추적이 필요 없는데 `Future`를 받으면 **아무도 안 보는 객체**가 생긴다.

## Q7. fire-and-forget이 남기는 질문

> **fire-and-forget이면 그 작업에서 난 예외는 어디로 가나?**

**컨트롤러는 이미 응답을 보냈고 아무도 결과를 보지 않는다.**

**"배경 작업의 예외도 500 응답이 된다"는 오해다**(§5) — **되지 않는다. 응답은 이미 나갔다.**

```
컨트롤러: redirect:/ 반환 → 사용자에게 200/302 가 나갔다
배경 작업: 그 뒤에 예외 발생 → 갈 곳이 없다
```

**그 답이 [[06-error-handling-in-concurrent-tasks]]이며, 거기서 `CompletableFuture`도 함께 나온다.**

**관련된 다른 경계들**(§6):
- **결과가 필요한 작업에는 맞지 않는다** — `AsyncTaskExecutor`나 `CompletableFuture`
- **순서가 보장되지 않는다** — **여러 작업을 제출하면 실행 순서가 정해지지 않는다**
- **애플리케이션이 죽으면 대기 중인 작업이 사라진다** — **반드시 처리돼야 하는 일이라면 메시지 큐가 맞다** → [[../chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/01-asynchronous-and-event-driven-communication|Ch12]]

**세 번째가 가장 무겁다** — `TaskExecutor`는 **프로세스 메모리 안의 큐**이므로 **내구성이 없다.**

## Q8. 카운터와 뒷방 비유가 깨지는 지점

**비유**: `TaskExecutor`는 **"카운터 직원이 서류를 뒷방으로 넘기는 것"**이다. **손님은 기다리지 않고 나간다.**

**깨지는 지점**: **뒷방에서 서류가 찢어졌을 때 어떻게 되는지를 담지 못한다.**

> **손님은 이미 떠났고 카운터는 그 사실을 모른다.**

**그것이 [[06-error-handling-in-concurrent-tasks]]가 다루는 문제이며, 비유상으로는 "뒷방에 자체 기록 절차가 있어야 한다"에 해당한다.**

```
비유:  서류가 찢어지면 누군가 알아채고 손님에게 연락한다
실제:  예외가 나면 아무 데로도 전파되지 않는다
       (기본 실행자는 로그조차 안 남길 수 있다)
```

**Q7과 같은 문제의 두 표현이다** — **응답 경로에서 떼어 내면 실패 보고 경로도 함께 떼어진다.**

**해법의 방향**: **뒷방 안에서 처리한다** — 작업 람다 안에 try-catch, 또는 `CompletableFuture.exceptionally`. **밖에서는 알 수 없으므로 안에서 기록해야 한다.**

**비유가 맞는 부분은 남는다** — **손님이 기다리지 않는다**(Q1의 응답 시간 단축). 깨지는 것은 **실패 처리**다.
