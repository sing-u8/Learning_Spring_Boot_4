## Q1. `thenMany`가 없으면

**테이블이 없는 상태에서 insert가 나갈 수 있다.**

> **`thenMany`가 이 파이프라인의 뼈대다. 순차 실행 보장이 없으면 테이블이 없는 상태에서 insert가 나갈 수 있다.**

```
CREATE TABLE ... .fetch().rowsUpdated()
        │
        └─ thenMany ─▶ insert 1      ← 테이블이 만들어진 뒤에만 돈다
                └─ thenMany ─▶ insert 2
                        └─ thenMany ─▶ insert 3
                                └─ subscribe()
```

**`thenMany`**: **앞 단계 완료 후 이어질 연산을 잇는 연산자.**

**`rowsUpdated()`가 함께 필요한 이유**: **값보다 완료 시그널이 필요하다.** `CREATE TABLE`의 반환값에는 관심이 없고 **"끝났다"는 신호**만 있으면 된다.

**`thenMany`와 `then`의 구분**(§5): **`then()`은 앞 값을 버리고 완료만 받는다.** **`thenMany`는 이어질 것이 여러 값일 수 있을 때** 쓴다. 여기서는 **순서 보장이 목적이라 어느 쪽이든 되지만, 뒤에 오는 것이 `Mono`인지 `Flux`인지에 맞춘다.**

**이 방식이 주는 것**: **초기화 과정 전체를 완전히 리액티브로 유지**한다. **스키마 생성과 insert 연산이 하나의 파이프라인으로 조합**되어 **각 단계가 순차 실행됨을 보장**한다.

## Q2. `subscribe()`를 빼면 / 인자 없이 부르면

**빼면: 아무것도 실행되지 않는다.**

**게으른 평가 때문에 구독자가 붙기 전에는 아무것도 실행되지 않는다.** 파이프라인은 **조립되기만 하고** 테이블도 데이터도 생기지 않는다. **그리고 오류도 안 난다.**

**인자 없이 부르면: 오류를 삼킨다.**

> **인자 없는 `subscribe()`는 오류 처리를 포기하는 것이다.** `CREATE TABLE`이 실패해도 **예외가 어디로도 전파되지 않고, 애플리케이션은 정상 기동한다.** 그러고 나서 **첫 요청에서 "테이블 없음"이 터진다.**

**대응**:
```java
.subscribe(v -> {}, err -> log.error("초기화 실패", err));
// 또는 CommandLineRunner 안에서
.block();   // 기동을 막는다
```

> **기동 시점의 블로킹은 이벤트 루프 문제가 아니다.**

**이 단서가 중요하다** — 리액티브에서 `block()`이 금지되는 것은 **이벤트 루프 스레드에서** 부를 때다. `CommandLineRunner`는 **기동 스레드**에서 돌므로 문제가 없고, 오히려 **초기화 실패를 기동 실패로 만드는** 것이 안전하다.

**비유의 깨짐이 이 둘이다** — **이사에서는 지시 없이도 사람이 알아서 시작하지만 리액티브 파이프라인은 `subscribe()` 없이는 계획서로만 남는다.** 그리고 **이사 중 선반이 부러지면 바로 알지만**, 이 코드는 **실패해도 애플리케이션이 정상 기동하고 테이블 없는 채로 서비스가 뜬다.**

## Q3. JPA에서 오는 사람이 가장 먼저 놀라는 차이

**스키마를 우리가 직접 정의해야 한다는 것.**

> **JPA에는 `ddl-auto`가 있어 엔티티에서 테이블을 만들어 줬다. R2DBC에는 그런 것이 없다.**

**스키마가 외부에 정의돼 있지 않다면 프로그래밍 방식으로 만들고 샘플 데이터를 리액티브 파이프라인으로 싣는다.**

**그리고 그 지점에서 [[02-choosing-r2dbc-and-a-reactive-data-store]]가 남긴 긴장이 드러난다**:

> **"R2DBC는 저수준이라 툴킷을 쓰라"고 했는데, 스키마만은 툴킷이 덮어 주지 않는다.**

**책이 자기 조언을 지키지 못하는 지점**(§5) — 초기화 코드는 **`template.getDatabaseClient().sql(...)`로 결국 저수준 `DatabaseClient`를 직접 쓴다.** **모순은 아니지만, 스키마 정의만은 툴킷이 덮어 주지 않는 영역이라는 사실이 원문에 명시되지 않는다.**

**왜 그래야 하나**: **`R2dbcEntityTemplate`은 도메인 타입 연산만 안다.** **DDL은 그 밖이라** 저수준으로 내려가야 한다.

**부수적 대가**: **`IDENTITY`는 H2 방언이다.** **다른 DB로 옮기면 이 SQL은 그대로 통하지 않는다.** **프로그래밍 방식 스키마 생성의 대가다.**

**[[03-creating-reactive-repositories-and-r2dbc-access]]의 "JPA의 편의가 없다"와 같은 목록이다** — 지연 로딩, 연관관계 매핑, 영속성 컨텍스트, dirty checking, **그리고 `ddl-auto`.**

## Q4. 이 초기화 코드를 production에 두면 안 되는 이유

**① 코드로 스키마를 만들면 안 된다.**
> **Flyway·Liquibase 같은 마이그레이션 도구를 쓴다. 이 방식은 예제용이다.**

**버전 관리가 없다** — 무엇을 언제 적용했는지 기록이 없고, **스키마 변경 시 되돌릴 방법도 없다.** [[../../part-3-releasing-an-application-with-spring-boot/chapter-7-releasing-an-application-with-spring-boot/04c-running-the-setup-with-docker-compose|Ch7]]이 같은 말을 했다.

**② `subscribe()`를 인자 없이 쓰면 오류가 조용히 사라진다**(Q2).

**③ 인스턴스가 여럿이면 중복 실행된다.**
> **기동할 때마다 `CREATE TABLE`이 돌아 두 번째부터 실패한다.**

**[[../../part-3-releasing-an-application-with-spring-boot/chapter-7-releasing-an-application-with-spring-boot/04c-running-the-setup-with-docker-compose|Ch7]]의 사전 적재 경고와 정확히 같은 문제다** — **"시작하고 멈추며 여러 인스턴스로 도는 애플리케이션은 지속 데이터 관리 정책을 적용하는 수단이 아니다."** 거기서는 `@Profile("setup")`으로 막았다.

**④ (추가) DDL을 리액티브 파이프라인에 넣는 것이 필수가 아니다.**
> **기동 시점의 일회성 작업이므로 블로킹이어도 무방하다.**

**즉 이 코드의 리액티브 조립은 "일관성을 위한 선택"이지 성능 요구가 아니다.** Q2의 `block()` 권고와 이어진다.

**`CommandLineRunner`를 고른 이유는 여전히 맞다** — **기동이 끝난 뒤여야** 한다. **bean 생성 도중에 DB에 쓰면 연결 팩토리가 아직 준비되지 않았을 수 있다.**
