## Q1. 웹 애플리케이션 스레드가 시간을 보내는 방식

**대부분의 시간을 일하지 않고 기다리며 보낸다.**

**블로킹 모델에서 벌어지는 일**: 들어오는 요청마다 **전용 스레드**가 배정되고(**스레드-per-요청**), 그 스레드가 DB 호출이나 HTTP 요청을 수행하면 **결과를 기다린다.** 그동안 스레드는:
- **아무 일도 하지 않는다 (idle)**
- **그런데도 시스템 자원을 소비한다**

> **두 번째 줄이 핵심이다. 스레드는 존재만으로 비용이다** — **스택 메모리를 잡고, 스케줄러의 관리 대상이고, OS의 자원**이다.

**DB 응답이 50ms 걸린다면, 그 50ms 동안 스레드는 비싼 자리를 차지한 채 아무 가치도 만들지 않는다.**

**왜 중요한가**: [[01-reactive-programming-and-backpressure]]의 **"스레드가 하나뿐인 브라우저가 왜 잘 확장되나"**에 대한 답이 여기 있다. **스레드가 적으면 일을 적게 하는 것이 아니라, 기다리는 자리가 적을 뿐**이다.

**그리고 이것이 리액티브의 적용 범위를 정한다** — **I/O 바운드에서만 이득이 나오고 CPU 바운드에서는 아무것도 개선되지 않는다.** 거기에는 **없앨 기다림이 없기** 때문이다.

## Q2. "한 스레드로 더 많은 일을 동시에"가 틀린 요약인 이유

**책이 못 박는 문장**:

> **목표는 한 스레드로 동시에 더 많은 일을 하는 것이 아니라, I/O 연산이 끝나기를 기다리며 시간을 낭비하지 않는 것이다.**

**즉 리액티브는 CPU를 더 빠르게 만들지 않는다. 낭비를 없앨 뿐이다.**

**틀린 요약이 낳는 오해들**:
| 오해 | 사실 |
|---|---|
| "논블로킹이면 더 빠르다" | **개별 요청의 응답 시간은 오히려 조금 느려질 수도 있다.** 빨라지는 것은 **같은 자원으로 감당하는 동시 요청 수**다 |
| "스레드가 적으니 CPU를 덜 쓴다" | **반대에 가깝다.** 스레드가 놀지 않으므로 **CPU 사용률은 올라간다.** **그게 목표다** |
| "CPU 바운드도 빨라진다" | **없앨 기다림이 없으므로 이득이 없다** |

**처리량과 지연은 다른 축이다** — 리액티브가 개선하는 것은 **처리량(throughput)**이고, **지연(latency)**은 오히려 약간 나빠질 수 있다(시그널 전달·스케줄링 오버헤드).

**리액티브 프로그래밍이 서는 자리**: **논블로킹 실행 + 배압 + 비동기 데이터 스트림**을 결합해, **시스템 자원이 효율적으로 쓰이고 처리할 여력이 있을 때만 작업이 진행되게** 한다.

## Q3. 스레드를 늘려 동시성을 올리는 방식의 세 한계

| 결과 | **왜 문제인가** |
|---|---|
| **큰 thread pool** | **스레드마다 스택 메모리가 든다** |
| **메모리 사용 증가** | **인스턴스당 감당할 수 있는 동시성이 메모리에 갇힌다** |
| **비싼 컨텍스트 스위칭** | **코어보다 스레드가 많을수록 CPU가 일 대신 전환에 시간을 쓴다** |

> **여기서 [[01-reactive-programming-and-backpressure]]가 말한 "수백~수천 인스턴스"의 이유가 드러난다.**

```
인스턴스 하나가 감당하는 동시성 = 스레드 수에 묶임
스레드 수 = 메모리와 스위칭 비용에 묶임
        ↓
인스턴스를 늘리는 것 말고 방법이 없어진다
```

**그것이 클라우드 청구서의 구조적 원인이다.**

**논블로킹이 푸는 방식**:
1. **연산을 시작만 한다** — **결과를 붙들고 있을 이유가 없기** 때문이다
2. **스레드를 반납한다** — **놀 바에 다른 요청을 처리하는 편이 낫다**
3. **결과가 오면 시그널로 알린다** — **어느 스레드든 이어받을 수 있어야** 한다
4. **남은 처리가 이어진다** — **처음 그 스레드일 필요는 없다**

> **그래서 적은 수의 스레드가 많은 수의 동시 요청을 다룰 수 있다.**

**4번이 대가를 만든다** — **스레드가 요청을 따라가지 않으므로 스택 트레이스가 한 요청의 전체 흐름을 보여 주지 않는다.** 이건 **학습 곡선이 아니라 영구적인 운영 비용**이다.

## Q4. 별도 스레드에 던져 놓고 거기서 블로킹하면

**호출자는 안 막히지만 그 스레드는 여전히 막혀 있다. 자원 관점에서는 아무것도 개선되지 않는다.**

```
호출자 스레드:  작업을 던지고 즉시 반환   ← 비동기 ✅
작업 스레드:    DB 응답을 50ms 기다림     ← 여전히 블로킹 ❌

▶ 기다리는 스레드의 개수는 그대로다
```

> **비동기 ≠ 논블로킹**

**Q1의 기준으로 판별하면 명확하다** — **"어딘가에서 스레드가 idle인 채 자원을 잡고 있는가?"** 그렇다면 개선이 없다. **기다림을 다른 스레드로 옮겼을 뿐**이다.

**어디서 이 실수가 나오나**: `CompletableFuture.supplyAsync(() -> jdbcTemplate.query(...))` 같은 코드. **API는 비동기로 보이지만 풀의 스레드 하나가 그대로 막힌다.**

**진짜 논블로킹이 되려면 I/O 자체가 논블로킹이어야 한다** — 드라이버가 **결과가 준비되면 시그널을 보내는** 방식이어야 한다. 그래서 **R2DBC** 같은 리액티브 드라이버가 따로 존재한다.

**같은 논리가 스택 전체에 적용된다**(§6): **스택 전체가 논블로킹이 아니면 한 지점의 블로킹이 이벤트 루프를 잡는다** → [[04a-scaling-with-project-reactor]].

**비유로 보면** 식당 종업원 — 논블로킹 종업원은 **주문을 주방에 넘기고 바로 다음 테이블로 간다.** **깨지는 지점 둘**:
- **종업원은 어느 음식이 어느 테이블 것인지 기억하지만, 논블로킹에서는 그 문맥을 프레임워크가 들고 다녀야 한다** — 그래서 **스택 트레이스가 끊긴다**
- **종업원 하나가 직접 요리를 시작하면 다시 모두가 멈춘다** — 그게 **"이벤트 루프에서 블로킹"**이다

**대안 하나**(§6): **명령형을 유지하면서 같은 목표를 노리는 길도 있다** — **가상 스레드**.
