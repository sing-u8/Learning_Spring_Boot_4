## Q1. POST를 하려면 GET에서 빈 객체를 줘야 하는 이유

**Thymeleaf가 `th:field`로 입력 칸을 만들려면 어떤 필드가 있는지 알아야 하고, 그 정보는 실제 객체 인스턴스에서 온다.**

```java
.modelAttribute("newEmployee", new Employee("", ""))   // ← 이 한 줄
```

**앞 버전과 딱 한 줄 다르다.**

**두 가지 일을 한다**:
- **어떤 필드가 있는지** — `th:field="*{name}"`이 대응할 대상
- **입력 칸의 초기값** — **수정 폼이라면 그 객체의 현재 값**이 들어간다. **새로 만드는 경우이므로 빈 값**이다

> **이 한 줄이 HTML 폼을 만들기 시작하는 데 필요한 전부다.**

**빼먹으면**: **폼이 아예 렌더링되지 않고 예외가 난다.** 비유의 깨짐이 이것이다 — **종이 양식은 칸이 비어 있어도 존재하지만, 모델 속성을 빼먹으면 폼 자체가 안 나온다.** **빈 객체가 선택이 아니라 필수인 이유다.**

**그리고 컴파일이 잡아 주지 않는다**(§5) — **모델 속성 이름과 `th:object`가 어긋나면 렌더링 시점에 예외가 난다.**

## Q2. `${...}`와 `*{...}`의 차이

| | **`${...}`** | **`*{...}`** |
|---|---|---|
| 기준 | **모델 전체 기준의 절대 경로** | **`th:object`가 정한 객체 기준의 상대 경로** |
| 예 | `${newEmployee.name}` | `*{name}` |

```html
<form th:object="${newEmployee}" ...>
    <input th:field="*{name}" />   ← newEmployee.name 을 가리킨다
```

> **폼 안에서는 객체 이름을 반복하지 않는다.**

**둘 다 동작한다** — **폼 안에서 `${newEmployee.name}`으로 써도 되지만 `*{name}`이 관례다.**

**왜 관례가 되었나**: 객체 이름을 바꿀 때 **`th:object` 한 줄만** 고치면 된다. `${...}`로 쓰면 **모든 필드를 고쳐야** 한다.

**Thymeleaf 디렉티브 셋도 함께**:
| 디렉티브 | 하는 일 |
|---|---|
| `xmlns:th="..."` | **XML 네임스페이스** — 이게 있어야 `th:` 지시자를 쓸 수 있다 |
| `th:each` | **for-each.** 항목마다 `<li>` 하나, `employee`가 대역 변수 |
| `th:text` | **노드에 텍스트를 삽입** |
| `th:action` | 처리 라우트로 가는 URL 생성 |
| `th:object` | 폼을 모델 속성에 **바인딩** |
| `th:field` | `<input>`을 record 필드에 **연결** |

**눈에 잘 안 보이는 규칙 하나**: **모든 HTML 태그가 닫혀 있어야 한다.** **Thymeleaf의 DOM 기반 파서** 때문이다. **`<IMG>` 같은 태그도 `</IMG>`를 붙이거나 `<IMG/>` 축약**을 써야 한다. **`<br>` 하나 때문에 템플릿 전체가 파싱에 실패할 수 있다** — **HTML5 문법으로는 유효한데 Thymeleaf에서는 아니다.**

## Q3. POST-redirect-GET을 쓰지 않으면

**새로고침에서 재전송 경고가 뜨고 중복 저장이 일어난다.**

**정상 흐름**:
```
1. GET /          → 목록 + 빈 폼
2. POST /new-employee → 저장
3. redirect:/     → 브라우저가 GET / 을 다시 요청
4. GET /          → 갱신된 목록. 입력 칸은 비어 있다
```

**3~4번이 POST-redirect-GET 패턴이다.**

**redirect 없이 POST 응답으로 페이지를 그리면**: 브라우저의 **현재 URL이 `POST /new-employee`인 채로** 남는다. **새로고침 = POST 재전송**이므로
- **브라우저가 재전송 경고**를 띄우고
- 확인을 누르면 **중복 저장**이 일어난다

**POST 핸들러의 반환 타입이 `Mono<String>`인 이유**: **`map`의 결과가 문자열(`"redirect:/"`)**이기 때문이다.

**책이 정리하는 문장이 이 메서드의 성격을 말해 준다** — **이 메서드가 취하는 동작 전체가 들어오는 데이터에서 시작해 나가는 동작으로 변환되는 Reactor flow**다. **중간 변수를 만지작거리는 고전적 명령형과 대비된다.**

> **참고 — 타입 있는 대안이 있다**(§5): 책은 `Mono<String>`에 `"redirect:/"` 문자열을 담는다. 동작하지만 WebFlux에는 **`Rendering.redirectTo(String)`**이라는 타입 있는 방법이 있다(`spring-webflux` 7.0.9에서 확인). **같은 장에서 `Rendering`을 이미 쓰고 있는데 redirect만 문자열 규약으로 돌아가는 것이 일관되지 않는다.**

**`@ModelAttribute`와 `@RequestBody`의 구분도 함께**(§5): **폼(`application/x-www-form-urlencoded`)이냐 JSON 본문이냐**로 갈린다. **폼에 `@RequestBody`를 쓰면 파싱에 실패한다.**

## Q4. WebFlux와 가상 스레드의 자리매김

**책의 Note가 이 장 전체에서 가장 균형 잡힌 서술이다**:

> **WebFlux가 도입한 리액티브 모델은 처음에 낯설고 예상보다 어려워 보일 수 있다.** 고전적인 thread-per-request와 달리 논블로킹·비동기 접근을 채택하며 **웹 요청의 모든 단계를 신중히 고려**해야 한다.
>
> **Spring MVC는 여전히 유효하고 웹 애플리케이션에는 더 단순하다.** 그러나 **I/O 바운드 고동시성 시스템**(스트리밍 서비스, API 게이트웨이, 수천 개의 동시 연결)에서는 리액티브 모델이 **스레드 사용을 극적으로 줄이고 자원 효율을 높인다.**
>
> Java 21과 Spring Boot 3.2 이후로는 **가상 스레드**가 **명령형 Spring MVC 모델을 유지하면서** 고동시성으로 가는 **또 다른 길**을 준다.
>
> **요점은 WebFlux가 본질적으로 더 낫다는 것이 아니라, 특정 시나리오에 더 낫다는 것이다.**

> **리액티브는 도구이지 승급이 아니다.**

**스스로 세우는 결정 기준**:

| 조건 | 선택 |
|---|---|
| **I/O 바운드 + 동시 연결 수천 개** | **WebFlux** |
| **I/O 바운드 + 고동시성 + 기존 명령형 코드 유지** | **가상 스레드 + MVC** |
| **동시성이 낮다 / CPU 바운드** | **MVC** (리액티브 이득 없음) |
| **스트리밍이 본질**(SSE, 백프레셔가 필요한 파이프라인) | **WebFlux** — 가상 스레드로는 배압을 못 얻는다 |

**핵심 판별 하나**: **가상 스레드는 "블로킹을 싸게" 만들지만 배압은 주지 않는다.** [[01-reactive-programming-and-backpressure]]의 배압이 필요한 문제라면 **가상 스레드로는 안 풀린다.**

**반대로 배압이 필요 없고 단지 동시성만 필요하다면** — **명령형을 유지하는 쪽이 디버깅과 학습 비용에서 압도적으로 유리하다**([[01a-blocking-vs-non-blocking]]의 "스택 트레이스가 끊긴다"가 영구 비용).

> **§6의 지적**: 이 책은 Chapter 11에서 가상 스레드를 다루지만 **두 선택지의 결정 기준은 어느 장에서도 정면으로 비교되지 않는다.** 위 표는 그 빈자리를 메운 것이다.
