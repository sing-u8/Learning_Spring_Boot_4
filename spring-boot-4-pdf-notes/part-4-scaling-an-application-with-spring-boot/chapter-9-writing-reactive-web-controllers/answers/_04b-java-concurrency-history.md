## Q1. 거대 thread pool이 어느 지점부터 느려지는 이유

**코어보다 스레드가 많아지면 컨텍스트 스위칭이 비싸지기 때문이다.**

> **CPU가 계산 대신 스레드를 갈아 끼우는 데 시간을 쓰기 시작한다. 스레드를 늘릴수록 각 스레드가 실제로 일하는 비율이 떨어진다. 어느 지점부터는 더 넣을수록 전체가 느려진다.**

```
스레드 수 ↑  →  각 스레드의 실제 작업 비율 ↓
                 스위칭 비용 ↑
        ↓
어느 지점부터 전체 처리량이 감소로 돌아선다
```

**초창기 Java 동시 프로그래밍에서 사람들이 거대한 thread pool을 만들었고, 그렇게 배웠다.**

**리액티브가 새 유행이 아니라 학습의 결과임을 보여 주는 대목이다** — [[04a-scaling-with-project-reactor]]의 **"코어당 스레드 하나"**가 임의의 선택이 아니라 **이 실패에서 나온 답**이다.

## Q2. 옛 동시성 도구가 도달한 결말과 공통 요구

**Java 코어에는 깨지기 쉬운 API가 많이 박혀 있다.** 초창기부터 **`synchronized` 메서드와 블록, lock, semaphore** 같은 도구가 주어졌지만, **효과적이면서 동시에 올바르게 쓰기가 정말 어렵다.**

**[[01-reactive-programming-and-backpressure]]가 요약한 세 결말**: **약속은 컸고, 구현은 까다로웠으며, 결과는 빈약했다.**

**공통으로 요구한 것**:

> **이 전술들은 애플리케이션을 비직관적인 방식으로 다시 쓰기를 요구하곤 했다.**

**즉 어려운 것이 두 가지였다** — **올바르게 만드는 것, 그리고 그렇게 만든 코드를 나중에 읽는 것.**

**대안이 더 나은 이유**: **코어당 스레드 하나 + 게으른 평가 + 논블로킹 + 작업 훔치기**의 조합이 **상당히 더 효율적일 수 있다.**

**공짜는 아니다** — **Reactor로 코딩하는 것도 익혀야 할 스타일이 있다.** 다만 그 스타일이 **널리 채택된 Java 8 Stream과 같은 방향**으로 크게 기울어 있어, **초창기 Java 동시 프로그래밍만큼 큰 요구는 아니다.**

> **이 절의 논지는 "어려움의 총량이 줄었다"는 것이지 없어졌다는 것이 아니다.**

**리액티브도 같은 대가를 일부 낸다** — 스택 트레이스가 끊기고([[01a-blocking-vs-non-blocking]]), 조립과 실행이 분리되고([[04a-scaling-with-project-reactor]]), 부수효과의 실행 횟수가 불확실하다([[04-consuming-data-with-reactive-post]]).

## Q3. "4코어에서 25% 손실"이 낙관적 하한인 이유

**책의 계산**:
> **4코어 머신에 Reactor 스레드가 4개뿐이라고 상상해 보라. 그중 하나가 블로킹 코드를 만나 기다리게 되면 전체 처리량의 25%를 날려 버린다.**

**낙관적인 이유**: **블로킹이 이벤트 루프를 잡으면 그 스레드에 배정된 모든 연결이 함께 멈춘다.**

> **Netty는 연결을 이벤트 루프에 고정 배정하므로, 실제 영향은 요청이 어떻게 분배됐느냐에 따라 25%를 크게 넘을 수 있다.**

```
산술:  4개 중 1개 = 25%
실제:  그 스레드에 배정된 연결이 100개면 그 100개가 전부 멈춘다
       분배가 고르지 않으면 훨씬 나빠진다
```

> **책의 숫자는 감을 주는 값으로 읽어야 한다.**

**요점은 정확한 비율이 아니라 무게의 차이다** — **이벤트 루프의 스레드는 소수 정예다. 하나가 멈추면 그 몫이 통째로 사라진다. 200개 중 하나가 막히는 것과는 무게가 다르다.**

**그래서 결론이 나온다** — **애플리케이션의 절대적으로 모든 부분이 이 방식으로 작성돼야 한다.**

**대응**(§5): **"블로킹을 없앨 수 없으면 리액티브를 못 쓴다"는 아니다.** **`boundedElastic`으로 격리하는 길이 있다.** 다만 **격리한 만큼 이득이 줄어드므로 어디까지 감수할지의 문제**가 된다.

## Q4. JDBC·JPA·JMS·servlet의 공통점

**전부 블로킹 패러다임 위에 세워졌다.**

| 명세 | **무엇이 막히나** |
|---|---|
| **JDBC** | **DB 질의** — 거의 모든 애플리케이션이 쓴다 |
| **JPA** | **JDBC 위에 서므로 함께 막힌다** |
| **JMS** | **메시지 수신** |
| **Servlet** | **요청 처리 자체** |

> **그래서 리액티브 애플리케이션에 적합하지 않다.**

**범위가 얼마나 넓은지가 요점이다** — **평범한 Spring Boot 앱의 데이터 계층 전체**가 리액티브와 맞지 않는다.

**이것이 다음 장 *Working with Data Reactively*가 존재하는 이유다.**

**주의**(§5): **이 절만 읽으면 "리액티브는 DB를 못 쓴다"로 오해하기 쉽다.** **JDBC/JPA가 문제라는 진단은 R2DBC라는 처방으로 이어진다.**

**다른 답도 있다**: **같은 문제(블로킹 API와 스레드 비용)에 Java 21은 다른 답을 내놨다** — **블로킹 코드를 그대로 두고 스레드를 싸게 만드는 것**, 즉 **가상 스레드**다. [[05b-crafting-a-thymeleaf-template]]의 마지막 Note가 짚는다.

**두 답의 방향이 정반대다**:
```
리액티브:   블로킹을 없앤다        → 코드 스타일이 바뀐다
가상 스레드: 스레드를 싸게 만든다   → 코드는 그대로
```

**§6의 실무 지침**: **데이터 계층 계획 없이 리액티브 웹만 도입하지 않는다**(병목이 아래로 이동할 뿐) · **레거시 블로킹 라이브러리가 많으면 전환 비용을 먼저 계산** · **`synchronized`를 파이프라인 안에서 쓰지 않는다**(이벤트 루프를 막는 또 다른 경로) · **동시성이 낮은 서비스라면 옛 모델의 문제가 애초에 발생하지 않는다.**

**비유로 보면** 고속도로 차선 — 옛 방식은 **차선을 200개로 넓히는 것**이었고, **합류와 차선 변경(컨텍스트 스위칭)이 늘어 오히려 막혔다.** **깨지는 지점 둘**:
- **4차선 중 1차선이 막히면 정확히 25%가 아니라 그 이상**이 영향을 받는다(Q3)
- **고속도로는 사고 차량을 견인할 수 있지만 블로킹 호출은 끝날 때까지 방법이 없다** — **사후 대응이 아니라 애초에 들이지 않는 것이 유일한 전략**이다
