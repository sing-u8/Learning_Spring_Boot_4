## Q1. `map` 안의 람다가 컨트롤러 호출 시점에 실행되지 않는 이유

**연산자를 쓰는 것은 어셈블리이지 실행이 아니기 때문이다.**

> **이 작은 flow들의 각 단계는 곧바로 수행되지 않는다.** `map`이든 `filter`든, **쓸 때마다 우리가 하는 것은 어셈블리다.** 각 연산은 **우리 동작을 수행하는 데 필요한 세부를 담은 작은 command object**를 조립한다.

```java
return newEmployee
    .map(employee -> {
        DATABASE.put(employee.name(), employee);   // ← 람다 안
        return employee;
    });
```

> **`DATABASE`에 저장하고 값을 반환하는 문장 전체가 Java 8 람다 안에 있다. 그리고 컨트롤러 메서드가 호출될 때 그 안쪽 람다가 같이 호출돼야 할 이유가 없다.**

**이 한 문장이 리액티브 코드를 읽을 때 가장 자주 걸리는 지점이다** — **코드의 작성 순서와 실행 시점이 분리된다.**

**실전 결과**(§5): **디버거로 컨트롤러 메서드에 중단점을 걸면 람다 안에는 멈추지 않는다.** **람다는 나중에, 다른 스레드에서 실행되기 때문**이다.

**[[01b-reactive-streams-details]]의 "구독하기 전에는 아무 일도 없다"가 코드 수준에서 나타나는 모습이다.**

## Q2. work stealing이 "지연을 기회로 바꾼다"

**Reactor flow의 모든 단계가 게으르고 논블로킹으로 동작하므로, I/O 바운드 지연이 생기면 현재 스레드가 응답을 기다리며 붙들리지 않는다. 대신 Scheduler가 내부 작업 큐로 돌아가 다른 작업을 집는다.**

**구체적 예**:
```
요청 A: DB 질의를 보냄 → 응답까지 50ms
        ↓ (블로킹이라면 스레드가 50ms 동안 논다)
        ↓ (리액티브라면)
스레드:  큐로 돌아가 요청 B 의 작업을 집는다
        요청 C 의 JSON 직렬화를 한다
        50ms 뒤 A 의 응답 시그널이 오면 누군가 이어받는다
```

> **전통적인 지연 문제가 다른 일을 끝낼 기회로 바뀐다.**

**[[01a-blocking-vs-non-blocking]]에서 "기다리며 낭비하지 않는다"고 한 것의 구현이 이것이다.**

**이 구조가 성립하는 전제**: Reactor는 **command object들을 모아 내부 작업 큐에 쌓고**, 실행을 **Scheduler**에 위임한다. **큐가 있어야 "다른 작업을 집는다"가 가능**하다.

**Scheduler를 고를 수 있다는 점도 여기서 나온다** — **단일 스레드**(순서 보장), **thread pool**(고정 크기), **`ExecutorService`**(기존 자원 재사용), **`boundedElastic`**(블로킹 격리).

## Q3. 코어 8개 서버에서 스레드를 200개 만들지 않는 이유

**코어보다 스레드가 많으면 CPU가 계산 대신 스레드를 갈아 끼우는 데 시간을 쓰기 때문이다.**

**Reactor가 하는 두 번째 일**: **200개짜리 거대 thread pool 대신, 코어당 스레드 하나를 쓰는 Scheduler가 기본.**

**주는 것 둘**:
- **컨텍스트 스위칭 오버헤드 감소**
- **가용 CPU 자원의 더 나은 활용** — 특히 **스레드가 기다리며 시간을 보냈을 I/O 바운드 워크로드**에서

**왜 코어당 하나로 충분한가**:
```
스레드가 기다리지 않는다면(논블로킹) 애초에 많이 필요하지 않다.
코어 수만큼만 있으면 CPU 를 꽉 채울 수 있다.
```

**반대로 블로킹 모델에서는 스레드를 늘릴 수밖에 없었다** — **기다리는 스레드는 CPU를 안 쓰므로, 동시성을 사려면 스레드를 사야** 했다. **기다림을 없애면 그 거래가 필요 없어진다.**

> **"코어당 하나"는 기본값이지 규칙이 아니다** — Scheduler를 바꾸면 달라진다. **요점은 숫자가 아니라 스레드를 늘려 동시성을 사지 않는다는 방향이다.**

**이 판단의 역사적 배경이 [[04b-java-concurrency-history]]다.**

## Q4. 블로킹 코드를 `boundedElastic`으로 옮기면

**해결되는 것: 이벤트 루프가 지켜진다.**
**남는 것: 그 Scheduler의 스레드는 여전히 막힌다.**

> **"격리"라는 표현이 정확하다. 없애는 게 아니라 피해가 이벤트 루프에 닿지 않게 가둔다.**

```
격리 전:  블로킹이 이벤트 루프 스레드를 잡는다 → 4코어면 25% 손실
격리 후:  블로킹이 boundedElastic 스레드를 잡는다 → 이벤트 루프는 계속 돈다
          단, boundedElastic 의 상한에 닿으면 대기가 생긴다
```

**근본 해법은 논블로킹 드라이버로 바꾸는 것이다** — 다음 장의 **R2DBC**.

**왜 이 제약이 생기나**: **블로킹 작업 — 블로킹 DB 호출, 파일 접근, 원격 HTTP 호출 — 은 리액티브 이벤트 루프 스레드에서 돌면 안 된다.** **블로킹 연산은 그 스레드를 붙들어 Reactor가 제공하려는 확장성 이득을 깎아 먹는다.**

**§6의 지침 넷**:
- **이벤트 루프에서 블로킹 호출을 하지 않는다** — **이것 하나가 리액티브 운영 사고의 대부분**이다
- **`block()`을 파이프라인 안에서 부르지 않는다** — 격리 없이 부르면 이벤트 루프가 멈춘다
- **CPU 바운드 작업을 이벤트 루프에 두지 않는다** — **기다림이 아니라 계산도 스레드를 붙든다**
- **Scheduler를 임의로 바꾸지 않는다** — 기본값에는 이유가 있고, **바꿀 때는 측정이 먼저다**

**비유로 보면** 주방 요리사 배치 — **화구 수만큼만 요리사를 두고, 오븐에 넣은 뒤 곧바로 다음 주문의 손질로 넘어간다.** **깨지는 지점 둘**:
- **요리사는 자기가 무엇을 하고 있었는지 기억하지만** 리액티브에서는 그 문맥을 **Reactor가 command object에 담아 다녀야** 한다 → 스택 트레이스가 끊긴다
- **요리사 하나가 설거지를 시작하면(블로킹) 화구 하나가 통째로 멈춘다.** **4명 중 1명이면 25%가 날아간다** → [[04b-java-concurrency-history]]

> **참고 — 이 절의 위치가 어색하다**: 원문은 이 내용을 **POST 절 뒤**에 배치했지만 다루는 것은 **"리액티브가 어떻게 확장을 만드나"**다. **[[01a-blocking-vs-non-blocking]] 다음에 읽으면 더 자연스럽다.**
