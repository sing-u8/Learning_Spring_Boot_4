## Q1. 소비자가 느릴 때 — 배압 없는 모델과 있는 모델

**배압이 없으면**: **빠른 데이터 스트림이 목적지를 압도한다.**

```
생산자가 소비자보다 빠르게 방출 → 시스템 불안정
   ├─ 지연 증가
   ├─ 자원 고갈
   └─ 심하면 장애
```

**이건 이론이 아니라 흔한 장애 시나리오다** — **Kafka 컨슈머가 밀린다, 큐가 무한히 자란다, `OutOfMemoryError`가 난다.** 전부 같은 이야기다.

**배압이 있으면**: **소비자가 흐름을 통제한다.** **무한정 밀려오는 스트림을 받는 대신 자기가 다룰 준비가 된 양을 명시적으로 알린다** — 1개, 10개, 또는 그 이상.

> **전통적 publish-subscribe가 수요 주도 상호작용(demand-driven)으로 바뀐다. 처리할 여력이 있을 때만 데이터가 간다.**

**발상의 전환이 여기 있다** — **"밀려오는 것을 어떻게 견딜까"가 아니라 "오지 않게 하려면 무엇을 안 해야 하나"로 문제가 바뀐다.**

**중요한 단서**(§6): **배압은 마법이 아니다.** **소비자가 느리면 시스템은 여전히 느리다. 다만 터지지 않고 느려질 뿐이다.**

**큐 크기 제한과의 차이**: **큐 제한은 넘친 것을 버리거나 막는 사후 대응이고, 배압은 애초에 그만큼만 보내게 하는 사전 조율이다.**

## Q2. 배압이 명세의 일부라는 사실의 이득

**여러 컴포넌트를 걸쳐 보존되므로, 리액티브 컴포넌트를 이어 붙이는 것만으로 흐름 제어가 파이프라인 전체로 전파된다.**

> **어느 부분도 압도되지 않는다.**

**흐름 제어를 손으로 짜면 무엇이 문제인가**: **컴포넌트마다 손으로 짜면 한 군데만 빠져도 그 지점에서 터진다.**

```
손으로 구현:  A(제어 있음) → B(제어 있음) → C(빠뜨림) → D
                                              ↑ 여기서 터진다
명세의 일부:  이어 붙이는 것만으로 유지된다
```

**조율이 일어나는 방식**: **수요를 관리하고, 오류를 전파하고, 완료를 알리는 잘 정의된 시그널 집합.** 세 가지를 함께 다룬다는 점이 중요하다 — **오류와 완료도 같은 채널로** 흐르므로 컴포넌트마다 따로 처리할 필요가 없다.

**구체적 강제 지점은 [[01b-reactive-streams-details]]에 있다** — `request(n)` 다음의 `onNext`가 **n을 초과할 수 없다**는 규칙이 코드 수준의 강제력이다.

## Q3. 단일 스레드 JavaScript 관찰에서 끌어낼 수 있는 것과 없는 것

**끌어낼 수 있는 것**: **확장의 열쇠가 "스레드를 더 많이"가 아닐 수 있다.**

**브라우저에는 스레드가 하나뿐인데도 논블로킹·이벤트 기반으로 접근하면 얼마나 잘 확장되는지를 보여 줬다.**

**끌어낼 수 없는 것**: **"스레드 하나면 충분하다."**

> **요점은 스레드 수가 아니라 기다림을 없애는 것**이며, [[01a-blocking-vs-non-blocking]]이 그 구조를 다룬다.

**왜 이 구분이 중요한가**: "스레드를 줄여라"로 이해하면 **CPU 바운드 작업에서도 스레드를 줄이려는** 잘못된 결론에 이른다. **거기서는 기다림이 없으므로 없앨 낭비도 없고**(§6), 스레드를 줄이면 그냥 느려진다.

**맥락**: 수십 년간 thread pool, `synchronized`, 컨텍스트 스위칭 기법들이 이 문제를 풀려 했다. **강력했지만 규모에서 올바로 쓰기가 어려웠다** — **약속은 컸고 구현은 까다로웠으며 결과는 빈약했다.** 그래서 **여전히 서비스를 수백~수천 개씩 돌리고 클라우드 청구서가 거대해진다.**

**"리액티브 = 비동기"도 같은 종류의 잘못된 요약이다** — **비동기이면서 배압이 없으면 그냥 더 빨리 터지는 시스템**이다. 정의에 **"non-blocking back pressure"**가 들어간 이유가 그것이다.

## Q4. RSocket이 HTTP와 다른 층에서 하는 일

**배압을 전송 계층에 내장한다.**

> **HTTP가 TCP 위에 서듯, RSocket은 배압이 내장된 리액티브 통신의 전송 계층을 제공해 분산 시스템끼리도 완전히 흐름 제어된 방식으로 데이터를 주고받게 한다.**

**즉 이 모델은 한 애플리케이션 안에 갇히지 않는다.**

```
애플리케이션 내부:  Reactive Streams 의 request(n)
애플리케이션 사이:  RSocket 이 같은 원리를 네트워크에 적용
```

**왜 필요한가**: Q2의 "파이프라인 전체로 전파"가 **프로세스 경계에서 끊기면** 의미가 반감된다. 서비스 A가 배압을 지켜도 **서비스 B에 HTTP로 밀어 넣으면** B는 자기 속도를 말할 방법이 없다.

**HTTP와의 층 관계**: RSocket은 HTTP의 대체가 아니라 **같은 자리(TCP 위)의 다른 프로토콜**이다. 요청-응답만이 아니라 **스트리밍과 채널**을 1급으로 다루고, 그 위에 **수요 신호**를 얹는다.

**리액티브 스트림의 공식 정의가 이 범위를 명시한다**:
> *"asynchronous stream processing with **non-blocking back pressure**. This encompasses efforts aimed at **runtime environments (JVM and JavaScript) as well as network protocols**."*

**세 가지가 들어 있다** — 비동기 스트림 처리, **논블로킹 배압**, 그리고 **JVM·JavaScript·네트워크 프로토콜까지 걸치는 범위.**

**비유의 깨짐도 함께**: 수도꼭지와 컵 — **실제 수도는 잠그면 물이 파이프에 그대로 남지만, 리액티브에서 요청하지 않은 데이터는 애초에 생성되지 않을 수도 있다**(게으른 평가). 그리고 **컵은 넘치면 눈에 보이지만 배압 없는 시스템의 붕괴는 메모리 그래프가 천천히 오르다가 갑자기** 온다.
