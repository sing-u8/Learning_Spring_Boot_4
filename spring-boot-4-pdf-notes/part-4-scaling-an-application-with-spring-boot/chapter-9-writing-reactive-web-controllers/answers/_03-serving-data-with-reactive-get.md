## Q1. `Flux`가 `List`와도 `Future`와도 다른 점

**책이 조심스럽게 짚는다** — *"`Flux`는 고전적인 `List`와 `Future`를 합친 것 같다. **그런데 사실 아니다.**"*

| 비교 대상 | 닮은 점 | **결정적 차이** |
|---|---|---|
| **`List`** | 여러 항목을 담는다 | **`List`는 한꺼번에 갖지만 `Flux`는 아니다.** 반복문으로 소비하지 않고 **`map`·`filter`·`flatMap` 같은 스트림 연산**을 쓴다 |
| **`Future`** | 형성될 때 내용이 아직 없고 **미래에 도착**한다 | Java 8 이전의 `Future`는 **`get` 하나뿐**이지만 **`Flux`는 연산자가 풍부하다** |

**왜 이 구분이 중요한가**: **`List`처럼 다루려는 순간(`for` 루프, `.size()`) 리액티브의 이점이 사라진다.**

**구체적으로**: `.collectList().block()`으로 꺼내 쓰면 **컴파일도 되고 동작도 한다.** 그런데 **`block()`은 이벤트 루프 스레드를 막는 행위**라 [[01a-blocking-vs-non-blocking]]에서 얻으려던 것을 **통째로 반납**한다.

**`Flux`의 정체**: **Reactor의 `Publisher` 구현이며 풍부한 리액티브 연산자를 제공**한다.

**컨트롤러는 MVC와 같아 보인다** — `@RestController`, `@GetMapping`은 **MVC에서 쓰던 것과 같은 애노테이션**이다. **이것이 WebFlux의 설계 의도**다 — **프로그래밍 모델을 새로 배우게 하지 않는다.** **구분은 반환 타입에 있다.**

## Q2. `concatWith`와 `mergeWith`를 원격 API 호출에 쓰면

| 연산자 | 결과 | **네트워크 요청** |
|---|---|---|
| **`concatWith`** | `alpha, bravo, charlie, delta` — **순서 보장** | **직렬로 나간다** |
| **`mergeWith`** | 실제 도착 순서대로, **교차 가능** | **병렬로 나간다** |

**이유**: **`concatWith`는 앞 스트림이 완료될 때까지 뒤 스트림을 구독조차 하지 않는다.**

```
concatWith:  A 호출 ────완료──▶ B 호출     (지연 = A + B)
mergeWith:   A 호출 ┐
             B 호출 ┘ 동시                (지연 = max(A, B))
```

> **순서가 의미를 가지면 `concatWith`, 지연을 줄이는 것이 중요하면 `mergeWith`다.**

**성능 차이가 여기서 생긴다.** 두 원격 호출이 각각 200ms면 **`concatWith`는 400ms, `mergeWith`는 200ms**다.

**반대 방향의 함정**(§6): **순서가 중요한데 `mergeWith`를 쓰면 조용히 잘못된 순서가 나간다.** 테스트 환경에서는 응답이 빨라 **우연히 순서가 맞을 수 있어** 더 위험하다.

## Q3. 컨트롤러가 `Flux`를 반환할 때 프레임워크가 하는 일

**직렬화와 JSON 응답 반환**, 그리고 **리액티브 스트림 생명주기 전체**:

| | |
|---|---|
| **구독** | 흐름을 실제로 시작시킨다 |
| **수요(`request`)** | 얼마나 받을지 요청한다 |
| **데이터 방출(`onNext`)** | 항목이 하류로 흐른다 |
| **완료(`onComplete`)** | 스트림의 끝을 알린다 |

> **[[01b-reactive-streams-details]]에서 본 5단계 프로토콜을 우리가 한 줄도 쓰지 않는 이유가 이것이다.**

**그리고 게으름이 기본이다** — **구독하기 전에는**
- **웹 호출이 나가지 않는다**
- **DB 연결이 열리지 않는다**
- **자원이 할당되지 않는다**

**시스템 전체가 밑바닥부터 게으른 평가로 설계됐다.**

**실무적 함의**: **컨트롤러가 `Flux`를 반환하지 않고 내부에서 조용히 만들기만 하면 아무 일도 일어나지 않는다.** 명령형 습관대로 **조립만 하고 다른 값을 반환하면 조용히 아무 일도 안 일어난다.**

**즉 "반환한다"가 곧 "실행을 프레임워크에 위임한다"이다.**

## Q4. `Flux.just(...)` 예제가 리액티브의 본질을 못 보여 주는 이유

**책 자신이 Note로 인정한다**:

> **"웹 메서드에서 `Flux`를 하드코딩 데이터로 미리 채우지 않았나요?" — 그렇다. 이 예제는 실제 애플리케이션에서의 `Flux`의 미래적 성격을 다소 거스른다.**

**`just`는 이미 값을 손에 들고 있다.** `Flux`의 요점은 **값이 아직 없고 미래에 도착한다**는 것인데, `just`는 그 성질을 없앤다.

> **실제로는 `just`로 미리 채우지 않고 리액티브 데이터베이스나 원격 네트워크 서비스 같은 데이터 소스를 연결한다. `Flux`의 더 정교한 API를 쓰면 값이 준비되는 대로 하류 소비를 위해 방출할 수 있다.**

**이 Note가 중요한 이유**: **`just`가 리액티브의 본질이 아니라 교육용 축약**임을 알려 준다. **실전 코드의 본보기로 삼으면 안 된다**(§6).

**실제 `Flux`는 [[04a-scaling-with-project-reactor]]에서 볼 Scheduler 위에서 값이 도착하는 대로 흘러야 한다.**

**비유로 보면** 주문서와 주방 — **컨트롤러가 반환하는 `Flux`는 완성된 요리가 아니라 주문서**다. **깨지는 지점 둘**:
- **주문서를 서랍에 넣어 두면 아무 일도 안 일어난다** — 반환하지 않은 `Flux`가 정확히 그렇다(Q3)
- **실제 주방은 주문서를 받는 순간 재료를 꺼내지만 `Flux.just(...)`는 이미 재료를 손에 들고 있다**
