## Q1. 템플릿 엔진 선택이 성능 결정이 되는 이유

**템플릿 렌더링이 I/O를 하기 때문이다.**

**템플릿 엔진이 하는 일**: **파일에서 템플릿을 읽고, 모델 데이터를 채워 넣고, 결과 문자열을 응답 스트림에 쓴다.**

> **이 중 파일 읽기와 응답 쓰기가 I/O다.**

**템플릿 엔진이 이걸 블로킹 방식으로 하면 이벤트 루프 스레드가 붙들린다** — [[04b-java-concurrency-history]]의 그 계산이 그대로 적용된다.

**전통적인 템플릿 엔진 상당수는 Servlet API의 `Writer`에 직접 쓰도록 설계됐고, 그건 곧 블로킹이다.**

> **그래서 Spring WebFlux에서는 아무 템플릿 엔진이나 쓸 수 없다.**

**책의 판단 기준**: *"리액티브 프로그래밍을 얘기하고 있으니 **블로킹하지 않는 템플릿 엔진**을 고르는 것이 이치에 맞다."*

**Thymeleaf를 고르는 이유 둘**: **Spring Boot와 매끄럽게 통합된다** · **리액티브 지원이 들어 있다.** **두 번째가 이 절의 이유 전부다.**

**비유로 보면** 수도관 필터 — [[02-creating-a-webflux-application]]에서 **주 배관을 논블로킹으로 바꿨는데, 여기에 물을 한 번에 한 컵씩만 통과시키는 필터를 달면 배관을 바꾼 의미가 없다.**

## Q2. GENERATE 대신 EXPLORE를 쓰는 이유

**프로젝트를 다시 만들면 그동안 쓴 코드가 사라지기 때문이다.**

> **EXPLORE는 프로젝트를 만들지 않는다 — 미리 보기다.** 이 절차의 목적은 **좌표를 확인해 복사**하는 것이지 프로젝트를 다시 받는 것이 아니다.

**절차 셋**: **① Maven 의존성을 선택 → ② 클립보드에 복사 → ③ IDE의 `pom.xml`에 붙여 넣기.**

> **Initializr를 의존성 좌표 조회 도구로 쓰는 것이 이 절차의 요점**이고, **앞선 장들에서 반복해 온 방식**이다.

**GENERATE를 누르면**: **기존 코드가 든 프로젝트와 별개의 새 ZIP이 생긴다.** 그 안의 `pom.xml`을 꺼내 쓸 수는 있지만 **불필요한 왕복**이다.

**왜 좌표를 손으로 안 쓰나**: `groupId`/`artifactId`를 **정확히 기억하기 어렵고**, 오타는 **의존성 해석 실패**로만 드러난다. Initializr가 **정본**이다.

**이 절이 새 프로젝트가 아니라 갱신인 이유도 같다** — [[02-creating-a-webflux-application]]에서 **웹 스택이 바뀔 때는 새로** 만들었지만, **의존성만 더할 때는 갱신**한다.

## Q3. 블로킹 템플릿 엔진의 문제가 개발 중에 잘 안 드러나는 이유

**동시성이 낮으면 증상이 없기 때문이다.**

```
개발 중:  요청 1~2개 → 이벤트 루프 스레드가 놀고 있다 → 블로킹해도 티가 안 난다
운영:     동시 요청 수천 개 → 스레드 4개 중 하나만 막혀도 처리량이 무너진다
```

**그리고 기능적으로는 정상 동작한다** — **HTML이 제대로 렌더링되고 응답 코드도 200**이다. **테스트도 통과한다.**

**[[02-creating-a-webflux-application]]의 함정과 같은 모양이다** — **웹 스택을 잘못 섞어도 코드가 컴파일되고 돌아간다.** **리액티브의 실패는 대체로 "동작 안 함"이 아니라 "성능이 안 나옴"**이고, 그래서 **부하 테스트 없이는 발견되지 않는다.**

**"Thymeleaf니까 리액티브다"도 같은 오해다**(§5) — **엔진이 지원한다는 것과 우리가 리액티브하게 쓴다는 것은 다르다.** **컨트롤러가 `Mono<Rendering>`을 반환해야 흐름이 이어진다** → [[05a-creating-a-reactive-web-controller]].

**그리고 엔진이 논블로킹이어도 우리가 넣은 코드가 막을 수 있다**(§6) — **템플릿 안에서 블로킹 호출을 하지 않는다.**

## Q4. 추가되는 두 좌표

| 좌표 | 무엇을 위한 것 |
|---|---|
| **`spring-boot-starter-thymeleaf`** | **Thymeleaf 템플릿 엔진** — 리액티브 지원을 갖춘 서버 사이드 렌더링 |
| **`spring-boot-starter-webflux-test`** | **Boot 4의 기능별 테스트 starter** — 앞서 넣지 않았다면 이때 들어온다 |

**두 번째가 이 절의 주제와 직접 관련은 없지만 함께 온다** — [[02-creating-a-webflux-application]]에서 본 **Boot 4의 테스트 starter 분리**의 결과다.

**설정은 앞서 내려받은 것과 동일하고 의존성 두 개만 추가된다.**

**이 starter가 Thymeleaf를 내려받으면 템플릿용 리액티브 웹 컨트롤러를 쓸 준비가 된 것**이고, 그것이 [[05a-creating-a-reactive-web-controller]]다.

**주의**(§6): **MVC용 템플릿 설정을 그대로 옮기지 않는다.** **리액티브 뷰 리졸버는 별개**다. 그리고 **JSON API만 제공하는 서비스라면 템플릿 엔진 자체가 필요 없다** — 프런트엔드가 별도 앱이라면 [[06-building-reactive-hypermedia-apis]] 쪽이 더 맞을 수 있다.
