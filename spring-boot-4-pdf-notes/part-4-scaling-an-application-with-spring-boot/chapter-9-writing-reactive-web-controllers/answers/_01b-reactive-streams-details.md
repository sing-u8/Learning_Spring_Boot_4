## Q1. 네 인터페이스와 `Processor`가 따로 필요한 이유

| 인터페이스 | **역할** |
|---|---|
| **`Publisher`** | **출력을 만들어 내는 쪽.** 출력 하나일 수도, 무한일 수도 있다 |
| **`Subscriber`** | **`Publisher`로부터 받는 쪽** |
| **`Subscription`** | **소비 시작에 필요한 세부를 담는 연결.** **`request(n)`과 `cancel`이 여기 산다** |
| **`Processor`** | **`Subscriber`이자 `Publisher`인 컴포넌트.** 받아서 변환해 다시 내보낸다 |

**`Processor`가 필요한 이유**: **파이프라인의 중간 단계**를 표현하려면 **받는 쪽이면서 보내는 쪽**인 타입이 필요하다. `map`·`filter` 같은 연산자가 개념적으로 여기 해당한다.

**그리고 그것이 [[01-reactive-programming-and-backpressure]]의 "배압이 파이프라인 전체로 전파된다"를 가능하게 한다** — 중간 단계가 **하류의 `request(n)`을 받아 상류로 다시 요청**하므로, **수요가 끝에서 시작점까지 거슬러 올라간다.**

**`Subscription`이 별도 타입인 것도 의미가 있다** — 배압 협상 채널을 **`Publisher`나 `Subscriber`가 아니라 그 사이의 연결**에 두었다. 구독마다 독립적인 수요 상태를 가질 수 있다.

**Java 9부터 같은 넷이 JDK에도 있다** — **`Flow` API**이며 **Reactive Streams와 1:1 호환**으로 설계됐다. **표준이 언어 안으로 들어왔다.**

> **주의**: **"인터페이스 4개뿐이라 명세가 단순하다"는 겉모습이다.** 명세의 본체는 **TCK와 규칙 문서**다 — **`request(n)`이 누적된다는 것, 취소 후에는 시그널을 보내면 안 된다는 것, `onNext`가 동시에 호출되면 안 된다는 것.** 이런 규칙이 **구현의 실제 난이도**를 만든다.

## Q2. 배압이 강제되는 지점

**`onNext`가 `request(n)`의 n을 초과할 수 없다는 규칙이다.**

| # | 시그널 | 하는 일 | **왜 이 단계가 있나** |
|---:|---|---|---|
| 1 | **`onSubscribe`** | 하류가 준비됐다는 표시 | **배압 협상의 채널(`Subscription`)이 먼저 서야 한다** |
| 2 | **`request(n)`** | `Subscriber`가 n개를 요청 | **소비자가 속도를 정하는 지점** |
| 3 | **`onNext`** | `Publisher`가 항목을 방출 | **n을 초과할 수 없다 — 이게 배압의 강제력** |
| 4 | 추가 `request` 또는 `cancel` | 더 요구하거나 끊는다 | **소비자가 언제든 조절·중단할 수 있어야** |
| 5 | **`onComplete`** | 더 보낼 것이 없음 | **끝을 명시적으로 알려야 하류가 정리할 수 있다** |

**3번이 [[01-reactive-programming-and-backpressure]]의 배압이 코드 수준에서 성립하는 방식이다.**

**1번이 먼저인 이유**: **채널이 없으면 요청할 수단이 없다.** `Subscription`을 손에 쥐어야 `request`를 부를 수 있으므로, **데이터보다 연결이 먼저** 온다.

**그런데 이걸 직접 쓰지는 않는다** — **지금 본 것은 저수준 프로토콜**이다. **Project Reactor와 Spring WebFlux 같은 상위 라이브러리가 세부를 추상화**해, 우리는 **메커니즘 관리가 아니라 데이터 흐름 조합에 집중**한다.

**그래도 알아 둘 값은 있다** — **어딘가에서 `request(n)`이 안 오면 스트림이 멈추고, 그때 이 그림 없이는 원인을 짚을 수 없다.**

## Q3. 리액티브에 void 메서드가 없는 이유

**데이터 결과가 없어도 시그널을 주고받을 필요가 남기 때문이다.**

> **데이터가 다뤄지거나 동작이 일어날 때마다 시그널이 따라붙는다. 데이터 교환이 없어도 시그널은 처리된다.**

**그래서 "아무것도 반환하지 않는" 리액티브 연산은 `Mono<Void>`가 된다.**

```
명령형:      void delete(id)          → 반환할 것이 없으니 void
리액티브:    Mono<Void> delete(id)    → 값은 없지만 "완료됐다"는 시그널은 있어야 한다
```

**무엇을 잃게 되나 — `void`로 만들면**:
- **언제 끝났는지 알 수 없다** — 후속 작업을 이어 붙일 수 없다
- **오류를 전파할 수 없다** — 예외를 던지면 어느 스레드에서 던지는지 불분명하다
- **구독할 대상이 없다** — Q4의 "조립만 하고 실행되지 않는" 문제와 만난다

**`Mono<Void>`는 "값은 없지만 완료 시그널은 있어야 한다"를 타입으로 표현한 것이다.**

**이것이 리액티브 API를 읽는 요령이기도 하다** — **반환 타입이 곧 계약**이다. `Mono<T>`는 최대 하나, `Flux<T>`는 0개 이상, `Mono<Void>`는 값 없는 완료.

## Q4. `flux.map(x -> save(x))`를 호출하고 반환값을 버리면

**아무 일도 일어나지 않는다.**

> **어셈블리는 실행이 아니다.**

```java
Flux<String> sample = Flux.just("learning", "spring", "boot")
        .filter(s -> s.contains("spring"))
        .map(s -> { System.out.println(s); return s.toUpperCase(); });

// 이 코드를 실행해도 System.out.println 은 찍히지 않는다
```

**각 줄이 어셈블리에서 command object로 포착될 뿐**이고, **구독이 일어나야 비로소 상호작용이 시작된다.**

**리액티브 스트림의 철칙**: **구독하기 전에는 아무 일도 없다.**

**왜 이것이 실전에서 무는가**:
```
명령형:    부수효과가 발생한다        → 잘못 써도 뭔가 일어난다
리액티브:  조용히 무시된다            → 에러도 로그도 없다
```

> **에러도 로그도 없이 그냥 동작하지 않는 것이 리액티브 초심자가 가장 자주 만나는 함정이다.**

**언제 구독이 일어나나**: **웹 메서드에서는 프레임워크가 구독해 준다.** 컨트롤러가 `Flux`를 반환하면 WebFlux가 구독한다([[03-serving-data-with-reactive-get]]). **그 밖에서는 우리 책임이다** — `subscribe()`를 부르거나, 반환해서 상위가 구독하게 한다.

**진단 요령**: "코드가 실행이 안 된다"면 **반환값을 버린 곳이 있는지** 본다. IDE가 "반환값을 쓰지 않음" 경고를 주도록 설정해 두면 도움이 된다.

**Reactor에 대한 사실 하나 더**: **Reactor 자체에는 Spring 의존성이 없다.** **Spring 팀이 만들지만 Spring에 의존하지 않는다** — Spring 없는 프로젝트에서도 쓸 수 있고, **반대로 Reactor 개념을 Spring 개념과 섞어 이해하면 혼란이 생긴다.** 명세가 표준이라 **RxJava** 같은 다른 구현과도 통합된다.

**비유로 보면** 주문형 인쇄 — **조립은 원고 편집, 구독은 인쇄 버튼, `request(10)`은 "10부만".** **깨지는 지점 둘**:
- **원고는 편집이 끝나야 인쇄하지만 리액티브 스트림은 무한할 수 있다**
- **인쇄 실수는 종이만 버리지만 구독하지 않은 흐름은 조용히 아무것도 안 한다**
