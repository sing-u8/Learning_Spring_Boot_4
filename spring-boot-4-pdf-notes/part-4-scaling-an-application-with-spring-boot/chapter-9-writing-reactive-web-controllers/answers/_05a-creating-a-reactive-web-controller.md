## Q1. `Mono<Rendering>`이 `String` + `Model`을 대신하는 이유

**둘 다 아직 준비되지 않았을 수 있기 때문이다.**

**템플릿 컨트롤러는 프레임워크에게 두 가지를 줘야 한다**:
1. **어떤 뷰를 렌더링할지** — `"index"`
2. **그 뷰에 넘길 모델 데이터** — `employees`

```
명령형 MVC:   Model 에 넣고 String 으로 뷰 이름 반환
              (둘 다 메서드 반환 시점에 준비돼 있다)
리액티브:     데이터가 미래에 도착하면
              뷰 이름과 모델을 묶는 일도 미래에 일어나야 한다
```

**그 자리를 채우는 것이 `Rendering`이다** — **렌더링할 뷰 이름과 모델 속성을 함께 담는 WebFlux 값 타입.**

**`Mono`로 감싸는 이유**: **렌더링 지시 자체가 미래에 만들어진다.** 데이터가 도착해야 모델을 채울 수 있으므로, **"무엇을 어떻게 그릴지"라는 지시도 그 뒤에** 완성된다.

**`@Controller`와 `@RestController`의 구분도 여기서 중요하다**(§5) — **앞의 것은 뷰 이름을 해석해 템플릿을 렌더링하고, 뒤의 것은 반환값을 본문에 직접 쓴다.** **템플릿 컨트롤러에 `@RestController`를 붙이면 `"index"`라는 문자열이 그대로 응답된다.**

## Q2. `fromIterable` → `collectList`가 왕복처럼 보이는데도 올바른 이유

**중간에 리액티브 연산자를 쓸 수 있게 되기 때문이다.**

**책이 스스로 짚는다** — 실제 데이터 소스가 아니라 **기본 Java `Map`에 담긴 통조림 데이터**라, **`fromIterable`로 `Flux`에 감쌌다가 `collectList`로 도로 빼내는 것이 다소 이상해 보인다.**

> **그런데 이건 `Iterable` 컬렉션을 건네받는 현실 상황을 보여 주기 위한 것이다.** 올바른 대처가 코드에 나온 그대로다 — **`Flux`로 감싸고, 각종 변환과 필터를 실행한 뒤, WebFlux 웹 핸들러에 넘겨 Thymeleaf로 렌더링한다.**

```
Flux.fromIterable(...)      ← 파이프라인에 들여온다
    .filter(...)            ← 여기가 이 구조의 값
    .sort(...)
    .collectList()          ← 템플릿은 리스트 전체가 필요하므로 모은다
    .map(... Rendering ...)
```

**요점은 "감쌌다 푸는 낭비"가 아니라 중간에 리액티브 연산자를 쓸 수 있게 되는 것이다.** **필터링이나 정렬이 들어가면 이 구조가 값을 한다.**

**주의**(§5): **`fromIterable`은 이미 있는 데이터를 감쌀 뿐 없던 비동기성을 만들어 주지 않는다.** **`DATABASE.values()`는 이미 메모리에 있고 즉시 완료된다.** **진짜 이득은 실제 리액티브 데이터 소스로 바꿀 때** 나온다.

**중간 연산자가 없다면 그냥 리스트를 모델에 넣어도 된다**(§6).

## Q3. "컨테이너 안에 두고 map한다"를 어기면

**`.block()`으로 꺼내는 순간 이벤트 루프가 막힌다.**

**책의 Note가 원칙을 말한다**:
> **컨테이너(`Flux`든 `Mono`든)를 갖고 그 안의 것을 map하며 계속 안에 두는 것이 함수형 프로그래밍의 기본이다.** 새 `Mono` 인스턴스를 만드는 걱정은 할 필요가 없다 — **Reactor API가 알아서 처리한다.** 우리는 **데이터를 변환하는 데 집중**하면 된다. **리액티브 컨테이너 타입 안에 매끄럽게 담겨 있는 한, 프레임워크가 알맞은 때에 풀어 제대로 렌더링한다.**

> **이 Note가 리액티브 코드를 읽는 자세를 알려 준다 — `.block()`으로 꺼내고 싶은 충동을 참는 것이 전부다.**

**`map`이 실제로 하는 일**: **`Mono` 안에 든 타입을 변환**한다. `List<Employee>`를 `Rendering`으로 바꾸되 **모든 것을 `Mono` 안에 유지**한다. 방식은 **원래의 `Mono<List<Employee>>`를 풀어 그 결과로 완전히 새로운 `Mono<Rendering>`을 만드는 것**이다.

**어기면 생기는 일**:
- **`block()`** → 이벤트 루프 스레드가 멈춘다([[04b-java-concurrency-history]]의 25% 계산)
- **꺼내서 명령형으로 처리** → 그 아래 전부가 블로킹 코드가 된다
- **프레임워크가 "알맞은 때에 푸는" 타이밍 제어를 잃는다**

**비유로 보면** 포장을 뜯지 않는 배송 — **최종 수령인(프레임워크)만 뜯는다.** **깨지는 지점 둘**:
- **실제 배송은 상자를 뜯어야 내용을 바꿀 수 있지만 `map`은 상자를 유지한 채 내용을 바꾼 새 상자를 만든다** — **교체지 수정이 아니다**
- **상자를 뜯는 시점이 정해져 있지만 리액티브에서는 아무도 안 뜯을 수도 있다** — **반환하지 않으면 `DATABASE.values()`조차 읽히지 않는다**

## Q4. `collectList`를 쓸 수 없는 상황

**무한 스트림이다.**

> **모든 항목을 모아야 하나의 `Mono`가 나오므로, 그 지점에서 점진적 처리가 끊긴다.** **템플릿 렌더링은 리스트 전체가 필요하므로 불가피하지만, 무한 스트림에는 쓸 수 없다** — **영원히 완료되지 않는다.**

```
Flux (무한)  →  collectList()  →  onComplete 가 오지 않는다 → Mono 가 완성되지 않는다
```

**`collectList`는 스트리밍을 포기하는 연산자다** — 그 대가로 **리스트 전체를 한 번에** 얻는다.

**언제 그 대가가 정당한가**: **템플릿 렌더링**처럼 **전체가 있어야 결과를 만들 수 있는** 경우. HTML 페이지 하나를 그리려면 목록 전체가 필요하다.

**언제 정당하지 않은가**: **[[03-serving-data-with-reactive-get]]의 JSON 스트리밍**처럼 **도착하는 대로 내보낼 수 있는** 경우. 거기서는 `Flux`를 그대로 반환해 **점진적으로** 흘린다.

**즉 이 절의 `collectList`는 "템플릿이라는 소비자의 요구" 때문**이지 리액티브의 일반 패턴이 아니다.

**§6의 나머지 경계**: **`.block()`으로 꺼내지 않는다**(Q3) · **`Iterable`을 감싸는 것이 항상 이득은 아니다**(Q2) · **데이터 소스가 블로킹이면 이 파이프라인이 아무리 예뻐도 이벤트 루프가 막힌다.**

**그리고 `build()`를 빼먹으면**(§5) **builder가 그대로 남아 타입이 맞지 않는다.** `Rendering`은 **불변 타입**이고 builder는 그 **조립 단계**다.
