## Q1. `@RequestBody Employee`와 `@RequestBody Mono<Employee>`

| | `Employee` | **`Mono<Employee>`** |
|---|---|---|
| 프레임워크가 | **본문을 다 모을 때까지 기다렸다가 넘겨준다** | **도착하는 대로 흘려보낸다** |
| 그동안 스레드는 | **기다린다** | **다른 요청을 처리한다** |
| 맞는 경우 | **작은 본문** | **큰 본문·스트리밍** |

**리액티브에서는 요청 본문이 아직 다 오지 않았을 수 있다.** **큰 본문이라면 네트워크에서 조각조각 도착**한다. **그것을 다 기다렸다가 객체를 만들면, 기다리는 동안 [[01a-blocking-vs-non-blocking]]에서 없애려던 그 낭비가 다시 생긴다.**

> **`@RequestBody Employee`도 WebFlux에서 동작한다** — 컴파일되고 돌아간다. 다만 **리액티브의 이점이 그만큼 줄어든다.** **작은 본문에서는 실용적 선택**이다.

**`Mono`**: **0개 또는 1개 값을 다루는 Reactor 타입.** `Flux`의 **단일 항목 대응물**이다.

**방향이 뒤집힌다는 점이 이 절의 요점이다** — **GET에서는 우리가 데이터를 내보냈고 프레임워크가 구독했다. POST에서는 데이터가 들어온다.** **들어오는 데이터도 리액티브 컨테이너 안에 감싸여** 오므로 `map`으로 그 안에 접근한다.

## Q2. `map`과 `flatMap`을 정하는 한 문장 기준

> **map할 함수의 반환 타입이 또 리액티브 타입인가? 그렇다면 `flatMap`이다.**

**매핑은 일대일 연산이다** — 10개짜리 `Flux`를 `map`하면 새 `Flux`도 10개다.

| 상황 | 연산자 | **결과** |
|---|---|---|
| `Employee` → `String` | `map` | `Flux<String>` |
| `Employee` → `Flux<Skill>` | `map` | **`Flux<Flux<Skill>>` — 대개 원치 않는 것** |
| `Employee` → `Flux<Skill>` | **`flatMap`** | **`Flux<Skill>` — 평탄화됨** |

**`flatMap`은 map과 평탄화를 한 번에** 한다.

**실무에서 `flatMap`이 자주 나오는 진짜 이유는 두 번째 행이다** — **리액티브 메서드를 호출하면 반환값이 또 리액티브 타입**이므로, **`map`을 쓰면 중첩이 계속 쌓인다.** [[06-building-reactive-hypermedia-apis]]의 집합 루트 구현이 그 대표 사례다.

**책의 예**: **문자열 하나를 그 글자들의 리스트로 map하면 리스트의 리스트가 된다.** **대개는 그 중첩을 걷어내고 모든 글자가 든 하나의 `Flux`를 원한다.**

**대가 하나**(§6): **`flatMap`의 동시성 기본값을 의식한다.** **기본적으로 여러 내부 스트림을 동시에 구독**하므로, **외부 API 호출에 쓰면 예상보다 많은 요청이 동시에 나갈 수 있다.**

## Q3. 함수형 라우팅을 고르는 정당한 이유와 아닌 이유

**정당한 이유**: **스타일·명시성·조합.**

> **라우트를 설정 코드에서 명시적으로 선언하고 핸들러 메서드에 매핑하는 방식**으로, **애노테이션 주도 요청 매핑을 피하고 더 함수형인 스타일을 받아들이며, 라우트를 함수형 구성으로 조합·중첩·필터링해 요청 처리를 세밀하게 제어**한다.

**정당하지 않은 이유**: **성능.**

> **애노테이션 기반보다 성능 이점이 있는 것은 아니다. 둘 다 리액티브이며 차이는 스타일·명시성·조합에 있다.**

**책이 명시적으로 못 박는다.** **함수형 라우팅을 성능 최적화로 오해하는 경우가 흔한데, 선택 기준은 스타일이다.**

**`RouterFunction`**: **설정 코드에서 라우트를 선언하는 WebFlux의 함수형 라우팅 구성 요소.** `HandlerFunction`과 짝을 이룬다.

**이 장이 애노테이션 모델을 쓰는 이유**: **주 목적이 HTTP 계층 재설계가 아니라 리액티브 웹 개발 소개이므로, 명료함과 집중을 위해서**다. **Boot 4는 두 스타일을 완전히 지원하며 아키텍처 취향에 맞는 쪽을 고를 수 있다.**

## Q4. `map` 안의 `DATABASE.put`이 언제 실행되나

**프레임워크가 구독할 때다. 컨트롤러 메서드가 호출될 때가 아니다.**

```
컨트롤러 메서드 호출  →  Mono 파이프라인이 조립될 뿐
                         (DATABASE.put 은 실행 안 됨)
프레임워크가 구독      →  이때 실제로 저장된다
```

> **람다 안의 `DATABASE.put`은 컨트롤러 메서드가 호출될 때 실행되지 않는다. 조립될 뿐이고, 실제 저장은 프레임워크가 구독할 때 일어난다.**

**[[01b-reactive-streams-details]]의 "구독하기 전에는 아무 일도 없다"가 여기에도 적용된다.** [[04a-scaling-with-project-reactor]]가 이 구조를 다룬다.

**그래서 부수효과가 위험하다**(§5): **`DATABASE.put`처럼 부수효과가 있는 코드를 `map`에 넣는 것은 이 예제의 단순화다.** **실제로는 부수효과가 몇 번 실행될지(재시도·재구독 시) 보장이 다르므로 조심해야 한다.**

**구체적으로**: 흐름을 **두 번 구독**하거나 **`retry`가 걸리면** `put`이 **여러 번** 실행된다. 명령형이라면 한 번 부른 코드가 한 번 도는데, 리액티브에서는 **구독 횟수만큼** 돈다.

**그리고 `map` 안에서 블로킹 호출을 하면 안 된다**(§6) — **그 자리가 이벤트 루프 스레드**다.

**비유로 보면** 택배 수령 — 리액티브는 **"도착하면 이렇게 처리해 주세요"라는 지시서를 붙여 두고 다른 일을 하러 가는 것.** **깨지는 지점 둘**:
- **지시서를 아무도 읽지 않으면(구독하지 않으면) 상자는 그대로 있다** — 그래서 **반환하는 것이 중요**하다
- **택배 상자는 한 덩어리로 오지만 HTTP 본문은 조각으로 온다** — **`Mono`가 감추는 것이 그 조립 과정**이다
