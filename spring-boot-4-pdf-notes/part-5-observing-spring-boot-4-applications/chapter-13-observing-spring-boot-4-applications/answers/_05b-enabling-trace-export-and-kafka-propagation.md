## Q1. Kafka observation을 둘 다 켜야 하는 이유

**생산자가 실어 보내야 하고, 소비자가 읽어야 하기 때문이다.**

| 설정 | 하는 일 | **없으면** |
|---|---|---|
| `kafka.template.observation-enabled` | **생산자가 span을 만들고 메시지에 컨텍스트를 싣는다** | **실을 것이 없어 전파가 시작되지 않는다** |
| `kafka.listener.observation-enabled` | **소비자 연산이 관측에 참여하고 컨텍스트 전파를 받는다** | **소비 쪽이 별개 트레이스가 된다** |

> **한쪽만 켜면 여전히 끊긴다.**

**앞의 두 줄이 [[05-tracing-with-opentelemetry-and-tempo]]가 말한 전파 경계 문제의 답이다.**

**나머지 세 스위치**:
| 설정 | **없으면** |
|---|---|
| `tracing.export.enabled: true` | **만들어도 나가지 않는다** |
| `tracing.sampling.probability: 1.0` | 기본값에 따라 **일부만 기록** |
| `opentelemetry.tracing.export.otlp.endpoint` | **어디로 보낼지 모른다** |

**[[03b-instrumenting-the-application-for-logging]]에서 `tracing.enabled: false`로 꺼 뒀던 것이 여기서 켜진다** — 그리고 그 순간 **`logback-spring.xml`의 `captureMdcAttributes`가 미리 심어 둔 traceId가 로그에 채워진다.**

## Q2. 트레이스만 요청 수에 정비례해 데이터가 늘어나는 이유

| 신호 | **요청 1건이 만드는 데이터** |
|---|---|
| **메트릭** | **0** (기존 카운터에 +1) |
| **로그** | 몇 줄 |
| **트레이스** | **span 여러 개 + 속성 전부** |

> **초당 1만 요청이면 초당 span 5만 개다.**

**메트릭은 [[04-metrics-with-micrometer-prometheus-and-grafana]]의 성질 때문이다** — **수많은 사건이 숫자 몇 개로 접힌다.** 요청이 열 배 늘어도 **저장되는 것은 여전히 5초마다 숫자 몇 개**다.

**트레이스는 접히지 않는다** — **개별 요청이 전부**이기 때문이다([[05a-setting-up-grafana-tempo]]의 "Prometheus는 개별 요청을 보관하지 않는다"의 반대편).

**그래서 샘플링이 트레이스에만 있다** — 메트릭은 애초에 샘플링할 것이 없고, 로그는 레벨로 조절한다.

## Q3. 샘플링을 10%로 낮췄을 때의 실무적 문제

**문제가 된 그 요청이 기록되지 않았을 확률이 90%다.**

| 값 | 뜻 | 언제 |
|---|---|---|
| `0.0` | 기록 안 함 | 트레이싱 끄기 |
| `0.1` | 약 10% | **트래픽 많은 운영** |
| `1.0` | **전부** | **로컬·개발** |

> **로컬 예제라 `1.0`을 쓰고 모든 요청을 Tempo에서 볼 수 있게 하지만, 운영에서는 트래픽 양·비용·관측 필요에 맞춰 낮은 샘플링 비율을 쓰라.**

**역설이 여기 있다** — **평범한 요청은 잔뜩 기록되고 문제 요청은 대개 빠진다.** 무작위 샘플링은 **희귀한 것을 놓치도록** 설계돼 있다.

**실무의 대응**: **"오류가 난 요청은 항상 기록" 같은 규칙 기반 샘플링**을 쓴다. 결정을 **끝에서**(응답 상태를 안 뒤에) 내리는 tail-based sampling이 그 방향이다.

**"`sampling.probability: 1.0`이 안전한 기본값이다"는 오해다**(§5) — **로컬에서만 그렇다.**

## Q4. 자동 계측만으로 얻는 트레이스의 한계

**도메인 언어가 없다.**

```text
http post /employees          1.2s
  └ EmployeeRepository.save   0.03s
  └ employee-events send      1.1s
```

> **기술적으로는 정확하지만 "직원을 생성하는 일"이 어디인지, "알림을 보내는 일"이 어디인지 span 이름만 봐서는 모른다.**

**책의 표현**: **"이 트레이스들은 처음에는 기술적 연산만 반영한다. 더 의미 있게 만들려면 핵심 도메인 행위를 나타내는 비즈니스 수준 span으로 강화할 수 있다."**

**해법**: `Observation.createNotStarted("employee.create", ...)`에 **`contextualName("create employee")`**를 붙인다 — **사람이 읽기 좋은 이름이 트레이싱 백엔드의 span 이름이 된다.**

**[[04b-adding-custom-business-metrics-with-micrometer]]의 인프라 메트릭 vs 비즈니스 메트릭과 같은 구도**다 — **자동으로 나오는 것은 기술 계층**이고, **도메인 사건은 우리가 표시해야** 한다.

**[[05c-verifying-distributed-traces-in-tempo]]의 화면에서 `create employee (1.17s)`라는 줄이 바로 이 코드의 산물이다.**

## Q5. Timer와 Observation의 감싸는 순서가 바뀐 것

```
전:  Timer.record( createEmployeeAndPublishEvent )
후:  Observation.observe( Timer.record( createEmployeeAndPublishEvent ) )
     └─ Observation 이 Timer 를 감싼다
```

> **타이머는 여전히 얼마나 걸렸는지 재지만, 감싸는 관측이 그 연산에 end-to-end 트레이스 안에서의 자리를 준다.**

| | **Timer만** | **Observation + Timer** |
|---|---|---|
| 얼마나 걸렸나 | 안다 | 안다 |
| **전체 요청의 몇 %인가** | **모른다** | **안다** |
| **앞뒤에 무엇이 있었나** | **모른다** | **안다** |
| **waterfall에 보이나** | **아니오** | **예 — `create employee`로** |

**"Observation이 Timer를 대체한다"는 오해다**(§5) — **감싼다.** **둘 다 살아 있고, 메트릭과 트레이스를 동시에 얻는다.**

**[[02-designing-an-observability-architecture]]의 "하나의 관측에서 세 신호가 파생된다"가 코드에서 확인되는 지점**이다 — `Observation` 하나가 **span을 만들고, 그 안의 Timer가 메트릭을 만들고, 로그에는 traceId가 실린다.**

**`.observe(() -> ...)`가 `.record(() -> ...)`와 같은 형태인 것도 일관적이다** — **시작 → 실행 → 종료**를 한 번에.

## Q6. `employee.role`이 저 카디널리티인 이유

| | **저 카디널리티** | **고 카디널리티** |
|---|---|---|
| 값의 가짓수 | **작고 정해져 있다** | **거의 무한** |
| 예 | `status=SUCCESS\|FAILED`, **`role=ADMIN\|USER`** | **`userId`, `email`, `orderId`** |
| 집계 | **안전** | 위험 |
| 색인 | 안전 | **시계열·라벨 폭발** |
| 쓸모 | **메트릭·span 태그** | **특정 요청 디버깅** |

**`employee.role`은 `ENGINEER`, `MANAGER`, `UNKNOWN` 정도로 제한된다.**

**`employee.id`였다면**: **직원 수만큼 값이 생긴다.** **메트릭에 넣으면 사용자가 10만 명일 때 시계열이 10만 개**, 메트릭이 5개면 **50만 개**다. **Prometheus 메모리가 감당하지 못한다.**

**`.lowCardinalityKeyValue(...)`라는 메서드 이름이 이미 경고를 담고 있다.**

> **기본은 낮은 카디널리티. 높은 카디널리티는 선택적으로 쓰고, 메트릭이나 널리 색인되는 필드에는 넣지 마라.**

**이 원칙이 [[04b-adding-custom-business-metrics-with-micrometer]]의 메트릭 태그 선택(`role`, `outcome`)과 정확히 같은 판단**이다 — **메트릭이든 span이든 같은 규칙**이 적용된다.

**"카디널리티는 메트릭만의 문제다"는 오해다**(§5) — **span 속성에도 적용된다. 그래서 API 이름이 `lowCardinalityKeyValue`다.**

**[[03a-setting-up-the-logging-infrastructure]]의 Loki 라벨 선택도 같은 문제**다 — **세 신호 전부에서 반복되는 규칙**이다.

## Q7. 고 카디널리티 속성이 유용한 경우

**특정 요청을 추적할 때다.**

> **"고 카디널리티는 무조건 나쁘다" — 특정 요청을 추적할 때는 유용하다. 메트릭이나 색인 필드에 넣지 말라는 것이 지침이다.**

```
트레이스 span 속성:  employee.id=42 를 넣어도 된다
                     → 그 트레이스를 열었을 때 어느 직원인지 보인다
                     → 집계 대상이 아니므로 폭발하지 않는다

메트릭 태그:         employee.id 를 넣으면 시계열 10만 개
                     → 금지
```

**즉 판단 기준은 "값 자체"가 아니라 "어디에 넣는가"다** — **집계·색인되는 자리인가, 개별 조회용 자리인가.**

**[[01-three-pillars-of-observability]]의 신호별 성격과 대응한다**:
- **메트릭 = 집계** → 저 카디널리티만
- **트레이스 = 개별 요청** → 고 카디널리티 허용
- **로그 = 개별 사건** → 본문에는 무엇이든(다만 Loki **라벨**은 저 카디널리티)

**§6의 관련 경계**: **모든 메서드를 관측으로 감싸면 안 된다** — **span이 수백 개가 되면 waterfall이 읽히지 않고 오버헤드도 커진다.** **도메인상 의미 있는 단위**만 감싼다.

## Q8. 작업 공정 비유가 깨지는 지점

**비유**: 비즈니스 span을 얹는 것은 **"기계 부품 목록 위에 작업 공정 이름을 덧붙이는 것"** — **"볼트 조임 3초"만 있던 자리에 "조립 공정 12초"가 생긴다.**

**깨지는 지점**: **공정과 부품이 같은 시간을 두 번 센다는 오해를 준다.**

> **실제로는 부모 span이 자식 span들을 포함하는 구조이며, 시간이 중복 계산되지 않고 계층으로 표현된다.**

```
오해:  조립 공정 12초 + 볼트 조임 3초 = 15초?
실제:  조립 공정 12초  (그 안에 볼트 조임 3초가 포함)
```

**[[05c-verifying-distributed-traces-in-tempo]]의 "span 시간을 다 더하면 총 시간이 된다"는 오해와 같은 것**이다.

**비유가 맞는 부분은 남는다** — **기술 용어 위에 도메인 용어를 얹는다**(Q4). 깨지는 것은 **시간의 합산 방식**이다.

**§6의 나머지 경계**: **샘플링을 낮추면 그 요청이 없을 수 있다**(Q3) · **전파는 프레임워크가 지원하는 경계에서만 자동이다** — **직접 만든 스레드 풀이나 미지원 클라이언트를 거치면 수동 전파가 필요하다.**

**책은 `NotificationService`의 Kafka 컨슈머 흐름과 DLT 리스너에도 같은 방식으로 관측을 감쌌다고 밝힌다** — 그래서 **알림 처리와 실패도 같은 분산 트레이스 안의 비즈니스 span**으로 나타난다.
