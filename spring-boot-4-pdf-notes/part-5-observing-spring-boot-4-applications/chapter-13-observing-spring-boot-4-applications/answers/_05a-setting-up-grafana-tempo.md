## Q1. 트레이스를 Loki나 Prometheus에 넣을 수 없는 이유

| | **못 하는 이유** |
|---|---|
| **Loki** | **텍스트 스트림용. 계층 구조와 지속 시간을 다루지 못한다** |
| **Prometheus** | **시계열용. 개별 요청을 보관하지 않는다** |
| **Tempo** | **trace ID로 조회, span 계층 보존, 대량 쓰기에 최적화** |

**[[05-tracing-with-opentelemetry-and-tempo]]의 Q6가 이유를 준다** — **span은 시작·종료 시각과 부모 관계를 갖는다.** Loki는 **텍스트 줄**만 알고, Prometheus는 **집계**만 안다.

**Prometheus가 특히 맞지 않는 이유**: [[04-metrics-with-micrometer-prometheus-and-grafana]]의 성질 — **개별 사건은 버리고 집계된 상태로 저장**한다. **트레이스는 개별 요청이 전부**다.

**세 신호에 세 저장소가 필요한 이유가 여기서 완성된다** — [[02-designing-an-observability-architecture]]의 백엔드 넷 중 셋이 각각 다른 데이터 모양을 다룬다.

## Q2. Tempo가 색인을 거의 만들지 않는 이유

**trace ID로 찾는 것이 주 용도이므로 그 하나만 빠르게 찾을 수 있으면 된다.**

> **덕분에 저장 비용이 낮다.**

**Loki의 "라벨만 색인한다"와 같은 계열의 선택**이다([[03-structured-logging-with-loki-and-grafana]]) — **Grafana 스택의 저장소들이 공통적으로 "색인을 최소화해 비용을 낮춘다"**는 방향을 택했다.

**대가**: **trace ID를 모르면 찾기 어렵다.** 그래서 **다른 신호에서 trace ID를 얻어 오는 경로**가 중요해진다 — [[06-correlating-logs-metrics-and-traces]]의 로그→트레이스 링크가 그 자리다.

**즉 Tempo는 혼자 쓰는 저장소가 아니다** — **메트릭이나 로그가 먼저 범위를 좁혀 주고, 그 결과의 trace ID로 조회**하는 구조를 전제한다. [[01-three-pillars-of-observability]]의 조사 순서가 저장소 설계에 반영된 것이다.

## Q3. `tempo.yml`의 네 부분과 트레이스의 생애

| 단계 | **컴포넌트** | **하는 일** | **필요한 이유** |
|---|---|---|---|
| **받기** | `distributor` | **OTLP로 들어오는 트레이스 수신** (4317/4318) | 입구 |
| **모으기** | `ingester` | **최대 5분까지 블록에 쌓았다가 flush** | **span 하나마다 파일을 쓰면 감당이 안 된다** |
| **안전** | **WAL** | **메모리에 있는 동안의 유실 방지** | **5분 사이에 죽으면 그만큼 날아간다** |
| **정리** | `compactor` | **작은 블록 합치기 + 보존 기간 지나면 삭제** | Q5 |

```
distributor (받는다) → ingester (모은다, 최대 5분)
                         ├─ WAL 에 선행 기록
                         └─ blocks 로 내려쓴다 → compactor (합치고 24시간 뒤 삭제)
                                                    ↑ Grafana 가 :3200 으로 질의
```

**`storage`도 함께 읽는다**: **`backend: local`은 로컬 파일 시스템**이고 **운영에서는 보통 객체 저장소(S3·GCS)**를 쓴다. **`/tmp` 아래라는 점**도 눈여겨볼 만하다 — **컨테이너를 지우면 트레이스도 사라진다.**

**`overrides.metrics_generator.processors: []`는 의도적이다**(§5) — **메트릭은 Prometheus가 맡으므로 중복을 피한다.**

## Q4. `ingester`가 5분까지 모으는 이유와 WAL

**모으는 이유**: **span 하나마다 파일을 쓰면 감당이 안 된다.**

**WAL이 필요한 이유**: **그 5분 동안 데이터가 메모리에 있으므로 프로세스가 죽으면 그만큼 날아간다.**

**WAL**: **최종 저장 전에 먼저 순차 기록해 두는 로그.**

```
span 도착 → 메모리 블록에 쌓임 (최대 5분)
          → 동시에 WAL 에 순차 기록      ← 죽어도 복구 가능
          → 5분 뒤 blocks 로 flush
```

**"WAL이 있으면 데이터가 안전하다"는 오해다**(§5) — **적재 중 프로세스 사망을 막아 줄 뿐, `/tmp` 아래 저장이라 컨테이너를 지우면 다 사라진다.**

**§6의 경계**: **`max_block_duration`을 늘리면 유실 위험 구간이 커진다.** **WAL이 있어도 flush 전 데이터는 복구 절차가 필요하다.**

**즉 5분은 두 비용의 절충**이다 — **짧으면 파일이 많아지고**(Q5), **길면 위험 구간이 커진다.**

## Q5. 컴팩션이 없으면

**파일 수가 폭증해 조회가 느려진다.**

> **5분마다 블록이 하나씩 생긴다. 하루면 288개, 한 달이면 8,640개다. 조회할 때마다 그 많은 파일을 열어야 하면 느리다. 합쳐 두면 파일 수가 줄어든다.**

**컴팩션**: **작게 흩어진 블록을 모아 큰 블록으로 합치는 작업.**

**두 번째 일도 한다** — **보존 기간이 지나면 삭제.** `block_retention: 24h`.

**보존 기간**: **데이터를 얼마나 두었다가 지울지.** **24시간은 로컬 예제라 짧게 잡은 값**이지만, **트레이스는 양이 많아 실제로도 짧게(며칠) 두는 경우가 흔하다.**

**"`block_retention`을 늘리면 다 보관된다"는 오해다**(§5) — **저장 공간이 그만큼 필요하다. 트레이스는 양이 많아 무한 보관이 현실적이지 않다.**

**비유의 깨짐이 이것과 이어진다** — 우편 집하장 비유는 **조회가 언제든 들어온다는 점을 담지 못한다.** **우편은 배달하면 끝이지만 트레이스는 저장된 뒤에도 24시간 내내 조회 대상이고, 그래서 컴팩션이 조회 성능을 위한 작업이기도 하다.**

## Q6. 3200·4317·4318 세 포트

| 포트 | **역할** |
|---|---|
| **3200** | **Grafana가 질의하는** HTTP 포트 (`server.http_listen_port`) |
| **4317** | **트레이스를 받는** OTLP gRPC (`distributor.receivers`) |
| **4318** | **트레이스를 받는** OTLP HTTP |

> **"3200이 트레이스를 받는 포트다" — 받는 것은 4317/4318이고 3200은 Grafana가 질의하는 포트다.**

**`docker-compose.yml`에는 3200만 노출된다** — **받는 포트는 컨테이너 네트워크 안에서 Collector가 접근**하면 되고, **질의 포트만 Grafana에서 필요**하다.

**Collector가 Tempo로 보낼 때 gRPC(4317)를 쓴다** — **애플리케이션이 Collector에 보낼 때는 HTTP(4318)를 썼다.** **같은 프로토콜의 두 전송 방식이 구간마다 다르게 쓰인 것**이다.

**[[04a-setting-up-prometheus-for-metrics]]와 대조하면 흥미롭다** — 거기서는 **Prometheus가 Collector를 pull**했고, 여기서는 **Collector가 Tempo로 push**한다. **백엔드마다 수집 모델이 다르고, Collector가 그것을 흡수한다.**

## Q7. `resource` 프로세서를 세 파이프라인이 공유하는 것

**`service.name=employee-service`가 로그에도, 메트릭에도, 트레이스에도 붙는다.**

| | **logs** | **metrics** | **traces** |
|---|---|---|---|
| receivers | `[otlp]` | `[otlp]` | `[otlp]` |
| **processors** | **`[resource, batch]`** | **`[resource, batch]`** | **`[resource, batch]`** |
| exporters | `[loki, debug]` | `[prometheus]` | `[otlp/tempo, debug]` |

> **이 일관성이 [[06-correlating-logs-metrics-and-traces]]에서 셋을 잇는 근거가 된다.**

**나중에 가능해지는 것**: **한 화면에서 "이 서비스의" 로그·메트릭·트레이스를 함께** 보고, **한 신호에서 다른 신호로 넘어갈 때 서비스 이름으로 필터**를 이어 갈 수 있다.

**[[03b-instrumenting-the-application-for-logging]]의 `${spring.application.name}` 참조와 짝을 이룬다** — **애플리케이션에서 한 번, Collector에서 한 번.** **어긋날 여지가 두 지점에서 모두 제거**된다.

**`otlp/tempo`의 슬래시**(§5): **경로가 아니라 인스턴스 이름**이다. **같은 종류 익스포터를 여러 개 둘 때 구분하는 문법**이며, **"OTLP 익스포터인데 tempo용"**이라는 뜻이다.

**`tls.insecure: true`는 로컬 예제용**이다 — **Collector와 Tempo가 같은 Docker 네트워크 안이라 인증서 없이 연결**한다. §6: **네트워크 경계를 넘는 구성에서는 반드시 TLS를 켠다.**

## Q8. 우편 집하장 비유가 깨지는 지점

**비유**: **접수(distributor), 자루에 모으기(ingester), 자루 합치기(compactor), 보관 기간 후 폐기(retention).**

**깨지는 지점**: **조회가 언제든 들어온다는 점을 담지 못한다.**

> **우편은 배달하면 끝이지만 트레이스는 저장된 뒤에도 24시간 내내 조회 대상이고, 그래서 컴팩션이 조회 성능을 위한 작업이기도 하다.**

```
우편:  자루 합치기 = 운송 효율
Tempo: 컴팩션 = 운송 효율 + 조회 성능 (Q5)
```

**저장소가 "거쳐 가는 곳"이 아니라 "머무는 곳"**이라는 차이다. Grafana가 `:3200`으로 **계속 질의**한다.

**비유가 맞는 부분은 남는다** — **단계별 처리와 보존 기간**(Q3). 깨지는 것은 **데이터의 종착 여부**다.

**§6의 나머지 경계**: **`backend: local`과 `/tmp` 경로는 운영용이 아니다** — **컨테이너 재생성으로 데이터가 사라지고, 여러 인스턴스가 공유할 수 없다.**
