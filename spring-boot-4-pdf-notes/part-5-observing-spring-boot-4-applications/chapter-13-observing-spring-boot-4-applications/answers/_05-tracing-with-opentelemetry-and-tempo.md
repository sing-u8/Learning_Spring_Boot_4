## Q1. 메트릭이 알려 준 뒤 막히는 네 질문

**`Average Employee Creation Time: 1.2s` (평소 40ms)를 봤다. 그다음**:

| 질문 | **메트릭으로 답할 수 있나** |
|---|---|
| **어느 구간이 느린가** | **아니오 — Timer는 전체만 잰다** |
| **DB인가 Kafka인가** | **아니오** |
| 느린 요청이 특정 role에만인가 | 태그가 있으면 **부분적으로** |
| **어느 요청이 느렸나** | **아니오 — 집계라 개별 요청이 없다** |

**로그를 뒤져도 마찬가지다** — **요청이 시작·종료한 로그 줄은 있지만 그 사이에 다른 요청 수백 건의 로그가 섞여 있고, 어느 줄이 같은 요청의 것인지 표시가 없다.**

> **트레이스가 정확히 이 빈틈을 메운다** — **"연산이 컴포넌트·서비스·비동기 경계를 넘어가는 경로를 포착해, 로그나 메트릭만으로는 이해하기 어려운 지연·의존성·실패를 드러낸다."**

**[[01-three-pillars-of-observability]]의 조사 순서가 여기서 두 번째 칸에 도달했다** — 메트릭이 **"어느 요청이?"**를 묻게 했고, 트레이스가 답한다.

## Q2. trace ID로 경로가 복원되는 원리

1. **요청이 들어오면 traceId를 만든다**
2. **요청이 시스템을 지나가는 각 단계마다 span을 만든다**
3. **모든 span이 같은 trace ID를 공유한다**
4. **나중에 그 ID로 모으면 전체 경로가 재구성된다**

> **이 단순한 아이디어가 분산 시스템에서 특히 강력해진다. 여러 프로세스, 여러 스레드에 흩어진 작업이 ID 하나로 다시 묶이기 때문이다.**

**span**: **작업 단위 하나.**

**[[03-structured-logging-with-loki-and-grafana]]에서 "traceId가 이 장 전체의 접착제"라고 한 것이 여기서 실체를 얻는다** — 로그에 실리는 그 값이 **트레이스의 뼈대**이기도 하다.

**핵심은 3번이다** — **"같은 ID를 공유한다"**가 성립하려면 **ID가 경계를 넘어 전달**돼야 한다 → Q3·Q4.

## Q3. 5번에만 괄호로 이름이 붙은 이유

**전파 경계이기 때문이다** — **Kafka Topic (Propagation Boundary).**

**전파 경계**: **트레이스 컨텍스트가 프로세스나 스레드를 넘어가야 하는 지점.**

| | **1–4번** | **5번 이후** |
|---|---|---|
| 같은 스레드인가 | **예** | **아니오** |
| 같은 프로세스인가 | 예 | 아닐 수 있다 |
| 같은 시각인가 | 예 | **아니다 — 몇 초 뒤일 수도** |
| **trace ID를 어떻게 아나** | **스레드 로컬에서 읽는다** | **메시지에 실려 와야 한다** |

**다른 여섯 단계는 span이 붙는 작업**이지만 **5번은 경계를 표시하는 개념적 단계**다(§5).

**"Kafka 토픽 자체가 span이다"는 오해다** — **토픽은 저장소**이고 **span은 발행 작업(4번)과 소비 작업(6번)에 붙는다.**

**7단계 각각이 span인 이유**:
| 단계 | **이 단계가 span인 이유** |
|---|---|
| 1 | **이후 전체의 맥락이 여기서 시작된다** |
| 2 | 요청 수신 시점을 표시 |
| 3 | **DB 작업이 얼마나 걸렸는지 분리** |
| 4 | **나가는 메시지**를 별도 작업으로 |
| 6 | **다른 프로세스·다른 시각의 작업** |
| 7 | **워크플로의 실제 끝** |

## Q4. 동기 구간과 비동기 경계의 trace ID 전달

```
동기:    trace ID 가 스레드에 붙어 다닌다 → 아무것도 안 해도 이어진다
비동기:  Kafka 에 메시지를 넣는 순간 스레드가 끝난다
         나중에 다른 스레드가 그 메시지를 꺼낸다
         → 그 사이를 이어 줄 것이 없으면 트레이스가 거기서 끊긴다
```

> **그래서 컨텍스트 전파가 필요하다.** **Kafka 메시지 헤더에 trace ID를 실어 보내고, 소비하는 쪽이 그것을 읽어 이어 붙인다.**

**컨텍스트 전파**: **실행 맥락을 호출 경계 너머로 실어 나르는 일.**

**자동으로 해 주는 스위치**: [[05b-enabling-trace-export-and-kafka-propagation]]의 **`spring.kafka.listener.observation-enabled`**와 **`spring.kafka.template.observation-enabled`** 두 줄.

**"trace ID만 있으면 알아서 이어진다"는 오해다**(§5) — **동기 구간은 그렇지만 비동기 경계는 명시적 전파가 필요하다. 안 하면 조용히 끊긴다.**

**§6의 관련 경계**: **전파를 지원하지 않는 경계가 있다** — **직접 만든 스레드 풀이나 외부 시스템을 거치면 컨텍스트가 끊길 수 있다.** [[../../part-4-scaling-an-application-with-spring-boot/chapter-11-virtual-threads-in-java-and-spring-boot/03-integrating-virtual-threads-with-taskexecutor|Ch11]]의 `TaskExecutor`도 같은 종류의 경계다.

## Q5. 컨텍스트 전파가 실패하면

**트레이스가 두 개로 쪼개진다 — 하나는 HTTP 요청, 하나는 알림 처리.**

> **그러면 "그 요청 때문에 이 알림이 실패했다"를 알 수 없고, [[04b-adding-custom-business-metrics-with-micrometer]]에서 지적한 "비동기 부분이 안 보이는" 문제가 그대로 돌아온다.**

**증상이 미묘하다** — **트레이스가 아예 없는 것이 아니라 둘 다 정상적으로 보인다.**
```
Trace A: 컨트롤러 → 서비스 → Kafka 발행   (완결돼 보인다)
Trace B: Kafka 소비 → 알림 처리           (완결돼 보인다)
         ↑ 둘이 같은 요청인 줄 아무도 모른다
```

**그래서 확인 방법이 필요하다** — [[05c-verifying-distributed-traces-in-tempo]]에서 **waterfall에 소비 쪽 span이 함께 있는지**를 본다.

**이것이 이 장 전체가 반복하는 "조용한 실패"의 또 다른 얼굴이다** — [[03c-verifying-logs-in-grafana]]의 로그 파이프라인, [[03b-instrumenting-the-application-for-logging]]의 `ObservabilityConfig` 누락과 같은 종류다.

## Q6. span이 로그 줄과 다른 점

**① 시작·종료 시각을 갖는다** — 로그는 **한 시점**의 기록이지만 span은 **구간**이다.
**② 부모 관계를 갖는다** — 로그는 평평하지만 span은 **계층**을 이룬다.

> **"트레이스는 로그를 순서대로 모은 것이다" — 다르다. 계층과 지속 시간이 있다는 점이 결정적이다.**

**그래서 waterfall로 그려진다** — **어느 작업이 어느 작업 안에 들어 있고, 각각 얼마나 걸렸는지**가 한눈에 보인다. 로그를 시각순으로 나열하면 **중첩 관계가 사라진다.**

**Q1의 "어느 구간이 느린가"가 이 두 성질에서 나온다** — **지속 시간**이 있어야 비교하고, **계층**이 있어야 "그 안의 어디"를 안다.

**"트레이스가 있으면 메트릭이 필요 없다"는 오해도 함께**(§5) — **트레이스는 보통 샘플링되므로 전체 통계를 대신하지 못한다.**

**얻는 것 정리**:
| 질문 | **트레이스가 주는 답** |
|---|---|
| 어느 구간이 느린가 | **span별 지속 시간을 나란히** |
| DB인가 Kafka인가 | **3번과 4번 span의 길이 비교** |
| 어느 요청이 느렸나 | **trace ID로 개별 요청을 특정** |
| 비동기 쪽은 | **6·7번 span이 같은 트레이스에** |

## Q7. 택배 송장 비유가 깨지는 지점

**비유**: **번호 하나로 집하·간선·배송을 전부 조회한다.**

**깨지는 지점**: **한 요청이 여러 갈래로 나뉜다는 점을 담지 못한다.**

> **택배는 한 경로를 따라가지만 요청은 DB 호출과 Kafka 발행처럼 여러 자식 작업으로 갈라지고 일부는 병렬이다. 그래서 결과가 목록이 아니라 계층을 가진 waterfall로 그려진다.**

```
택배:  집하 → 간선 → 배송   (선형)
요청:  컨트롤러
         ├─ DB 저장
         └─ Kafka 발행 → (비동기) 소비 → 알림   (분기 + 계층)
```

**Q6의 "계층"이 이 차이의 결과**다.

**비유가 맞는 부분은 남는다** — **ID 하나로 전 구간을 조회한다**(Q2). 깨지는 것은 **경로의 모양**이다.

**§6의 나머지 경계**: **트레이스는 비싸다** — **요청마다 데이터를 만들므로 전량 수집은 부담**이고 [[05b-enabling-trace-export-and-kafka-propagation]]에서 **샘플링**을 다룬다. **span이 너무 잘면 읽기 어렵다** — **모든 메서드를 span으로 만들면 waterfall이 수백 줄**이 된다.

**저장은 Tempo가 맡고**([[05a-setting-up-grafana-tempo]]), **[[05c-verifying-distributed-traces-in-tempo]]에서 waterfall로 보게 된다.**
