## Q1. 인프라 메트릭으로 잡을 수 없는 장애

> **`POST /employees`가 200을 잘 반환한다. CPU 20%, 메모리 여유, 응답 시간 40ms. 그런데 알림이 한 건도 발송되지 않고 있다.**

**이유**: **알림이 HTTP 응답 뒤에 비동기로 처리된다.** **Kafka 컨슈머가 계속 실패해도 HTTP 지표는 완벽하다.**

| 무엇이 망가졌나 | **인프라 메트릭에 나타나나** |
|---|---|
| **알림 발송 실패율 90%** | **아니오** |
| **중복 이벤트가 절반** | **아니오** |
| 특정 role의 생성만 느림 | **아니오** (평균에 묻힌다) |
| **직원 생성이 0건** | **아니오** (요청이 없으면 정상으로 보인다) |

**마지막 줄이 특히 교묘하다** — **아무 일도 안 일어나는 것**은 인프라 관점에서 **가장 건강해 보인다.**

> **생성된 직원 수, 생성 실패, 발송된 알림, 처리된 DLT 이벤트 같은 비즈니스 메트릭이 관측 가능성을 훨씬 더 유용하게 만든다.**

**"인프라 메트릭이 정상이면 서비스가 정상이다"는 오해다**(§5) — **이 장의 예제가 반례**다.

## Q2. "재는 것을 정하기 전에 알고 싶은 것을 적는다"

| **질문** | **필요한 메트릭 종류** |
|---|---|
| 직원이 몇 명 생성됐나 | **Counter** — 단조 증가만 하는 누적 수치 |
| 직원 생성에 얼마나 걸리나 | **Timer** — 작업 소요 시간 |
| 알림이 몇 건 수신·발송·실패·중복됐나 | **Counter + 태그로 구분** |

**왜 순서가 중요한가**: **거꾸로 하면 "잴 수 있는 것"만 재게 된다.** 인프라 메트릭이 자동으로 나오므로 **그것을 보다가 "이걸로 뭘 알 수 있지?"를 묻게** 되고, Q1의 사각지대가 그대로 남는다.

**질문에서 출발하면 메트릭 종류도 자연히 정해진다** — **"몇 건"이면 Counter, "얼마나 걸리나"면 Timer, "어떤 종류로 나뉘나"면 태그.**

**[[01-three-pillars-of-observability]]의 "모니터링은 무엇을 볼지 미리 알고 있다를 전제한다"와 긴장 관계에 있다** — 커스텀 메트릭도 **미리 정해야** 한다. 다만 **도메인 사건은 기술 지표보다 예측 가능**하다.

## Q3. `.record(() -> ...)`가 손으로 시각을 찍는 것보다 나은 이유

> **재려는 작업을 람다로 감싼다. 시작·종료 시각을 손으로 찍는 대신 감싸면, 예외가 나도 시간이 기록되고 `finally`를 잊을 여지가 없다.**

```java
// 손으로
long start = System.nanoTime();
Employee saved = doWork();          // ← 여기서 예외가 나면
timer.record(System.nanoTime()-start, NANOSECONDS);  // 이 줄이 실행되지 않는다

// .record()
timer.record(() -> doWork());       // 예외가 나도 시간이 기록된다
```

**"`.record(...)`는 편의 문법이다"는 오해다**(§5) — **예외 상황에서도 시간이 기록되게 보장한다.** **손으로 시각을 찍는 것과 동등하지 않다.**

**실패한 요청의 소요 시간이 특히 중요하다** — **타임아웃으로 30초 걸린 요청**이 기록에서 빠지면 **평균이 실제보다 좋아 보인다.**

**나머지 요소들**:
| 요소 | **없으면** |
|---|---|
| `MeterRegistry` 주입 | **메트릭을 등록할 곳이 없다** |
| `.description(...)` | **메트릭 목록에서 뜻을 모른다** |
| `.tag("role", role)` | **role별 비교가 불가능하다** |
| `.register(meterRegistry)` | **파이프라인으로 나가지 않는다** |

## Q4. `roleForMetrics`가 `UNKNOWN`을 돌려주는 이유

**태그 값이 `null`이면 메트릭 등록이 실패하거나 이상한 라벨이 생기기 때문이다.**

> **항상 유효한 값을 보장하는 것이다.**

```
role 이 null → 태그 값이 null → 등록 실패 또는 라벨이 빈 문자열/"null" 문자열
role 이 없으면 "UNKNOWN" → 정상적인 라벨 값. 질의에서 구분 가능
```

**부수 이득**: **`UNKNOWN`이 얼마나 많은지 자체가 정보**가 된다. **역할 없이 생성되는 직원이 있다는 사실**을 대시보드에서 발견할 수 있다.

**null을 그냥 두는 것과 비교하면** — 등록이 실패하면 **그 메트릭만 조용히 사라지고**, 빈 문자열이 되면 **질의에서 걸러 내기 애매**하다.

**일반화하면**: **메트릭 태그 값은 항상 유한하고 유효한 집합에서 나와야** 한다. 그것이 Q5의 카디널리티 관리와도 이어진다.

## Q5. 태그의 이득과 대가

**이득**: **질의 가능한 차원이 생긴다.**
```
태그 없음:  employee.created.count = 1500        → 총 1500건만 안다
태그 있음:  {role=ENGINEER}=900, {role=MANAGER}=600 → 역할별 분포·특정 역할의 이상
```

> **타이머와 카운터 양쪽을 역할별로 분석할 수 있어, 직원 유형에 따른 활동량이나 지연 시간을 비교할 수 있다.**

**Prometheus에서 `sum by (role) (employee_created_count_total)` 같은 질의가 성립하는 근거다**([[04c-verifying-metrics-in-prometheus-and-grafana]]).

**대가**: **태그 값 조합마다 별개의 시계열이 생긴다.**

> **`role`처럼 값이 몇 개뿐이면 괜찮지만, 직원 ID를 태그로 넣으면 시계열이 직원 수만큼 생긴다.**

**이 위험이 고 카디널리티 문제**이고, **[[05b-enabling-trace-export-and-kafka-propagation]]에서 책이 Note로 정면으로 다룬다.**

**"태그는 많을수록 분석이 잘 된다"는 오해다**(§5) — **값의 가짓수가 적은 것만 태그로 쓴다.**

**§6의 경계**: **비즈니스 메트릭에도 카디널리티 상한이 있다.** **`role`이 수백 종이 되면 태그로 부적합해진다.**

## Q6. 알림 결과를 태그 하나로 묶은 판단

**질의가 쉽고 확장에 유리하기 때문이다.**

```java
private void recordNotificationMetric(String outcome) {
    meterRegistry.counter("employee.notification.count", "outcome", outcome).increment();
}
```

| `outcome` 값 | 언제 |
|---|---|
| `received` | 이벤트를 Kafka에서 받았을 때 |
| `duplicate` | 중복 이벤트를 걸렀을 때 |
| `failed` | 발송에 실패했을 때 |
| `sent` | 발송에 성공했을 때 |

> **메트릭 이름은 하나이고 태그 값으로 결과를 구분한다.**

**이렇게 하면**:
- **`sum by (outcome) (...)` 한 줄로 전체 분포를 볼 수 있다**
- **새 결과 유형이 생겨도 메트릭을 추가하지 않아도 된다**

**메트릭을 넷으로 나눴다면**: 분포를 보려면 **네 질의를 각각 던져 합쳐야** 하고, 다섯 번째 유형이 생기면 **대시보드도 고쳐야** 한다.

**"결과 종류마다 메트릭을 따로 만드는 게 명확하다"는 오해다**(§5).

**`Math.random() < 0.5`는 Ch12에서 재시도·DLT를 실험하려고 넣은 장치**인데, **여기서는 실패 메트릭이 실제로 오르는 것을 보기 위한** 용도가 된다.

> **원문 오류 두 가지**: (1) **중복 이벤트 분기에 `System.out.println`이 그대로 남아 있다** — [[03b-instrumenting-the-application-for-logging]]은 모든 `System.out`을 SLF4J로 바꿨다고 말한다. **이 줄은 Logback을 거치지 않으므로 Loki에 도달하지 않는다.** (2) **항목 설명은 `recordNotificationMetric("received")`와 `("duplicate")`를 호출한다고 하지만 인쇄된 코드에는 그 두 호출이 없다.** [[04c-verifying-metrics-in-prometheus-and-grafana]]의 대시보드에는 `received 23`, `duplicate 8`이 찍혀 있으므로 **실제 저장소 코드에는 있고 지면에서 빠진 것으로 보인다.**

## Q7. `employee.create.time`이 재지 못하는 구간

**Kafka 발행 이후의 비동기 알림 흐름이다.**

```
[HTTP 요청 안 — Timer 가 재는 범위]
컨트롤러 → EmployeeService → DB 저장
                          → Kafka 발행
- - - - - - - - - - - - - - - - - - -  경계
[HTTP 응답 후 — 별도 메트릭이 필요]
Kafka 리스너 → NotificationService → 발송·실패·중복
```

> **`employee.create.time`은 점선 왼쪽까지만 잰다. 오른쪽에서 무슨 일이 벌어져도 이 타이머는 정상으로 보인다.**

**책이 짚는 전환**:
> **직원 생성 워크플로는 `EmployeeService`가 저장하는 것으로 끝나지 않는다.** … **비즈니스 프로세스의 일부가 원래 HTTP 요청 밖에서 일어나고, 그 부분에는 자기만의 메트릭이 필요하다.**

**Q1의 "대시보드는 초록인데 알림이 안 간다"가 정확히 이 구조에서 나온다.**

**[[01-three-pillars-of-observability]]의 Q5와 같은 사실이다** — **비동기 구간의 실패는 HTTP 응답 시간에 나타나지 않는다.** 거기서는 문제 제기였고, 여기서는 **`NotificationService`에 별도 카운터를 두는 것**이 해법이다.

## Q8. 계기판/장부 비유가 깨지는 지점

**비유**: **"차량 계기판과 매출 장부"** — **엔진은 정상인데 배달이 안 되고 있을 수 있다.**

**깨지는 지점**: **둘이 같은 계측기에서 나온다는 점을 담지 못한다.**

> **여기서는 `MeterRegistry` 하나가 JVM 메모리도, 생성된 직원 수도 함께 다루고, 같은 파이프라인으로 나가 같은 대시보드에 놓인다. 장부와 계기판이 한 화면에 있는 셈이다.**

```
자동차:  계기판과 장부는 다른 시스템, 다른 화면
관측:    같은 MeterRegistry → 같은 OTLP → 같은 Prometheus → 같은 Grafana
```

**이것이 실무적 이득이다** — **인프라 이상과 비즈니스 이상을 나란히 놓고 인과를 추정**할 수 있다. "메모리가 오를 때 알림 실패도 올랐다"를 한 화면에서 본다.

**비유가 맞는 부분은 남는다** — **재는 대상이 다르고, 한쪽이 정상이어도 다른 쪽이 망가질 수 있다**(Q1). 깨지는 것은 **계측 경로의 분리**다.

**§6의 나머지 경계**: **`processedEvents`가 무한히 자란다** — **비우지 않으므로 장기 실행 시 메모리 누수**. **중복 판정이 인스턴스 로컬이다** — **컨슈머를 두 대로 늘리면 중복 제거가 깨진다**([[../../part-4-scaling-an-application-with-spring-boot/chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/05b-idempotent-consumers|Ch12]]가 이미 지적한 것).

3. 타임아웃으로 30초 걸린 요청이 평균에서 빠졌다. 어떤 코드였겠는가?
4. `role`이 `null`인 직원이 생성됐다. 태그는 어떻게 되는가?
5. 직원 ID를 태그로 넣었다. 시계열이 몇 개 생기는가?
6. 알림 결과 유형이 다섯 번째로 늘었다. 태그 방식과 메트릭 분리 방식에서 각각 무엇을 고치는가?
7. `employee.create.time`이 40ms인데 알림이 전멸했다. 무엇이 필요한가?
8. 메모리가 오를 때 알림 실패도 올랐다. 이것을 한 화면에서 볼 수 있는 이유는?
