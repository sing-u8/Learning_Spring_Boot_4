## Q1. 흩어진 파일 로그로 조사할 때 막히는 다섯 단계

1. **어느 인스턴스가 그 요청을 받았는지 모른다** → **세 대에 다 접속한다**
2. **각각 `grep`으로 시간대를 찾는다**
3. **로그 형식이 문장이라 `grep`이 부정확하다** (`"failed"`가 다른 맥락에도 등장한다)
4. **Kafka 컨슈머는 또 다른 인스턴스라 거기도 봐야 한다**
5. **찾아낸 줄들이 정말 같은 요청인지 확신할 수 없다**

> **로그를 남기고 있는데도 답이 안 나온다. 문제는 양이 아니라 형태와 위치다.**

**5번이 가장 근본적이다** — 앞의 넷을 다 해도 **증거를 하나의 이야기로 엮을 수 없다.**

## Q2. "형태와 위치"를 푸는 정거장

| 문제 | **필요한 것** | **정거장** |
|---|---|---|
| **흩어져 있다** (위치) | **중앙 수집** | **5 Collector · 6 Loki** |
| **사람이 읽는 문장이다** (형태) | **구조화** | **2 Logback** |
| **같은 요청인지 모른다** | **상관관계 키 — traceId** | **2 Logback**(MDC에서 꺼내 싣는다) |

**일곱 정거장과 "없으면 무엇이 깨지는가"**:
| 정거장 | **없으면** |
|---|---|
| 1 애플리케이션 | 로그가 없다 |
| **2 Logback** | **형식이 자유 문장이라 파싱이 불가능하다** |
| 3 OpenTelemetry | **백엔드마다 다른 형식으로 내보내야 한다** |
| 4 OTLP | 전송 방식을 직접 만들어야 한다 |
| 5 Collector | **애플리케이션이 백엔드 주소를 직접 안다** |
| 6 Loki | **흩어진 채로 남는다** |
| 7 Grafana | **저장돼 있지만 사람이 볼 수 없다** |

**2번이 두 가지 일을 동시에 한다** — **형식을 바꾸고, 맥락을 붙인다.** 그래서 세 문제 중 둘이 여기서 풀린다.

## Q3. 구조화 로깅이 정규식 파싱보다 나은 이유

**필드가 처음부터 나뉘어 있으므로 파싱이 필요 없다.**

```text
기본:  2026-04-20 01:25:08.172  INFO 12345 --- [nio-8080-exec-1] c.l.NotificationService : Received ...
구조화: {"body":"Received ...","severity":"INFO","instrumentation_scope":{"name":"com.springbootlearning4.NotificationService"}}
```

> **사람은 읽기 쉽지만 기계는 이 줄에서 "어느 서비스", "어느 레벨", "어느 클래스"를 안정적으로 뽑아낼 수 없다. 정규식으로 하면 형식이 조금만 바뀌어도 깨진다.**

**얻는 것**: **`severity`로 필터하고 `instrumentation_scope.name`으로 그룹핑할 수 있다.**

**정규식 방식의 취약점**:
- **형식이 바뀌면 조용히 깨진다** — 로그는 계속 쌓이는데 파싱만 실패
- **메시지 안에 구분자가 들어가면** 깨진다
- **파서를 별도로 유지보수**해야 한다

**"구조화 로깅은 로그를 예쁘게 찍는 것이다"는 오해다**(§5) — **사람이 읽기에는 오히려 나쁘다.** **목적은 기계가 파싱할 수 있게 만드는 것**이고, **사람은 Grafana가 다시 정리해 준 화면으로 본다.**

## Q4. traceId가 이 장 전체의 접착제인 이유

**흩어진 로그를 한 요청으로 다시 묶는다.**

| 붙이는 것 | **무엇을 가능하게 하나** |
|---|---|
| **MDC** | **요청 단위 정보를 메서드마다 넘기지 않고도 모든 로그에 싣는다** |
| **traceId** | **흩어진 로그를 한 요청으로 다시 묶는다** |
| **spanId** | **그 요청 안의 어느 단계인지 구분한다** |

> **앞의 조사 시나리오에서 "찾아낸 줄들이 같은 요청인지 확신할 수 없다"던 문제가 이 값 하나로 사라진다**(Q1의 5번).

**그리고 [[06-correlating-logs-metrics-and-traces]]가 그 위에서 동작한다** — **로그에서 트레이스로, 트레이스에서 로그로 오가는 것이 전부 이 ID를 통해서**다.

**[[02-designing-an-observability-architecture]]의 "하나의 관측에서 세 신호가 파생된다"가 여기서 값을 낸다** — traceId를 손으로 넣는 것이 아니라 **관측이 자동으로 심는다.**

**"traceId는 Logback이 만든다"는 오해다**(§5) — **만들지 않는다.** **트레이싱이 켜져 있어야 생기고, Logback은 그것을 MDC에서 꺼내 로그에 실을 뿐이다** → Q5.

---

## Q5. 이 절에서 트레이싱을 꺼 두는 이유

**순서 때문이다 — 트레이싱을 켜야 traceId가 생긴다.**

> **[[03b-instrumenting-the-application-for-logging]]에서는 `management.tracing.enabled: false`로 두고 로그에만 집중하며, traceId는 [[05b-enabling-trace-export-and-kafka-propagation]] 이후에 채워진다.**

**그 결과 지금 로그에 없는 것**: **traceId와 spanId.**

**즉 이 절이 세우는 파이프라인은 아직 "형태와 위치"만 푼다.** Q2의 표에서 **세 번째 문제("같은 요청인지 모른다")는 미해결**로 남는다.

**학습 설계로 읽으면**: **한 번에 하나씩 켠다.** 로그 파이프라인이 도는 것을 확인한 뒤 트레이싱을 얹으면, **문제가 생겼을 때 어느 층인지 안다.**

**§6의 경계**: **로그만으로는 이 장의 목표에 못 미친다.** **"얼마나 자주"와 "어디를 지나갔나"는 답이 없다** → [[04-metrics-with-micrometer-prometheus-and-grafana]], [[05-tracing-with-opentelemetry-and-tempo]].

## Q6. Loki가 라벨만 색인하는 선택

| | **전문 색인 방식** | **Loki** |
|---|---|---|
| 색인 대상 | **로그 본문의 모든 단어** | **라벨만** |
| **저장 비용** | **높다** | **낮다** |
| 라벨 질의 | 빠르다 | 빠르다 |
| **본문 검색** | 빠르다 | **스트림을 좁힌 뒤 스캔** |

**이득: 저장 비용이 낮다.** **대가: 본문 검색이 2단계**가 된다.

> **먼저 라벨로 범위를 좁히고 그 안에서 본문을 훑는다.** `{service_name="employee-service"} |= "employee"`라는 [[03c-verifying-logs-in-grafana]]의 질의가 정확히 그 모양이다.

**이 성질 때문에 어떤 속성을 라벨로 올릴지가 설계 결정이 된다** — [[03a-setting-up-the-logging-infrastructure]]의 `loki.resource.labels`.

**§6의 경고**: **라벨을 남발하면 Loki가 무너진다.** **라벨 조합마다 스트림이 하나씩 생기므로, 고유 값이 많은 속성(요청 ID 같은)을 라벨로 올리면 저장소가 감당하지 못한다.**

**"Loki는 Elasticsearch 같은 것이다"는 오해다**(§5) — **색인 전략이 다르다.**

## Q7. 우편물 비유가 깨지는 지점

**비유**: **편지를 쓰고(1), 규격 봉투에 넣어 주소를 적고(2), 우체국 표준 형식으로 분류하고(3–4), 집배 센터가 모아 분류하고(5), 지역 우체국에 쌓이고(6), 수취인이 찾아본다(7).**

**깨지는 지점**: **같은 편지가 세 종류의 우편함에 동시에 들어간다는 이 장의 구조를 담지 못한다.**

> **실제로는 하나의 관측에서 로그·메트릭·트레이스가 함께 나가 서로 다른 백엔드에 쌓이고, 나중에 같은 번호로 다시 모인다.**

```
우편:  편지 하나 → 한 수취인에게
관측:  Observation 하나 → Loki + Prometheus + Tempo 에 동시에
                          → 같은 traceId 로 다시 이어진다
```

**[[01-three-pillars-of-observability]]와 [[02-designing-an-observability-architecture]]의 비유가 깨진 지점과 같은 사실이다** — **셋이 같은 순간에서 파생된다**는 것을 어느 비유도 담지 못한다.

**비유가 맞는 부분은 남는다** — **정거장마다 형식이 표준화되고, 중앙에 모이고, 수취인이 찾아본다**(Q2). 깨지는 것은 **산출물의 갈래**다.
