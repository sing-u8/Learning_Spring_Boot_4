## Q1. 세 신호를 각각 다른 라이브러리로 만들면

| 문제 | **결과** |
|---|---|
| **세 라이브러리가 서로를 모른다** | **로그에 traceId가 안 들어간다 → 상관관계 불가** |
| **같은 일을 세 번 선언한다** | **하나를 빠뜨리면 그 신호만 조용히 사라진다** |
| **각각 다른 백엔드 SDK에 묶인다** | **저장소를 바꾸면 애플리케이션 코드를 고쳐야 한다** |

```java
log.info("employee created");                        // 로깅 라이브러리
meterRegistry.counter("employee.created").increment(); // 메트릭 라이브러리
tracer.spanBuilder("create").startSpan();            // 트레이싱 라이브러리
```

**첫 번째가 [[01-three-pillars-of-observability]]의 조사 흐름을 통째로 무너뜨린다** — **"메트릭 → 트레이스 → 로그"는 셋이 같은 요청에서 나왔음을 알 수 있어야 성립**한다.

**두 번째는 조용히 실패한다** — 컴파일도 되고 테스트도 통과한다. **장애가 나서 조사할 때야 그 신호가 없다는 것을 안다.**

> **Spring Boot 4의 답은 선언을 하나로 합치는 것이다.**

## Q2. "하나의 관측에서 세 신호가 파생된다"

> **작업 단위 하나를 한 번 선언하면, 거기서 세 신호가 파생된다.**

```
작업 단위 (HTTP 요청 · DB 호출 · 메시지 처리)
        ↓
   Observation  ← 한 번 선언
        ├─▶ 메트릭 (얼마나 걸렸나 · 몇 번인가)
        ├─▶ 트레이스 (span 하나)
        └─▶ 로그 상관관계 데이터 (traceId · spanId)
```

**Q1의 세 문제가 각각 풀린다**:
| 문제 | **해결** |
|---|---|
| 신호들이 서로를 모른다 | **같은 관측에서 나오므로 traceId가 자동으로 로그에 실린다** |
| 세 번 선언한다 | **한 번만 선언한다. 빠뜨릴 여지가 없다** |
| 백엔드 SDK에 묶인다 | **관측은 추상이고, 실제 형식 변환은 아래 계층이 맡는다** |

**Micrometer**: **특정 모니터링 시스템에 묶이지 않고 계측할 수 있게 해 주는 Spring 생태계의 파사드.**
**Observation API**: **"작업 단위 하나"를 나타내는 추상.**

**"Micrometer는 메트릭 전용이다"는 오해다**(§5) — **이름은 그렇지만 Observation API를 통해 트레이스와 로그 상관관계까지 파생시킨다. 그것이 Spring Boot 4 관측 모델의 핵심이다.**

**[[05b-enabling-trace-export-and-kafka-propagation]]에서 `Observation.createNotStarted("employee.create", ...)`를 쓰는 것이 이 API를 직접 부르는 모습이다.**

## Q3. 표준화 단계(OpenTelemetry)가 없으면

**벤더 중립성을 잃는다 — 백엔드를 바꿀 때 애플리케이션을 고쳐야 한다.**

> **애플리케이션이 Prometheus의 형식으로 직접 내보내면 나중에 다른 시계열 DB로 바꿀 때 애플리케이션을 고쳐야 한다. 표준 형식으로 내보내면 바꿀 곳이 파이프라인 설정뿐이다.**

**OpenTelemetry**: **텔레메트리의 데이터 모델·의미 규약·API를 정의하는 벤더 중립 표준.**

**전송은 OTLP로 나간다** — **gRPC(4317)와 HTTP(4318)** 두 방식이 있고, **이 장의 예제는 HTTP를 쓴다.**

**"OpenTelemetry가 Micrometer를 대체한다"는 오해다**(§5) — **층이 다르다.** **Micrometer는 애플리케이션이 선언하는 층, OpenTelemetry는 표준 형식과 전송 층**이다. **둘이 겹쳐 동작한다.**

**§6의 대가**: **표준화에는 손실이 있을 수 있다.** **벤더 고유 기능(특정 백엔드만의 집계 방식 등)은 벤더 중립 형식으로 표현되지 않는다.**

## Q4. Collector가 선택 사항인데도 권장되는 이유

| **Collector가 하는 일** | **없으면** |
|---|---|
| **배칭** | **애플리케이션이 매 신호마다 네트워크 왕복을 한다** |
| **필터링** | **불필요한 데이터까지 저장 비용을 낸다** |
| **강화** | **서비스 이름·환경 같은 공통 메타데이터를 애플리케이션마다 설정해야 한다** |
| **라우팅** | **백엔드가 바뀌면 모든 애플리케이션의 설정을 고쳐야 한다** |

> **마지막 줄이 결정적이다. Collector가 있으면 애플리케이션은 "Collector로 보낸다"만 알면 되고, 그 뒤가 Loki든 Elasticsearch든 상관하지 않는다. 결합을 한 지점으로 모은 것이다.**

**OpenTelemetry Collector**: **애플리케이션과 백엔드 사이에서 텔레메트리를 받고 가공해 내보내는 독립 프로세스.**

**"Collector가 없으면 관측이 안 된다"는 오해다**(§5) — **된다.** **애플리케이션이 백엔드로 직접 보낼 수 있다.** **Collector는 운영에서의 유연성을 위한 선택**이다.

**§6의 대가**: **Collector는 운영 부담을 만든다.** **프로세스 하나가 더 늘고, 그것이 죽으면 텔레메트리가 통째로 끊긴다.** **단일 서비스 규모에서는 직접 전송이 단순하다.**

**책의 표현대로 신호와 백엔드가 여러 개일 때 이 유연성이 특히 커진다.**

## Q5. 백엔드를 Loki에서 다른 것으로 바꿀 때

**Collector 설정만 고친다.**

```
애플리케이션:  "Collector 로 보낸다"          ← 안 바뀐다
Collector:     exporter 를 Loki → 다른 것으로  ← 여기만
```

**Q3과 Q4가 각각 절반씩 기여한다**:
- **OpenTelemetry 표준 형식**이라 **애플리케이션이 특정 백엔드 형식을 모른다**
- **Collector**가 **라우팅을 한 지점에 모은다**

**둘 중 하나만 있으면**:
- 표준만 있고 Collector가 없으면 → **모든 애플리케이션의 exporter 설정**을 고쳐야 한다
- Collector만 있고 표준이 없으면 → **애플리케이션이 이미 특정 형식으로 만들었으므로** 변환이 어렵다

**즉 "바꿀 곳이 한 군데"는 두 설계의 곱**이다.

## Q6. Grafana가 별도 컴포넌트로 있어야 하는 이유

**저장소 셋은 각자 자기 신호만 알기 때문이다.**

| 컴포넌트 | 맡는 신호 | 하는 일 |
|---|---|---|
| **Prometheus** | 메트릭 | **시계열 저장, PromQL 질의** |
| **Loki** | 로그 | **로그 저장·색인, LogQL 질의** |
| **Tempo** | 트레이스 | **트레이스 저장, ID 조회** |
| **Grafana** | — | **셋을 하나의 인터페이스로 묶는다** |

> **셋을 오갈 수 있게 만드는 층이 따로 필요하고, 그것이 [[06-correlating-logs-metrics-and-traces]]의 주제다.**

**[[01-three-pillars-of-observability]]의 조사 흐름(메트릭 → 트레이스 → 로그)이 실제로 클릭 몇 번이 되려면** — **한 화면에서 셋을 오갈 수 있어야** 한다. 저장소를 따로 열어 ID를 복사해 붙이는 것은 **조사 흐름이 아니라 노동**이다.

**"Grafana가 데이터를 저장한다"는 오해다**(§5) — **저장하지 않는다.** **Loki·Prometheus·Tempo에 질의를 던지고 결과를 그린다.**

**그래서 Grafana를 잃어도 데이터는 남는다** — 조회 층과 저장 층이 분리돼 있다.

## Q7. 통신사 비유가 깨지는 지점

**비유**: **기자(Observation)가 한 번 취재하면 통신사(Collector)가 표준 형식으로 배포하고 각 신문(백엔드)이 자기 지면에 싣는다.**

**깨지는 지점**: **한 취재에서 성격이 다른 세 기사가 나온다는 점을 담지 못한다.**

> **여기서는 관측 하나가 숫자(메트릭)·경로(트레이스)·사건(로그)이라는 서로 다른 종류의 산출물로 동시에 갈라지고, 그 셋이 같은 ID를 공유하기 때문에 나중에 다시 이어 붙일 수 있다.**

```
통신사:  기사 하나 → 여러 신문이 같은 기사를 싣는다        (같은 내용, 다른 매체)
관측:    Observation 하나 → 세 가지 다른 종류의 산출물     (다른 내용, 같은 ID)
```

**"같은 ID를 공유한다"가 이 구조의 핵심 산물이다** — [[01-three-pillars-of-observability]]의 비유가 깨진 지점("셋이 같은 순간에서 파생된다")과 **같은 사실의 다른 표현**이다.

**비유가 맞는 부분은 남는다** — **한 번 만들어 여러 곳으로 배포하고, 중간 계층이 형식을 표준화한다**(Q3·Q4). 깨지는 것은 **산출물의 동질성**이다.
