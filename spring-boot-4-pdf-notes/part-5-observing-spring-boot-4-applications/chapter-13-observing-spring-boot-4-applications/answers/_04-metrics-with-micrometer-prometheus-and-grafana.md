## Q1. 로그로 답할 수 없는 질문 다섯

| 질문 | **로그로 답할 수 있나** |
|---|---|
| 이 요청이 얼마나 걸렸나 | 시작·끝 로그의 시각 차로 **추정**은 된다 |
| **그게 평소보다 느린가** | **불가능 — 비교 대상이 없다** |
| 오늘 몇 건이 생성됐나 | 로그를 세면 되지만 **비싸다** |
| 알림 실패율이 오르고 있나 | **실패 로그를 세고 성공 로그를 세고 나눠야** 한다 |
| **지난주 대비 어떤가** | **사실상 불가능** |

> **문제는 로그가 개별 사건의 기록이라는 데 있다. 집계를 하려면 매번 사건 전부를 훑어야 한다. 사건이 하루 백만 건이면 "실패율"을 구하는 일이 백만 줄 스캔이 된다.**

**메트릭은 반대 방향이다** — **집계된 상태로 저장한다. 개별 사건은 버리고 "5초 동안 12건, 평균 43ms"만 남긴다.**

> **로그는 무슨 일이 있었는지 말하고, 메트릭은 얼마나 자주 일어났는지, 얼마나 걸렸는지, 시간에 따라 정상적으로 동작하는지를 말한다.**

## Q2. "집계된 상태로 저장한다"가 만드는 질의 비용 차이

```
로그로 실패율 구하기:  하루 100만 줄 스캔 → 성공/실패 세기 → 나누기
메트릭으로:            이미 세어진 카운터 두 개를 읽어 나누기
```

**"로그를 집계하면 메트릭이다"는 계산상 가능하지만 비용이 다르다**(§5) — **메트릭은 애초에 집계된 상태로 저장되므로 질의가 싸다.**

**차이의 크기가 규모에 비례한다** — 사건이 열 배 늘면 **로그 집계 비용은 열 배**지만 **메트릭 질의 비용은 그대로**다(저장되는 것은 여전히 5초마다 숫자 몇 개).

**대가**: **개별 사건이 버려진다.** **"어느 요청이 실패했는가"는 메트릭이 답하지 못한다.**

**"메트릭이 로그보다 낫다"는 오해다**(§5) — **답하는 질문이 다르다.** **메트릭은 "무엇이 잘못됐나"를 알려 주지만 "왜"는 로그에만 있다.** [[01-three-pillars-of-observability]]의 조사 순서가 그 관계다.

## Q3. 일곱 정거장에서 다른 칸

| 정거장 | 로그 | **메트릭** |
|---|---|---|
| 1 | 애플리케이션 | 애플리케이션 |
| **2** | **Logback** | **Micrometer** |
| 3 | OpenTelemetry (Logs) | OpenTelemetry (Metrics) |
| 4 | OTLP | OTLP |
| 5 | Collector | Collector |
| **6** | **Loki** | **Prometheus** |
| 7 | Grafana | Grafana |

**딱 두 칸만 다르다 — 2번(생산자)과 6번(저장소).**

> **파이프라인의 뼈대는 신호가 바뀌어도 그대로이고, 양 끝(생산자와 저장소)만 갈아 끼운다.**

**왜 좋은 설계인가**:
- **[[04a-setting-up-prometheus-for-metrics]]가 [[03a-setting-up-the-logging-infrastructure]]와 같은 세 파일에 항목을 더하는 작업**이 된다 — 새로 배울 것이 적다
- **3~5번(표준화·전송·가공)을 재사용**하므로 **한 번 만든 인프라가 신호마다 반복되지 않는다**
- **트레이스를 얹을 때도 같은 구조**([[05a-setting-up-grafana-tempo]])

**이 반복이 [[02-designing-an-observability-architecture]]가 말한 통합 모델의 실질적 이득이다.**

## Q4. Micrometer의 "수집"과 "내보낼 준비"의 차이

| 하는 일 | 뜻 |
|---|---|
| 계측한다 | **애플리케이션 코드에 측정 지점을 만든다** |
| 관측을 만든다 | [[02-designing-an-observability-architecture]]의 Observation |
| **메트릭을 수집한다** | **카운터·타이머 값을 메모리에 누적한다** |
| **내보낼 준비를 한다** | **주기적으로 스냅숏을 떠서 넘긴다** |

> **메트릭은 사건마다 나가지 않는다. 메모리에 쌓였다가 정해진 주기로 한 번에 나간다.**

**[[04a-setting-up-prometheus-for-metrics]]의 `step: 5s`가 그 주기다.**

**로그와의 근본적 차이가 여기 있다** — **로그는 사건 하나가 레코드 하나이지만, 메트릭은 수많은 사건이 숫자 몇 개로 접힌다.**

**"메트릭도 사건마다 전송된다"는 오해다**(§5) — **주기적으로 스냅숏을 떠서 보낸다.** 그래서 **매우 짧은 스파이크는 놓칠 수 있다** → Q6.

## Q5. 메트릭을 Loki에 넣으면 안 되는 이유

**시계열 데이터베이스가 필요하기 때문이다** — **"시각 → 수치" 쌍을 저장하고 구간 질의·집계에 최적화된 저장소.**

| | **로그 저장소(Loki)** | **시계열 DB(Prometheus)** |
|---|---|---|
| 저장 단위 | **텍스트 줄 + 라벨** | **(시각, 숫자) 쌍 + 라벨** |
| 최적화 대상 | **스트림 선택 후 스캔** | **구간 집계·비율 계산** |
| 대표 질의 | "이 서비스의 ERROR 로그" | **"지난 1분간 초당 몇 건"** |
| **데이터 압축** | 텍스트 압축 | **숫자 특화 압축(델타·XOR)** |

> **마지막 줄이 실질적이다. 5초마다 값 하나씩 한 달을 쌓으면 51만 8천 개인데, 시계열 DB는 연속한 숫자의 차이만 저장하는 식으로 이것을 극도로 줄인다. 텍스트 저장소로는 불가능한 압축이다.**

**즉 "저장할 수 있느냐"가 아니라 "그 규모를 감당할 수 있느냐"의 문제**다.

**"시계열 DB는 그냥 숫자용 DB다"는 오해다**(§5) — **시간축 특화 압축과 구간 집계가 핵심**이다.

**책의 표현**: **"Loki는 로그를 맡지만 메트릭에는 시간에 따른 수치를 저장할 수 있는 시계열 데이터베이스가 필요하다."**

## Q6. 5초 주기 전송이 놓치는 것

**그보다 짧은 스파이크다.**

> **주기 사이의 급변은 사라진다. 5초 주기라면 그보다 짧은 스파이크는 평균에 묻힌다.**

```
실제:  0~1초 정상 → 1.2초에 100건 급증 → 1.4초에 정상
5초 스냅숏:  "5초 동안 총 120건" 하나로 접힌다
             → 언제 몰렸는지, 얼마나 뾰족했는지 안 보인다
```

**Q4의 "수많은 사건이 숫자 몇 개로 접힌다"의 대가**다.

**주기를 줄이면?** 해상도가 올라가지만 **저장량과 부하가 는다** — [[04a-setting-up-prometheus-for-metrics]]가 `5s`를 **로컬 예제용**이라고 밝히고, 운영에서는 보통 **15–60초**를 쓴다.

**놓친 것을 다른 신호로 메운다** — **어느 요청이 느렸는지**는 [[05-tracing-with-opentelemetry-and-tempo]]의 트레이스가, **그때 무슨 일이 있었는지**는 로그가 답한다.

**§6의 다른 경계도 함께**: **메트릭은 개별 요청을 되짚지 못한다** — **"p99가 나빠졌다"까지가 한계**다. 그리고 **태그가 많아지면 비용이 폭발한다** → [[04b-adding-custom-business-metrics-with-micrometer]]의 카디널리티.

## Q7. 일지와 계기판 비유가 깨지는 지점

**비유**: **일지는 사건을 적고 계기판은 현재 수치를 보여 준다.**

**깨지는 지점**: **계기판이 일지에서 만들어지지 않는다는 점을 흐린다.**

> **자동차 계기판은 센서를 직접 읽지만, 여기서는 계기판과 일지가 같은 관측에서 동시에 파생된다. 그래서 계기판의 눈금 하나에서 그 순간의 일지로 곧장 넘어갈 수 있고, 그것이 [[06-correlating-logs-metrics-and-traces]]의 주제다.**

```
자동차:  계기판(센서) 과 일지(운전자 기록) 는 별개 출처
관측:    하나의 Observation → 메트릭과 로그가 동시에, 같은 traceId 를 갖고
```

**이 장의 다른 비유들이 깨진 지점과 같은 사실이다** — [[01-three-pillars-of-observability]]의 의료 검사, [[02-designing-an-observability-architecture]]의 통신사, [[03-structured-logging-with-loki-and-grafana]]의 우편물. **어느 비유도 "같은 순간에서 셋이 파생된다"를 담지 못한다.**

**비유가 맞는 부분은 남는다** — **성격이 다른 두 정보이고, 각각 다른 질문에 답한다**(Q1). 깨지는 것은 **출처의 공유**다.

**책의 요약이 파이프라인 전체를 담는다**:
> **애플리케이션이 Micrometer를 통해 메트릭을 기록하고, OpenTelemetry가 표준화해 OTLP로 내보내고, Collector가 처리하고, Prometheus가 저장하고, Grafana가 시각화한다.**

**각 컴포넌트가 정확히 하나의 책임만 갖는다** — 그래서 **어느 하나를 바꿔도 나머지가 영향을 받지 않는다.**
