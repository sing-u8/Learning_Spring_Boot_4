## Q1. 모니터링이 답하지 못하는 질문

**`POST /employees`가 느려졌다. 어디서 느려졌는가?**

**모니터링이 주는 것**: `CPU 42% / 메모리 3.1GB / 가동시간 14일 / 요청/초 120`

**그런데 다섯 후보 중 어느 것도 이 화면으로는 구분되지 않는다**:
| 후보 | 겉으로 보이는 증상 |
|---|---|
| 느린 DB 쿼리 | HTTP 응답 지연 |
| 다운스트림 서비스 다운 | HTTP 응답 지연 |
| **Kafka 컨슈머 정체** | **아무 증상 없음** (요청은 이미 끝났다) |
| 다른 컴포넌트의 설정 문제 | 엉뚱한 곳에서 오류 |
| 재시도 폭주 | CPU 상승 |

> **눈에 보이는 증상은 종종 진짜 원인에서 멀리 떨어진 곳에 나타난다.**

**구조적 이유**: **모니터링은 "무엇을 볼지 미리 알고 있다"를 전제한다.** **CPU 그래프를 그리려면 CPU를 재기로 미리 정했어야 한다.** 그런데 **문제는 예측 가능하지 않다.**

**관측 가능성이 바꾸는 것은 데이터 양이 아니라 질문할 수 있는 범위다**:
| | **모니터링** | **관측 가능성** |
|---|---|---|
| 질문 시점 | **미리 정한다** | **실행 중에 떠오른 것을 묻는다** |
| 답할 수 있는 것 | 예상한 실패 | **예상 못 한 실패** |
| 대표 질문 | **"떠 있는가?"** | **"왜 느린가? 어디서 실패하나? 무엇이 바뀌었나?"** |

> **"추측에서 이해로(from guessing to understanding)."**

## Q2. "외부 출력"이 뜻하는 것

**관측 가능성 = 외부 출력만 보고 내부 상태를 이해할 수 있는 능력.**

**"외부 출력"은 시스템이 스스로 내보내는 텔레메트리**다 — **로그·메트릭·트레이스.**

**뜻하는 것**: **프로세스에 붙어 들어가 보지 않고**, **재현하지 않고**, **디버거를 걸지 않고** 내부를 이해할 수 있어야 한다.

```
불가능한 것:  운영 중인 프로세스에 디버거를 붙인다
가능해야 하는 것: 이미 나간 출력만으로 무슨 일이 있었는지 재구성한다
```

**왜 이 제약이 정의에 들어가나**: **운영 장애는 대개 재현되지 않는다.** 그 순간 나온 출력이 **유일한 증거**다.

**그래서 "무엇을 출력할 것인가"가 설계 문제가 된다** — 나중에 물을 질문을 미리 다 알 수 없으므로 **충분히 풍부하되 상관 가능한** 출력이 필요하다.

**"로그를 많이 남기면 관측 가능성이 생긴다"는 오해다**(§5) — **양이 아니라 상관 가능성이 관건이다.** **로그가 아무리 많아도 traceId가 없으면 요청 하나의 흐름을 재구성할 수 없다.**

## Q3. 50밀리초 요청에 대해 세 신호가 말하는 것

| 신호 | **말해 주는 것** | **말해 주지 못하는 것** |
|---|---|---|
| **로그** | **요청이 시작됐고 끝났다** | **50ms가 정상인지** |
| **메트릭** | **응답 시간 50ms, 다른 요청들과 비교해 정상인지 이상인지** | **그 50ms가 어디서 쓰였는지** |
| **트레이스** | **컨트롤러 5ms · 서비스 8ms · DB 30ms · 외부 호출 7ms** | **왜 DB가 30ms였는지의 세부** |

**각 신호의 성격**:
- **로그** = **사건의 기록.** **특정 시점의 구체적 세부를 보존** — **예외의 스택 트레이스나 실패한 이메일 주소 같은 것은 로그에만 있다**
- **메트릭** = **시간에 따라 수집되는 수치.** **개별 사건이 아니라 집계된 추세**
- **트레이스** = **요청 하나가 지나간 경로.** **인과 순서로** 잇고 **어느 구간에서 시간이 쓰였는지** 보여 준다

> **혼자서는 어느 것도 조사를 끝내지 못한다.**

**"트레이스가 있으면 로그는 필요 없다"는 오해다**(§5) — **트레이스는 "어느 구간이 느렸나"까지**이고 **왜 느렸는지의 세부는 로그에만** 있다.

---

## Q4. "메트릭 → 트레이스 → 로그" 순서

**각 신호가 다음 신호의 질문을 만든다.**

```
1. 메트릭:  "p99 가 어제보다 3배"        → 어느 요청이?
2. 트레이스: "그 요청의 78%가 알림 처리"  → 알림 처리에서 무슨 일이?
3. 로그:    "재시도 3회 후 타임아웃"
```

**왜 이 순서인가**: **범위가 점점 좁아진다.**
- **메트릭은 전체를 본다** — 이상이 있는지 없는지만 안다
- **트레이스는 요청 하나를 본다** — 어느 구간인지 좁힌다
- **로그는 그 구간의 사건을 본다** — 무슨 일인지 밝힌다

**역순은 성립하지 않는다** — 로그부터 보면 **어느 로그를 봐야 할지** 모른다. 하루에 수백만 줄이 쌓이는데 **탐색의 시작점이 없다.**

> **셋을 하나의 상관된 텔레메트리 스트림에서 파생시켜 통합적으로 분석해야 한다.**

**그 "하나에서 파생"이 [[02-designing-an-observability-architecture]]의 주제이고, "오갈 수 있게 만드는 것"이 [[06-correlating-logs-metrics-and-traces]]의 주제다.**

## Q5. 비동기 구간의 실패가 응답 시간 메트릭에 안 나타나는 이유

**요청이 이미 끝났기 때문이다.**

```
HTTP 요청 → 컨트롤러 → 서비스 → DB 저장
                              → Kafka 이벤트 발행
                              → 응답 반환        ← 여기서 응답 시간 측정이 끝난다
                                  ┊
                                  └─(비동기) 컨슈머 → 알림 발송 → 실패 → DLT
                                     ↑ 이 구간은 응답 시간에 안 들어간다
```

**[[../../part-4-scaling-an-application-with-spring-boot/chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/01-asynchronous-and-event-driven-communication|Ch12]]의 설계가 의도한 결과이기도 하다** — **notification service의 실패가 클라이언트 요청에 영향을 주지 않는다.** 그 격리가 **관측에서는 사각지대**가 된다.

**"메트릭이 정상이면 문제가 없다"는 오해다**(§5) — **평균은 개별 실패를 숨긴다.** 그리고 **비동기 구간의 실패는 HTTP 응답 시간에 전혀 나타나지 않는다.**

**그래서 필요한 것**: **컨슈머 쪽의 별도 메트릭**(처리 건수, 실패 건수, 랙)과 **[[../../part-4-scaling-an-application-with-spring-boot/chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/05a-dead-letter-topics|Ch12의 DLT]] 감시**. [[04b-adding-custom-business-metrics-with-micrometer]]가 그 자리를 다룬다.

**[[../../part-4-scaling-an-application-with-spring-boot/chapter-12-messaging-and-asynchronous-communication-in-spring-boot-4/01a-core-components-of-event-driven-systems|Ch12]]가 "관측 체계가 없다면 이벤트 주도로 가지 않는다"고 한 이유가 이것이다.**

## Q6. 프로파일링이 트레이스보다 좁혀 주는 것

| | **세 기둥** | **프로파일링** |
|---|---|---|
| **해상도** | **요청·연산 단위** | **코드 라인·메서드 단위** |
| **답하는 것** | **어느 구간이 느린가** | **그 구간의 어느 코드가 시간을 쓰는가** |
| **필요한 것** | 라이브러리·설정 | **전용 백엔드 + 프로파일러 에이전트** |

> **트레이스가 "알림 처리 span이 2.18초"까지 좁혀 주면, 프로파일링은 그 안에서 어떤 메서드가 CPU를 태웠는지 말해 준다.**

**책이 다루지 않는 이유**: **순전히 비용** — **별도 백엔드와 에이전트가 필요해 선택적 확장으로 남긴다.** **Grafana Pyroscope와 OpenTelemetry profiling 스펙**을 참고 링크로 준다.

**즉 Q4의 사슬이 한 칸 더 이어진다**: 메트릭 → 트레이스 → 로그 → **프로파일링**. 각 단계가 **해상도를 한 단계씩** 높인다.

**지속적 프로파일링**: **실행 중 성능 데이터를 계속 수집·분석해 코드 수준 병목을 찾는 방법.**

## Q7. 의료 검사 비유가 깨지는 지점

**비유**: **로그는 진료 기록, 메트릭은 체온·혈압 같은 활력징후, 트레이스는 조영술로 본 혈류.**

**깨지는 지점**: **셋이 같은 순간에서 파생된다는 점을 담지 못한다.**

> **병원에서는 검사를 따로 받지만, 여기서는 하나의 관측이 세 신호를 동시에 만들어 낸다. 그래서 서로를 가리키는 링크가 자동으로 성립하고, [[06-correlating-logs-metrics-and-traces]]가 가능해진다.**

```
병원:  체온 측정 / 혈액 검사 / 조영술 → 각각 따로 받는다 → 같은 환자라는 것만 공유
관측:  Observation 하나 → 메트릭·트레이스·로그가 동시에 → 같은 traceId 를 공유
```

**이 차이가 [[02-designing-an-observability-architecture]]의 설계 이유 전체다** — **따로 만들면 이어 붙일 수 없다.**

**비유가 맞는 부분은 남는다** — **셋이 각각 다른 질문에 답하고, 하나만으로는 진단이 안 된다**(Q3). 깨지는 것은 **생성 방식**이다.

**§6의 경계도 함께**: **세 신호 모두 비용이 있다** — **로그는 저장 비용, 메트릭은 카디널리티 폭발, 트레이스는 데이터 양.** 그래서 [[05b-enabling-trace-export-and-kafka-propagation]]에서 **샘플링**을 다룬다. 그리고 **관측 가능성이 설계를 대신하지 않는다** — **무슨 일이 일어났는지 보여 줄 뿐이고, 그 일이 일어나지 않게 하는 것은 별개다.**

2. 운영 장애가 재현되지 않는다. 관측 가능성의 정의가 그것을 어떻게 전제하는가?
3. 트레이스만 보고 "DB가 30ms"를 알았다. 그다음 질문은?
4. 로그부터 조사를 시작하면 무엇이 문제인가?
5. Kafka 컨슈머가 밀리고 있다. HTTP 응답 시간 그래프에 나타나는가?
6. 트레이스로 span 하나를 좁혔는데 원인을 모르겠다. 다음 도구는?
7. "셋을 따로 수집한다"가 왜 문제인가?
