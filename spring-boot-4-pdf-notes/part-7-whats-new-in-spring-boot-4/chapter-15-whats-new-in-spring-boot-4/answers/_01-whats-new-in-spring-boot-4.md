## Q1. 네 가지 변경 성격과 가장 위험한 것

| 성격 | 예 | 언제 드러나나 | 대응 |
|---|---|---|---|
| **이름이 바뀜** | `starter-web`→`starter-webmvc`, `@MockBean`→`@MockitoBean`, Jackson 패키지 | **빌드 시점** | 기계적 치환 |
| **기능이 제거됨** | Undertow, Spock 통합, 실행 스크립트, Session Hazelcast/MongoDB | 빌드 또는 시작 시점 | 대체재로 이전 |
| **기본값이 바뀜** | `@SpringBootTest`의 웹 테스트 자동 구성, Batch 인메모리, DevTools LiveReload, health probes | **런타임에 조용히** | 명시적으로 켠다 |
| **새 기능이 생김** | `BeanRegistrar`, `JmsClient`, OTel 스타터, AOT Cache | 안 써도 무방 | 필요할 때 도입 |

**가장 위험한 것은 세 번째 — "기본값이 바뀜"이다.**

> **컴파일도 되고 시작도 되는데 동작만 다르다.**

**왜 그것이 위험의 기준인가 — 오류 메시지의 유무가 아니라 "발견 시점"이 기준이다.**

- 1번은 **컴파일러가 대신 찾아 준다.** 빌드가 안 되면 아직 배포되지 않았다.
- 2번도 의존성 해석 실패나 빈 없음 오류로 **시작 시점까지는** 잡힌다.
- 3번은 **어느 단계에서도 아무 오류를 내지 않는다.** 파이프라인이 초록불이고 테스트가 통과한다. 그런데 **운영에서만 다르게 돈다.**

**그래서 §1의 출발 장면이 "컴파일 오류 다섯 개는 그나마 낫다"로 시작한다** — 진짜 문제는 그것들을 고쳐 빌드가 통과한 **뒤에** 나타난다:

- `@SpringBootTest` 통합 테스트에서 `MockMvc`가 주입되지 않는다
- 배치가 돌긴 하는데 **재시작하면 이전 실행 이력이 없다**
- 브라우저 자동 새로고침이 안 된다
- Elasticsearch 커스터마이저가 호출되지 않는다

**4번이 목록에 있는 이유**: 대응이 필요 없다는 것을 **명시적으로 분류해 두기 위해서**다. 34개를 한 덩어리로 보면 신규 기능까지 마이그레이션 작업 목록에 들어가 버린다.

## Q2. 배선 공사 비유가 깨지는 지점과 그 빈자리

**비유가 맞는 곳** — Boot 3 → 4는 집 전체 배선 교체다:

| 배선 공사 | Boot 4 |
|---|---|
| 스위치 위치가 바뀐다 | 이름 변경 |
| 안 쓰는 회선을 철거한다 | 기능 제거 |
| 어떤 콘센트는 기본이 꺼진 채 나온다 | 기본값 변경 |
| 새 규격 단자가 생긴다 | 신규 기능 |

**깨지는 지점**:

> **배선 공사는 끝나면 눈으로 확인할 수 있다. 스위치를 눌러 보면 된다.**

**Boot 4의 변경 상당수는 눌러 볼 스위치가 없다** — 위 표 세 번째 줄, **살아 보고 나서야 아는** 것들이다.

- **배치를 재시작해 봐야** 메타데이터가 없다는 걸 안다
- **통합 테스트를 돌려 봐야** `MockMvc`가 없다는 걸 안다

**벽을 뜯어 확인할 방법이 없다는 점에서 비유가 멈춘다.**

**빈자리를 메우는 것 — `spring-boot-properties-migrator`(§2.10)다.**

> **벽을 뜯어 보는 대신 배선도를 받아 보는 것.**

마이그레이터는 사용 중단·개명된 프로퍼티를 **시작할 때 보고**해 준다. 즉 **"운영 중에야 아는 것"을 "시작 시점에 아는 것"으로 끌어올린다.** 비유가 깨진 자리를 **도구로** 메운 것이지, 비유를 고쳐서 메운 것이 아니다.

**단, 마이그레이터도 전부를 메우지는 못한다** — 프로퍼티 이름 변경(이 장에서만 21개)은 잡지만, Batch 인메모리 기본값처럼 **프로퍼티가 아닌 기본값 변경**은 잡지 못한다.

## Q3. Undertow 제거가 Spring 팀의 선택이 아닌 근거

**근거는 인과의 순서다.**

1. Boot 4는 **Jakarta EE 11에 정렬**한다(§2.0)
2. 그래서 **서블릿 명세 기준선이 6.1로 올라간다**
3. **Undertow가 현재 Servlet 6.1을 지원하지 않는다**
4. → Boot 4는 Undertow 지원을 제거한다 — 스타터도, 내장 컨테이너로 쓰는 것도

> **이 제거는 Spring 팀의 선택이 아니라 기준선 상승의 결과다.**

**"선택이 아니다"를 어떻게 확인하는가** — **반사실 검사**를 해 보면 된다. Spring 팀이 Undertow를 남기고 싶었다면, Servlet 6.1 기준선을 포기하거나 Undertow가 지원할 때까지 기다려야 한다. **둘 다 Undertow 하나 때문에 Jakarta EE 11 정렬 전체를 미루는 것**이다.

**대응**: Servlet 6.1을 만족하는 컨테이너(**Tomcat 또는 Jetty**)로 옮긴다. Tomcat을 명시적으로 제외하고 Undertow로 바꿔 뒀다면 그 제외를 지우고 기본 Tomcat으로 돌아가거나 Jetty 스타터를 더한다.

**이 패턴이 §3의 첫 그림이 말하는 것이다** — 이름 변경·제거의 상당수가 `Spring Framework 7 · Jakarta EE 11 · Java 17` 토대에서 뻗어 나온 화살표다. **Spring 팀이 이름을 바꾸고 싶어서가 아니라 토대가 움직였기 때문이다.**

## Q4. `jackson-annotations`만 그룹 ID가 그대로인 것이 만드는 혼란

**Jackson 3의 이동 규칙에 예외가 하나 있다.**

| 무엇이 | 이전 | Boot 4 |
|---|---|---|
| Maven 그룹·패키지 | `com.fasterxml.jackson` | **`tools.jackson`** |
| **단 `jackson-annotations`는** | — | **그대로 `com.fasterxml.jackson.core` / `...jackson.annotation`** |

**실무에서 만드는 혼란**:

1. **"전부 치환"이 틀린 전략이 된다.** `com.fasterxml.jackson` → `tools.jackson` 일괄 치환을 돌리면 **애노테이션 import까지 같이 바꿔** 컴파일이 깨진다. 그리고 이때의 오류 메시지(`package tools.jackson.annotation does not exist`)는 **"덜 바꿨다"처럼 보여서** 더 바꾸는 방향으로 사람을 몰고 간다.
2. **거꾸로도 틀린다.** 애노테이션이 그대로라는 걸 확인하고 "Jackson은 안 바뀌었네"라고 판단하면 `databind`·`core` 쪽이 다 깨진다.
3. **한 파일 안에 두 그룹의 import가 공존한다.** 코드 리뷰에서 "이거 마이그레이션 덜 된 거 아냐?"가 반복해서 나온다.

**같이 바뀌는 것들도 함께 기억해야 한다**:

| 관련 | 이전 | Boot 4 |
|---|---|---|
| 애노테이션 | `@JsonComponent`, `@JsonMixin` | `@JacksonComponent`, `@JacksonMixin` |
| 지원 클래스 | `Json…` | `Jackson…` |
| JSON 전용 프로퍼티 | `spring.jackson.read.*` | `spring.jackson.json.read.*` |
| 커스터마이저 | `Jackson2ObjectMapperBuilderCustomizer` | `JsonMapperBuilderCustomizer` |

**완충 장치**: `spring.jackson.use-jackson2-defaults`로 Jackson 3을 **Boot 3.x의 Jackson 2 기본값에 가깝게** 맞출 수 있고, 사용 중단된 Jackson 2 지원도 함께 들어 있다.

**책이 짚는 경계** — 대부분은 Boot의 의존성 관리가 알아서 처리한다. **직접 Jackson을 선언하거나, 커스텀 serializer/deserializer·mixin을 쓰거나, `ObjectMapper`를 커스터마이즈하거나, 특정 Jackson 2 기본값에 의존하는** 애플리케이션만 검토 대상이다.

## Q5. 집중형 스타터가 전이 의존성 문제의 답인 이유

**문제부터**: ****전이 의존성**** — 내가 선언하지 않았는데 딸려 오는 라이브러리.

**Boot 3까지의 규칙**:

> **어떤 라이브러리가 클래스패스에 있다는 이유만으로 기능이 켜졌다.**

**여기서 두 사실이 겹치면 문제가 된다** — (a) 자동 구성의 입력은 **클래스패스**이고, (b) 클래스패스에는 **내가 선언하지 않은 것도 들어온다.** 그래서 **내가 모르는 의존성이 내가 모르는 기능을 켠다.**

**Boot 4의 규칙**:

> **의도를 선언해야 켜진다.**

| 이전 | Boot 4 |
|---|---|
| `spring-boot-starter-web` (서블릿+리액티브 모호) | **`spring-boot-starter-webmvc`** |
| `spring-boot-starter-web-services` | `spring-boot-starter-webservices` |
| `spring-boot-starter-aop` | `spring-boot-starter-aspectj` |
| 테스트는 `starter-test` 하나 | **기술별** — `starter-webmvc-test`, `starter-webflux-test`, `starter-security-test` |
| **라이브러리만 있으면 자동 구성** | **전용 스타터 필요** (Flyway → `spring-boot-starter-flyway`) |

**마지막 줄이 답의 핵심이다.** Flyway가 어딘가에서 딸려 왔다는 이유로 마이그레이션이 돌지 않는다. **`spring-boot-starter-flyway`를 내가 적었을 때만** 돈다.

**즉 "무엇이 켜지는가"의 입력을 "우연히 클래스패스에 있는 것"에서 "내가 명시한 것"으로 옮긴 것이다.** 전이 의존성을 없앤 게 아니라 **전이 의존성이 동작을 결정하지 못하게** 했다.

**업그레이드용 완충 — **클래식 스타터****: `spring-boot-starter-classic`, `spring-boot-starter-test-classic`. 책이 두 번 못 박는다 — **임시 마이그레이션 보조 수단**이고, 새 애플리케이션과 장기 유지보수에는 집중형 스타터를 쓰라. 클래식 스타터로 업그레이드를 끝내면 **빌드는 통과하지만 Boot 4가 만든 명시성을 하나도 얻지 못한 채 넓은 클래스패스를 유지**하게 된다(§6).

## Q6. `@SpringBootTest` 웹 테스트 제거가 "슬라이스의 성질을 확장한 것"인 이유

**슬라이스가 원래 갖고 있던 성질이 무엇인가부터**:

> ****테스트 슬라이스**는 "필요한 층만 띄운다."** `@WebMvcTest`는 웹 계층만, `@DataJpaTest`는 데이터 계층만.

**`@SpringBootTest`는 그 반대편에 있었다** — 전체 컨텍스트를 띄우고, **웹 테스트 클라이언트까지 자동으로** 붙여 줬다.

**Boot 4의 변경**:

| 필요한 것 | 붙여야 할 애노테이션 |
|---|---|
| `MockMvc` | `@AutoConfigureMockMvc` |
| `TestRestTemplate` | `@AutoConfigureTestRestTemplate` |
| `WebTestClient` | `@AutoConfigureWebTestClient` |

**책이 밝히는 의도** — 전체 컨텍스트 테스트를 **더 의도적으로** 만들고, **필요 없을 때 웹 테스트 인프라를 구성하지 않기** 위해서다.

**"확장"이라는 말이 정확한 이유**: 슬라이스의 원리는 "**층을 좁힌다**"가 아니라 "**필요를 선언한 것만 켠다**"였다. 전자는 전체 컨텍스트 테스트에 적용할 수 없지만 — 전체를 띄우는 게 목적이니까 — **후자는 적용할 수 있다.** 컨텍스트는 전부 띄우되 **웹 테스트 도구는 opt-in**으로 만든 것이 정확히 그 적용이다.

**그래서 §2.10 표에서 이 항목이 방향 ①(명시성)에 들어간다** — 집중형 스타터·Flyway 전용 스타터와 **같은 종류의 변경**이다.

**대가 — 이것이 §1 표의 "기본값이 바뀜"의 대표 사례다.** 컴파일도 되고 컨텍스트도 뜨는데 **주입만 안 된다.** 오류 메시지가 원인을 바로 가리키지 않는다.

## Q7. Batch 6 인메모리 기본값이 조용히 위험한 이유 — 재시작 시나리오

**무엇이 바뀌었나**: Spring Batch 6은 데이터베이스 기반 `JobRepository` **없이도** 동작할 수 있고, Boot 4의 `spring-boot-starter-batch`는 **이 인메모리 모드를 기본으로 쓴다.** 단순 배치에서 데이터베이스 요구를 없앤 것이다.

**대가**: 인메모리 인프라는 **애플리케이션 재시작 간에 지속되지 않는다.** ****배치 메타데이터**** — 작업 인스턴스, 실행 메타데이터, 재시작 정보 — 가 애플리케이션이 멈추면 사라진다.

**재시작 시나리오**:

```text
Boot 3.5                                 Boot 4 (아무것도 안 바꿈)
─────────────────────────────           ─────────────────────────────
1. 야간 정산 job 실행                     1. 야간 정산 job 실행
2. 10만 건 중 7만 건에서 실패             2. 10만 건 중 7만 건에서 실패
3. DB의 JobRepository에                   3. 인메모리 메타데이터에
   실행 상태·스텝 진행 기록                  실행 상태 기록
4. 애플리케이션 재시작                     4. 애플리케이션 재시작
5. 같은 파라미터로 재실행                  5. 같은 파라미터로 재실행
   → "이미 완료된 스텝"을 건너뛰고            → 이력이 없다
     7만 건 지점부터 재개                     → 처음부터 다시 돈다
                                             → 앞의 7만 건이 중복 처리된다
```

**왜 "조용히"인가 — 세 겹으로 조용하다**:

1. **빌드가 통과한다.** 스타터 이름도 그대로 `spring-boot-starter-batch`다.
2. **애플리케이션이 시작된다.** `DataSource`가 없다고 실패하지 않는다.
3. **평상시에는 결과도 같다.** job이 성공적으로 끝나는 한 인메모리와 DB는 구별되지 않는다.

**차이가 드러나는 건 오직 "실패하고 재시작하는" 경로**다. 그리고 그 경로는 **테스트에서 거의 밟지 않는다.**

**§1에서 "배치를 재시작해 봐야 안다"고 한 것이 정확히 이 항목이다.**

**대응**:

| 필요한 것 | 무엇을 쓰나 |
|---|---|
| 단순 배치, 이력 불필요 | 기본 `spring-boot-starter-batch` (인메모리) |
| 영속 메타데이터, 재시작 가능성, 실행 이력, 스텝 단위 추적 | **`spring-boot-starter-batch-jdbc` + `DataSource`** |

**판별 질문**: "이 job이 중간에 죽었을 때 **처음부터 다시 돌려도 되는가**?" 안 된다면 `-jdbc`가 필요하다.

## Q8. liveness와 readiness가 따로 있어야 하는 이유

**묻는 질문이 다르기 때문이다.**

| 프로브 | 묻는 것 | 오케스트레이터의 반응 |
|---|---|---|
| **liveness** | **"이 프로세스를 재시작해야 하는가?"** | 실패 → **파드를 죽이고 다시 띄운다** |
| **readiness** | **"지금 트래픽을 보내도 되는가?"** | 실패 → **로드밸런서에서 뺀다** (죽이지는 않는다) |

**둘의 답이 갈리는 상태가 실제로 존재한다** — **기동 중이거나 잠시 과부하인 인스턴스**는 **살아 있지만(liveness OK) 준비되지 않았다(readiness NG).**

**합치면 무슨 일이 나는가 — 재시작 루프다**:

```text
합쳐진 프로브 하나만 있을 때
  파드 시작 → 컨텍스트 로딩 중 (30초)
           → 프로브 실패 (아직 준비 안 됨)
           → 오케스트레이터: "죽었구나" → 재시작
           → 파드 시작 → 컨텍스트 로딩 중 …
  → 영원히 뜨지 못한다
```

**기동 시간이 프로브 임계값보다 길기만 하면 절대 못 뜬다.** 그리고 이건 코드가 잘못돼서가 아니라 **질문 두 개를 하나로 합쳤기 때문**이다.

**Boot 4의 변경**: 이 프로브들이 **모든 애플리케이션에서 기본으로 켜진다.** 이전처럼 **Kubernetes에서 도는 것이 감지될 때만**이 아니다.

- actuator health 엔드포인트가 노출돼 있으면 `/actuator/health/liveness`와 `/actuator/health/readiness`가 **항상 있다**
- 원치 않으면 `management.endpoint.health.probes.enabled=false`

**이것도 §1 표의 "기본값이 바뀜"이다** — 다만 방향이 **켜지는** 쪽이라 위험보다는 **의도치 않은 노출**이 관심사다.

## Q9. SSL 인증서 만료 보고 방식 변경이 기존 경보를 무력화하는 방식

**무엇이 바뀌었나**:

| | 이전 | Boot 4 |
|---|---|---|
| 만료 임박 시 **상태** | **`WILL_EXPIRE_SOON`** | **`VALID` 그대로** |
| 만료 정보의 위치 | 상태 값 | health 응답의 **`expiringChains` 항목** |

**`WILL_EXPIRE_SOON` 상태는 더 이상 쓰이지 않는다.** 만료 임박 인증서도 **상태는 `VALID`로 남고**, 만료 정보만 health **세부**에 노출된다.

**무력화되는 방식**:

```text
기존 경보 규칙:
  if (ssl.status != "VALID") → 알림

Boot 3.x:  만료 30일 전 → status = WILL_EXPIRE_SOON → 조건 참 → 알림 발송 ✅
Boot 4  :  만료 30일 전 → status = VALID            → 조건 거짓 → 침묵 ❌
           만료 당일   → 핸드셰이크 실패           → 서비스 장애로 발견 💥
```

**이 경보는 "고장 났다"고 알려 주지 않는다. 그냥 영영 울리지 않는다.**

**이것이 §1 표 세 번째 줄의 가장 지독한 형태인 이유**: 다른 "기본값이 바뀜" 항목들은 **애플리케이션의 동작**이 조용히 달라진다. 이 항목은 **감시 장치 자체**가 조용히 멎는다. 애플리케이션은 멀쩡하고, 경보 시스템도 멀쩡히 돌고 있고 — **다만 아무것도 보고하지 않는다.** 그리고 정상 운영 중에는 침묵이 곧 정상 신호라서, **경보가 죽었다는 사실 자체를 감지할 방법이 없다.**

**대응**: **상태 값이 아니라 세부 항목을 본다** — `expiringChains`가 비어 있지 않으면 알림.

**교훈**: 업그레이드 점검 목록에 **애플리케이션뿐 아니라 애플리케이션을 감시하는 것들**도 들어가야 한다.

## Q10. 두 가지 AOT의 결정적 차이 — 그리고 세 번째

**결정적 차이는 "JVM을 버리는가"다.**

| | **GraalVM 네이티브 이미지** | **Java AOT Cache** |
|---|---|---|
| 실행 환경 | **JVM 없음** (기계어 실행 파일) | **표준 JVM** |
| 빌드 산출물 | 플랫폼별 바이너리 | JAR + 캐시 파일 |
| 동적 기능 | **런타임 힌트로 미리 선언해야 함** | **제약 없음** |
| 필요 버전 | GraalVM Native Image 25+ | Java 24+ (buildpack 지원은 25+) |
| 개선 폭 | 크다 | **애플리케이션·환경·학습 실행의 대표성에 달렸다** |

**AOT Cache의 동작**: JVM이 **학습 실행(training run)** 한 번에서 시작 데이터를 기록해 **이후 실행에서 재사용**한다. Java 24에서 도입돼 Java 25에서 쓸 수 있고, 이 책이 주로 쓰는 Java 버전이 25다.

**책이 짚는 지점**: AOT Cache는 애플리케이션을 **계속 표준 JVM 위에서 돌게 한다.** 시작 시간과 메모리를 줄이면서도 **일반 JVM 배포의 유연성을 유지**한다.

**그 유연성이 구체적으로 무엇인가** — 리플렉션, 동적 프록시, 런타임 클래스 로딩을 **미리 선언하지 않아도 된다.** 네이티브 이미지에서 라이브러리 하나 때문에 힌트를 손으로 쓰던 그 작업이 없다.

**대신 개선 폭이 보장되지 않는다** — **학습 실행이 실제 운영을 얼마나 대표하는가**에 달렸다. 학습 실행에서 안 밟은 경로는 캐시에 없다.

**세 번째 "AOT" — Chapter 3의 Spring Data AOT repository**다. 리포지토리 구현을 **빌드 시점에 생성**한다.

**판별 질문 하나로 정리된다**:

> **"무엇을 미리 만드는가?"**
> - **실행 파일**이면 → GraalVM 네이티브 이미지
> - **시작 데이터**면 → Java AOT Cache
> - **리포지토리 구현**이면 → Spring Data AOT

**셋 다 "빌드 시점으로 옮긴다"(§2.10 방향 ④)는 같은 방향이지만 옮기는 대상이 다르다.**

## Q11. 다섯 방향과 그 예 — 그리고 예외

| 방향 | 무슨 뜻인가 | 이 장의 예 |
|---|---|---|
| **① 명시성** | 넓은 기본값 → 좁은 선언 | 집중형 스타터, `@SpringBootTest` 웹 테스트 opt-in, Flyway 전용 스타터, MongoDB UUID·BigDecimal 표현 |
| **② 모듈 세분화** | 큰 묶음 → 기술별 모듈 | `spring-boot-persistence`, 기술별 test starter, OTel 전용 스타터 |
| **③ 벤더 중립 표준 채택** | Spring 고유 → 업계 표준 | JSpecify, Framework 재시도, `@MockitoBean`, Observation API, OpenTelemetry |
| **④ 빌드 시점으로 이동** | 런타임 결정 → 빌드 시점 분석 | `BeanRegistrar`, AOT 처리, AOT Cache, 네이티브 이미지 |
| **⑤ 책임의 이전** | Spring Boot가 쥐던 것을 놓음 | Spring Session Hazelcast·MongoDB, Kafka Streams 커스터마이저, Spring Retry |

**방향을 아는 것의 값**: 34개를 따로 외우는 대신 **처음 보는 변경도 예측할 수 있다.** "이 기능이 Boot 4에서 어떻게 됐을까?" → 넓은 기본값이었다면 좁아졌을 것이고, Spring 고유 API였다면 표준으로 대체됐을 것이다.

**예외는 ⑤에 있다 — Spring Authorization Server다.**

**밖에 있던 것이 Spring Security 안으로 들어왔다**(§2.4). 그래서 버전이 별도 `spring-authorization-server.version` 프로퍼티가 아니라 **Spring Security를 통해 관리된다.** 다른 ⑤ 예들과 **반대 방향**이다.

**그래서 방향 ⑤의 이름을 다시 붙이면**:

> **"덜어낸다"가 아니라 "각 기능이 있어야 할 자리로 보낸다"에 가깝다.**

Session Hazelcast는 **Hazelcast 팀**이, Session MongoDB는 **MongoDB 팀**이 더 잘 안다. 인가 서버는 **Spring Security 팀**이 더 잘 안다. **판단 기준은 "누가 가장 잘 아는가"이지 "누가 줄이는가"가 아니다.** 예외 하나가 원래 규칙의 진짜 형태를 드러낸다.

## Q12. 첫 수가 `spring-boot-properties-migrator`인 이유 — §1의 진단과의 연결

**§1의 진단**: 네 성격 중 **"기본값이 바뀜"이 가장 위험하다.** 조용히 무시되고 조용히 기본값으로 떨어지기 때문이다.

**연결 고리 — 이 장의 프로퍼티 이름 변경만 21개다**:

| 영역 | 개수 |
|---|---:|
| MongoDB | 8 |
| Jackson | 2 |
| Session | 2 |
| 영속성 (`spring.dao.exceptiontranslation` → `spring.persistence.…`) | 1 |
| Kafka | 1 |
| Redis | 1 |
| DevTools | 1 |
| health probes | 1 |
| 기타 | 4 |

**이름이 바뀐 프로퍼티는 "이름 변경"처럼 보이지만 실제로는 "기본값 변경"으로 작동한다.**

```text
application.yml 에 spring.dao.exceptiontranslation.enabled=false 가 남아 있다

Boot 4는 이 키를 모른다
  → 오류를 내지 않는다 (알 수 없는 프로퍼티는 무시된다)
  → spring.persistence.exceptiontranslation.enabled 는 설정되지 않았다
  → 기본값(true)으로 떨어진다
  → 내가 끄려던 기능이 켜진 채로 돈다
```

**여기가 §1 진단과 정확히 맞물리는 지점이다** — 컴파일도 안 깨지고, 시작도 안 깨지고, **설정 파일에는 내가 쓴 줄이 멀쩡히 남아 있다.** 파일을 봐도 문제를 찾을 수 없다.

**마이그레이터가 하는 일**: 빌드에 잠시 넣어 두면 **시작할 때 그런 프로퍼티를 보고**해 준다.

**왜 "첫 수"인가**:

1. **가장 큰 사각지대를 가장 싸게 없앤다.** 의존성 한 줄, 실행 한 번.
2. **다른 세 성격은 이미 도구가 있다.** 이름 변경은 컴파일러가, 제거는 의존성 해석과 빈 없음 오류가 잡는다. **"기본값이 바뀜"만 잡아 주는 것이 없었다.**
3. **다른 작업의 결과를 왜곡하지 않는다.** 마이그레이터 없이 스타터부터 바꾸면, 나중에 나오는 이상 동작이 스타터 때문인지 프로퍼티 때문인지 구별되지 않는다.

**§1 비유의 완결**:

> **벽을 뜯어 보는 대신 배선도를 받아 보는 것.**

배선 비유가 깨졌던 자리 — "**눌러 볼 스위치가 없다**" — 를 마이그레이터가 메운다. **운영 중에야 알 것을 시작 시점으로 끌어올린다.**

**한계**: 프로퍼티만 본다. **Batch 인메모리 기본값**처럼 프로퍼티가 아닌 기본값 변경은 잡지 못한다. 그래서 첫 수이지 **마지막 수가 아니다.** 나머지는 §2의 아홉 영역을 손으로 훑어야 한다.
